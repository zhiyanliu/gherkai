# 演示制作规范

本文件合并已确认的定位、表达、视觉与音视频约定。成稿以 [最终 PPT](https://github.com/zhiyanliu/gherkai/blob/HEAD/docs/presentations/value-method/gherkai-value-method-v12.pptx) 为准。现场执行材料由 [示例仓库的 runbook](https://github.com/zhiyanliu/gherkai-webapp-demo/blob/HEAD/docs/demo-runbook.md) 维护。

## 定位与方法

受众以 QA、测试负责人为主，约占 70%，兼顾测试开发与工程角色。第一份的目标是让客户理解 gherkai 的价值、认同背后的工作方法，并找到可尝试的业务试点。先说明主张，再给必要解释和证据，避免在观众理解方法之前进入内部实现细节。

主张是以团队认可的业务用例组织 AI 测试，连接个人迭代与团队复用。gherkai 沉淀测试用例、执行编排与反馈闭环，具体引擎承接执行。四项原则：

1. 需求确定验收要求；QA 审阅，agent 帮助形成用例与确定性步骤代码。
2. 按任务选择 AI 推理与代码执行。精确检查和高频操作复用代码，需要页面理解的工作由 AI 承担。
3. 将测试结果、失败原因与现场证据带回，帮助 QA 或 agent 调整测试、完善确定性步骤，也为开发者或编程 agent 排查应用缺陷提供依据。修改后按原验收要求复验。
4. 将验证过的执行能力发布、维护并复用。本机支持快速运行与调试；云端提供共享执行服务；模块化架构使上层用例、编排与反馈方式能够随执行技术变化继续使用。

这些原则与成熟测试实践有重叠。增量在于：开放 Gherkin 用例组织 AI 与代码的混合执行，面向 agent 的 CLI 与 skill 连接测试实现和反馈，以及个人迭代、共享服务和可替换引擎之间的衔接。不要声称发明了需求驱动测试，也不要用孤立功能勾选表否认其他工具的重叠能力。

## 表达边界

- 写“确定性步骤（代码）”或“确定性步骤代码”，避免单独写“步骤”造成歧义；AI 部分写“AI 步骤”。
- 区分编程 agent 帮忙实现测试，与执行引擎在运行某个 AI 步骤时理解页面、推理操作。避免“运行时 AI”等难懂词。
- Gherkin 是已有的开放业务行为描述语言；不把它说成兼容所有执行器的通用协议，也不把一个 Feature 简化等同于一个测试用例。
- 本机模式指 worker 的执行位置，不等于不使用云端浏览器或模型。当前实测本机模式仍使用 AWS 服务。
- 云端执行体现服务化及提供方、调用方分工，不等于只适用于团队；本机模式也支持 agent 驱动的应用与测试快速迭代。
- 当前 AWS 部署依赖有独立模块边界，但没有证明其他云已经可用。引擎替换与部署替换是两个维度，确定性步骤仍可能需要适配引擎接口。
- 代码执行可以减少对应的模型调用和推理等待。未做同条件成本实验，不给节省比例，也不声称所有代码步骤都在毫秒内完成。
- 反馈能够辅助修复；已有缺陷演示不证明 agent 自主修复。缺陷注入与应用恢复属于演示准备。
- 读者首次接触内容时，避免裸露需求编号、scope 名、错误枚举、时间戳等内部标识；工程追溯信息放讲者备注和证据材料。

## 视觉与页面

最终 PPT 可直接作为第二份的视觉参考，不需要旧版参考 deck 或构建链。

- 16:9，明亮、较丰富的蓝紫青科技色，专业且有极客感。内容区保证对比度，避免整页深色或过饱和。
- 首页比内容页略浓重，用有业务含义的概念图吸引注意；封底使用独立的四节点循环图，帮助回想主张。
- 统一页眉、横线、引导词、标题与底部空间。每页页眉保留项目入口；表头字号、底色和字重明确区别于数据行。
- 图表、流程与概念图承担理解任务，文字说明尽量放备注。不要为了装饰而添图，也不要编造数字图表。
- 优先抽象概念图，与封面保持一致。若确需人物，采用地域中性的亚洲面孔、阳光漂亮；两人场景为一男一女。
- 中文字体 Hiragino Sans GB，英文字体 Helvetica Neue，地址与代码 Menlo。字体由编辑环境提供，不随仓库分发。
- 图标沿用 Lucide，许可与 SVG 在 [图标源文件](https://github.com/zhiyanliu/gherkai/blob/HEAD/tools/presentations/assets/icons/)；原色参考保存在图标文件中。

图片由 Gemini 生成并编辑，代表方法概念，不是产品截图或精确技术架构。最终采用的主视觉及相关提示词、模型记录集中在素材包的 `artwork/` 中；无需重新生图即可继续编辑。缺陷证据来自 [真实运行证据包](https://github.com/zhiyanliu/gherkai-webapp-demo/blob/HEAD/internal/presentations/demo/evidence.zip)，不能用生成图替代。

## 口播、字幕与视频

- 讲者备注包含口播正文与不朗读的提示。纯口播稿只含应送入语音模型的内容；提示、来源与舞台指令不送入配音。
- MiniMax 使用已确认的声音与积极表达方式：“专业中透着激情”，避免平淡或过快。声音 ID 和密钥从本机环境提供。
- 已认可参数：`speech-2.8-hd`，`speed=1.02`，`emotion=happy`，后期保留音高至 `1.1×`。品牌词采用 `gherkai/格儿凯`，两音节连读、首音为“格”且保留儿化。
- 第一份最终时长 265.75 秒，1920×1080、60 fps。成片综合响度 −13.15 LUFS，真峰值 −0.84 dBFS；这是最终音轨的观测值。
- 第 0 帧即为完整首页，开头不留黑屏、不渐入，口播与字幕保持原时间轴。页间直切；末页讲完经 0.1 秒淡出黑屏，结尾黑屏停留 0.15 秒。
- 人工修订的 SRT 是最终字幕源；不得重新加句末标点、重分句或重排时间。更换字幕时复制画面与音轨，核对内嵌字幕和外部 SRT 一致。
- 素材包保留原始逐页 MP3，尚未加速或统一音量。仅更新画面时复制现有成片音轨，避免不必要的重复编码或付费配音。

## 修改与验收

编辑最终 PPT 时保留原生表格、图表、嵌入工作簿、超链接和逐页备注；导出后逐页检查。第一份的口播正文已经确认，不能因文件整理顺手改写。

修改画面而保持讲稿与时间线时，可解压素材包，替换对应 `slides/NN.png`，用视频工具复用成片音轨及字幕。修改口播时先审阅文字，再按页生成配音，重新对齐章节和字幕；不要继续套用旧时间线。

交付时核对：页数及图文布局、PPT/备注/口播一致性、媒体完整解码、章节时间、字幕正文和时间轴、逐页画面对照、切换、首页首帧与结尾淡出、音量，以及 ZIP 完整性。校验清单和 SHA-256 存入最终 manifest；不保留重复渲染和验证日志。

## 溯源与保存规则

产品能力的依据来自 gherkai 项目文档与实现，以及示例仓库的需求、用例、确定性步骤和真实运行记录。实测代码版本与运行 ID 见 [证据说明](https://github.com/zhiyanliu/gherkai-webapp-demo/blob/HEAD/internal/presentations/demo/evidence.md)。第 12 页的包职责和链接已保存在最终 PPT 及交付 manifest。

最终 PPT 的资料备注中仍有定稿时的本机路径与历史素材名称，用于原始溯源，不作为今后的文件依赖：`yaozhou/` 指 gherkai 仓库；`reports/presentation-evidence/` 对应现在的证据包；旧 `value-method/assets/` 对应素材包 `artwork/` 和最终 PPT 内嵌图片。外部讲者备注已整理成可直接阅读的最终稿，口播与演示提示保持原文。

只将定稿、必要素材、维护规范与复用工具纳入 Git。新制作的临时数据放 `tools/presentations/work/`；交付文件使用确认的版本号，当前为 `v12`；仓库只保留当前版本，历史由 Git 记录。API 密钥、账号凭证、带签名下载地址和机器连接配置不得入库。
