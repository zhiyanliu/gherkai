# 独立复核与同僚复核 — 工作约定

> 给维护本仓库的 AI agent：本文是 CLAUDE.md「工作方式」里独立复核一条的细则。约束的是**功能**（独立复核 → 分歧裁决 → 闭合确认），不是某个工具：另一家模型的只读同僚是首选实现，没有它时按本文的替代方式执行，不许静默跳过。护栏分层的同一形态见 [ADR 0046](../adr/0046-guardrail-layers-tests-hooks-and-lean-claude-md.md)（hook 只在 Claude Code 生效、测试兜底）。

## 一、功能约束与触发点

- **角色**：作者是写出受审材料并发起复核的一方（通常是 contributor 侧 AI agent），分歧裁决也由它做；复核者是独立核查的一方；「交人」即交 owner。
- **三步缺一不可**：独立复核（复核者不继承原会话，拿到的是待审主张、拟议改法、基准与证据，剔除既有的评审判词与裁决）→ 分歧裁决（每条由裁决者到仓库核实后定）→ 闭合确认（补写后对更新后的完整材料再确认一次）。
- **触发点**：① 设计定稿——ADR 新增、反转或改动契约 / 不变量；② 待批项交人之前——复盘的待批报告、要 owner 拍板的倾向与建议（倾向本身就是待批项，先过复核再交人：经本家复核即可交，注明还没有经另一家模型核过，之后另一家模型核出会改变结论的问题时再回来找 owner；熔断通知里的倾向同此）；③ 成批 code 落地之后的闭合（按 ADR 核「落到位」）。
- **复核的对象是设计与 code，规格随后果定**：复核核的是设计有没有反例、决策之间是否相抵、契约与不变量是否成立，以及落地的 code 是否照 ADR 做到位。措辞、指针、Status 头、文件名这类能机械判定或属于文档卫生的，交护栏测试与文档健康复盘，不为它们开复核轮，也不排在实装之前。基准只写设计必须成立的性质，不把「文字逐句无可挑剔」写成性质：长篇文字在强对抗复核下总能再找出成立的意见（第四节「闭合确认」条），拿它当闭合条件会一直推迟实装。设计点随实装批次定（CLAUDE.md「代码纪律」），每一批的设计定稿都过触发点①（下条）；实装中的测试与真实执行是对设计的再一次核查，不代替它。本仓库的样本：一次上游重新设计的 ADR 写回，四天里核了八十多轮，两次熔断都卡在文字层面的性质上（把计划的时刻转述成保证、注释指针与 ADR 现文是否一致），其间实装没有开工。
- **一个实装批有两道关口，关口之内先本家、后另一家模型。** ① 设计敲定之后才实施：设计由本家做出并复核打磨，该交 owner 的决定先讨论确认（判据见 CLAUDE.md「工作方式」），再送另一家模型核（触发点①）；改用档二或不送的，实施之前写明原因。② 一批 code 落地、经本家复核与真实执行之后送另一家模型核（触发点③），过了才算闭合。两家之间不并行，先打磨再送。没有新设计点的批次（纯删除、文档校准、小修）不过关口①。
- **这套流程防的是三种耗时，各有对应的做法**（本仓库一次实装里时间主要花在这三处）：
  - 文字层面反复送审：基准只写必须成立的性质并带边界，不收敛即熔断（第三、四节）；本家打磨以「没有必须改的」为准，通常一到两轮，不追求零意见。
  - 设计问题到落地之后才发现、整批返工：关口①；设计依赖的外部行为先取证（第三节「mock 之外的行为」条）。
  - 把等复核当成停工：同一步里互不依赖的部分分给几个代理同时做；等另一家模型的时候做不依赖被审结论的工作（取证、测试准备、文档、下一批的只读摸底）；互不相关的受审对象同时送。
  - 调整流程以数据为据：过程文档里每批记下从设计开工到闭合的时长、两道关口各几轮、返工出在哪一步。
- **为什么**：同一模型、同一上下文的盲区同源。本仓库的样本显示两路发现互补：移动设备支持的一次设计核对里，同僚核出 31 项差集、本家对抗核验核出 9 项、只重合 7 项；一轮代码复盘里，同僚对八项裁定倾向核出五处设计层修正，对已落地的 code 核出一处真缺陷与两处既有真跑样本未覆盖的 SDK 行为。样本只说明互补，不证明哪一路更优。

## 二、两档实现与选档

| 档                                               | 什么时候                                                            | 怎么做                                                                                       |
|--------------------------------------------------|---------------------------------------------------------------------|----------------------------------------------------------------------------------------------|
| **档一·另一家模型的只读同僚**（首选）              | 可用即默认启用；关闭须在报告或提交说明写明原因                       | 另一家厂商的模型，只读受审仓库（不修改它），按下文简报独立判；本仓库现用 Codex CLI，见第五节       |
| **档二·本家模型的独立上下文**（兜底，不与档一等效） | 档一不可用（工具或模型不在 contributor 环境里）或已说明原因后显式关闭 | 子代理或新会话，按同一份简报重核，简报里要求先假设有错（对抗驳回）；同样不继承原会话、不带既有判词 |

- **披露**：待批报告附录或落地提交说明写「独立复核：档一（工具与轮次）/ 档二（形态）」与关闭原因；两档都没做的不交人、不标整轮完成。
- 需要真实验证（真跑、真实 SDK、真实进程）而复核者缺权限或环境时，交具备条件的执行者取证，相关条目保留未闭合状态。

## 三、简报怎么写（两档通用）

- 只读；给出亲自核到的文件与行号；不复述已写对的内容；结尾一句总判定与流程处置（下面「逐条要求」条）。
- **基准内联**：复核者核的是「改动是否落到位、有没有过度声称」，基准（owner 裁定原文、已删除的 journey 全文、ADR 的目标设计）要整段放进简报，不要让它自己猜；其中既有的评审判词与裁决仍按第一节剔除，owner 裁定原文保留。没有这类现成基准的受审对象，简报里先写一段它要做到什么（用途、必须成立的性质），这一段就是基准。基准在首轮之前定下，同时是裁决的标尺与闭合的定义（第四节）；它列出共同的适用范围与各条性质的特殊前提（对谁成立、信任什么、不防什么），使一个反例在不在范围内可以判定——没有边界的基准（简报不给基准，或性质写成不带前提的「不会……」「一定……」）让每个反例都成立，循环没有终点。保证的强度由既定用途与实际或计划中的依赖推出；只需约束做法的，写成「我们怎么做」，不另外承诺结果。涉及产品取舍的前提（防到哪一类对手、承诺到什么程度），已有 owner 裁定的沿用，没有的首轮之前交 owner 定。复核者可以对基准本身提意见（漏了必须成立的性质、定得过宽或过窄），这类意见不算基准之外；它要说明在既定用途或约束下不改会有什么具体后果，裁决之前不改变验收要求（裁决按第四节，涉及产品取舍的交 owner），要等这个裁定才能继续的工作先停下。
- 逐条要求三元判定：主张成立 / 不成立 / 存疑，处理意见同意 / 修改 / 反对。每条意见另附不处置的后果：谁、在什么情形下、会得到什么错的结果；成立但落在基准之外的意见单列。意见先指出必须恢复的性质；随附的修法没有核验过的，标为候选。结尾给出流程处置，取「已闭合」「继续修正」「待取证」「待裁定」「熔断」五个值之一，各值的含义与选择规则见第四节「停下来的原因」条；是熔断的写明触发条件、相关轮次、反复失败的性质与恢复之前必须先确定什么。不用「尚未闭合」「尚不能确认收敛」代替流程处置。
- **固定标记**：新对象的首轮与换了上下文的后续轮，基准放在一个标题含「基准」的小节里，标题行顶格、以 `#` 加空格开头（如「## 基准：受审对象要做到什么」）。同一受审对象的后续轮，不论续接还是换了上下文，另带三样：① 一行「趋势」，列出各轮基准之内的意见条数与当轮最重的后果（如「趋势：基准之内 6（误处置活进程）→ 3（同上）→ 1（文档失真）」），条数只是摘要，「变轻」看的是后果；② 同一项性质在同一保障机制上被再次指出的，列出这一项的性质与机制、出现的轮次、本轮改法改变了什么（只给重复项列，不为全部意见建台账）；③ 一行「上轮流程处置」，抄复核者上一轮的原判；上一轮是待取证、待裁定或熔断的，再加一行「解除依据」（第四节「停下来的原因」条），还没有解除依据时不送。能机械检查的标记与检查的范围见第五节；重复项的资料是否齐备、解除依据是否成立由作者与复核者核查，发送工具放行不构成恢复送审的授权。
- **mock 之外的行为点名要真跑**：进程、信号、并发时序、第三方 SDK 的真实响应，简报里写「请用真实进程（或真实安装的 SDK）复现」并列出拓扑或输入——这类缺陷本家单测全绿也照不出。设计依赖的外部行为，能用临时资源现在实测的先实测、结论写进受审材料，确实要等部署的才列为待取证。
- **结论依赖跨步骤的状态变化时，点名核查相关间隔**：从基准里的性质出发，列出相关的检查与动作、重复读取及提交位置，推演基准允许的状态或时钟变化发生在其间时性质是否仍成立；有共同保障的等价情形可以合并。对推演出的可达反例或尚缺证据的关键间隔，用事件或钩子固定先后验证；没有可执行的实现或缺少执行条件时，注明推演的前提与待取证项。已有场景没有覆盖的先后，不能拿这些场景的通过当证据。
- 成批改动按范围分批送；每轮先把同僚意见与本方补充发现一并落地再送下一轮，否则它会把本方的补充发现原样再提。

## 四、分歧裁决与闭合

- **同僚不是答案源**：凡非「成立且同意」的条目即分歧，由裁决者到仓库核实后判维持 / 采纳 / 合并 / 已消失撤回 / 交人；判「维持」须写理由（进 ADR 被拒方案或报告附录）。
- **成立不等于要处置：裁决答两问，采纳与维持同样写理由。** 一问意见是否成立，二问不处置的后果落在哪里。后果落在基准之内的采纳；落在基准之外、或说不出后果的，判维持并记为已知局限（写进受审材料的局限说明或报告附录）。只有维持要写理由时，全部采纳是最省事的处置，裁决这一步形同虚设；所以采纳也写一句后果。处置的代价要计入它新增的受审面（下条）。
- **修正先看能否收窄，再考虑加机制。** 一条成立的意见是「声称」与「实际」之间的差，两头都能改：改实现去符合声称，或收窄声称、删掉机制去符合实际。新增的机制与新写的声称都是没有审过的新材料，会成为下一轮的受审对象；绝对化的声称（「完全相同」「不可能」）的每个反例都是成立的意见。选择加机制的，写明收窄为什么不行。作者可以自行收窄材料多出的声称，但不得自行削弱基准或 owner 已定的原则，也不能拿自己定的「不做」清单排除基准之内的缺陷。能修的先修；无法修正或代价涉及产品取舍的交 owner，暂停按下面「停下来的原因」条执行。裁定之前，不把基准之内的缺陷记为已知局限。复核者随意见给出的修法是候选，要另核它是否充分：反例成立不等于候选修法成立。
- **依据只在一处写全；别处放指针或逐字引用，不另写概括。** 一句转述是一条新的声称：换一种说法，原句的主体、条件与作用范围都可能走样；写出来的句子没有审过，依据改动时还多一处要同步。所以受审材料与修正里用到的一项依据（基准、owner 的裁定、已接受的边界、字段定义、实测结果）只在一处写全（依据放在哪里、指针可以指向什么，沿用 CLAUDE.md「文档纪律」，本条不另作规定；简报里的基准按第三节整段内联，不在此列）。别处提到它时放指针（文件、节、那一条开头的文字），确需陈述时逐字引用，连同原句的主体与限定一起引。必须换说法的两种情形各有核法：由出处确定性生成的副本，核它与生成结果相同；面向另一类读者另写的句子（如用户文档里的产品表达），受审时列出每一句与出处的对应，逐句核主体、条件与作用范围与出处一致、不比出处多出承诺。同一件事有几个范围时（实测了什么、要求怎样做、检查实际覆盖什么），先看能否合成一个；合不成的分开写明，不让一句话兼指几个范围。文字上的同一项性质反复失守时，结构重审先看这一条：去掉转述，不把转述改得更细。本仓库三次样本，各自的处置不同：一批文档对一条写序的说法连续三轮失准，集中写全一次之后新写的概括又被举出反例，后来把这类说法限定为所在 code 的步骤、写明前提的契约、指针或逐字引用、生成的副本、与出处逐句对应的产品表达，其余推断删去，下一轮闭合；为它拟的处置在概括已接受的边界时，把出处的「这一写不落任何判定明细、不生成报告」写成了「没有判定明细也没有报告」，改为不转述边界与字段定义、只放指针或逐字引用之后闭合；一条写法约束在三个文件里各写一遍，实测样本、写法要求、检查实际覆盖是三个不同的范围，连续两轮被指出超出实测或与检查实际接受的范围不齐，把三个范围合成一个、约束只在一处写全之后闭合。
- **不缩小人的审批面**：复核只收敛提案的质量，待批项仍逐项交人；判「交人」的分歧单列在前。
- **同一受审对象默认续接复核者的上一轮会话，新对象用全新上下文**（两档通用）：闭合确认与「按意见改完再核」核的是复核者自己上一轮提的意见，续接让它直接引用已读过的材料，减少重复读取与重建理解，模型侧缓存可用时还用得上前缀缓存；带着的整段历史仍有成本，见下条。首轮复核、换了受审对象或话题的复核一律全新上下文：无关的旧上下文没有用处，还会让复核者顺着旧结论走，损害独立性。同一对象占用过线或发生过压缩的换全新上下文（下条）；基准或保障结构大改、审查的前提已变的，也可以换。换上下文不是流程重启：简报带上未闭合项（复核者上一轮的原意见与本方的处置；它们是闭合轮要核的对象，不属第一节要剔除的既有判词）与第三节「固定标记」条的各项。第一节「复核者不继承原会话」指的是作者一侧的会话，与复核者续接自己的会话不冲突。具体工具的续接方式见第五节。
- **续接上限：复核者主线程的上下文占用到模型上下文窗口的三分之二左右为止**（两档通用）：看的是复核者主线程自己的上下文——续接时被带上、会被压缩的是它；复核者自行分派的子代理各有独立的上下文，不计入这个占比。过线后下一轮改用全新上下文；续接链上发生过压缩的按过线处理（压缩后的占用读数变小、看似仍在线下，压掉的细节却已不在上下文里）。判据是占用，不是续接轮数；用占窗口的比例而不用 token 绝对数，换模型不必改规则。理由按约束强弱排：其一（硬约束），有的工具在上下文接近窗口时自动压缩历史，压掉的正是续接要保留的细节，所以要给本轮的读取与推理留足余量；其二，续接轮每次模型调用都带着整段历史，成本随上下文线性增长；其三，长上下文下判断质量可能下降（本仓库没有这方面的数据，只作保守理由）。「三分之二」是判断，不是实测得出的阈值，取值的依据与样本见第五节。例外：过了线但下一轮确定很小（如只确认一处措辞）仍可续接。Codex CLI 上占用的读法见第五节；读不到复核者占用时（档二），只在明确属于小闭合轮时续接同一个子代理或会话，其余用全新上下文。
- **闭合确认：闭合相对基准，不相对复核者。** 闭合指受审对象达到基准、上一轮意见处置到位；「复核者再提不出意见」不是闭合的定义：高推理强度的对抗复核对任何有一定复杂度的对象都能继续提出成立的意见，以它为终点的循环靠修正到不了头。简报写明受审的版本与文件集；补写后对更新后的材料再送一轮，只问两件事：上一轮意见是否处置到位，修正是否引入基准之内的新问题。这两问限定的是复核者要去找什么，不限定它可以报告什么：闭合轮里发现的其它基准之内的问题照样报告、照样裁决，但不因此要求它重新通读全部材料。闭合轮里出现的基准之外的意见按上面「裁决答两问」处置，不因此再开一轮。拿「我改完了」收尾不算闭合；它给的措辞建议原样采纳的，也送一轮确认。提交与否遵循原任务的提交纪律。修正换了保障结构的，送出之前重定受影响性质的核查范围，不沿用「小修之后只核原例」的尺度。
- **停下来的原因，各有解除的依据。** 已闭合：达到基准，不再送。待取证：缺执行证据，取到之后再送。待裁定：缺继续复核所必需的 owner 决定，答复之后再送（方案最终要 owner 批准不算，它不妨碍先把方案复核完）。熔断：见下面三条。后三种是暂停，对象保持未闭合，不拿继续开轮代替缺的证据或决定；下一轮简报写明上一轮暂停的原因与解除依据（第三节「固定标记」条）。多种暂停原因同时成立时，流程处置按熔断、待裁定、待取证的顺序选一个，并列明其余没有解除的原因；送下一轮之前逐项核对解除依据。没有暂停原因时，达到基准的写「已闭合」，仍有须处置的基准之内意见的写「继续修正」。
- **每轮送出下一轮之前看趋势，不收敛即熔断。** 收敛的样子是基准之内的意见逐轮变少、变轻。触发条件，任一成立即熔断：① 基准之内的意见连续两轮既不减少也不变轻；② 同一项基准性质在同一保障机制上，连续两轮经裁决仍有须处置的问题，不因它被归为「没改到位」还是「新反例」而区别对待；③ 复核者的流程处置是熔断。两轮是启动结构重审的阈值，不证明这个对象此后不会收敛；总量下降与局部机制反复失败可以同时成立。新意见集中在上一轮为修正而新写的内容上是线索，它本身不触发，也不抵销已经满足的触发条件。
- **熔断之后：停止逐条修补与送审，重审结构。** 修复的单位从「这条意见」上移到「反复产生意见的那个结构」。先核基准：反复失败的那项性质是否必要，适用范围与信任边界是否写明，当前的反例在不在范围内；缺的是产品取舍的，交 owner 定。再看机制能否满足确定之后的基准：它为什么不断出问题，能否换结构或删掉。补明前提不代替对范围内缺陷的修正。几处各自独立的修正都在加机制时，再往上找一层：这些分支共同来自哪一个上游的设计决定（例如同一份状态有不止一个写入方，同一个量分两处记录），去掉它要砍掉什么功能、改哪条已定决策，去掉之后还剩几条分支。要砍功能或改已定决策的，把这三个答案作为要 owner 确定的问题写进熔断通知（下条）。不沿着「每个反例加一条机制」走下去。复核者要求熔断而作者对触发的事实有异议的，按「同僚不是答案源」条裁决，撤销要列证据，裁决之前不恢复；熔断带来的是先停下的义务，不是全部采纳的义务。
- **熔断的通知与恢复。** 熔断之后通知 owner 一次：已用轮数、趋势、已核实的事实与分歧、要 owner 确定的问题，标明对象尚未闭合。通知不必先过另一家模型的复核，也不以依赖那个裁定的方案闭合为前提；带上改法与倾向的，注明它经过了哪一档复核（第一节触发点②）。恢复送审的依据是下面三种之一：不需要 owner 的结构处置，写明它怎样处理反复失效的原因（「不需要 owner」要有已有的授权或决定作依据，不因为技术上可行就成立）；owner 的裁定（基准的前提、产品取舍、已定决策的改动都要它，等到答复为止，这期间做不依赖它的工作）；撤销熔断的裁决及证据。经过一次结构处置之后同一失效原因再次触发的，等 owner；换会话或给问题换个说法不重置这段记录。
- 为什么单设熔断：循环里的每一步单看都合理（意见成立、修掉、验证、送闭合），问题只出现在跨轮的趋势里，逐步执行的 agent 不专门去看就看不见；条件 ② 不区分「没改到位」与「新反例」，避免用归类代替结构重审。本仓库三次样本：一批工具改动复核了六轮、约 38 条意见，旧意见每轮闭合，同一个子问题仍连续四轮被指出；六份简报都没有写基准，修正多数是加机制，其中一件工具从 47 行长到 530 行、另加约一千行自检。另一处没有写前提的安全性质，五轮意见是 6、3、3、2、3 条；第三轮之后换了机制、通知了不在线的 owner 之后又送两轮，直到 owner 定下信任边界，相关的反例才落到基准之外。第一次说明局部闭合不等于整体收敛，第二次说明换机制代替不了边界的裁定。第三次是本机后台 run 的两批后续设计（查询命令接手推进的改法、事件库里解析不了的记录）：两批各做了两三轮设计与复核，几乎每一轮都找到新的异常时序，反例多半引出一条新机制，循环由 owner 叫停；根因不在这两批的分支上，而在上游的两个设计决定，推进权没有唯一的持有者，run 的状态与 job 的状态分开写。改为本机由一把生命期锁保证只有一个推进器、run 的状态只由 job 的终态算出、云端后端只支持 `submit` 之后，两批里的大部分机制不再需要（ADR 0034「推进器与触发源」、ADR 0031 决定三、ADR 0016 决策 A）。它说明逐步执行的一方看不见跨批的趋势，结构重审也不能只看单个机制，还要看几处分支是否同出一个上游的设计决定。

## 五、实现示例：Codex CLI

- 调用：经发送工具 `uv run python tools/codex_review.py --round first|followup --brief <简报文件> --out <输出文件> [--model <模型>] [--effort <该模型支持的高推理配置>]` 送出。`--round` 必须给出：新对象的首轮是 `first`，同一受审对象的后续轮是 `followup`（续接或换了上下文都是）。它先检查简报里第三节的固定标记，缺即退出、不调用 codex；通过后在简报末尾附上固定的一段（请复核者在给出结论之前先读本文第四节的闭合与熔断各条，再按第三节给出流程处置；同一会话已读过、文件没有变、此后也没有发生过上下文压缩时可以沿用，发生过压缩的按没读过处理；判据由复核者从本文读取，工具不另抄一份），执行的是 `codex exec -s read-only [-m <模型>] [-c model_reasoning_effort="<强度>"] -o <输出文件> -`，简报作标准输入，codex 的输出写进日志文件（`--log`，缺省为输出文件名加 `.log`）。`--model` 与 `--effort` 不给时沿用 contributor 自己 `~/.codex/config.toml` 配的模型与推理档，repo 不规定、但推荐高推理模型配高推理档（本仓库 owner 用 Bedrock 上的 `openai` 的 `astra` 模型，配 `ultra`）；在仓库根目录执行；工具本身不后台化，本机用后台方式执行它。
- 续接：同一个工具加 `--resume <会话 id>`（只与 `--round followup` 同用），它执行的是 `codex exec resume <会话 id> -c sandbox_mode="read-only" …`（续接子命令没有 `-s`，只读沙箱经 `-c sandbox_mode` 指定，启动后在日志里核对 `sandbox: read-only`）。会话 id 在上一轮日志开头的 `session id:` 一行，工具结束时也会把这一行打印出来。续接轮的简报只写增量（改了什么、落在哪个提交或文件、要它核什么），不再附上一轮意见全文。日志报的 token 用量是根线程未命中缓存的输入加输出、按会话累计，算增量要减去上一轮；命中缓存的输入不在这个数里，复核者自行分派的子代理也不在——子代理的用量记在各自的记录文件里，分项连同子代理用下条的脚本读。本仓库两次样本（未命中缓存的输入加输出／命中缓存的输入；括号外只计根线程、与日志一致，括号内连同子代理）：小的闭合轮，不续接约 9.5 万／104 万（13.5 万／122 万），续接约 1 万／18 万（该轮没有子代理）；改动较多的闭合轮，续接约 3.6 万／111 万（7.1 万／202 万），同一对象的首轮是 12.6 万／202 万（40.0 万／441 万）。续接轮每次模型调用都带着整段历史，所以历史越长、轮内调用越多，命中缓存的输入越大，节省主要在未命中缓存的部分与重读文件的次数上。
- 上下文占比：会话记录在 `~/.codex/sessions/`，会话归档后移到 `~/.codex/archived_sessions/`（另设 `CODEX_HOME` 时在它下面），同一会话的线程可能分在两处；一个线程的记录可能分成多个片段文件，线程与会话的归属按片段首行的元数据判断、不看文件名，根线程的线程 id 就是会话 id；每次模型调用记一条该次调用的用量，轮次开始与每次调用之后的事件带模型窗口大小。`tools/codex_usage.py <会话 id>` 默认同时查找活动与归档两处（输出的「统计范围」一行列出实际查找的目录，`--sessions-dir` 给出时只查给出的目录），按轮次汇总根线程与各子代理的用量分项（输入、命中缓存、未命中缓存、缓存写入、输出、调用次数），列出每个线程每轮结束时上下文占窗口的比例（本轮有压缩时注明次数），表尾一行是根线程最近一次调用之后的占比，即第四节续接上限要看的数。这个读数是近似值，最近一次调用之后新写入的历史不在其中：读数可能过期（之后又写入了历史或发生了压缩、最后一轮被中断或没有结束记录）或根线程发生过压缩时，表尾逐条注明；注明发生过压缩的，按第四节当作已过线。根线程的片段先后无法确定时脚本不给读数并说明原因。口径与记录格式见脚本头注释。本仓库一次读数：上面改动较多的那条链在续接一轮后，根线程约 15.9 万比 25.8 万、约六成，在上限之内，下一轮仍可续接。
- 续接上限取三分之二的依据（样本都来自本仓库的 Codex 会话）：决定一轮成本的是当前上下文大小乘以轮内模型调用次数，与已续接几轮没有直接关系——一串小闭合轮续下去仍划算，一轮大的首轮之后第一次续接就可能不太省；子代理的用量只在算成本时合计。是否压缩、何处触发因工具而异，历史被改写后缓存命中也可能下降。一次样本里改动较多的闭合轮让主线程占用增加约 12 个百分点，线下留出的三分之一够容纳两轮这样的闭合；工具触发压缩的确切位置没有核过。线划在一半的代价按近期约八十个首轮的读数：约五分之一的对象首轮结束时主线程占用已过一半，首轮之后就不能续接（线在三分之二时约十五分之一）；首轮结束在四成到五成之间的约三成，一轮改动较多的闭合（约 12 个百分点）之后即过线。
- 复核轮闸门：检查做在发送工具里，执行时读真实的简报文件：首轮与换了上下文的后续轮（不带 `--resume`）要有顶格的「基准」标题行；后续轮要有「趋势」一行，与「上轮流程处置：」后接五个取值之一的一行，取值是待取证、待裁定或熔断的另要「解除依据：」一行且冒号之后有内容；缺即退出。工具只检查这些标记在不在，不检查重复项的资料，不推断意见真伪与解除依据是否成立（写着「已通知、仍待答复」的解除依据它照样放行），所以放行不是恢复送审的授权；被拦下时先读本文第三、四节再补简报。Claude Code 里另有一道兜底 hook `.claude/hooks/review-round-gate.sh`：Bash 命令以直接的 `codex exec` 开头时拦下、提示改经发送工具。两者只覆盖 Codex CLI 这一种实现，为什么这样分工、盲区与被拒方案见 [ADR 0046](../adr/0046-guardrail-layers-tests-hooks-and-lean-claude-md.md) 决策 6。
- 等待：输出文件非空不等于完成，还要看进程退出状态与报告是否完整（有总判定与流程处置）；进程异常退出而无输出时，按日志里的错误处理后重起同一份简报；进程匹配别用会自匹配命令行的模式。
- 材料（简报、输出、日志）放系统临时目录、轮次递增编号；不入库，必要的结论内联进 ADR 或报告附录。临时目录不保证持久，跨会话还要用的复制到持久位置。
- 并行两轮时核对进程归属，重复启动会让两个进程写同一个输出文件。
- 固定受审版本：受审对象是一个提交时，在这个提交上另建一个工作副本（`git worktree add --detach <仓库之外的目录> <提交>`），在它的根目录执行发送工具，简报写明提交号。复核者读到的是固定的版本，作者可以接着改主工作区。工作副本放在仓库之外，放在仓库里全仓检索会出现两份命中；后续轮核新的提交时先把它切到新提交再送；这个对象闭合之后用 `git worktree remove` 清掉，并用 `git worktree list` 核对。发送工具只用标准库，可以用主工作区的解释器执行。
- 取证的交接：Codex 的只读沙箱各轮能做的不一样（有的轮次能起真实进程，有的连系统临时目录也写不了）。它这一轮做不了所需的取证时，按第二节交具备条件的执行者，把受审版本、命令、关键输出与退出状态写进下一轮简报，由它判断证据是否足够。本仓库有的轮次里，Codex 读源码推演、构造反例，补出了已有的真实执行没有覆盖到的问题，简报可以据此点名还缺证据的位置；这些样本不作为固定分工的依据，按这一轮的证据缺口与执行条件分工，两路都可以推演，也都可以真实执行。
