# 独立复核与同僚复核 — 工作约定

> 给维护本仓库的 AI agent：本文是 CLAUDE.md「工作方式」里独立复核一条的细则。约束的是**功能**（独立复核 → 分歧裁决 → 闭合确认），不是某个工具：另一家模型的只读同僚是首选实现，没有它时按本文的替代方式执行，不许静默跳过。护栏分层的同一形态见 [ADR 0046](../adr/0046-guardrail-layers-tests-hooks-and-lean-claude-md.md)（hook 只在 Claude Code 生效、测试兜底）。

## 一、功能约束与触发点

- **三步缺一不可**：独立复核（复核者不继承原会话，拿到的是待审主张、拟议改法、基准与证据，剔除既有的评审判词与裁决）→ 分歧裁决（每条由裁决者到仓库核实后定）→ 闭合确认（补写后对更新后的完整材料再确认一次）。
- **触发点**：① 设计定稿——ADR 新增、反转或改动契约 / 不变量；② 待批项交人之前——复盘的待批报告、要 owner 拍板的倾向与建议（倾向本身就是待批项，先过复核再交人）；③ 成批 code 落地之后的闭合（按 ADR 核「落到位」）。
- **为什么**：同一模型、同一上下文的盲区同源。本仓库的样本显示两路发现互补：移动设备支持的一次设计核对里，同僚核出 31 项差集、本家对抗核验核出 9 项、只重合 7 项；一轮代码复盘里，同僚对八项裁定倾向核出五处设计层修正，对已落地的 code 核出一处真缺陷与两处既有真跑样本未覆盖的 SDK 行为。样本只说明互补，不证明哪一路更优。

## 二、两档实现与选档

| 档 | 什么时候 | 怎么做 |
|---|---|---|
| **档一·另一家模型的只读同僚**（首选） | 可用即默认启用；关闭须在报告或提交说明写明原因 | 另一家厂商的模型，只读受审仓库（不修改它），按下文简报独立判；本仓库现用 Codex CLI，见第五节 |
| **档二·本家模型的独立上下文**（兜底，不与档一等效） | 档一不可用（工具或模型不在 contributor 环境里）或已说明原因后显式关闭 | 子代理或新会话，按同一份简报重核，简报里要求先假设有错（对抗驳回）；同样不继承原会话、不带既有判词 |

- **披露**：待批报告附录或落地提交说明写「独立复核：档一（工具与轮次）/ 档二（形态）」与关闭原因；两档都没做的不交人、不标整轮完成。
- 需要真实验证（真跑、真实 SDK、真实进程）而复核者缺权限或环境时，交具备条件的执行者取证，相关条目保留未闭合状态。

## 三、简报怎么写（两档通用）

- 只读；给出亲自核到的文件与行号；不复述已写对的内容；结尾一句总判定。
- **基准内联**：复核者核的是「改动是否落到位、有没有过度声称」，基准（owner 裁定原文、已删除的 journey 全文、ADR 的目标设计）要整段放进简报，不要让它自己猜；其中既有的评审判词与裁决仍按第一节剔除，owner 裁定原文保留。没有这类现成基准的受审对象，简报里先写一段它要做到什么（用途、必须成立的性质），这一段就是基准。基准有界、在首轮之前定下，同时是裁决的标尺与闭合的定义（第四节）：简报不给基准，复核者只能拿受审材料自己的声称和它心目中的理想状态当标准，这个标准没有边界。复核者可以对基准本身提意见（漏了必须成立的性质、定得过宽或过窄），这类意见不算基准之外。
- 逐条要求三元判定：主张成立 / 不成立 / 存疑，处理意见同意 / 修改 / 反对。每条意见另附不处置的后果：谁、在什么情形下、会得到什么错的结果；成立但落在基准之外的意见单列。
- **两处固定标记**：首轮与全新上下文的轮次，基准放在一个标题含「基准」的小节里，标题行顶格、以 `#` 加空格开头（如「## 基准：受审对象要做到什么」）；续接轮带一行「趋势」，列出各轮基准之内的意见条数（如「趋势：基准之内 6 → 3 → 0」）并请复核者一并判断循环是否在收敛；全新上下文的闭合轮两样都带。经 Codex CLI 送出时这两处由 hook 检查（第五节）。
- **mock 之外的行为点名要真跑**：进程、信号、并发时序、第三方 SDK 的真实响应，简报里写「请用真实进程（或真实安装的 SDK）复现」并列出拓扑或输入——这类缺陷本家单测全绿也照不出。
- 成批改动按范围分批送；每轮先把同僚意见与本方补充发现一并落地再送下一轮，否则它会把本方的补充发现原样再提。

## 四、分歧裁决与闭合

- **同僚不是答案源**：凡非「成立且同意」的条目即分歧，由裁决者到仓库核实后判维持 / 采纳 / 合并 / 已消失撤回 / 交人；判「维持」须写理由（进 ADR 被拒方案或报告附录）。
- **成立不等于要处置：裁决答两问，采纳与维持同样写理由。** 一问意见是否成立，二问不处置的后果落在哪里。后果落在基准之内的采纳；落在基准之外、或说不出后果的，判维持并记为已知局限（写进受审材料的局限说明或报告附录）。只有维持要写理由时，全部采纳是最省事的处置，裁决这一步形同虚设；所以采纳也写一句后果。处置的代价要计入它新增的受审面（下条）。
- **修正先看能否收窄，再考虑加机制。** 一条成立的意见是「声称」与「实际」之间的差，两头都能改：改实现去符合声称，或收窄声称、删掉机制去符合实际。新增的机制与新写的声称都是没有审过的新材料，会成为下一轮的受审对象；绝对化的声称（「完全相同」「不可能」）的每个反例都是成立的意见。选择加机制的，写明收窄为什么不行。
- **不缩小人的审批面**：复核只收敛提案的质量，待批项仍逐项交人；判「交人」的分歧单列在前。
- **同一受审对象的后续轮续接复核者的上一轮会话，新对象用全新上下文**（两档通用）：闭合确认与「按意见改完再核」核的是复核者自己上一轮提的意见，续接让它直接引用已读过的材料，减少重复读取与重建对受审对象的理解，模型侧缓存可用时还用得上前缀缓存；带着的整段历史仍有成本，见下条。首轮复核、换了受审对象或话题的复核一律全新上下文：无关的旧上下文没有用处，还会让复核者顺着旧结论走，损害独立性。第一节「复核者不继承原会话」指的是作者一侧的会话，与复核者续接自己的会话不冲突。档二同理：闭合轮回到上一轮那个子代理或会话，新对象另起一个。具体工具的续接方式见第五节。
- **续接上限：复核者主线程的上下文占用到模型上下文窗口的三分之二左右为止**（两档通用）：看的是复核者主线程自己的上下文——续接时被带上、会被压缩的是它；复核者自行分派的子代理各有独立的上下文，不计入这个占比（它们的用量只在算成本时合计）。过线后下一轮改用全新上下文，简报附上未闭合项（复核者上一轮的原意见与本方的处置；它们是闭合轮要核的对象，不属第一节要剔除的既有判词）。续接链上发生过压缩的，下一轮按过线处理，同样改用全新上下文并附未闭合项：压缩后的占用读数变小、看似仍在线下，压掉的细节却已不在上下文里。判据是占用，不是续接轮数：决定一轮成本的是当前上下文大小乘以轮内模型调用次数，与已续接几轮没有直接关系——一串小闭合轮续下去仍划算，一轮大的首轮之后第一次续接就可能不太省。用占窗口的比例而不用 token 绝对数，换模型不必改规则。理由按约束强弱排：其一（硬约束），有的工具在上下文接近窗口时自动压缩历史（是否压缩、何处触发因工具而异），压掉的正是续接要保留的细节，历史被改写后缓存命中也可能下降，所以要给本轮的读取与推理留足余量；其二，续接轮每次模型调用都带着整段历史，成本随上下文线性增长；其三，长上下文下判断质量可能下降——本仓库没有这方面的数据，只作保守理由。「三分之二」是判断，不是实测得出的阈值：依据是本仓库一次样本里改动较多的闭合轮让主线程占用增加约 12 个百分点，线下留出的三分之一够容纳两轮这样的闭合；工具触发压缩的确切位置没有核过。线划在一半的代价按近期约八十个首轮的读数：约五分之一的对象首轮结束时主线程占用已过一半，首轮之后就不能续接（线在三分之二时约十五分之一）；首轮结束在四成到五成之间的约三成，一轮改动较多的闭合（约 12 个百分点）之后即过线。例外：过了线但下一轮确定很小（如只确认一处措辞）仍可续接。Codex CLI 上占用的读法见第五节；档二读不到复核者占用时，只在明确属于小闭合轮时续接同一个子代理或会话，其余用全新上下文。
- **闭合确认：闭合相对基准，不相对复核者。** 闭合指受审对象达到基准、上一轮意见处置到位；「复核者再提不出意见」不是闭合的定义：高推理强度的对抗复核对任何有一定复杂度的对象都能继续提出成立的意见，以它为终点的循环靠修正到不了头。简报写明受审的版本与文件集；补写后对更新后的材料再送一轮，只问两件事：上一轮意见是否处置到位，修正是否引入基准之内的新问题。这两问限定的是复核者要去找什么，不限定它可以报告什么：闭合轮里发现的其它基准之内的问题照样报告、照样裁决，但不因此要求它重新通读全部材料。闭合轮里出现的基准之外的意见按上面「裁决答两问」处置，不因此再开一轮。拿「我改完了」收尾不算闭合；它给的措辞建议原样采纳的，也送一轮确认。提交与否遵循原任务的提交纪律。
- **每轮送出下一轮之前看趋势，不收敛即熔断。** 收敛的样子是基准之内的意见逐轮变少、变轻。出现下列任一情形即不收敛：基准之内的意见连续两轮既不减少也不变轻；同一处（同一机制或同一段设计）连续两轮在修正之后又被指出新的问题（上一轮意见没有改到位而被重提的不算，那是修正没做完）。新意见集中在上一轮为修正而新写的内容上是线索，不单独触发：数量与轻重都在下降时它是正常的收尾。熔断是停止逐条修补，把修复的单位从「这条意见」上移到「反复产生意见的那个结构」：它为什么不断出问题，能否换结构、删掉，或者基准定得不对；向 owner 报告一次（已用轮数、趋势、拟议的结构性改法）之后再继续。单设这一条的原因：循环里的每一步单看都合理（意见成立、修掉、验证、送闭合），问题只出现在跨轮的趋势里，逐步执行的 agent 不专门去看就看不见。本仓库一次样本：两件内部核验工具入库的一批改动复核了六轮、约 38 条意见，每轮旧意见都闭合，新意见多数落在上一轮的修正上，同一个子问题（工具的报告怎样输出才不影响它包裹的命令）连续四轮被指出；六份简报都没有写基准，每条成立的意见都被采纳，修正多数是加机制，其中一件工具从 47 行的一次性脚本长到 530 行、另加约一千行自检。

## 五、实现示例：Codex CLI

- 调用：`codex exec -s read-only -m <模型> -c model_reasoning_effort="<该模型支持的最高推理配置>" -o <输出文件> - < <简报文件>`，`-m` 与 `-c` 不给时沿用 contributor 自己 `~/.codex/config.toml` 配的模型与推理档，repo 不规定、但推荐高推理模型配最高推理档（本仓库 owner 用 Bedrock 上的 `openai.gpt-6-astra` 配 `ultra`）；在仓库根目录启动或显式指定工作目录；本机用 `nohup … &` 后台运行。
- 续接：`codex exec resume <会话 id> -c sandbox_mode="read-only" -m <模型> -c model_reasoning_effort="<同上>" -o <输出文件> - < <简报文件>`。会话 id 在上一轮日志开头的 `session id:` 一行；续接子命令没有 `-s`，只读沙箱经 `-c sandbox_mode` 指定，启动后在日志里核对 `sandbox: read-only`。续接轮的简报只写增量（改了什么、落在哪个提交或文件、要它核什么），不再附上一轮意见全文。日志报的 token 用量是根线程未命中缓存的输入加输出、按会话累计，算增量要减去上一轮；命中缓存的输入不在这个数里，复核者自行分派的子代理也不在——子代理的用量记在各自的记录文件里，分项连同子代理用下条的脚本读。本仓库两次样本（未命中缓存的输入加输出／命中缓存的输入；括号外只计根线程、与日志一致，括号内连同子代理）：小的闭合轮，不续接约 9.5 万／104 万（13.5 万／122 万），续接约 1 万／18 万（该轮没有子代理）；改动较多的闭合轮，续接约 3.6 万／111 万（7.1 万／202 万），同一对象的首轮是 12.6 万／202 万（40.0 万／441 万）。续接轮每次模型调用都带着整段历史，所以历史越长、轮内调用越多，命中缓存的输入越大，节省主要在未命中缓存的部分与重读文件的次数上。
- 上下文占比：会话记录在 `~/.codex/sessions/`，会话归档后移到 `~/.codex/archived_sessions/`（另设 `CODEX_HOME` 时在它下面），同一会话的线程可能分在两处；一个线程的记录可能分成多个片段文件，线程与会话的归属按片段首行的元数据判断、不看文件名，根线程的线程 id 就是会话 id；每次模型调用记一条该次调用的用量，轮次开始与每次调用之后的事件带模型窗口大小。`tools/codex_usage.py <会话 id>` 默认同时查找活动与归档两处（输出的「统计范围」一行列出实际查找的目录，`--sessions-dir` 给出时只查给出的目录），按轮次汇总根线程与各子代理的用量分项（输入、命中缓存、未命中缓存、缓存写入、输出、调用次数），列出每个线程每轮结束时上下文占窗口的比例（本轮有压缩时注明次数），表尾一行是根线程最近一次调用之后的占比，即第四节续接上限要看的数。这个读数是近似值，最近一次调用之后新写入的历史不在其中：读数可能过期（之后又写入了历史或发生了压缩、最后一轮被中断或没有结束记录）或根线程发生过压缩时，表尾逐条注明；注明发生过压缩的，按第四节当作已过线。根线程的片段先后无法确定时脚本不给读数并说明原因。口径与记录格式见脚本头注释。本仓库一次读数：上面改动较多的那条链在续接一轮后，根线程约 15.9 万比 25.8 万、约六成，在上限之内，下一轮仍可续接。
- 复核轮闸门：Claude Code 里执行带 `codex exec` 的命令之前，`.claude/hooks/review-round-gate.sh` 读经 `<` 给出的简报，缺第三节的固定标记（不带 `resume` 的轮次缺顶格的「基准」标题行、带 `resume` 的续接轮缺「趋势」一行）即拦下这次调用；被拦下时先读本文第三、四节再补简报。判断不了的情形一律放行；它只覆盖 Codex CLI 这一种实现，为什么要它、盲区与被拒方案见 [ADR 0046](../adr/0046-guardrail-layers-tests-hooks-and-lean-claude-md.md) 决策 6。
- 等待：输出文件非空不等于完成，还要看进程退出状态与报告是否完整（有总判定）；进程异常退出而无输出时，按日志里的错误处理后重起同一份简报；进程匹配别用会自匹配命令行的模式。
- 材料（简报、输出、日志）放系统临时目录、轮次递增编号；不入库，必要的结论内联进 ADR 或报告附录。临时目录不保证持久，跨会话还要用的复制到持久位置。
- 并行两轮时核对进程归属，重复启动会让两个进程写同一个输出文件。
