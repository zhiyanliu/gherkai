# 测本机或内网里的被测应用

浏览器运行在云端，访问不到 `http://localhost:3000`。本机 local 与云端 cloud 两个后端在这一点上相同：local 只是把 worker 进程放在你的机器上，浏览器始终在云端，所以两个后端测本机应用都要用 `--expose-local`。

`--expose-local` 的前置、行为、隧道由哪个进程持有与何时关闭、限制如下。执行方式与执行后端三种组合的选择、结果读法与退出码见 [`running-and-results.md`](./running-and-results.md)；选项与环境变量总表见 [`configuration.md`](./configuration.md)；按症状排障见 [`troubleshooting.md`](./troubleshooting.md)。

## 工作方式

`--expose-local <ORIGIN>` 让 gherkai 在本机起一条出站隧道，并在组装任务时把 feature 文本里的 `ORIGIN` 替换成隧道分配的公网地址。feature 与 AI 都不感知隧道；引擎只在第一个场景之前多访问一次会话预热地址（见本节末段）。

![云端浏览器经隧道服务商边缘回到本机持有隧道的 gherkai 进程，再由它转发给被测应用；第三方域资源由浏览器直连、不经隧道，公网上不带凭据的访问者被拦在边缘](../diagrams/local-app-testing-tunnel-topology.svg)

图注（隧道拓扑）：图上的实线链是请求方向，浏览器先到边缘，再到本机持有隧道的 gherkai 进程，最后到被测应用；响应沿同一路径返回。隧道是这个 gherkai 进程里的一条会话，由它向隧道服务发起出站连接，你的机器不开入站端口，也不另起隧道进程；三种组合各由哪个 gherkai 进程持有隧道，见下「隧道由哪个进程持有、何时关闭」。隧道服务商、凭据与请求头的具体形态见下文各节。

`ORIGIN` 是「运行 CLI 的这台机器可达」的任意地址，不限 `localhost`：局域网另一台机器上的应用（如 `http://192.168.1.50:3000`）同样可以，目标机器不需要任何配置。

隧道模式下，桌面目标的云端浏览器发出的请求恒带一个固定请求头 `ngrok-skip-browser-warning: 1`，用于跳过 ngrok 对浏览器返回的警告页（被测应用的访问日志里会看到它）；设备上的浏览器无法附加请求头，它们的请求不带这一项，目前在设备浏览器上也没有出现过这个警告页。机读输出里对应 `extra_http_headers` 字段（只测设备的 run 也照常写出），应用侧不需要为它做任何处理。

隧道受本次运行专用的会话保护：引擎的浏览器在第一个场景之前访问一次「会话预热地址」换到会话 cookie，之后对隧道的请求都带着它；预热在 worker 建好浏览器会话之后、执行第一个 step 之前只做一次，不按场景重做。机读输出里预热地址是 `run_meta` 的 `session_warmup_url`。

## 前置：tunnel 组件与 `NGROK_AUTHTOKEN`

两项都要。给了 `--expose-local` 的 `run` 与 `submit` 在开始执行之前先查这两项，早于上传安装包、启动后台进程与连接云端；缺任一项即以退出码 2 结束，说明缺的是哪一项、怎么补。`plan` 与 `gherkai doctor` 不检查这两项。

1. 安装 gherkai 时带上 tunnel 组件，并与已经装的其它组件一并列出：在本机运行时如 `uv tool install 'gherkai[local,tunnel]'`，只往云端提交时如 `uv tool install 'gherkai[tunnel]'`。tunnel 组件是 ngrok 官方的 Python SDK，隧道建在 gherkai 自己的进程里，机器上不需要 ngrok 可执行文件。
2. 在执行 gherkai 的 shell 里设置环境变量 `NGROK_AUTHTOKEN`（免费账号即够）：

```bash
export NGROK_AUTHTOKEN=<token>
```

gherkai 只从这个环境变量取令牌，不读 ngrok 命令行工具的配置文件，用 `ngrok config add-authtoken` 写进那里的令牌不会被用到。`submit` 在本机起的后台进程继承执行 `submit` 时的环境变量，不需要另外设置。

`<token>` 在 ngrok dashboard（https://dashboard.ngrok.com/ ）的 **Your Authtoken** 页取。不要用 **API Keys** 页上的值：API key 只能调 ngrok 的管理接口，拿它起不了隧道。两类值都是较长的随机字符串，从外观上无法区分，请按所在页面取值。填错时以「隧道没有建成：…」失败，说明里带着 ngrok 给出的原因与错误码（令牌无效是 `ERR_NGROK_105`）。

另有一项版本要求：本机后端的引擎 worker 要与命令行工具装成同一个版本，较旧的 worker 不支持会话预热，会在起隧道之前以退出码 2 结束；云端后端还没有版本戳（在 1.4.0 之前部署、此后没有重新部署过）时，带 `--expose-local` 的 run 以退出码 2 结束，要先由部署方运行 `gherkai deploy` 升级。处置见[排错](./troubleshooting.md)。

## 用法

feature 里照写原始地址，不要写隧道地址：

```bash
# 前台运行：隧道随这条命令结束而关闭
gherkai run my_app.feature --expose-local http://localhost:3000

# 提交到本机后台运行
RUN_ID=$(gherkai submit my_app.feature --expose-local http://localhost:3000)

# 提交到云端后端运行
RUN_ID=$(gherkai submit my_app.feature --backend cloud --prefix gherkai- \
  --expose-local http://localhost:3000)

# 用例预检：plan 不起隧道，按原文打印每个 step，并回显你给的取值
gherkai plan my_app.feature --expose-local http://localhost:3000
```

选项值只写到端口为止（如 `http://localhost:3000`）；末尾多一个 `/`（`http://localhost:3000/`）也可以，按不带斜杠的形式处理。取值带路径、查询串、片段或用户信息（如 `http://localhost:3000/app`、`http://user@localhost:3000`），或者不以 `http://`、`https://` 开头时，`run`、`submit` 与 `plan` 都以退出码 2 结束，报错说明这个取值不是 origin，`run` 与 `submit` 不会起隧道；路径写在 feature 的 step 里。

`https://` 开头的被测应用同样可以，用自签证书也行：隧道到被测应用的这一段不校验证书。

选项值必须与 feature 中书写的形式完全一致：`http://localhost:3000` 与 `http://127.0.0.1:3000` 两者不会互相匹配。替换覆盖 step 文本以及它挂的 DocString 与 DataTable 单元格，替换进去的是干净的隧道地址，不带任何凭据。

只替换「作为一个地址出现」的选项值：后面紧跟路径、查询串、片段或句末标点，或者正好到此结束的才算（`http://localhost:3000/login`、`去 http://localhost:3000。`、`(见 http://localhost:3000)` 都替换）；`http://localhost:30000`、`http://localhost:3000.evil/` 是别的端口或主机，不会被改坏；`xhttp://localhost:3000` 这类不是地址起点的也不替换。

`plan` 的「注：」行只是把你给的取值回显出来（末尾的 `/` 已去掉），不检查 feature 里有没有这个地址——地址写错时 `plan` 同样不报异常。把这一行的地址与 `plan` 打印出的 step 文本逐字符对照（大小写、端口、`localhost` 与 `127.0.0.1` 都要一致），即可确认能替换上。

隧道建立后命令打印一行「隧道已建立」，依次给出原始地址与替换后的公网地址，并说明持有隧道的 gherkai 进程退出时隧道随之关闭；`submit` 在这个 run 建好之后打印这一行。`run` 在起隧道期间按 Ctrl-C，以退出码 130 结束并说明没有开始执行。`--tunnel` 选择隧道服务，当前只有 `ngrok` 一个取值，默认即它。

## 隧道由哪个进程持有、何时关闭

隧道是持有它的 gherkai 进程里的一条会话，不是另起的进程。这个进程怎样退出（正常结束、出错退出、被信号结束，包括 `kill -9`），隧道都随之关闭；正常结束时它先关闭隧道再退出。没有要你手动结束的 ngrok 进程，也没有记录隧道的文件。

| 组合 | 持有隧道的进程 | 何时关闭 |
|---|---|---|
| `run` | 执行这条命令的 gherkai 进程 | 命令结束时 |
| `submit`（默认 `--backend local`） | 本机的后台推进进程：`submit` 在本机起的后台进程，它建立这个 run 并执行到结束，日志在 `<report-dir>/<run_id>/reconcile.log` | run 执行结束、这个进程退出时 |
| `submit --backend cloud` | 本机的隧道守护进程（日志在系统临时目录的 `gherkai-tunnel-watch-<run_id>.log`） | 守护进程每 5 秒查一次 run 的状态，run 结束时关闭隧道并退出；最晚到这个 run 允许运行的时间之后 300 秒 |

公网入口另有一道时限：隧道服务一侧在这个 run 允许运行的时间（见[运行测试与查看结果](./running-and-results.md)「允许运行的时间」）之后 300 秒关闭它，此后的请求一律答 403，带令牌的预热请求同样被拒。这道时限不依赖本机的任何进程：持有隧道的进程被暂停或卡住、没有退出时，公网入口照样到点关闭。三种组合都带这道时限，`run --no-report` 同样；隧道没有另外可调的存活时长。

因此：**用了 `--expose-local`，本机要保持开机联网直到 run 达终态**。隧道拓扑图上从边缘回到被测应用那一段全在你的机器这一侧，关机、断网或持有隧道的进程退出，隧道都随之断开，剩下的 scenario 会以导航失败告终。云端后端通常可以在提交后关机，用了 `--expose-local` 时不行，这是唯一的例外。本机提交的后台推进进程（或前台 `run` 的进程）中途退出时，隧道随之关闭，这个 run 不再往下执行：用 `settle-runs` 或 `status --wait` 把它记为已结束（见[运行测试与查看结果](./running-and-results.md)「结束停住的 run」），再重新提交或执行。

提交后用 `gherkai status <run_id> --wait` 等到 run 达终态：这条命令会一直等到 run 结束再返回。本机后端用过非默认 `--report-dir` 时要带上同一个值，否则查不到这个 run；云端后端还要带 `--backend cloud --prefix <前缀>`。两个后端的定位参数都与 `submit` 时一致，照抄 `submit` 打出的那行提示即可。

## 带 `--expose-local` 的 `submit` 怎样提交

两个后端都是先起隧道、再建立 run，起隧道失败时不建立 run。

- **本机后端**：`submit` 做完各项检查与准备（含上传安装包）之后，在本机起后台推进进程，自己等它回报。后台推进进程起隧道、建立 run，把结果交回 `submit`；`submit` 打出「隧道已建立」与查进度的命令，在标准输出给出 `run_id` 后退出，后台推进进程留在本机把这个 run 执行到结束。报告目录所在的文件系统不受支持时，`submit` 在各项检查里查出即以退出码 2 结束，不上传安装包、不起后台推进进程，也就不起隧道；各项检查之后这个位置所在的文件系统才变了的（例如在那里挂载了别的文件系统），由后台推进进程在起隧道之后、建立 run 时再检查一次查出，同样以退出码 2 结束、不建立 run，说明相同，这时起过的隧道随即关闭（报告目录的要求见[运行测试与查看结果](./running-and-results.md)「本机后端的报告目录」）。没有建成时（起隧道失败、在报告目录里建立 run 失败，如写记录失败、给 run 的目录加锁失败）`submit` 原样给出后台推进进程报出的原因，以退出码 2 结束。
- **云端后端**：`submit` 过完云端的各项检查之后在本机起隧道守护进程，等它起好隧道、交回公网地址，再把 run 写进云端、把 `run_id` 交给守护进程，打出「隧道已建立」、守护进程的日志位置与「本机需保持开机联网直到 run 终态」的提醒，在标准输出给出 `run_id` 后退出。起隧道失败、守护进程在交回地址之前退出，或 `submit` 在建立 run 之前的那一次检查查到守护进程已经退出时，不建立 run，以退出码 2 结束；查过之后守护进程才退出的，run 照常建成，其中要访问被测应用的 job 会失败。建立 run 失败时，`submit` 先让守护进程关闭隧道，等它退出之后再报错、以退出码 2 结束，等待有时限，守护进程在时限内没有退出时照样报错。

等待期间按 Ctrl-C，`submit` 以退出码 130 结束，标准输出为空：

- 本机后端：说明已停止等待提交结果，这次提交可能仍会建立 run 并执行。后台推进进程在建立 run 之前查一次 `submit` 是否还在：查到 `submit` 已经退出时不建立 run、自行退出，隧道随之关闭；查过之后才被打断的，照常建立 run 并执行、照常持有隧道。请先用说明里给出的 `gherkai list-runs` 命令确认，再决定是否重新提交。`submit` 已经收到建成的结果、还没有输出时被打断的，说明这个 run 已经提交，给出 `run_id` 与查进度的命令。
- 云端后端：还没有开始建立 run 时，说明没有建立 run，守护进程随之关闭隧道、退出。中断落在建立 run 的过程中时，说明这个 run 可能已经写入云端、给出确认用的 `gherkai list-runs` 命令；已经建立时，给出 `run_id` 与查进度的命令。守护进程这时还没有收到 `run_id` 的随之关闭隧道、退出，说明里写明隧道已不再可用、这个 run 里要访问被测应用的 job 会失败。

## 安全

- 隧道存活期间，被测应用可从公网访问。gherkai 为每次运行生成专用的访问令牌与会话 cookie 值，由 ngrok 在边缘节点校验：只有带着本次会话 cookie 的请求才会被转发到你的机器，不带或不对的请求在边缘就被拒（隧道拓扑图上被拦在边缘的那条支路）；引擎的浏览器凭访问令牌在预热地址上换到这枚 cookie。令牌与 cookie 在隧道关闭时失效，最晚到这个 run 允许运行的时间之后 300 秒（见上「隧道由哪个进程持有、何时关闭」）。
- step 文本里只有干净的隧道地址，不带凭据，所以发给模型的提示里不会出现令牌。令牌只出现在预热地址里，它记在提交记录 `run_meta.json` 的 `session_warmup_url`（明文，执行这个 run 要用到它）；引擎的浏览器访问过预热地址，所以引擎原生产物里可能记下它。gherkai 自己产出的文字里令牌与 S3 预签名地址的签名类参数显示为 `***`：失败消息、`explain` 输出、`run --json`、AI 证据的 JSON、本机转发的 worker 日志与云端 worker 自己写进 CloudWatch 的诊断行都是如此。隧道的流量策略（同时含令牌与会话 cookie 值）只在持有隧道的 gherkai 进程里交给隧道服务，不写成文件。仍是明文的：`run_meta.json`、引擎自己的原生产物（Nova Act 的轨迹文件、Midscene 的报告页）、云端 CloudWatch 日志里由引擎 SDK 自己写出的内容，以及测试设备上的网页时 Device Farm 控制台里该会话的录像与日志（设备浏览器访问过预热地址，AWS 保留 400 天）；报告与日志仍应按内部资料对待。
- 已知边界：会话 cookie 会随每个请求到达被测应用，出现在它的访问日志里（在边缘剥掉它是服务商的付费功能）；被测应用若用 `Clear-Site-Data` 清掉 cookie，之后的请求会被边缘拒绝；确定性 step 里自己发起的 HTTP 请求要经浏览器上下文发出才带这枚 cookie。
- 只把测试环境的实例接上隧道，不要暴露带生产数据或生产凭证的服务。
- 隧道只存在于持有它的 gherkai 进程里：这个进程退出，隧道即关闭，被 `kill -9` 结束时也是如此，不会留下在公网上继续暴露被测应用的隧道。持有隧道的进程被暂停期间，请求不再转发到本机，恢复之后隧道重新在线；公网入口仍按上面那道时限到点关闭。

## 限制

- 一个 run 只能暴露一个地址。重复给 `--expose-local` 不会报错，只有最后一个取值生效——前面给的地址不会被替换，用到它的 scenario 会导航失败。被测应用依赖多个本机地址时，先让它们收敛到同一个入口再测。
- 只替换与选项值完全相同、且作为一个地址出现的部分，`localhost` 与 `127.0.0.1` 不互认（见上「用法」）。
- 被测应用收到的 `Host` 头是隧道分配的 ngrok 域名，不是 `localhost`——「工作方式」的隧道拓扑图上，浏览器导航的是边缘分配的公网地址。校验 Host 的开发服务器要先放行这个域名（Vite 设 `server.allowedHosts`、Django 加 `ALLOWED_HOSTS`、Rails 放宽 host authorization），否则应用会在框架层拒绝请求。这个域名由 ngrok 按账号分配：新注册的免费账号是 `ngrok-free.dev` 下的一个固定域名（形如 `xxx.ngrok-free.dev`），每次起隧道都相同，把「隧道已建立」那一行里的域名加进允许列表一次即可；较早注册的账号每次起隧道的域名都不同（形如 `xxx.ngrok-free.app`），要用通配写法（如 `.ngrok-free.app`）。团队成员各用自己的 ngrok 账号时，同样改用通配写法（如 `.ngrok-free.dev`）。
- 新注册的 ngrok 免费账号同一时间只有一条隧道能在线。这个账号上已有一条在线的隧道（另一个带 `--expose-local` 的运行，或在别处起的 ngrok）时，再起隧道以「隧道没有建成：这个 ngrok 账号上另一条在线的隧道占用了同一个地址（ERR_NGROK_334）」失败，等那条隧道下线之后再试；它属于另一个带 `--expose-local` 的 gherkai 运行时，持有它的进程退出之后它就会下线。较早注册的账号上可以同时有多条隧道，但同时在线的会话数有上限，超出时同样起不来隧道。
- 隧道转发 HTTP、HTTPS 与 WebSocket 流量。被测应用自身域下的请求（HTML、脚本、样式、图片、接口）全部经隧道，吞吐与延迟受隧道链路影响，也都计入 ngrok 配额；页面引用的第三方域资源由云端浏览器直接访问，不经隧道（隧道拓扑图上通向第三方域资源的那条虚线）。
- ngrok 免费层有配额（量级为每月 1 GB 流量与 2 万次请求，以 ngrok 的定价页为准），重度使用可能超出配额，表现为 429 或断流。
- gherkai 不为隧道做断线重连：持有隧道的进程被暂停后恢复时隧道重新在线，本机断网或休眠之后隧道能否恢复取决于隧道服务，不作保证。受影响的 scenario 以导航失败告终，解决导致中断的问题后重新运行即可。
- 隧道只服务网页目标：桌面浏览器与真机浏览器访问替换后的地址时经过隧道。原生应用（`@app:<别名>`）连本机或内网里的后端目前不支持：应用请求的后端地址打包在安装包里，gherkai 只替换 step 文本里的地址、不改写应用；应用目标也不做会话预热，应用打开替换后的隧道地址时不带会话 cookie，请求会在边缘被拒。测原生应用时让它连公网可达的测试环境。

## 常见故障

起隧道失败时 `run` 与 `submit` 都以退出码 2 结束、不建立 run，说明分四种：没有安装 tunnel 组件（装了但无法加载另有一句）、没有设置 `NGROK_AUTHTOKEN`、这个 ngrok 账号上另一条在线的隧道占用了同一个地址、其余原因（带隧道服务给出的原因与错误码，20 秒内没有连上隧道服务也属此类）。原因都在这一句说明里，gherkai 不另写隧道的日志文件；每种的处置见[排错](./troubleshooting.md)的隧道节。下表只列隧道特有的其它症状。

| 症状 | 原因 | 处置 |
|---|---|---|
| 隧道起来了，但每个 scenario 都在第一步导航失败 | 选项值与 feature 里书写的地址不一致（取值带路径时会在开始执行之前以退出码 2 被拒，不会表现为这里的导航失败）；或被测应用没在监听该地址 | 执行 `gherkai plan my_app.feature --expose-local <ORIGIN>`，把回显的取值与打印出的 step 文本逐字符对照；再在本机直接访问一次该地址，确认应用正在运行 |
| 页面返回「Host 不被允许」一类的提示或 400，但 `plan` 对照无误、本机直连也正常 | 被测应用只接受自己配置的域名，拒绝了隧道域名 | 在应用的允许域名列表里加上隧道域名（地址见「隧道已建立」那一行），或临时放开该校验后重新运行 |
| run 执行到中途开始，之后每个 scenario 都导航失败 | 隧道已断开：本机关机、断网或休眠，或持有隧道的进程退出了（云端提交时是本机的隧道守护进程，它的日志见上「隧道由哪个进程持有、何时关闭」） | 重新提交，并保持本机开机联网、持有隧道的进程不被结束，直到 run 结束 |
| run 的每个 scope 都没执行任何 step，`status` 里 job 的消息是「隧道会话预热被拒绝：访问令牌或会话 cookie 不被边缘节点接受…」 | 访问到的已不是这个 run 的隧道：持有它的进程已经退出，同一个地址上现在是另一次运行的隧道（新注册的 ngrok 账号地址固定）；或提交侧与后端对隧道的配置不一致 | 重新提交这次运行；仍出现时核对命令行工具与后端是否同版本 |
| job 的消息是「隧道会话预热被拒绝：边缘节点没有收到有效的隧道会话 cookie…」 | 浏览器没有保存或没有带上会话 cookie | 确认持有隧道的进程仍在、浏览器允许安全 cookie，必要时换浏览器或设备后重新提交 |
| job 的消息是「隧道会话预热未能确认就绪（已尝试 3 次）…」 | 隧道已关闭（持有它的进程已经退出），或云端浏览器到隧道入口的网络不通（预热访问的两个地址都由隧道边缘直接响应，与本机应用是否在运行无关） | 确认持有隧道的进程能保持运行、本机能访问外网后重新提交 |
| job 的消息是「后端未传递会话预热地址，部署版本可能低于命令行工具，请重新部署后再提交」 | 云端后端比命令行工具旧，读提交记录时丢掉了预热地址 | 请部署方运行 `gherkai deploy` 升级后端，再重新提交 |
| 加载变慢、间歇 429 | 碰到免费层的配额或带宽限制 | 减少单次运行的 scenario 数，或升级 ngrok 套餐 |
| `submit --backend cloud` 以退出码 2 结束，`持有隧道的本机后台进程退出了，没有提交；它退出之前如果有输出，原因在上面。…` | 本机的隧道守护进程在交回公网地址之前、或在建立 run 之前退出了；它出错退出时原因打在这句之前，被系统或别的进程结束时（如 `kill -9`、内存不足）没有输出 | 有输出时按它处理好原因，没有输出时查看是什么结束了这个进程，然后重新执行；这时没有建立 run |
| `submit --backend cloud` 以退出码 0 结束，同时打出 `run … 已经提交，但持有隧道的本机后台进程已经退出（它退出之前如果有输出，原因在上面），隧道已不再可用：…` | 守护进程在 run 建立之后、收到 `run_id` 之前退出了；run 已由云端照常执行 | 这个 run 里要访问被测应用的 job 会失败，不必等它的结果；处理好原因后重新提交 |
| `submit --backend cloud` 以退出码 2 结束，`无法启动持有隧道的本机后台进程：…。没有提交。` | 本机起不了新进程（进程数或内存耗尽等，原因在冒号之后） | 处理报出的原因后重新执行 |

云端提交时隧道守护进程的日志 `gherkai-tunnel-watch-<run_id>.log` 在系统临时目录里，从收到 `run_id` 起记下它在等哪个 run、读不到这个 run 的状态时的说明（同一种情形连续出现只记一次，恢复读到时再记一句），以及隧道在什么时候、因为什么关闭；在那之前的输出打在 `submit` 的终端上。

feature 的写法与断言规范见 [`writing-features.md`](./writing-features.md)，示例 feature 在 [`features/`](../../features/)。
