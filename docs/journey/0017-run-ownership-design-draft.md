## 背景与问题

0054 之后的两组设计（本机接力的改法、事件库里解析不了的记录）在复核里不收敛，根因有两条。

- **推进权没有唯一的持有者。** 0034 让谁都可以从事件库重放、接着推进后台 run；本机 `status --wait` 分不清推进进程的死活、一律接力，只能从外面猜。两类外部推断都不成立：「靠时钟加一段固定时长的做法已经三次失守」（0054 决策二「本机接力的改法」，后两种由真实进程复现），凭进程标识核对则每轮复核都有新的反例（被拒方案）。
- **run 的状态与 job 的状态分开写。** run 级在某一刻汇总、单独写一次后冻结，另有三条路不看 job 就结束 run（到期收尾、处置、云端读不到运行定义），于是有「run 已结束而 job 仍是 `pending` 或 `running`」「job 全部通过而 run 是 `error`」，要靠 run 级说明解释记录。

## 决策

### 一、执行组合与推进方

- 执行方式与执行后端的组合有三种：本机前台（`run`）、本机后台（`submit --backend local`）、云端后台（`submit --backend cloud`），下称三种组合。**云端后端只支持 `submit`**：命令行给出 `run --backend cloud` 时以退出码 2 结束并指向 `submit`；配置文件设为云端时与命令行给出时相同，这样的项目每次 `run` 都要显式给出 `--backend local`。前台才有的几样（逐步的进度、`--fail-fast`、使用方中断、网络故障时整个 job 重试）云端暂时没有，后台取消是之后要补的第一项。理由：它是唯一由本机进程推进、执行在云端的组合，云端因它有后端不知推进方死活的 run，0054 决策九为此另设到期处置与各 Lambda 的分流；不支持它，云端的推进方只有后端自己。
- **本机后端的 run 任何时刻至多一个推进方**：前台是执行 `run` 的进程，后台是 `submit` 启动的后台推进进程，都持有它的生命期锁（决策二；交接期间提交进程也持锁、不推进）。认领、启动 job、写 job 的执行中与终态只由它做，结束写（决策六）由它或处置方做。本机 worker 是推进方的子进程，生死系在它身上。
- **云端允许多次 Lambda 调用重叠推进同一个 run**，`kicker`（runs 表流与定时触发）与 `reconciler`（events 表流）两个入口保留，每一步写带条件（决策十）。
- **后台执行标记只作描述**（是否由 `submit` 提交，只进 `list-runs --json` 的 `detached`），不参与任何判断：云端的 run 都由 `submit` 提交，触发过滤与各 Lambda 不看它；处置不分前台与后台（决策十一）。

### 二、生命期锁：加在 run 目录上

- **对象**：run 目录本身。持有方以只读方式打开 `<report-dir>/<run_id>/`、取排他的 `flock`；锁按打开的文件描述计：同一进程另一次打开同样被挡，共用这个打开的进程里有一个还开着，锁就在。
- **谁在何时拿**：
  - `run`（生成记录时）：建出 run 目录、拿到锁之后才写运行定义与运行态，持有到进程退出；锁已被持有时以退出码 2 结束（试拿方只碰运行态已读得出的目录，这只在 run_id 重复时出现）。
  - `submit --backend local`：提交进程同样先拿锁再建 run，启动后台推进进程时把描述符交给它，只关掉自己那一份、不解锁，退出；交接期间两者都持锁，提交进程关掉之后推进进程退出即释放（「前提与边界」）。推进进程先核对交来的描述符是目录、设备号与 inode 同这个 run 目录，再对它取一次锁；核对不过或没有交来锁时不推进、退出。
  - 云端后端没有锁。
- **谁在何时试拿**：等待中的 `status --wait` 在 run 未结束时每次轮询试一次，`settle-runs` 对每个未结束的本机 run 试一次，都只对运行态已读得出的目录；不阻塞，拿到之后持有到这次处置做完。
- **结果的判读**：只有成功算拿到，只有「已被持有」（`EWOULDBLOCK`）算持有者还在；其余错误一律按锁不可用：建 run 的一方以退出码 2 结束，处置的一方只剩期限一条。
- **产品边界：本机后端的报告目录及其中的 run 目录要在本机文件系统上**（检查见下一条）。同一个内核上经同一个挂载或其绑定挂载访问的在边界之内（实测宿主与容器、容器之间）；网络文件系统、经虚拟机共享进来的目录在边界之外（实测 macOS 的 Docker Desktop：宿主目录在容器里是 `fakeowner` 类型、被拒，宿主一侧是 APFS、放行，两侧的锁互不阻挡）；多台机器共用记录用云端后端。用户文档写明并列出清单。
- **边界检查**（本机后端）在取锁与试拿锁的动作里、先于取锁（`run`、`submit`、等待中的 `status --wait`、`settle-runs`），对要取锁的那个 run 目录的描述符判断（后台推进进程用提交进程判断过的那一次打开，不另判断）；建 run 的一方另在建 run 目录之前对报告目录（不存在时取最近一层已存在的上级）判断一次，这一次被拒时不留目录。类型不在清单里或判断不了（如读不到挂载信息、平台不是 macOS 与 Linux）即以退出码 2 结束，说明写原因（这样的目录上无法确认执行 run 的进程是否还在）、检测到的类型与怎么办（列出清单）。`settle-runs` 在报告目录存在时另查它（不存在即没有可处理的 run，照常结束）；某个 run 目录不过只跳过它、在结果里写明原因（决策十一）。`doctor` 对配置的报告目录做同一判断（本机后端时必修，不碰锁）；其余命令不碰锁，也不查。放行不证明在边界之内、锁有效（「前提与边界」第一条；不靠读回，见被拒方案）。两个平台同一条规则：各处都对打开的目录的描述符取文件系统类型，由内核解析路径（含符号链接、绑定挂载与盖住它的上层挂载；两个平台上实测按挂载表的最长前缀会取到被盖住的那条），只放行清单里的类型；清单只收照决策二理由实测过的，先实测再加：
  - macOS 由 `fstatfs` 取类型名。实测（arm64）：APFS 为 `apfs`，HFS+、FAT 的磁盘映像为 `hfs`、`msdos`，autofs 自动挂载点为 `autofs`。清单：`apfs`。HFS+、FAT 上的锁只核过互斥、同一进程再开被挡、被杀后释放，不进清单。
  - Linux 由描述符的 `mnt_id`（`/proc/self/fdinfo`）在 `/proc/self/mountinfo` 取那一条。实测（内核 7.0）：被盖住、经符号链接、容器里的路径都取到实际所在的挂载，绑定挂载显示源的类型，不存在的目录取上级、与新建后同类型，懒卸载后取不到；NFS 为 `nfs4`、`nfs`。清单：`ext4`、`tmpfs`、`overlay`（宿主与容器上实测）；`xfs`、`btrfs`、`ext3`（回环镜像、缺省选项、`btrfs` 顶层子卷上重做，除数值外与 `ext4` 相同）。
- **不被子进程继承**：描述符不可继承，持锁的进程只经 exec 启动子进程（worker、隧道 agent），收到交接的推进进程先置为不可继承。
- 理由：死活由操作系统在进程退出时给出，不需要对方配合，也不靠时钟。真实进程核过（macOS 的 APFS，Linux 清单里的类型与绑定挂载，括注的除外）：被暂停的持有方仍持有，已退出未回收的已释放；交接后仍持有，交出方关掉自己那一份之后接收方被杀即释放（关掉之前仍被挡：macOS 的 APFS、Linux 的 ext4）；fork 而不 exec 的子进程延长持有，`subprocess` 缺省方式启动的不会，`multiprocessing` 以 fork 起的会（Linux 上 Python 3.12、3.13 的缺省）；交出方显式解锁连同接收方的一并解开；对交来的持锁打开、或一个没被锁的别的文件再取锁都立即成立（同一 run 目录另一次未加锁的打开被挡），所以接收方先核对对象。放弃：POSIX 记录锁（只读打开的目录取不上排他的；按进程计，关掉任一指向该文件的描述符即释放；交接后原进程一关即释放，Linux 的 ext4 上核过）；长期持有 `.runstate.lock`（读改写用的短锁，长期持有挡住所有写）。

### 三、死活的判断与处置的条件

- 管这个 run 的进程还在不在，由试拿锁回答：拿得到即已不在；被暂停的进程仍持有锁，算还在。
- **管它的进程不在了的 run 不续**：不再认领、不再启动 job，由别的一方把它结束（下称 run 处置，本文单说「处置」都指它；job 到了截止时刻被停下另称 job 到点停止）。能处置的只有：`settle-runs`；等待中的 `status --wait`；云端的 run 另有后端自己到期结束（决策十）；以后的取消命令（条件与对推进方的作用在取消的设计里定）。`list-runs`、不带 `--wait` 的 `status`、`explain` 只读。
- **可以处置的条件是两者之一**：试拿锁拿到了；或当前时刻严格晚于运行期限加 300 秒。云端只有后一条。300 秒给时钟偏差与仍在的推进方按期限自己结束（决策六）留出余量，不是收尾时长的上界（「前提与边界」「期限加 300 秒按墙钟判断」一条）。
- 处置做什么：读运行态，已结束则不动；否则做结束写，写成的一方生成报告（决策八）。处置不推演事件，不替事件里有、运行态里还没有的结果下结论：推进方在 worker 退出之后、写下终态之前中断（云端触发链断开时这段可以很久），处置看到 `running`，记 `aborted`「没有结果」；同一次中断在云端通常由流的重试与之后的触发记下真实结果，三种组合的 job、run 状态与退出码可能不同。

### 四、各命令写什么

| 命令 | 写 |
|---|---|
| `run` | 建 run、建 run 之后与开始执行之前写隧道记录（决策十二）、认领、job 的执行中与终态、自己到期与 fail-fast、使用方中断时的结束写、报告、隧道记录的「已拆」标记 |
| `run --no-report` | 不写记录、不拿锁，同一套规则在内存里给出结果 |
| `submit --backend local` | 拿锁、建 run、写隧道记录（决策十二），把锁交给后台推进进程；不推进；交棒之前就地拆隧道时写「已拆」标记 |
| `submit --backend cloud` | 写隧道记录、建 run（隧道记录在建 run 之前，决策十二）；不推进；建 run 失败或交棒之前就地拆隧道时写「已拆」标记 |
| 本机后台推进进程、云端 Lambda（`kicker`、`reconciler`） | 认领、job 的执行中与终态、自己到期的结束写、报告；云端退出观察者只写退出记录，后端到期结束属于处置；本机后台推进进程与云端隧道守护进程另写「已拆」标记（决策十二） |
| `status --wait`、`settle-runs` | 处置条件成立时做结束写与报告；不认领、不启动、不投影；另按决策十二补拆隧道、写「已拆」标记，两个后端相同 |
| `list-runs`、不带 `--wait` 的 `status`、`explain` | 只读，不碰锁 |

报告只由使 run 成为终态的写入方生成（决策八）。退出码：`run` 按记录里的 run 状态，`passed` 为 0、其余为 1；处理过使用方中断时按信号取 130 或 143；run 在本次执行结束之前已被别处结束时为 1（不输出汇总与 `--json`，0054 决策五），同时处理过中断时仍按信号取。`status --wait` 一到终态即返回，`passed` 为 0、其余终态为 1（自己处置的同样），被 Ctrl-C 打断为 130；`status` 未结束或 `passed` 为 0、其余终态为 1。开始执行之前的问题与查不到 run 为 2，另有：边界检查不过（四个命令，`settle-runs` 指报告目录）；锁已被持有、锁不可用（只对建 run 的一方，决策二）；`run` 给出云端后端。`submit` 其余不变；`settle-runs` 执行完成为 0，跳过（决策十一）不改变退出码，写入失败为 2。

### 五、job 的终态只写一次，run 的状态只由 job 的终态算出

- job 的状态只前进：`pending`、`running`、终态；终态只写一次，迟到的结果（终态之后才到的退出记录与事件）不被采用。
- **run 的状态**：有 job 未结束时，全部是 `pending` 为 `pending`，否则为 `running`；全部结束时按序取第一条成立的：有 `error` 则 `error`；否则有 `failed` 则 `failed`；否则有 `aborted` 或 `skipped` 则 `aborted`（这个 run 没有执行完）；否则 `passed`。run 是终态当且仅当全部 job 是终态。零个 job 的 run 按取法为 `passed`。
- run 的状态字段没有自己的写入逻辑：每次改变 job 状态的写在同一次写里按取法写 run 状态（云端连同状态分组），使 run 成为终态的那次写同时写下结束时刻；run 一到终态，运行态的任何写都不再成立。依赖方：`status --wait`、`list-runs`、CI 把读到的终态当定论，报告据记录生成。前提：写都经端口的写入口。
- **本机**：所有写入口在 `.runstate.lock` 内读改写，按锁内读到的整份运行态计算。**云端**：运行态条目带写入序号，每次写加一；记下 job 终态的写与结束写以「序号等于读到的值」为条件，写不成即重读再算，且对 `jobs` 整体替换；认领与投影沿用各自的条件（决策十），同样加一。认领计数只作 `status --json` 的诊断键（成功认领的次数）。理由：两个调用各记一个 job 的终态、各自读到对方的 job 未结束时，不加条件会留下「全部 job 已结束、run 仍为 `running`」；按 job 逐个加条件，表达式随 job 数增长，放弃（实测逐个路径写在两百多个 job 时超长）。真实 DynamoDB 上在写入层核过（未经产品代码）：整体替换的表达式长度与 job 数无关，50、300、1000 个 job 都写得成，上限由单条记录的大小上限决定（各种终态轮换的样本，1327 个 job 写成、1335 个被拒）；两个进程以同一序号并发写，每次恰有一个写成，另一个重读重算后写成、恰有一方使 run 成为终态；不加条件时逐个路径写留下上述情形、整体替换丢掉另一方的终态。
- 由此 0031 决定三的过滤名单、空判定集规则与例外不再需要，0034 机制三的两条 run 级钳制成为推论。run 状态会变的情形列在影响清单的 0031 一节；退出码不变：这些变化都在非 `passed` 的终态之间，处理过中断时仍按信号取。

### 六、结束一个 run 只有一种写法

- **结束写**是一次条件写：run 未结束时，把每个未结束的 job 写成终态并各带一句说明，运行态里是 `pending` 的（从未认领，因而没有启动）记 `skipped`，是 `running` 的（已认领而没有结果）记 `aborted`；run 状态按决策五随之成为终态，run 级写下结束的原因与结束时刻。判断只看运行态，不读事件。
- 来路：执行方自己到期（已过停止启动的时刻、没有执行中的 job，余下的都没有启动）；前台的 fail-fast 与使用方中断（执行中的 job 停下、各自得出结果之后，余下没有启动的）；处置；云端后端到期；以后的取消。各来路的条件不变，写法只此一种。
- **运行定义不可用时**（云端推进方读不到可用的运行定义；本机后台推进进程同样处理），同一种写，但每个未结束的 job 记 `error`：这些 job 不是被中途结束，是没法执行；run 随之为 `error`。
- 说明文字：

| 来路 | run 级 | `skipped` | `aborted` |
|---|---|---|---|
| 执行方自己到期 | 已超过允许运行的时间 | 这个 run 已超过允许运行的时间，job 没有启动 | 不出现 |
| fail-fast | 有 job 出错，余下的 job 不再启动（fail-fast） | fail-fast：其他 job 出错，本 job 没有启动 | 不出现 |
| 使用方中断 | 收到中断信号，余下的 job 不再启动 | 收到中断信号，本 job 没有启动 | 不出现 |
| 处置：锁拿到了 | 执行这个 run 的 gherkai 进程已退出 | 执行这个 run 的 gherkai 进程已退出，job 没有启动 | 执行这个 run 的 gherkai 进程已退出，job 没有结果 |
| 处置：已过期限加 300 秒（含云端后端到期） | 已超过允许运行的时间 | 这个 run 已超过允许运行的时间，job 没有启动 | 这个 run 已超过允许运行的时间，job 没有结果 |
| 运行定义不可用 | 读不到定义的原因（0037 决策 7 的几句） | 未结束的 job 都记 `error`，说明同 run 级 | 同左 |

  处置的各句末尾另加「（已记为已结束）」；两个条件同时成立的处置取「锁拿到了」那一行。
- 理由：所有来路一种写法，「run 已结束」与「每个 job 都已结束」同时成立。0054 被拒方案「到期时把未启动的 job 记为 `error` 或 `skipped`」的 `skipped` 一半由此反转（当时拒它是因为后台要新设一种记录，结束写正是那一种）。

### 七、被期限截断的 job 记 `aborted`

- 被 run 的期限截断的 job 记 `aborted`，说明仍是「这个 run 已超过允许运行的时间，job 被中止」；用完自己预算的 job 仍是 `error` 加超时。起作用的截止时刻由记录里的认领时刻、job 的预算与 run 的期限算出（`run_deadline.job_cutoff`，相等时算预算），不看说明；内容完整的 job 照旧不改判（0034 机制二）。
- 终结函数的超时一行按起作用的截止时刻分开：预算为 `ERROR`、`timeout`，期限为 `ABORTED`、无归因。

### 八、判定明细与报告

- **状态的权威是运行态，输出里的状态就是记录里的状态**：`run` 的汇总与 `--json`、`status`、`list-runs`、`explain`、报告里 job 与 run 的状态都取运行态，不在读取时另派生；判定明细对 scenario、step 与归因负责，由执行结果结束的 job 的说明也在明细里。理由：job 的终态只在运行态里写一次，由结束写结束的 job 没有明细，明细的写又不带条件（决策十），只有运行态对每个 job 都有且分出了先后。这收窄了 0027 与词表「判定真值」的「唯一权威」：明细不再是状态的来源与判定接口，给脚本读状态的入口是 `status --json`。收窄的条文（0027 等）见影响清单；按 scope 读明细里状态的 CI 改读 `status --json`；读取权限不改：`status` 先读运行定义的版本头（0037 决策 7），本机运行定义（含隧道访问令牌，0035 决策 5、0051 决策 13）与运行态都是 `0600`、明细是 `0644`（0030 决定三），所以以别的用户身份读报告目录的 CI 只能以同一用户执行 `status --json`，放宽要连运行定义一起、令牌随之可读。云端要有 runs 表的读权限（令牌也在这张表里）。
- **job 的终态点名它的那一份明细**：每次保存明细，写入方生成一个随机的标识，明细存成带这个标识的一份，同一个 job 可以有多份、互不覆盖，本机推进方对同一次保存的重试（下一条）用同一个标识。记下 job 终态的那次条件写（决策五）在这个 job 的记录里同时写下这个标识，即点名，点名随终态只写一次、此后的写原样保留；由结束写结束的 job 不点名。读者只认被点名的那一份：`explain`、报告与其余读回明细的各处都先从运行态取 job 的清单与各自点名的标识，再读那一份，不列举目录或前缀；没被点名的明细不读、不列、不清理。`status --json` 的 `jobs[]` 每项带这个标识（未点名时按运行态的惯例省键）；明细文件的存放形态不是对外的约定，直接读明细文件不再是对外的读法，机器读结果的入口是 CLI 的 `--json`（状态用 `status`，明细用 `explain`）。理由：明细的写不带条件、可能有多份，只有记下终态的那次写分出了先后，由它点名，输出与记录一致就延伸到 scenario、step 与归因，明细的写也不必另带条件。代价：明细的存放形态改变（本机与云端），读明细的一方要先读运行态（跨用户的读者读不到运行态，分不出哪一份被点名）；每个 job 的记录多出标识的长度，单条运行态记录容纳的 job 数相应减少（决策五的样本，实测项 6 重做）。
- **由执行结果结束的 job，明细先于终态写下**：保存成功之后才写终态，所以读到这类 job 的终态时它点名的明细已在。依赖方：`explain` 与报告。保存失败时这个 job 这次不写终态：云端由流的重试或之后的触发再做；本机两种推进方按指数退避重试 3 次（间隔 1、2、4 秒），仍失败即放弃，推进方退出（前台 `run` 以非零退出码结束），执行中的 job（含同一轮已存下明细的）留在 `running`，之后被处置为「进程已退出」那句：描述属实，只是没有说明为什么退出（前台终端里另有存储错误），结果丢失。一时的失败见对照表。后台推进同样逐 job 先存明细、再写终态（一次写可记多个 job）。
- **被点名的那一份就是写成终态的那一方存的**：job 的终态至多写成一次（决策五），写成的一方点名的是自己存下的那一份，与终态出自同一个执行结果（写不成而重读再算时沿用这一份，改用别的结果先另存一份）；云端两次调用重叠、本机期限加 300 秒的处置抢先、推进方恢复之后迟落下的保存，都只多出没被点名的明细。依赖方：`explain` 与报告不把没被采用的结果当成结果展示。由此**报告里的判定由记录确定**：run 到终态之后运行态与被点名的明细都不再变，报告里的状态、scenario、step 与归因不随生成的时机变化。依赖方：只由一方生成一次的报告（决策十）与 `status`、`explain` 一致。
- **执行方得知 run 已结束之后不再存明细**（迟到的结果不被采用）：前台在停手信号成立之后，后台与云端在一轮读到终态之后。run 到终态之后新落下的明细只剩已开始的保存（前台是那一次，后台与云端是那一轮的各个 job），三种组合都有。
- **由结束写结束的 job** 没有执行结果，结束写不写明细、不点名，状态与说明在运行态里；执行方在存明细与写终态之间中断时留下的那一份没被点名、不被读。`explain` 对这类 job 给出运行态里的状态与说明，已经执行过的 step 从事件流补取（0042 决策七；云端只在事件的保留期 7 天之内，0033）。
- **`run --json` 的 `jobs[]`** 列出运行定义里的全部 job，状态与由结束写结束的 job 的说明取运行态；被点名的附上那一份明细的各键，没有的不带。
- **报告**：使 run 成为终态的那次写的写入方（执行方或处置方）在这次写之后从记录（运行态加各 job 被点名的明细）生成，没写成的一方不生成。被处置的本机后台 run 由此照常有明细与报告：明细由推进进程在各 job 结束时写下并点名，报告由处置方生成。这是做法：写入方在生成之前中断则没有报告；事件里有结果而运行态还没有终态的 job 见决策三。

### 九、说明只是描述

run 与 job 上的说明文字不参与任何计算：状态、退出码、是否超时、是否可以处置都不看说明。理由（owner 原话）：一旦对内容有要求，就需要对未来的任何描述都保持这种要求，这本身是坏味道。

### 十、云端后端

- **定时触发**：`kicker` 收到 STATE 条目的新建（META 已先写）时建两次一次性的定时触发。期限那一次对仍在执行的 job 做 job 到点停止、再推进：某个 job 自己的触发缺失、worker 又不出事件时照样在期限被截断（决策七），同本机。期限加 300 秒那一次是**后端到期结束**：run 仍未结束即按决策三处置。建不成时这次调用失败、由流重试（名字确定，重试不重复建）。到点的处理重新读墙钟确认已过，不以收到触发为证据，未过则在这次调用里等到已过（同 job 到点停止的到点复查，0034）；run 已结束时只清扫。
- **清扫**：run 到终态之后，后端按启动时带的 run id 列出仍在执行的 task 逐个停掉（可重复，不写 runs 表；失败时这次调用失败，流触发的由流重试，定时触发的按 Lambda 异步调用的重试）。使 run 成为终态的那次写经流（新映像的状态分组不是 `live` 的 STATE 条目）触发 `kicker` 清扫，过滤命中的只有这一次写（终态之后运行态不再有写，决策五）；没停到的（如之后才启动的，本决策末条）由此后带到这个 run 的任一次调用停掉：worker 的事件、退出记录、定时触发。
- **`status --wait` 不调用 `kicker`**，只盯到终态、条件成立时处置；返回之前按决策十二补拆隧道，同本机后端。
- **重叠时各记录靠什么分出先后**：
  - META 条目：只在不存在时写，之后不变。
  - 运行态条目：建 run 要求不存在；认领要求 job 为 `pending` 且 run 未结束；投影要求 HWM 不小于库中值、run 未结束、job 不越过 `running`；记下 job 终态与结束写要求写入序号等于读到的值。每个 job 的终态与 run 的终态各至多写成一次（决策五），条件写不保证最终写成。
  - 判定明细：写不带条件，用哪一份由 job 的终态点名（决策八）。
  - 报告的生成方：只有使 run 成为终态的那次写的写入方，这样的写至多一次；所含判定由记录确定（决策八）。
  - 退出记录：观察到的退出与启动失败的补写覆盖同键，补写的未知退出只在没有记录时写入，之间按最后一次写为准；job 终态写下之后的变化不被采用，两者可能长期不一致，以运行态为准。
  - 定时触发按确定的名字建立，已存在即视为已建。
- **task 的启动不随记录分出先后**：认领成功之后、启动调用完成之前 run 被结束时 task 仍会启动，由后端清扫停掉（0054「边界与已知局限」）。

### 十一、`settle-runs` 与查看命令的提示

- **`settle-runs`**（形态同 0054 决策七）不给 `run_id` 时处理这个后端里全部未结束与运行态读不出的 run，不分前台与后台；处理完之后，另对列举到的未标已拆的隧道记录按决策十二「两个处置命令补拆」逐个看（给了 `run_id` 时只看这个 run 的那一份）。每个 run 依次看运行态、边界检查与试拿锁（本机）、期限，`reason` 取第一条成立的：`unreadable`（运行态读不出）、`already_finished`（已结束，含结束写被别处抢先）、`unsupported_filesystem`（run 目录不过边界检查）、`advancer_exited`（锁拿到了）、`past_deadline`（已过期限加 300 秒）、`lock_held`（锁被持有，未必是推进方）、`undetermined`（锁不可用或期限读不出）、`within_deadline`（云端未过期限加 300 秒）。`advancer_exited` 与 `past_deadline` 的 `outcome` 是 `settled`，`--dry-run` 下是 `would_settle`（不写，锁拿到即放开）；其余是 `skipped`。写入失败时就此停止、以退出码 2 结束，再执行一次是安全的：已处置的给 `already_finished`。拆隧道不改变 `reason` 的取值、机读输出与退出码（决策十二）。
- **查看命令的提示**：`list-runs` 与不带 `--wait` 的 `status` 不碰锁，提示只看记录与期限：未结束而已过期限加 300 秒的 run 提示「已超过允许运行的时间（可用 settle-runs 或 status --wait 记为已结束）」，其余不给期限提示（run 级说明照旧）；`list-runs --json` 与 `status --json` 带 `deadline_at`，不另给由它推出的键。等待中的 `status --wait` 在处置条件（决策三）不成立时继续等待：锁被持有不另说明，锁不可用时说明原因；返回之前另按决策十二补拆隧道。

### 十二、隧道记录跟着 run 的记录放；宿主收尾时拆，run 已结束时处置命令补拆，拆之前都在回环地址上按端点名问 ngrok 的本机接口；公网入口到期限加 300 秒在边缘关闭

- **缺口**：给出 `--expose-local` 时，gherkai 在使用者的机器上启动一个 ngrok 代理进程，把本机的被测应用暴露成公网地址（0035 决策 1）。隧道由宿主在 run 结束后拆（0035 决策 3 的表）：前台 `run` 的宿主是执行它的进程，本机 `submit` 的是后台推进进程，云端 `submit` 的是隧道守护进程。宿主没有走完收尾就退出（如被 SIGKILL）之后没有人拆，代理进程与公网地址一直留着。本机后台现在还由 `status --wait` 接力推进时顺带拆（`drive_local_reconcile` 调 `cleanup_tunnel`，拆后删 `tunnel.json`）；设计里接力已经去掉（被拒方案「本机接力，及其改法」），这条路随接力一并去掉。下文的「两个处置命令」指 `status --wait` 与 `settle-runs`。
- **启动**：
  - 启动命令多带 `--name <端点名>`，端点名是 `gherkai-` 加每次启动新生成的随机串；流量策略最前面多一条到点拒绝的规则（下面「边缘到点拒绝」）。
  - 本机接口的地址：端口取代理日志里 `starting web service` 一行 `addr` 的端口（这份日志就是现在取公网地址的那一份，`NgrokTunnel._launch`）；主机只用回环地址：日志里的主机是回环地址（`127.0.0.0/8`、`::1`）或 `localhost` 时照它问，是全部接口（`0.0.0.0`、`::`）时改问同一地址族的回环地址（这几种写法下都问得到，见理由里「接口绑在哪个地址上」的实测），其余（如一个局域网地址）按启动失败处理（使用前提第 2 点）。记下的是实际去问的那个地址；回环地址上的这个端口没有被转发到别处时，回答来自这台机器（「前提与边界」「处置命令要在启动这个 run 的环境里执行」）。
  - 在现有的启动超时之内（`NgrokTunnel.start` 的 `timeout_s`）轮询，直到日志里有公网地址与接口地址、且按拆隧道的第 1 步问得 200、返回的名字是这个端点名；不依赖两行日志的先后，也不只问一次。被直接启动的进程在这期间退出，或到时限仍不成立，按启动失败处理：启动方凭进程句柄结束刚启动的代理（它此时是代理的父进程，不走拆隧道的做法），以退出码 2 结束，同现在隧道起不来（决策四「开始执行之前的问题」）。
  - 代理的标准错误接到一个文件，与日志文件同样处理，报错带两者的尾部（现在两路输出都丢掉、报错只带日志尾部；参数不被识别时日志是空的，原因只在标准错误里，见理由里的实测）。报错按卡在哪一步分四种说法：
    1. 一直没有拿到公网地址（含进程在这之前退出），且不是下一种：同现在的说法（authtoken 未配置或没有外网），另列 ngrok 配置里固定的 `web_addr` 已被占用与 ngrok 版本不认 `--name`（低于 3.18.0，见标准错误）。
    2. 公网地址已在线：代理没有建成隧道，日志里的错误带 `ERR_NGROK_334`（理由里「新注册的免费账号上同时两条隧道」的实测）。说明这个账号的隧道地址已经被另一条在线的隧道占用：可能是另一个带 `--expose-local` 的 run 正在执行，也可能是之前的 run 留下的隧道还没有拆，后一种情形执行 `gherkai settle-runs`。报错带上这个错误码，不提代理进程。不自动清理之后重试（被拒方案「起隧道遇到地址已在线时，自动拆掉自己留下的隧道再重试」）。
    3. 拿到了公网地址而日志里一直没有接口地址：说明隧道暴露需要 ngrok 的本机接口、不能在 ngrok 配置里关掉。
    4. 两者都有而核对一直不过：进程仍在时说明两种常见原因：ngrok 版本低于 3.30.0，本机接口不在回环地址上；进程在核对通过之前退出时说明代理进程已退出，原因见附带的尾部。
  - **使用前提**（三点，owner 已接受，用户指南的前置与排障、agent skill 的前置清单都写明），不满足任一点即按上一条启动失败：
    1. 本机接口开着。ngrok 配置里写 `web_addr: false` 时隧道照常建立、日志里没有接口地址，报第三种说法；使用者不能关掉它。
    2. 本机接口在回环地址上。`web_addr` 配成别的地址时报第四种说法；现在的启动命令只要公网地址，在这种配置下可用（理由里的实测）。
    3. ngrok 是 3.30.0 或更新：按名字问端点的 `/api/endpoints` 从这一版起有（理由里的更新记录）；更旧的版本按卡在哪一步落在第四种或第一种说法上。
  - 一条已建立隧道的事实（`TunnelInfo`）多两项：接口地址、端点名。
- **隧道记录**：
  - 内容：进程号、公网地址、本机源地址、接口地址、端点名，另有一个「已拆」标记；不含访问令牌与预热地址（同现在）。
  - 位置：run 的记录里单独的一项，跟着 run 的记录放。本机后端是 run 目录里的 `tunnel.json`，每个带隧道的 run 一个；云端后端是 runs 表里同一个 `run_id` 名下的第三种条目，`item_type` 在 `META` 与 `STATE` 之外另取一个值（0030 决定六给同一个 run 加条目类型留了口子），不新增索引，也不另设一张表（下「列举」）。云端没有任何本机文件。没有给 `--expose-local` 的 run 没有这一项；`run --no-report` 没有记录，同现在。
  - 存取：隧道记录的写入、标已拆与列举是 runtime 一层自己的一小块存取，两个后端各一个实现（本机读写 run 目录里的 `tunnel.json`，云端读写 runs 表里的隧道条目），由组合根调用；core 的 RunStore 端口、运行定义与运行态都不为它改，0035「core 对隧道无知（映射在组合根完成）」不变。现在 `tunnel.json` 的写与读已经在 runtime（`detached.write_tunnel_file`、`detached.cleanup_tunnel`），守护进程在 runtime 里直接装配 runs 表的读（`tunnel_host.watch_run_and_stop_tunnel`）。
  - 写入的时机：开始执行之前，三种组合都是。云端建 run 即开始执行（STATE 条目的新建触发 `kicker`，决策十），所以隧道条目紧挨建 run 之前写下（`_submit_cloud` 里各道闸与填完运行定义之后、`create_run` 之前），带「条目不存在」的条件。本机建 run 不开始执行，`tunnel.json` 在建 run 之后、开始执行之前写下：前台 `run` 在第一次起 worker 之前，本机 `submit` 在启动后台推进进程之前。本机也可以在建 run 之前写：决策二里 run 目录由建 run 的一方先建出并持锁，写运行定义之前写 `tunnel.json` 与决策二不相抵。不取：那样 run 目录里有一段时间只有 `tunnel.json`、没有运行态，其间不给 `run_id` 的 `settle-runs` 列举到它，按下「两个处置命令补拆」里 run 不存在的一条，会把这条刚建立、run 还没开始执行的隧道拆掉；在建 run 之后写，本机就没有这段时间。云端只能先写（这段时间见「前提与边界」「云端建 run 期间不另设防」）。
  - 写不成：三种组合同一种处理，同启动失败：不开始执行，启动方凭进程句柄结束代理（它是代理的父进程，还没有交棒），以退出码 2 结束（决策四「开始执行之前的问题」）。云端这时还没有建 run。本机这时 run 已经建成、全部 job 为 `pending`，按现有的「已落库但未交棒」一格处理（0035 决策 3「被接受的代价」一条），不另设规则：这个 run 没有推进方，启动方退出、锁随之释放之后，由两个处置命令按说明表「锁拿到了」一行结束（job 记 `skipped`），没有人执行处置命令时一直不结束（「前提与边界」「本机没有常驻的处置方」）。现在本机 `submit` 在这一格另打一句「隧道已拆除……若上面已经打出提交成功，这个 run 就别再往下推……先修掉报出来的问题，再重新提交」，前台 `run` 在建 run 之后、起 worker 之前出错时没有专门的处理，异常结束进程，run 记录同样留着。
  - 云端隧道条目写下之后建 run 失败（云端不可达，或条件不成立）：启动方同样凭进程句柄结束代理，并把条目标已拆（它确知代理已经结束），以退出码 2 结束；标记写不成时按下「已拆」标记的写不成处理。启动方在写下隧道条目之后、建 run 完成之前被强杀时，留下的是一个没有对应 run 的未拆条目：不给 `run_id` 的 `settle-runs` 列举到它时，run 不存在即没有宿主在管，按 run 已结束同样处理（下「两个处置命令补拆」）。
  - 现在（`cli/gherkai_cli/__main__.py`、两个 RunStore adapter 的 `create_run`）：两个命令都是先起隧道（`_setup_tunnel`，公网地址要替换进 job 的文本）、再生成运行定义（`_build_run_meta`）、再建 run。本机的 `create_run` 自己建出 run 目录，在 `.runstate.lock` 里先写 `run_meta.json`、再写 `run_state.json`；云端的 `create_run` 先以强一致读确认 META 与 STATE 都不在、再依次写 META 与 STATE，各带条件，不是一次事务。前台 `run` 建 run（`persistence.begin`）之后装配事件库与引擎，进入调度、认领之后才起 worker；本机 `submit`（`_submit_local`）建 run 之后依次建事件库、调 `write_tunnel_file` 写 `tunnel.json`（不是原子写，只有进程号、公网地址、本机源地址）、开 `reconcile.log`、启动后台推进进程；云端 `submit`（`_submit_cloud`）建 run 之后启动守护进程，只把进程号经命令行交给它。前台 `run` 与云端 `submit` 现在都不写隧道记录。
  - 流的过滤：决策十里 runs 表的流上只有 STATE 条目的新建与使 run 成为终态的写触发 `kicker`，隧道条目的写（新建与标已拆）不触发。现在部署的过滤（`deploy_aws/gherkai_deploy_aws/stack.py` 里 runs 表的流到 `kicker` 的事件源）按两项筛：事件名为 `INSERT`，新映像里 `detached` 为真；不看 `item_type`。带 `detached` 的只有 STATE 条目（`DynamoDBRunStore._state_item`），隧道条目不带，现在的过滤不收它。改写之后过滤不看 `detached`（决策一），新建那一路与决策十给终态那次写加的一路都要同时限定 STATE 条目（`item_type`）：隧道条目的写入也是新建，它的分组也不是 `live`。改写之后的过滤对隧道条目的两种写都不触发，没有核过（实测项 12）。
  - **「已拆」标记**：
    - 只从否写成是，多方先后写的结果相同；run 结束之前之后都可以写。它不属于运行态，也不在运行定义里：运行定义建 run 之后不变、run 到终态之后运行态不再改变，这两条都不动，运行定义的结构版本（0037 决策 7）也不变。本机写在 `tunnel.json` 里，写入与改写标记都是原子写（同运行态）；云端在隧道条目上去掉状态分组属性、写上标记，同一次写，条件是条目存在。
    - 只在确知时写，两个后端相同：宿主与交棒之前就地拆的启动方，发出了终止信号或确认自己的代理已经不在（下面第 3 种）时写；云端建 run 失败时凭进程句柄结束了代理的启动方写（上「云端隧道条目写下之后建 run 失败」一条）；处置命令只在自己发出终止信号成功时写。处置命令得到第 3 种时不写：它可能不在启动隧道的机器上，这时写「已拆」等于删掉一份有效的记录。得到第 4 种时谁都不写。
    - 代价：宿主没有走完收尾就退出、之后代理也自己没了的（机器重启，或代理进程被别的原因结束），没有哪一方确知，标记一直是「否」：之后每一次不给 `run_id` 的 `settle-runs` 都会再读到它、再问一次接口，问到连接被拒，或端口被后来的代理占用时的 404（第 3 种），或端口被一个不是 ngrok 的程序占用、它答的不是 404（第 4 种），都不做任何事、不提示（下「没有拆成时」），所以不带来重复的提示，只是每次多几次本机请求。接受这项代价，不设手动清除或手动标已拆的入口（被拒方案）。同样一直留着的还有任何一方拆成（或确知代理已不在）而标记没有写成的。云端的这类条目一直留在索引的专用分组里（runs 表没有过期删除），条数随历史累积，每次列举都读到全部。
    - 标记写不成（存储不可达）不改变退出码、不算决策十一的写入失败，后果同上一条。
  - **列举**：供不给 `run_id` 的 `settle-runs` 用，只列未标已拆的。本机在列举 run 目录时顺带看各目录里的 `tunnel.json`（`settle-runs` 本来就列举 run 目录，同 `list_runs` 列报告目录的子目录）。云端不读全部历史：隧道条目带状态分组索引（`status_group-run_id-index`，0030 决定六）的分区键属性 `status_group`，取一个不是 `live`、也不是任何状态值的专用分组值；标已拆在同一次写里去掉这个属性，条目随之离开索引。列举是查这个分组，再按键读各条目（索引投影不含隧道的各项）。对照 code 与实测核到的：
    - 现在的表与索引（`deploy_aws/gherkai_deploy_aws/stack.py`、`core/gherkai_core/adapters/run_store/ddb.py`）：每个 run 两种条目，分区键 `run_id`、排序键 `item_type`，取值 `META`（运行定义）与 `STATE`（运行态）；状态分组索引的分区键是 `status_group`、排序键是 `run_id`、投影 INCLUDE 只含 `worker_task_def_arns`；只有 STATE 条目带 `status_group`（`DynamoDBRunStore` 的写入规则）。
    - 与索引现有的两个读者相容：worker revision 清理只查 `live` 分组（`deploy_aws/gherkai_deploy_aws/workers.py` 的 `_live_reference_snapshot`）；`list-runs` 只查 `live` 与所请求的各终态分组，读回只取每个 run 的 STATE 与 META（`DynamoDBRunStore.list_runs`）。两者都碰不到专用分组里的条目；runs 表上没有按 `run_id` 读整个分区的读者。
    - 实测（真实的 DynamoDB，us-east-1，一张键结构与索引定义同 runs 表的临时表，一次，用完即删；未经产品代码）：给同一个 `run_id` 再写一种条目（`item_type` 取 `TUNNEL`），带 `status_group` 等于一个专用值，查这个分组列出的正是这些条目，`live` 分组与按终态值的分组里仍然只有 STATE 条目；标已拆（去掉 `status_group`、写上标记，条件是条目存在）之后这个条目离开索引，同一个 run 的 STATE 条目逐字未变，按终态值的分组不变；对没有隧道条目的 run 做同一个写，条件不成立、什么都没有写。写入消耗：写一个隧道条目计基表 1.0、索引 1.0 个写单位，标已拆同样各 1.0，重复标一次基表 1.0、索引 0。索引查到的条目只有键与分组属性，隧道的几项要再按键读条目。所以每个带隧道的 run 多两次索引写，重复标已拆不再增加索引写。
    - 0030 决定六随之要改的句子见影响清单。
  - **权限**：写隧道条目的是云端 `submit`（建 run 之前的一次新建）；标已拆的是守护进程、建 run 失败时的启动方与两个处置命令（带条件的更新）；列举的是不给 `run_id` 的 `settle-runs`（索引上的查询，再按键读条目）。守护进程现在只读（`watch_run_and_stop_tunnel` 只调 `load_run_state`），用的是 `submit` 那次的 region 与 profile。0033 编排进程角色一段给 `submit`、`status` 的机器的是「runs 表读写」，不给 `run_id` 的 `settle-runs` 另有索引 ARN 上的 `dynamodb:Query` 与表 ARN 上的 `dynamodb:BatchGetItem`；按 0033 配的最小权限下这几处写与读是否都够，没有核过（实测项 12）。凭证在守护进程收尾之前过期时标记写不成，按上「已拆」标记的写不成处理。
  - **守护进程**：云端 `submit` 仍在建 run 之后启动它，隧道的几项（进程号、接口地址、端点名）与存活上限（下面「边缘到点拒绝」）经命令行交给它（现在交的是进程号与 TTL）。它拆的时候不读隧道记录，发出终止信号或得到第 3 种之后标已拆（上「已拆」标记一条）。
- **拆隧道只有一种做法**：宿主收尾、交棒之前的就地拆（0035 决策 3 表外的一条）、两个处置命令补拆都这样做，按隧道的事实（`TunnelInfo`，或隧道记录里、交给守护进程的同样几项）；启动失败、隧道记录写不成与云端建 run 失败时，代理刚由启动方启动、run 还没有开始执行，启动方凭进程句柄结束它（「启动」「隧道记录」两条）：
  1. 在记下的接口地址上问 `GET /api/endpoints/<端点名>`，短超时，直连、不经环境变量或系统设置里配置的代理（Python 的 `urllib` 缺省按这两处选代理，环境里设了 `HTTP_PROXY` 而 `no_proxy` 没有列出这个地址时，对回环地址的请求同样经代理转发，回答就不是代理的）。
  2. 答 200 且返回的名字是这个端点名：给进程号发 SIGTERM。
  3. 连接被拒，或答 404，或发信号时进程已经不在（`ESRCH`）：这里没有我们的代理（已经退出，或这条命令不在启动它的环境里），不提示。
  4. 其余（超时、别的状态码、读不懂的回答、连接被重置、没有回答就关闭、发信号被拒）：拿不准，不发信号（发信号被拒的不再发）、不标已拆；提示与否见「没有拆成时」。隧道记录读不懂或缺项时同样按这一种处理。

  什么时候标已拆见上「已拆」标记。
- **谁在什么时候拆**：
  - **宿主收尾**：前台 `run` 在进程退出时；本机后台推进进程在退出时，不论 run 是否已到终态（如明细一直写不进、交来的锁核对不过而中途退出）；云端守护进程在轮询到终态、到了存活上限、收到 SIGTERM 或 SIGHUP 时（`_cmd_tunnel_watch` 把这两个信号转成退出，SIGINT 由 Python 缺省转成 `KeyboardInterrupt`，都经 `watch_run_and_stop_tunnel` 的 `finally` 拆；装配 store 出错（region 解析不出、凭证坏）时经同一个 `finally` 立即拆，这时标记写不成；轮询里读库出错只记一句、继续轮询，到存活上限才拆）。宿主与代理在同一个环境里。推进器只有一个，它退出之后这个 run 不会再被推进，前台与本机后台由此在同一个时机拆。现在的后台推进进程只在 run 到终态之后拆（`drive_local_reconcile` 在循环正常返回之后才调 `cleanup_tunnel`），中途退出时不拆，与前台不同。
  - **两个处置命令补拆，本机后端与云端后端相同**：
    - 等待中的 `status --wait` 在返回之前，对这个 run：run 已结束、有隧道记录、没有标已拆时，按上面的做法拆。
    - `settle-runs <run_id>`：处理完这个 run（决策十一）之后，同上。
    - 不给 `run_id` 的 `settle-runs`：先按决策十一处理全部未结束与运行态读不出的 run，再对列举到的未标已拆的隧道记录逐个看：run 已结束的（含这一次刚处置成已结束的）按上面的做法拆；run 不存在的（按键强一致读不到 STATE 条目，只有 META 条目的也算；云端启动方在写下隧道条目之后、建 run 完成之前被强杀时留下，上「隧道记录」），没有宿主在管，按 run 已结束同样处理；run 未结束的、运行态在而读不出的不动。处置因写入失败而停止（决策十一）时不再往下看。
    - 条件看的是 run 已结束，不是「这个 run 是我结束的」：推进方写下终态、还没拆就被强杀时，run 已经结束，处置命令不会再结束它，按后者就没有人拆。`settle-runs --dry-run` 不拆；只读的命令（决策三）不拆。
    - 拆隧道不属于 run 处置：处置只改记录（「前提与边界」），拆隧道是这两个命令另做的一件事，不进 `settle-runs` 的机读输出，不改变退出码。
  - 在别的机器上对同一个云端 run 执行处置命令时，问到的是那台机器自己的回环地址：没有把这个端口转发过来时得到第 3 种，那台机器上同一个端口被别的程序占着时可能得到第 4 种，都不发信号、不标已拆、不提示（下一条，处置命令拿不准时不提示）；这不需要机器标识（端点名每次启动随机生成）。
  - **没有拆成时**：提示只在确知有隧道没有拆掉时给，两种情形：宿主或交棒之前就地拆的启动方对自己持有的那条隧道得到第 4 种（它与代理在同一个环境里，按确知处理；会误报的情形见「前提与边界」「核对与发信号之间不另设防」「ngrok 的本机接口没有鉴权」）；任何一方核对通过（答 200 且名字一致）而发信号被拒。提示说明哪个 run 的隧道没有拆掉与它的公网地址，处理办法只写 gherkai 自己的命令：之后执行 `gherkai settle-runs`，发信号被拒时写由启动这个 run 的使用者在启动它的环境里执行；不写请使用者结束进程，不给进程号。其余情形（处置命令得到拿不准的回答）不提示：标记没有写上，下一次处置命令会再问。提示是诊断，不改变退出码，不进机读输出：命令行里走 stderr，`--json` 下 stdout 的 JSON 不变（0041 决策三「stdout 只放数据、诊断走 stderr」）；后台推进进程写进 run 目录里的 `reconcile.log`，守护进程写进它的日志。
  - **补拆成功时**：处置命令发出终止信号成功时在 stderr 给一句，说明拆掉了哪个 run 的隧道（标记写不成也给）；不进机读输出，不改变退出码。
  - **没有人执行处置命令时**：代理留到关机或重启（它是本机可见的独立进程）；公网入口到期限加 300 秒在边缘关闭（下一条）。这是做法的边界，不是保证。
- **边缘到点拒绝**：
  - 流量策略最前面加一条规则：`timestamp(time.now) >= timestamp('<时刻>')` 成立时直接答 403 与一句固定的说明，不再往后判（`time.now` 是 ngrok 流量策略成文的变量，`https://ngrok.com/docs/traffic-policy/variables/time/`：「The current UTC time in RFC3339 format.」）。时刻是这个 run 的运行期限加 300 秒（0054 决策六里任何一方都可以结束这个 run 的那个时刻）。三种组合都带，`run --no-report` 同样（它也有运行期限）。
  - 时刻怎样得到：现在创建时刻与运行期限在起隧道之后才取（`_build_run_meta`）。改为创建时刻在起隧道之前取一次，运行期限与策略里的时刻都由这一次读数算出，生成运行定义时用同一个值；给不给 `--expose-local` 都在同一位置取。期限要的各 job 预算与停止宽限在两个命令里都在 `_setup_tunnel` 之前已经取得；起隧道的耗时由此计入 0054 决策二的 900 秒一次性余量，0054 随之要改的句子见影响清单。
  - 守护进程的存活上限：现在另有一条公式（`tunnel_host.compute_watch_ttl_s`：900 秒加各 job 的预算与每 job 210 秒，按单调时钟计），与运行期限的公式结构相同（0054 决策二：创建时刻加 900 秒加各 job 的预算与尾段，云端尾段同为 210 秒）。改为从运行期限推出：守护进程到运行期限加 300 秒为止，按墙钟比较（0054 决策二「检查用墙钟」）。两处不再各算一遍。
  - **`--tunnel-ttl`（`submit` 的显式覆盖项）去掉**（owner 定）：调大没有意义（期限之后 job 已被截断，到期限加 300 秒公网入口也已关闭），调小会在 run 未完时拆掉隧道。这个参数、它的 `--help`、取值校验的报错与用户文档里讲它的一节随实装删去（影响清单）。
  - 实测（macOS，ngrok 3.39.13，较早注册的免费账号，一次）：现有四条规则前面加这一条共五条，隧道照常建立；到点之前，没有 cookie 的请求答 401、带令牌的预热请求答 200 并下发 cookie、带 cookie 的请求照常转发；到点之后所有请求答 403，带令牌的预热请求也是、不下发 cookie（按本机时钟，记下的第一个 403 是过点后 1.7 秒发出、2.9 秒收到回答的请求，切换落在哪个区间没有记）；到点之后代理进程还在，本机接口按名字问仍答 200。六条规则的策略启动失败，代理退出，日志与标准错误里是 `Policy configuration has exceeded its rule per policy limit of 5 … ERR_NGROK_2264`。所以这个账号每个策略至多五条，加上这一条正好用满；`runtime/gherkai_runtime/tunnel.py` 的 `POLICY_RULE_LIMIT` 是 5、现用 4 条。新注册的免费账号上（macOS，ngrok 3.39.13，一次）六条规则的策略启动成功。产品的策略保持在 5 条以内，两种账号都能用。ngrok 的免费套餐说明页现在写「Traffic policy rules (per policy) 15」，与较早注册的账号上看到的不同。没有核过的：Linux、代理与边缘重连之后规则是否照常、长时间运行、ngrok 3.30.0。
  - 它给出什么、不给什么（这是做法，不是保证）：到点之后公网入口在 ngrok 边缘关闭，不依赖本机的任何进程，带令牌的预热请求同样被拒；代理进程与账号的在线名额仍占着（免费套餐说明页写「Online endpoints Up to 3」「Concurrent agents 3」），要等有人拆或关机；新注册的免费账号上，留下的代理在到点之后仍挡住之后的隧道（「前提与边界」「同一个账号同一时间只有一条隧道在线」）。现在令牌在隧道存活期间一直有效（0051 决策 13），这条规则给它加了一个到点失效，对正常结束的 run 同样起作用。时钟与规则数的边界见「前提与边界」。
- 理由：
  - 宿主没有走完收尾就退出之后要有人拆。不另起专门拆隧道的进程（被拒方案）；管它的进程不在了的 run 本来就由两个处置命令结束（决策三），由它们在 run 结束之后拆，不多一个进程。
  - 隧道记录跟着 run 的记录放：找得到这个 run 的命令就读得到它，本机与云端一样，没有另一套定位；本机后端与云端后端因此是同一种做法（项目约定同一种情形本机与云端相同）。
  - 记录单独成一项、不放进运行定义或运行态：它带一个 run 结束之后还会变的标记，而运行定义建 run 之后不变、运行态到终态之后不再改变；单独一项，这两条规则与它们的写入口都不用动。云端要能列举未拆的隧道，本来也需要一个能进索引的条目；它与 run 的另两种条目在同一张表、同一个分区里，借用现有的状态分组索引就能列举（上「列举」的实测）。
  - 存取不进 core：只有隧道一方读写这份记录，core 不解释它；放在 runtime 一层、由组合根调用，0035「core 对隧道无知」与 RunStore 端口都不动。
  - 写在开始执行之前：写不成时还没有执行，按开始执行之前的问题结束，不会留下一个在执行而没有隧道记录的 run。云端建 run 即开始执行（STATE 的新建触发 `kicker`），所以隧道条目先于建 run；本机建 run 不开始执行，先建 run 再写，run 目录里就没有一段只有 `tunnel.json` 的时间（上「写入的时机」）。
  - 不需要判断「是不是这台机器」：端点名每次启动随机生成，只有我们启动的那个代理会对它答 200（同机程序冒充回答不在防护之内，见「前提与边界」「ngrok 的本机接口没有鉴权」）；只在回环地址上问，这个端口没有被转发到别处时回答来自这台机器（被转发时见「前提与边界」「处置命令要在启动这个 run 的环境里执行」）。
  - 标记只在确知时写、记录不删：问到连接被拒或 404 只说明这里没有这个代理，说明不了它在别处也没有。
  - 不给 `run_id` 的 `settle-runs` 也收隧道：云端的宿主（守护进程）没了之后，run 照常由云端推进到结束，留下的正是「run 已结束而隧道还在」；使用者执行 `settle-runs` 时预期这个后端里该收的都收掉。有了标记，它只问未标已拆的那几个，不必把带过隧道的 run 逐个问一遍。另有一项事实：在免费套餐、新注册账号这种用法下，没拆的代理会挡住之后的隧道（「前提与边界」「同一个账号同一时间只有一条隧道在线」），其中有记录、属于同一个后端与报告目录、在启动它的环境里执行的，`settle-runs` 能拆掉（拆不掉的几种见同一条）；主要的理由仍是前面那一条。
  - 拆之前要核对：直接按记录的进程号发信号会误杀（被拒方案「按记录的进程号直接发信号、不核对」）。ngrok 代理自带本机 HTTP 接口，能回答「这个端点还在不在这个代理上」；端点名由我们每次新生成，答 200 且名字一致的就是我们启动的那个代理（信任范围见「前提与边界」「ngrok 的本机接口没有鉴权」）。宿主收尾时代理同样可能已在 run 中途退出，所以宿主也先问：已建立的隧道只有一种拆法。
  - 拿不准时不发信号、不标已拆，提示只给按确知处理的两种情形：处置命令可能不在启动隧道的机器上，也可能隔了很久，它得到的拿不准的回答说明不了隧道还在；不提示时标记没有写上，下一次处置命令会再问。宿主与处置命令同时拆时，后到的一方可能问在代理退出的过程中，得到连接被重置或没有回答就关闭（下面「代理退出的过程中去问接口」的实测），这属于第 4 种：后到的一方是处置命令时不提示；是宿主时多出一句提示，接受（「前提与边界」「核对与发信号之间不另设防」）。
  - 边缘规则与守护进程、补拆各管什么：守护进程与宿主在正常情况下拆；补拆在宿主没有拆成、有人执行处置命令时拆；边缘规则在两者都没有发生时到点关掉公网入口。前两者结束代理进程，后一者只管公网入口，不是为同一件事叠的三层。ngrok 自己没有到期释放：免费套餐说明页（`https://ngrok.com/docs/pricing-limits/free-plan-limits/`）原话「Free endpoints have no timeout—they can stay online indefinitely. To keep one running unattended, run it as a background service.」，`ngrok http` 也没有寿命或超时一类的参数（查的是 `https://ngrok.com/docs/agent/cli/`）。
  - 时刻对齐到 run 而不是 job：一条隧道只有一份策略、启动时定下；各 job 什么时候开始在那时还不知道；运行期限已经是每个 job 截止时刻的上限（0054 决策二第 2 条）。
  - 实测（macOS 上的 ngrok 3.39.13、Linux 上的 3.39.11；两个平台都做的结果相同，只在一处做的注明）：
    - 接口是成文的：ngrok 的 agent API 文档写明基址缺省 `http://127.0.0.1:4040/api`、没有鉴权，在配置文件里改 `web_addr` 时基址随之变；写明「The ngrok agent API never makes breaking changes to the API unless the caller explicitly opts in to a newer version」；`/api/tunnels` 一组标为弃用、改用 `/api/endpoints`；`GET /api/endpoints/:name` 答 200 或 404，`DELETE /api/endpoints/:name` 答 204 或 404。
    - 接口实际监听的地址写在代理自己的日志里：`{"obj":"web","msg":"starting web service","addr":"127.0.0.1:4040"}`；看过的一次里这一行在 `started tunnel` 之前。缺省配置下同时开着的第二个代理这一行是 `127.0.0.1:4041`，端口被占用时顺延（4040 被一个不是 ngrok 的程序占用时也是，代理另记一条 `can't bind default web address, trying alternatives`，只在一台机器上看过）。所以缺省配置下不用改使用者的配置，多个 run 并存时各问各的地址；0035 决策 1 记的不用接口的理由（不可配端口，多 run 并存还撞默认 4040）由此不再成立。配置里写了固定的 `web_addr`、而那个地址已被另一个代理占用时，第二个代理绑定失败（`bind: address already in use`）、进程退出（只在一台机器上看过，第一个代理此时的状态没有查），按「启动」一条报第一种说法。`ngrok http` 有 `--name`，没有 `--web-addr`。
    - 接口绑在哪个地址上（只在 macOS 上看过，ngrok 3.39.13，每种配置一次）：`web_addr` 配成下面几种写法时隧道都照常建立，日志里的地址就是配置写的那一个。绑在 `0.0.0.0:<端口>` 或 `[::]:<端口>` 时，在 `127.0.0.1`、`[::1]`、`localhost` 上按名字问都答 200；绑在 `localhost:<端口>` 或 `127.0.0.1:<端口>` 时，在 `127.0.0.1` 与 `localhost` 上答 200、在 `[::1]` 上连接被拒；绑在 `[::1]:<端口>` 时，在 `[::1]` 上答 200、在 `127.0.0.1` 上连接被拒。所以「日志里的主机是回环地址或 `localhost` 时照它问，是全部接口时改问同一地址族的回环地址」这条规则在这几种写法上都问得到。配成这台机器的一个局域网地址时隧道照常建立，本机的直连请求超时，原因没有查明；所以有「接口开着、却不在回环地址上」的配置，现在可用，按设计会启动失败（使用前提第 2 点）。Linux 上没有核（实测项 12）。
    - 参数不被识别时（只在 macOS 上看过一次）：代理以退出码 1 结束，指定的日志文件是空的，标准输出为空，标准错误里是 `ERROR:  unknown flag: …`。所以启动失败的报错另带标准错误的尾部。
    - 版本：`--traffic-policy-file` 从 3.12.1 起有，`--name` 从 3.18.0 起有，`/api/endpoints` 从 3.30.0 起有。三条原话出自 ngrok 的 agent changelog（`https://ngrok.com/docs/agent/changelog/`）：
      - 「ngrok Agent 3.12.1 - [2024-07-11] ... Added --traffic-policy-file flag that accepts Traffic Policy configuration for HTTP, TCP, or TLS traffic. Deprecated --policy-file flag」
      - 「ngrok Agent 3.18.0 - [2024-10-17] Added --name field for endpoints and tunnels when created from the agent config or CLI.」
      - 「ngrok Agent 3.30.0 [2025-09-23] A new agent HTTP API, /api/endpoints, has been introduced that corresponds to the agent config version 3 format」

      所以使用前提的第 3 点是 3.30.0。现在的流量策略（`on_http_request` 阶段的 `custom-response` 动作，`tunnel.py` 的 `_POLICY_TEMPLATE`）连同到点拒绝的一条在 3.30.0 上能不能用，没有核过。
    - 在日志给出的地址上按名字问 `GET /api/endpoints/<名字>`，拆隧道的四种回答按下面这些情形分：
      - 这个代理还在：200，返回的 `name` 与 `url` 都对得上；监听这个端口的进程就是启动时拿到进程号的那个。
      - 问同时开着的另一个代理（另一个端口）：404。
      - 这个代理被强杀之后：连接被拒。
      - 这个代理没了，后来的代理占了同一个端口：404。
      - 这个代理被暂停（SIGSTOP）：不回答，客户端超时。
    - `DELETE /api/endpoints/<名字>` 答 204，端点关闭（之后查是 404），代理进程还在；接口根资源只列出 tunnels、requests、update、status，没有让代理进程退出的资源。所以接口只用来核对，结束代理靠终止信号。
    - 代理收到 SIGTERM 立即退出（退出码 0），之后那个地址连接被拒。所以发信号之后不再确认。
    - 代理退出的过程中去问接口（只在 macOS 上做，ngrok 3.39.13，六轮，每轮六个客户端连续按名字问）：代理收到 SIGTERM 之后约 4 毫秒退出；从发信号到退出这段时间里在途的请求，除了答 200 的，六轮中五轮出现了连接被重置或没有回答就关闭，之后全部是连接被拒。所以同时拆时后到的一方可能得到第 4 种（上「拿不准时」一条）。
    - 代理与 ngrok 边缘断开、重连（只在 Linux 上做过一次：代理运行在容器里，断开容器的网络 60 秒再接回）：期间按名字问一直答 200（只记了状态码）；`/api/status` 给出的代理状态由 `online` 变为 `reconnecting`、接回之后回到 `online`；自始至终是同一个进程，只有一条 `started tunnel`、一个公网地址。实测的那 60 秒里没有出现 404 或连接被拒；更长的断开没有测，不外推。
    - ngrok 配置里写 `web_addr: false` 时（实测用附加配置文件叠加）：隧道照常建立，日志里没有 `starting web service` 一行，没有地址可问。所以启动时就核对，这种配置在启动时就暴露，而不是到拆的时候才发现拆不掉。
    - 公网地址在实测的两个免费账号上不同（都不带 `--url`）：较早注册的免费账号上，两台机器上先后启动的代理每次拿到的地址都不同（`*.ngrok-free.app`），带不带端点名、端点名相同与否都一样；正常停掉之后马上再起、同时开着的两个也各不相同，这两种只在一台机器上看过。新注册的免费账号上（只在 macOS 上做，ngrok 3.39.13，一次），地址是 `ngrok-free.dev` 下的一个固定域名，停掉再起仍是同一个。免费套餐说明页写免费套餐有一个随账号分配的开发域名（「It doesn’t change when you restart the agent」），与新注册的账号一致；实测只有这两个账号，区别是不是出自注册早晚没有依据，文中「较早注册」「新注册」只指这两个账号，写回与用户文档按看得到的行为（地址固定与否）分两种写。两种账号上公网地址都分不出是不是我们这一次启动的代理：前一种每次由服务商分配，后一种同一账号的各次启动都相同。所以公网地址不当作核对的依据（被拒方案「按公网地址核对」）。0035 与用户指南里「账号固定的开发域名、重启不变」的说法只对后一种账号成立（影响清单）。
    - 新注册的免费账号上同时两条隧道（同上一次实测）：第一条在线时，第二个代理按现在的启动方式启动失败，日志的 `err` 是 ``failed to start tunnel: The endpoint '…' is already online. Either 1. stop your existing endpoint first, or 2. start both endpoints with `--pooling-enabled` to load balance between them. ERR_NGROK_334``，标准错误里是同一段话、逐行带 `ERROR:` 前缀（记下的部分截断在错误码之前），代理随后是否退出没有记下；第一条不受影响；第二个代理带 `--pooling-enabled` 同样失败（先起的那一条没有带），两条都带的没有核过。留下一个代理、它的边缘规则已经到点（带 cookie 的请求答 403）时，新的代理同样以 `ERR_NGROK_334` 启动失败（日志的 `err`）。六条规则的策略在这个账号上启动成功（上「边缘到点拒绝」）。较早注册的账号上两条隧道同时在线、地址不同（0035「边界与不变量」「同一 ngrok 账号多条隧道并存」）。所以启动失败多一种说法（「启动」第二种说法），这种用法下的限制见「前提与边界」「同一个账号同一时间只有一条隧道在线」。
    - 容器（只在 Linux 上做：宿主上启动 ngrok 3.39.11，docker 容器里按端点名问同一个接口地址、对记录的进程号做存在性检查）：

      | 容器的拓扑 | `/proc/self/ns/net` 与宿主 | `/proc/self/ns/pid` 与宿主 | 按名字问接口 | 记录的进程号在容器里 |
      |---|---|---|---|---|
      | 缺省网络（bridge） | 不同 | 不同 | 连接被拒 | 不存在 |
      | 与宿主共用网络，进程命名空间各自独立 | 相同 | 不同 | 200 | 不存在（发信号得到「没有这个进程」） |
      | 网络与进程命名空间都与宿主共用 | 相同 | 相同 | 200 | 就是那个代理 |

      所以接口的回答只在启动方的网络命名空间里可信、进程号只在它的进程命名空间里可信：网络不同时问到连接被拒；网络相同而进程命名空间不同时核对通过，信号却发给容器里同号的进程（实测里容器里没有这个进程）。这是「前提与边界」「处置命令要在启动这个 run 的环境里执行」一条的依据。
  - 四种回答按判错的方向排：拿不准的一律不发信号、不标已拆；处置命令拿不准时也不提示，留给之后的处置命令再问。所依赖的前提见「前提与边界」。

## 三种组合的对照

| 情形 | job | 三种组合 |
|---|---|---|
| 被期限截断 | `aborted`、期限那句 | 相同；到了期限加 300 秒推进方还在收尾时见「前提与边界」「期限加 300 秒按墙钟判断」一条 |
| 推进方中断（本机进程退出；云端一次调用失败） | 本机不续、被处置，按说明表「锁拿到了」一行（交接期间提交进程被暂停时按下一行，「前提与边界」）；云端由流的重试与之后的触发接着推进 | 不同，出自决策一、三 |
| 推进停住，过了期限加 300 秒被处置 | 按说明表「已过期限」一行 | 被处置时相同；本机没有人执行处置命令时不结束（「前提与边界」） |
| 保存明细失败，重试成功之前没有被处置 | 照常记下 | 相同 |
| 保存明细一直失败 | 本机重试 3 次之后推进方退出、被处置；云端由流的重试或之后的触发再做 | 不同，出自决策八 |
| 运行定义不可用 | 未结束的 job `error`（决策六） | 两种后台相同（前台没有这种情形） |
| 隧道的宿主（或写下记录之后、交棒之前的启动方）没有走完收尾就退出 | 不涉及，job 与 run 按上面各行 | 相同：run 结束之后，有人在启动它的环境里执行两个处置命令之一时拆（给不给 `run_id` 都算，决策十二「两个处置命令补拆」）；`run --no-report` 没有记录、不补拆；公网入口到期限加 300 秒在边缘关闭（决策十二「边缘到点拒绝」） |

其余情形三种组合相同：job 得出结果或用完预算（终结函数）、到期有 job 没有启动（`skipped`）、启动失败（`error`，0054 已统一）、终态之后到达的结果（不采用）。run 的状态都按决策五取；前台才有的几样见决策一。

## 前提与边界

- **本机文件系统，文件锁有效**：产品边界之内（决策二）保证的前提是 `flock` 对所有读写这个 run 目录的进程按打开的文件描述互斥（运行态的写锁本来就依赖它）。边界之外的共用不在保证之内：两侧的锁（含运行态的短锁）可能互不可见（NFS 上的实测见被拒方案），运行态的写可能互相覆盖。检查放行而在边界之外的：同一块设备挂在两个内核上、两边取到的类型都在清单里；同一个内核里经两个文件系统实例访问同一份数据（实测：容器 overlay 与它的上层目录之间锁互不阻挡）。依赖方：两个本机处置方与「本机至多一个推进方」。
- **边界检查信任内核给出的挂载信息**（macOS 的类型名，Linux 的挂载表与描述符的挂载 ID），不防伪造它的一方，与下一条同类；判断与取锁对同一次打开做。
- 有人改动、删除 run 目录里的文件，以及掉电与内核崩溃（原子写不做 fsync），不在防护之内。
- 持锁的进程启动子进程只经 exec；交接只经启动后台推进进程那一次，接收方核对交来的是这个 run 目录。依赖方：「拿得到锁即管它的进程已不在」与「本机至多一个推进方」。交接期间提交进程也持锁：它在关掉自己那一份之前被暂停时，推进进程退出了也拿不到锁，处置要等到它关掉那一份或退出，或期限加 300 秒。
- **本机没有常驻的处置方**（决策三）：推进方退出或停住、又没有人执行 `status --wait` 或 `settle-runs` 的 run 一直不结束，`list-runs` 照常列出；隧道的宿主没有走完收尾就退出时代理同样留着，公网入口到期限加 300 秒在边缘关闭，见决策十二。
- 本机推进方被暂停期间，它启动的 worker 照常执行、没有人按截止时刻停它们（0054「边界与已知局限」）。
- **期限加 300 秒按墙钟判断，不是推进方收尾时长的上界**：处置方与推进方各读自己的墙钟，本机两者读同一个内核的；云端两者的时钟可能不同，处置方的比推进方慢时处置推迟，快时提前，推进方在期限之后的余量是 300 秒减去快出的量，快出的量超过 300 秒加这个 run 离期限的余量时，仍在期限之内的 run 被结束。停止与落库调用可能阻塞更久（0054 决策二「尾段与余量」一段），被暂停的推进方不受时长约束。到点时结束写只看运行态（决策六）：`running` 的 job 记 `aborted`、`pending` 的记 `skipped`，不论推进方一侧走到哪一步；没写进运行态的结果不论是什么都不再被采用（决策五），run 不会是 `passed`（推进方本会使它通过的也是）。此后的事按既有各条：`run` 的退出码与终端输出按决策四；还会落下哪些明细、报告由谁生成见决策八；留下的执行由谁停见「处置只改记录」一条。
- 云端 `status --wait` 不唤醒推进：推进链断开的 run 由之后的事件或定时触发带起；后端在期限加 300 秒安排到期处置，那次调用确认已过之后把它结束（没有 job 出错或未通过时以 `aborted` 告终，需要重新提交），前提是 `kicker` 收到 STATE 的新建、建成定时触发、那次调用成功。任一环最终失败时不保证后端自行结束它；此后也没有别的后端触发带到这个 run 时，只有用户一侧的处置方能结束它。
- **云端用户一侧的处置方**（`status --wait`、`settle-runs`）要能做 runs 表的条件写、读运行定义与判定明细、写报告；缺后两项时结束写照样写成而这个 run 没有报告。依赖方：被处置的云端 run 有报告。
- 处置只改记录：本机 worker 在推进方退出之后靠核验所属进程自行退出（0024 终止契约，通常十余秒，失效情形见 0054「边界与已知局限」）；前台推进方发现 run 已结束之后对它启动的 worker 发停止（0054 决策五），本机后台推进进程发现之后退出；云端由后端停掉 task。隧道由宿主与两个处置命令另行拆除，不属于处置（决策十二）。
- 运行态本身读不出的 run 无法做条件写，不处置，`status --wait` 只等待并说明原因。
- **隧道代理就是被直接启动的那个进程**（决策十二）：记录的进程号是代理的。被直接启动的进程在核对通过之前退出的，按启动失败挡在启动时；另一种不成立的情形是被启动的是包装程序、代理是它另起的进程而它在核对通过之后才退出或一直在：核对照样通过，信号落在包装程序上，它已退出时进程号可能已被别的进程占用，它还在时代理可能留着。现在按进程号拆的做法已经依赖这一点。
- **处置命令要在启动这个 run 的环境里执行**（决策十二）：两个处置命令的补拆只在启动这个 run 的那个环境里起作用（同一台机器，同一个网络与进程命名空间）；接口地址只在启动方的网络命名空间里有意义，进程号只在它的进程命名空间里有意义（决策十二理由里的容器实测）。这是使用前提，写进用户文档。不满足时：
  - 别的机器（没有把这个端口转发过来）、缺省网络的容器：问到第 3 种，或同一个端口被那里别的程序占着时问到第 4 种，都不发信号、不标已拆、不提示；之后在启动它的环境里执行仍然拆得掉。
  - 问到的回环地址通到启动方的代理而进程命名空间不同（实测的第二种容器拓扑；容器把接口端口发布到宿主的同一个端口，或别的机器把启动方的这个端口转发到自己的同一个端口，如 `ssh -L`，这两种没有实测）：核对通过，终止信号发给这个环境里同号的进程。没有这个进程时得到「没有这个进程」，按第 3 种、不标已拆；有这个进程而没有权限时得到「发信号被拒」，按第 4 种给出提示（决策十二「没有拆成时」），在这个环境里每次执行都再给一次；有这个进程且有权限时就是误发，并且会标已拆，真正的代理留着而记录说已拆。不为它加机制（被拒方案「记下并比较命名空间标识」）。
- **核对与发信号之间不另设防**（决策十二）：核对通过到发出信号之间代理恰好退出、进程号又被别的进程占用时，信号落到别的进程上；间隔极短。本机 `submit` 之后接 `status --wait` 是常规用法，这时宿主与处置命令同时拆是常见的，两个处置命令之间也可能同时拆：两方都可能核对通过、各发一次信号，后一次落在同一个代理上，或落进上面这个间隔；后到的一方也可能问在代理退出的过程中，得到连接被重置或没有回答就关闭（第 4 种，决策十二理由里「代理退出的过程中去问接口」的实测）。后到的是处置命令时不提示；是宿主时多出一句「隧道没有拆掉」的提示，而隧道已经被先到的一方拆了、标记也由它写下，接受，不为它再问一次（被拒方案「拿不准时隔一小段时间再问一次」）。
- **ngrok 的本机接口没有鉴权**（决策十二）：能在记下的接口地址上应答的是这台机器上的程序，含别的用户的（端点名在代理的命令行里，接口端口缺省是 4040 起顺延），它们能冒充回答：冒充 200 会让拆的一方给记录的进程号发信号，冒充 404 会让它不发信号（宿主随之标已拆）。本机上的程序在信任范围内，同一台机器上的别的用户冒充接口不在防护之内，与「边界检查信任内核给出的挂载信息」一条同类。代理在 run 中途自己退出、端口随后被一个不是 ngrok 的程序占用而它答的不是 404 时（第 4 种），宿主给出「隧道没有拆掉」的提示而代理早已不在，标记一直是「否」（决策十二「已拆」标记的代价）。只在回环地址上问（决策十二「启动」），接口不在回环地址上的配置在启动时就失败。
- **404 按代理已不在处理**（决策十二）：404 只说明这个地址上的代理没有这个端点。实测里代理还在而答 404 的只有端点被 `DELETE` 之后（gherkai 不这样做），这时不发信号，代理进程留着、已经没有这个端点；宿主随之标已拆，处置命令不标。代理与 ngrok 边缘断开、正在重连时，实测的那 60 秒里按名字问一直答 200（只看了状态码），没有出现 404 或连接被拒（决策十二理由，只在 Linux 上做过一次），不外推。
- **实测的是 ngrok 3.39.11 与 3.39.13**（决策十二）：使用前提里的 3.30.0 出自 ngrok 的更新记录，3.30.0 本身与更旧的版本上都没有实测（实测项 12）；边缘到点拒绝、新注册账号上的几项、接口绑定地址与代理退出过程中的回答都只在 macOS 的 3.39.13 上做过。接口、端点名、日志里的接口地址、流量策略的时间变量都是 ngrok 的，换隧道服务商时这一块要重做。
- **流量策略的规则已经用满**（决策十二）：加上到点拒绝的一条，每个策略五条，正是较早注册的免费账号实测的上限（新注册的免费账号上六条能启动；免费套餐说明页写 15，与较早注册的账号上的实测不同）。用满是对上限 5 条的账号而言；产品的策略保持在 5 条以内，两种账号都能用。再要加规则，先要合并现有的规则（例如两条答 401 的），没有实测。
- **同一个账号同一时间只有一条隧道在线**（决策十二）：现在的隧道实现用 ngrok；在它的免费套餐、新注册账号（固定开发域名）这种用法下，按产品现在的启动方式（不带 `--pooling-enabled`），同一个账号同一时间只有一条隧道能在线，于是同一时间只能有一个带 `--expose-local` 的 run，留下没拆的代理会让之后带 `--expose-local` 的 run 都起不了隧道（边缘规则到点也一样；起隧道时报「启动」第二种说法，决策十二理由里「新注册的免费账号上同时两条隧道」的实测）。两条都带 `--pooling-enabled` 的没有核过（免费套餐说明页写开发域名上「You can point up to 3 online endpoints at it」）。这是这个服务商在这种用法下的限制，不是 gherkai 的设计：设计上每个 run 一条隧道、彼此无关，服务商经 0035 决策 1 的 `TunnelProvider` 替换。不为它改决策条文，不为它加机制。下「隧道没有人拆的几处」里没有记录的、处置命令不在启动它的环境里执行的、得到第 4 种的，属于别的后端或报告目录的，以及这个账号上不是 gherkai 起的隧道，`settle-runs` 都拆不掉，它们在线时之后带 `--expose-local` 的 run 一直起不了隧道。较早注册的账号上各条隧道地址不同、可以并存（已有实测）；付费套餐与自定义域名下怎样没有核过。0035 的边界与用户指南照此写明（影响清单）。
- **云端建 run 期间不另设防**（决策十二）：云端的隧道条目先于建 run 写下，两者之间（建 run 的先读、卸载 step 参数正文与两次写）这个条目已在专用分组里而 run 还不存在；这时恰有不给 `run_id` 的 `settle-runs` 在同一台机器上列举到它，会按 run 不存在处理、核对通过即拆，这个 run 随后在被测应用不可达下执行。间隔是建 run 的几次调用，不为它加机制。本机在建 run 之后写 `tunnel.json`，没有这段间隔（决策十二「写入的时机」）。
- **边缘规则按提交那台机器的时钟**（决策十二）：策略里的时刻按提交那台机器的墙钟算出，由 ngrok 边缘的时钟比较。本机时钟偏慢超过 300 秒、又在本机执行时，公网入口会在 job 还没有到期限时关闭；云端执行不受影响（云端按自己的时钟在期限截断 job）。不为它再加余量（owner 已定）。
- **本机接口留有经隧道的请求记录**（决策十二）：缺省启动的代理把经隧道转发的请求（地址、请求头、原始字节）留在本机接口的 `GET /api/requests/http` 里，同机的程序读得到；转发的请求带着会话 cookie，cookie 的值因此也在其中（由请求头被记下推出，没有单独核；写回时并进 0051 决策 13 的残留面）。owner 定保留它，以便用 ngrok 自带的页面看隧道里的请求（被拒方案「启动时带 `--inspect=false`」）。macOS 实测一次：带 `--inspect=false` 时请求记录为空，隧道与按名字问照常。
- **隧道没有人拆的几处**（决策十二），每一处公网入口仍在期限加 300 秒在边缘关闭（策略是代理启动时带上的），代理进程留到关机或重启；有记录的几处，之后有人在启动它的环境里执行 `gherkai settle-runs` 时仍能拆掉：
  - 没有记录的：`run --no-report` 的宿主没有走完收尾就退出；启动方在启动代理之后、写下隧道记录之前没有走完收尾就退出（本机是写下 `tunnel.json` 之前，云端是写下隧道条目之前）。
  - 有记录而没有人执行处置命令的：宿主或写下记录之后、交棒之前的启动方没有走完收尾就退出，之后没有人在启动它的环境里执行 `status --wait` 或 `settle-runs`（决策十二「没有人执行处置命令时」）。运行态读不出的 run（决策十一的 `unreadable`）不会被读成已结束，同样不补拆。
  - 处置命令不在启动它的环境里（上面「处置命令要在启动这个 run 的环境里执行」一条）。
  - 宿主与之后的处置命令都得到第 4 种回答（如代理一直被暂停）。

## 被拒方案

- **心跳或租约**：续写本身也会被暂停与时钟偏差打断，判「过期」仍要一段时长。
- **读对方进程的信息**（pid 空间标识、进程启动时刻、进程状态）：Linux 上连续五轮复核每轮都出现新的反例（pid 命名空间、同一滴答里启动的两个进程、时间命名空间的偏移、`/proc` 被换掉或预先绑定挂载），macOS 与 Linux 各要一套取法；锁把同一个问题交给内核回答。
- **机器标识**：会随镜像克隆被复制，认错的方向是把仍在执行的 run 结束；锁只在同一个内核里有意义，不需要它。
- **在 run 目录之外另放锁文件**：锁与 run 目录分处两地，run 目录被移动、复制或换报告目录时两者对不上，还要另定命名与清理。
- **改用 run 目录里的锁文件**（写方式打开）：为网络盘换它也不干净。Linux 的 NFS（同机回环挂载）上没有写委托时四个挂载两两互斥，持锁方有写委托时 v4.2 不共用超级块的挂载之间不互斥，服务端本地路径与各挂载之间两种情形下都不互斥；文件锁的非阻塞试拿有的 10 到 87 秒才返回（服务端刚启动、另一版本的挂载持锁时），有的到 30 秒上限、一次到 6 分钟以上仍未返回（进程被杀为止）。APFS 与 Linux 的 ext4、tmpfs、overlay、绑定挂载上两者各项行为相同（锁文件没有测 `multiprocessing`），目录锁少一个文件，也没有锁文件删掉重建、新旧两份各被一方持有的问题。
- **启动时自检**（拿到锁的一方再开一次 run 目录试取），以及凡取锁之后读回的做法：Linux 的 NFS（v4.2、v3，同机回环挂载）上对只读打开的目录取排他 `flock` 不报错、同一进程再开一次也被挡，锁却只在共用超级块的挂载之间互斥（nosharecache 挂载、另一版本的挂载、服务端本地路径都拿得到）；它只查得出同一进程两次打开是否互斥。
- **macOS 只看本机标志**（`fstatfs` 的 `MNT_LOCAL`）：带这个标志的都放行，含没有照决策二理由实测过的类型（实测 HFS+ 与 FSKit 挂载的 FAT 都带）；owner 定两个平台用同一条规则。
- **由后台推进进程自己建 run 并拿锁，提交进程等它回报**：要另建一条回报通道，提交侧的报错要经它转述；交接用同一把锁覆盖了全程。
- **没有交来锁的后台推进进程自己试拿、拿到即接着推进**：那就是续一个管它的进程已不在的 run（决策三）。
- **本机接力，及其改法**（凭时钟或进程核对判断认领方是否已收尾完，再补写未知退出）：推进方唯一之后没有可接力的对象。
- **云端按 run 串行的队列**：各触发源都要改投到按 run 分组的队列，多一个组件与一跳延迟，还挡不住 `status --wait`、`settle-runs` 这类不经队列的写者，条件写仍要保留。
- **把云端的推进入口收成一个**：同一个函数的多次调用照样并发（流按分片并发，定时触发与退出观察各自唤醒），挡不住重叠；两个入口各过滤自己的触发面。
- **处置只写 run 级、job 保持原样（0054 决策六）**、**到期时未启动的 job 保持 `pending`（0054 决策二）**、**按原因区分到期与中断的 run 级优先序（0054 决策二）**、**run 级在 job 之外单独写一次终态（0030 决定三）**：都要另靠说明解释记录，与 job 的终态分开写正是第二条根因。
- **读取时派生状态**（停在 `pending`、`running` 的 job 加说明另给一个状态）：输出与记录各一套，每个读者都要复刻同一条派生。
- **配置文件设为云端时 `run` 忽略这个值**（提示一句后在本机执行）：「配置写的后端」对 `run` 与 `submit` 含义不再一致，其余命令仍按配置查云端、查不到这个 run。
- **处置方先按事件记下已有结果的 job，再结束其余的**：与云端一致，但本机处置方要推演事件，云端的 `status --wait`、`settle-runs` 要多出读 events 表、写明细的权限，不给则两种云端处置方结果不同。
- **接受明细与终态不对应**（明细照旧每个 job 一份、后写的覆盖先写的）：由执行结果结束的 job，只在云端重叠时 `explain` 与报告配的明细可能出自没写成终态的那一次；由结束写结束的 job，残留明细里的 scenario 与 step 照样当作它的判定列出（如 `aborted` 配全部通过的 step），而不是标为取自事件流。
- **为由结束写结束的 job 补写明细**（写成结束写的一方补写一份只有状态与说明的明细）：补写在结束写之后，run 已是终态、运行态的写不再成立（决策五），这份明细无从被点名，读者不认。
- **保存明细失败时一直重试**（直到写成，或 run 被处置、推进方读到终态停手）：存储一直写不进时不保证 run 结束：执行中的 job 留在 `running`（执行方自己到期只在没有执行中的 job 时做，决策六），推进方仍持锁（前台即 `run` 不退出），只剩期限加 300 秒的处置（磁盘满时它的写同样写不进），本机没有人查看时一直不结束（「前提与边界」）。
- **保存明细失败即退出、不重试**：一次临时的写入失败就丢掉已经得出的结果（决策八重试用完之后的情形），云端同一情形由流的重试记下真实结果。
- **本机后端也起一个专门拆隧道的守护进程**（同云端 `submit` 的隧道守护进程）：它同样会被强杀，问题只是挪了一层；要它被强杀时也有人拆，就要再有一个进程管它，没有尽头。
- **与隧道同生命期的锁**（启动方对一个文件取 `flock`、让代理继承描述符后关掉自己那一份，拆的一方试拿这把锁判断代理在不在）：实测可行，启动方退出之后锁仍在，代理被暂停时仍在，代理结束后释放。但它依赖「代理不关掉、不转交继承来的描述符」，ngrok 没有成文，只能靠实测；起隧道的次序要改到锁文件所在的 run 目录建出之后；推进方自己收尾也要走锁。本机接口是成文的（决策十二理由），做法更少。
- **按记录的进程号直接发信号、不核对**：拆的时候代理可能早已退出（在 run 中途退出，或处置在很久以后、机器重启之后），进程号可能已被不相干的进程占用，会误杀；宿主收尾时同样如此。
- **读进程信息核对它是不是隧道代理**（命令行、启动时间）：各平台取法不同，不是 ngrok 给出的接口；同一类做法用在死活判断上的反例见「读对方进程的信息」一条。
- **只经接口关闭端点、不发信号**：实测 `DELETE` 之后端点关闭而代理进程还在，接口也没有让代理退出的资源。
- **按公网地址核对**：地址由服务商分配，两次启动的地址同不同不由我们决定：较早注册的账号上每次不同，新注册的账号上是一个固定域名、同一账号的各次启动都相同（决策十二理由），都分不出回答的是不是我们这一次启动的那个代理；端点名由我们每次新生成。
- **经 ngrok 云端的 API 停掉代理会话**：要使用者另配 API key。
- **发终止信号之后再问一次、确认代理退出才标已拆**：实测代理收到终止信号立即退出（约 4 毫秒），不为没有观察到的情形加一步。
- **使用者关掉本机接口时照常启动、不核对**：已建立的隧道有了两种拆法。前台 `run` 的宿主是代理的父进程，可以凭进程句柄结束它；后台两种组合与补拆在这种配置下要么按进程号直接发信号（上面「按记录的进程号直接发信号、不核对」一条），要么拆不掉，三种组合不再相同。
- **启动时叠加一份配置把本机接口打开**（`ngrok http` 的 `--config` 可以给多个、合并生效；0035 决策 1 把先用 `ngrok config check` 找到缺省配置、再用 `--config` 叠加临时的 `web_addr` 记作备选）：盖过使用者有意关掉的设置（0035 决策 1 记作要劫持使用者的配置），还要先找到使用者缺省配置的位置。
- **云端的隧道记录放在提交那台机器的本机文件里**：云端 run 没有与它对应的本机位置，要另定一个。试过的系统临时目录与使用者主目录都由写入方与查找方各按当次的环境解析（前者按 `TMPDIR` 一类环境变量，后者按 `HOME`；实测 `Path.home()` 随 `HOME` 变，`HOME` 没设时才查账号数据库），同一台机器、同一个使用者换了环境就找不到，记录还在而处置命令不拆也不提示。
- **问到连接被拒或 404 就删记录（或标已拆）**：这条命令可能不在启动隧道的环境里，删掉的是一份有效的记录。
- **隧道记录经 core 的 RunStore 端口存取**（如由 `create_run` 一并写下，端口另给标已拆与列举）：与 0035「core 对隧道无知（映射在组合根完成）」相抵；记录只有隧道一方读写，放在 runtime 一层，端口、运行定义与运行态都不为它改（决策十二「隧道记录」）。
- **云端只由守护进程拆**：owner 要两个处置命令对云端的 run 同样补拆：它们的范围本来就包括云端后端的 run，守护进程没了就没有人拆，与本机后端不一致。
- **记下并比较命名空间标识**（Linux 上的网络与进程命名空间，另记启动方的平台）：只挡得住一部分（两台 macOS、两个内核的初始标识相同都挡不住），读不到标识、平台不同还要各有规则；不在连接被拒时删记录之后，在另一个环境里执行的主要后果已经没有。
- **端点名里带 run 标识、由之后的命令扫描接口端口找到代理**：要另有一套找接口地址的办法（缺省从 4040 起顺延，使用者可以配成别的）。
- **不设「已拆」标记、不给 `run_id` 的 `settle-runs` 不收隧道**：云端的泄露正是 run 已结束而隧道还在，使用者要先查出 run 的标识才能拆；没有标记时又只能把带过隧道的 run 逐个问。
- **边缘规则的时刻按 job 对齐**：一条隧道只有一份策略、启动时定下，那时还不知道各 job 什么时候开始（决策十二理由）。
- **启动时带 `--inspect=false`**：owner 定保留请求记录（「前提与边界」「本机接口留有经隧道的请求记录」）。
- **改用已弃用的 `/api/tunnels/<名字>` 把版本前提降到 3.18.0**：依赖标着弃用的接口；它在 3.30.0 之前能不能按名字问、对另一个代理与被杀之后怎样回答，都没有核过。
- **把隧道记录放进运行定义、「已拆」标记放进运行态记录**：run 结束之后要改写含运行态的那份记录；云端要列举时仍然得另有一个进索引的条目。
- **拿不准时隔一小段时间再问一次**：为的是不出多余的提示；拿不准的回答不提示之后，再问一次没有用处。
- **手动清除或手动标已拆的入口**（给没有哪一方确知、标记一直是「否」的记录）：多一个使用者可见的入口，换来的只是少几次本机请求；拿不准的回答不提示，这类记录不带来重复的提示（决策十二「已拆」标记的代价）。
- **起隧道遇到地址已在线时，自动拆掉自己留下的隧道再重试**：起 run 的命令多出一份清理的职责；留下的代理可能属于另一个后端或另一个报告目录下的 run，它未必找得到。
- **保留 `--tunnel-ttl`，只允许调小**：调小会在 run 未完时拆掉隧道，剩余 job 在被测应用不可达下以导航失败告终；守护进程的存活上限已由运行期限推出，公网入口到期限加 300 秒在边缘关闭，不需要使用者另给一个时长。
- **云端另设一张表维护隧道记录，或给它另建一个稀疏索引**：现有的状态分组索引已经能列举（实测，决策十二「列举」），不需要多一张表与它的部署、权限；另建索引要多一份索引的定义与部署（CloudFormation 一次更新只能新增或删除一个 GSI，0030 决定六），带隧道的 run 同样各多两次索引写。

## 对既有 ADR 的影响

0054、0034、0031、0030、0027、0016、0040、0041 的相应决策被取代、反转或收窄，另有十一篇的相关条文随之改写；写回哪一篇的哪一节见 [0018](./0018-run-ownership-adr-writeback-plan.md)。

决策十二（隧道由谁拆）是在归位方案之后补的，0018 里还没有它的归位行。0018 里已有的几处隧道条目写于决策十二之前，以决策十二为准：0054 决策七一行的「含处置方据 tunnel.json 拆隧道」，0035 一节的主线（推进器退出之后由处置方拆）、Status 头一行（「兜底拆除」改为由处置方拆除）与决策 3 表一行（local submit 改为由处置方据 tunnel.json 拆）。这些条目里拆的条件是推进器退出、做法是直接据记录拆；决策十二的条件是 run 已结束而隧道记录未标已拆，拆之前在回环地址上按端点名核对，三种组合都写记录，本机与云端相同。下面引的条文都按现在的 ADR 文本检索核过（引的是该处开头的文字）。决策十二改动的条文：

- 0035 决策 1：「协议形状：`start(local_origin, *, timeout_s) -> TunnelInfo`」一条里 `TunnelInfo` 多接口地址与端点名，「+**模块级 `stop_tunnel(pid)`**」与「停止面按 **pid** 而非进程对象/实例方法」换成决策十二拆隧道的做法，「就绪判据 = 轮询 agent 日志到 `started tunnel` 行」加上按名字核对；启动带 `--name`、接口地址只用回环地址、核对不过按启动失败、报错的四种说法与标准错误的尾部按决策十二「启动」；「选择参数：`--tunnel <provider>`」一条的「将来加实现零接口变化」收窄（隧道记录与拆法依赖 ngrok 的本机接口，换服务商时随之改）；「**首发只做 ngrok**」一条的「免费层的两条硬约束已实测：每个策略至多 5 条规则」按账号类型写（较早注册的账号至多 5 条，新注册的账号六条能启动），补上产品的策略保持在 5 条以内、现在五条；「**拿公网 URL 走日志文件通道**」一条里不用本机接口的理由按决策十二理由里的实测改写，「若未来真变，备选 =」一句连同「经 TunnelProvider 口子替换、不动调用方」删去（被拒方案「启动时叠加一份配置把本机接口打开」），「**稳定性权衡**」与解析不到即 fail-loud 的护栏扩到 `starting web service` 一行。
- 0035 决策 2「**`plan` 输出替换前的原始地址**」一条（「ngrok 不带 `--url` 时落在账号固定的开发域名上，不是每 run 随机」）与决策 4「**隧道鉴权：默认开启**」一条（「隧道地址不算保密面（ngrok 不带 `--url` 时落在账号固定的开发域名上，重启不变）」）：只对新注册的账号成立，写回时按账号类型写：新注册的账号是 `ngrok-free.dev` 下的一个固定域名、重启不变，较早注册的账号每次不同（`*.ngrok-free.app`），两种都有实测（决策十二理由里的公网地址一条）；同一条的「安全面不变：每 run 一换的令牌与 cookie + 终态即拆 + 精确比对」加上到点失效。
- 0035 决策 3：表的三行按决策十二改写（三种组合都写隧道记录；`run` 一行「SIGKILL 与处理器装上之前或恢复之后到达的 SIGTERM 不兜」、云端一行「SIGKILL 与处理器装上之前到达的 SIGTERM 不兜」改为指向「边界与不变量」里没有人拆的几处；local `submit` 一行「per-run 进程崩溃时由 `status --wait` 接力者走同一入口、据 `tunnel.json` 兜底拆」改为后台推进进程在退出时拆、宿主没有拆成时由两个处置命令补拆；云端一行「轮询 run 终态即拆 + TTL 兜底自杀」改为到运行期限加 300 秒为止，补拆同本机）；「表外还有一处就地拆，**判据 = 交棒边界**」一条用同一个做法、有记录时标已拆、得到第 4 种时同宿主给出提示，另写启动失败、隧道记录写不成与云端建 run 失败时启动方凭进程句柄结束代理（云端建 run 失败时随后标已拆）；「**隧道 agent 进程自身也 setsid**」一条的「这唯一拆除面」改为这一个做法；表下新增隧道记录（含它的存取在 runtime 一层、两个后端各一个实现）与「已拆」标记、拆隧道的做法、谁在什么时候拆、没有拆成时与补拆成功时的提示、边缘到点拒绝几条，决策十二理由里的实测内联在这里与决策 1。「**TTL 按 definition 算，不是一个常数**」一条整条删去（守护进程到运行期限加 300 秒为止，`--tunnel-ttl` 去掉）：其中「**余量兜什么**」的组成（一次性 900 秒，每 job 210 秒为 60、120、30 三段）与「**公式是按已知组成的估算**」及三条「被拒方案：」、「保留一个给「不超时」job 记账的固定值」是 0054 决策二云端尾段与 900 秒余量的依据，移到 0054 决策二「尾段与余量是预算的取值」一段（那里另有一种推法：云端停止等待预算不超过 140 秒，加排空余量与心跳约预算加 146 秒，取 210 秒），写回时两种说法合成一种。「cloud submit 的语义澄清」一条里打印的「生效的 TTL」改为公网入口在边缘关闭的时刻。
- 0035「边界与不变量」：使用前提三点（写出版本号）；「前提与边界」里标着决策十二的各条（被直接启动的进程、处置命令要在启动这个 run 的环境里执行、核对与发信号之间、本机接口没有鉴权、404 的判读、实测版本、规则已经用满、同一个账号同一时间只有一条隧道在线、云端建 run 期间、边缘规则的时钟、请求记录、没有人拆的几处）。「**同一 ngrok 账号多条隧道并存**」一条按账号类型改写：较早注册的账号上两条同时在线（现有的实测）；新注册的免费账号上第二条以 `ERR_NGROK_334` 启动失败，这是服务商在这种用法下的限制、不是设计的性质，工具仍不加互斥（「前提与边界」「同一个账号同一时间只有一条隧道在线」）。「core 对隧道无知（映射在组合根完成）」一条不动：隧道记录的存取在 runtime 一层，不经 core 的 RunStore 端口（决策十二「隧道记录」）。
- 0035「被拒/被缓方案」：现有四条（CDP 请求拦截喂送、Playwright `exposeNetwork`、cloudflared quick tunnel、AgentCore Browser VPC 模式）之后并入本文「被拒方案」里关于隧道的二十五条（从「本机后端也起一个专门拆隧道的守护进程」到「保留 `--tunnel-ttl`，只允许调小」）；末条「云端另设一张表维护隧道记录，或给它另建一个稀疏索引」归 0030 决定六（见下 0030 一条）。

## 实测项（实装时以真实进程或环境核）

1. macOS 上目录的 `flock` 与目录里文件的 POSIX 记录锁（事件库）互不阻挡（Linux 清单的类型上已核）；`btrfs` 其他子卷与快照里照做决策二理由的各项。
2. 边界检查：Linux 的 NFS 与 FUSE 挂载、macOS 的 SMB、NFS 挂载与 HFS+ 磁盘映像、Docker Desktop 容器里的绑定挂载上，四个命令按决策二处理、`doctor` 那一项不过，报告目录不过时没有留下目录；已有的 run 目录本身是挂载点或符号链接、落在这类文件系统上时不取锁、不写记录。
3. 推进方不在：本机两种推进方各被 SIGKILL 一次（后台的在提交进程退出之后），`status --wait` 下一次轮询即按说明表「锁拿到了」一行处置、有报告、退出码 1，孤儿 worker 释放会话后退出；SIGSTOP 时到期限加 300 秒才处置，SIGCONT 之后推进方的写被拒、停手、不再存明细。
4. 交接：经 CLI 重做决策二理由里交接的各项（锁这一层已核）；交来的描述符不是这个 run 目录时不推进。
5. 期限：三种组合各一个期限落在执行中途的 run，`status --json` 与 `explain` 一致且符合决策七与说明表（内容完整的保留判定）。
6. 只写一次：终态之后到达的退出记录、前台终态写、投影都不改变记录，两个 adapter 对拍；经 Lambda 的代码在真 DynamoDB 上重做决策五的并发与几百个 job 的结束写（按实际的 job 项大小，含点名的标识），只有一方生成报告。
7. 云端到期与清扫：停掉 events 表流的事件源映射、不执行处置命令，到期限时 task 被停，期限加 300 秒之后 run 由后端结束，记下两次触发的到达时刻；流上只有 STATE 的新建与使 run 成为终态的写触发 `kicker`；`settle-runs` 结束的 run、结束之后才启动的 task 都被清扫。
8. 运行定义不可用：云端与本机后台都得到未结束的 job `error`、run `error` 与同一句说明。
9. 保存失败：本机两种推进方各注入一次明细写入失败，重试之后照常记下、点名的是重试所用的标识、进程不退出；一直注入失败时重试 3 次之后进程退出，执行中的 job 留在 `running`，`status --wait` 按说明表「锁拿到了」一行处置。
10. 点名：云端两次调用重叠、各存一份同一个 job 的明细时，`explain` 与报告取到的是写成终态那一方的；本机两种推进方各在存下明细之后、写下终态之前被 SIGKILL，随后被处置时，`explain` 与报告不出现那份明细，`explain` 从事件流补取已执行的 step。
11. 决策十一：本机推进方不在、仍在、另一处置方持锁、被暂停过了期限加 300 秒，run 目录在清单之外、运行态损坏、已结束，云端期限加 300 秒前后，`settle-runs` 的结果与 `list-runs`、`status` 的提示都相符，`--dry-run` 之后锁拿得到。
12. 隧道（决策十二），macOS 与 Linux 上各用真实的 ngrok 代理核，没有注明的两个平台各做一次：
    - 写入：三种组合开始执行之前有隧道记录（带接口地址、端点名，标记为否）；记录写不成时不开始执行、刚启动的代理已结束、退出码 2；云端写下隧道条目之后建 run 失败时代理已结束、条目已标已拆；云端启动方在这两步之间被强杀时，不给 `run_id` 的 `settle-runs` 拆掉并标已拆；较早注册的账号上两个带隧道的 run 同时执行时接口地址不同、各拆各的。
    - 宿主收尾各拆一次并标已拆：前台 `run` 正常结束；本机后台推进进程在 run 到终态与推进中途退出时；云端守护进程在 run 到终态、到运行期限加 300 秒、收到 SIGTERM、收到 SIGHUP 时；宿主收尾时代理已经自己退出（第 3 种）也标已拆。守护进程装配存储出错时经收尾立即拆，这时标记写不成。
    - 补拆：本机与云端各让宿主被 SIGKILL 一次，run 结束之后 `status --wait`、`settle-runs <run_id>`、不给 `run_id` 的 `settle-runs` 各能拆掉、标已拆，stderr 有一句拆掉了哪个 run 的隧道；云端的在另一台机器上执行时不发信号、不标、不提示；`settle-runs --dry-run` 不拆；代理被 SIGSTOP 时宿主给出提示（只有 run、公网地址与 `gherkai settle-runs`），处置命令不拆、不提示；退出码与 `--json` 的 stdout 都不变。
    - 云端：经产品代码重做「列举」的实测（只读到未标已拆的条目，标已拆之后离开索引，两个读者的结果不变）；隧道条目的新建与标已拆不触发 `kicker`（改写之后的流过滤）；`submit`、守护进程与两个处置命令按 0033 配的权限写得成、读得到隧道条目。
    - `web_addr` 的几种写法：回环地址、`localhost`、全部接口在 Linux 上再核一次（macOS 上已核），记下 Linux 上 `localhost` 问到的地址族；局域网地址给出第四种说法；`web_addr: false` 给出第三种说法。
    - 到点前后边缘的回答与规则条数在 Linux 上再核一次；记下代理与边缘重连之后规则是否照常、重连期间按名字问返回的名字与 `url`。
    - 创建时刻先于起隧道取，策略里的时刻等于运行期限加 300 秒，`run --no-report` 同样带这条规则；守护进程到运行期限加 300 秒时拆。
    - 新注册的账号：公网地址固定、同时两条隧道时第二条失败、六条规则能启动，在另一个平台再核一次；经产品代码起第二条隧道时以退出码 2 结束、给出第二种说法，记下代理是否随之退出、标准错误里是否带 `ERR_NGROK_334`。
    - 同时拆（宿主与 `status --wait`、两个处置命令之间）：没有观察到给别的进程发信号；后到的是处置命令时不提示；后到的是宿主时给出一句提示，记下出现的频度。
    - 另一个环境（Linux 上三种容器拓扑，对宿主上启动的隧道执行处置命令）：缺省网络时不发信号、不标已拆；共用网络而进程命名空间各自独立时核对通过、得到「没有这个进程」、不标已拆；网络与进程命名空间都共用时拆掉并标已拆。
    - 3.30.0 上现在的启动命令连同五条规则照常起隧道、会话保护照常（没有实测过）；更旧的版本给出第四种或第一种说法。

## 重议闸门

- **跨机器早于期限判死活**，或**本机后端的报告目录放到网络文件系统上、跨内核共用**成为使用需要时：再议心跳、租约或跨内核的死活判断。
- **没被点名的明细占用的存储成为实际问题**时：再议清理。
- **前台云端执行的需要**（逐步进度、中断）：再议以 `submit` 加等待与取消的组合补上，而不是恢复由本机进程推进的云端 run。
