## 背景与问题

0054 之后的两组设计（本机接力的改法、事件库里解析不了的记录）在复核里不收敛，根因有两条。

- **推进权没有唯一的持有者。** 0034 让谁都可以从事件库重放、接着推进后台 run；本机 `status --wait` 分不清推进进程的死活、一律接力，只能从外面猜。两类外部推断都不成立：「靠时钟加一段固定时长的做法已经三次失守」（0054 决策二「本机接力的改法」，后两种由真实进程复现），凭进程标识核对则每轮复核都有新的反例（被拒方案）。
- **run 的状态与 job 的状态分开写。** run 级在某一刻汇总、单独写一次后冻结，另有三条路不看 job 就结束 run（到期收尾、处置、云端读不到运行定义），于是有「run 已结束而 job 仍是 `pending` 或 `running`」「job 全部通过而 run 是 `error`」，要靠 run 级说明解释记录。

## 决策

### 一、执行组合与推进方

- 执行方式与执行后端的组合有三种：本机前台（`run`）、本机后台（`submit --backend local`）、云端后台（`submit --backend cloud`），下称三种组合。**云端后端只支持 `submit`**：命令行给出 `run --backend cloud` 时以退出码 2 结束并指向 `submit`；配置文件设为云端时与命令行给出时相同，这样的项目每次 `run` 都要显式给出 `--backend local`。前台才有的几样（逐步的进度、`--fail-fast`、使用方中断、网络故障时整个 job 重试）云端暂时没有，后台取消是之后要补的第一项。理由：它是唯一由本机进程推进、执行在云端的组合，云端因它有后端不知推进方死活的 run，0054 决策九为此另设到期处置与各 Lambda 的分流；不支持它，云端的推进方只有后端自己。
- **本机后端的 run 任何时刻至多一个推进方**：前台是执行 `run` 的进程，后台是 `submit` 启动的后台推进进程，都持有它的生命期锁，从建 run 起持有到进程退出（决策二）。认领、启动 job、写 job 的执行中与终态只由它做，结束写（决策六）由它或处置方做。本机 worker 是推进方的子进程，生死系在它身上。
- **云端允许多次 Lambda 调用重叠推进同一个 run**，`kicker`（runs 表流与定时触发）与 `reconciler`（events 表流）两个入口保留，每一步写带条件（决策十）。
- **后台执行标记只作描述**（是否由 `submit` 提交，只进 `list-runs --json` 的 `detached`），不参与任何判断：云端的 run 都由 `submit` 提交，触发过滤与各 Lambda 不看它；处置不分前台与后台（决策十一）。

### 二、生命期锁：加在 run 目录上

- **对象**：run 目录本身。持有方以只读方式打开 `<report-dir>/<run_id>/`、取排他的 `flock`；锁按打开的文件描述计：同一进程另一次打开同样被挡，共用这个打开的进程里有一个还开着，锁就在。
- **谁在何时拿**：
  - `run`（生成记录时）：建出 run 目录、拿到锁之后才写运行定义与运行态，持有到进程退出；锁已被持有时以退出码 2 结束（试拿方只碰运行态已读得出的目录，这只在 run_id 重复时出现）。
  - `submit --backend local`：提交进程不拿锁、不建 run。它启动的后台推进进程同 `run`：建出 run 目录、拿到锁之后才写运行定义与运行态，持有到进程退出；锁已被持有或锁不可用时不建 run，经回报由 `submit` 以退出码 2 结束（次序与回报见决策十二「三种组合的宿主与次序」）。
  - 云端后端没有锁。
- **谁在何时试拿**：等待中的 `status --wait` 在 run 未结束时每次轮询试一次，`settle-runs` 对每个未结束的本机 run 试一次，都只对运行态已读得出的目录；不阻塞，拿到之后持有到这次处置做完。
- **结果的判读**：只有成功算拿到，只有「已被持有」（`EWOULDBLOCK`）算持有者还在；其余错误一律按锁不可用：建 run 的一方以退出码 2 结束，处置的一方只剩期限一条。
- **产品边界：本机后端的报告目录及其中的 run 目录要在本机文件系统上**（检查见下一条）。同一个内核上经同一个挂载或其绑定挂载访问的在边界之内（实测宿主与容器、容器之间）；网络文件系统、经虚拟机共享进来的目录在边界之外（实测 macOS 的 Docker Desktop：宿主目录在容器里是 `fakeowner` 类型、被拒，宿主一侧是 APFS、放行，两侧的锁互不阻挡）；多台机器共用记录用云端后端。用户文档写明并列出清单。
- **边界检查**（本机后端）在取锁与试拿锁的动作里、先于取锁（`run`、本机 `submit` 启动的后台推进进程、等待中的 `status --wait`、`settle-runs`），对要取锁的那个 run 目录的描述符判断；建 run 的一方另在建 run 目录之前对报告目录（不存在时取最近一层已存在的上级）判断一次，这一次被拒时不留目录。类型不在清单里或判断不了（如读不到挂载信息、平台不是 macOS 与 Linux）即以退出码 2 结束，说明写原因（这样的目录上无法确认执行 run 的进程是否还在）、检测到的类型与怎么办（列出清单）。`settle-runs` 在报告目录存在时另查它（不存在即没有可处理的 run，照常结束）；某个 run 目录不过只跳过它、在结果里写明原因（决策十一）。`doctor` 对配置的报告目录做同一判断（本机后端时必修，不碰锁）；其余命令不碰锁，也不查。放行不证明在边界之内、锁有效（「前提与边界」第一条；不靠读回，见被拒方案）。两个平台同一条规则：各处都对打开的目录的描述符取文件系统类型，由内核解析路径（含符号链接、绑定挂载与盖住它的上层挂载；两个平台上实测按挂载表的最长前缀会取到被盖住的那条），只放行清单里的类型；清单只收照决策二理由实测过的，先实测再加：
  - macOS 由 `fstatfs` 取类型名。实测（arm64）：APFS 为 `apfs`，HFS+、FAT 的磁盘映像为 `hfs`、`msdos`，autofs 自动挂载点为 `autofs`。清单：`apfs`。HFS+、FAT 上的锁只核过互斥、同一进程再开被挡、被杀后释放，不进清单。
  - Linux 由描述符的 `mnt_id`（`/proc/self/fdinfo`）在 `/proc/self/mountinfo` 取那一条。实测（内核 7.0）：被盖住、经符号链接、容器里的路径都取到实际所在的挂载，绑定挂载显示源的类型，不存在的目录取上级、与新建后同类型，懒卸载后取不到；NFS 为 `nfs4`、`nfs`。清单：`ext4`、`tmpfs`、`overlay`（宿主与容器上实测）；`xfs`、`btrfs`、`ext3`（回环镜像、缺省选项、`btrfs` 顶层子卷上重做，除数值外与 `ext4` 相同）。
- **不被子进程继承**：描述符不可继承，持锁的进程只经 exec 启动子进程（worker；隧道在宿主进程里、不是子进程，决策十二）。
- 理由：死活由操作系统在进程退出时给出，不需要对方配合，也不靠时钟。真实进程核过（macOS 的 APFS，Linux 清单里的类型与绑定挂载，括注的除外）：被暂停的持有方仍持有，已退出未回收的已释放；fork 而不 exec 的子进程延长持有，`subprocess` 缺省方式启动的不会，`multiprocessing` 以 fork 起的会（Linux 上 Python 3.12、3.13 的缺省）。放弃：POSIX 记录锁（只读打开的目录取不上排他的；按进程计，关掉任一指向该文件的描述符即释放）；长期持有 `.runstate.lock`（读改写用的短锁，长期持有挡住所有写）。

### 三、死活的判断与处置的条件

- 管这个 run 的进程还在不在，由试拿锁回答：拿得到即已不在；被暂停的进程仍持有锁，算还在。
- **管它的进程不在了的 run 不续**：不再认领、不再启动 job，由别的一方把它结束（下称 run 处置，本文单说「处置」都指它；job 到了截止时刻被停下另称 job 到点停止）。能处置的只有：`settle-runs`；等待中的 `status --wait`；云端的 run 另有后端自己到期结束（决策十）；以后的取消命令（条件与对推进方的作用在取消的设计里定）。`list-runs`、不带 `--wait` 的 `status`、`explain` 只读。
- **可以处置的条件是两者之一**：试拿锁拿到了；或当前时刻严格晚于运行期限加 300 秒。云端只有后一条。300 秒给时钟偏差与仍在的推进方按期限自己结束（决策六）留出余量，不是收尾时长的上界（「前提与边界」「期限加 300 秒按墙钟判断」一条）。
- 处置做什么：读运行态，已结束则不动；否则做结束写，写成的一方生成报告（决策八）。处置不推演事件，不替事件里有、运行态里还没有的结果下结论：推进方在 worker 退出之后、写下终态之前中断（云端触发链断开时这段可以很久），处置看到 `running`，记 `aborted`「没有结果」；同一次中断在云端通常由流的重试与之后的触发记下真实结果，三种组合的 job、run 状态与退出码可能不同。

### 四、各命令写什么

| 命令 | 写 |
|---|---|
| `run` | 建 run、认领、job 的执行中与终态、自己到期与 fail-fast、使用方中断时的结束写、报告 |
| `run --no-report` | 不写记录、不拿锁，同一套规则在内存里给出结果 |
| `submit --backend local` | 启动后台推进进程，由它建 run 并推进；自己不拿锁、不建 run、不推进，转述它回报的结果（决策十二） |
| `submit --backend cloud` | 建 run；不推进 |
| 本机后台推进进程、云端 Lambda（`kicker`、`reconciler`） | 本机后台推进进程另拿锁、建 run（决策二）；认领、job 的执行中与终态、自己到期的结束写、报告；云端退出观察者只写退出记录，后端到期结束属于处置 |
| `status --wait`、`settle-runs` | 处置条件成立时做结束写与报告；不认领、不启动、不投影 |
| `list-runs`、不带 `--wait` 的 `status`、`explain` | 只读，不碰锁 |

报告只由使 run 成为终态的写入方生成（决策八）。退出码：`run` 按记录里的 run 状态，`passed` 为 0、其余为 1；处理过使用方中断时按信号取 130 或 143；run 在本次执行结束之前已被别处结束时为 1（不输出汇总与 `--json`，0054 决策五），同时处理过中断时仍按信号取。`status --wait` 一到终态即返回，`passed` 为 0、其余终态为 1（自己处置的同样），被 Ctrl-C 打断为 130；`status` 未结束或 `passed` 为 0、其余终态为 1。开始执行之前的问题与查不到 run 为 2，另有：边界检查不过（四个命令，`settle-runs` 指报告目录）；锁已被持有、锁不可用（只对建 run 的一方，决策二；本机后台的经回报由 `submit` 给出）；本机后台推进进程在回报之前退出（`submit` 给出，这时 run 可能已经建成，决策十二）；`run` 给出云端后端。`submit` 其余不变；`settle-runs` 执行完成为 0，跳过（决策十一）不改变退出码，写入失败为 2。

### 五、job 的终态只写一次，run 的状态只由 job 的终态算出

- job 的状态只前进：`pending`、`running`、终态；终态只写一次，迟到的结果（终态之后才到的退出记录与事件）不被采用。
- **run 的状态**：有 job 未结束时，全部是 `pending` 为 `pending`，否则为 `running`；全部结束时按序取第一条成立的：有 `error` 则 `error`；否则有 `failed` 则 `failed`；否则有 `aborted` 或 `skipped` 则 `aborted`（这个 run 没有执行完）；否则 `passed`。run 是终态当且仅当全部 job 是终态。零个 job 的 run 按取法为 `passed`。
- run 的状态字段没有自己的写入逻辑：每次改变 job 状态的写在同一次写里按取法写 run 状态（云端连同状态分组），使 run 成为终态的那次写同时写下结束时刻；run 一到终态，运行态的任何写都不再成立。依赖方：`status --wait`、`list-runs`、CI 把读到的终态当定论，报告据记录生成。前提：写都经端口的写入口。
- **本机**：所有写入口在 `.runstate.lock` 内读改写，按锁内读到的整份运行态计算。**云端**：运行态条目带写入序号，每次写加一；记下 job 终态的写与结束写以「序号等于读到的值」为条件，写不成即重读再算，且对 `jobs` 整体替换；认领与投影沿用各自的条件（决策十），同样加一。认领计数只作 `status --json` 的诊断键（成功认领的次数）。理由：两个调用各记一个 job 的终态、各自读到对方的 job 未结束时，不加条件会留下「全部 job 已结束、run 仍为 `running`」；按 job 逐个加条件，表达式随 job 数增长，放弃（实测逐个路径写在两百多个 job 时超长）。真实 DynamoDB 上在写入层核过（未经产品代码）：整体替换的表达式长度与 job 数无关，50、300、1000 个 job 都写得成，上限由单条记录的大小上限决定（各种终态轮换的样本，1327 个 job 写成、1335 个被拒）；两个进程以同一序号并发写，每次恰有一个写成，另一个重读重算后写成、恰有一方使 run 成为终态；不加条件时逐个路径写留下上述情形、整体替换丢掉另一方的终态。
- 由此 0031 决定三的过滤名单、空判定集规则与例外不再需要，0034 机制三的两条 run 级钳制成为推论。run 状态会变的情形列在影响清单的 0031 一节；退出码不变：这些变化都在非 `passed` 的终态之间，处理过中断时仍按信号取。

### 六、结束一个 run 只有一种写法

- **结束写**是一次条件写：run 未结束时，把每个未结束的 job 写成终态并各带一句说明，运行态里是 `pending` 的（从未认领，因而没有启动）记 `skipped`，是 `running` 的（已认领而没有结果）记 `aborted`；run 状态按决策五随之成为终态，run 级写下结束的原因与结束时刻。判断只看运行态，不读事件。
- 来路：执行方自己到期（已过停止启动的时刻、没有执行中的 job，余下的都没有启动）；前台的 fail-fast 与使用方中断（执行中的 job 停下、各自得出结果之后，余下没有启动的）；处置；云端后端到期；以后的取消。各来路的条件不变，写法只此一种。
- **运行定义不可用时**（云端推进方读不到可用的运行定义；本机后台推进进程同样处理），同一种写，但每个未结束的 job 记 `error`：这些 job 不是被中途结束，是没法执行；run 随之为 `error`。
- 说明文字：

| 来路 | run 级 | `skipped` | `aborted` |
|---|---|---|---|
| 执行方自己到期 | 已超过允许运行的时间 | 这个 run 已超过允许运行的时间，job 没有启动 | 不出现 |
| fail-fast | 有 job 出错，余下的 job 不再启动（fail-fast） | fail-fast：其他 job 出错，本 job 没有启动 | 不出现 |
| 使用方中断 | 收到中断信号，余下的 job 不再启动 | 收到中断信号，本 job 没有启动 | 不出现 |
| 处置：锁拿到了 | 执行这个 run 的 gherkai 进程已退出 | 执行这个 run 的 gherkai 进程已退出，job 没有启动 | 执行这个 run 的 gherkai 进程已退出，job 没有结果 |
| 处置：已过期限加 300 秒（含云端后端到期） | 已超过允许运行的时间 | 这个 run 已超过允许运行的时间，job 没有启动 | 这个 run 已超过允许运行的时间，job 没有结果 |
| 运行定义不可用 | 读不到定义的原因（0037 决策 7 的几句） | 未结束的 job 都记 `error`，说明同 run 级 | 同左 |

  处置的各句末尾另加「（已记为已结束）」；两个条件同时成立的处置取「锁拿到了」那一行。
- 理由：所有来路一种写法，「run 已结束」与「每个 job 都已结束」同时成立。0054 被拒方案「到期时把未启动的 job 记为 `error` 或 `skipped`」的 `skipped` 一半由此反转（当时拒它是因为后台要新设一种记录，结束写正是那一种）。

### 七、被期限截断的 job 记 `aborted`

- 被 run 的期限截断的 job 记 `aborted`，说明仍是「这个 run 已超过允许运行的时间，job 被中止」；用完自己预算的 job 仍是 `error` 加超时。起作用的截止时刻由记录里的认领时刻、job 的预算与 run 的期限算出（`run_deadline.job_cutoff`，相等时算预算），不看说明；内容完整的 job 照旧不改判（0034 机制二）。
- 终结函数的超时一行按起作用的截止时刻分开：预算为 `ERROR`、`timeout`，期限为 `ABORTED`、无归因。

### 八、判定明细与报告

- **状态的权威是运行态，输出里的状态就是记录里的状态**：`run` 的汇总与 `--json`、`status`、`list-runs`、`explain`、报告里 job 与 run 的状态都取运行态，不在读取时另派生；判定明细对 scenario、step 与归因负责，由执行结果结束的 job 的说明也在明细里。理由：job 的终态只在运行态里写一次，由结束写结束的 job 没有明细，明细的写又不带条件（决策十），只有运行态对每个 job 都有且分出了先后。这收窄了 0027 与词表「判定真值」的「唯一权威」：明细不再是状态的来源与判定接口，给脚本读状态的入口是 `status --json`。收窄的条文（0027 等）见影响清单；按 scope 读明细里状态的 CI 改读 `status --json`；读取权限不改：`status` 先读运行定义的版本头（0037 决策 7），本机运行定义（含隧道访问令牌，0035 决策 5、0051 决策 13）与运行态都是 `0600`、明细是 `0644`（0030 决定三），所以以别的用户身份读报告目录的 CI 只能以同一用户执行 `status --json`，放宽要连运行定义一起、令牌随之可读。云端要有 runs 表的读权限（令牌也在这张表里）。
- **job 的终态点名它的那一份明细**：每次保存明细，写入方生成一个随机的标识，明细存成带这个标识的一份，同一个 job 可以有多份、互不覆盖，本机推进方对同一次保存的重试（下一条）用同一个标识。记下 job 终态的那次条件写（决策五）在这个 job 的记录里同时写下这个标识，即点名，点名随终态只写一次、此后的写原样保留；由结束写结束的 job 不点名。读者只认被点名的那一份：`explain`、报告与其余读回明细的各处都先从运行态取 job 的清单与各自点名的标识，再读那一份，不列举目录或前缀；没被点名的明细不读、不列、不清理。`status --json` 的 `jobs[]` 每项带这个标识（未点名时按运行态的惯例省键）；明细文件的存放形态不是对外的约定，直接读明细文件不再是对外的读法，机器读结果的入口是 CLI 的 `--json`（状态用 `status`，明细用 `explain`）。理由：明细的写不带条件、可能有多份，只有记下终态的那次写分出了先后，由它点名，输出与记录一致就延伸到 scenario、step 与归因，明细的写也不必另带条件。代价：明细的存放形态改变（本机与云端），读明细的一方要先读运行态（跨用户的读者读不到运行态，分不出哪一份被点名）；每个 job 的记录多出标识的长度，单条运行态记录容纳的 job 数相应减少（决策五的样本，实测项 6 重做）。
- **由执行结果结束的 job，明细先于终态写下**：保存成功之后才写终态，所以读到这类 job 的终态时它点名的明细已在。依赖方：`explain` 与报告。保存失败时这个 job 这次不写终态：云端由流的重试或之后的触发再做；本机两种推进方按指数退避重试 3 次（间隔 1、2、4 秒），仍失败即放弃，推进方退出（前台 `run` 以非零退出码结束），执行中的 job（含同一轮已存下明细的）留在 `running`，之后被处置为「进程已退出」那句：描述属实，只是没有说明为什么退出（前台终端里另有存储错误），结果丢失。一时的失败见对照表。后台推进同样逐 job 先存明细、再写终态（一次写可记多个 job）。
- **被点名的那一份就是写成终态的那一方存的**：job 的终态至多写成一次（决策五），写成的一方点名的是自己存下的那一份，与终态出自同一个执行结果（写不成而重读再算时沿用这一份，改用别的结果先另存一份）；云端两次调用重叠、本机期限加 300 秒的处置抢先、推进方恢复之后迟落下的保存，都只多出没被点名的明细。依赖方：`explain` 与报告不把没被采用的结果当成结果展示。由此**报告里的判定由记录确定**：run 到终态之后运行态与被点名的明细都不再变，报告里的状态、scenario、step 与归因不随生成的时机变化。依赖方：只由一方生成一次的报告（决策十）与 `status`、`explain` 一致。
- **执行方得知 run 已结束之后不再存明细**（迟到的结果不被采用）：前台在停手信号成立之后，后台与云端在一轮读到终态之后。run 到终态之后新落下的明细只剩已开始的保存（前台是那一次，后台与云端是那一轮的各个 job），三种组合都有。
- **由结束写结束的 job** 没有执行结果，结束写不写明细、不点名，状态与说明在运行态里；执行方在存明细与写终态之间中断时留下的那一份没被点名、不被读。`explain` 对这类 job 给出运行态里的状态与说明，已经执行过的 step 从事件流补取（0042 决策七；云端只在事件的保留期 7 天之内，0033）。
- **`run --json` 的 `jobs[]`** 列出运行定义里的全部 job，状态与由结束写结束的 job 的说明取运行态；被点名的附上那一份明细的各键，没有的不带。
- **报告**：使 run 成为终态的那次写的写入方（执行方或处置方）在这次写之后从记录（运行态加各 job 被点名的明细）生成，没写成的一方不生成。被处置的本机后台 run 由此照常有明细与报告：明细由推进进程在各 job 结束时写下并点名，报告由处置方生成。这是做法：写入方在生成之前中断则没有报告；事件里有结果而运行态还没有终态的 job 见决策三。

### 九、说明只是描述

run 与 job 上的说明文字不参与任何计算：状态、退出码、是否超时、是否可以处置都不看说明。理由（owner 原话）：一旦对内容有要求，就需要对未来的任何描述都保持这种要求，这本身是坏味道。

### 十、云端后端

- **定时触发**：`kicker` 收到 STATE 条目的新建（META 已先写）时建两次一次性的定时触发。期限那一次对仍在执行的 job 做 job 到点停止、再推进：某个 job 自己的触发缺失、worker 又不出事件时照样在期限被截断（决策七），同本机。期限加 300 秒那一次是**后端到期结束**：run 仍未结束即按决策三处置。建不成时这次调用失败、由流重试（名字确定，重试不重复建）。到点的处理重新读墙钟确认已过，不以收到触发为证据，未过则在这次调用里等到已过（同 job 到点停止的到点复查，0034）；run 已结束时只清扫。
- **清扫**：run 到终态之后，后端按启动时带的 run id 列出仍在执行的 task 逐个停掉（可重复，不写 runs 表；失败时这次调用失败，流触发的由流重试，定时触发的按 Lambda 异步调用的重试）。使 run 成为终态的那次写经流（新映像的状态分组不是 `live` 的 STATE 条目）触发 `kicker` 清扫，过滤命中的只有这一次写（终态之后运行态不再有写，决策五）；没停到的（如之后才启动的，本决策末条）由此后带到这个 run 的任一次调用停掉：worker 的事件、退出记录、定时触发。
- **`status --wait` 不调用 `kicker`**，只盯到终态、条件成立时处置。
- **重叠时各记录靠什么分出先后**：
  - META 条目：只在不存在时写，之后不变。
  - 运行态条目：建 run 要求不存在；认领要求 job 为 `pending` 且 run 未结束；投影要求 HWM 不小于库中值、run 未结束、job 不越过 `running`；记下 job 终态与结束写要求写入序号等于读到的值。每个 job 的终态与 run 的终态各至多写成一次（决策五），条件写不保证最终写成。
  - 判定明细：写不带条件，用哪一份由 job 的终态点名（决策八）。
  - 报告的生成方：只有使 run 成为终态的那次写的写入方，这样的写至多一次；所含判定由记录确定（决策八）。
  - 退出记录：观察到的退出与启动失败的补写覆盖同键，补写的未知退出只在没有记录时写入，之间按最后一次写为准；job 终态写下之后的变化不被采用，两者可能长期不一致，以运行态为准。
  - 定时触发按确定的名字建立，已存在即视为已建。
- **task 的启动不随记录分出先后**：认领成功之后、启动调用完成之前 run 被结束时 task 仍会启动，由后端清扫停掉（0054「边界与已知局限」）。

### 十一、`settle-runs` 与查看命令的提示

- **`settle-runs`**（形态同 0054 决策七）不给 `run_id` 时处理这个后端里全部未结束与运行态读不出的 run，不分前台与后台。每个 run 依次看运行态、边界检查与试拿锁（本机）、期限，`reason` 取第一条成立的：`unreadable`（运行态读不出）、`already_finished`（已结束，含结束写被别处抢先）、`unsupported_filesystem`（run 目录不过边界检查）、`advancer_exited`（锁拿到了）、`past_deadline`（已过期限加 300 秒）、`lock_held`（锁被持有，未必是推进方）、`undetermined`（锁不可用或期限读不出）、`within_deadline`（云端未过期限加 300 秒）。`advancer_exited` 与 `past_deadline` 的 `outcome` 是 `settled`，`--dry-run` 下是 `would_settle`（不写，锁拿到即放开）；其余是 `skipped`。写入失败时就此停止、以退出码 2 结束，再执行一次是安全的：已处置的给 `already_finished`。
- **查看命令的提示**：`list-runs` 与不带 `--wait` 的 `status` 不碰锁，提示只看记录与期限：未结束而已过期限加 300 秒的 run 提示「已超过允许运行的时间（可用 settle-runs 或 status --wait 记为已结束）」，其余不给期限提示（run 级说明照旧）；`list-runs --json` 与 `status --json` 带 `deadline_at`，不另给由它推出的键。等待中的 `status --wait` 在处置条件（决策三）不成立时继续等待：锁被持有不另说明，锁不可用时说明原因。

### 十二、隧道建在宿主进程里：宿主退出，隧道随之消失；公网入口到期限加 300 秒在边缘关闭

- **缺口与做法**：给出 `--expose-local` 时，gherkai 把本机可达的被测应用暴露成公网地址（0035 决策 1）。现在由一个 ngrok 代理进程持有隧道（`NgrokTunnel._launch` 以新会话启动 `ngrok http`），宿主在 run 结束后按进程号拆（`stop_tunnel(pid)`，0035 决策 3 的表）；宿主没有走完收尾就退出（如被 SIGKILL）时代理与公网地址一直留着，而代理是与记录分开的另一样东西，只能从外面推断它在不在（被拒方案「隧道由独立的 ngrok 代理进程持有……」）。改为：隧道是宿主进程里由 ngrok 官方 Python SDK 建立的一个会话，把被测应用转发到一个公网地址，带本 run 的流量策略（0051 决策 13 的四条规则，前面加一条到点拒绝的规则，下「边缘到点拒绝」），策略随调用在内存里交给 SDK、不落盘。不再启动 ngrok 可执行文件，没有代理进程、进程号、本机接口与日志文件；也不提供 ngrok 自带的本机查看页面与请求记录（owner 定不要；1.8.0 的类型声明里没有这一类选项，宿主进程有没有在本机监听端口见实测项 12）。
- **寿命**：宿主怎样退出（正常结束、未捕获的异常、被任何信号结束），隧道都随进程消失；正常路径上宿主先显式关闭会话。没有拆隧道的记录或命令：两个处置命令不涉及隧道（决策十、十一）；处置只改记录，被结束的 run 的宿主发现之后照常退出（三种宿主各自怎样发现，见下「前置条件与启动失败」第 3 种），隧道随之消失。
- **三种组合的宿主与次序**（创建时刻都在起隧道之前取，下「边缘到点拒绝」）：
  - **前台 `run`**：执行它的 CLI 进程。做完现有的各项检查与补全运行定义之后，取创建时刻，起隧道，生成运行定义，建 run（生成记录时，决策二），执行，退出。现在 `_cmd_run` 先起隧道（`_setup_tunnel`）并用 `atexit` 登记按进程号拆，再生成运行定义（`_build_run_meta`）、建 run（`persistence.begin`）。
  - **本机 `submit`**：后台推进进程。`submit` 做完计划与补全运行定义（现有的各项检查、账号比对与安装包上传都在这之前）之后以新会话启动后台推进进程，经它的标准输入把建 run 所需的输入一次交给它，另给它一条通向 `submit` 的回报管道。后台推进进程依次取创建时刻、起隧道、生成运行定义、建 run（含决策二的边界检查与取锁）、建事件库，回报结果并关闭管道（建成了：run 的标识与公网地址；没有建成：原因与退出码，开始执行之前的问题是 2），然后推进到 run 结束、退出。`submit` 收到回报之后输出结果并退出：建成时同现在（进度行，stdout 只有 run 的标识，退出码 0）；没有建成时报出原因、以回报里的退出码结束。由此本机的一个 run 从建立到结束都在一个进程里，前台是 `run` 的进程，后台是后台推进进程，步骤与次序相同。
    - 输出：后台推进进程回报之前的输出接在 `submit` 的标准错误上（`submit` 这时还在等，崩溃的原因直接显示在终端；run 目录这时可能还不存在），回报之后改写进 run 目录里的 `reconcile.log`。
    - `submit` 在收到回报之前退出或被强杀（如按下 Ctrl-C；后台推进进程在另一个会话里，收不到终端的信号）：后台推进进程在建 run 之前查一次回报管道，另一端已经关闭即不建 run，关闭会话、退出。理由：没有人收到 run 的标识，使用者多半是要放弃这次提交；在建 run 之前停下，没有记录要收拾。
    - 这次检查之后 `submit` 才退出：run 已经建成，回报写不出去，后台推进进程照常推进，只在 `reconcile.log` 记一句。理由：建成之后它就是一个有推进器、持着锁的普通 run，与 `submit` 收到回报之后、输出之前被强杀相同；要在这时结束它，结束写就得多一种来路与说明（决策六），只为建 run 的那一刻。它照常出现在 `list-runs` 里。
    - 后台推进进程在回报之前退出：`submit` 读到管道关闭而没有回报，报错、退出码 2，说明 run 可能已经建成而没有推进器、可以用 `gherkai settle-runs` 记为已结束（决策三；锁随进程释放，按说明表「锁拿到了」一行）。
    - `submit` 不另设等待时限：起隧道的时限是 `TunnelProvider` 的 `timeout_s`（SDK 的调用本身不带时限参数，`timeout_s` 怎样截住它、没有外网时 SDK 怎样都还没有核，实测项 12），其余是本机操作；后台推进进程被暂停时 `submit` 一直等，使用者结束 `submit` 即落到上面第二条或第三条（看暂停落在它查回报管道之前还是之后）。
    - 现在（`cli/gherkai_cli/__main__.py`）：`_cmd_submit` 先起隧道（`_setup_tunnel`）、再生成运行定义（`_build_run_meta`）；`_submit_local` 自己建 run（`create_run`）、建事件库、写 `tunnel.json`、开 `reconcile.log`，再以新会话启动 per-run 进程（`_reconcile <run_id>`，入口 `_cmd_reconcile` 调 `detached.drive_local_reconcile`），交给它的只有 run 的标识与几项参数；启动成功之前出错时 `_cmd_submit` 就地拆隧道（`on_handoff` 之前的 `stop_tunnel`）。生命期锁还没有实装，code 里的 `flock` 只有运行态读改写用的 `.runstate.lock`（`LocalRunStore`）。
  - **云端 `submit`**：本机的隧道守护进程。云端的推进器在云上、读不到本机起的隧道，本机必须另有一个进程持有它。`submit` 先过云端的各道闸并补全运行定义（版本、资源 preflight、worker variant、设备请求与安装包，同现在 `_submit_cloud` 在 `create_run` 之前的各步；这些闸现在从运行定义取 job 与有没有预热地址，改为从 job 与有没有给 `--expose-local` 取；版本闸的缺戳例外里「有预热地址」那一半改看有没有给 `--expose-local`，「有 job 的目标不是桌面」那一半照旧从 job 取），再取创建时刻、算出运行期限，以新会话启动守护进程并把到点时刻（运行期限加 300 秒）交给它；守护进程起隧道，把公网地址与预热地址经回报管道交给 `submit`；`submit` 生成运行定义、建 run，把 run 的标识交给守护进程；守护进程轮询 run 的状态（读不出或读不到这个 run 时记一句、继续轮询，同现在），到终态或到运行期限加 300 秒（墙钟，0054 决策二「检查用墙钟」）时关闭会话、退出。
    - 守护进程起不来隧道或在回报之前退出：`submit` 报出原因（后者是管道关闭）、退出码 2，没有建 run。建 run 失败（云端不可达或条件不成立）：`submit` 关闭管道、以退出码 2 结束（同现在），守护进程随之退出。
    - 与本机同一条规则，建 run 的一方在建 run 之前查一次管道：`submit` 查到守护进程那一端已经关闭即不建 run，报错、退出码 2。这次检查之后守护进程才退出：run 已经建成、由云端推进，`submit` 交出标识时写不进管道，照常输出 run 的标识、退出码 0（已提交，0031 决定五），另在 stderr 说明隧道已经不在、这个 run 里要访问被测应用的 job 会失败；与守护进程在 `submit` 退出之后才没了相同（「前提与边界」）。
    - `submit` 在交出 run 的标识之前退出或被强杀：管道关闭，守护进程退出；这时 run 已经建成的，由云端照常推进，要访问被测应用的 job 会失败（同上一条）。
    - 守护进程的存活上限由运行期限推出，不再有它自己的公式（`tunnel_host.compute_watch_ttl_s`：900 秒加各 job 的预算与每 job 210 秒，按单调时钟计）。**`--tunnel-ttl` 去掉**（owner 定）：调大没有意义（期限之后 job 已被截断，到期限加 300 秒公网入口已在边缘关闭），调小会在 run 未完时断掉隧道；参数、`--help`、取值校验的报错与用户文档里讲它的一节随实装删去（影响清单）。
    - 守护进程不再把 SIGTERM、SIGHUP 转成退出（现在 `_cmd_tunnel_watch` 这样做，是为了经 `finally` 拆掉另一个进程里的代理）：缺省处置下进程结束，隧道随之消失（实测）。日志：回报之前接在 `submit` 的标准错误上，收到 run 的标识之后写进系统临时目录里的 `gherkai-tunnel-watch-<run_id>.log`（同现在的文件名）。
    - 现在：`_submit_cloud` 在各道闸与 `create_run` 之后才启动守护进程（`_tunnel_watch`），隧道此前已由 `_cmd_submit` 起好，交给守护进程的是进程号与 TTL（`--tunnel-pid`、`--ttl`）；守护进程每 5 秒读一次运行态（`watch_run_and_stop_tunnel`），读库出错只记一句、继续轮询，到 TTL 才拆。
- **`TunnelProvider` 的口子保留，形状随之变**（逐项对照 0035 决策 1 现文）：「协议形状：`start(local_origin, *, timeout_s) -> TunnelInfo`」里 `start` 多收到点时刻，`TunnelInfo` 去掉 `pid`（余下公网地址、本机源地址、预热地址），返回的对象带一个关闭会话的方法；「+**模块级 `stop_tunnel(pid)`**」去掉。「停止面按 **pid** 而非进程对象/实例方法」反过来：起隧道的进程就是宿主、也是唯一收尾的一方，停止是宿主进程内的动作，不能由别的进程代做。「就绪判据 = 轮询 agent 日志到 `started tunnel` 行」改为 SDK 建立监听的调用返回（实测返回之后的第一个请求即得到策略的回答），「不做持续健康探活」不变。「**拿公网 URL 走日志文件通道**」一条（连同其中的「**稳定性权衡**」与「若未来真变，备选 =」）不再适用，公网地址是 SDK 调用的返回值；其中前置一句改为下「前置条件」，免费层配额一句保留。「**首发只做 ngrok**」一条里服务商要具备的能力多两项（会话建在宿主进程里、随进程消失；流量策略能按时刻拒绝），规则上限按账号写（下「边缘到点拒绝」）。「选择参数：`--tunnel <provider>`」不变。
- **边缘到点拒绝**：
  - 流量策略最前面加一条规则：`timestamp(time.now) >= timestamp('<时刻>')` 成立时直接答 403 与一句固定的说明，不再往后判（`time.now` 是 ngrok 流量策略成文的变量，`https://ngrok.com/docs/traffic-policy/variables/time/`：「The current UTC time in RFC3339 format.」）。时刻是这个 run 的运行期限加 300 秒（0054 决策六里任何一方都可以结束这个 run 的那个时刻）。三种组合都带，`run --no-report` 同样（它也有运行期限）。
  - 时刻怎样得到：现在创建时刻与运行期限在起隧道之后才取（`_build_run_meta`）。改为创建时刻在起隧道之前取一次，运行期限与策略里的时刻都由这一次读数算出，生成运行定义时用同一个值；给不给 `--expose-local` 都在同一位置取。期限要的各 job 预算与停止宽限在起隧道之前都已取得；起隧道的耗时由此计入 0054 决策二的 900 秒一次性余量（影响清单）。
  - 它给出什么、不给什么（这是做法，不是保证）：到点之后公网入口在 ngrok 边缘关闭，不依赖本机的任何进程，带令牌的预热请求同样被拒；到点之后宿主如果还在，会话还在，请求一律答 403。现在令牌在隧道存活期间一直有效（0051 决策 13），这条规则给它加了一个到点失效，对正常结束的 run 同样起作用。时钟的边界见「前提与边界」。
  - 规则条数：现有四条加上它共五条（`tunnel.py` 的 `POLICY_RULE_LIMIT` 是 5、现用 4 条）。较早注册的账号每个策略至多 5 条、正好用满，新注册的账号上六条能建成；产品的策略保持在 5 条以内，两种账号都能用。ngrok 的免费套餐说明页现在写「Traffic policy rules (per policy) 15」，与较早注册的账号上看到的不同。
  - 理由：宿主一直不退出时（被暂停之后恢复、卡在别处），公网入口照样到点关闭；ngrok 自己没有到期释放，免费套餐说明页（`https://ngrok.com/docs/pricing-limits/free-plan-limits/`）原话「Free endpoints have no timeout—they can stay online indefinitely. To keep one running unattended, run it as a background service.」。时刻对齐到 run 而不是 job：一条隧道只有一份策略、启动时定下；各 job 什么时候开始在那时还不知道；运行期限已经是每个 job 截止时刻的上限（0054 决策二第 2 条）。不另加余量（owner 定）。
- **前置条件与启动失败**：
  - 前置：装了 SDK 这个可选依赖；令牌取环境变量 `NGROK_AUTHTOKEN`（SDK 的标准取法；按 1.8.0 的接口声明，只有显式传入与这个环境变量两种取法，不读 ngrok 命令行工具的配置文件；只设环境变量起隧道见实测项 12）。不再要求机器上有 ngrok 可执行文件。
  - 可选依赖的落点：SDK（PyPI 上的包名 `ngrok`）由 runtime 的 `tunnel.py` 导入，按 0037 决策 2c「直接 import 就直接声明」，runtime 加 `[tunnel]`（`ngrok`，下限取实测的 1.8.0），CLI 加 `[tunnel]`（`gherkai-runtime[tunnel]=={{ version }}`），与 `[local]`、`[deploy-aws]` 正交，使用者装 `gherkai[tunnel]`。现在 runtime 只有 `[aws]`，CLI 只有 `[local]` 与 `[deploy-aws]`（两个 `pyproject.toml` 的依赖 hook 表），两个包都要求 Python 3.13 或更新，SDK 要求 3.12 或更新。SDK 只在给了 `--expose-local` 时导入（同本机路径不 import boto3 的懒加载，0037 决策 2c），没给时装不装都没有影响。
  - 两项前置在 `run` 与 `submit` 共用的前置检查里先查（补全运行定义、上传安装包之前），缺了即以退出码 2 结束，不上传、不起后台进程：同现在把配置错挡在「没开始执行就被拒」层的次序（`_plan_and_preflight`）；两种后台宿主由同一个解释器、同一份环境启动，`submit` 查到的就是它们会遇到的。
  - 启动失败的说法按原因分，产品语言，不带内部说法，都以退出码 2 结束（决策四「开始执行之前的问题」）；第 1、2 种在上一条的前置检查里查出，第 3、4 种在起隧道时遇到，本机 `submit` 经后台推进进程的回报、云端经守护进程的回报由 `submit` 报出；不提结束 ngrok 进程（已经没有这个进程）：
    1. 没有装可选依赖：说明怎么装。
    2. 没有令牌：说明设哪个环境变量。
    3. 这个账号的隧道地址已经被另一条在线的隧道占用（SDK 的错误里带 `ERR_NGROK_334`，报错带上这个错误码）：等那条隧道下线之后再试。它通常属于另一个带 `--expose-local` 的 run，隧道在那个 run 的宿主退出时下线；宿主发现 run 已结束之后退出（本机后台推进进程在下一轮读到终态时，云端守护进程在下一次轮询读到终态时或到运行期限加 300 秒时，前台 `run` 在下一次认领、重试之前的读或写 job 状态时，决策五、八），所以 run 已经是终态而隧道还在线一段时间是可能的（云端守护进程读不到 run 的状态时要到运行期限加 300 秒；宿主被暂停时要等它恢复）。在线的隧道也可能不是 gherkai 起的，所以报错说「这个账号上另一条在线的隧道」，不点名 run。报错不提 `gherkai settle-runs`：处置只改记录，隧道在它的宿主退出时才下线。
    4. 其余（没有外网、流量策略被拒等）：「隧道没有建成」，带 SDK 给出的原因。
- 理由：
  - 隧道的寿命就是宿主进程的寿命，由操作系统给出，与生命期锁同一个思路（决策二理由）：宿主怎样退出隧道都随之消失，没有另一样东西可留下，也就不需要记下它、找到它、核对它再拆（被拒方案「隧道由独立的 ngrok 代理进程持有……」）。
  - 本机 `submit` 由后台推进进程自己建 run：隧道要由推进器持有（它没了，run 也没有推进器，两者一起没了），公网地址要在建 run 之前拿到（替换进运行定义里 job 的文本），所以起隧道与建 run 都在后台推进进程里；锁由建 run 的进程从建 run 起持有到退出，交接随之取消，前台与后台是同一种做法（决策二）。回报通道本来就要有：`submit` 要把公网地址、run 的标识或失败原因告诉使用者。
  - 建 run 的一方在建 run 之前查一次管道，本机与云端相同：另一端已经不在时不建，免得留下一个没有人知道、或一开始就没有隧道的 run；查过之后的那一刻不另设防，它与建成之后才没了是同一种情形。
  - 实测（ngrok 官方 Python SDK 1.8.0，Python 3.13；macOS 上新注册的账号与较早注册的账号各一次，Linux（内核 7.0，x86_64）上较早注册的账号一次；没有注明的三次结果相同）：
    - 宿主进程里的隧道带产品现有的四条规则加到点规则共五条，macOS 上约 1 秒建成（1.09 秒、0.97 秒），Linux 上 0.29 秒；没有 cookie 的请求答 401，带令牌的预热请求答 200 并下发 cookie，带 cookie 的请求转发到本机应用。
    - 宿主被 SIGKILL 或 SIGTERM 之后，公网请求得到「端点不在线」（404，`ERR_NGROK_3200`）：macOS 上第一次请求就是，Linux 上第一次请求是连接被对端关闭、0.5 秒内转为 404。SDK 的发行包里没有 ngrok 代理的可执行文件，只有 Python 文件、一个原生扩展与一个 `ngrok-asgi` 入口脚本（查看 macOS 上装好的 1.8.0 的文件清单）。
    - 宿主主线程在忙循环里（占着解释器锁）时，8 个带 cookie 的请求全部正常转发。
    - 宿主被暂停（SIGSTOP）45 秒：公网请求先超时（客户端时限 20 秒），下一次请求（约 23 秒时）macOS 上得到 404，Linux 上先答 503（`ERR_NGROK_3004`）、27 秒时转为 404；恢复后 2 秒内重新在线、带 cookie 的请求照常转发。
    - 到点规则经 SDK 生效：到点之后带 cookie 的请求答 403。
    - 同一账号第二条隧道：新注册的账号上建不成，SDK 抛出的错误里带 `ERR_NGROK_334`（地址已在线）；较早注册的账号上建成、地址不同。
    - 六条规则：较早注册的账号上建不成，错误里带 `ERR_NGROK_2264`（每个策略至多 5 条）；新注册的账号上建成。
    - 请求耗时（macOS，新注册的账号，同一个本机应用，各 10 个请求，一次）：经 ngrok 可执行文件（3.39.13）成功 9 个、中位数 1.64 秒，经 SDK 成功 8 个、中位数 1.73 秒；没有成功的几个，原因没有记下。
    - 发行包（PyPI 上的 1.8.0）：许可 MIT 或 Apache-2.0，没有别的依赖，要求 Python 3.12 或更新；有 macOS（x86_64、arm64 与通用包）、Linux（glibc 的 x86_64、aarch64、armv7l，musl 的 x86_64、aarch64）、Windows 的预编译包，每个 3 到 7 MB，装好之后约 17 MB（macOS arm64）。本机后端的两个平台都有预编译包。
    - 没有核过的：长时间运行、宿主断网之后重连、SDK 与 CLI 进程里别的线程长期共存（实测项 12）。
  - 用 ngrok 可执行文件做、仍然有用的实测（macOS，ngrok 3.39.13，各一次）：较早注册的账号上五条规则的策略照常建立，到点之后所有请求答 403，带令牌的预热请求也是、不下发 cookie（按本机时钟，记下的第一个 403 是过点后 1.7 秒发出、2.9 秒收到回答的请求），六条规则以 `ERR_NGROK_2264` 启动失败；新注册的账号上地址是 `ngrok-free.dev` 下的一个固定域名、停掉再起不变，第一条在线时第二条以 `ERR_NGROK_334` 失败（只给第二条加 `--pooling-enabled` 同样失败，两条都加的没有核过），第一条的边缘规则已经到点而它仍在线时同样失败，六条规则能建成；较早注册的账号上每次启动的地址不同（`*.ngrok-free.app`）。

## 三种组合的对照

| 情形 | job | 三种组合 |
|---|---|---|
| 被期限截断 | `aborted`、期限那句 | 相同；到了期限加 300 秒推进方还在收尾时见「前提与边界」「期限加 300 秒按墙钟判断」一条 |
| 推进方中断（本机进程退出；云端一次调用失败） | 本机不续、被处置，按说明表「锁拿到了」一行；云端由流的重试与之后的触发接着推进 | 不同，出自决策一、三 |
| 推进停住，过了期限加 300 秒被处置 | 按说明表「已过期限」一行 | 被处置时相同；本机没有人执行处置命令时不结束（「前提与边界」） |
| 保存明细失败，重试成功之前没有被处置 | 照常记下 | 相同 |
| 保存明细一直失败 | 本机重试 3 次之后推进方退出、被处置；云端由流的重试或之后的触发再做 | 不同，出自决策八 |
| 运行定义不可用 | 未结束的 job `error`（决策六） | 两种后台相同（前台没有这种情形） |
| 隧道（给了 `--expose-local`） | 宿主中途没了：本机的宿主就是推进方，按「推进方中断」一行；云端的 run 照常推进，要访问被测应用的 job 失败（「前提与边界」） | 宿主退出时隧道随之消失、公网入口到运行期限加 300 秒在边缘关闭，三种组合相同（决策十二）；宿主中途没了时不同，出自决策一（云端的推进器不在本机） |

其余情形三种组合相同：job 得出结果或用完预算（终结函数）、到期有 job 没有启动（`skipped`）、启动失败（`error`，0054 已统一）、终态之后到达的结果（不采用）。run 的状态都按决策五取；前台才有的几样见决策一。

## 前提与边界

- **本机文件系统，文件锁有效**：产品边界之内（决策二）保证的前提是 `flock` 对所有读写这个 run 目录的进程按打开的文件描述互斥（运行态的写锁本来就依赖它）。边界之外的共用不在保证之内：两侧的锁（含运行态的短锁）可能互不可见（NFS 上的实测见被拒方案），运行态的写可能互相覆盖。检查放行而在边界之外的：同一块设备挂在两个内核上、两边取到的类型都在清单里；同一个内核里经两个文件系统实例访问同一份数据（实测：容器 overlay 与它的上层目录之间锁互不阻挡）。依赖方：两个本机处置方与「本机至多一个推进方」。
- **边界检查信任内核给出的挂载信息**（macOS 的类型名，Linux 的挂载表与描述符的挂载 ID），不防伪造它的一方，与下一条同类；判断与取锁对同一次打开做。
- 有人改动、删除 run 目录里的文件，以及掉电与内核崩溃（原子写不做 fsync），不在防护之内。
- 持锁的进程启动子进程只经 exec；锁只在建 run 的那个进程里，不在进程之间传递。依赖方：「拿得到锁即管它的进程已不在」与「本机至多一个推进方」。
- **本机没有常驻的处置方**（决策三）：推进方退出或停住、又没有人执行 `status --wait` 或 `settle-runs` 的 run 一直不结束，`list-runs` 照常列出。
- 本机推进方被暂停期间，它启动的 worker 照常执行、没有人按截止时刻停它们（0054「边界与已知局限」）。
- **期限加 300 秒按墙钟判断，不是推进方收尾时长的上界**：处置方与推进方各读自己的墙钟，本机两者读同一个内核的；云端两者的时钟可能不同，处置方的比推进方慢时处置推迟，快时提前，推进方在期限之后的余量是 300 秒减去快出的量，快出的量超过 300 秒加这个 run 离期限的余量时，仍在期限之内的 run 被结束。停止与落库调用可能阻塞更久（0054 决策二「尾段与余量」一段），被暂停的推进方不受时长约束。到点时结束写只看运行态（决策六）：`running` 的 job 记 `aborted`、`pending` 的记 `skipped`，不论推进方一侧走到哪一步；没写进运行态的结果不论是什么都不再被采用（决策五），run 不会是 `passed`（推进方本会使它通过的也是）。此后的事按既有各条：`run` 的退出码与终端输出按决策四；还会落下哪些明细、报告由谁生成见决策八；留下的执行由谁停见「处置只改记录」一条。
- 云端 `status --wait` 不唤醒推进：推进链断开的 run 由之后的事件或定时触发带起；后端在期限加 300 秒安排到期处置，那次调用确认已过之后把它结束（没有 job 出错或未通过时以 `aborted` 告终，需要重新提交），前提是 `kicker` 收到 STATE 的新建、建成定时触发、那次调用成功。任一环最终失败时不保证后端自行结束它；此后也没有别的后端触发带到这个 run 时，只有用户一侧的处置方能结束它。
- **云端用户一侧的处置方**（`status --wait`、`settle-runs`）要能做 runs 表的条件写、读运行定义与判定明细、写报告；缺后两项时结束写照样写成而这个 run 没有报告。依赖方：被处置的云端 run 有报告。
- 处置只改记录：本机 worker 在推进方退出之后靠核验所属进程自行退出（0024 终止契约，通常十余秒，失效情形见 0054「边界与已知局限」）；前台推进方发现 run 已结束之后对它启动的 worker 发停止（0054 决策五），本机后台推进进程发现之后退出；云端由后端停掉 task。
- 运行态本身读不出的 run 无法做条件写，不处置，`status --wait` 只等待并说明原因。
- **宿主被暂停**（决策十二）：请求不再转发到本机，恢复后重新在线；暂停期间与恢复时公网一侧的回答见决策十二理由里的实测「宿主被暂停（SIGSTOP）45 秒」一条，公网一侧从什么时候开始答不在线没有测到；宿主所在的机器休眠、断网时怎样没有核过（实测项 12）。这期间访问被测应用的 job 会失败。
- **云端的守护进程没了**（被强杀、本机关机，决策十二）：隧道随之消失，云端的 run 照常推进，之后要访问被测应用的 job 会失败。这与现在代理中途没了的后果相同（0035「边界与不变量」「本机关机/断网」一条）。
- **同一个账号同一时间只有一条隧道在线**（决策十二）：现在的隧道实现用 ngrok；在它的免费套餐、新注册账号（固定开发域名）这种用法下，同一个账号同一时间只有一条隧道能在线（实测：第二条以 `ERR_NGROK_334` 建不成）。起隧道时遇到它的 run 怎样报错、使用者怎么办，按决策十二「启动失败的说法按原因分」一条的第 3 种说法，这里不另作概括。这是这个服务商在这种用法下的限制，不是 gherkai 的设计：设计上每个 run 一条隧道、彼此无关，服务商经 0035 决策 1 的 `TunnelProvider` 替换。较早注册的账号上各条隧道地址不同、可以并存（实测）；付费套餐与自定义域名下怎样没有核过。0035 的边界与用户指南照此写明（影响清单）。
- **流量策略的规则在上限 5 条的账号上已经用满**（决策十二）：加上到点拒绝的一条，每个策略五条，正是较早注册的账号实测的上限（新注册的账号上六条能建成；免费套餐说明页写 15）。产品的策略保持在 5 条以内，两种账号都能用；再要加规则，先要合并现有的规则（例如两条答 401 的），没有实测。
- **边缘规则按起隧道那台机器的时钟**（决策十二）：策略里的时刻按起隧道那台机器的墙钟算出（三种组合都是使用者的机器），由 ngrok 边缘的时钟比较；job 由执行它的一方（本机或云端的推进器）按自己的时钟在期限截断。执行方的时钟比边缘的慢得超过 300 秒时，公网入口会在 job 还没有到期限时关闭。不为它再加余量（owner 已定）。
- **SDK 是带原生库的包，实测的是 1.8.0**（决策十二）：长时间运行、断网之后的重连、与 CLI 进程里别的线程长期共存都没有核（实测项 12）。流量策略的时间变量、规则上限与「地址已在线」的错误都是 ngrok 的，换隧道服务商时这一块要重做。

## 被拒方案

- **心跳或租约**：续写本身也会被暂停与时钟偏差打断，判「过期」仍要一段时长。
- **读对方进程的信息**（pid 空间标识、进程启动时刻、进程状态）：Linux 上连续五轮复核每轮都出现新的反例（pid 命名空间、同一滴答里启动的两个进程、时间命名空间的偏移、`/proc` 被换掉或预先绑定挂载），macOS 与 Linux 各要一套取法；锁把同一个问题交给内核回答。
- **机器标识**：会随镜像克隆被复制，认错的方向是把仍在执行的 run 结束；锁只在同一个内核里有意义，不需要它。
- **在 run 目录之外另放锁文件**：锁与 run 目录分处两地，run 目录被移动、复制或换报告目录时两者对不上，还要另定命名与清理。
- **改用 run 目录里的锁文件**（写方式打开）：为网络盘换它也不干净。Linux 的 NFS（同机回环挂载）上没有写委托时四个挂载两两互斥，持锁方有写委托时 v4.2 不共用超级块的挂载之间不互斥，服务端本地路径与各挂载之间两种情形下都不互斥；文件锁的非阻塞试拿有的 10 到 87 秒才返回（服务端刚启动、另一版本的挂载持锁时），有的到 30 秒上限、一次到 6 分钟以上仍未返回（进程被杀为止）。APFS 与 Linux 的 ext4、tmpfs、overlay、绑定挂载上两者各项行为相同（锁文件没有测 `multiprocessing`），目录锁少一个文件，也没有锁文件删掉重建、新旧两份各被一方持有的问题。
- **启动时自检**（拿到锁的一方再开一次 run 目录试取），以及凡取锁之后读回的做法：Linux 的 NFS（v4.2、v3，同机回环挂载）上对只读打开的目录取排他 `flock` 不报错、同一进程再开一次也被挡，锁却只在共用超级块的挂载之间互斥（nosharecache 挂载、另一版本的挂载、服务端本地路径都拿得到）；它只查得出同一进程两次打开是否互斥。
- **macOS 只看本机标志**（`fstatfs` 的 `MNT_LOCAL`）：带这个标志的都放行，含没有照决策二理由实测过的类型（实测 HFS+ 与 FSKit 挂载的 FAT 都带）；owner 定两个平台用同一条规则。
- **`submit` 建 run、拿锁，启动后台推进进程时把锁交给它**（0054 决策三现在的写法）：隧道要由后台推进进程持有、公网地址要在建 run 之前拿到（决策十二），回报通道本来就要有，交接不再省下什么；交接期间锁在不是推进器的进程手里，它在关掉自己那一份之前被暂停时，推进进程退出了也拿不到锁，处置要等它关掉那一份或退出。交接本身可行（实测，macOS 的 APFS、Linux 的 ext4：交出方关掉自己那一份之后锁仍在、接收方被杀即释放；交出方显式解锁连同接收方的一并解开；对交来的持锁打开、或一个没被锁的别的文件再取锁都立即成立，所以接收方要先核对对象）。
- **`submit` 仍然建 run，把锁经套接字传给先启动的后台推进进程**：交接还在，交接期间仍有两个进程持锁，两个进程互相等对方的产出（`submit` 等公网地址，后台推进进程等锁）。实测锁在传递之后保持（目录上的排他 `flock`，描述符经 UNIX 套接字传给已在运行的进程，发送方关掉自己那一份之后仍被持有、接收方关掉之后释放；macOS 与 Linux 各一次），可行但不取。
- **后台推进进程接手一个已经建成的 run**（试拿它的锁、拿到即接着推进）：那就是续一个管它的进程已不在的 run（决策三）。
- **本机接力，及其改法**（凭时钟或进程核对判断认领方是否已收尾完，再补写未知退出）：推进方唯一之后没有可接力的对象。
- **云端按 run 串行的队列**：各触发源都要改投到按 run 分组的队列，多一个组件与一跳延迟，还挡不住 `status --wait`、`settle-runs` 这类不经队列的写者，条件写仍要保留。
- **把云端的推进入口收成一个**：同一个函数的多次调用照样并发（流按分片并发，定时触发与退出观察各自唤醒），挡不住重叠；两个入口各过滤自己的触发面。
- **处置只写 run 级、job 保持原样（0054 决策六）**、**到期时未启动的 job 保持 `pending`（0054 决策二）**、**按原因区分到期与中断的 run 级优先序（0054 决策二）**、**run 级在 job 之外单独写一次终态（0030 决定三）**：都要另靠说明解释记录，与 job 的终态分开写正是第二条根因。
- **读取时派生状态**（停在 `pending`、`running` 的 job 加说明另给一个状态）：输出与记录各一套，每个读者都要复刻同一条派生。
- **配置文件设为云端时 `run` 忽略这个值**（提示一句后在本机执行）：「配置写的后端」对 `run` 与 `submit` 含义不再一致，其余命令仍按配置查云端、查不到这个 run。
- **处置方先按事件记下已有结果的 job，再结束其余的**：与云端一致，但本机处置方要推演事件，云端的 `status --wait`、`settle-runs` 要多出读 events 表、写明细的权限，不给则两种云端处置方结果不同。
- **接受明细与终态不对应**（明细照旧每个 job 一份、后写的覆盖先写的）：由执行结果结束的 job，只在云端重叠时 `explain` 与报告配的明细可能出自没写成终态的那一次；由结束写结束的 job，残留明细里的 scenario 与 step 照样当作它的判定列出（如 `aborted` 配全部通过的 step），而不是标为取自事件流。
- **为由结束写结束的 job 补写明细**（写成结束写的一方补写一份只有状态与说明的明细）：补写在结束写之后，run 已是终态、运行态的写不再成立（决策五），这份明细无从被点名，读者不认。
- **保存明细失败时一直重试**（直到写成，或 run 被处置、推进方读到终态停手）：存储一直写不进时不保证 run 结束：执行中的 job 留在 `running`（执行方自己到期只在没有执行中的 job 时做，决策六），推进方仍持锁（前台即 `run` 不退出），只剩期限加 300 秒的处置（磁盘满时它的写同样写不进），本机没有人查看时一直不结束（「前提与边界」）。
- **保存明细失败即退出、不重试**：一次临时的写入失败就丢掉已经得出的结果（决策八重试用完之后的情形），云端同一情形由流的重试记下真实结果。
- **隧道由独立的 ngrok 代理进程持有，留下时由处置命令按隧道记录补拆**（连同它带出的隧道记录与「已拆」标记、拆之前在回环地址上按端点名问代理的本机接口、按进程号发信号、云端借用状态分组索引列举、本机接口的使用前提）：记录与进程是分开的两样东西，记录只能在确知时写，代理自己没了的记录会一直留着；问到连接被拒分不出「代理没了」与「这条命令不在启动它的环境里」，在别的环境里执行有误发信号的可能。依据（ngrok 3.39.13 在 macOS、3.39.11 在 Linux）：按端点名问接口，代理在时答 200，问另一个代理或端口被后来的代理占用时答 404，代理被强杀之后连接被拒，代理被暂停时不回答；Linux 的容器里，缺省网络下问到连接被拒，与宿主共用网络而进程命名空间各自独立时核对通过、记录的进程号在容器里却不存在（发信号得到「没有这个进程」）；代理被暂停 12 秒时公网一侧仍按在线回答，34 秒时与它已退出时相同（macOS，两种账号各一次）。
- **经 ngrok 云端的 API 查端点、远程让代理退出**：要另配一个账号级的 API key；代理仍是独立进程。
- **保留 ngrok 可执行文件、由宿主直接启动并把它的寿命绑在宿主上**：代理仍是另一个进程，要它随宿主退出得另靠操作系统的机制，各平台有没有、怎样用没有核过；会话建在宿主进程里不需要这一层。
- **本机 `submit` 也用一个单独的隧道守护进程**（同云端 `submit`）：多一个进程；隧道的寿命是守护进程的而不是推进器的，推进器没了之后要靠它自己发现才退出。
- **建 run 之后才起隧道、公网地址在启动 job 时再替换**：云端做不到（云端的推进器读不到本机起的隧道，地址必须在运行定义里），本机与云端就成了两种做法；隧道起不来要等到 run 建成之后才报。
- **边缘规则的时刻按 job 对齐**：一条隧道只有一份策略、启动时定下，那时还不知道各 job 什么时候开始（决策十二「边缘到点拒绝」）。
- **保留 `--tunnel-ttl`，只允许调小**：调小会在 run 未完时断掉隧道，剩余 job 在被测应用不可达下以导航失败告终；守护进程的存活上限已由运行期限推出，公网入口到期限加 300 秒在边缘关闭，不需要使用者另给一个时长。

## 实测项（实装时以真实进程或环境核）

1. macOS 上目录的 `flock` 与目录里文件的 POSIX 记录锁（事件库）互不阻挡（Linux 清单的类型上已核）；`btrfs` 其他子卷与快照里照做决策二理由的各项。
2. 边界检查：Linux 的 NFS 与 FUSE 挂载、macOS 的 SMB、NFS 挂载与 HFS+ 磁盘映像、Docker Desktop 容器里的绑定挂载上，四个命令按决策二处理、`doctor` 那一项不过，报告目录不过时没有留下目录；已有的 run 目录本身是挂载点或符号链接、落在这类文件系统上时不取锁、不写记录。
3. 推进方不在：本机两种推进方各被 SIGKILL 一次，`status --wait` 下一次轮询即按说明表「锁拿到了」一行处置、有报告、退出码 1，孤儿 worker 释放会话后退出；SIGSTOP 时到期限加 300 秒才处置，SIGCONT 之后推进方的写被拒、停手、不再存明细。
4. 本机后台的 run 自建立起锁就在后台推进进程手里：经 CLI 提交，run 目录里出现运行态之后、后台推进进程退出之前的任何时刻（含 `submit` 退出之前与之后）别的进程试拿都得到「已被持有」（决策二「谁在何时拿」：「持有到进程退出」）；后台推进进程被 SIGKILL 之后即拿得到。
5. 期限：三种组合各一个期限落在执行中途的 run，`status --json` 与 `explain` 一致且符合决策七与说明表（内容完整的保留判定）。
6. 只写一次：终态之后到达的退出记录、前台终态写、投影都不改变记录，两个 adapter 对拍；经 Lambda 的代码在真 DynamoDB 上重做决策五的并发与几百个 job 的结束写（按实际的 job 项大小，含点名的标识），只有一方生成报告。
7. 云端到期与清扫：停掉 events 表流的事件源映射、不执行处置命令，到期限时 task 被停，期限加 300 秒之后 run 由后端结束，记下两次触发的到达时刻；流上只有 STATE 的新建与使 run 成为终态的写触发 `kicker`；`settle-runs` 结束的 run、结束之后才启动的 task 都被清扫。
8. 运行定义不可用：云端与本机后台都得到未结束的 job `error`、run `error` 与同一句说明。
9. 保存失败：本机两种推进方各注入一次明细写入失败，重试之后照常记下、点名的是重试所用的标识、进程不退出；一直注入失败时重试 3 次之后进程退出，执行中的 job 留在 `running`，`status --wait` 按说明表「锁拿到了」一行处置。
10. 点名：云端两次调用重叠、各存一份同一个 job 的明细时，`explain` 与报告取到的是写成终态那一方的；本机两种推进方各在存下明细之后、写下终态之前被 SIGKILL，随后被处置时，`explain` 与报告不出现那份明细，`explain` 从事件流补取已执行的 step。
11. 决策十一：本机推进方不在、仍在、另一处置方持锁、被暂停过了期限加 300 秒，run 目录在清单之外、运行态损坏、已结束，云端期限加 300 秒前后，`settle-runs` 的结果与 `list-runs`、`status` 的提示都相符，`--dry-run` 之后锁拿得到。
12. 隧道（决策十二），经产品代码、用真实的 ngrok 账号，没有注明的 macOS 与 Linux 各做一次：
    - 三种组合（含 `run --no-report`）经真实的 run 起隧道并执行通过。
    - 三种宿主各被 SIGKILL 一次：公网一侧随即不在线，没有留下与隧道有关的进程（worker 见「前提与边界」「处置只改记录」一条）。
    - 本机 `submit` 的回报：建成、起隧道失败、报告目录不合要求各一次，`submit` 的输出与退出码符合决策十二；后台推进进程的输出符合决策十二本机 `submit` 下「输出」一条：回报之前「接在 `submit` 的标准错误上」，回报之后「改写进 run 目录里的 `reconcile.log`」。
    - `submit` 在收到回报之前被强杀：落在后台推进进程查回报管道之前时，它没有建 run、已经退出；落在之后时，run 照常推进、`reconcile.log` 里有一句，进程不因回报写不出去而退出；记下两个平台上它怎样查到回报管道的另一端已经关闭。
    - 后台推进进程在回报之前被强杀：`submit` 的报错与退出码符合决策十二「后台推进进程在回报之前退出」一条；run 已经建成时，`settle-runs` 按说明表「锁拿到了」一行结束它。
    - 云端守护进程在 `submit` 交出 run 的标识之前、之后各被强杀一次：之前时 `submit` 不建 run 并以退出码 2 结束，或输出 run 的标识与那句说明、退出码 0（看强杀落在检查之前还是之后，记下）；之后时 run 照常推进、要访问被测应用的 job 失败。`submit` 在交出标识之前被强杀时守护进程退出。
    - 守护进程退出的时机符合决策十二「云端 `submit`」一条里「守护进程轮询 run 的状态」那一句，读到终态与到运行期限加 300 秒两条路径各一次；之后公网一侧不在线。
    - 到点前后边缘的回答：到点之前预热与带 cookie 的请求照常；到点之后「宿主如果还在，会话还在，请求一律答 403」（决策十二「它给出什么、不给什么」一条），让宿主在过点之后仍在的办法实装时定、记下；策略里的时刻等于运行期限加 300 秒，创建时刻先于起隧道取。
    - 新注册的账号上第二个带隧道的 run：以退出码 2 结束，给出第 3 种说法（本机 `submit` 经回报）。
    - 没有装可选依赖、没有令牌时：三种组合都以退出码 2 结束、给出第 1、2 种说法，没有上传安装包、没有起后台进程。
    - 只设 `NGROK_AUTHTOKEN`、不显式传入令牌时起隧道成功。
    - 没有外网、DNS 不通时起隧道：以第 4 种说法、退出码 2 结束；记下 SDK 调用本身的行为与耗时，以及 `timeout_s` 能不能截住它。
    - 记下：长时间运行（数小时）的隧道；宿主所在的机器断网、休眠一段时间之后会话是否恢复，恢复之后规则是否照常；SDK 与前台的线程池、后台的读事件线程长期共存；宿主被暂停时新注册的账号上另一条隧道能否建成；宿主进程在本机有没有监听端口；SDK 请求耗时实测里没有成功的那几个请求的原因。

## 重议闸门

- **跨机器早于期限判死活**，或**本机后端的报告目录放到网络文件系统上、跨内核共用**成为使用需要时：再议心跳、租约或跨内核的死活判断。
- **没被点名的明细占用的存储成为实际问题**时：再议清理。
- **前台云端执行的需要**（逐步进度、中断）：再议以 `submit` 加等待与取消的组合补上，而不是恢复由本机进程推进的云端 run。
