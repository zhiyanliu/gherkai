## 已经闭合的取法

这些在五轮里被提出、处置之后没有再被质疑，附录的补丁里都有：

- 发起进程标识在记录里四项都是字符串（pid 写十进制数字串，启动时刻写原样文本）；记录键是 `launcher`，code 里叫 `launcher_id`；只有 `run` 写，`submit` 不写。
- 列举项另带出期限、后台执行标记的三种情形（后台、前台、取值不合法）、提交记录的三种情形（不存在；结构版本读不出或不认；结构版本认）。标记不合法的 run 仍按可读的行计入列举的名额，它不被处置，机读项的 `detached` 为 null。
- 判定只看结构版本，不看写出版本。提交记录本身解析不了时 `status` 现在是未捕获的异常，这一批归到退出码 2。
- 分类的次序（`settle-runs` 的 `reason` 在条件重叠时取哪个）：run 不存在；`unreadable`；`already_finished`；`detached`；`launcher_exited`；`past_deadline`；`launcher_alive`；`undetermined`。
- 运行态解析不了的 run：三个触发面都不对它尝试条件写，`status` 以退出码 2 结束并说明。
- 对使用者或 agent 可见、Codex 同意的取法：`settle-runs` 途中存储失败以退出码 2 结束而 stdout 不输出；`status` 不带 `--wait` 也给判定提示；`explain` 点名没有判定的 scope 时说明并以退出码 0 结束，`explain --json` 顶层加 run 级 `message`；agent 可以自己执行 `settle-runs`（先 `--dry-run`）；提示里的 `status` 命令带显式给出的 `--ddb-table` 与 `--region`、不带 `--profile`；后台 run 已过期限的提示推迟到第 5 步之后。
- Linux 上核对发起进程的取法，在读取环境没有被人改动的前提下已经由 Codex 对照内核源码逐项确认：pid 空间标识由 `boot_id`、`/proc/self/ns/pid`、`/proc/self/ns/time` 组成；记录时读 `/proc/self/stat`；核对时对记录的 pid 打开 pidfd，经同一个已打开的 `/proc` 目录读 `self/fdinfo/<fd>` 的 `Pid` 与 `<Pid>/stat`。两处实测（新的 pid 命名空间而不重新挂载 `/proc`；时间命名空间的偏移）已在一台 Ubuntu 上做过，写在补丁里决策八的实测记录。

## 没有收敛的一处，与原因

Linux 上「核对发起进程是否还在」这一处，连续五轮在修正之后出现新的反例：

| 轮次 | 反例 | 当轮的修法 |
|---|---|---|
| 228 | 核对方所见的 `/proc` 不属于自己的 pid 命名空间，按 pid 读到另一个进程 | 两侧自检 |
| 229 | 自检靠启动时刻相等，两个进程可以在同一个滴答里启动 | 改用 pidfd 定位 |
| 230 | 内核给启动时刻加了读取方所在时间命名空间的偏移 | 时间命名空间进标识，并把「值要在同样的读取环境下取得」写成规则 |
| 231 | 两次读取之间有人把 `/proc` 换成另一个实例再换回 | 几次读取经同一个目录句柄；写明核对要防的范围 |
| 232 | 核对开始之前，有人已经在 `/proc/<发起进程>` 上绑定挂载了另一个进程的条目 | 未处置，交 owner |

原因有两层。一是这一处要读别的进程的信息，取值对象的对应关系与值的可比性最初都没有写成规则，前几轮各补一个维度。二是给复核定的基准没有范围：最初写的是「不会把还在的发起进程判成已退出」，第 231 轮之后改成「在读取环境的静态差异与正常的并发之下」，仍然把「挂载的现状」整体算在内，于是「有人预先在某个进程的条目上挂了别的东西」也成了范围内的反例。每一个更刻意的环境都是成立的反例，循环靠修正到不了头。

## 待 owner 裁定

1. **核对的信任范围。** 建议按信任关系划界，不按时机划界：核对信任核对方自己的读取环境，即所见的 `/proc` 是内核提供的原样视图。在这个前提下，命名空间不同、`/proc` 属于别的 pid 命名空间、时间命名空间有偏移、发起进程退出、pid 被复用、`/proc` 被整体重新挂载这些情形，都不把还在的发起进程判成已退出。有人改动了核对方读取环境里的 `/proc`（在某个进程的条目上另挂东西、伪造内容）时结论不可靠，本功能不承担对抗读取环境控制者的职责。这是一条产品的信任假设，不依赖「能改挂载的进程也能改记录」这类权限上的推论（Codex 第 232 轮指出那个推论不成立）。
   另一种做法是继续加机制，让读取不穿过覆盖在 `/proc` 条目上的挂载（Linux 的 `openat2` 加 `RESOLVE_NO_XDEV`，Python 标准库没有封装，要自己调系统调用）。它只挡住这一种改动，挡不住别的伪造手段，范围仍然要写。
2. **`list-runs` 读量的口径。** ADR 0054 实测项 6 现在写「`list-runs` 的读量与请求数不因新属性变化」。Codex 第 232 轮指出这是绝对的保证：运行态条目加上发起进程标识之后如果跨过 4 KB，强一致读的消耗会从 1 个读单位变成 2 个；批量读回的响应变大也可能带来更多的重试请求。建议把口径改为「不新增读取的键、不改变名额与主动分页的规则」，并写明条目大小与响应大小仍会影响实际消耗。
3. **第 4 步里对使用者可见的几处取法**（上面「已经闭合的取法」的倒数第二条），以及第 2、3 步里已经实装、在提交说明里注明「尚待 owner 过目」的几处：`status --json` 的诊断键 `claim_count`；前台收尾写不成时 stdout 为空；到期时未启动的 job 不进判定清单、`run --json` 不另设清单；到期的 run 级 `error` 优先于使用方中断的 `aborted`；被期限截断的 job 用另一句说明；`run --no-report` 遵守期限；前台 job 的超时由单调时钟改按墙钟。

## owner 的裁定（2026-11-15）

1. 核对的信任范围：按建议。核对方信任自己所见的 `/proc`；有人刻意改动读取环境不属于正常情况，本功能不防。
2. `list-runs` 的读量：不作承诺。owner 的意见是没有人需要这个承诺，写了才引出口径是否准确的争论。实测项 6 改写成做法上的约束（列举不为期限与发起进程标识逐个 run 多读一次），不谈读量变不变。
3. 对使用者可见的各处取法：
   - 同意：`claim_count` 作诊断键；前台收尾写不成时的出口；到期的 run 级 `error` 优先于使用方中断的 `aborted`；被期限截断的 job 用另一句说明（预算那一句留给 job 自己的预算先到的情形）；`run --no-report` 遵守期限；前台 job 的超时改按墙钟；`status` 不带 `--wait` 也给判定提示；agent 可以自己执行 `settle-runs`；提示里的 `status` 命令带 `--ddb-table` 与 `--region`、不带 `--profile`；`explain` 点名没有判定的 scope 时说明并以退出码 0 结束（scope 名不在这个 run 里的仍报未找到、退出码 2）。
   - 改定：到期时未启动的 job 要进 `run --json` 的 `jobs[]`，并且不拿 `pending` 当终态。取法与落点见 [0013](./0013-mobile-devices-implementation.md)「六步之外已定的后续批次」第 2 项；被收尾的 run 里停在 `running` 的 job 怎样显示，放进这一步的设计一起定。

次序上的变化（2026-11-16）：补丁里与发起进程标识的取法、核对有关的段落（决策三、八）随「本机接力的改法」提前应用与实装，见 [0013](./0013-mobile-devices-implementation.md)「六步之外已定的后续批次」第 1 项；其余段落（判定与处置、`settle-runs`、`status --wait`、`list-runs`）仍在第 4 步。
