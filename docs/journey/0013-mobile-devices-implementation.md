本节是这次施工照着执行的清单，做完即删。产品还没有使用者，开发后端在暂停使用的前提下迁移一次（产品不提供从更早索引形态迁移的路径，ADR 0041 决策七「更早的索引形态」），要迁移的只有项目自己的开发后端；下面的操作约束与核对在暂停之下仍照做，用来查出遗漏的旧 run。产品侧的长期行为（清理的就绪检查只放行 `ACTIVE`）以 ADR 为准，不在本节。「迁移实测」各项做完后，对长期设计有用的结论（CloudFormation 拒绝更新与回滚的形态、`DELETING` 期间能否删除另一个索引、回填时长的量级）连同数据吸收进 ADR 0030 决定六「形态变更」条，其余随本节删除。

### 约束、起点与操作约束

约束（均为官方文档明确）：CloudFormation 一次更新只能新增或删除一个 GSI（同一次更新里删一个、加一个算改动两个，更新失败），且不等回填完成，新增的索引 `ACTIVE` 之前不能使用它，这张表也不能再更新（`AWS::DynamoDB::Table` 文档）；DynamoDB 不能修改已有 GSI 的键与投影。三个索引操作（建一个、删两个）各占一次部署，次数不能更少。**起点**：迁移只从「`status-index` 与 `status-run_id-index` 都在且都为 `ACTIVE`」的后端出发，第一次部署前以 `describe-table` 核对；别的起点不在范围内，依据是发行边界（现阶段没有使用者，不做旧版本兼容）。**操作约束**：从第一次部署起，只用本阶段的 CLI 提交 run 与执行 `push-worker`（哪个版本的 CLI 执行了这次部署，之后就只用它，直到下一次部署）；每次部署从开始到成功完成之间不提交 run、不执行 `push-worker`，部署成功之后才恢复，且只用新版本。CLI 旧于后端时版本 skew 闸只警告不拦（[0037](../adr/0037-distribution-and-packaging.md) 决策 7），这条约束不由闸保证；提交一侧由下面「第二次部署之前的核对」补上，核对之后到第二次部署完成之间仍靠操作者遵守。早于第一次部署写出的 STATE 没有 `status_group`，回填收不进新索引；第一次部署之后又经写 run 级 `status` 的写入（认领、把 run 级写成 `running` 的投影与前台 job 写、两条终态写）的，由那次写入补上分组属性而进入新索引（0030 决定六的写入规则）。补上的那一刻新索引项才开始传播，所以补上属性不等于切换时已在新索引里可见，第二次部署的放行不以它为准（见下「第二次部署之前的核对」）。不写 run 级 `status` 的写入不补：全 pending 的投影只写事件进度，写入 `pending` 的前台 job 写只写该 job。没补上的切换之后清理与 `list-runs` 都看不到，已收尾的历史 run 也从清单里消失；按发行边界不做兼容。每次部署前用 `cdk diff` 核对 runs 表上只变了一个索引（命名常量与写端变化会改变 Lambda 资产，其它资源随之变化是预期的）。`run`、`submit`、`status` 的数据访问路径不依赖被替换的索引；迁移期间仍遵守上面的暂停与版本约束。

### 各阶段的 code 与步骤

- **各阶段的 code**：清理按 ADR [0038](../adr/0038-worker-image-delivery.md)「不变量」清理 pass 条的完整新协议，从第一阶段起生效，包括静默期与补打、就绪检查、每趟一次引用快照、映射重读、逐候选最后核对及对应的失败处置；各阶段只切换读取的索引：第一阶段读 `status-index`，就绪检查查它、只放行 `ACTIVE`，快照按 `pending`、`running` 两个分区读它的 `worker_task_def_arns`（这一阶段 `pending` 到 `running` 换键的间隙与现行相同）；第二、三阶段读 `status_group-run_id-index` 的 `live` 分组。这些规则与读哪个索引无关，提前到第一阶段，迁移期间就不再有按 `registeredAt` 起算的孤儿静默期，也不再有不带就绪检查的清理。取消孤儿复用（0038 步 5：只在映射的二元组一致且所指 revision 仍为 ACTIVE 时跳过注册，其余一律新注册）同样与索引无关，也从第一阶段的 code 起生效。第一阶段的 code 第一次执行清理时，已有的孤儿还没有 `gherkai:retired-at`，这一趟给它们补打，回收至少再等 1 小时，偏保守，此后它们也不再被推送复用；仍在映射里却带着这个 tag 的（早先版本留下的共用）这一趟摘掉；已有的退休 revision 带的值是早先的 code 以命令开始时刻打的，早于它离开映射，早出的是那条命令写映射之前的执行时长（推送镜像等），归一之后照常从这个值起算；这里假设这段时长远小于静默期，使静默期给新建 run 留的余量仍然够用，这是操作假设、不是无条件成立的事实（下「只在这次迁移中成立的残余风险」），按发行边界接受。写端从第一阶段起写 `status_group`。`list-runs` 第一阶段仍读 `status-run_id-index`（就绪检查照现行判据），第二阶段起读新索引。
- **第一次部署**：模板新增 `status_group-run_id-index`；写端开始写 `status_group`（core 的 RunStore：推进器 Lambda 的代码随这次 stack 更新换代，CLI 一侧的写者随操作者换用新版本 CLI 换代）；清理读 `status-index`、`list-runs` 读 `status-run_id-index`。部署之后到新索引 `ACTIVE` 之前，两者都可用、读的都是旧索引；新索引在回填，只收带 `status_group` 的 item。**同一次 stack 更新既加索引又换推进器的代码**，与 `AWS::DynamoDB::Table` 文档「加索引的那次更新不改其它资源」的建议相悖，接受。这不是全部写者的原子切换：stack 更新期间 Lambda 新旧代码可能交替处理事件，各台机器上的 CLI 何时换用新版本由操作者决定，所以由上面的操作约束（部署成功之后才恢复提交、只用新版本）把写者的换代收拢到部署成功这一刻之后。写端必须在新索引的读者（第二阶段）上线之前就位，否则第二次部署之前建的 run 没有分组属性、切换之后对清理不可见（这类 run 由下面的核对查出）。建 run 写 `live` 的 CLI 与写终态分组的推进器 Lambda 都须已换代：用新版 CLI 建、由旧代码的 Lambda 收尾的 run，STATE 已到终态却留在 `live` 分组。它的后果是增加 `live` 分组的读量、阻止它引用的 revision 被回收（对清理偏保守）；默认清单按读回的状态仍显示它的真实终态，单查该终态（`--status <该终态>`）时它不在所查的分组里而缺席。相悖之处的后果是：这次部署若因其它资源失败而回滚，已发起的新索引可能留在表上、不在模板里，须手动删除后重试（ADR 0041 决策七「更早的索引形态」所记限制的第二条）；这一状态由重试之前的 `describe-table` 核对发现，两个旧索引及其读者不受影响。
- **等待一**：`describe-table` 看到新索引 `ACTIVE`（ADR 0041 决策七「实测项」云端一条所记约两百个 item 的后端，部署报完成后又过了十余分钟）。提前执行第二次部署时，CloudFormation 拒绝更新这张表、整次部署失败回滚——这是由文档「新增索引 `ACTIVE` 之前不能更新这张表」推出的，具体的失败与回滚形态待核（下「迁移实测」）。安全结论不依赖这一形态：清理只在部署成功的末尾执行，不会误删。
- **第二次部署之前的核对**：目的是在切换之前确认，旧版本写出、仍可能执行的 run 都已收尾。旧版本写出的 run 指早于第一次部署建立的，以及第一次部署之后由旧版 CLI 建立的：它们建 run 时不带 `status_group`，要等新版本的写者写它的 run 级状态才补上，补上的那一刻新索引项才开始传播。这一刻可能晚于它引用的 revision 的静默期起点很久，静默期给新建 run 留的约 1 小时传播余量覆盖不到它；强一致读回看得到基表上的分组属性，不说明新索引里已经可见（GSI 异步传播，官方文档明确；上述交错是推演）。所以不以「带 `status_group`」或「推进一次、补上属性」放行，只以收尾放行：已到终态的 run 不再起 task，它引用的 revision 被注销也无妨。由第一阶段的 CLI 建立的 run 在建 run 的那次写里就带 `status_group`，索引项从建 run 起传播，与正常的新建 run 是同一条依赖（[0038](../adr/0038-worker-image-delivery.md)「不变量」清理 pass 条边界情形 (b)），不在核对之列。**前置**（由操作者确认）：停用旧版本的写者，即不再用旧版 CLI 提交 run、执行前台 `run` 或 `status --wait`（推进器 Lambda 已随第一次部署换代）；确认没有仍在执行的旧版本前台 run（各提交机器上由旧版 CLI 发起的前台执行都已结束）。**核对步骤**：①分页 `Query` `status-index` 的 `pending`、`running` 两个分区，只取键（只读这两个分区、不 Scan）；②按 run_id 去重；③以 `BatchGetItem`（`ConsistentRead=True`，每次请求至多 100 个键）读回各 run 的 STATE 与 META，`UnprocessedKeys` 带退避重试、次数有界，重试耗尽不算核对通过，从①重新执行；④按读回的状态与写出版本（META 的提交记录头部，与 ADR 0041 决策七「写出版本的标记」同一读取）分类：已到终态的与读回为空的（item 已不在）不再关心；非终态、写出版本是第一阶段 CLI 版本的不在核对之列；其余非终态的（写出版本较旧，或头部读不到）进入放行判定，并取出 STATE 上的 detached 标记。按写出版本排除有一个前提：第一阶段的版本串能与旧写者区分。版本串由 git 状态派生，不同的未提交改动可以得出相同的版本串（脏树只带 `+dirty` 一类本地段），editable 安装的元数据是安装时算出的快照、之后的改动不会反映进去（[0037](../adr/0037-distribution-and-packaging.md) 决策 2b）。所以第一阶段的 code 从独立的提交构建，安装之前刷新安装元数据（重装，使版本串按这个提交重算），并确认它的版本串与旧写者的版本串不同；无法确认时，不用「版本相同」排除，非终态的 run 一律进入放行判定。必须回表：`status-index` 的投影只有键与 `worker_task_def_arns`，GSI 的 `Query` 取不到未投影的属性（官方文档明确），状态的当前值与写出版本都要从基表读。**放行条件**：④里进入放行判定的每个 run，都已无执行者、不会再起 task，才算通过。前台执行被强制结束、不会再起 task 的可以忽略：切换之后它不再出现在清单与引用检查里，它引用的 revision 不再因它保留。detached 的 run 有推进器与接力者，随时可能被接力执行，不算遗留：用 `status --wait` 把它推进到终态，或等它收尾，再核对一次；只推进一次、补上分组属性不算通过。前台执行仍在进行的等它结束。不要求结果为空：前台遗留的 run 永远停在非终态，不会从结果里消失。**完备性**：第一阶段 `status-index` 上 `pending` 到 `running` 的换键间隙仍在，一次核对可能漏掉恰在核对期间换到 `running` 的旧 run，所以前置与核对并用，并以相隔数分钟的两次核对都满足放行条件为准。run 级状态只进不退（[0034](../adr/0034-detached-batch-reconciler.md) 机制三），一个 run 的这次换值至多一次：第一次核对落在间隙里的 run，到第二次核对时已在 `running` 分区可见或已收尾，前提是索引传播短于两次核对的间隔，这是操作假设（列入下「只在这次迁移中成立的残余风险」）。旧版本的写者停用之后，旧 run 只可能由新版本的写者推进（推进器 Lambda 与新版 CLI 的接力），核对找出这些仍可能被推进的旧 run、要求它们收尾；收尾之后不再起 task，切换之后看不到它们也不会误删在用的 revision。核对也能查出第一次部署之后由旧版 CLI 提交的 run；第二次部署之后 `status-index` 不在了，这次核对只能在此之前做。**权限**：执行核对的身份需要 `status-index` 索引 ARN 上的 `dynamodb:Query`（部署方已有）与 runs 表 ARN 上的 `dynamodb:BatchGetItem`（部署方没有，用 `list-runs` 的身份有，[0033](../adr/0033-iac-aws-backend-and-composition-wiring.md)「编排进程角色」段）。由 owner 人工执行，命令随实装记在本节（用户指南不写，见下「用户指南不写这些步骤」条）。
- **第二次部署**：上面的前置与核对完成之后才执行。模板删除 `status-index`；清理与 `list-runs` 一同切到新索引，两者的就绪检查都改查新索引。部署之后两者都可用，这次部署末尾的清理已走新的引用检查。`status-index` 在 `DELETING` 期间，本阶段的 code 不读它；第一阶段的 code 若被用来操作这个后端（违反上面的操作约束），清理的就绪检查看到它 `DELETING` 或已不在即跳过并警告。
- **等待二**：`describe-table` 里不再有 `status-index`。一个索引 `DELETING` 期间能否删除另一个索引没有核过，等它消失最稳。
- **第三次部署**：等待二结束之后才执行。模板删除 `status-run_id-index`，code 删去它的命名常量。部署前后两者都可用。第二、三次之间旧索引仍在付写入，第三次应尽快执行。
- **删除索引的那次部署若回滚**：第二、三次部署都是整个 stack 一次更新，删除索引已经发起之后别的资源失败、触发回滚时，CloudFormation 会尝试把被删的索引重建回来（要重新回填），也可能停在 `UPDATE_ROLLBACK_FAILED`（推论，待核，见下「迁移实测」）。处置：等 `describe-table` 里的索引集合与各索引状态重新稳定（被重建的索引 `ACTIVE`，或删除已完成）、stack 回到可更新的状态之后再重试这次部署，必要时先手动处理（如继续回滚）。被重建的索引 `ACTIVE` 之前，下一次部署同样改不了这张表。这期间不误删：第二、三阶段的 code 不读被删的索引，被重建的旧索引对它们没有影响；回滚之后的推进器 Lambda 是上一阶段的代码，同样写 `status_group`；清理只在部署成功的末尾执行。
- 用户指南不写这些步骤，CHANGELOG 也不为此写升级须知：产品还没有使用者，要迁移的只有项目自己的开发后端。

### 代码与后端阶段错配（操作约束）

code 能自证的只有一类——索引缺失或未就绪的错配不注销。每个阶段的 code 的清理都带就绪检查、只放行 `ACTIVE`，检查的是该阶段读的那个索引；索引缺失、未就绪或 `DescribeTable` 失败时整趟不注销并打印一行警告，不依靠对已删除或删除中的索引做 `Query` 时的报错形态。就绪检查证明不了索引里的数据已经完整：新索引 `ACTIVE` 之后、上面的前置与核对完成之前，旧版本写出、尚未收尾的 run 可能不在新索引里，或刚补上分组属性、索引项仍在传播，第二阶段的 code 看到索引 `ACTIVE` 照常放行，会漏掉这些 run、注销它们在用而已满静默期的 revision。所以这段时间禁止用第二阶段的 code 执行清理或部署（含第二次部署本身：它末尾的清理就是第二阶段的 code，`gherkai deploy` 不过版本 skew 闸；非纯净版本的 `push-worker` 也跳过这道闸），这是操作约束，code 无法自证。就绪检查覆盖的错配：第一阶段的 code 遇到 `status-index` 已在删除或已删除的后端（第二次部署之后），清理跳过；第二、三阶段的 code 遇到新索引不存在或尚未 `ACTIVE` 的后端，清理跳过，`list-runs` 以退出码 2 结束。CLI 新于后端时 `push-worker`、`run` / `submit` 与 `list-runs` 都被版本 skew 闸拦下（0037 决策 7；非纯净版本跳过这道闸），所以错配通常只有「旧阶段的 code 对新阶段的后端」这一个方向。不在就绪检查保证之内的还有早于第一阶段的 code：它的清理没有就绪检查，查 `status-index` 的 `Query` 失败即不注销，靠的是没有实测的报错形态，孤儿仍按 `registeredAt` 起算；它在第一次部署之后只会以 CLI 旧于后端的形态出现，由上面的操作约束排除，按发行边界接受。

一并遵守：新索引已 `ACTIVE`、但上面「第二次部署之前的核对」的前置与核对尚未完成时，不得用第二阶段的 code 执行清理或部署（含第二次部署本身），也不得用非纯净版本的第二阶段 code 执行 `push-worker`；code 无法自证这一条。

### 被拒的部署序列

先删 `status-run_id-index`、再以它的名字重建新索引：同样三次部署，而从第一次部署到新索引 `ACTIVE` 之间 `list-runs` 不可用；先增后删在每一步都至少留一个两者能读的索引。先单独部署写端代码、再单独新增索引，之后照上面删两个旧索引，共四次部署：只为符合「加索引那次不改其它资源」的建议，换来多一个过渡阶段，以及随之多出的一组代码与后端错配组合要守；它避开的后果（回滚后手动删除留下的新索引、再重试）可由 `describe-table` 发现、可恢复，不涉及 run 数据与清理的正确性。把写端推迟到第二次部署、与新索引的读者一同上线：第二次部署之前建的 run 没有分组属性，切换之后对清理不可见。

### 各阶段的权限

- 部署方（清理）：第一阶段的清理仍查 `status-index`，runs 表 ARN 上的 `dynamodb:DescribeTable` 与 `ecs:UntagResource` 从第一阶段起就要，新索引 ARN `table/{prefix}runs/index/status_group-run_id-index` 上的 `Query` 从第二阶段起要（ADR 0038「权限面增量」）。
- 编排进程角色（`list-runs`）：第一阶段仍查 `status-run_id-index`，第二阶段起查新索引，索引 ARN 随之切换（ADR 0041 决策七「权限」条、ADR 0033「编排进程角色」段）。
- 执行「第二次部署之前的核对」的身份：见该步的「权限」。

### 只在这次迁移中成立的残余风险

- 第二次部署之前写出、仍可能执行的旧 run 缺分组属性，切换之后对清理的快照不可见：由「第二次部署之前的核对」要求它们收尾之后才切换（ADR 0038「不变量」清理 pass 条「为什么一次快照就够」其三把这类 run 排除在论证之外）。核对之后到第二次部署完成之间，仍靠操作者遵守「只用本阶段的 CLI」。
- 早于第一阶段的 code 的清理没有就绪检查，查 `status-index` 的 `Query` 失败即不注销，靠的是没有实测的报错形态，孤儿仍按 `registeredAt` 起算；它在第一次部署之后只会以 CLI 旧于后端的形态出现，由操作约束排除。
- 第一阶段的 code 第一次执行清理时，已有的退休 revision 带的 `gherkai:retired-at` 是早先的 code 以命令开始时刻打的，早于它离开映射，早出的是那条命令写映射之前的执行时长。**操作假设**：这段时长远小于静默期，静默期给新建 run 留的余量因此仍然够用；它不由 code 保证（那条命令若在写映射之前执行了很久，余量随之缩小，极端时为零），接受。
- 「第二次部署之前的核对」的完备性。**操作假设**：索引传播短于两次核对的间隔（数分钟）。GSI 异步传播是官方文档明确的，官方没有给出传播时长的上界；两次核对都漏掉同一个恰在换键间隙里的旧 run、切换之后它引用的 revision 被误删，是由此推出的情形。接受这一边界，靠前置（停用旧版本的写者）与两次核对并用把它压到很小。

### 迁移实测（做完即记，结论按上文吸收）

- 按上面的步骤逐步执行三次部署，每步记录 `describe-table` 的索引集合与状态、`cdk diff` 中 runs 表的变化，并在每两次部署之间（含第一次部署之后新索引回填期间）执行一次 `list-runs` 与一次带候选的清理 pass，确认各自可用；顺带记录 `status-index` `DELETING` 期间能否删除另一个索引。
- 第二次部署之前的核对：以旧版 CLI 提交一个 detached run，记录新代码的推进器认领之后它是否带上分组属性（预期带上；核对仍按写出版本把它列为待判定，推进到终态之后才放行）；以第一阶段的 CLI 提交一个 run，核对按写出版本把它排除在外；以旧版 CLI 执行一个前台 run 并强制结束它的进程，核对经回表按写出版本把它列为待判定，由操作者判定为遗留之后放行；两次核对相隔数分钟，记录两次的待判定集合是否一致。
- 新索引 `ACTIVE` 之前提前执行第二次部署，记录 CloudFormation 的失败与回滚形态、表上索引的状态。删除索引的那次部署在删除发起之后人为让另一个资源失败，记录回滚之后表上的索引集合与状态、stack 的状态，以及何时能再次部署。
- 就绪检查的阶段错配：以第二阶段的 code 对新索引尚未 `ACTIVE` 的后端执行清理（第一次部署之后、等待一结束之前），以第一阶段的 code 对 `status-index` 已在删除或已删除的后端执行清理（第二次部署之后），两种情形都跳过并打出一行警告、不注销任何 revision（CLI 新于后端时版本 skew 闸会先拦下 push-worker，这两种错配用不经该闸的非纯净版本构造，或直接调用清理）。另核新索引回填期间 `status-index` 的 `IndexStatus` 仍为 `ACTIVE`，第一阶段的清理据此放行；若这期间它不是 `ACTIVE`，这期间的清理都会跳过，不误删，只是回收推迟到新索引就绪之后。
- 切换之后核 `list-runs` 与切换之前同一批 run 的清单一致（早于第一次部署写出的 run 除外）；ADR 0041 决策七与 ADR 0038 实测项 8、9 的长期项在第三次部署之后的后端上执行。

**第一次部署实录（2026-11-12，开发后端）**：起点两个旧索引都为 `ACTIVE`、表里一百余个 item、没有运行中的 task，未到终态的只有一条此前强制结束演练留下的前台 run。`deploy --diff` 后正式部署约一分半结束；部署结束时新索引为 `CREATING`（回填中），约十分钟内转为 `ACTIVE`；回填期间两个旧索引一直是 `ACTIVE`（第一阶段清理的就绪检查因此照常放行）。推送两个引擎的 worker 镜像成功。写端核对：一次 `submit`（两个 job）与一次前台云端 run，从建 run 到收尾以强一致读连续读运行态（各一百四十次以上），`status_group` 在未到终态时恒为 `live`、收尾的那一次读即为终态值，没有一次与 run 级状态不对应；两条 run 收尾后都出现在新索引的 `passed` 分组里，`live` 分组为空（那条遗留的前台 run 写于部署之前、没有分组属性，不在新索引里）。`list-runs` 与 `list-workers` 照常（仍读旧索引）。
