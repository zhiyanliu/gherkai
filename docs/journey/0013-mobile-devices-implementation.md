- 待开的一批：遗留前台 run 的收尾（owner 于 2026-11-12 提出并定了方向，当前这批索引工作收口之后起设计轮：先落 ADR、经同僚复核，再实装；它同时关闭 ADR 0041 文末「遗留的非终态 run」那条重议闸门）。已定的方向：
  - 定位：系统认出执行者已经不在的 run 并把它记为已结束，属于对遗留状态的清理，不是「使用者放弃一个 run」；判定靠建 run 时记录下来的事实，不靠使用者事后担保，拿不准就不动。
  - 范围：只处理不带 detached 标记的未结束 run（由前台 `run` 建立、只有发起它的那个 CLI 进程会推进它、没有接力手段；`run --backend cloud` 也属此类）。带标记的后台 run 仍以 `status --wait` 接力为出口，取消后台 run 是另一件事、不在这一批。
  - 依据记在提交记录里，本机与云端两个后端都记：执行者标识（主机、pid、进程启动时刻）与允许运行到的最晚时刻。后者由各 job 的墙钟预算确定性算出（预算是 job 级配置：`@timeout:N`、`--default-job-timeout`、内建缺省，已在提交记录的 job 定义里，执行者按它强制停 job；没有 run 级 timeout），算式（保守的串行相加、重试、固定余量）在设计轮给出。执行者标识属于执行环境，放进提交记录要与 ADR 0034「执行环境属性不进运行定义的模型」对齐，设计轮写明放在哪里与理由，冲突处交 owner。
  - 判据：同一台机器上查到记录的进程已不存在，立即可记为已结束；否则已过允许运行到的最晚时刻，可记为已结束；其余不动。桌面 scope 被显式设为不超时的 run 算不出这个时刻，只能靠同机的进程判定。
  - 触发方式为显式：新增子命令 `gherkai settle-runs`（名字已定；批量判定并处理，带 `--dry-run`、`--json`，可给 run_id 只处理一个）；`status --wait` 遇到这类 run 不再空等、按同一判据处理；`list-runs` 保持只读，只显示判定结果。三处共用同一个判定。
  - `list-runs` 表格加两列（已结束的 run 第一列显示总时长）：已运行多久并括注距期限还剩多久（超过时括注已超多久），以及允许运行到的时刻（本机时区）；没有期限的格子用 `-`，与表格里现有的空值写法一致。后台 run 同样显示。列的排布与 `--json` 的对应字段在设计轮给出。
  - 心跳或租约这一轮不做，写进这项功能的 ADR 作为重议闸门（跨机器的判定需要早于允许运行到的最晚时刻时再加）。
  - 同样已由 owner 确认：处理结果写成 run 级 `error` 并附说明（不用 `aborted`）；run 里各 job 的状态保持原样、不替它们下结论；人读文案事实在前、处置放括号，措辞为：列名「允许运行至」，处置「记为已结束」，同机判定的事实说成「发起它的 gherkai run 进程已退出」（不用「执行进程」，避免与 job 在哪里执行混淆；`status --wait` 现有那句等待提示届时一并改），提示形如「发起它的 gherkai run 进程已退出（可用 settle-runs 记为已结束）」「已超过允许运行的时间（可用 settle-runs 记为已结束）」，后台 run 超过时为「已超过允许运行的时间（可用 status --wait 接力）」。
- 验证环境 vfy 保留（Device Farm 项目为重新部署后的新项目；验收期对照用的临时执行角色已删）。跳板机的操作要点与演练装置不入库。
