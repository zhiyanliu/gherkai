**本文自己的复核状态。** 交 owner 之前，本文送另一家模型核了四轮（基准之内的意见 10、2、1、3 条）：

## 甲、ADR 里「到什么时候会怎样」的说法（对象：0054、0034、0031、0030、0027 的写回）

**事实。** 设计里云端的 run 有两次 run 级定时触发：期限那一次对仍在执行的 job 做到点停止并推进；期限加 300 秒那一次由后端结束 run。它们是两次独立的异步调用，各自可能延迟或失败，完成的先后没有保证（写全在 0054 决策九第 1 条）。三轮里同一项性质连续失守：

| 轮 | 位置 | 失守的句子 |
|---|---|---|
| 第一轮 | 0034「重议闸门」 | 「最晚由后端在期限加 300 秒结束」：把计划时刻写成结束的上界 |
| 闭合轮 | 0054「边界与已知局限」的表 | 「期限那一次定时触发此前已对它做过 job 到点停止」：把计划时刻写成此前已完成 |
| 第三轮 | 0054 实测项 8 | 「期限那一次到达时 run 仍未结束的，由它的 job 到点停止停掉 task」：从调用先到达推出停止由它完成 |

闭合轮之后做过一次结构处置：这类陈述只在 0054 决策九第 1 条、决策六、决策八、决策二与 0034「job timeout」节写全，别处只放指针；作者按词检索枚举了约 160 句。复核者第三轮按简报给的词表得到 137 个命中行，逐句看过，在基准之内只剩实测项 8 这一处；它另指出写全处里有一句过度声称（0054 决策二后台推进条把检查间隔说成停止请求延迟的上界，暂停的进程可以突破），这句在写回之前就有，判在基准之外。所以这次枚举的范围是按词命中的句子，不是对五篇的完整语义证明。

上一次的规则把实测项里「实装时要核什么」的句子归为验收内容，只要求它不把计划时刻写成必然的完成时刻，没有规定一条验收断言凭什么成立。第三轮那一句是作者一侧在处置上一轮意见、改写实测项 8 时新写的。

**要定的问题。** ADR 的实测项里，关于「哪一次调用做了什么、谁先谁后、结果怎样」的断言，凭什么才可以写。

**选项。**

- 甲一：给实测项的断言定依据。实测项里的每一条断言都要有完整的依据，二者之一：写全处写明的契约，连同它的全部前提；或这条实测项自己的布置把交错固定住了（例如固定「A 读快照、B 认领落库、A 再写」的次序，或把别的来源关掉）。两种依据都没有、只凭「计划的时刻」「先到达」「先读到」推出某次调用完成了某件事的，不写成断言，改成要记下的事实。闭合的核法：0054、0034 的实测项逐条列出「断言、依据的出处与前提、布置固定了什么、还剩哪些交错」，每条断言在剩下的每一种交错下都成立才算过；这张表靠人逐条核，是做法，不保证此后不会再被指出。
  - 后果：受控交错下对责任与次序的断言保留（如 0054 实测项 7 断言 A 的写被序号条件挡下）。实测项 8 这一类要么加布置把交错固定，要么把对单次调用作用的断言降为记下事实；它对结果的断言也要按出处的全部前提重写（0054「边界与已知局限」已写明 task 已启动而列举暂时看不到、各次清扫都没有列到、此后又没有触发时没有人停，所以「task 被停掉」不能无条件断言）。具体改写在规则定下之后做，仍要过复核。
- 甲二：这类验收不放在 ADR 里，留给实装计划。
  - 后果：ADR 少了「实装时要核什么」的一部分；项目约定是实测项与结果内联在 ADR 里，这样做与约定不一致。
- 甲三：实测项一律不写哪一次调用做了哪件事、谁先谁后，只写布置、结果与要记下的事实。
  - 后果：规则简单，但会删掉受控交错下合理的验收（上面实测项 7 那一类），或把本该判通过与否的要求降成只记事实。

**作者的倾向：甲一。** 理由：三次失守的共同点是「断言没有完整的依据」，前两次是正文里的转述，第三次是验收断言；甲一要求每条断言指得出依据，核的是依据而不是句式。它不改变项目对实测项的既有约定。

## 乙、code 注释里的 ADR 指针（对象：其余十二篇 ADR 的写回，连同 code、测试与各包技术文档注释里的指针）

**事实。** 写回只改了 ADR，code 还是旧设计。基准里有一条：注释里的 ADR 指针所括的说法要与所指小节的现文一致；code 还没有跟上的地方可以保留对现在行为的说明，但不带指向目标设计那一节的指针。这一条不要求先改 code：把错误的归属去掉即可。三轮：

| 轮 | 作者做了什么 | 复核者又核出（注释与技术文档里的） |
|---|---|---|
| 第一轮 | 只改所指小节已搬走或条名已变的指针 | 3 处：`core/DEVELOPMENT.md` 的设计导航把「run 级裁决」归给 0054；`result_store/local.py` 把到收尾才批量保存归给 0030；`test_cloud_reconcile.py` 把认领计数的条件接到 0054 实测项 7 |
| 闭合轮 | 改掉点名的各处及当时看到的同类 | 2 类 3 处：两处 `project_state` 文档串把「run 终态是收尾专属」归给 0030；`compose.py` 把云端前台无报告执行归给 0016 决策 A |
| 第三轮 | 结构处置：定规则（指针声明的是「那一节现在就是这样写的」，不一致的去掉指针、保留对现在行为的说明；判断单位是整个注释块），对 151 个文件里指向这次改过的 22 篇 ADR 的指针全量核对，分 14 批，每批有独立复核 | 4 处：`serialize.py` 把经 `begin/finalize` 落结束时刻归给 0030；`__main__.py` 一处以 0054 决策五支持「已得出的判定已写入」；`stack.py` 把入口读到终态即返回归给 0034；`test_conditional_writes.py` 一个节头以 0034 机制三条①为依据而其下用例验证以认领计数限制收尾 |

几个数字的口径：全量核对的调查记录有 342 条（其中一部分是把指针挪到同一块里一致的那一句旁、没有去掉；一部分标「无对应」，随那段 code 一起删去，不加回）。现在这 151 个文件里指向这 22 篇的指针约 2458 处，在 146 个文件里；其中带小节或条名的约 1600 处，只写篇号的约 858 处。带条名的指针做过一次机械差集，它只查「条名在写回之前的 ADR 里有、现在没有」，结果是 0；条名在所指 ADR 里从来没有出现过的既有指针不在这个差集里。

复核者第三轮确认：「挪到一致的句子旁」「补全相对指代」「收窄混合指针」三种判法成立；节头的判法边界不清，不能把没有限定范围的主题节头解释成只为某个字段的存在背书；第一轮、闭合轮、第三轮各有一处是同一种绑定（用现行的 0030 为旧的独立收尾时序作依据），全量核对之后仍有遗漏。它要求 owner 确定后续的结构处置，明确复合句与主题节头的引用范围及其覆盖的核验方式。

作者的分析：这一项性质原则上可以核到头（去掉一处错误的归属不需要改 code）。三轮的遗漏有两类，作者没有证据说哪一类是主因：一类是引用范围有歧义的（复合句里一个指针括住了哪几个分句，节头的指针是否为其下的用例背书，第三轮的 `test_conditional_writes.py` 节头属于这一类）；一类是归属写得很明确、按注释块阅读时仍然漏过的（闭合轮的 `compose.py` 直接写着「ADR 0016 决策 A：`--no-report --backend cloud` 仍在 Fargate 上运行」，第三轮的 `serialize.py` 明确把经 `begin/finalize` 落起止时刻归给 0030）。三轮用的都是同一种做法：读注释块、判断、改。它没有一份可以核「哪些指针已经逐个看过」的清单。

**要定的问题。** 后续的结构处置取哪一种：不降低基准、把指针的引用范围改成没有歧义再逐项核；还是降低写回这一步的基准、把语义一致留到实装。

**选项。**

- 乙一：改指针的引用结构，逐项映射。取消两种隐含的背书：复合句拆开，指针紧跟它背书的那一个分句；节头不带指针，指针下放到各个用例或各条说明。每个保留的指针只为一句具体的陈述或一个具体的用例背书。然后给出完整的出处映射：每个保留的指针、它背书的那一句、ADR 现文里对应的那一句。核验分两层，不能互相替代：覆盖用差集核（映射表里的指针集合等于检索到的指针集合）；语义逐项核（那一句与 ADR 对应的那一句是否一致）。范围是这 151 个文件里指向这 22 篇的全部指针（约 2458 处）；所指小节在写回里没有改动的，映射项可以只标「所指小节未改」。
  - 后果：基准不降低，完成有可核验的定义。代价：约 2458 项映射，要改动约 146 个文件的注释结构（只动注释与文档串）；这些注释里有相当一部分在实装批里还会随 code 重写，这部分工夫是一次性的。它是做法：逐项的语义判断仍靠人，不保证此后不会再被指出，但每一项的判断对象是明确的两句话。
- 乙二：在完整的受影响引用集上机械删除。这 151 个文件里指向这 22 篇的指针全部去掉（约 2458 处），不判断一致与否，实装时再加；核验是检索结果为零。
  - 后果：闭合可以机械核验，基准不降低。代价：这些文件在实装之前失去全部指向这 22 篇的导航，其中多数指针现在是一致的；加回要靠版本历史与调查记录。缩小删除范围（只删指向改过小节的、或只删要改写的文件里的）就要先把那个范围定准并核验，范围本身又成了受审对象。
- 乙三：明示接受过渡期的风险，把语义一致留到实装。写回这一步只保证机械可核的部分（改写前有、改写后没有的条名为 0），已做的清理保留，这一轮指出的 4 处照改。语义一致随实装做，并固定责任范围：以这 151 个文件为清单，每个实装批核它改到的文件，全部实装批之后对清单做一次差集，没有被任何一批核过的文件（实装不需要改的 code 文件、各包技术文档）另作一批核完。
  - 后果：降低了写回这一步的基准。code 跟上之前仍有注释把旧行为归给 ADR，数量未知（三轮各抽出 3、3、4 处），读注释的人可能把旧行为当作 ADR 支持的设计。清单与最后的差集保证每个文件终究被核一遍，不保证过渡期里的准确。
- 乙四：按更细的判法再做一遍阅读式的全量核对，不改指针的结构。
  - 后果：机制与上一次相同，歧义的来源还在，没有依据预期这次的结果不同。

**作者的倾向：乙一。** 理由：它把「读注释块、判断」换成「逐个指针列出来、逐项核」，对上面两类遗漏都适用：差集保证没有一个指针被跳过，归属明确的错误在逐项核对时各自面对 ADR 里对应的那一句；拆开复合句、节头不带指针，去掉的是第一类里范围的歧义。它不降低基准，完成有定义。作者没有证明它针对的就是三轮共同的失效原因，它是一个结构上不同、还要靠执行来验证的做法。owner 的口径是不因工作量妥协、方法层的修复要通用。乙三是另一条站得住的路，但它是一项要 owner 明示接受的风险，不是技术上的必然。

## 丙、云端 run 的本机隧道记录按什么定位（对象：设计稿决策十二「隧道由谁拆」）

**事实。** owner 已定：云端 `submit` 的隧道守护进程没有拆成时，也由 `status --wait` 与 `settle-runs` 补拆，办法是在提交那台机器上多写一份隧道记录。基准相应的一条：宿主没有拆成、run 已结束而记录还在时，云端凭提交那台机器上的本机记录补拆。这个对象经过两轮（首轮、闭合轮）：

| 轮 | 记录的位置 | 复核者指出 |
|---|---|---|
| 首轮 | 系统临时目录（按 `TMPDIR` 解析） | 同一台机器、同一个使用者，提交时与处置时 `TMPDIR` 不同，记录在而找不到，不拆也不提示 |
| 闭合轮 | 主目录下的 `~/.gherkai/tunnels/`（按 `HOME` 解析），并把「`HOME` 不同时找不到」写成边界 | 换目录没有消除原因：写入方与查找方仍各按当次的环境变量定位；基准里没有「提交与处置使用相同 `HOME`」这个前提，把它写成边界等于自行收窄基准。它同时写明：改 `HOME` 可以理解为主动切换存储上下文，这支持请 owner 定适用前提，不支持作者自行收窄，也不推出必须扫描历史主目录 |

实测（macOS 上 Python 3.13、Linux 上 Python 3.12，各一次）：`pwd.getpwuid(os.getuid()).pw_dir` 不随 `HOME`、`TMPDIR` 变；`Path.home()` 随 `HOME` 变，`HOME` 没设时与前者相同。按用户号查到的主目录来自系统的账号服务，来源可以是本地数据库，也可以是目录服务；它不是一个不会变的机器定位值。

**要定的问题。** 这份记录的定位依赖什么、接受哪些前提；或者回到上一层，云端要不要这份本机记录。

**候选的做法。**

- 丙一，按账号定位：主目录取账号服务按当前用户号给出的值，不读 `HOME`；记录放在它下面的 `.gherkai/tunnels/`。
- 丙二，按 `HOME` 定位：用 Python 的 `Path.home()`。`HOME` 设了就按它的值（它可以是相对路径，这时结果还随工作目录变；设成 `~` 时解析失败），`HOME` 没设时取账号服务给出的值。记录放在它下面的 `.gherkai/tunnels/`。这是仓库里别处取主目录的做法。
- 丙三，回到上一层：云端不写本机记录，隧道只由守护进程拆；守护进程没有走完收尾就退出时隧道留到使用者手动结束，ADR 写明这与本机后端的差别。这要改动 owner 已定的一项（云端也在本机写一份隧道记录、按同一条规则拆）。提出它的原因：这份记录的定位连续两轮没有收敛，每换一个位置就带出一组新的前提。

**已经核实的事实与例子**（按两条规则逐条算过；不是完整的比较）：

- 两种定位方式都要求：放记录的那个目录在提交时与处置时是同一个，并且两个时刻都看得到。
- 提交时与处置时 `HOME` 的值不同、账号服务两个时刻都查得到且映射没有变：丙一找得到记录；丙二去另一个位置找，找不到、不拆、不提示。
- 两个时刻 `HOME` 设成同一个绝对路径，而账号的主目录映射在其间改了，或处置时账号服务查询失败：丙二找得到；丙一找不到，或这一次定位不了。
- 提交时账号服务查询失败：丙一解析不出位置，没有记录（给出提示、照常提交，这个 run 没有补拆）；丙二在 `HOME` 设了的时候仍写得成。
- 两种方式下，解析出位置而目录写不成，都是给出提示、照常提交、没有补拆。
- 主目录被另一个内核共用时（网络文件系统上的主目录、挂进容器或虚拟机），两种方式的后果相同：另一侧的处置命令读得到这份记录；平台不同的由下面第 1 条挡住；平台相同而命名空间标识比较挡不住的（两台 macOS 机器，或两个 Linux 内核的初始命名空间标识相同），那一侧问的是它自己的接口地址，多数情况下得到连接被拒或 404、删掉这份有效的记录，提交那台机器上之后无从补拆；接口地址配成那一侧也连得上时，可能答 200，终止信号发给那台机器上同号的进程。

取丙一或丙二，基准里「云端凭提交那台机器上的本机记录补拆」那一条都要带上相应的前提，由 owner 接受；取丙三，那一条改为云端不补拆。

**同一轮的另外三条（不属于重复失守，定位定下之后一并改）：**

1. Linux 上的启动方读不到命名空间标识时不记标识，而 macOS 上的处置命令在记录没有标识时会往下问；记录里没有来源平台，分不出「macOS 本来没有」与「Linux 读取失败」。处置：记录多记启动方的平台；两个处置命令先比较平台，不同就不拆、不问接口、不删记录；平台相同且都是 Linux 时再比较命名空间标识，任一边读不到即不拆。这样「一边 Linux、一边 macOS」的各个方向都不往下问。它不覆盖平台相同而在另一个内核上的情形（见上面主目录被另一个内核共用的那一条）。这一条并入待 owner 定的「处置命令在另一个环境里执行」那一项。
