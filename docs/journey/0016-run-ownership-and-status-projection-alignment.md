# 推进权与状态投影：上游设计的对齐记录

2026-11-16、17 与 owner 逐条讨论的结果。它是写设计文字（新 ADR）与送复核时的依据：owner 的各条决定只在这里写全，别处引用本文或逐字引用。设计闭合、写进 ADR 之后删除本文。

## 为什么回到上游

ADR 0054 的后台推进实装之后，两批后续设计（本机接力的改法、事件库里解析不了的记录）在复核里越修越大：每一轮都找到新的异常时序，每个反例都引出一条新机制。owner 追问根因，结论是两条：

- **推进权没有唯一的持有者。** ADR 0034 的取法是谁都可以从事件库重放、接着推进一个后台 run。本机上 `status --wait` 分不清推进进程的死活，一律自己也推进（接力），于是一个推进方要从外面猜另一个进程的状态，而 worker 的生死只系在认领它的那个进程上。
- **run 的状态与 job 的状态分开写。** run 的状态是在某一刻汇总、单独写一次、然后冻结，另有几条路不看 job 就把 run 结束，由此出现「run 已结束而 job 还是 `pending` 或 `running`」「job 全部通过而 run 是 `error`」这类情形。

## 已对齐的决定

1. **推进权。** 本机后端的 run，前台与后台都只有一个推进方：那一个进程启动时对 run 目录拿一把由操作系统管的生命期锁，持有到退出；拿不到锁的进程不推进。云端后端允许多次 Lambda 调用重叠，由条件写保证记录一致，`kicker` 与 `reconciler` 两个入口保留。
2. **死活的判断。** 管这个 run 的进程还在不在，由试拿这把锁回答：拿得到即已不在（被暂停的进程仍持有锁，算还在）。不读对方进程的信息，不在别处另放锁，不设机器标识。前提写明：本机后端的目录所在的文件系统上，文件锁对所有来读写它的进程都有效（这也是运行态写锁本来就依赖的前提）。「启动时自检文件系统是否理会锁」要不要，写设计时定。
3. **`status --wait`。** 两个后端都只盯到终态，run 一到终态就返回并按判定给退出码。不推进，也不触发推进（云端不再「催一下」；去掉它要和后端到期结束 run 的那个出口一起落地）。
4. **管它的进程不在了的 run 不续。** 由别的一方把它结束（下称处置）。能处置的只有：`settle-runs`；等待中的 `status --wait`；云端的 run 另有后端自己到期结束；以后的取消命令。`list-runs`、不带 `--wait` 的 `status`、`explain` 只读。可以处置的条件是两者之一：试拿锁拿到了；或当前时刻已过运行期限加 300 秒。
5. **云端后端只支持 `submit`。** `run --backend cloud` 砍掉，执行方式从四种变成三种（本机前台、本机后台、云端后台）。前台才有的几样（终端里逐步的进度、`--fail-fast`、中途取消、网络故障时整个 job 重试）云端暂时没有；后台取消是之后要补的第一项。
6. **结束一个 run，就是在同一次写里把它没结束的 job 结束掉。** 没启动的记 `skipped`，已认领而没有结果的记 `aborted`，各带一句说明。到期、处置、取消都是这一种写法。job 的终态只写一次，之后不再改，迟到的结果不被采用。
7. **run 的状态只由 job 的终态算出。** 按序取第一条成立的：有 job 是 `error` 则 `error`；否则有 `failed` 则 `failed`；否则有 `aborted` 或 `skipped` 则 `aborted`（这个 run 没有执行完）；否则 `passed`。还有 job 没结束时 run 不是终态。run 的状态字段保留，但没有自己的写入逻辑：哪个 job 的状态一变，它在同一次写里跟着变。
8. **说明只是描述。** run 与 job 上的说明文字不参与任何计算。owner 的原话：一旦对内容有要求，就需要对未来的任何描述都保持这种要求，这本身是坏味道。
9. **被 run 的期限截断的 job 记 `aborted`**，说明仍是「这个 run 已超过允许运行的时间，job 被中止」；用完自己预算的 job 仍是 `error` 加超时。是哪一个时刻起的作用，由记录里的认领时刻、job 的预算与 run 的期限算出，不看说明。
10. **云端读不到可用的运行定义时**，各 job 记 `error`，run 随之是 `error`：它们不是被中途结束，是没法执行。
11. **输出里的状态就是记录里的状态**，不在读取时另派生一个状态值。

## 被取代或要回看的先前裁定

- 2026-11-15「被期限截断的 job 用另一句说明」：说明保留，状态由 `error` 改为 `aborted`（第 9 条）。

- ADR 0054 决策六「job 保持原样」与被拒方案「到期时把未启动的 job 记为 `error` 或 `skipped`」：反转（第 6 条）。

## 取证之后的调整（2026-11-17、18）

- **本机后端只支持本机文件系统上的目录，作为产品边界；锁仍加在 run 目录本身**（owner 2026-11-17 定的方向）。取证（一台 Linux 机器，内核 7.0，NFSv4.2 与 NFSv3 经本机回环挂载）：对只读打开的目录取排他锁在 NFS 上不报错，但服务端不记这把锁，它只在同一个挂载内有效，同一个导出的另一个挂载、另一种版本的挂载、服务端本地路径都能再拿到。本机文件系统上没有这个问题。owner 的判断：锁加在目录上是技术上更干净的做法（不多出一个文件，也没有锁文件被删掉重建的问题），问题只出在网络盘上，所以不为网络盘换锁的对象，而是把网络盘划到产品边界之外。
- **配套的手段**：用户文档写明这条要求；程序在取锁与试拿锁之前判断，不满足就报错退出。判断按目录所在的文件系统来做，不靠「取锁之后读回看锁在不在」：取证里，同一个进程在同一个挂载上再开一次去试拿，照样被挡，读回查不出别的挂载看不到它；owner 接受。只在依赖这把锁的命令里判断（owner：「只对那些依赖锁/要求单例运行的情况才做检查」）：`run`、`submit`、等待中的 `status --wait`、`settle-runs`。
- **不做「取锁后再开一次试拿」的自检**，理由同上；另一家模型也判它不是保证所必需的。取锁报错的情形由「只有明确的『已被持有』才算持有者还在，其余错误一律按锁不可用」这条判读挡住。
- 本机文件系统（ext4、tmpfs、容器的 overlay、宿主与容器共用的绑定挂载）上，设计稿里关于锁的各句陈述都被证实：被暂停的进程仍持有；被杀后别人约 1 毫秒内拿到；僵尸已释放；交接之后原进程关闭不影响持有；fork 而不 exec 的子进程会延长持有。宿主与容器、容器与容器之间互斥。
- 真实 DynamoDB 上：以写入序号为条件、对 `jobs` 整体替换的写，50、300、1000 个 job 都写得成，3000 个因单条记录超过大小上限被拒（各种终态轮换的样本上 1327 个写成、1335 个被拒，平均每项约 308 字节）；两个并发的写恰有一个写成。逐个路径写的做法在 215 到 258 个 job 时因表达式超长被拒。
- **2026-11-18 定的几项**：
  - 两个平台同一条规则：对打开的目录取文件系统类型，只放行实测过的类型，加一种先实测再加。Linux 是 `ext4`、`tmpfs`、`overlay`、`xfs`、`btrfs`、`ext3`；macOS 只有 APFS（owner：「让 macOS 也只放行实测过的类型」），不再看内核给的本机标志。
  - `settle-runs` 遇到某个 run 目录不过检查时跳过它、写明原因（owner 的倾向）；报告目录本身不过时整体以退出码 2 结束（作者的取法，已告知 owner）。
  - `doctor` 对配置的报告目录做同一判断，不碰锁（owner 同意加）；它在本机后端时是必修项（作者按 0041 决策四的判据定，已告知 owner）。
  - 等待中的 `status --wait`：run 已是终态时直接返回、不检查；run 未结束而目录不过检查时立即以退出码 2 结束，不取「只读地等到终态、不处置」（owner 不取后者；前者是作者的取法，已告知 owner）。
- **2026-11-18 补的取证**：
  - Linux 上按打开的描述符取挂载类型成立：被上层挂载盖住的两个方向、经符号链接、容器里的路径、目录不存在时取上级，都取到实际所在的挂载；按路径的最长前缀在被盖住时取到错的那条。
  - xfs、btrfs（顶层子卷）、ext3 的回环镜像上重做整套锁实验，去掉数值后与 ext4 逐行相同。
  - 容器 overlay 与它在宿主上的上层目录之间，锁互不阻挡；两条路径的类型都在清单里，检查拦不住，列为检查放行而在边界之外的情形。
  - macOS 的 Docker Desktop（VirtioFS）：宿主目录绑定挂载进容器后类型是 `fakeowner`、被拒；宿主一侧是 APFS、放行；宿主与容器之间目录锁与文件锁两个方向都互不阻挡，容器之间互斥；命名卷是 `ext4`。

## owner 对待定九项的裁定（2026-11-18）

编号是当时设计稿「待 owner 定」的编号。

1. 事件里已有结果、运行态里还没有的 job 被处置时：只做结束写、记 `aborted`。处置方不按事件记结果；同一种中断在云端通常由后端接着记下真实结果，这个差别 owner 接受。
2. 判定明细要对应写成终态的那一次写（owner：「保持一致性是个比较重要的产品特性」，先答取「接受不对应」，听过说明之后改定）：每次保存明细存成带唯一标识的一份、不覆盖；记下 job 终态的那次写同时记下它对应的是哪一份；读明细的一方只认运行态点名的那一份；没被点名的不清理。直接读明细文件不再是对外的读法，机器读结果的入口是 CLI 的 `--json`。云端被结束写结束的 job，已执行的 step 只在事件的保留期（7 天）之内能从事件流补取，这个前提是事后向 owner 补告的。
3. 由结束写结束的 job 不写判定明细。
4. 确认：期限加 300 秒按墙钟判断，不是推进方收尾时长的上界；到点时结束写只看运行态，没写进运行态的结果不再被采用。
5. 本机推进方保存明细失败：指数退避重试 3 次（owner：「不行再放弃」），间隔 1、2、4 秒；仍失败按现在的做法退出。云端不变。
6. 配置文件把后端设为云端时执行 `run`：以退出码 2 结束并指向 `submit`。
7. 确认：job 与 run 状态的权威是运行态，给脚本读状态的入口是 `status --json`，读取权限不改。
8. 名称：run 级叫「run 处置」，job 级叫「job 到点停止」（不用「超时」：同一个处理也用在被 run 的期限截断的 job 上，这些 job 按第 9 条决定不算超时）。
9. 认同：边界检查信任内核给出的挂载信息，不防伪造它的一方。
