# 文档健康度复盘（全部项目文档）— 任务说明

> 给执行此任务的 AI agent：本文件是**可复用的任务指令**。读它就按这里的目标与方法做，不要退化成"扫一眼改改错别字"。下面标 **【强制】** 的步骤不可跳过——它们是这套复盘产生价值（而非走过场）的关键，省掉任何一个都会漏掉真问题或误改。姊妹任务见 [`code-health-review.md`](./code-health-review.md)（代码复盘）。

## 为什么做（价值）

ADR/CONTEXT 是随构建**逐步长起来**的：每次在前人文档上叠加、修改，单点看合理，累积起来会漂移——描述与 code 脱节、跨文档自相矛盾、同一事实多处重述且各自漂移、坏链接、被取代的决策没标历史。这些债对**读者是 AI coding agent（约 80%）**的文档库尤其致命：AI 据陈旧/矛盾的文档去构建，会把错误放大进 code。此任务定期把文档拉回"高密度、单一事实源、精确、无矛盾"的状态。

## 何时做（触发）

**事件驱动，非纯周期**：文档漂移是构建的函数、不是时间的函数。触发时机——完成一个显著构建里程碑后 / 一批 ADR 有增改后 / 主观感到文档跟不上 code 时。没构建就别空跑。

## 目标与准绳

- **读者比例决定优化方向**：ADR/CONTEXT 约 80% 给 AI coding agent 读 → 优化向**信息密度、单一事实源、精确指针**，冗余=context 噪声、敢压；README 约 80% 给人读 → 保叙事、不激进压缩。**据此定每一处"压缩 vs 保留"。**
- **单一事实源**：同一事实应有唯一权威表述，别处用**带指针的简短重述**引它——不是各写一份完整副本（那必漂移）。
- **精确无歧义**：与 code 不符即错；坏链接即错；行号引用易漂移（尽量用"XX 段"而非"line N"）。

## 红线护栏（违反=改错了）

- **绝不删**：决策理由（why）、权衡（trade-off）、反模式/被拒方案、关键不变量。压缩时必须完整保留——这些是 ADR 的核心价值。
- **有意重复 ≠ 冗余**：ADR 该能被（AI）单独读懂，跨切面事实带指针的**简短**重述是可读性设计。只压"同一事实多处**完整**重复且已漂移"的。
- **历史记录 ≠ 过时**：明确用"曾/原/已被 X 取代"框住的旧世界是有意保留的决策脉络，不算过时、不删。
- 不改 ADR 编号、不跨 ADR 搬内容（除非专门决策拆分）。

## 五类问题（分类找）

1. **CONTRADICTION**：文档内部自相矛盾，或两文档互相矛盾。
2. **STALE**：描述与当前 code 不符，或描述已被取代的旧世界却没标历史。
   - **「对照 code」是检测手段、不是权威**（本项目先 ADR/CONTEXT 后 coding，设计文档不瞄着 code 写）。发现不一致后按三类处置，**判据 = 被引句是「对实装的描述」还是「决策/契约/不变量」**：
     - ① **描述性内容**（路径 / 文件名 / 模块 / flag / 依赖版本 / 实装现状注 / 实测证据）→ **随 code 校准文档**（ADR 不是它们的权威）。
     - ② **被后来的 ADR 有意反转的决策** → **给旧 ADR 加 Status 反向链与历史注、不改决策本身**（权威仍是新的那篇 ADR）。
     - ③ **code 偏离了 ADR 已定的设计、且没有任何 ADR 记录这次偏离** → **不落文档改、不算客观类**：报人裁定是「实现没对齐设计 → 改 code」还是「设计该变 → 人拍板后显式改 ADR」，并移交姊妹任务 [`code-health-review.md`](./code-health-review.md) 的 VIOLATES_ADR 条接收。**报裁定时必附复盘方的倾向与理由**——实现更合理还是设计更合理、依据是什么（两边各能核到的真值、代价、与其它 ADR 的牵连）——人只做拍板、不从零判；只报「不一致」不给倾向 = 把判断成本原样推回给人。
   - **本任务最该防的误伤**：复盘顺手把 ADR 改成 code 的样子 = 把漂移合法化。
3. **DEADLINK**：指向不存在的 ADR/文件/锚点，或引用已删除的字段/函数名。**对 REFERENCES.md 与技术笔记这类"外部来源 + 源码内点"文档额外查**：① 文中指向的具体源码路径/内部符号是否随重构失效——对照 code 核实；② 外部 URL 是否明显过期（不强求逐个 fetch，但结构性失效/改版要标）。这类文档路径密度高、最易 STALE，是重灾区。
   - **引用方向违规（悬空指针的一类，判据见 CLAUDE.md 文档纪律「引用方向单向」+「指针只指稳定物」）**：长期文档（ADR/CONTEXT/README）里 ① 指向 `docs/journey/` 的链接、② 裸 WP 编号（`WP-S`/`WP3-B`…）、③ 只在某次会话/任务成立的指代（「#1 修复」「本轮那个 bug」）——都是指向易删/易变物的悬空引用，一律报。**修法不是删信息**：把被引的证据/结论**内联**进 ADR 使其自包含，血缘用**对未来读者自明的事件描述**（如「据中断丢失实测预演」）替代 journey 链接/WP 编号。**唯一例外绑死 Status 头**：Draft ADR 施工中可暂留 journey 引用（未吸收完的过程标记），Accepted/冻结 ADR 则必清（翻 Status 时的审计点，见下「Status 头」节）。
4. **REDUNDANCY**：同一事实多处完整重述且漂移 / 可合并段落 / 可精化冗长句 / 单 ADR 内可重组以提升 AI 检索的段落顺序。
5. **SEDIMENT（施工叙事沉积）**：迭代过程叙事在长期文档里的残留——「先做 X 后发现 Y 改成 Z」的施工节奏、「P3b/步骤几」这类过程编号、被后续迭代覆盖却没删的旧描述层、**现场流水**（坐标型数字——run_id / revision 号 / 时刻 / 单次耗时——与逐条命令过程；判据型数字不算，粒度判据见 CLAUDE.md「Journey 吸收进 ADR」条）。**处置：归主观类待批**（「决策脉络 vs 过程节奏」有判断边界）。
   - **检测**：它是**构建的累积函数**（每层叠加时单点看合理，累积起来稀释密度），快照式读当前文照不出——检测法见第一层【强制】提纯审计。
   - **留/删边界**：留「为何这样设计」（why/被拒方案/决策脉络，见红线护栏），删「分几步/施工节奏/过程编号」——判据即 CLAUDE.md 文档纪律首条给 ADR 划的内容边界「ADR 记稳定决策（what/why/trade-off），施工进度属实现计划、放对话或 PR」，写入与审计同一把尺、此处不另立标准。
   - **不误伤**：把某次实测/commit 当稳定证据内联引用的（如「据中断丢失实测预演」）是自包含证据、不是沉积；`docs/journey/` 里过程坐标合法、不在此类射程内。
   - **与 DEADLINK 的分工**：过程编号作为叙事内容归本类（删叙事保决策）；作为指向 journey 的悬空引用归 DEADLINK 引用方向违规条（内联证据+换自明描述）——同一句可能两症并发，按各自修法处理。

## 按文档类型的复盘侧重（用对判据）

不同类型的文档，主要风险不同、别用一把尺子：
- **ADR / CONTEXT**：查决策一致性、跨文档矛盾、被取代未标历史、Status 头（见下）、施工叙事沉积（SEDIMENT 类，ADR 是其主战场）、**引用方向合规 + 自包含**（不引用 journey、不用裸 WP 编号；Accepted ADR 须结论连同证据内联、自成一体——见「五类问题」DEADLINK 的引用方向违规条）。
- **README（使用者向：根 + 各包，各包 README 逐字上 PyPI/npm）**：查安装 / 命令 / 参数 / 退出码过时；保叙事、不激进压缩。**加查使用者向边界**（判据与各层去向见 ADR 0039 面二去向表、CLAUDE.md 文档纪律「README / DEVELOPMENT 分层」）：contributor 内容（目录结构、开发环境、测试、spike、发布流程）或内部指代（ADR 编号、决策号、内部机制名）出现在使用者面 = 越界，修法是搬去同目录 `DEVELOPMENT.md`、不是删。护栏 `cli/tests/test_package_readmes.py` 只管禁词正则、相对链接与 DEVELOPMENT.md 存在性，正则外的语义越界靠本任务。
- **DEVELOPMENT.md（contributor 向：根 + 各包，与同目录 README 成对）**：查目录树 / 测试与开发命令 / ADR 编号范围与指针过时——全是枚举型，逐条对 `ls` / `git ls-files` / argparse；允许 ADR 指针与内部机制名。
- **docs/guides/（给人的阅读理解层）**：按 README 同侧判据（保叙事）；主查三样——STALE（派生视图最易随上游漂移，对照 code 与权威 ADR）、**越界复述 why**（决策理由/权衡出现在 guide 正文 = 双源苗头；写作判据在 CLAUDE.md 文档纪律 guides 条，修法 = 压回指针）、**guide 之间的主题归属与重叠**（同一机制只一篇作 owner、其余给指针；两篇各讲一遍必各自漂——修法是定归属、留指针，不是压句子；新增 guide 时既有篇的延伸阅读要指过来；归属表 = `docs/guides/README.md` 索引，审计时对照它）。
- **agent skill（`cli/gherkai_cli/skills/gherkai/**`，随 CLI wheel 发行、`gherkai skill install` 拷进使用方项目）**：按各包 README 同侧判据（零 ADR 编号 / 决策号 / 内部机制名，只用绝对 URL，跨文件指针写反引号裸路径），去向与链接形态见 ADR 0039 面二去向表 + [0043](./adr/0043-agent-skill-for-driving-gherkai.md)。护栏 `cli/tests/test_skill.py` 管禁词 / 相对链接 / URL 钉 HEAD·tag / flag 归属与排他 / JSON 键名 / 契约副本等值（provider 侧 `deploy`·`destroy` token 在 `deploy_aws/tests/test_skill_deploy_tokens.py`）；本任务只查正则与真值集之外的——语义越界（行话、contributor 内容漏进使用者面）与「安装态的 agent 照它做还对不对」。**`references/cli-json-contract.md` 是 `docs/guides/cli-json-contract.md` 的确定性转换产物、一律不手改**：副本与源的同步由护栏等值断言机械保证（改源页后跑 `tools/render_skill_contract.py` 重渲染），本任务要查的是那份**手写源**与 code 是否一致。
- **REFERENCES / 技术笔记/配方**（SIGV4-RECIPE 这类）：**没有"决策矛盾"维度，重在"配方/引用还灵不灵"**——代码片段是否还与当前 SDK/实现对得上、踩坑点是否还成立、指向的 ADR/源码路径/外链是否有效。对照 code 核实是主要手段。

## 执行方法（多轮复盘验证过的最佳路径）

**一轮的次序**：⓪ 按锚点读上轮落地提交里的「方法复盘」，其提议的规则变更作为本轮第一份待批（见下「产出与提交」）→ ① 定覆盖范围（下）→ ② 第一层片内审计（条目里凡标 **【强制】** 的都不可跳过）→ ③ 第二层 cross-ADR（【强制】，Status 枚举与判定方法在配套的「Status 头」节）→ ④ 第三层事实族横切（【强制】）→ ⑤ 落地（客观类直接改，**例外 = STALE 第③类不改文档、报人裁定**，见下「落地纪律」；主观类出报告待批）→ ⑥ 提交。**三层是一轮里的三个视角、不是三轮**：第三层按事实族切、与前两层按文档切正交，同一轮里都要做。

覆盖范围：**全部项目文档**——不预设"只有某几类相关"，凡人/AI 会消费的项目 Markdown 都在内：
- `docs/adr/*.md`（重点，80% 给 AI 读）
- `CONTEXT.md`（术语/概念总表）
- `docs/REFERENCES.md`（外部一手来源 + 源码内点自查资料，AI 用）
- 全部 README（根 / `cli` / `core` / `core/tests` / `runtime` / `deploy_aws` / `engines/*` / `.github/workflows`，主要给人读；使用者向 / contributor 向的分界见上「按文档类型的复盘侧重」——`core/tests` 与 `.github/workflows` 两份不进发行包、按 contributor 向判，ADR 指针与相对链接在它们里合法）
- 全部 `DEVELOPMENT.md`（根 / `cli` / `core` / `runtime` / `deploy_aws` / `engines/*`，contributor 向，与同目录 README 成对——判据见上「按文档类型的复盘侧重」）

- `docs/guides/*.md`（给人的阅读理解层，派生视图——判据侧重见上「按文档类型的复盘侧重」）
- 随 CLI wheel 发行的 **agent skill markdown**（`cli/gherkai_cli/skills/gherkai/SKILL.md` + `references/*.md`，5 份入库）——使用者/agent 面，安装态没有仓库上下文；判据侧重见上「按文档类型的复盘侧重」。

- 未来新增的 docs/ 与子工程根下文档同样纳入（本任务名"文档健康度"、不焊死在某几类上——每次 `find . -name "*.md"` 扫一遍、别漏新文件，排除项见下「明确排除」（唯一权威清单））。

**明确排除**：`.claude/` 除 `commands/` 外的部分与 `.agents/`（`.claude/skills/`、settings 等个人工具配置，不入库；随 wheel 发行的 `cli/gherkai_cli/skills/` 与入口 `.claude/commands/` 都在范围内，见上覆盖范围）；`node_modules/`、`.venv/`、`.pytest_cache/`（依赖/缓存）；**`graphify-out/`**（graph.json / GRAPH_REPORT.md / wiki/ 全是 graphify 生成物，刷新走 DEVELOPMENT.md「知识图刷新」，不当文档审）；**repo 内 code 注释/docstring 的引用方向违规归姊妹任务 [`code-health-review.md`](./code-health-review.md)**（本任务只管 `.md`，分工线两侧一致）。

### 第一层：片内审计（可用 workflow 并行）

- **分片按主题耦合分组**——把主题相关、易互相矛盾的 ADR 分在同一片，便于发现**跨片矛盾**（先看当前 ADR 集自行按主题聚类，别照抄某一时刻的固定分组；聚类真值 = ADR 互引图（第二层那张，先算）+ 各 ADR 点名的 code 文件重叠，知识图社区不作依据——见姊妹任务分片条）。
- **【强制】STALE 类必须 Read/Grep 实际 code 核实**，禁止凭印象——本任务最大的一类问题就是"code 改了、文档没跟"，只有对照 code 才抓得到。
  - **枚举型内容是最高收益的机械核对点：做「文档清单 vs 真值集」的差集、别靠读**——目录树 / flag·选项表 / 模块清单 / 字段·事件类型列表 / 交叉引用 / ADR 编号范围，每一项都拿文档清单去 `ls` / grep / 对照 argparse 逐条比对源真值。**为什么必须做差集**：遗漏项（实际有、文档漏列）在你读"已列出的内容"时是隐形的，读列表本身永远发现不了漏了什么（亲历：目录树、CLI 选项表、ADR 接口清单都曾漏列，全是散文读着没问题、逐条对真值集才现形）。
- **【强制】矛盾/过时/坏链接等客观类，逐条对抗验证**：交一个独立视角读原文+code 尝试**证伪**（默认怀疑），只保留 CONFIRMED 的——防止误判（把有意历史记录/风格偏好当成 bug）。
- **【强制】提纯/密度审计（审计集 = 全部 ADR + CONTEXT，选材与跨轮沿用规则见下）**——纠错抓「错」，这条抓「稀」；没有它，复盘会结构性偏向纠错、提纯永远被挤掉（亲历：曾有整轮发现全是纠错、零提纯）：
  - **选材（全量，同本任务「全部项目文档」基调）**：审计集 = **全部 ADR + CONTEXT**——「何时做」的事件驱动只定何时触发，不缩覆盖范围。**有界工作量靠跨轮沿用、不靠缩范围**：自上轮提纯审计以来无改动的 ADR 可沿用上轮对它的具名结论作判无依据（仍是内容锚定、可核）；动过的必须重审。**锚点 = 上轮落地提交**（删掉待批 journey 报告的那个），**它的定位不靠提交说明的自然语言、靠 trailer**——四步：
    - ① 取锚点：`git log --format='%h %(trailers:key=Doc-Health-Round,valueonly)' | grep -m1 .`（`Doc-Health-Round` / `Doc-Health-Records` 两个 trailer 的写法、哪个提交算落地提交见下「产出与提交」；trailer 缺失（早期轮次）时退回 `git log --grep=提纯` 找、同法取回）。
    - ② 取回上轮具名记录：`git show <锚点>^:<路径>` 从父提交取回（路径见锚点的 `Doc-Health-Records:` trailer）——记录随落地一起删、git 历史就是它的归宿，不另留永久 ledger（journey 不是永久文档）。
    - ③ 判动没动：`git log <锚点>^..HEAD -- <路径>` 取区间（起点用**锚点的父提交**——上轮的落地改动都在锚点里，从锚点起算会把上轮刚改过的文档误判成「未动」），零命中 = 可沿用、有命中 = 必重审；**动/没动清单写进报告**（可复核，不许沉默断言）。
    - ④ 排序（churn 只决定读的细致程度，**不做截断线**）：热区 = 动过的文档 ∪ 一跳依赖——引用了动过的 ADR 的其它文档（引用图入度，第二层会算）作温区先读，因为改一篇 ADR 失效的常是别处一字未动、引它的那句。首次执行本任务时无前轮可沿用 = 全量深清、建立基线。
  - **检测（时间维度，与 STALE 同构）**：提纯的真值集不是 code，是**文档自己的 git 历史**——对审计集逐个层读增长史，找「被后续迭代覆盖却没删的旧描述层」与「逐层叠加的施工括注」（SEDIMENT 类）。快照式读当前文照不出沉积层，同「枚举差集照遗漏项」的道理：不靠读、靠对照真值集。**层读三步、必须有界**：`git log --oneline` 看层数 → `--stat` 挑大改层 → `git show <commit>` 只读大改层的差异（**别对长历史文件全量 `git log -p`**——会撑爆执行者上下文，亲历中正是层数多的长文件把并行审计员撑到停摆，限读后即过）。
  - **判据（密度非行数，逐句布尔、无任何百分比/行数触发线）**：逐句问「这句是否承载受保护要素」——要素以上「红线护栏」节为唯一源（why/trade-off/反模式·被拒方案/不变量/有意重复/历史框定），增补四项：决策本身、精确指针、Accepted ADR 内联的自包含证据（判据型；坐标型现场不在保护内，见 SEDIMENT）（CLAUDE.md「值得让 ADR 长一点」）、叙事连贯骨架句。不承载任一 = 填充/施工流水/可指针化的完整重复 = 提纯候选。**密度与行数解耦**：250 行逐句全承载 = 满密度不动；短段落半数过场 = 照报。**粒度在候选句自身跨度上评**——一句填充紧挨一条不变量仍是填充，保护不从邻居继承。**骨架句限定**：受保护的是让论证可跟随的结构功能（过渡/框定/次序），不是挂在骨架上的重述——测试 = 删了它论证结构是否断，仅重述已说过的点则骨架去掉它照样立；ADR 是 80% AI 读、按密度优化，在 ADR 上援引「骨架」须说清丢的是哪个结构功能，不能只说「读着顺」。
  - **提案过独立红线复核**：每条提纯提案交独立视角对照红线护栏尝试**证伪**（提案方可能漏看候选句承载的要素；宁严勿松，拿不准即否决）——与客观类的对抗验证同构，只是真值集换成红线护栏。**已知误伤形态**（亲历被否的提案全落在这三种）：「反模式实例 / 带指针的有意重复 / 历史框定」被误判成沉积。被否的存档不落改。
  - **产出槽（本条的牙）**：报告**必须**含具名提纯审计记录——审计集里每个 ADR 一条：提纯提案，或判无+一句依据。**判无依据须内容锚定、不可移植**——点出具体险成候选却因某要素（指名+定位）留下的句子，或复述 git 层读到的史实（如「3 层增长、后层完全替换前层无残留」）；一句原样可粘到别的 ADR 还成立的套话（「均承载受保护要素」）不算数。**空槽/沉默 = 该步未执行、复盘未完成。**
  - **无配额**：不设「必须报 N 条」——配额会把执行者逼向最长的散文（恰是 why/trade-off/内联证据）下刀凑数、直接破红线。真干净就零候选，牙在「必须审、必须具名交代」，不在「必须删」；候选改与否仍走主观类待批。

### 第二层：cross-ADR 视角（片内审计漏掉的结构问题）

**【强制】** 这一层不能省——分片审计天然只查片内，结构问题只在整体视角暴露：

- **构建引用图**（谁引用谁、入度/出度）：找孤儿节点（无人引用，可能已废）、超级枢纽（出入度都极高，可能过载——但高内聚总纲不该拆，只在"某段频繁独立变更且牵动无关段"时才是拆分信号）。**顺带标记反向违规边**：任何「长期文档 → `docs/journey/`」的引用都是方向违规（稳定物依赖了易删物），引用图里最易一眼看出——全部报（按 DEADLINK 引用方向违规条修）。
- **Status 头一致性**：每个 ADR 有无标准 Status 头（见下）；被取代/证伪的是否标了历史，"被取代"链是否双向（新 ADR 指向旧的，旧 ADR 也标了 superseded-by、反向指针补全）。
- **文件名合规（机械项，`ls` 一遍即可）**：`docs/` 下全部文件名英文 kebab-case；`docs/adr/`、`docs/journey/` 带四位编号且各自不复用；例外只有约定俗成的全大写入口文件（判据在 CLAUDE.md 文档纪律「文档文件名」条）。

### Status 头（第二层的配套：枚举、判定与连带审计；头本身是每个 ADR 开头一行）

格式：`> **Status:** <枚举> · <superseded-by NNNN 若有> ·（<Partial 注解若有：结论存什么 / 立场变什么>）`

枚举：
- **Accepted**：决策仍完整有效、当前 code 就这么实现（或有意 defer 但决策不变）。
- **Superseded-by NNNN**：整个决策被后续 ADR 取代、已不作数（保留作决策史）。
- **Partially-superseded-by NNNN**：核心结论/理由仍成立，但某操作性立场或实现细节被后续反转。注解须写清"结论存什么、立场变什么"。
- **Draft**：前瞻/尚未实现的设计。
- **Historical**：纯决策史，所述机制已不存在。

判定方法：Read 全文看自述 → 查**编号更大的引用源**有没有明说取代它（核心结论 vs 操作立场，只有后者变=Partial）→ 必要时对照 code → 拿不准标 UNCERTAIN 交人定，别硬猜。

**Status 头连带审计——Accepted 必自包含**：一个 ADR 标（或本次将改为）**Accepted/冻结**态时，顺带查它是否已清掉 journey 引用/裸 WP 编号（Draft 可暂留、Accepted 必清——这条例外绑死 Status，判据与修法见「五类问题」DEADLINK 引用方向违规条）。**发现「Accepted ADR 仍引 journey/带 WP 编号」= 到期未还的债，必修**——按该条修法处理（内联证据 + 换自明描述）；这是该纪律唯一的定期审计点，别漏。

### 第三层：按事实族横切（【强制】，与按文档分片正交）

分片按文档聚类只能抓片内矛盾，cross-ADR 层只做结构；「同一事实在两个分片各写一份且已漂移」——正是 REDUNDANCY 与跨文档 CONTRADICTION 的主形态——前两层都照不出（亲历：曾抓到的几条跨文档矛盾，全靠某个审计员恰好两边都读了，换一种聚类就漏）。本层换轴：**按事实族切、不按文档切**。
- **族清单每轮从真值集类别现列**（不照抄某一轮的固定清单）：退出码语义 / 状态枚举与终态 / 事件类型与字段 / CLI 子命令与 flag / 目录树与模块清单 / 版本·模型 ID·依赖锁 / 命名契约（prefix、SSM 路径、表名、镜像 tag）/ 角色术语 / 数字类（超时、并发、保留期、票数）——本质是 CLAUDE.md 文档纪律「枚举型内容」那条的族级视图；新 ADR 每引入一个机读面，族清单随之加一行。
- **每族一个审计员**：grep 全部项目文档（含 README / guides / skill / CONTEXT）里该族的每一处提及，横向比对一致性并**指认权威位置**（ADR 的决策段 / code 真值 / 生成副本的源）。不一致报客观类（对抗验证同第一层）；「完整副本且已漂」报 REDUNDANCY，修法 = 压成带指针的简短重述、不是删信息（红线「有意重复 ≠ 冗余」仍适用——带指针的简短重述放行）。
- **产出槽**：每族一条记录——权威位置 + 提及处清单 + 一致 / 不一致判定；CONTEXT.md 若对该族没有指向权威的指针，报一条（它是「术语 → 精确指针」的索引）。空槽 = 本层未执行。

## 落地纪律

- **客观类（矛盾/过时/坏链接）直接改**——它们有唯一正确答案；**例外 = STALE 条的第③类**（code 偏离已定设计），不改文档、报人裁定。
- **主观类（压缩/重组/施工叙事提纯）先出报告待人批**——"冗余/沉积"判定有主观性，过度压缩会伤可读性，逐条给人定夺。**搁置也要落锚**：对某候选判「保留」时，理由须写成具体受保护要素的引用（指名+定位，同判无依据的锚定标准），不许「边界情况/差不多」搪塞——防「浮出→搁置→形式满足而净提纯恒零」。
- 产出**分类报告**：可直接改（已对抗验证 CONFIRMED）/ 待批（压缩重组/提纯提案）/ 存疑（UNCERTAIN）/ 已驳回（REFUTED），**外加具名提纯审计记录**（见第一层【强制】提纯审计的产出槽——全量审计集的动/没动清单可见，人可抽查任一条判无依据对 `git log -p` 复核，依据可移植/不可核 = 该步判失败），**外加事实族横切记录**（第三层产出槽，每族一条）。
- **待批报告的呈报形式**：默认对话内呈报；人要异步审时落 `docs/journey/`（过程产物，批毕落改吸收即删）。**给人批的视图控制长度和表达方式，方便审批**

## 产出与提交

- 客观类改完给 diff 汇报；主观类批准后再改。
- 纯文档改动，独立成 commit（与 code 改动分开），commit message 说清各类各改了几条、守了哪些护栏，并记「本轮提纯浮出 N 条 / 纠错 M 条」——N 必须等于具名审计记录里提案条数的机械汇总（不许自由填报），只记条数不记比值、不设健康区间（N=0 配扎实判无记录是完全合格的结果）；这行让「整理被纠错挤掉」在每轮可见。**落地提交**（删待批 journey 报告的那个）说明末尾以 git trailer 形式带 `Doc-Health-Round: N` 与 `Doc-Health-Records: <被删报告路径>`——两行与 `Co-Authored-By` 同在最后一个段落（trailer 块中间不能有空行），是下一轮跨轮沿用的锚点（定位法见第一层「选材」条）。
- **方法复盘（落地提交说明里、与 trailer 同处，三五行不写散文）**：本轮哪些规则抓到了真问题（点名规则 + 一条实例）、哪些规则跑了但零命中或全是误报、执行卡在哪（agent 停摆 / 反复返工的步骤）、由此提议的规则增删改。这是「动规则」的唯一入口——SEDIMENT 只管措辞，规则本身只在这里凭证据变：下一轮开局按锚点读到它，提议的规则变更作为该轮**第一份待批**交人，批了才改方法文档。**退场判据**：连续两轮零命中、且不承担防误伤职责的规则，提议合并或降为一句提示；新增规则必须写明它防的失败形态。
