## 定位：一个 CDK 工程建齐「`--backend cloud` 需要的全部 AWS 资源」

本 ADR 定 **IaC 工程定位/资源清单/命名契约/preflight** 与 **组合根把 `FargateEngine` 接进云端后端** 的稳定决策。执行环境特有的中断/grace 韧性见 [0032](./0032-fargate-execution-environment.md)；region/profile 贯通见 [0016](./0016-execution-architecture-core-lib-run-model.md) 决策 C；events-out/job-in 传输见 [0024](./0024-worker-core-protocol.md)；产物→S3 见 [0029](./0029-engine-artifacts-to-s3.md)。

`--backend cloud` 按 [0016](./0016-execution-architecture-core-lib-run-model.md) 决策 A = **存储上云（DDB/S3）+ Fargate 执行**（单一选项）。这两半的 AWS 资源此前一律「假定已存在、建表归 IaC」（[0030](./0030-realtime-persistence-seam.md) 决定六：adapter 不持 schema/建表权知识），生产侧从无建表建桶代码——只在 moto 单测 fixture（`core/tests/conftest.py`）里程序化建出。**本 ADR 决定把这些 fixture 里的建表建桶动作固化成真 CDK。**

**决策：新建顶层工程 `iac_aws_backend/`（Python CDK），与 `core/`/`cli/`/`engines/` 平级。**（历史注：[0037](./0037-distribution-and-packaging.md) 决策 6 实装后，该工程收编进发行包 `gherkai-deploy-aws`（`deploy_aws/gherkai_deploy_aws/`：stack / app / names / cli(Provider) / lambdas/，另加 worker 镜像族命令 `workers` 与容器引擎口子 `container`（[0038](./0038-worker-image-delivery.md)）），经 `gherkai deploy` 执行；下文「`iac_aws_backend`」即指今住在该包里的 stack 代码。）

- **工程名**：`iac_` 前缀对齐「工程」定位；`aws_backend` 精确覆盖它建的东西 = 「`--backend cloud` 这个 backend 所需的 aws 资源」——含**存储**（DDB/S3）**与执行**（Fargate/ECR），不窄化成只有存储。（与决策 A「backend=存储+执行单一选项」呼应。）
- **语言 = Python CDK**（aws-cdk-lib）。理由：与 core/cli 同语言（团队心智一致、CI 复用 uv 工具链）；不引入第二语言/Terraform HCL。
- **统一一个工程建齐、不拆散**：存储资源（含现在已有 adapter 的 RunStore 表 / S3 桶）也**收编进本 IaC**——此前它们「假定已存在」是收编前的遗留态，本 ADR 让「`--backend cloud` 的每一个 AWS 依赖」都有 IaC 出处、单一部署入口。

## 资源清单（CDK 建什么）

一套 CDK stack（可按 prefix 多实例化，见「命名」）建：

**DynamoDB（2 张表，均 `PAY_PER_REQUEST`；schema 权威源为 `deploy_aws/gherkai_deploy_aws/stack.py`；合成测试见 `deploy_aws/tests/test_stack.py`，RunStore 共用测试表见 `core/tests/conftest.py`）：**
1. `{prefix}runs`（控制面 / RunStore，已有 adapter，本 ADR 纳入统一 IaC）：PK=`run_id`(S)、SK=`item_type`(S，值 `META`/`STATE`）。只有一个只索引 STATE item 的稀疏 GSI：按 `status_group` 分区的 `status_group-run_id-index`，供 worker revision 清理（[0038](./0038-worker-image-delivery.md)）与 `list-runs`（[0041](./0041-agent-facing-cli-affordances.md) 决策七）共同读取。按 `status` 分区的两个旧索引 `status-index`（原供清理读）与 `status-run_id-index`（原供 `list-runs` 读）都已从部署模板删除。键与投影见 [0030](./0030-realtime-persistence-seam.md) 决定六。
2. `{prefix}events`（events-out，本 ADR 新增）：PK=`pk`(S，值 `run_id#scope_id`)、SK=`seq`(N)；非键属性 `body`(S) 不进 AttributeDefinitions。**独立于 runs 表、绝不合表**（[0024](./0024-worker-core-protocol.md)：两种访问模式——runs 点读/单元素刷、events 大量追加+范围 Query；合表会踩 run_id 热分区）。

**S3（1 个桶）：**
3. `{prefix}artifacts`：承 ResultStore（判定真值，`jobs/` 下每次保存一个对象、键只由这次保存的标识构成，由 job 的终态点名，[0030](./0030-realtime-persistence-seam.md) 决定三「点名」条与决定六）+ ReportStore（`index/manifest`）+ **job-in（`jobs-in/<quote(scope_id)>.json`——独立前缀、非 `jobs/`）** + artifact-upload（trajectory/report/log），以上全部按 key 前缀 `<report_dir>/<run_id>/` 分片。桶根下另有两个不随报告前缀变化的前缀：定义前缀 `definitions/` 放云端提交记录里的 jobs 对象（键与存放形态见 [0030](./0030-realtime-persistence-seam.md) 决定六「云端提交记录」条），不设过期规则：jobs 对象要与 runs 表里指向它的头保留一样久，runs 表的条目不过期，jobs 对象先于头消失时这个 run 的整份定义就读不出（这时各方怎样处理见同一条「jobs 对象取不到时」一项）；桶上两条按对象 tag 过期的规则（下「preflight fail-fast」节的「job-in S3 对象生命周期」条，与本条下文安装包的那一条）也不作用于它，jobs 对象不带这两个 tag；设备目标的安装包放在应用前缀 `apps/<sha256>/<原文件名>`（按内容哈希跨 run 复用，带对象 tag `gherkai=app`，按该 tag 过期的生命周期规则见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 9）。**报告前缀不与这两个保留前缀重叠**：报告前缀（规范化之后，同下 preflight 节「产物前缀一致性」条的分隔符规范化）不得等于 `definitions` 或 `apps`、也不得落在它们之下。两个保留前缀各有专门的权限与规则（worker 对定义前缀的读与写显式拒绝，提交者在应用前缀上有写与列举），报告前缀落进去，这些权限与规则就作用到 run 的对象上：取成 `definitions` 时，worker 自己的 job 输入与产物落在它被拒绝读写的位置，提交成功而 task 读不到输入。拒绝点在使用者给值的入口：云端命令的 `--report-dir` 解析之后（各层取值来源合并、规范化）等于这两个前缀之一或落在其下的，命令以退出码 2 结束，说明陈述这个报告前缀与它落进的那个前缀；用到报告前缀的云端命令（`submit`、`status`、`explain`、`settle-runs`、`doctor`）都是这一条规则，`doctor --backend cloud` 也在入口以退出码 2 结束，与别的入参错误同一处理；云端的 `list-runs` 不用报告前缀，照旧忽略这个参数（[0041](./0041-agent-facing-cli-affordances.md) 决策七「命令形态」）。这项检查是入参校验的一部分，不读 AWS，先于任何云端读（含云端后端接口版本的比对，[0037](./0037-distribution-and-packaging.md) 决策 7「各入口比什么」）。`gherkai deploy` 不设这项检查：后端的报告前缀没有部署入参（两个推进 Lambda 的 `REPORT_DIR` 由 IaC 有意不注入、取 Lambda 内的缺省 `reports`，资源清单 12.；改它要改 IaC 或直接改 Lambda 的配置），`deploy` 没有可检查的取值。后端的前缀在提交之前已被改成保留前缀时，也提交不进 run：命令行工具的值要与后端的一致才能提交（下 preflight 节「产物前缀一致性」条），而与它一致的值在入口就被拒绝。比对之后、run 执行期间才被改的不在此列：后端的报告前缀不是产品给出的配置项，改它的后果由那次改动承担（同一条）。（job 桶与 artifact 桶合一；worker 的 S3 读写授在整桶对象上，定义前缀显式拒绝，见下 task role 表。）**job-in 用 `jobs-in/` 而非 `jobs/`**：两者的键由不同的一方各自定——job-in 的键由 `FargateEngine` 定，判定真值的键由 ResultStore 定，存放形态对使用者不是约定；判定明细在 run 位置之内的键归 run 记录格式版本（[0030](./0030-realtime-persistence-seam.md) 决定三、[0037](./0037-distribution-and-packaging.md) 决策 7）；共用 `jobs/` 就要两边一起约定互不相撞，分开前缀则哪一边改键的形态都不牵连另一边。job-in 键里的 scope_id 一律 `quote(safe='')`（`/`→`%2F`、`:`→`%3A`），不造 S3 假子前缀。

**ECS / Fargate：**
4. ECS cluster `{prefix}cluster`。
5. **每引擎一个 task definition + 一个容器镜像（2 个，见「2 镜像」节）**：task-def family = `{prefix}{engine}-worker`（`engine`=引擎规范名 `novaact`/`midscene`，即 `{prefix}novaact-worker` / `{prefix}midscene-worker`——须与命名真源 `gherkai_runtime.names.task_def_name` 一致：CDK 侧 `stack.py` 直接 import 同一函数，不再复刻，见下「命名」）。Fargate 兼容、`networkMode=awsvpc`。**`stopTimeout` 显式设为 120s（`stack._resolve_stop_timeout`，贴 Fargate ≤120s 平台上限）、可经 `gherkai deploy --stop-timeout N` 覆盖（provider 拼成 `-c stop_timeout=`，stack 侧仍读 context）**（synth 期对非整数/越界 `[1,120]` fail-fast）——做成可配是为 grace 真容器标定期迭代试不同值免改 code。**grace 预算解法归 [0032](./0032-fargate-execution-environment.md)、已真容器标定**（曾担心 Nova grace 下限 > 120s 硬上限的冲突，0032 结论 4 实测厘清：subprocess 侧压 margin 60→30 后下限 150 满足不变量、Fargate 侧对最坏长 act 结构性接受 SIGKILL+TTL 兜底；`ACT_TIMEOUT_S` 不动），**不是 stopTimeout 是否设值**（云端停 task 由推进器调 `StopTask`，宽限不能逐次传，真实宽限由此 task-def 期 `stopTimeout` 决定，[0024](./0024-worker-core-protocol.md)「终止契约」节机制层）。**task-def 内 container 元素名 = `{engine}-worker`（不带 prefix，见下「container 名约定」）**。**task-def 不设 `AWS_REGION`/`AWS_PROFILE`**（见「task-def 不焊 region/凭证」）。**container 日志走 `awslogs` log driver → 每引擎一个 CloudWatch 日志组 `/{prefix}worker/{engine}`**（stream 前缀 = 引擎名、保留 14 天、随 stack 销毁）——cloud 后端没有本机 worker 日志文件，排障看它（[0041](./0041-agent-facing-cli-affordances.md) 决策二）。
6. ECR 仓库（2 个，各承一镜像）：名 = task-def family 名 `{prefix}{engine}-worker`（`names.ecr_repo_name` 恒等于 `task_def_name`，规则见 [0038](./0038-worker-image-delivery.md)「概念模型」）。
7. VPC 网络：subnet(s) + security group(s)（`awsvpcConfiguration` 用；ID 由 IaC 注进两个推进器 Lambda 的 env，见「组合根接线（非 IaC）」节「Fargate 配置参数」条）。**VPC 来源三种取值可指定**（见下「VPC 来源」）——曾默认建新（历史注：0037 决策 6 实装后 `gherkai deploy --vpc default|new|<vpc-id>` **必给、无隐式默认**，三种取值能力不减），支持复用现有/默认 VPC 避 NAT 成本。

**IAM：**
8. **task role**（容器内凭证链 `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` 解析目标）——**最小权限**（见「IAM 最小权限」）。
9. **task execution role**（拉 ECR 镜像 / 写 CloudWatch 日志的标准 Fargate execution role）。
10. **3 个 Lambda 执行角色**（随 12. 的各 Function 自动建、**与 task role/execution role 分立**）：exit-observer 只需 events 表写（`PutItem` 写 `task_exited`），环境变量只有 events 表名与 region，不带 runs 表名、不读 runs 表——它不按后台执行标记分流，凡带 run 与 scope 标识的 task 停止都写退出记录（[0034](./0034-detached-batch-reconciler.md) 端到端 cloud 1b「触发过滤不看后台执行标记」）；reconciler / kicker 权限相同——起 worker task（`ecs:RunTask` 按引擎 task-def ARN + `iam:PassRole` 到 execution role、各 task role 与 `{prefix}timeout-scheduler`——后者是 CreateSchedule 传 Target role 的 IAM 前置，带条件 `iam:PassedToService=scheduler.amazonaws.com`，见 15.）+ `ecs:DescribeTasks`/`StopTask`/`ListTasks`（退出码兜底、job 到点停止的定位与停、run 结束之后按 run id 清扫仍在执行的 task，[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九）+ runs 表读写 + events 表读 + `PutItem`（launch 失败补偿，与 job 到点停止的兜底两路「退出事件丢投、task 无踪」直写退出记录——在跑的 task 一律只 StopTask、等观察链，[0034](./0034-detached-batch-reconciler.md) 机制二推论与「job timeout」节；仍不给 Update/Delete）+ 桶读写（含桶上的列举权限 `s3:ListBucket`，它是一项依赖：读整份运行定义时取定义前缀下的 jobs 对象，有列举权限，缺键才得到「键不存在」，后端据此把它归为运行定义不可用、做结束写的 error 变体，[0030](./0030-realtime-persistence-seam.md) 决定六「jobs 对象取不到时」一项；收窄成只读写对象时，缺键得到的是拒绝访问，被当作失败、由之后的触发反复重试）+ `scheduler:CreateSchedule`/`DeleteSchedule`（job 到点停止与 run 的两次定时触发，资源域为专用 schedule group，见 15.）；不读 SSM（曾为缺 `worker_task_defs` 的旧 definition 按默认指针解析而授过 `GetParameter`/`GetParametersByPath`，随 [0038](./0038-worker-image-delivery.md)「读侧不留兼容路径」撤除）。**起 task 的能力集中在 reconciler / kicker 两个角色上**（exit-observer 不起 task），故 submit/status 机器无需任何 ECS 写/执行权限（[0034](./0034-detached-batch-reconciler.md) 最小权限卖点）。

**SSM：**

source》有一句「DynamoDB 的事件源映射只支持对 `dynamodb` 键过滤」，CDK 的 Lambda 构造库文档的过滤示例却把 `eventName`（取 `INSERT` 或 `MODIFY`）与 `dynamodb` 写在同一条过滤里，AWS 知识中心也建议用过滤只处理 INSERT 与 MODIFY、跳过 TTL 15. **一次性定时触发的配套**：两类 one-time schedule 共用一套——job 到点停止的触发（[0034](./0034-detached-batch-reconciler.md)「job timeout」节），与每个 run 的两次 run 级定时触发（期限那一次与期限加 300 秒那一次，由 kicker 在收到 STATE 条目的新建时建；时刻与各做什么见 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九第 1 条）。schedule 本身运行期由推进器建、名字确定、触发之后自动删除，**非 CDK 建**；CDK 建的是下面的 group 与执行 role。
    - **专用 schedule group `{prefix}schedules`**：CDK 建立（`AWS::Scheduler::ScheduleGroup`，不 RETAIN）、随 stack 删除，两类 schedule 都建在里面。
    - **group 内的名字不带 prefix**：job 到点停止为 `job-timeout-` 加 `sha1(run_id#scope_id)` 的前 20 位；run 级为 `run-timer-` 加 `sha1(run_id#kind)` 的前 20 位，`kind` 取 `deadline` 或 `overdue`。两族基名不同，摘要的输入互不相撞（scope_id 是用户文本，不与 run 级的种类共用名字空间）；用摘要而不直接拼名字，是因为 job 到点停止的名字要区分 scope，而 scope_id 是用户文本，字符集与长度都可能超出 schedule 名所允许的；run 级一族与它同取摘要，两族的名字形态一致、长度固定。run_id 只含字母、数字与连字符、不超过 36 个字符，属跨版本不变的约定（[0037](./0037-distribution-and-packaging.md) 决策 7「跨版本不变的约定」约定四），直接拼进 run 级的名字也放得下，取摘要不是因为它。名字由 run 与 scope（或种类）确定，重试不重复建：同名已存在得到 `ConflictException`，视为已建。
    - **表达式与目标**：`at(yyyy-mm-ddThh:mm:ss)`（UTC，带秒、截去小数秒）、`FlexibleTimeWindow OFF`、`ActionAfterCompletion=DELETE`、`GroupName={prefix}schedules`；Target 是 kicker 加执行 role `{prefix}timeout-scheduler`，载荷 job 到点停止为 `{run_id, timeout_scope}`、run 级为 `{run_id, run_timer}`（`deadline` 或 `overdue`）。载荷以键 `run_id` 带出 run 标识，这一点属跨版本不变的约定（[0037](./0037-distribution-and-packaging.md) 决策 7），后端靠它从旧部署建的定时触发里认出是哪个 run；载荷的其余部分、group 与名字由新部署按 0037 决策 7「后端形态变更的迁移口径」承接，保留到旧触发都已执行。RetryPolicy 用缺省：投递至少一次，缺省重试至多 185 次、24 小时（官方文档）；各处理幂等，晚到与重复到达都无害。建 schedule 的代码两类共用一处，差别只在调用方怎样处理建不成（见本条末句）。
    - **执行 role `{prefix}timeout-scheduler`**：`scheduler.amazonaws.com` assume，信任策略带 `aws:SourceAccount` 条件；只授 invoke kicker，用**确定性 kicker ARN 字符串**授权以避免 role↔function 互引成环；推进器对它的 `iam:PassRole` 带 `iam:PassedToService` 条件（见 10.）。
    - **IAM 资源域 `arn:aws:scheduler:{region}:{account}:schedule/{prefix}schedules/*`**，一条语句覆盖两族，以后再加一族一次性触发不改 IAM。**IaC 的资源域与推进器的 group 名、建名同源推导**（命名真源 `runtime/gherkai_runtime/names.py`，基名 `schedules`、`job-timeout`、`run-timer`、`timeout-scheduler` 都在那里），同 Lambda 名那款「单一命名事实源」：单侧硬编码改名 → CreateSchedule 撞资源域 AccessDenied。
    - **依据**：① 生命周期：这些 schedule 的目标（kicker）与执行 role 都属于 stack；删除 group 时它进入 DELETING，直到 Scheduler 删完其中全部 schedule（官方文档），所以 destroy 连同还没有到点的触发一并删除，不会有触发在 stack 删除之后仍按时投递到一个已不存在的目标（放在 default group 里时，缺省重试最长 24 小时、185 次）。② 名字与 prefix 解耦：schedule 名长度固定，prefix 上限改由带 prefix 的资源名里最紧的 IAM role 名推出（「命名」护栏），超出即合成失败，不会部署出一个 CreateSchedule 每次被拒、job 到点停止的保护静默降级的后端。③ 授权与列举按 group：资源域是 group 而不是名字前缀通配；`ListSchedules --group-name {prefix}schedules` 只列这个部署的触发。schedule 只能在建立时归入 group、之后不能移出或改归（官方文档），所以从第一次建立起就放进去。
    - **实测**（临时 stack，只含 schedule group）：group 建成即 ACTIVE，schedule ARN 形如 `schedule/<group>/<名字>`；同一 group 里用已有的名字再建得到 `ConflictException`（消息为该名字已存在）；schedule 名 64 个字符建得成、65 个字符得到 `ValidationException`；group 里还有未到点的 schedule 时删 stack，删除正常完成，之后 group 与其中的 schedule 都不在。**前提**（部署之后核）：按 group 资源域授权 CreateSchedule、DeleteSchedule 足够，不另需 group 资源本身的授权（现网按 `schedule/default/<名字前缀>*` 授权已在用，是同一种资源域写法），不成立时补授 group 资源；账户还能再建一个 group（每个账户的 group 数配额未核）；group 名的长度上限不小于 56 个字符（只核了 schedule 名的上限，「命名」护栏按 64 计），不成立时 prefix 上限改由 group 名推出；信任策略与 PassRole 的两个条件不挡住真实投递，条件写错时定时触发全部失效、立刻看得见，不成立时改条件写法；group 里的一次性触发真实投递到 kicker 之后按 `ActionAfterCompletion=DELETE` 自动删除（上面的实测只建了未到点的触发、随后删栈，没有经过投递；[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 实测项 21）。
    - **被拒**：default group 加带 prefix 的名字（上面三条依据；也不作专用 group 用不了时的退路）；run 级触发沿用 job-timeout 的名字空间（名不副实，摘要输入 scope_id 是用户文本）；由 CLI 在 submit 时建（提交一侧多出 Scheduler 与 PassRole 权限，违背 [0034](./0034-detached-batch-reconciler.md) 的最小权限）。
    - 两类触发建不成时的后果不同：job 到点停止的触发是 best-effort（只打日志），这个 job 的保护降级为 tick 的防御扫与 run 的定时触发（0034「job timeout」节「best-effort 边界」条、0054 决策九第 1 条）；run 的两次触发建不成时怎样处理、后端到期结束的前提见 0054 决策九第 1 条。

`table/{prefix}runs/index/status_group-run_id-index`（表 ARN 上已有的 `Query` 授权覆盖不到 GSI；见 0041 决策七「权限」条），以及表 ARN 上的 `dynamodb:BatchGetItem`（按 run_id 批量读回 STATE 与 META item）；不用 `list-runs` 可不授。**`submit`/`status` 的机器只需「runs 表读写 + 上述只读探活 + `ssm:GetParameter`（`/{prefix}backend/*`，用途同上）+ 定义前缀上的 `s3:PutObject`（资源为桶内 `definitions/*` 对象：每次 `submit` 都写这个 run 的 jobs 对象，[0030](./0030-realtime-persistence-seam.md) 决定六）」、无任何 ECS 写/执行权限**（起 task 全走 Lambda 执行角色，见 10.——[0034](./0034-detached-batch-reconciler.md) 最小权限卖点）。**处置方**（等待中的 `status --wait` 与 `definitions/*`），这是判定所需、每次处置都要，缺它时按读写记录失败结束、不处置；报告前缀上的读判定明细（`jobs/` 下被点名的明细，`s3:GetObject`）与写报告（`s3:PutObject`，`index/manifest`）只为生成报告、可不授，缺这两项时结束写照样写成、这个 run 没有报告并给出原因（0054 决策七、八）；两个推进 Lambda（`{prefix}kicker`、`{prefix}reconciler`）上的 `lambda:GetFunction`（报告前缀比对，见下 preflight 节「产物前缀一致性」条）。不需要 `lambda:InvokeFunction`（处置方不唤醒推进，0054 决策八），也不需要 `s3:ListBucket`：没有列举权限时取不存在的键得到拒绝访问，明细键按读写失败如实说明（0054 决策七「报告」）；取不到 jobs 对象时不论得到哪种错误，都按读写记录失败说明、不处置（[0030](./0030-realtime-persistence-seam.md) 决定六「jobs 对象取不到时」一项）。**S3 `run_id` 时要列出这个后端里的 run，另需上述 `list-runs` 的两项。**部署方（`gherkai deploy`，[0037](./0037-distribution-and-packaging.md) 决策 6）**另需：VPC 取值三态比对 `cloudformation:DescribeStacks` + **`RemovalPolicy.RETAIN` = 表/桶/ECR（防误删），其余随 stack 销毁**：2 张 DDB 表 + artifacts 桶设 `RETAIN`（承载 run 数据/产物，误删代价高）；**ECR repo 也设 `RETAIN`**（保住已 push 的镜像，且非空 repo `cdk destroy` 本就删不掉）。可随 stack 销毁的（cluster/task-def 模板 revision/stack 写的 SSM 参数（含数据版本参数与版本戳，资源清单 11.）/日志组/schedule group）用默认/`DESTROY`；schedule group 删除时其中运行期建立的触发（含还没有到点的）一并删除（资源清单 15.）。另有两类不归 stack 管理、`destroy` 不删（[0038](./0038-worker-image-delivery.md) 引入）：`push-worker` 与 deploy 派生注册的各 variant task-def revision，以及命令写入的 SSM `worker-variant/*` 与 `worker-default`。`destroy` 不读也不比数据版本（[0037](./0037-distribution-and-packaging.md) 决策 7）。**代价（运维须知）**：`gherkai destroy` 后表/桶/ECR **残留、需手动删**（`aws dynamodb delete-table` / `aws s3 rb --force` / `aws ecr delete-repository --force`）；否则同 prefix 重新 deploy 会因资源已存在而处理为导入/冲突。拆除之后未结束的 run 再没有人结束（定时触发随 group 删除，推进 Lambda 也不在），也不能靠重新部署接着处理，所以拆除之前先让执行中的 run 结束，或用 `settle-runs --backend cloud` 记为已结束（它要用后端的两个推进 Lambda 核对报告前缀，拆除之后执行不了）；保留的 runs 表里未结束的 run 随 runbook 的删表一并删除。Device Farm 项目 `{prefix}devices` 由 `deploy` 在 cdk 之前用 SDK 找回或建立、不归 stack 管理，`destroy` 不删，项目连同其中的会话记录与录像一起保留，须手动删除（`aws devicefarm delete-project --region us-west-2 --arn <项目 ARN>`，[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 10）。清理 runbook 见 `docs/user-guide/cloud-backend.md`「拆除与清理」节。

## 命名：资源名由一个前缀推出

**问题**：一个 AWS 账户下可能有**多套**环境（prod/stage）；逐个资源改名不可维护。

**决策：名字类资源的名字由 `--prefix` 推出，没有给单个资源另起名字的入口。**

- **`--prefix`**（默认 `gherkai-`）决定**所有名字类资源**的名字——`{prefix}runs`/`{prefix}events`/`{prefix}artifacts`/`{prefix}cluster`/`{prefix}novaact-worker`/`{prefix}midscene-worker`/`{prefix}kicker`/`{prefix}reconciler`/`{prefix}exit-observer` 等（task-def 用引擎规范名 `novaact`，非 `nova`；三个 Lambda 名 cli 侧 preflight 也按此拼，见「资源清单」12.）。**CDK 部署吃同一 prefix**（`gherkai deploy --prefix prod-`，命令拼成 `-c prefix=`），故 CDK 建的名 = cli 推出的名 → **单一事实源、不漂移**。`--prefix prod-` 一键切整套。**命名真源的落位演进**：曾因「CDK 独立工程、不能 import `gherkai_cli`」在 `iac_aws_backend/names.py` **复刻**一份命名函数（双写、靠对拍测试防漂移）；组合根共享层抽为平级包（今 `runtime/gherkai_runtime`）后（[0016](./0016-execution-architecture-core-lib-run-model.md)「演进」节），命名纯函数移入零依赖的 `runtime/gherkai_runtime/names.py`，部署包直接 import（`gherkai_deploy_aws.names` re-export；workspace 源 `gherkai-runtime = { workspace = true }`）——复刻消除、护栏测试转为「真同源」的结构性保证。
- **云端后端不接受给单个资源另起的名字**：没有给表、桶或别的资源单独起名的参数、环境变量或配置键（只供本机后端的 `--app-bucket`、`--device-farm-project-arn` 在云端不生效，[0053](./0053-project-config-file.md) 决策 3）。一个云端后端由前缀、区域与凭证所属的账户定位（[0041](./0041-agent-facing-cli-affordances.md) 决策六），命令行工具读的数据版本参数、读写的 runs 表与产物桶、探测的各项资源都属于这一个后端（被拒方案见本节末「给表与桶单独起名的覆盖层」）。

**护栏（必记）：**
- **CDK↔cli prefix 必须一致**：prefix 是 CDK 与 cli 的**共享约定**。若 `gherkai deploy --prefix prod-` 但 cli 跑时用默认 `gherkai-`，cli 会拼出 `gherkai-events` 去连——那张表不存在。这不是缺陷，是按前缀定位的固有耦合；靠云端命令开头的数据版本比对与 preflight（见下）在启动时探出并**报错点名 prefix**，不静默跑到一半炸。
- **prefix 含分隔符、原样拼**：默认 `gherkai-` 自带连字符 → 名 `gherkai-runs`。用户给 `--prefix prod`（无连字符）会拼成 `prodruns`——**分隔符由用户负责**（与 [0016](./0016-execution-architecture-core-lib-run-model.md) 的 S3 key 前缀不同：那里组合根在 `--report-dir` 非空且无尾 `/` 时补 `/`；资源名 prefix 组合根不猜、不补，原样拼、文档写明）。
- **prefix 长度上限由带 prefix 的资源名里最紧的一条推出（今为 47），由合成期校验守**：最紧的是 Scheduler 执行 role `{prefix}timeout-scheduler`，IAM role 名上限 64 个字符，容 47；其次 Lambda `{prefix}exit-observer` 容 51、桶名 `{prefix}artifacts` 容 54。schedule group `{prefix}schedules` 按与 schedule 名相同的 64 个字符计容 55：group 名的长度上限没有核过，是前提（资源清单 15.「前提」），在这个前提下它不是起约束的那一项。role 名的基名与 IAM 的名字上限都在 `runtime/gherkai_runtime/names.py`（stack 的 role 名经同一基名拼出），上限由 `prefix_max_len()` 按公式推出、不写死。一次性 schedule 的名字不带 prefix、长度固定（资源清单 15.），不参与这条上限。`BackendStack._validate_prefix` 在合成期 fail-fast，报错给出上限与当前长度、说明起约束的是那个 IAM role 名；`gherkai deploy --prefix` 的 help 同样注明上限。超出即合成失败，不会部署出一个缺了某类资源、或某类调用每次被拒的后端。代价：deploy 在调 cdk 之前就找回或建立 Device Farm 项目（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 10），超长 prefix 在合成期被拦下时账户里已留下 `{prefix}devices` 项目（destroy 也不删它，须手动删除）；若要避开，可把校验移到 provider 的 deploy 路径上、排在找回或建立项目之前。**摘要长度取舍**：一次性 schedule 名里的摘要取固定的 20 位 hex（80 bit），同一 group 内碰撞概率可忽略；名字长度因此固定（job 到点停止 32 个字符、run 级 30 个），不随 prefix 变化。**被拒方案：一次性 schedule 放在 default group、名字带 prefix**——见资源清单 15.「依据」与「被拒」。
- **被拒方案：把 prefix 写进 SSM 让 cli「发现」**——否决。prefix 是 cli 定位资源的**钥匙**，不能又是它要去发现的输出：SSM 路径固定则多环境互相覆盖，路径含 prefix 则「要先知道 prefix 才能读 prefix」= 循环依赖。多环境的区分标识（prod/stage）本身就是 prefix，没有「先于 prefix」的东西定位它。故 prefix 只能是**输入**（`--prefix` / 默认）。
- **被拒方案：给表与桶单独起名的覆盖层**（`--ddb-table`、`--s3-bucket`，环境变量 `AWS_DDB_TABLE`、`AWS_S3_BUCKET`，项目配置文件 `[cloud]` 节的 `ddb-table`、`s3-bucket`；给出完整的名字、不经前缀）：后端由 `deploy` 按一个前缀建全套，`deploy` 没有给表或桶单独起名的入参，事件流与推进 Lambda 只认这一套，命令行另指一张表或一个桶，指到的不是这个前缀对应的后端。前缀指向后端 A 而表名指向后端 B 的表时，数据版本比的是 A 的参数、读写的是 B 的记录；桶指向另一个写得进的桶时，运行定义的 jobs 对象写进后端的推进 Lambda 读不到的地方（它只有自己那个桶的权限）。这个方案里能另起名字的只有 runs 表与桶两项，events 表、集群与三个 Lambda 都只按前缀取名，覆盖其中两项得不到一套自洽的资源（owner 2026-11-25 认定不设）。

## VPC 来源：三种取值可指定（默认建新，均公有子网出网、零 NAT）

> 历史注（[0037](./0037-distribution-and-packaging.md) 决策 6 实装后）：「默认建新」已取消——`gherkai deploy --vpc default|new|<vpc-id>` 必给、无隐式默认（漏 context 合成危险变更集的坑由命令封死），三种取值能力一一对应；下文 `-c vpc_id=` / `-c use_default_vpc=` 是包化前的裸 cdk 写法，今由命令按 `--vpc` 拼出，且生效取值随 stack 写进 SSM 供三态比对。

Fargate awsvpc 模式要 VPC 的 subnet/sg。**VPC 从哪来是部署决策、不焊死**——三种取值（CDK context 优先级）：

- **复用现有**（`-c vpc_id=vpc-xxx`）：`Vpc.from_lookup(vpc_id=…)`——用账户已有 VPC。
- **用默认 VPC**（`-c use_default_vpc=true`）：`Vpc.from_lookup(is_default=True)`——账户 default VPC。
- **建新**（都不给，默认）：`Vpc(max_azs=2, nat_gateways=0)`——全新 VPC，**零 NAT**。

**三种取值统一走公有子网 + `assignPublicIp=ENABLED` 出网、零 NAT 成本**：worker **只出不入**（连 AgentCore/Bedrock/S3/DDB），公有子网 + 公网 IP 即够、无需 NAT Gateway（常驻计费 ~$32/月）；安全组是本 stack 新建的 worker 安全组 `WorkerSg`（出站全开、无入站）。subnet 选取「优先 VPC 的公有子网、无则回落私有」**只有一处落点**（`BackendStack._worker_subnet_ids`）。起 worker task 的只有 reconciler / kicker 两个推进器，两者经 `_advancer_function` 共用同一份 env，其中的 `SUBNETS` 由 `_worker_subnet_ids` 生成，kicker 起的首批与 reconciler 续起的 task 因此落在同一批子网；选取出错只在 RunTask 时才暴露，合成测试锁定两个推进器的 `SUBNETS` 相同、由 subnet 资源的 Ref 拼成且不为空。`assignPublicIp` 由推进器的组合根缺省为 `ENABLED`（IaC 不注入 `ASSIGN_PUBLIC_IP`，见「资源清单」12.），与公有子网配套。**为何默认建新而非默认复用**：建新自包含、无外部假设（不依赖账户已有 VPC 的存在/形态），且零 NAT 后无常驻成本代价。**「默认建新」对增量 deploy 是陷阱（实测踩过）**：CDK context 不进 stack state，后续每次 `diff`/`deploy` 都必须重带与首次部署相同的 vpc context——对以 `use_default_vpc=true`（或 `vpc_id`）取值部署的环境漏给该 context，CDK 即按默认取值合成「新建整套 VPC + WorkerSg 换 VpcId（replacement）」的变更集；护栏 = deploy 前先 `cdk diff`（带同一组 context），见到 VPC 级资源出现在 diff 里即停下查 context（`docs/user-guide/cloud-backend.md`「VPC 的三种取值」节有同一警告）。

- **被拒（曾经的建新取值）：`nat_gateways=1` + 私有子网出网**——曾想让建新取值做「私有子网隔离」，但 `_worker_subnet_ids` 恒优先公有子网、推进器的 `assignPublicIp` 恒 ENABLED，NAT 会被建却从不承载 worker 流量（空转计费 + 隔离承诺落空）。故建新取值也走公有子网、零 NAT。**真私有隔离留 backlog**：需同步 `_worker_subnet_ids` 选私有子网 + 在 IaC 给两个推进器注入 `ASSIGN_PUBLIC_IP=DISABLED`，届时再作第四种取值或改建新取值语义。

## preflight fail-fast：用已解析 prefix 探资源存在性，错误点名 prefix

**目标**：别跑到一半才因「表/cluster/task-def/Lambda 不存在」炸；启动即探、报错点名缺的资源与所用的 prefix（这个前缀下没有部署后端由开头的数据版本比对报出，见下「先于本节的探测」条；桶不探测，桶有错时在哪一步报出，见下「preflight 探哪些资源」条）。

**决策：云端 `submit` 在建 run 之前另做一次资源 preflight**（`compose.preflight_cloud_resources`，探测不过以退出码 2 结束；它与本机 `RunPersistence.begin` 里（`create_run` 之前）的 Store 探活是两回事，云端 Store adapter 的 `preflight()` 不参与，见 [0030](./0030-realtime-persistence-seam.md) 决定七），**不引入 SSM 存 prefix**。

- **先于本节的探测**：云端命令开头第一件事是比云端后端接口版本（读这个前缀下的数据版本参数，[0037](./0037-distribution-and-packaging.md) 决策 7）；不读 AWS 的入参校验在它之前（「资源清单」3. 里报告前缀与保留前缀的检查）。前缀给错（这个前缀与区域下没有部署后端）时在那一步以读不到数据版本结束，说明里点名参数的路径（含前缀）与区域，不先报资源不存在；接口版本不同时也在那一步结束，不探本节的资源。
- cli 用**已解析的 prefix** 拼出 cloud 资源名，启动时探存在性（`DescribeTable`/`DescribeClusters`/`DescribeTaskDefinition`，`submit` 另有 `GetFunction`）。
- 探测得到别的错误（拒绝访问、限流、网络）时带上原错误、说明读不到这项资源，同样以退出码 2 结束，不说成资源不存在；不给 `run_id` 的 `settle-runs` 与 `list-runs` 核对索引时的 `DescribeTable` 同此。
- 不存在 → fail-fast 退 2，**错误信息带上 prefix**：如「用 `--prefix=gherkai-` 拼出的表 `gherkai-events` 不存在」；只陈述缺的是哪一项、名字怎样拼出，不断定原因（数据版本比对已通过，这个前缀下有部署过的后端）。
- **preflight 探哪些资源**：云端后端只有 `submit`（[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 A），它建 run、交后端推进，**恒探** runs 表 + events 表 + cluster + **本 run 用到引擎的 task-def**，另探事件驱动链三 Lambda（下条）。**不探测桶**：用户一侧的资源检查（云端命令的 preflight 与 `doctor --backend cloud` 的资源行，[0041](./0041-agent-facing-cli-affordances.md) 决策四）都不探测它。理由：普通桶的 `HeadBucket` 要的授权动作是 `s3:ListBucket`，与用户一侧不授不带前缀条件的列举（上「资源清单」末段编排进程角色）相抵，按最小权限授予的提交者会在探测这一步被拒；这个前缀与区域下没有部署后端时，命令在开头的数据版本比对那一步结束（上「先于本节的探测」条）；表与桶的名字由同一个前缀推出，前缀对时桶名就是这个后端的桶。表的探测照不出的是桶这一侧的问题：后端的桶在部署之后被改动过，或提交者没有被授予桶上的写；这时由第一次读写对象的那一步失败，说明里点名桶：通常是建 run 时写 jobs 对象（[0030](./0030-realtime-persistence-seam.md) 决定六「建 run 是条件写」条，这一步失败时什么记录都没写下），带设备目标时是在它之前的上传安装包，两处的失败说明都点名桶。
- **task-def 与事件驱动链 Lambda 已纳入 preflight（原「暂不探」护栏兑现反转）**：task-def 即上条「恒探」那组里那项（`DescribeTaskDefinition`，按本 run **实际用到**的引擎探、**不探全注册表**）——反转理由 = 原先该维度的 prefix 配错要漏到 RunTask 才炸（退 1、不点名 prefix）。`submit` 另探事件驱动链三 Lambda（kicker/reconciler/exit-observer，`GetFunction`）——链上任一缺，提交会成功而 run 不按正常的链推进：缺 kicker 时首批 job 不启动、这个 run 的两次定时触发也不建，缺 reconciler 时起首批之后没有由事件驱动的推进，缺 exit-observer 时退出记录写不进；这样的 run 记下什么结果、在何时结束，取决于还剩下的触发与用户一侧的处置（后端到期结束的前提见 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九第 1 条），preflight 把它挡在提交前。探针全为只读（Describe*/Get*），submit 机器权限面仍无任何 ECS 写/执行权限（[0034](./0034-detached-batch-reconciler.md) 最小权限卖点不破）。
- **产物前缀一致性**（存在性之外唯一**会致失败**的语义探针；另有 `MAX_CONCURRENCY` 超 cap 提示、不致失败，见 [0034](./0034-detached-batch-reconciler.md) 机制四）：`submit` 在提交前比对；云端两个处置方（等待中的 `status --wait`、`settle-runs`）对未结束的 run，在一条命令里第一次处置得出结果之后、开始等待或写下处置之前比对一次，已结束的 run 不比对（时机与理由见 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策八「云端处置方的报告前缀」条）；三处调同一个函数。运行定义里没有这个 run 的报告落点，这项比对是两个来源之间唯一的核对。云端后端的产物前缀有**两个独立来源**——提交侧 `--report-dir`（提交一侧不在它之下写对象，用户与查询命令按它找这个 run 的产物；云端提交记录的 jobs 对象在桶根下的定义前缀里，不随它变化，见「资源清单」3.）与推进侧 Lambda 的 `REPORT_DIR` env（判定真值 `jobs/`、RunReport `index/manifest`、worker 产物、job-in 全按它落；IaC **有意不注入**、由 Lambda 内缺省 `reports` 供给，见「资源清单」）。两者不一致时提交成功、run 也跑得完，但**结果落在用户没指定的前缀下**（用户在自己给的前缀里找不到报告）——典型「不可达但代价高的静默失败」，在提交前挡在源头；处置方不一致时则会读不到推进侧写下的明细、把报告写到推进侧之外的前缀，同样在写下处置之前挡下。**实现即复用已有探针**：`lambda:GetFunction` 的返回体已含 `Configuration.Environment`，submit 因此零额外 AWS 调用与权限；处置方另发这两次调用，客户端与其它云端客户端同一个会话（profile、region），权限与 submit 是同一项。比对**两个推进器**（kicker/reconciler；exit-observer 不读 `REPORT_DIR`、不比），env 缺该键视作 Lambda 侧缺省 `reports`，两侧过同一分隔符规范化再比（`reports` 与 `reports/` 不算冲突），不一致即退 2 并**点名两侧值**，给使用者的修法只有一条：改 `--report-dir` 使它与后端一致。不把「在 CDK 给推进器注入 `REPORT_DIR`」作为产品给出的修法：后端的报告前缀没有部署入参（「资源清单」12.），改 IaC 属部署方自行改动后端，取成保留前缀（「资源清单」3.）等后果由那次改动承担，比对之后、run 执行期间才改的同样如此。与桶根下的保留前缀重叠的 `--report-dir` 不到这项比对，在入口解析之后就以退出码 2 结束（规则与理由见「资源清单」3.「报告前缀不与这两个保留前缀重叠」一句）。**为何选「比对 fail-fast」而非「云端后端拒绝非默认值」**：后端的报告前缀没有部署入参、取 Lambda 内的缺省（「资源清单」12.），所以在产品给出的配置之内两种做法放行的 `--report-dir` 相同（`--report-dir` 在云端后端是查询命令定位 run 落点的参数，[0016](./0016-execution-architecture-core-lib-run-model.md)「单 S3 桶 + `--report-dir` 复用为 key 前缀」、[0041](./0041-agent-facing-cli-affordances.md) 决策六），差别只在说明与比对的位置：比对拿使用者的值与推进侧实际所用的值比，说明点名两侧的值，推进侧的值被部署方改过时同样核得出不一致；拒绝非默认值拿它与命令行工具里的缺省比，说明只能说云端只接受缺省，推进侧的值被改过时核不出，结果落在使用者找不到的前缀下。
- **job-in S3 对象生命周期**：`FargateEngine` 每 scope `PutObject` 一个 `jobs-in/<quote(scope_id)>.json` 对象（`start_scope` 经 `_put_job_and_run_task`；因 RunTask overrides 8192 上限塞不下含 feature 的 job）——喂 worker 的一次性输入、worker `GetObject` 读完即无用，无清理会随 run 堆积。**决策：S3 lifecycle 自动过期（7 天），按对象 tag `gherkai=job-in` 过滤——不用 key 前缀**。
  - **为何 tag 而非前缀**：job-in 落 `<report_dir>/<run_id>/jobs-in/`（run_id 在 key 中间），S3 lifecycle 的 filter 是**纯前缀**、框不住中间的 run_id；且同 `<run_id>/` 前缀下还有判定真值 `jobs/` 与报告 `index/manifest`（长期保留、误删代价高），前缀规则会误伤。tag 精确只框 job-in——`FargateEngine._put_job_and_run_task` 上传时打 `Tagging="gherkai=job-in"`、CDK 桶挂 `LifecycleRule(tag_filters={"gherkai":"job-in"}, expiration=7d)`。判定真值/报告不打此 tag、不受影响。
  - **7 天**：对齐 events 表 TTL 心智（输入/协调类脚手架，留窗口供事后调查失败 run，之后自动清）。
  - **打 tag 在推进器、非 worker**：`put_object` 在 `FargateEngine`（推进器 Lambda 一侧的组合根注入的 s3_client、Lambda 执行角色的凭证，见「资源清单」10.）上跑，worker 只 `GetObject` 读——故**无需给 worker task role 加 `s3:PutObjectTagging`**（避免为清理反而扩 task role 权限，与「IAM 最小权限」一致）。
  - **真跑验证**：cloud job 真跑后核实真 S3——job-in 对象带 `gherkai=job-in` tag、判定真值 `jobs/` 无 tag（lifecycle 精确不误伤）、桶 lifecycle rule 生效。护栏：core `test_start_scope_job_in_tagged_for_lifecycle` + iac `test_artifacts_bucket_job_in_lifecycle`（含「不得用 Prefix filter」负向护栏）。
  - **已知边界（可接受）**：tag 过滤不追溯——部署此 lifecycle **之前**写的旧 job-in 对象无 tag、不被本规则清理；要清需一次性手动删（`aws s3api list-objects-v2 ... jobs-in/ | delete`），非本规则职责。

## 2 镜像：Nova / Midscene 各一（依赖环境本质不同）

**决策：两个容器镜像 + 两个 task-def，不合并。** 两个引擎 worker 运行时依赖差异大、合并镜像既臃肿又耦合升级：

- **Nova 镜像**：Python 3.13 + `nova-act`（含 boto3 / bedrock-agentcore / **playwright 库**）。入口 `python -m gherkai_worker_novaact`。
- **Midscene 镜像**：Node ≥22（基础镜像 `node:22-slim`，与包 `engines.node` 同源，[0037](./0037-distribution-and-packaging.md) 决策 3；代码本身也要 `AbortSignal.timeout`/`fs recursive`/`Dirent.parentPath`）+ 包 `dependencies` 的全部运行时依赖（`tsx`、`@midscene/web` 与 `@midscene/core`、**playwright 库**、设备目标经 Appium 驱动远程设备用的 `webdriverio`、全部 `@aws-sdk/*`（含 Device Farm 客户端）、`openai` 等；清单以 `engines/midscene/package.json` 为准）。入口 = 包 bin `gherkai-worker-midscene`（→ `dist/bin.mjs`）——**本进程即 worker**、不套包装进程（中间多一层就吞掉 EVENTS_FD 的 fd 继承，[0024](./0024-worker-core-protocol.md) 三通道）。
- **不装 chromium 二进制（真跑证实）**：桌面目标上两个引擎 worker 都用 `connect_over_cdp` 连 **AgentCore 云浏览器**（浏览器跑在云端），playwright 只作 **CDP 客户端库**、**不 launch 本地 chromium**（设备目标上 Midscene 经 Device Farm 远程访问会话驱动真机上的浏览器或应用，同样不在容器内起浏览器）——故只需 playwright 库（pip/npm 已装）、**不需 `playwright install chromium` 的二进制 + 系统库**（省几百 MB、build 快得多）。真跑核实：去掉二进制后 worker 走到 `connect_over_cdp` 那步（连 AgentCore WebSocket），从不报缺 chromium。
- **构建平台 `--platform linux/amd64`（必记坑）**：Fargate task-def 默认 `X86_64` runtime；arm Mac（M 系列）build 不加则出 arm64 镜像、Fargate 容器启动期 `exec format error` 挂死（错误在启动期、不易一眼看出是架构问题）。
  - **构建陷阱（历史，已消解）**：Midscene 曾把运行时真需要的 SDK（`@midscene/web`/playwright/bedrock-agentcore/signature-v4/openai）大多放在 **devDependencies**，只有 `client-dynamodb`/`client-s3` 在 dependencies，故当时 Dockerfile **不能用 `npm install --production`**（会漏装）。[0037](./0037-distribution-and-packaging.md) 决策 3 实装后运行时依赖（含 `tsx`）已全在 `dependencies`——被消费的 npm 包只装 `dependencies`、不挪即崩——且基础镜像改为按版本 `npm install -g @gherkai/worker-midscene`（发行前验镜像时装本地 tarball），本陷阱不再可触发。

镜像入口 CMD = 现有 subprocess cmd 去掉 stdin/fd 传输（job 走 S3、events 走 DDB，[0024](./0024-worker-core-protocol.md)）——worker 引擎逻辑不因执行环境变（[0016](./0016-execution-architecture-core-lib-run-model.md)）。

## container 名约定：`{engine}-worker`（不带 prefix）—— CDK↔cli 硬契约

**CDK 建 task-def 时，其内部 container 元素名必须恰为 `{engine}-worker`（`novaact-worker` / `midscene-worker`，不带 prefix）。** 这是命名真源 `gherkai_runtime.names.container_name` 定的名，CDK 侧必须兑现，否则 cloud 每个 run 都炸：

- **为什么不带 prefix**：container 是 **task-def 内部**名、随已带 prefix 的 task-def 走（task-def family 已是 `{prefix}{engine}-worker`），再叠 prefix 冗余。故 container 名只用引擎规范名 `{engine}-worker`。
- **为什么是硬契约**：core 的执行 adapter `FargateEngine`（`core/gherkai_core/adapters/fargate_engine.py`）RunTask 用 `overrides.containerOverrides[].name = {engine}-worker` 把 `JOB_S3_URI`/`EVENTS_DDB_TABLE`/`RUN_ID`/`SCOPE_ID`/`AWS_REGION`/`ARTIFACT_S3_*` 注进容器。ECS 要求该 name 与 task-def 里的 container 元素名**逐字匹配**，否则 RunTask 报 `container ... does not exist in task definition`——env 注入全落空、worker 拿不到 job/events/落点。
- **单一事实源**：与 task-def family 名（`{prefix}{engine}-worker`）、prefix 一致护栏同理——CDK 侧 `stack.py` 直接调用同一函数（`add_container(names.container_name(engine))`），契约由共享命名真源结构性保证。
- **归哪个数据版本**：容器名与由前缀推出的各资源名归云端后端接口版本，改名要给它加号；cluster 名 `{prefix}cluster` 属跨版本不变的约定，清扫按它与 task 启动时贴的 `startedBy` 列出别的版本起的 task（[0037](./0037-distribution-and-packaging.md) 决策 7、[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九）。

## task-def 不焊 region/凭证（决策 C 的非对称落到 IaC）

- **task-def 不设 `AWS_REGION`**：worker 的 region 只有一个来源，即推进器的组合根经 **RunTask overrides 的 `containerOverrides.environment`** 注入的部署所在区域（与推进器自己建 client 用的是同一个值，见「组合根接线（非 IaC）」节「Fargate 配置参数」条；注入前须是具体字符串的理由见 [0016](./0016-execution-architecture-core-lib-run-model.md) 决策 C）；task-def 里再写一份就有了两个来源。
- **task-def 不设 `AWS_PROFILE`**：Fargate 容器用 **task role** 凭证链（`AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` 由平台自动注）；注入 profile 名会 `ProfileNotFound` 盖过 task role（[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 C 的正确非对称——profile 只对 subprocess 有意义）。
- 凭证一律经 task role，不在镜像/task-def 里放任何 access key。

## IAM 最小权限（安全最佳实践）

**task role**（容器内 worker 的凭证）——按动作 × 目标资源收窄，不给通配：

| 动作 | 目标资源 | 引擎 |
|---|---|---|
| `dynamodb:PutItem` | events 表 ARN（`{prefix}events`）——**不给 runs 表**（worker 绝不碰 RunState，[0024](./0024-worker-core-protocol.md)「DynamoDB 作 events-out 传输」节的红线条）| 两个引擎 |
| `s3:GetObject` | artifacts 桶全部对象（`arn:…:{prefix}artifacts/*`；worker 读 job-in 用；定义前缀除外，见下面的显式拒绝）| 两个引擎 |
| `s3:PutObject` + `s3:AbortMultipartUpload` | artifacts 桶全部对象（与上一行同一条 statement）——**不给 DeleteObject**（worker 只上传+删本地，S3 侧只 Put，[0029](./0029-engine-artifacts-to-s3.md)）。`AbortMultipartUpload` 必给：`upload_file`（TransferManager，>8MB 走 multipart）分段失败时清理已传分段，缺则 abort AccessDenied + 孤儿分段计费 | 两个引擎 |
| 显式拒绝（`Deny`）`s3:GetObject` 与 `s3:PutObject` | 定义前缀下的全部对象（`arn:…:{prefix}artifacts/definitions/*`）——上两行整桶授权之内唯一的例外，整桶授权照旧、只多这一条拒绝。理由：worker 按设计不读也不改运行定义（runs 表不授，见本表第一行；[0024](./0024-worker-core-protocol.md)「DynamoDB 作 events-out 传输」节的红线条），云端提交记录的 jobs 部分放在这个前缀下（[0030](./0030-realtime-persistence-seam.md) 决定六「云端提交记录」条），这条边界随之延到桶里的这个前缀上。jobs 对象里没有令牌（令牌在提交记录的头里），这条拒绝守的是「worker 不读也不改运行定义」，不是保密。被拒：不加拒绝、把 jobs 对象与 job 输入同样对待（前提是 worker 镜像与确定性 step 代码是团队自己的）——运行定义的一部分就成了 worker 能读、也能改写的对象，worker 不碰提交记录这条边界在桶里断开 | 两个引擎 |

## 组合根接线（非 IaC）

`runtime/gherkai_runtime/compose.py`（产品本体，曾居 `cli/`——[0016](./0016-execution-architecture-core-lib-run-model.md)「演进」节）的 `build_engines` 只产 `SubprocessEngine`（两个引擎，local 执行），CLI 一侧的组合根只装配它；云端后端的执行 adapter `FargateEngine` 由 `build_fargate_engines` 装配，调用方是推进器 Lambda 一侧的组合根（云端后端只有 `submit`，[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 A）：

- **`build_fargate_engines`（对称 `build_engines` 的 dict）**：按 `job.engine` 造 `FargateEngine`（把 run 的 run_id + cluster + 按引擎选的 task-def + network + events 表名 + container-name + job-s3 + artifact-s3 + **SDK 产物落点 env** + 经 RunTask overrides 注入的额外 env（额外请求头、会话预热地址、Nova 单 act 超时，分别见 [0035](./0035-local-app-testing-via-tunnel.md) 决策 4、[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13、[0024](./0024-worker-core-protocol.md)「组合根持引擎特定的值」条）+ region 一起注入构造，对称已有 store 注入；**不传 profile**——决策 C 非对称）。
- **产物上传要注入两组 env、缺一不可（真跑暴露）**：worker `ArtifactUploader` 上传需要 ① `ARTIFACT_S3_BUCKET`/`PREFIX`（S3 落点）**和** ② SDK 产物本地落点 env（`NOVA_LOGS_DIR`/`MIDSCENE_RUN_DIR`，容器内路径，如 `/tmp/gherkai-run/<run_id>/{nova-trajectories,midscene-run}`）——uploader 用后者的父级算 `run_dir`/相对 key，**缺它 `run_dir=None` → uploader no-op → 报 `file://` → 产物写容器盘、STOPPED 后随盘销毁必丢**（ADR [0029](./0029-engine-artifacts-to-s3.md)）。subprocess 侧 `build_engines` 本就注入 SDK 落点 env，Fargate 侧曾漏（只注 S3 落点）——**只注 ①不注②等于没上传**。这两组按引擎不同（Nova `NOVA_LOGS_DIR` / Midscene `MIDSCENE_RUN_DIR`），组合根按引擎算好、`FargateEngine` 引擎无关地转发。
- **按引擎选 task-def**：`job.engine` → `{prefix}{engine}-worker`（对称 `EngineResolver` 按 engine 选 cmd）。（历史注：[0038](./0038-worker-image-delivery.md) 实装后**运行时不再由 family 名推导**——组合根必须收到 `worker_task_defs`（引擎 → task-def **revision** ARN；提交侧 preflight 按 variant 解析、写进 definition），RunTask 传**显式 revision、绝不传 family**（传 family 会取最新 ACTIVE revision、让一次推送劫持运行中的 run）；映射里没有的引擎装空腿、真去起它才抛。family 名本身不变、仍是命名契约（见上「资源清单」5. 与「命名」），只是不再作 RunTask 入参。）
- **Fargate 配置参数**：cluster、events 表与桶的名字由 prefix 推导；subnet 与安全组是 AWS 生成的 ID（不可预测、无法由 prefix 推导），取同一 stack 里得到的值；region 取 stack 所在区域（`REGION`）；这几项都由 IaC 注进两个推进器 Lambda 的 env（见「命名」「VPC 来源」两节），推进器的组合根读 env 造 `FargateEngine`，读 env 的是组合根、adapter 不 sniff env（[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 C）。
- **执行 adapter 按组合根分**：CLI 的 `run` 只有本机后端、只装配 `SubprocessEngine`；`FargateEngine` 只由推进器 Lambda 一侧的组合根装配，不实装 `Engine` port（决策 A 落到组合根的形态，[0016](./0016-execution-architecture-core-lib-run-model.md)；边界见 [0034](./0034-detached-batch-reconciler.md)「Engine port 演进」节）。
- **`--no-report` 只跳过落库、不改执行引擎**：`run --no-report` 只跳过 store 落库（`persistence=None`），执行引擎照旧是 `SubprocessEngine`。
- **真部署验证**：组合根接线（`build_fargate_engines`）与 CDK 工程本体（`iac_aws_backend/`）经真部署验证，范围是两个引擎 ×（确定性+AI）的执行全部通过、产出物三处核对。

## 已定的两项（原开放项）

- **Midscene region 全可配（修硬编码，不接受 east 固定）**：Midscene 的 AgentCore + Bedrock 模型连接此前用硬编码 `REGION="us-east-1"`（`engines/midscene/src/lib/agentcore-sigv4.mts` + `engines/midscene/src/worker/run-scope.mts` 的 `BedrockAgentCoreClient({region})`）——注入 `AWS_REGION=us-west-2` 时其 events/job/artifact 走 west、但浏览器会话+模型仍走 east（半贯通）。**决策：改成惰性读 `process.env.AWS_REGION`**（`getRegion()`/`getBaseUrl()`，与 I/O 边缘同源），使 region 真正全可配、与 Nova 侧一致（Nova 全程读同一 env、无此问题）。这样 Midscene task role 的 AgentCore/Bedrock 权限**不锁死 east**、跟注入的 region 走。（region=None 时的 fail-loud 语义随之统一，对齐 [0016](./0016-execution-architecture-core-lib-run-model.md) 决策 C。）**唯一的固定区域例外**：Device Farm 只在 us-west-2，worker 与 Python 侧的 Device Farm 客户端固定该区域，S3 与 SSM 客户端仍用后端所在区域（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 10）。
- **events 表开 TTL（worker 写时间戳）**：worker emit 时给每条 event item 多写一个 `expires_at`（epoch **秒**，= 写入时刻 + **7 天**），CDK 在该属性上开 DynamoDB TTL。**7 天的理由**：events 是协调/进度脚手架，权威数据在运行态与判定真值（[0030](./0030-realtime-persistence-seam.md) 决定三；events 归约完即死重）——但留 7 天窗口供事后调查失败 run（如「worker 到底 emit 没 emit scope_done」），几天后仍可查、又自动清、免手工清理。属性名 `expires_at`（DDB TTL 惯例、epoch 秒）；两个引擎 worker 对称写（Nova put_item / Midscene PutItemCommand 的 `{N}`）。**`expires_at` 兼作从 events 表归约事件时的时刻来源**：events 表没有别的时间属性，`DdbEventLog` 与 `tools/events_wallclock.py` 以 `expires_at` 减 7 天还原 worker 写入时刻；worker 写它时取整到秒，故 `submit --backend cloud` 的 step、scenario、scope 时长与 `explain --backend cloud` 从事件流补取的 step 时长都量化到整秒。7 天因此是两个 worker 与这两个读端共守的常量，改 TTL 须四处同步。整秒精度是已接受的边界，暂不加专用时间属性的理由、需要时的加法做法与被拒的「把 `expires_at` 写成带小数的值」见 [0024](./0024-worker-core-protocol.md)「时长的两种测量口径与整秒精度边界」条。TTL 是**最终清理、非精确**（DDB 可能延迟至 48h 才删过期项）。**过期项缺席并非无碍——无状态推进的全量重放读端恰恰依赖事件在场**（[0034](./0034-detached-batch-reconciler.md)：reconciler 每次都从 events 全量重放推演 RunState），故设三条护栏：① 退出记录（`task_exited`）**有意不写 `expires_at`**、不随 TTL 过期——重放判定 job 的进程已终止靠的是它（[0034](./0034-detached-batch-reconciler.md) 机制二「两件都要」）；job 的终态写下之前它若被清掉，重放把这个 job 推演为未退出，而 STOPPED 事件不会有第二次，这个 job 的真实结果就记不下来。已写下的终态不受影响（终态只写一次，[0031](./0031-job-lifecycle-states-and-severity.md) 决定一·补），未结束的 run 怎样结束见 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九第 1 条（含前提）与决策八；② TTL 的 `REMOVE` 记录**两层都滤**（events 表事件源 filter + reconciler handler 内再跳一次，见「资源清单」13.——事件源那道要重新部署才生效，handler 那道不依赖部署）；③ **已提交终态的 run，两个云端推进器一律不再重放**（[0034](./0034-detached-batch-reconciler.md) 端到端流程 ④）。②③ 免去对已结束 run 的白读与错算（两层各挡哪些触发见 [0034](./0034-detached-batch-reconciler.md) 端到端流程 cloud 一节「已收尾的 run 不再推演」条）：7 天后 worker 事件已清、只剩退出记录，已结束的 run 若被重放推演，会推演出「每个 job 都 error、零 scenario」；这样的结果写不进记录，执行方得知 run 已结束之后也不再存明细（[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策五），读者只认被终态点名的那一份判定真值（[0030](./0030-realtime-persistence-seam.md) 决定三）。

## 留待（defer）

- **镜像瘦身**：属施工，不在本 ADR 决策面。
- **build & push ECR 的自动化程度**：手动步骤曾由 `tools/build_push_workers.py` 固化（ECR 登录 + 两引擎 `docker build --platform linux/amd64` + push 一条命令）——**已退役**（[0038](./0038-worker-image-delivery.md)）：使用方按三行模板自己 build 定制镜像，部署方 `gherkai deploy push-worker` 推送并注册 revision（推送前校验 linux/amd64，把 Fargate 启动期 `exec format error` 提前拦下）；基础镜像由发布方的 CI 发 GHCR（[0037](./0037-distribution-and-packaging.md) 决策 8）、`gherkai deploy` 同步进使用方 ECR。使用方定制镜像的 CI 属使用方自己的流水线，不在本项目。

## 重议

- 若多环境需求超出「prefix 切名」（如跨账户、跨 region 多活）→ prefix 单层不够，重议是否引入 CDK context/环境配置文件。
- 若编排进程也上云（WebUI 后端跑在 AWS）→ 编排进程角色需正式建，届时并入本 stack。
