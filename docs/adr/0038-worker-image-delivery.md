## 背景与问题

[0037](./0037-distribution-and-packaging.md) 决策 5 定了 worker 镜像**两层分工**：发布方按版本发基础镜像到 GHCR，使用方在本地叠自己的确定性 step 构建定制镜像。本 ADR 定**最后一层怎么交付到云端后端并被 run 使用**。

**施工前**：每个引擎一个镜像；部署方用 `tools/build_push_workers.py` 从整个 repo 构建、推自己私有 ECR 的 `{prefix}{engine}-worker:latest`；task-def 由 IaC 建、镜像栏焊死 `tag="latest"`；RunTask 只传 task-def 的 **family 名**（ECS 取该 family 最新 ACTIVE revision）；CLI 完全不知道也不能选跑哪个镜像；「更新 steps」= 改 repo 里的脚手架文件、整体重建、重推 `latest`，下次起 task 自然拉到。使用方 build 时必须带 `--platform linux/amd64`，漏给的后果是 Fargate **启动期** `exec format error`（[0033](./0033-iac-aws-backend-and-composition-wiring.md) 记的坑）。

**要解的问题**：
- **多套 step 集并存**：不同测试开发 / 分支在同一个共享后端上各跑各的确定性 step 集而互不覆盖；跑时可选。单 tag cover 不了。
- **版本噩梦**：同一个 tag 名在不同人嘴里指不同内容。要让「用的是哪份」可见、可查、run 内一致。
- **所有权**：改共享后端用的镜像是一次部署变更，应归部署方；镜像**构建**是测试开发自己的容器工作，gherkai 不该拥有。默认画像 = 一人兼测试开发与部署方两顶帽子（同一台机器 build 完就推）；团队拆角色时权限边界要现成（角色模型与「帽子不是人」的一般化见 [0040](./0040-consumer-role-model-and-terminology.md)）。
- **架构错误提前暴露**：`--platform` 漏给的错误不该拖到 Fargate 启动期才炸，应在推送前 fail-loud。**不支持 ARM64**（被拒方案，理由见下）。

**AWS 事实（决定形状，均已对照官方文档）**：RunTask 的容器 override 字段全集是 command / environment / environmentFiles / cpu / memory / memoryReservation / resourceRequirements / name，**不能换镜像**；镜像与 `runtimePlatform` 都写在 task-def **revision** 里，revision 是不可变快照、无继承；RunTask 可传 `family`（最新 ACTIVE）或 `family:N`（精确）；task-def 镜像栏支持 `repo@sha256:<digest>`；`DeregisterTaskDefinition` 把 revision 置 INACTIVE——**不影响在跑的 task，但不能再用它起新 task，且注销后最多 10 分钟内这条限制可能尚未生效**；`DeleteTaskDefinitions` 永久删除 INACTIVE revision（有关联 task 时先 DELETE_IN_PROGRESS）；task-def 类 IAM 动作（Register / List / Describe）**不支持资源级权限，只能 `Resource: "*"`**；ECR 仓库 tag 可变性默认 MUTABLE；Fargate ARM64 的不可用面**按 AZ**（官方明列 us-east-1 的 `use1-az3`）。

## 概念模型

| 概念 | 定义 | 载体 |
|---|---|---|
| **基础镜像** | 由发布链发布的镜像 `ghcr.io/zhiyanliu/gherkai-worker-<engine>:X.Y.Z`，linux/amd64 单架构，零使用方内容（[0037](./0037-distribution-and-packaging.md) 决策 5） | GHCR |
| **variant** | 一套具名的确定性 step 集 = 一个定制镜像；名字由测试开发自取（`login`、`checkout-v2`）；基础镜像同步进 ECR 的那份固定叫 `base` | 使用方私有 ECR，tag = `<CLI 版本>-<variant>` |
| **默认指针** | 提交时不给 `--worker-variant` 就用哪个 variant；部署级一个；deploy 初始化为 `base` | SSM |
| **revision** | 每个（引擎，版本，variant）一个 task-def revision（同名 variant 在不同版本下各有各的；新注册的 revision 只被发起注册的那条映射引用，见「`push-worker` 流程」步 5）：从模板复制、镜像栏换成 `repo@sha256:<digest>`、以 tags 记血缘与退休时刻 | ECS task-def family `{prefix}{engine}-worker` |
| **模板 revision**（revision 的母本） | deploy 时 CDK 建出的那个 revision，承载 cpu / memory / task role / execution role / 日志组 / `runtimePlatform`（X86_64）等只有部署后才存在或全局固定的值；**镜像栏保留 `tag="latest"` 作占位**（CDK 必填；该 tag 在 ECR 里可以不存在）——它**永不被 RunTask**、只作复制母本；definition 缺字段按定义违约标 error、不回落（见「运行时与 preflight」节「读侧不留兼容路径」） | ECS；其 ARN 由 stack 资源写进 SSM |
| **架构** | 固定 linux/amd64；push-worker 推送前 `inspect` 校验，不匹配退 2 | 模板 revision 的 `runtimePlatform`，variant revision 原样复制 |

**tag 命名 = 单一真源、同时是单一校验点**：`gherkai_runtime.names.image_tag(version, variant)` → `<归一化版本>-<variant>`。PEP 440 的 `+`（本地段）与 `!`（epoch）不在 docker/ECR tag 字符集 `[A-Za-z0-9_][A-Za-z0-9_.-]{0,127}` 内（`1.4.0.post3.dev0+28c1684` 直接 `docker tag` 报 `invalid reference format`，实测），函数把 `+`/`!` → `.`、返回前按正则校验、不匹配即抛。同处新增 `names.ecr_repo_name(prefix, engine)`（= `task_def_name`），收拢曾散在 `stack.py` 注释与（已退役的）`tools/build_push_workers.py` 内联副本里的「ECR repo 名复用 task-def family 名」规则。

**tag 可变，replace 与否交给使用方**：重推同名 variant 直接放行、只在推送后打印「原 digest → 新 digest」。不设不可变仓库——bugfix 不想改 variant 名是正当需求，机制给到、用错不算产品欠缺。run 内一致性不靠 tag 靠 revision（下）。**护栏**：这条正确性依赖 ECR 保留被顶掉 tag 的 untagged 镜像（运行中 run 的旧 revision 按 digest 指着它），故 ECR 仓库**不设 untagged 过期的 lifecycle 规则**；代价是每次重推永久留一层 untagged 存储、随重推次数增长——记为已知运行期成本，回收与 `delete-worker` 同批设计（重议闸门）。

**定制镜像模板（唯一真源，[0037](./0037-distribution-and-packaging.md) 只指向此处）**：测试开发自己 build，任何本地名字，gherkai 不拥有构建；**必须 `--platform linux/amd64`**（arm Mac 上尤其）；**基础镜像版本须与使用方 CLI 版本一致**（`gherkai --version`）：

```dockerfile
FROM ghcr.io/zhiyanliu/gherkai-worker-novaact:<CLI 版本>
COPY steps/ /app/steps
ENV GHERKAI_STEPS_DIR=/app/steps
```

```
docker build --platform linux/amd64 -t acme-novaact:login .
```

## 命令族（全在 `gherkai-deploy-aws`，云端写操作归部署方）

- **`gherkai deploy push-worker <本地镜像> --engine <novaact|midscene> --variant <名> [--set-default]`**：推送一个本地镜像并注册为该引擎的一个 variant。一次一个引擎，两个引擎跑两次（两引擎镜像本就分别 build）。
- **`gherkai deploy list-workers`**：按 family 列 revision 并读 tags 与 SSM，输出各引擎当前版本的 variant、digest、推送时间、默认指针，以及已退休待清理与孤儿 revision；`--json` 出同一份内容的机读形态（字段表与 stdout/stderr 分流归 [0041](./0041-agent-facing-cli-affordances.md) 决策三）。**待清理条目**（随「不变量」清理 pass 条把静默期起点归一到 `gherkai:retired-at`）：只列不在任何版本的 `worker-image/*` 映射里、带血缘 tags 的 ACTIVE revision，判据与清理 pass 的候选判据是同一份（全部版本映射所引用的 revision ARN 集合）。`reason` 仍是 `retired` / `orphan` 闭集：带 `gherkai:retired-at` 的为 `retired`，`retired_at` 即静默期的起点，替换映射时打上的与清理 pass 补打的不再区分；还没有这个 tag 的为 `orphan`（`retired_at` 为 null），之后的清理 pass 在满足补打条件时（注册时刻早于那一趟开始读映射的时刻）给它补打，此后列为 `retired`。文本形态照旧：`retired` 行写「已退休 <时刻>」，`orphan` 行写「孤儿：无任何版本的映射引用」。仍在某个映射里的 revision 不列为待清理，即使它带着 `retired-at`：那是之后的清理 pass 会摘掉的 tag，它是在用的 revision。曾有的布尔字段 `still_mapped` 与对应文本已删除（被拒方案「在 `list-workers` 里把『已退休、仍被映射引用』单独标出」条）；它没有随任何发行版发出，删去它不破坏已发布的契约（0041 决策五的加法兼容）。字段登记在 `--json` 字段契约页，由 0041 决策五的护栏对照真实输出核对。
- **`gherkai deploy delete-worker`**：留口子，落地时套同一套清理 pass 语义（退休 tag + 静默期 + 运行中 run 引用检查，见「不变量」；静默期一律从 `gherkai:retired-at` 起算、缺这个 tag 的由清理 pass 补打；引用检查读状态分组索引的 `live` 分组，同见该条）。
- **`gherkai deploy` 的 worker 镜像四步**：登记模板（随 cdk 事务）、同步基础镜像为 `base`、初始化默认指针、重派生既有 variant（后三步在 cdk 之后）。
- **`push-worker` 与 `list-workers` 的前置**：先读 SSM `version` 戳与自身版本比对，**原样沿用** [0037](./0037-distribution-and-packaging.md) 决策 7 的三态——CLI **新于**后端 → 退 2 并指向「先 `gherkai deploy`，或用与后端同版本的 CLI（`uvx --from 'gherkai[deploy-aws]==X.Y.Z' gherkai deploy …`）」；CLI **旧于**后端 → 警告不拦；戳缺失 → 警告不拦；非纯净版本跳过；决策 7 不设放行口，此处同样没有。否则 CLI 跑在后端前面的人会把镜像静默推进一个没人解析的版本命名空间，而提交者的 preflight 提示又把他推回同一步、形成死循环。**`gherkai deploy` 的四步不做此前置**——deploy 本身就是改戳的动作（第 1 步随 cdk 事务写入新戳），前置在 cdk 前会把自己拦死、在 cdk 后恒真。
- **定制镜像的构建不在命令族里**：模板见上。

## `push-worker` 流程

1. **解析目标**：ECR repo = `names.ecr_repo_name(prefix, engine)`、tag = `names.image_tag(CLI 版本, variant)`；region/prefix 与 `gherkai deploy` 同一解析链；版本 skew 前置（上）。
2. **容器引擎 `inspect` 本地镜像**：取**存在**与**架构**；架构 ≠ linux/amd64 → 退 2，提示 `docker build --platform linux/amd64`——把 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 记的启动期 `exec format error` 提前到推送前；本校验在**任何 ECR/ECS 调用之前**（先于它的远程读只有两次 SSM 点读：步 1 的 skew 前置与本引擎模板 revision ARN）。**本地引用是多平台索引时**（containerd 镜像存储——Docker 29 起新装的缺省、GitHub 托管 runner 亦然）：`inspect` 顶层给的是本机平台那一份的视图——本机平台的内容不在时（amd64 主机只拉了 arm64；arm 主机上按文档只构建 linux/amd64）`Os` / `Architecture` 是空串、`Descriptor` 是 index，此时再问一次目标平台的视图（`inspect --platform linux/amd64`）——本机有 linux/amd64 的内容才算匹配；索引列了该平台却没拉取内容（视图两字段仍为空）或根本不含该平台（引擎报「找到了镜像但没有这个平台」）都拒，提示只构建 linux/amd64 一个平台。旧的 overlay2 存储装不下索引、`inspect` 恒给单平台视图：arm Mac 上得到 arm64、被拒（实测项 7）。**此时不取 digest**——推送前 `inspect` 读到的东西不证明仓库里有这份内容：`RepoDigests` 随镜像存储而不同（overlay2 存储下未推送的镜像为空；containerd 镜像存储下构建后即有本地名一条、`tag` 到 ECR ref 后即有该 repo 一条，都没有推送，实测项 6），`.Id` 在 overlay2 存储下是 config digest、**不是** `repo@sha256:` 需要的 manifest digest（拿它注册 ECS 只校格式、RunTask 拉镜像时才 `manifest unknown`）。
3. **ECR 登录**：boto3 `ecr:GetAuthorizationToken` → 引擎 `login`。
4. **推送**：引擎 `tag` + `push`；**digest 的唯一来源 = `push` 成功返回之后对目标 ref 再 `inspect`，取 `RepoDigests` 中匹配本 ECR repo 的那一条**。只在推送成功之后取：`push` 以非零退出码失败即报错、走不到读 digest 这一步，读到的就是仓库已收下的那份内容——这在两种镜像存储下都成立；containerd 镜像存储下本 repo 的条目在 `tag` 时就已出现，推送前读到它不说明推送过（步 2）。按本 repo 挑：基础镜像同步路径先 `pull` 过 GHCR，`RepoDigests` 会有多条，不得取第一条。目标 tag 若原已存在，此时打印「原 digest → 新 digest」。
5. **查重**：SSM 现映射的（模板 revision ARN、digest）二元组与本次一致、且映射指向的 revision 仍为 ACTIVE → 跳过注册，沿用映射记录的 revision，并在确认之后对它无条件摘除一次 `gherkai:retired-at`（这个分支不经过步 7 的写映射，此前某次交错留下的 tag 不该等到命令末尾的清理 pass 才摘，命令在末尾之前失败时就摘不掉）。除此以外一律往下新注册一个 revision（步 6），在步 7 写映射替换：二元组不一致、映射缺失，或未能确认映射指向的 revision 仍为 ACTIVE（按映射缺失处理，见「不变量」清理 pass 条「注册与回收的竞争」段）。映射存在时，所指 revision 是否仍为 ACTIVE 在这一步确认（判据同「运行时与 preflight」节「缺失的判定口径」），二元组不一致的分支也据此决定步 8 是否给它打 tag：未确认仍为 ACTIVE 的不打。不在 family 里找未被映射、同二元组的 revision 复用（被拒方案「孤儿复用」条）。中断在步 6 与步 7 之间时，重新执行会再注册一个，上次注册的那个从未被映射引用，由清理 pass 在静默期之后回收（ECR 镜像层共享，只多一条 task-def）。deploy 第 4 步的重派生同样不复用。于是每个新注册的 revision 只被发起注册的那一条映射引用，被替换即离开最后一条映射，退休与清理按（版本，variant）独立判，与「variant 按版本隔离」（「SSM 参数与命名真源」节）的生命周期一致；早先版本留下的共用见「不变量」清理 pass 条「已退休却仍被映射引用」段。
6. **注册 revision**：`DescribeTaskDefinition`（模板，`include=["TAGS"]`）→ 剔除只读字段（`taskDefinitionArn` / `revision` / `status` / `requiresAttributes` / `compatibilities` / `registeredAt` / `registeredBy`）→ 镜像栏改 `repo@sha256:<digest>`，其余（含 `runtimePlatform`）原样 → `RegisterTaskDefinition`，**tags 记血缘**：`gherkai:variant`、`gherkai:version`、`gherkai:digest`、`gherkai:template`（模板 ARN）。注册之后、步 7 写映射之前，对新注册的 revision 再 `DescribeTaskDefinition`（`include=["TAGS"]`）一次，仍为 ACTIVE 且不带 `gherkai:retired-at` 才往下写映射；否则（含描述返回 `ClientException` 且本次 ACTIVE 列举未发现它，判据同「缺失的判定口径」，这不证明它已被注销或删除；其余读失败原样抛出）重新注册一个、同样再读，至多重新注册一次，第二次仍不满足时命令失败并提示稍后重新执行。不满足的情形包括进程于两步之间停留超过静默期、恰有一趟清理 pass 在注册之后读映射并给它补打，以及刚注册的 revision 尚未在查询结果中可见；后者会额外注册一个 revision，连续两次都未可见时命令失败。被补打或额外注册的那个从未被映射引用，满静默期后照常回收，只多一条 task-def。这次再读看到的只是那一刻的状态，不证明没有一趟清理已把它收为成熟候选（另一趟清理可能已摘掉自己补打的 tag），也不证明再读与写映射之间没有清理改动它，见「不变量」清理 pass 条「注册与回收的竞争」段与残余风险的总括。
7. **写 SSM**：`worker-image/<engine>/<版本>-<variant>` = JSON（模板 revision ARN、revision ARN、digest、推送时间）；写成功之后立即对写进映射的 revision 无条件摘除 `gherkai:retired-at`（`UntagResource`，不先读它带不带这个 tag；对不带这个 tag 的 revision 摘除成功返回、不改变它（ECS 文档没有写明，真实账户上核过，实测项 11）；失败只警告，留给之后的清理 pass；理由见「不变量」清理 pass 条「打 tag 与写映射的交错」段）；`--set-default` 时写默认指针，若该 variant 在其它引擎尚无镜像则**警告不拦**（「variant `X` 在 midscene 尚无镜像，用到该引擎的 run 会在 preflight 被拦」——与 preflight「按本 run 用到的引擎判」同一判据，单引擎团队不必凭空推另一引擎）。
8. **退休被替换的旧 revision**：给它打 tag `gherkai:retired-at=<时刻>`（**不在本次删除**；打不上只警告），然后执行一次清理 pass（不变量）。未确认仍为 ACTIVE 的旧 revision 不打（步 5 已核对它的状态）。时刻紧邻 `TagResource` 请求之前现读时钟，不用命令开始时取的时刻（「不变量」清理 pass 条「时钟」段）；回收不依赖这一步打上，没打上的由清理 pass 按孤儿补打；它若仍被另一条映射引用（早先版本留下的共用），清理 pass 摘掉这个 tag。输出 tag / digest / revision，以及「提交时用 `--worker-variant <名>`」。次序 = 写映射 → 退休旧 revision → 写指针 → 清理（两者无依赖）；`--set-default` 不在与基础镜像同步共享的推送路径上。registry host 的取法见「权限面增量」。

## `gherkai deploy` 的 worker 镜像四步（第 1 步随 cdk 事务，后三步在 cdk 之后；全部幂等）

1. **登记模板**：各引擎 task-def revision 的 ARN 由 **stack 资源**（`ssm.StringParameter`，值取 CDK 内 `taskDefinition.taskDefinitionArn`——`AWS::ECS::TaskDefinition` 的 `Ref` 返回带 revision 的 ARN；CDK 更新 task-def 属性即替换出新 revision、参数值随之更新）写进 SSM `worker-template/<engine>`——与 0037 的 `version`/`vpc` 同理，随部署事务同生死、回滚不留错值，deploy 命令不事后 `put_parameter`。push-worker 永远从它复制，**不抄「最近一次」revision**——那可能是某个 variant 的、且模板改过后已过期。
2. **同步基础镜像**：经容器引擎从 GHCR `pull` 当前版本基础镜像、走 push-worker 同一条内部流程推成 `<版本>-base`、注册 revision。零 step 的团队部署完即可跑，不碰 docker build。**非纯发行版本（`.dev`/`.post`/本地段）跳过本步**并打明确警告——那些版本由 tag 之后的 commit 派生、GHCR 上不可能有对应基础镜像（0037 决策 2b）；contributor 在 dev 树上部署是正常用法，硬失败只会逼人绕过命令手工推。第 3/4 步照常（默认指针仍初始化为 `base`；dev 版要能跑：本地 build 后 `push-worker … --variant base`）。容器引擎也只在本步探活——非纯版本不探，没装 docker 的机器上第 3/4 步照样收敛。
3. **初始化默认指针**：缺失 → `base`；存在 → **不动**（升级不重置，见「与版本升级的交互」）。
4. **重派生 + 清理**：对 SSM 里**当前版本**的每个 variant，记录的模板 ARN 与新模板一致、且映射指向的 revision 仍为 ACTIVE → 跳过，并在确认 ACTIVE 之后对它无条件摘除一次 `gherkai:retired-at`（同 push-worker 步 5：ACTIVE 的判定、读失败的口径与跳过分支的摘除都同那里）。否则——模板 ARN ≠ 新模板，或未能确认映射指向的 revision 仍为 ACTIVE（按映射缺失处理，同步 5）——用新模板 + 映射里记录的 digest 新注册一个 revision（血缘 tags 同上；不在 family 里匹配已有的 revision，同 push-worker 步 5；写映射之前的再读同步 6）、更新映射（写成功之后同步 7 立即摘除新 revision 上的 `gherkai:retired-at`）、旧 revision 打 `gherkai:retired-at`（时刻同步 8 现读时钟；未确认仍为 ACTIVE 的旧 revision 不打，模板变了的分支同样先确认，同「不变量」清理 pass 条「注册与回收的竞争」段其三）。重派生中断在注册与写映射之间时，映射仍指向本次准备替换的原 revision，重新执行会再注册一批；前一批从未被映射引用，由清理 pass 在静默期之后回收。原因：revision 是不可变快照、无继承，deploy 调了 cpu 后旧 variant 会一直跑旧 cpu 直到有人重推；重派生让所有 variant 与模板同步而镜像一个字节不动。重派生**保留原 `pushed_at`**（记的是镜像推上去的时刻）；repo URI 从模板容器的镜像栏反推（模板即 `<repo-uri>:latest` 占位）——重派生不登录 registry。随后跑一次清理 pass（不变量）。

**四步的失败语义**：cdk 已成功而后三步任一失败 → 退 1，提示「stack 已生效；重跑 `gherkai deploy` 幂等收敛」；基础镜像 pull 因 GHCR 上缺该版本镜像失败（[0037](./0037-distribution-and-packaging.md) 决策 8 承认的「PyPI 已发、镜像缺失」半发布态）→ 提示等镜像发布完成后再 `gherkai deploy`。

## 不变量

- **运行时只用 definition 里的显式 revision，永不用 family 取最新**（迁移前的 IaC 曾传 family，理由见下「被拒方案」的『RunTask 传 family』条）。
- **revision 按 digest 引用镜像**，重推同名 variant 产生新 revision、运行中的 run 手里的旧 revision 不受影响；一个 run 内镜像固定。
- **幂等**：push-worker 与 deploy 四步的每一步先查再做，中断后重跑收敛。ECR push 天然幂等（同 digest 无操作）；`RegisterTaskDefinition` 不幂等，故以二元组查重；中断在注册与写映射之间时，重新执行会再注册一个，上次注册的那个不被任何映射引用，由清理 pass 在静默期之后回收，收敛的是映射与在用的 revision，多出的 revision 只滞留到回收（不复用这类 revision，被拒方案「孤儿复用」条）；ECR 登录令牌 12 小时有效、重跑重登；SSM 写是覆盖语义。
- **并发写者：最后写者赢，孤儿由对账回收**。SSM 无条件写，两人同时 push 同名 variant 会各注册一个 revision、后写者的映射赢；先写者的 revision 不在映射里也没被打退休 tag——**清理 pass 按 family 全量对账**（凡带血缘 tags、ACTIVE、不在 SSM **任何版本**的 `worker-image/*` 映射里的 revision 视作孤儿，与已退休的 revision 同样进入清理候选，清理 pass 看到它不在任何映射里、且它的注册时刻早于那一趟开始读映射的时刻时给它补打 `gherkai:retired-at`、静默期从补打的时刻起算（下条「候选与静默期起点」；不以 `registeredAt` 作起点，见被拒方案「孤儿的静默期从 `registeredAt` 起算」条）；旧版本 variant 的 revision 仍在映射里、**不是**孤儿，其回收归 `delete-worker`），不只看映射。同一 variant 的并发 push 不建议但不禁止。
- **清理 pass = 静默期 + 运行中 run 引用检查，机会式执行、无定时任务**：pass 由 `push-worker` 末步与 `gherkai deploy` 第四步末各跑一次（将来 `delete-worker` 也跑）；列 family 全部 revision 读 tags，对已退休（`gherkai:retired-at`）或对账出的孤儿，只在**退休满 1 小时**（覆盖「提交侧 preflight 刚解析成 R、definition 尚未落库」的窗口与注销后最多 10 分钟的生效延迟）且**无未到终态的 run 引用**时才 `DeregisterTaskDefinition` + `DeleteTaskDefinitions`；有引用或未满静默期 → 留到下次 pass。长期无人 push/deploy 时退休 revision 会滞留，无害（ACTIVE 但无人引用）。「退休满 1 小时」的起点见本条下「候选与静默期起点」段，引用检查的做法见「引用检查」段。引用判定的访问路径定死：run 用到的 revision ARN 在 `create_run` 时**同时写成 STATE item 的顶层属性 `worker_task_def_arns`**（同 [0034](./0034-detached-batch-reconciler.md) 的 `detached` 顶层标记先例），清理经 runs 表的稀疏 GSI（只索引 STATE item）读非终态 run 的这个属性——不扫全表（runs 表 `RETAIN`、无 TTL、随历史单调增长，Scan 成本无上界）。detached run 逐 job 起 task，删早了剩余 job 全部起不来。ECS 侧稳态只留每个（版本，variant）当前一个 revision。**实装细则**：孤儿判据要枚举 SSM **全部版本**的映射，枚举失败 → **整趟放弃清理**（当作「没有映射」会把每个在用 revision 都判成孤儿并补打 `gherkai:retired-at`，一小时后的下一趟就会批量回收）；`registeredAt` 只用作补打 `gherkai:retired-at` 的附加条件，取不到时本趟不打，宁滞留不早删（若一直取不到，这个 revision 每一趟都不被补打，一直滞留、永不回收，偏保守。真实 ECS 上不应发生，依据是本模块在真账户上的观察（`list-workers` 输出的就是这个字段，真账户上读得到；moto 不返回这个字段，单测里取不到是模拟层的差异），没有文档保证：ECS API 参考里 `TaskDefinition` 的返回字段（含 `registeredAt`）都标为非必有，待核（实测项 10））。
  - **候选与静默期起点**：`gherkai:retired-at` 的含义改为「这个 revision 从何时起不被任何映射引用」，静默期一律从它的值起算。打这个 tag 的有两处：替换映射的那一步（push-worker 步 8 与重派生）给被替换的旧 revision 打，时刻紧邻 `TagResource` 请求之前现读时钟；清理 pass 给缺这个 tag 的孤儿补打。每趟 pass 读完全部版本的映射（开始读之前记下时刻 t1）之后，对每个带血缘 tags 的 ACTIVE revision：在任一映射里的，不是候选；它若带着 `gherkai:retired-at`，摘掉这个 tag（`UntagResource`，失败留到下一趟）——任何一趟见到「仍在映射里却带着这个 tag」的 revision 都摘。不在任何映射里、还没有这个 tag 的：`registeredAt` 早于 t1 的补打（值为此刻），本趟不作为候选、留下；`registeredAt` 不早于 t1 或取不到的本趟不打，留到下一趟（一直取不到时一直滞留，见上「实装细则」）；打不上同样留下，下一趟再打。不在任何映射里、tag 已满 1 小时的是成熟候选，进入引用检查；未满的留下。**重读**：本趟补打过 tag 或有成熟候选时，在补打与引用检查的快照都完成之后、注销之前重读一次全部映射，两件事共用这一次读：本趟补打过的 revision 若已在映射里，当场摘掉；成熟候选若已在映射里，不注销、摘掉 tag（理由见下「注册与回收的竞争」段）。重读失败时把本趟补打的 tag 全部摘掉（下一趟重打，回收晚一趟），成熟候选全部留下。「本趟补打过」含 `TagResource` 调用报错的那些：报错（如超时）不说明服务端没有打上，摘一个不存在的 tag 无害。依据：静默期要覆盖的是「preflight 已解析出 R、definition 尚未落库」的窗口，所以起点必须不早于 R 离开最后一个映射的时刻——R 离开之后，新的 preflight 不再解析到它。两处打的值都满足这一点：替换的一步在写映射成功之后现读时钟，值不早于 R 离开被替换的那条映射；补打的那一趟读到的映射里已经没有 R，值不早于这次读取，也就不早于 R 离开映射。R 被替换时若仍被另一条映射引用，替换的一步打的值早于它离开最后一条映射，清理 pass 见到它仍在映射里即摘掉（下「已退休却仍被映射引用」段），最后一条映射被替换时再打。命令开始的时刻与 `registeredAt` 都不满足这一点：前者早于写映射（下「时钟」段），后者可能早于它离开映射很久（被拒方案「孤儿的静默期从 `registeredAt` 起算」条）。孤儿与替换时没打上 tag 的 revision 走同一条补打路径，回收不依赖替换的一步打上 tag。摘除对这个 revision 自身的回收只会推迟、不会提前：已被某一趟收为成熟候选的，摘除在那一趟注销之前的最后核对之前可见时，核对读到 tag 已不在，那一趟不注销（下「引用检查」段⑤）；晚于核对的见下例二。依据是取消孤儿复用之后，一个 revision 进入映射只有一条路：发起注册的那条命令把自己刚注册的它写进自己那条映射（步 5、步 6 与重派生）。被摘掉 tag 的 revision 若在映射里，它本来就不该带这个 tag；若不在任何映射里，它不会被别的命令写回映射，只会在之后某一趟被再次补打、从更晚的时刻起算，回收晚一趟。例一：同一 variant 的两条推送并发，一条读到旧映射、走步 5 的跳过分支，另一条随即替换了这条映射并给旧 revision 打 tag，跳过分支确认 ACTIVE 之后的摘除落在打 tag 之后。例二：一趟清理凭它读到的、已过时的映射，摘掉一个此后已离开映射的 revision 的 tag，而另一趟清理已把它收为成熟候选：摘除在那一趟的最后核对之前可见时，那一趟不注销，下一趟重新补打，回收晚一趟；落在最后核对之后时，那一趟照旧注销，它确实不在任何映射里，那次注销本来就满足前置条件。「不会被写回映射」的唯一例外是某条命令刚注册、尚未写映射的那个 revision。摘除与它有关：推送写映射之前的再读以「不带 tag」为放行条件，一趟清理摘掉自己补打的 tag（如重读失败之后），会让推送的再读放行，而另一趟清理可能已凭这个 tag 的旧值把它收为成熟候选；这一交错由注销之前的最后核对关掉，余下的部分在残余风险的总括之内（下「注册与回收的竞争」段与残余风险⑥）。本段与下面各段所说「进入映射只有一条路」，指本版本的命令；旧版 CLI 仍从 family 里复用孤儿（CLI 旧于后端时版本 skew 闸只警告不拦，[0037](./0037-distribution-and-packaging.md) 决策 7），它写的映射不在这些论证之内，与残余风险⑤同属发行边界下接受的旧版本写者。
  - **打 tag 与写映射的交错**：取消孤儿复用之后，替换的一步（push-worker 步 8 与重派生）只给它从映射里读到、随即被自己替换掉的 revision 打 tag；那个 revision 已离开这条映射、不会被写回（上段末），它仍在别的映射里只可能是早先版本留下的共用，由清理 pass 摘除（下「已退休却仍被映射引用」段；摘除落空的情形见残余风险①）。所以会让 R 带着一个早于它被映射的 tag 的，只剩清理 pass P 的补打：P 读映射时，另一条 push 或重派生 Q 已注册了 R（步 6）、还没把它写进映射（步 7），P 给它补打，Q 随后把它写进映射。若不摘，R 日后离开映射、而替换的一步没能以新值覆写时，静默期可能早已满。处置有三道：P 打了 tag 之后重读全部映射，R 已在映射里就当场摘掉（上段「重读」）；Q 写映射成功之后立即对 R 无条件 `UntagResource`（步 7 与重派生写映射处；步 5 跳过分支确认 ACTIVE 之后的摘除是又一道，处置此前任何交错留下的 tag）；Q 末尾的 pass 见到「仍在映射里却带着 tag」再摘一次。论证按读到 Q 所写那个参数的时刻进行：映射枚举是分页读取，每一页在各自的时刻取回，结果不是某一时刻的快照，所以不按读取开始或结束的时刻论证。设 P 的第一次读与重读取回含该参数那一页（参数此前不存在时，指它若存在应在的那一页）的时刻分别为 r1、r3，P 在 t2 打上 tag（r1 < t2 < r3），Q 在 tw 写映射成功、随后在 tu 摘除：tw 早于 r1 时，P 第一次读就看到 R 在映射里，不打；tw 在 r1 与 r3 之间时，重读看得到 R，当场摘掉；tw 晚于 r3 时也就晚于 t2，Q 在 tu 的摘除发生在 tag 落下之后，把它摘掉（Q 末尾的 pass 是又一道）。这几种次序的论证依赖三条可见性与次序：①写映射成功之后，其它调用方的 `GetParametersByPath` 取回含该参数的那一页时读得到它；②`TagResource` 成功之后，此后发出的 `DescribeTaskDefinition`（`include=["TAGS"]`）读得到这个 tag（Q 末尾的 pass、「注册与回收的竞争」段的再读依赖它）；③在一个已成功返回的 `TagResource` 之后发出的 `UntagResource` 作用在它之上、不被它覆盖（Q 的立即摘除依赖它）。ECS 的官方文档明确它的 API 采用最终一致模型，②③因此没有保证，③是推断；SSM 没有找到跨调用方读后写可见、或分页读取构成一致快照的官方保证，`GetParametersByPath` 文档里分页的说明也证明不了强一致或最终一致，①同样没有保证。所以上面的论证只在这三条成立时闭合，不成立时的落空写进残余风险①；实测项 10 只能补充观察，不能关闭这一风险。立即摘除相对只靠 Q 末尾的 pass 缩小了两类窗口：不必等整条命令执行到末尾（写映射之后命令中途失败、在清理之前返回，如 push-worker 写默认指针失败、deploy 的基础镜像同步之后的步骤失败，Q 一侧不再因此留下 tag），也不必先读到 tag（不依赖②）。它消除不了三种情形：写映射之后、摘除之前进程崩溃或被中断；摘除失败；tag 晚于摘除落下（`TagResource` 报错而服务端在摘除之后才生效，或③不成立）。它缩小窗口，不是绝对的保证。多趟 pass 并发时论证逐趟成立：每个误补打的 tag 都出自某一趟，那一趟的 t2 早于它自己的 r3，tw 早于 r3 时由那一趟的重读摘掉，晚于 r3 时由 Q 的摘除摘掉；另一趟若在 P 的 tag 可见之前列了 family，会再补打一次、以它自己的值覆盖（同一个 key 再打，新值覆盖旧值，ECS 官方文档明确；文档不保证并发请求落下的先后，后落下的值不一定更晚，见残余风险①），这一次出自那一趟，按那一趟自己的 r1、t2、r3 同样落在上面三种次序之内。「`registeredAt` 早于 t1 才补打」是附加的一道：Q 在 t1 之后才注册的 R，P 根本不打，不依靠后面的摘除；步 6 到步 7 之间只有一次再读与一次 SSM 写，新注册的 revision 多半落在这里；注册早于 t1、写映射晚于 t1 的仍靠写映射之前的再读（「注册与回收的竞争」段）、重读与摘除。`registeredAt` 由 ECS 的时钟给出、t1 取本机时钟：本机时钟偏慢只让本趟少打（偏保守），偏快时这道附加保护变弱，仍有重读与 Q 一侧的摘除。t1 是 P 开始读映射之前的本机时刻，只用于这道附加条件；上面三种次序按 r1、r3 论证，与 t1 无关。
  - **注册与回收的竞争**：步 6 注册之后、步 7 写映射之前（重派生同样在注册与写映射之间），新注册的 revision R 不在任何映射里。推送进程 Q 在这两步之间停留超过静默期（命令长时间执行或进程被挂起）时，一趟 pass P 可能给 R 补打 tag，满 1 小时之后另一趟 pass P′ 把 R 收为成熟候选，Q 这时才把 R 写进映射。它不依赖 AWS 的可见性。取消孤儿复用之后，这是不在映射里的 revision 进入映射的唯一一条路，也是「写进映射」与回收竞争的唯一来源（离开映射一侧，替换的一步打 tag 与回收的竞争见残余风险①）。后果按 Q 写映射与 P′ 注销 R 的操作次序分两类，两类的后果并不互斥。**先注销、后写映射**：映射悬空。注销状态对读取可见之后，用这个 variant 的提交在 preflight 因 revision 不是 ACTIVE 以退出码 2 结束、提示推送；在此之前，刚注销的 revision 可能短时仍读作 ACTIVE（推断，见残余风险⑥），preflight 也可能接纳提交，该 run 随后起 task 失败（同残余风险②）。同一 digest 重推时，步 5 若只比二元组，就会直接沿用这条映射、跳过注册，按提示操作也恢复不了（下面其三处理）。**先写映射、后注销**：Q 写映射并立即摘掉 tag 之后，P′ 内存里仍是它此前收下的候选与快照——摘除撤销不了它们，P′ 若不再核对就会注销 R（下面其二的最后核对处理）。这时 R 已在映射里，新的 preflight 可能已解析到它、STATE 尚未落库，快照看不到这类 run，清理误删了在用的 revision；这也破坏下面「为什么一次快照就够」的前提其一（候选在静默期内没有被写进映射）。设计上补三条。其一，写映射之前对 R 再 `DescribeTaskDefinition`（`include=["TAGS"]`）一次，仍为 ACTIVE 且不带 `gherkai:retired-at` 才写；不满足（含描述返回 `ClientException` 且本次 ACTIVE 列举未发现它）即重新注册一个、同样再读，第二次仍不满足时命令失败并提示稍后重新执行（步 6 末尾）。它挡下的是再读时已可见的 tag 与注销，不证明写进映射的 revision 没有正被回收：再读依赖上段的可见性②；再读与写映射之间被打上的 tag 由上段的各道摘除处理；再读看到「不带 tag」也可能是因为补打它的那一趟清理已摘掉了自己补打的 tag（如那一趟的重读失败），而另一趟清理此前已凭这个 tag 的旧值把它收为成熟候选（下面其二的最后核对处理）。剩下的情形见残余风险⑥。其二，清理在注销候选之前做两道核对。先重读一次全部映射，已在映射里的候选不注销、摘掉 tag（上「候选与静默期起点」段的「重读」，与补打之后的重读是同一次读）；再逐个重读仍不在映射里的候选的 `gherkai:retired-at`，与判定成熟时读到的值不一致（被改写或被摘掉）或这次读取失败的，本趟不注销（下「引用检查」段⑤）。Q 写映射落在映射重读之后时，只要 Q 写映射之后的立即摘除在最后核对之前可见，就由最后核对拦下；上面「再读看到不带 tag」的那种交错同样由它拦下，只要摘掉 tag 的那一步在最后核对之前可见。映射重读检查当时可见的映射，最后核对检查当时可见的 tag 与 ACTIVE 状态。写映射后的摘除未执行、失败，或旧值被恢复时，即使写映射早于最后核对，也可能未被识别；剩余边界见残余风险总括与⑥。其三，步 5 的第一个判断在二元组一致时还要求映射指向的 revision 为 ACTIVE；未能确认它仍为 ACTIVE（描述成功且状态不是 ACTIVE，或描述返回 `ClientException` 且本次 ACTIVE 列举未发现它）时按映射缺失处理：往下新注册，写映射替换悬空的那条；被替换的那条未确认仍为 ACTIVE，步 8 不对它打 `gherkai:retired-at`。二元组不一致的分支同样先确认被替换的那条仍为 ACTIVE，未确认就不打。列举未发现它不证明它已被注销或删除：它若只是尚未在查询结果中可见，即多注册一个 revision，被替换的那条成为不在映射里、不带 tag 的 revision，由之后的清理 pass 按孤儿补打、满静默期后回收。只有上述两种情形按缺失处理，其余读失败（描述报权限不足、限流、网络等其余错误，这时不列举；描述报 `ClientException` 而它仍被列出；或列举本身失败）原样抛出、命令失败，与 preflight「缺失的判定口径」同一判据。这给出悬空映射的恢复路径，与 preflight 的提示一致：同一镜像再执行一次 `push-worker`；纯发行版本的 `base` 也可由 `gherkai deploy` 的基础镜像同步经同一条推送路径恢复（非纯发行版本跳过这一步，用 `push-worker … --variant base`）。代价是步 5 与重派生在映射存在时多一次 `DescribeTaskDefinition`（跳过分支用它确认 ACTIVE，二元组或模板不一致的分支用它在给被替换的旧 revision 打 tag 之前确认它仍为 ACTIVE），描述报 `ClientException` 时另加一次按 family 的 `ListTaskDefinitions`；有成熟候选或补打过 tag 的那一趟清理多一次映射枚举，每个走到注销这一步的候选多一次 `DescribeTaskDefinition`。剩下的风险见残余风险⑥。
  - **时钟（实装要求）**：tag 的值紧邻 `TagResource` 请求之前现读时钟，读时钟与发出请求之间不插入其它远程调用（替换的一步与清理 pass 的补打都如此）；紧邻只缩短取值与请求之间的间隔，进程在两者之间被挂起时，恢复后仍会把较早的值写回（残余风险①）。t1 在开始读映射之前现读。两者都不用命令开始时的时刻：push-worker 的命令开始早于 docker push、deploy 的早于 cdk 与基础镜像同步，都早于本命令写映射，拿它当 tag 的值会让起点早于 R 离开映射，破坏上面的核心不变量。静默期的比较可以用命令的时刻：它早于实际时刻，算出的已过时长偏小，偏保守。测试注入时钟函数，守「补打的值不早于本趟读完映射的时刻、替换的一步打的值不早于写映射成功的时刻」，含命令在读映射之前已执行很久的用例。t1 取开始读之前的时刻是有意的：它越早，`registeredAt` 早于它的 revision 越少，附加保护越保守；tag 的值则须不早于读完映射，因为 R 可能在开始读之后、读到它那条映射之前离开映射。
  - **引用检查（已实装）**：每趟一次快照，与候选数无关。①先收齐全部引擎的候选（上条），没有成熟候选就不读 runs 表（多数 pass 如此），本趟补打过 tag 时仍做上条的「重读」。②就绪检查：对 runs 表做一次 `DescribeTable`，`status_group-run_id-index` 的 `IndexStatus` 为 `ACTIVE` 才继续；缺失、`CREATING`、`UPDATING`、`DELETING` 或 `DescribeTable` 本身失败，全部候选留下，打一行产品语言的警告（说明这次没有回收旧的 worker revision、下次 push-worker 或 deploy 会再试）。判据比 `list-runs` 严（[0041](./0041-agent-facing-cli-affordances.md) 决策七「索引就绪判据」放行 `UPDATING`）：清单读不到只是少一行，清理误判会让 run 后续的 job 起不来；跳过一趟只是让 revision 多留到下一趟。也不依靠「`Query` 一个回填中的索引会报错」这一行为（它没有实测过；若某种情形下返回不完整的结果，就会误删）。③快照：`Query` 分区 `status_group = live`，`ProjectionExpression` 取 `worker_task_def_arns`，按 `LastEvaluatedKey` 翻页读完，把全部 ARN 并成一个集合。不加过滤：过滤在读取之后才应用，不减少读量；一次读回全部 ARN，就不必对每个候选各查一遍。④候选的 ARN 在集合里的留下；其余候选经上条的「重读」，已在映射里的不注销、摘掉 tag。⑤最后核对：仍不在任何映射里的候选，注销之前逐个再 `DescribeTaskDefinition`（`include=["TAGS"]`）一次，读出的 `gherkai:retired-at` 与本趟判定成熟时读到的值逐字相同、且它仍为 ACTIVE，才紧接着发出 `DeregisterTaskDefinition` + `DeleteTaskDefinitions`（`failures` 的处置不变），读取与注销请求之间不插入其它远程调用；值不同、tag 已不在、revision 已不是 ACTIVE，或这次读取失败时，本趟跳过该 revision 并打印一行警告，继续核对其余候选。后续 pass 仅对仍为 ACTIVE 的 revision 按届时状态重新判定。它关掉两种交错，都是本趟收下候选之后、别的命令改了它的 tag：其一，早先版本留下的共用 revision，一条映射被替换时打上 t0、此后没有一趟清理摘掉它，超过静默期之后最后一条映射被替换，替换的一步写入新时刻之前，本趟已按 t0 把它收为成熟候选，新时刻随后成功写入；其二，一条推送注册了 R、尚未写映射，一趟清理给 R 补打之后停留超过静默期，本趟把 R 收为成熟候选、完成快照与映射重读，补打的那一趟随后重读失败、按协议摘掉自己补打的 tag，推送的再读于是看到 ACTIVE、不带 tag，把 R 写进映射。新时刻或摘除在核对之前可见时，最后核对读到的值已不是判定成熟时的值，本趟不注销。限度：它只看得到核对时刻已可见的改动——核对之后的改动（含核对与注销请求之间的）看不到，读取依赖可见性②，改动已成功而尚不可读时同样看不到；其一里替换的一步晚于核对才打上新时刻的，本趟按 t0 注销（残余风险的总括）。逐字相同也不证明其间没有改动：tag 的值没有变化的落空（替换时没有覆写、旧值被写回），以及 tag 被摘掉之后又被同一个值写回（补打的请求在服务端晚于摘除才生效），都不在它能识别的范围内（残余风险①与⑥）。②③任一步失败（`Query` 报错、权限不足、索引不存在）或重读失败，全部候选留下并打一行警告；②③失败时，本趟补打过 tag 的仍照常做上条的「重读」，处置补打的那些；⑤里被跳过的候选各打印一行警告（见⑤），不影响其余候选。
  - **为什么一次快照就够**：过了静默期的候选，引用它的未到终态的 run 只减不增，前提有三。其一，候选确实不在任何映射里，且静默期内没有被写进映射：「不在映射里」是本趟读映射得出的，依赖上面「打 tag 与写映射的交错」段的可见性①；取消孤儿复用之后，不在映射里的 revision 被写进映射只有一种情形，即它是某条命令刚注册、在写映射之前停留超过静默期的那一个（「注册与回收的竞争」段的「先写映射、后注销」），注销之前的映射重读与最后核对降低但不排除这一风险，具体边界见残余风险总括与⑥；这一部分不在论证之内。其二，新的 preflight 解析不到不在映射里的它，解析到它的 run 在 preflight 之后几分钟内落库，远短于 1 小时。其三，正常生命周期里已落库的 run 从 `live` 分组离开只有收尾一条路，不会回来（run 级状态只进不退，[0034](./0034-detached-batch-reconciler.md) 机制三；两条终态写之后 `status_group` 是终态值，终态被改写也只在终态分组之间移动）；端口上 `save_run` 以非终态的状态整体覆盖一个已收尾的 run 会让它回到 `live` 分组，生产 code 没有这样的调用，不在论证之内；旧版本写出、缺分组属性的非终态 run 在新版本的写者写它的 run 级状态时才进入 `live` 分组，此前对快照不可见，补上之后索引项还要传播。这类 run 有两个来源：从更早的索引形态迁移而来的后端上、改用状态分组索引之前写出的（产品不提供这种迁移的路径，[0041](./0041-agent-facing-cli-affordances.md) 决策七「更早的索引形态」），与已是状态分组索引的后端上由旧版 CLI 建立的（下面残余风险⑤的已知盲区），都不在论证之内。这些前提成立时，快照与注销之间相隔的几秒不会漏掉新的引用。
  - **三种边界情形**：(a) run 正在从 `pending` 换到 `running`：`status_group` 随同一次写写成同值 `live`，revision 列表不变，索引键不变、不计写，索引项一直在 `live` 分组，快照看得到它。依据分三层：DynamoDB 官方的 GSI 写入规则明确，索引写按这次写入实际改变了哪些属性判定，只改既非索引键、也不在投影里的属性时索引项不变、不写索引；同值写没有改变 `status_group` 的值，按这条规则不产生索引写，这是对规则的解读，0034 实测项 6 在以 `status` 为键的索引上对索引键属性的同值写测得为 0；新索引上的真实行为（含「不计写即索引项不受影响」）待核，见实测项 8。(b) run 刚建、STATE 还没传播进索引：快照看不到它，保护只来自静默期——它的 preflight 在 R 离开映射之前就解析到 R，`gherkai:retired-at` 的值不早于 R 离开映射，删除至少再等 1 小时，只要从 preflight 到 STATE 在索引里可见短于 1 小时就不会漏。GSI 的传播没有承诺上界（文档只说通常不到一秒、异常时可能更长），所以这是一条对传播时长的依赖，余量约为 1 小时减去 preflight 到落库的时长。这条依赖是本条原有的静默期论证本来就有的，任何经 GSI 找引用的做法都有，本设计没有新增，只是让它对孤儿与替换时没打上 tag 的 revision 也成立。(c) `run --backend cloud --no-report` 不写 STATE：仍是下面记的已知盲区，不变。收尾中的 run 若因传播滞后仍留在 `live` 分组，只会让它的 revision 多留一趟，偏保守。
  - **残余风险**：**总括**：清理的各项读取与注销不是原子操作，ECS 与 SSM 之间没有跨服务的条件写。映射以最后一次映射重读中各页分别取回的时刻为依据，tag 与 ACTIVE 状态以逐候选最后核对（上「引用检查」段⑤）为依据。从各自读取到服务端实际执行注销之间的变化，包括注销请求在途期间的变化，均可能未被本趟识别；可见性延迟（上「打 tag 与写映射的交错」段①②）还可能隐藏读取之前已发生的变化。最后核对读到同一 tag 值，不证明映射没有变化，也不证明 tag 中途未被改动。各道重读只缩短各自的窗口，不能保证互斥。同样的非原子性还出现在另外三处：两处先检查后执行的写，即清理的补打（读映射在前、打 tag 在后）与推送、重派生写映射之前的再读（再读在前、写映射在后）；以及替换的一步（push-worker 步 7 与步 8、重派生）先写映射、后给被替换的 revision 打 tag，两次写之间它已离开映射、仍带着此前的 tag（若有），一趟清理在这期间读映射、做完核对并发出注销，依据的就是这个此前的值。tag 与映射都是无条件写。下面 ① 与 ⑥ 里与其它命令交错的各项是这一形态的已知实例，逐条注明由哪一道核对关掉、或仍在总括之内；其余各项是调用失败、进程中断与并发写造成的落空，不由核对关掉。① R 在映射里时带上了一个早于它离开映射的 `gherkai:retired-at`，离开映射时又没有被新值覆写、新值晚于某一趟清理的最后核对才可见，或覆写之后又被旧值覆盖（上面「打 tag 与写映射的交错」段剩下的落空）。已知实例：(a) 补打之后推送写映射，各道摘除都没有生效：Q 写映射晚于 P 的重读取回该参数的时刻，Q 的立即摘除没执行到（写映射之后、摘除之前进程崩溃或被中断）、失败，或 tag 晚于摘除落下（`TagResource` 调用报错、服务端在摘除之后才生效），且 Q 末尾的 pass 也没有摘掉（没执行到：映射枚举失败整趟放弃、命令在清理之前失败返回或被中断；或摘除失败）；或 P 自己的摘除失败（重读看到 R 已在映射里而摘除失败、重读失败之后摘除也失败）；或 `TagResource` 调用报错、服务端在 P 重读并摘除之后才生效。属调用失败与进程中断，不由核对关掉。(b) 可见性与次序（上「打 tag 与写映射的交错」段①②③）不成立：P 的读没看到已写的映射、Q 末尾的 pass 没看到已打的 tag、Q 的摘除被晚生效的 tag 覆盖，各方调用全部成功而 tag 留在正在使用的 revision 上。仍在总括之内；这三条没有官方保证，实测只能观察、不能排除。(c) 补打的旧值写回：P 读映射时 R 已注册、尚未写进映射，P 取了 tag 的值之后、发出打标请求之前长时间停留（如进程被挂起），这期间 Q 把 R 写进映射并摘除，之后另一条命令 S 替换了这条映射、在替换的一步给 R 打上正确的值；P 恢复后发出请求，以较早的值覆盖 S 写下的值（新值覆盖旧值是官方明确的行为，文档不保证并发请求落下的先后，也不保证后落下的值更晚），而 P 重读时 R 已不在映射里，不摘。它要求 P 的停留跨过 Q 写映射与 S 替换两件事，不需要任何调用失败或可见性异常。这是补打一侧的总括实例；最后核对关不掉它：写回的旧值就是此后各趟读到的值，核对时值一致。上「时钟（实装要求）」段的「紧邻打标请求之前现读时钟」只缩短取值与请求之间的间隔。(d) 早先版本留下的共用 revision：它的一条映射被替换时，替换的一步打的值早于它离开最后一条映射，靠清理 pass 见到它仍在映射里时摘掉（替换它的那条命令末尾的 pass 是第一道）。此后直到最后一条映射被替换都没有一趟 pass 摘掉它时，分三种：最后一条映射被替换时没有覆写（替换的一步没打上，或被并发推送的后写者顶掉、没有经过替换它的那一步），不由核对关掉；覆写成功，随后又被一个较早取值的打标请求覆盖（同 (c) 的形态），不由核对关掉；覆写成功之前，旧值已被另一趟清理收为成熟候选：覆写在那一趟的最后核对之前可见时，由最后核对关掉（核对读到新值即不注销）；覆写晚于最后核对或核对时尚不可读的，仍在总括之内（替换的一步先写映射、后打 tag）。缓解：此后只要有任何一趟 pass 在 R 仍在映射里、且读得到这个 tag 时执行到摘 tag 这一步，tag 就会被摘掉；R 日后被替换时，替换的一步以新值覆写这个 tag（同一个 key 再打，新值覆盖旧值，ECS 官方文档明确），覆写可见之后，按旧值的判定不再成熟；覆写之前已按旧值收下它的那一趟，覆写在它的最后核对之前可见时由最后核对拦下，晚于最后核对的仍在总括之内（(c) 与 (d) 所说的旧值覆盖新值除外）。所以 (a)(b) 还要求从 Q 到 R 离开映射之间没有这样一趟 pass，且 R 离开映射时没有被覆写，或覆写晚于按旧值收下它的那一趟的最后核对。以上任一种发生时，R 离开映射时静默期可能已满，只剩快照这一道保护，它覆盖不到当时正处于 preflight 与落库之间的 run。后果与下面的 ② 相同。② 误删的后果有界：该 run 剩下的 job 起 task 失败、判为 error，不会挂死，也不会自愈（revision 钉在 definition 里），重新提交即可恢复；已在执行的 task 不受影响。③ 部署方机器之间的时钟偏差直接加减到静默期上：tag 由一台机器的时钟写入，在另一台机器上比较。④ 从未收尾的 run（前台执行被强制结束留下的）一直在 `live` 分组，它引用的 revision 一直保留（以 `status` 为键时同样如此），快照读量随这类 run 增长。⑤ 前提是全部 STATE 写者都维护 `status_group`（[0030](./0030-realtime-persistence-seam.md) 决定六）：没写它的 STATE 对快照不可见。本版本的写端在 core 的 DynamoDB RunStore 一处，由覆盖全部写路径的不变量测试守；测试守不到旧版本的写者。CLI 旧于后端时版本 skew 闸只警告不拦（[0037](./0037-distribution-and-packaging.md) 决策 7），所以由旧版 CLI 向已是状态分组索引的后端建的 run 在新版本的写者写它的 run 级状态之前没有分组属性（detached 的通常在推进器第一次认领时补上，由旧版 CLI 前台执行的一直没有），这期间对引用检查与 `list-runs` 都不可见，补上之后新索引项还要传播，而这时它引用的 revision 的静默期可能早已开始。所以它执行期间有人重推它用的 variant 时，它后续的 job 可能起不来（后果同 ②）。这与 `--no-report` 同列为已知盲区（下「已退休却仍被映射引用」条末的「已知盲区」），在发行边界下接受：现阶段没有使用者，不做旧版本兼容。⑥ 注册与回收的竞争（上「注册与回收的竞争」段）。各实例都要求 Q 从注册到写映射的总间隔超过静默期：成熟候选的 tag 是在 R 注册之后才补打的，满 1 小时才成熟（部署方机器之间的时钟偏差会缩短这个要求，见 ③）。两类按操作次序区分，后果并不互斥。已知实例：(a) **先注销、后写映射**，Q 写映射之前的再读没拦下：再读没看到已打的 tag 或已做的注销（tag 的可见性②不成立、注销状态尚不可读，或 tag 与注销在再读之后才落下），或补打的那一趟在再读之前已摘掉自己的 tag、而另一趟此前已按这个 tag 注销了 R。这是写映射一侧的总括实例，清理的核对关不掉它。后果是映射悬空：注销状态可见之后，用这个 variant 的提交被 preflight 以退出码 2 拦下；此前 ECS 的读取可能仍把刚注销的 revision 读作 ACTIVE（ECS 官方文档明确它的 API 最终一致，注销之后的具体表现是推断），preflight 也可能接纳提交，该 run 随后起 task 失败（同 ②）。恢复：同一镜像再执行一次 `push-worker`（纯发行版本的 `base` 也可再执行一次 `gherkai deploy`），按「未能确认映射指向的 revision 仍为 ACTIVE 即按映射缺失处理」新注册一个 revision、替换映射；推送若仍把它读作 ACTIVE，会沿用悬空的映射，稍后再执行一次即可。(b) **先写映射、后注销**，补打的那一趟摘掉了自己的 tag：P0 给 R 补打之后停留超过静默期，P′ 把 R 收为成熟候选、完成快照与映射重读，P0 随后重读失败、按协议摘掉自己补打的 tag，Q 的再读看到 ACTIVE、不带 tag，写映射。P0 的摘除在 P′ 的最后核对之前可见时，由最后核对关掉（核对读到 tag 已不在）；摘除晚于最后核对或核对时尚不可读的，仍在总括之内（P′ 实际注销早于 Q 写映射时，落入 (a)；晚于 Q 写映射时，仍属 (b)）；P0 补打的请求在服务端晚于 P0 的摘除与 Q 写映射之后的摘除才生效、写回同一个值的（推断：报错之后的重试请求延迟落下），核对读到的值与判定成熟时相同，不由核对关掉，属 ①(a) 所列的调用失败。(c) **先写映射、后注销**，Q 的写映射落在 P′ 的映射重读之后，且 Q 的再读没拦下（tag 在再读之后才打上并在写映射之前成熟，或再读没看到已打的 tag）：Q 写映射之后的立即摘除在最后核对之前可见时，由最后核对关掉；摘除晚于最后核对或核对时尚不可读的，仍在总括之内；摘除没执行到或失败的，属调用失败与进程中断，不由核对关掉。(b)(c) 漏过时后果是误删在用的 revision：写映射之后解析到 R 的 run 后续 job 起不来（同 ②），映射随之悬空，恢复同 (a)。(b)(c) 还要求清理一侧的核对与 Q 的写映射、摘除恰好交错，比 (a) 更窄，但不能排除。
  - **取舍依据**：可选的做法按「先保证不误清在用的 revision，再看运行成本与结构，最后看部署次数」排序。引用检查对 GSI 的依赖有两处：一是以 `status` 为键时，`pending` 到 `running` 的换键在删旧项与写新项之间可能留下两个分区都查不到的间隙；二是新建 run 的索引项要在静默期之内可见（上面边界情形 (b)）。第二处是以 `status` 为键的旧索引上本来就有的依赖，任何经 GSI 找引用的做法都有，选定方案不新增、也不消除。选定方案关闭的是第一处：换值不改变索引键，没有这次换键，也就没有它的间隙。以 `status` 为键的做法保留这次换键，靠复查降低漏检：趟内复查要求间隙短于一次分区读取加等待时长，余量是秒级；跨趟确认要求同一个间隙短于两趟的间隔 T，T 取到约 1 小时时，它对传播上界的依赖与第二处同一量级，两者在这一点上差的是余量大小、不是有无。跨趟确认与选定方案的区别因此在其余几项：运行成本上，只留 KEYS_ONLY 的列举索引时每趟要强一致读回全部非终态 run 的整个 STATE，选定方案在正常生命周期下每个 run 3 个索引写单位、表上一个索引、清理一次 `Query` 不读回；协议上，它多一个 revision 级的确认标记，回收多等一趟；对传播上界的依赖余量取决于 T。从当时表上两个以 `status` 为键的索引出发，选定方案要经过多次 stack 更新（CloudFormation 一次更新只改动一个索引），多于只留其中一个索引的一次；部署次数这一项只在从更早的索引形态迁移时才起作用，而状态分组索引这一形态确定时产品还没有使用者、不提供这种迁移的路径（[0041](./0041-agent-facing-cli-affordances.md) 决策七「更早的索引形态」），所以排在最后（被拒方案见下「被拒方案」节与 [0030](./0030-realtime-persistence-seam.md) 决定六）。
  - **已退休却仍被映射引用**：上面「打 tag 与写映射的交错」段的交错也会短暂留下这个状态，由那里的各道摘除处理；不靠交错、持续存在的这个状态只来自早先版本留下的跨 variant、跨版本共用——一条映射被替换时，替换的一步给被替换的 revision 打 `retired-at`，另一 variant 或另一版本的映射仍引用它。取消孤儿复用之后，新的共用不会再产生：新注册的 revision 只被发起注册的那一条映射引用（步 5、步 6 与重派生都只把自己刚注册的 revision 写进自己那条映射）；跳过注册的分支沿用的是本条映射自己记录的 revision，不写映射。早先版本留下的共用只会随映射被替换而减少，不会经本模块重新形成：本模块不再把一个已有的 revision 写进任何映射，被清理 pass 摘掉 tag 的共用 revision 也不会被另一条映射重新引用（复用存在时，旧版本重推旧 digest 就能复用它、重新形成共用）。「不再产生」只对本版本的命令写的映射成立：手工改 SSM 不在论证之内，旧版 CLI 仍会复用孤儿（上「候选与静默期起点」段末）。在现阶段没有使用者、不做旧数据兼容的发行边界下，这类 revision 被清理 pass 摘掉 tag 之后就是一个普通的在用 revision，等它的最后一条映射被替换时再打 tag、从那时起算静默期。映射引用仍是清理的前置条件，与运行中 run 引用并列：在任一映射里的 revision 不是候选。**已知盲区**：`run --backend cloud --no-report`（有意的逃生舱）不写 STATE item，其 revision 引用对这道引用检查不可见——这样一个跑超过 1 小时的 run 期间别重推同名 variant。引用检查改读状态分组索引之后另有一类同性质的盲区：旧版 CLI 写出、不带分组属性的 run（上面残余风险⑤）。
- **默认指针不自动重置**（含版本升级）：它记的是团队意图。
- **不判 steps 内容**：镜像里的 steps 是否最新由使用方管理；preflight 不比对镜像内 steps 与本地 steps——越权替使用方判断，且提交者（feature 作者、CI 机器）手头未必有 steps 目录、会被误拦。想区分就换 variant 名。

## 运行时与 preflight

- **选择进 definition**：`run/submit --backend cloud [--worker-variant <名>]`，缺省取默认指针；CLI 在 preflight 把 variant 解析成各引擎的 revision ARN，写进 definition——`RunMeta.worker_variant`（人读）与 `RunMeta.worker_task_defs`（引擎 → revision ARN），本机后端为 null（键集随结构版本固定，[0037](./0037-distribution-and-packaging.md) 决策 7），沿用 `max_concurrency`/`extra_http_headers` 随 definition 走的惯例（[0034](./0034-detached-batch-reconciler.md)/[0035](./0035-local-app-testing-via-tunnel.md)）；同一批 ARN 同时写成 STATE 顶层属性（清理的引用检查用）。云端推进器（kicker / reconciler）与同步 `run` 的 `FargateEngine` 一律照 definition 起 task。local 后端忽略该 flag（直接读 steps 目录）。
- **读侧不留兼容路径**（随 [0037](./0037-distribution-and-packaging.md) 决策 7 的「读端只认当前一个结构版本」改写）：云端 definition 必带 `worker_task_defs`（提交侧解析 variant 后写入），推进器读到缺值按定义违约处置——不推进该 run、记一条诊断、把 run 标为 error；**不**按后端当前默认指针解析（那会让运行中的 run 中途换 step 集，破坏「一个 run 内镜像固定」的不变量），**不**回落 family 最新 ACTIVE（那可能是别人的 variant），**也不**用模板 revision（其 `latest` 占位在从未推过 `latest` 的全新 prefix 上根本拉不到镜像）。曾有的「缺字段按默认指针解析」兼容路径服务的是引入本 ADR 那一次升级前提交的 run 与旧 CLI 提交的 run，1.5 不假设存量用户、读端对旧 definition 一律拒绝，该路径随之删除。
- **preflight 只做存在性与一致性，不判内容**，位置在既有 preflight（表/桶/cluster/task-def/三 Lambda）与**版本 skew（[0037](./0037-distribution-and-packaging.md) 决策 7）之后**——skew 的修复动作（deploy）是镜像重推的前置，反过来会让用户白推一轮。对**本 run 用到的每个引擎**（对齐既有 task-def 判据「不探全注册表——没用到的引擎不该拦」）：请求的 variant 在 SSM 有**当前版本**（= 提交者 CLI 自身版本，与 push-worker 打 tag 用的同一个）的映射、revision ACTIVE、ECR 镜像（按 digest `describe-images`）存在——任一缺 → 退 2，**不回落默认**（回落是静默行为）；提示语按 skew 分叉：CLI 与后端同版本 → 「`gherkai deploy push-worker … --variant <名>`」；CLI 旧于后端（决策 7 只警告不拦的那一类）→ 「升级 CLI 到后端版本」，不引导去推一个旧版本 tag 的镜像；通过则打印各引擎解析到的 variant / digest。**缺失的判定口径**：AWS 读失败按以下规则分流；其中 ECS 的「本次未确认可用」不等于确认资源不存在。算作缺失的——SSM `ParameterNotFound`；ECS 的 revision 描述报 `ClientException` 时，列举它所在 family 的 ACTIVE revision，本次列举未发现该 ARN 即按本次未确认可用处理、算作缺失（这个错误码泛指请求本身有问题、ECS 的说明里也包括调用方对动作或资源没有权限，单凭错误码分不出「资源不在」与其它客户端错误；列举成功而其中有它，原错误原样抛出；列举本身失败，抛出列举的错误；revision ARN 不是完整的任务定义 revision ARN 形态 `arn:<分区>:ecs:<区域>:<账号>:task-definition/<family>:<编号>` 时不列举、原错误原样抛出），描述报其余错误（访问被拒、限流、服务端错误、网络错误）时含义明确，原样抛出、不发列举请求——列举只在确有歧义时发生，描述被拒时使用者看到的是缺描述权限，不会被随后一次列举的结果盖住；分流只看错误码，不解析报错文本。本实现仅在描述返回 `ClientException` 时列举核对。从未注册过的 revision 在真实 ECS 上返回这个错误码；本次真实账户观察中，发起删除后仍能描述该 revision，返回状态为 `DELETE_IN_PROGRESS`，按「状态不是 ACTIVE」判为不可用、不经过列举；它最终消失之后描述返回 `ClientException`、与从未注册过的编号相同（实测项 11）。若返回其他错误，则原样抛出，该次调用不会修复这条映射（push-worker 与重派生以该错误失败、不注册新的 revision 替换它）。这条限定只能做在代码里：`ecs:ListTaskDefinitions` 与 `ecs:DescribeTaskDefinition` 不支持资源级权限，`Resource` 必须为 `"*"`；仍可使用适用的 IAM 全局条件键，例如 `aws:RequestedRegion`（依据 AWS Service Authorization Reference 的 Amazon Elastic Container Service 一页：这两个动作的资源类型一栏为空；条件键一栏为空只说明没有 ECS 自己的条件键，该参考的表格说明写明适用于任意动作的全局条件键不列在表里，IAM 文档写明 `aws:RequestedRegion` 始终在请求上下文里），IAM 条件表达不了「描述报某个错误码之后才列举」，用到列举的时机由判据本身收窄；ECR `ImageNotFoundException` / `RepositoryNotFoundException`；权限不足、限流、网络等其余 botocore 错误原样抛出，由 `run` / `submit` 入口以退出码 2 结束并提示核对凭证 / region / 权限，不给推镜像的提示——翻成缺失会把缺只读权限（`ecr:DescribeImages` / `ecs:DescribeTaskDefinition` / `ecs:ListTaskDefinitions`）的提交者引去重推镜像、原地绕圈。push-worker 与重派生判断映射所指的 revision 是否仍为 ACTIVE、注册之后的再读，都用这一个判据。列举未发现该 ARN 不证明 revision 已被注销或删除：刚注册的 revision 可能尚未出现在列举结果里；查询结果尚未可见时，push-worker 与重派生可能额外注册一个 revision，提交侧可能暂时拒绝提交（提示推送，并提示刚推送过的稍后重新提交）。
- **一个 run 一个 variant 名**，跨引擎同名；某引擎缺该 variant 即上条的退 2。

## 多版本与多环境

**一个部署（一个 prefix）在任一时刻只有一个后端版本**：Lambda 代码、模板 revision、SSM 版本戳都是单份，本 ADR 与 0037 的版本真源都建立在这个前提上；不做同一 prefix 内的双版本并行。variant 按版本隔离只是历史保留，不是旧版本在运行。**要多个版本并存（多人/多团队各用各的），用不同 prefix 部署成不同环境**——prefix 本就是全部云资源的命名空间（[0033](./0033-iac-aws-backend-and-composition-wiring.md)），CLI 经 `--prefix` 显式选择连哪个环境，这是现有机制、无新增设计；闲置成本近零（[0034](./0034-detached-batch-reconciler.md) 的事件驱动、无常驻），只多一份 ECR 存储。local 后端不涉及云端部署、无此问题：CLI 升级即全部升级（worker 经 `[local]` 装在同一 venv）。

## SSM 参数与命名真源

| 参数（前缀 `/{prefix}backend/`） | 值 | 写者 |
|---|---|---|
| `worker-template/<engine>` | 模板 revision ARN | stack 资源（随 `gherkai deploy` 事务） |
| `worker-image/<engine>/<版本>-<variant>` | JSON：模板 revision ARN、revision ARN、digest、推送时间 | `push-worker`（含 deploy 的基础镜像同步与重派生） |
| `worker-default` | 默认 variant 名（部署级一个） | deploy 初始化、`push-worker --set-default` |
| `device-farm-project` | 云端 Device Farm 项目 `{prefix}devices` 的 ARN（stack 拿不到项目 ARN 时不建这个参数） | stack 资源（值由 `deploy` 在 cdk 之前找回或建立项目后经 context 传入，随 `gherkai deploy` 事务写、随 `destroy` 删除；项目本身不归 stack 管理，`destroy` 保留） |

键名常量与路径构造**单点在 `gherkai_runtime.names`**（`ssm_path` / `worker_template_key` / `worker_image_key` / `WORKER_DEFAULT_KEY` / `WORKER_IMAGE_ROOT_KEY` / `BACKEND_VERSION_KEY` / `SUBNETS_KEY` / `SECURITY_GROUPS_KEY` / `VPC_KEY` / `DEVICE_FARM_PROJECT_KEY`）——推送方、解析方、IaC、Lambda 拼同一个函数/常量，调用点不写裸字面量（曾在组合根、IaC 命名层、deploy 皮三个模块各写裸 `"version"`）。

退休时刻与血缘**不进 SSM**、以 task-def 的 tags 承载（`gherkai:variant` / `version` / `digest` / `template` / `retired-at`；`retired-at` 表示从何时起不被任何映射引用，由替换映射的一步与清理 pass 打，由写映射一方与清理 pass 摘，见「不变量」清理 pass 条）——与 revision 同生死、不撑 SSM 标准参数 4KB 上限、清理对账只看一处。`version`、`vpc` 两个参数归 [0037](./0037-distribution-and-packaging.md)，`subnets`、`security-groups` 归 [0033](./0033-iac-aws-backend-and-composition-wiring.md)「subnet/sg 走 SSM」，`device-farm-project` 的找回或建立、核对与无权限降级归 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 10。全部落在 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 已授的 `/{prefix}backend/*` 通配内。枚举用 `GetParametersByPath`（`Recursive=true`，单页最多 10 条须翻页）。variant **按版本隔离**：键含版本，旧版本的 variant 留在 ECR 与 SSM 作历史、不参与当前版本解析，`delete-worker` 落地后可清。

## 权限面增量

[0033](./0033-iac-aws-backend-and-composition-wiring.md)「资源清单」末段是编排机器权限的单一登记处（已按下列增量改毕），此处只列增量；**资源域按 0033「结构上只能 `*` 的动作诚实保留、单开 statement」的纪律标注**：

- **部署方**：ECR repo 域动作 `ecr:BatchCheckLayerAvailability` / `InitiateLayerUpload` / `UploadLayerPart` / `CompleteLayerUpload` / `PutImage` + **`ecr:DescribeImages`**（推送前读旧 digest 以打印「原 → 新」；限两个 `{prefix}{engine}-worker` repo ARN）；**只能 `*`** 的 `ecr:GetAuthorizationToken`（其 `proxyEndpoint` 即 registry host——授权响应里的权威值、与 moto 一致，**不需要** `sts:GetCallerIdentity`）、`ecs:RegisterTaskDefinition` / `ListTaskDefinitions` / `DescribeTaskDefinition`（task-def 类动作官方明文不支持资源级权限）、`ecs:TagResource`（注册时打血缘 tag、退休时打 `retired-at`）；`ecs:DeregisterTaskDefinition` / `DeleteTaskDefinitions`（清理 pass 回收 revision 用）同属 task-def 类动作、按 `Resource: "*"` 授；`iam:PassRole`（task / execution role，RegisterTaskDefinition 需要）；SSM `GetParameter`（点读模板/映射/默认指针）+ `PutParameter` + `GetParametersByPath`（`/{prefix}backend/*`）；runs 表 `dynamodb:Query` 供清理的引用检查——**资源须含索引 ARN** `table/{prefix}runs/index/status_group-run_id-index`（只给表 ARN 查不了 GSI）；runs 表 ARN 上的 `dynamodb:DescribeTable`（清理的就绪检查）；`ecs:UntagResource`（push-worker 步 7、重派生写映射之后与步 5 跳过分支确认 ACTIVE 之后立即摘除，清理 pass 摘掉仍在映射里的 revision 上的 `gherkai:retired-at`；与 `TagResource` 同样按 `Resource: "*"` 授）；`ecs:TagResource` 另用于清理 pass 补打 `gherkai:retired-at`，`ecs:ListTaskDefinitions` 另用于描述 revision 报 `ClientException` 时的核对，只在这一类无法从错误码区分「资源不在」与其它客户端错误的报错时用到（「缺失的判定口径」；这个动作不支持资源级权限，`Resource` 必须为 `"*"`，仍可使用适用的 IAM 全局条件键，例如 `aws:RequestedRegion`；用到它的时机只能限定在代码里）。
- **提交者**：只读 `ecr:DescribeImages`（repo 域）、`ecs:DescribeTaskDefinition` 与 `ecs:ListTaskDefinitions`（两个动作不支持资源级权限，`Resource` 必须为 `"*"`；仍可使用适用的 IAM 全局条件键，例如 `aws:RequestedRegion`；依据 AWS 的服务授权参考，见「缺失的判定口径」；后者只在描述 revision 报 `ClientException`、无法从错误码区分「资源不在」与其它客户端错误时用于核对它是否仍在 ACTIVE revision 里，描述报访问被拒、限流等其余错误时不发列举请求）；SSM 读落在已授通配内。
- **云端推进器**：`ecs:RunTask` 资源域须覆盖 family 全部 revision——当前 IaC 已按 `task-definition/{family}:*` 授权（reconciler 与 kicker 同源），**无增量**；不读 SSM（曾为兼容回落默认指针授过 `GetParameter` + `GetParametersByPath`，随「读侧不留兼容路径」撤除；exit-observer 从未授过）。
- **测试开发不需要任何 AWS 写权限**（不推送时）：这是构建与推送解耦的直接收益。

## 容器引擎口子

只需五个动词：`inspect`（存在、架构；推送后再取 digest）、`tag`、`login`、`push`、`pull`。默认 docker，`--container-engine podman` / env `GHERKAI_CONTAINER_ENGINE` 切换（podman 子命令相同），只实现 docker（podman 经同一口子接入，见重议闸门）。产品 code 里碰 docker 的只有 `gherkai_deploy_aws/container.py`（push-worker 与 deploy 的基础镜像同步经它；密码只走 `--password-stdin`）与两个 Dockerfile，CLI / runtime / CDK 都不碰它；发布链另在 `.github/workflows/release.yml` 用 docker 官方 action 构建并推基础镜像，`release.yml` 与 `ci.yml` 的镜像 gate 另以 local 态构建同样两个镜像、不推送（均见 [0037](./0037-distribution-and-packaging.md) 决策 8）。`--container-engine` 在 `deploy` 与 `push-worker` 上都收（deploy 的第 2 步也要它）；两类失败分开决定退出码——名字不认 → 退 2（本地参数问题，先于 VPC 取值比对）；装了但不可用 → cdk 前只警告、cdk 后退 1「stack 已生效、重跑幂等收敛」。**deploy 机器需要容器引擎**（同步基础镜像要 pull / push；非纯发行版本跳过该步、不探活）；免容器引擎的 registry 直拷是重议闸门里的加法。

## 与版本升级的交互

[0037](./0037-distribution-and-packaging.md) 决策 7 的「升级即三步」中，本 ADR 负责第 ②③ 步的镜像半边：②`gherkai deploy` 同步新版本 `base`、登记新模板、对新版本已有的 variant 重派生（升级当下通常没有）；③团队有自定义 variant 或自定义默认的，从新版本基础镜像重新 build 各引擎镜像、`push-worker` 推上去。**默认指针不重置**：它记的是 variant 名（如 `common`），新版本 `1.5.0-common` 未推之前 preflight 退 2、提示「默认 variant `common` 在 1.5.0 尚无镜像：`push-worker … --variant common`，或临时 `--worker-variant base`」；推上去即恢复，不必再 `--set-default`。升级窗口内**运行中的旧 run**（definition 无 `worker_task_defs`）由推进器标 error、不执行（「读侧不留兼容路径」；[0037](./0037-distribution-and-packaging.md) 决策 7 不设存量兼容）。

## 实测项（1-7 **已清零**；8-10 **待核**：10 所核的静默期起点与各道核对已实装，8、9 所核的状态分组索引与新引用检查已实装，待在部署出的后端上执行；11 已核；「绿≠对」——每条都依赖 mock 之外的真实行为，证据内联于各条）

1. 使用方按模板 build 后 `push-worker`，自定义 variant 与 `base` 并存、各自跑通两引擎；arm Mac 上不带 `--platform` build 出的镜像被步 2 拒绝并给出提示；`--worker-variant` 对某引擎缺失时严格退 2；`--set-default` 在另一引擎缺失时只警告。（**真账户已验**（独立 prefix、dev 版本、本地态基础镜像作 `base`）：两引擎 `push-worker … --variant base` 真推 ECR → 推后取 digest → 注册 revision → 写 SSM；`--worker-variant nope` 退 2 并给 push 提示；`--set-default probe2` 只警告 midscene 缺映射，随后不带 flag 的双引擎 submit 在 preflight 被 midscene 缺映射拦下退 2；恢复 `base` 后双引擎 run passed。**发行版基础镜像亦已验**：v1.4.0 首发后用 `uvx gherkai==1.4.0` 提交双引擎 run，两 task 分别用 GHCR 同步来的 `1.4.0-base` revision（两引擎的 ECR 镜像 digest 与 GHCR manifest digest 逐字相同），exit 0、run passed。**自定义 variant 携带真实使用方 step 亦已验**（v1.4.0 发行版）：使用方项目 `steps/title_check.py` + `steps/title-check.mts` 注册同一条 `页面标题包含 "…"` 的确定性 step，按三行模板 `FROM ghcr.io/…:1.4.0` + `COPY steps/` + `ENV GHERKAI_STEPS_DIR` 各 build 一个镜像、`push-worker --variant custom` ×2，`submit --worker-variant custom` 的三 scope run：novaact 与 midscene 正例各 passed、novaact 故意错的标题断言 **failed**（证明走的是确定性 handler 而非 AI 兜底），三个 task 用的正是 custom 的 revision、worker 均 exit 0。**未另跑（判据已验、场景等价）**：arm Mac 上不带 `--platform` 真 build 这一场景没单独跑——`inspect` 得 arm64 → 步 2 拒的判据已在真 docker 上用真 arm64 镜像验过（见下 6），同一分支不重复跑。）
2. push-worker 幂等：在推送与注册之间、注册与写 SSM 之间人为中断后重跑收敛；两个终端并发 push 同名 variant 后 `list-workers` 标出孤儿、静默期后清理回收。（**真账户部分已验**：同镜像重推 → 「映射已是（当前模板，本 digest）→ 跳过注册」；同名 variant 换 digest 重推 → 打印「原 → 新 digest」、旧 revision 打 `retired-at`、`list-workers` 列为待清理；与 `base` 同 digest 的新 variant 注册自己的 revision、不复用 `base` 的（此处真跑抓出并修掉「跨 variant 复用」，见被拒方案「孤儿复用」条）；**中断重跑**（按血缘 tags 手工注册一个 variant 的 revision、不写 SSM 以模拟中断在注册与写 SSM 之间 → 重跑 push-worker 复用它、不重复注册；验的是当时的孤儿复用，它已取消（被拒方案「孤儿复用」条），取消之后改为新注册、留下的那个由清理回收，待核于实测项 10）；**并发 push 同名 variant**（两进程不同 digest 同时推 → 各注册一个 revision、后写者映射赢，`list-workers` 把先写者标为孤儿）。**静默期回收已验**：退休满 1 小时的 revision 在下一次 push-worker 末尾被回收，同趟未满 1 小时的留着（见下 3）。）
3. 清理 pass：有运行中的 detached run 引用时被拦下、run 结束且静默期满后下次 pass 成功；「preflight 刚解析完立即 submit」的对抗用例不被清理打断；deploy 改 cpu 后重派生使既有 variant 的 revision 更新且旧 revision 被打 `retired-at`。（**真账户已验**：`gherkai deploy --stop-timeout 100` 只改模板 → 六个（引擎，variant）全部重派生到新 revision（继承 `stopTimeout=100`、镜像仍按原 digest、`pushed_at` 保留）、旧 revision 打 `retired-at`、默认指针不动；**静默期回收**：退休满 1 小时后的下一次 push-worker 末尾清理 pass 真回收了该 revision（`DeregisterTaskDefinition` + `DeleteTaskDefinitions`，AWS 侧随即 `DELETE_IN_PROGRESS`），同一趟里未满 1 小时的退休/孤儿 revision 全部留着。**运行中 run 拦截已验**：把一个已退休 3 小时的 revision 交给一条非终态 STATE（`worker_task_def_arns` 含它）引用，清理 pass 留下它（ECS 仍 ACTIVE）；把该 run 置终态后下一趟回收（`DELETE_IN_PROGRESS`）——GSI Query + `contains` 的引用检查在真 DynamoDB/ECS 上成立。「preflight 刚解析完立即 submit」的窗口由 1 小时静默期覆盖，未另做对抗。）
4. 重推同名 variant 期间运行中 run 的后续 job 仍用旧 revision；无 `worker_task_defs` 的 definition 由推进器标 error、不执行（「读侧不留兼容路径」；曾有的默认指针兼容路径在真账户验过后随 [0037](./0037-distribution-and-packaging.md) 决策 7 撤除）。（**重推期间运行中 run 的后续 job 仍用旧 revision已验**：3 个 scope `--max-concurrency 1` 串行 run 跑到第一段时重推同名 variant（digest 换、旧 revision 打退休 tag、新 revision 注册），随后的第二、第三段 task 仍用旧 revision（definition 钉死），run passed。）
5. 升级演练：CLI 升版后 deploy → 默认指针悬空的 preflight 提示 → push 同名 variant 后恢复，不需 `--set-default`；CLI 版本超前于后端时 push-worker 被 skew 前置拦下。（**真账户已验**（跳板机克隆打本地 tag 得纯 `1.4.0` CLI + 改写 SSM 版本戳模拟后端版本）：戳 1.3.0 → `list-workers`/`submit` 均 block 退 2、push-worker 侧多给带 `[deploy-aws]` extra 的 uvx 出路；戳 1.5.0 → warn 不拦；戳 1.4.0 → 静默放行、`1.4.0-base` 未推 → submit 退 2 点名 push；push 同名 `base` → submit 解析到新映射、run passed、默认指针未动。**真 `gherkai deploy` 写新版本戳 + 同步 GHCR 基础镜像已验**：用发行版 `uvx --from 'gherkai[deploy-aws]==1.4.0' gherkai deploy` 把验证环境从 dev 版升到 1.4.0——SSM 戳变 `1.4.0`、两引擎从 GHCR 拉 `1.4.0` 基础镜像推成 ECR `1.4.0-base` 并注册 revision、默认指针不动、无需重派生（新版本尚无其它 variant）；随后 `uvx gherkai==1.4.0 submit` 的 run 用新 revision 跑通。）
6. 本地未推送镜像的 `inspect` 在两种镜像存储下给出的 `RepoDigests` 都不能证明目标仓库已有该内容，推送后取到的 digest 与 ECR `describe-images` 一致、注册的 revision 能被 RunTask 拉起。（**已验**：真 docker——overlay2 存储（Docker 29.9.3）下未推送镜像 `RepoDigests` 空、`docker tag` 到 ECR ref 后仍空；containerd 镜像存储（Docker 29.1.3，amd64 主机）下，刚构建、从未推送的镜像 `RepoDigests` 即有一条 `<本地名>@sha256:X`，`docker tag` 到 ECR ref 后多出一条 `<该 repo>@sha256:X`（同一个 X），全程没有推送——本地出现某个仓库的条目不证明仓库里有这份内容，所以步 4 只在推送成功之后取、按本 repo 挑，两种存储下同一条规则都成立；arm64 镜像被步 2 拒。真引擎用例自带一个现构建的测试镜像、按引擎报告的镜像存储分两支断言，不借用本机已有的 worker 镜像：做过 push-worker 的机器上它已带着 ECR 的 repo digest，「从未推送」的前提不成立。真账户——推后取到的 digest 被 `describe-images` 认（preflight 三环通过），kicker 起的 Fargate task 的 `taskDefinitionArn` 正是 push-worker 注册出的那个 revision（显式 revision、非 family 最新），两引擎 task 各 exit 0、run passed；containerd 镜像存储下的 digest 链逐环对过（两个引擎各一份、由不带构建证明的经典构建器构出的单平台镜像）：本地镜像上该仓库条目的 digest、ECR 里该对象的 digest、注册出的 revision 引用的 digest 三者相同，ECR 里的对象是单个 OCI image manifest，云端 task 由这个 revision 拉起并执行；这一存储下本地的 image Id 与该 digest 相同。**已验范围到此为止**：带构建证明（provenance / SBOM）而在本地成为 OCI 索引的镜像，在 containerd 存储下推送后仓库收下的是什么对象、本仓库条目的 digest 是否仍与之一致，没有核过；基础镜像的发布关掉了构建证明（[0037](./0037-distribution-and-packaging.md) 决策 8），同步路径上不会遇到，使用方自己构建的定制镜像可能遇到。）
7. 多平台本地镜像的两种存储形态（**都已在真引擎上核过**）。overlay2 存储**装不下多平台镜像**——`docker buildx build --platform linux/amd64,linux/arm64 --load` 直接报 `docker exporter does not currently support exporting manifest lists`，`inspect` 恒给单平台视图（arm 主机上得到 arm64 → 被拒，过严但安全）。containerd 镜像存储（Docker 29.1.3，amd64 主机）：`docker pull --platform linux/arm64 alpine:3.20` 后本地引用是索引——`inspect` 顶层 `Os` / `Architecture` 为空串、`Descriptor` 是 index、`RepoDigests` 是索引 digest；`inspect --platform linux/arm64` 给出 linux/arm64 与该平台 manifest 的 Descriptor；`inspect --platform linux/amd64` 退出码 0 但两字段仍为空（索引列了 amd64、内容没拉）；同一索引只拉 amd64、或 amd64 与 arm64 都拉时，顶层直接给 linux/amd64（顶层 = 本机平台那一份的视图，有则填、无则空）；对本地 `docker build --platform linux/amd64` 构出的单平台镜像，顶层字段有值、`--platform linux/arm64` 报 `does not provide the specified platform`。步 2 据此以「顶层为空就问目标平台视图」为判据：由此推演（未在 arm 主机真跑）arm Mac 开 containerd 存储时按文档 `--platform linux/amd64` 构出的镜像，顶层为空而目标平台视图有值，能通过校验——旧判据会把它拒成「平台是 ?/?」（GitHub 托管 runner 换到 containerd 存储后，CI 的真引擎用例先暴露了旧判据把索引当成未知平台）。`docker image ls --tree` 仍是实验特性、不用。amd64 主机上含 amd64 内容的索引通过校验后 `docker push` 推的是 index，推后 `RepoDigests` 即 index digest，task-def 按它引用，ECS 从 index 选 amd64——**无安全问题**；索引里别的平台缺内容时 docker 自己以 content missing 拒推，不在本工具处置。
8. **待核**：状态分组索引上的索引写与成员资格。在部署出的 runs 表上以 `ReturnConsumedCapacity=INDEXES` 取每次更新对 `status_group-run_id-index` 的写入消耗：建 run 为 1.0；认领、前台 job 写与两种投影把 run 级从 `pending` 换到 `running`（同一次写带同值的 `status_group`）时为 0；收尾换分组为 2.0。同时在一个 run 从建立到收尾的全程紧密循环 `Query` `live` 分组，记录它在换到 `running` 前后是否缺席过。只能给出观测，给不出上界；它核的是「不计写即索引项不受影响」这一推论，清理不依赖间隙的长度。
9. **待核**：新引用检查在真 DynamoDB / ECS 上成立。重做实测项 3 的拦截与回收：分别以 run 级 `pending` 与 `running` 的非终态 STATE 引用一个已过静默期的 revision，清理 pass 留下它；收尾之后下一趟回收。另核就绪检查：对 `status_group-run_id-index` 尚未 `ACTIVE`（回填中）与不存在的 runs 表执行清理，都跳过并打出一行警告、不注销任何 revision（回填中的情形可在一张已有数据的表上新增该索引构造；CLI 新于后端时版本 skew 闸会先拦下 push-worker，这类情形用不经该闸的非纯净版本构造，或直接调用清理）。
10. **待核**：静默期起点。替换 R 的那条命令给 R 打上的 `gherkai:retired-at` 不早于写映射成功的时刻；手工摘掉 R 的这个 tag 以模拟替换时没打上，命令末尾的 pass 给 R 补打、不删，R 从补打时起满 1 小时才回收，补打之后 `list-workers` 把它列为 `retired`；给一个仍在映射里的 revision 手工打上 `gherkai:retired-at`，下一趟 pass 把它摘掉，期间 `list-workers` 不把它列为待清理。交错：一条推送停在写映射之前的再读之后（以下放行推送的用例除另注明的外都停在这里：停在再读之前时，放行后的再读看到 tag、改为重新注册，测不到预定的那道保护），让一趟 pass 给它注册的 revision 补打，在补打与重读之间放行推送写映射，重读后当场摘掉；`registeredAt` 晚于该趟读映射时刻的 revision 不被补打；补打的值不早于该趟读映射的时刻。中断与重新执行：推送停在注册与写映射之间时中断，重新执行时新注册一个、不沿用上次注册的那个，上次那个由之后的清理补打、满 1 小时后回收；重派生中断在注册与写映射之间后重新执行，再注册一批，前一批同样回收。注销之前的重读：一条推送停在写映射之前的再读之后，它注册的 revision 在再读之后被补打、超过静默期成为成熟候选（静默期可用手工打一个早于此刻 1 小时以上的值构造），在快照之后、重读之前放行推送写映射，这一趟不注销它并摘掉 tag。注销之前的最后核对：一个成熟候选在快照与映射重读之后、最后核对之前，`gherkai:retired-at` 被改写为新值，或被摘掉，这一趟都不注销它，下一趟按新值重新判定（新值未满静默期即留下）。摘掉自己补打的 tag 放行推送的交错：一条推送停在写映射之前的再读之前（这条用例要它的再读落在 P0 摘掉 tag 之后），一趟 pass P0 给它注册的 revision 补打，这个 tag 满静默期之后另一趟 pass P1 把它收为成熟候选、停在映射重读之后与最后核对之前；让 P0 的重读失败、按协议摘掉自己补打的 tag，放行推送（它的再读看到 ACTIVE、不带 tag，写映射），再放行 P1：P1 不注销，这个 revision 仍在映射里、仍为 ACTIVE。早先版本留下的共用 revision：带着早于静默期的 `gherkai:retired-at`、只剩一条映射引用它时，一趟 pass 在这条映射被替换之后、替换的一步打 tag 之前把它收为成熟候选并停在最后核对之前，放行替换写入新时刻，再放行这趟 pass：不注销。悬空映射：把映射指向一个已注销的 revision，同一镜像重推替换映射、不再沿用。可见性与次序（「打 tag 与写映射的交错」段的①②③）：SSM 写映射成功后另一进程的 `GetParametersByPath` 是否立即读到，`TagResource` 成功后另一进程的 `DescribeTaskDefinition`（`include=["TAGS"]`）是否立即读到这个 tag，紧随 `TagResource` 的 `UntagResource` 是否总把它摘掉。对不存在的 tag 键执行摘除、同键再次赋值的观察已记于实测项 11；这里的跨进程可见性与请求次序仍待核。可见性与次序三项只能给出观测，给不出上界或保证，不关闭残余风险①。新注册的推送：在注册之后、再读之前给新注册的 revision 打上 `gherkai:retired-at`，推送改为重新注册，写进映射的是不带这个 tag 的那个；在再读之后、写映射之前打上，写映射之后它不再带这个 tag（写映射一方的立即摘除）。`registeredAt`：记录真账户上 `DescribeTaskDefinition` 返回的带血缘 tags 的 revision 是否都带这个字段（「实装细则」所说的一直滞留只在取不到时出现）。
11. ECS 对任务定义 revision 在各阶段的真实返回（已核，除末尾一项）。在真实账户上用一个临时 family 注册一个 revision，依次观察：
    - 刚注册之后：`DescribeTaskDefinition` 返回 `ACTIVE`，同一 family 的 `ListTaskDefinitions`（`status=ACTIVE`）在注册后约一秒的第一次查询起就列出它（连续八次都列出）。「刚注册的 revision 暂时不在列举结果里」在这次观察里没有出现，仍按最终一致对待，不作为保证。
    - 从未注册过的编号、从未注册过的 family：`DescribeTaskDefinition` 返回 `ClientException`（消息为无法描述该任务定义）。「缺失的判定口径」只在这个错误码上列举核对，与真实返回相符。
    - 注销之后：`DescribeTaskDefinition` 成功、状态为 `INACTIVE`，`ACTIVE` 列举里不再有它；对它打 tag 成功。
    - `DeleteTaskDefinitions` 之后：响应里状态为 `DELETE_IN_PROGRESS`、没有 `failures`；此后至少八分钟内 `DescribeTaskDefinition` 一直成功、状态为 `DELETE_IN_PROGRESS`，不返回错误，它出现在 `status=DELETE_IN_PROGRESS` 的列举里；对它打 tag、摘 tag 都成功，再次注销返回 `ClientException`。因此，本次观察到的 `DELETE_IN_PROGRESS` 响应由「状态不是 `ACTIVE`」这一支判为不可用，不经过 `ClientException` 加列举这一支（最终消失之后的返回见本项末条）；moto 对已删除的 revision 返回 `ClientException`，与真实 ECS 在这段时间里的形态不同，测试里以 moto 的形态模拟删除的用例守的是列举这一支本身。
    - 同一个 tag 键再打一次：读回的是后一次的值（与官方文档的说法一致）。对不带某个 tag 键的 revision 摘除这个键：成功返回，不报错。
    - `DELETE_IN_PROGRESS` 最终消失之后：发起删除约三四十分钟后的一次描述返回 `ClientException`（消息同上），与从未注册过的编号相同；这时由「描述报 `ClientException`、ACTIVE 列举未发现」这一支判为本次未确认可用。
- **mock / 无凭证层的覆盖面**（真账户证据见上各条）：真 synth 出的模板含 runs 表 `status_group-run_id-index`（分区键 `status_group`、排序键 `run_id`、INCLUDE `worker_task_def_arns`）、推进器角色无 SSM 读策略、ECR 无 lifecycle、无模板 env；moto 验了八步幂等（二元组查重、中断后重新执行即新注册、不匹配 family 里已有的 revision、退休 tag）、清理的三个前置条件（静默期 + 对 `live` 分组的一次 GSI Query + 映射引用）、就绪检查只认状态分组索引（表上其它索引 `ACTIVE` 而它缺失时不注销、不 Query）、快照翻页读完、重派生、指针不重置、`--set-default` 只警告、skew 前置；**跨组件真互通**——真 `DynamoDBRunStore` 的 `create_run`、把 run 级写成 `running` 的 job 写与 `finalize_run` 写出的 STATE 被真实的清理快照在键与投影都与 stack 相同的索引上读到：建 run 后与换到 `running` 后都在快照里，收尾之后不在，META item 与不带 revision 列表的 run 不贡献 ARN；其余快照用例以 core 写端的同一个派生函数写出分组属性，验 `pending` 与 `running` 的 run 在同一次查询里被读到、各终态的 run 不在快照里；core 侧另有用例守真写端写出的分组与 META 不进索引。真 push 写的 SSM/ECS/ECR 三件套被提交侧的 `resolve_worker_variant` 原样读回。synth 断言 runs 表恰有 `status_group-run_id-index` 一个索引，`status-index` 与 `status-run_id-index` 都不在。

## 被拒方案（护栏，防未来重踩）

- **gherkai 拥有定制镜像的构建（曾拟 `build-workers` 命令即时生成 Dockerfile、build、push 一体，且住 CLI 本体）**：镜像构建是测试开发自己的容器工作，gherkai 拥有它就得替所有构建方式与引擎负责；只保留三行模板，云端侧的推送与注册归部署方、归 `gherkai-deploy-aws`。
- **支持 ARM64 / 多架构基础镜像、架构随 variant 走**：Fargate ARM64 的不可用面按 AZ（us-east-1 的 `use1-az3`），要按 ZoneId 排除子网、维护排除表、多架构 buildx、`--base-arch` 旋钮，换来约 20% 的 task 单价；复杂度不值，且使用方 build 仍需注意平台。固定 linux/amd64，push-worker 推送前校验把 `--platform` 漏给的错误提前 fail-loud。锁文件静态核查两侧依赖均有 linux/arm64 产物（Python 侧 playwright 等 18 个平台 wheel、Node 侧 esbuild/sharp），将来要省钱路是通的，见重议闸门。
- **preflight 校验 steps 漂移（steps 目录摘要作第二个 tag 或存 SSM 比对）**：越权替使用方判断内容；提交者手头未必有 steps 目录会被误拦；需要区分就换 variant 名。
- **variant 参数叫 `--tag`**：它只是 ECR tag 的后缀，与镜像 tag 混；`--variant` / `--worker-variant`。
- **push-worker 一次收两个引擎（`novaact=<img> midscene=<img>`）**：参数形式重、两引擎镜像本就分别 build；一次一个引擎、`<本地镜像>` 作唯一位置参数。
- **读基础镜像 LABEL 校验镜像的基础镜像版本**：唯一用途是防「旧基础镜像 build 推成新版本 tag」，去掉后此错误在运行期以 worker 协议错误暴露，与「内容由使用方负责」一致；`inspect` 只用来取存在与架构。
- **推送前用本地 `inspect` 的 image Id 当 digest**：overlay2 存储下那是 config digest，不是 manifest digest，注册能过、RunTask 才 `manifest unknown`。更一般地，无论哪种镜像存储，推送前本地给出的值（`.Id` 或 `RepoDigests` 里的条目）都只说明本机有什么、不证明仓库里有这份内容（containerd 存储下 `tag` 之后就有该 repo 的条目，实测项 6）；digest 只在推送成功之后取、按本 repo 挑。
- **不可变 ECR tag（重推同名 variant 须先删）**：bugfix 不想改名是正当需求；replace 交给使用方，run 内一致性由 digest 引用的 revision 保证。
- **默认镜像 = 不带 variant 后缀的裸版本 tag，重推即覆盖**：会把 `base` 从映射里抹掉、退路只能重拉；默认改为指针，所有镜像都有 variant 名。
- **RunTask 传 family（取最新 ACTIVE revision）**：多 variant 下任何一次 push 都会劫持默认；一律显式 revision。缺失字段时也不回落 family，按定义违约标 error。
- **缺字段时回落模板 revision（`latest` 占位）**：全新 prefix 从未推过 `latest`，RunTask 拉镜像直接失败、错误拖到 Fargate 启动期；缺字段按定义违约标 error（默认指针解析也曾作为回落、已随「读侧不留兼容路径」撤除）。
- **revision 按 tag 引用镜像**：重推同名 variant 会让运行中 run 的后续 job 换镜像；按 digest 引用。
- **push-worker 抄「最近一次」revision 作模板**：最近一次可能是某个 variant 的、且模板改过后已过期；永远从 deploy 登记的模板 revision 复制。
- **模板 revision ARN 由 deploy 命令事后 `put_parameter`**：回滚留错值；stack 资源随事务。
- **deploy 改模板后不重派生既有 variant**：旧 variant 会一直跑旧 cpu/配置直到有人重推，且无人会想起来；重派生按模板 ARN 与映射所指 revision 是否仍为 ACTIVE 判定是否需要、幂等。
- **升级时自动把默认指针重置回 `base`**：抹掉团队意图；不重置，preflight 提示指向 push 或临时 `--worker-variant base`。
- **重派生/重推后立即删旧 revision**：INACTIVE 不能再起新 task（且注销后最多 10 分钟才生效），detached run 逐 job 起 task 会断；先打退休 tag、静默期满且无运行中 run 引用才删。
- **退休名单存 SSM 参数（JSON 列表）**：撑 4KB 标准参数上限（一轮连续推送即可撑爆）、与 revision 分家、对账要看两处；改为 revision 自身的 `gherkai:retired-at` tag。
- **清理靠定时任务**：多一个常驻资源与凭证面；机会式 pass 挂在 push-worker / deploy / delete-worker 上，滞留无害。
- **清理靠全表 Scan runs 表**：runs 表 `RETAIN`、无 TTL、无界增长；改 STATE 顶层属性 + GSI 的 Query（状态分组索引 `live` 分组的一次 Query，不 Scan）。
- **孤儿复用（从 family 里捡回未被映射的同配置 revision）**（曾采用，已取消）：推送与重派生在二元组不一致时，先按血缘 tags 在 family 里找同（模板 ARN、digest）、未被映射的 revision 写进映射，找不到才注册。它让「不被引用」的 revision 多出「可能被捡回去」这一种状态，判定与使用之间、摘 tag 与回收之间都会与清理竞争。已核到的几种：复用一方扫描 family 时它不带 tag，扫描结果被持有超过静默期之后才写映射，这期间清理已补打并把它收为成熟候选；一趟清理凭过时的映射，摘掉一个已离开映射、已是成熟候选的 revision 的 tag，使它重新满足复用条件、被另一条推送当场写进映射，而另一趟清理按此前收下的候选正要注销它——不需要谁停留，也不需要 AWS 读写延迟；早先版本留下的跨版本共用，在清理摘掉 tag 之后，经旧版本重推旧 digest 被复用而重新形成。每一种都要另加判据与再读才能收窄，且收窄不到互斥；判据本身也一再要补限定：不限 variant 时，variant B 的镜像 digest 恰与 A 相同就复用了 A 在用的 revision，A 换 digest 重推后它被退休回收、B 的映射悬空（真账户上遇到过）；不限版本时，升级后模板 ARN 不变，新版本推同一份镜像就复用旧版本映射着的 revision，两个版本的映射共用它，它的去留由另一版本的映射决定；排除已退休的则要靠 tag 区分「已判下岗」与「可捡回」。而它省下的只是一次 `RegisterTaskDefinition`：ECR 镜像层共享，多出的 revision 不被引用、由清理在静默期之后回收。取消之后，一个 revision 只剩两种状态：被映射引用，或不被引用、等待回收；进入映射只有发起注册的那条命令一条路，上面几种竞争连同为它们设的限定一起消失（「不变量」清理 pass 条「打 tag 与写映射的交错」「注册与回收的竞争」「已退休却仍被映射引用」三段）。
- **在 `list-workers` 里把「已退休、仍被映射引用」单独标出（另立一个 `reason` 取值，或加布尔字段 `still_mapped`）**：`retired-at` 归一之后这个状态不再需要保留，下一趟清理 pass 就摘掉 tag，单独标出只报告一个短暂的中间态，而它是在用的 revision、不是待清理的。另立 `reason` 取值另有两个问题：`reason` 是机读形态里的闭集，按它分支的消费方会把新取值当成未知；`reason` 说的是条目为何成了清理候选，「此刻哪个前置条件阻止回收」是另一个维度，混进同一枚举后再有别的阻塞条件就只能组合取值。`still_mapped` 曾被采用（没有随发行版发出），已随归一删除（「命令族」节）。
- **待清理条目的文本写成单一的解锁条件（如「删除旧版本 variant 后才会回收」）**：`delete-worker` 尚未提供，这句指向一个不存在的入口；何时回收取决于静默期、未到终态的 run 引用与下一次清理 pass 何时执行，写成单一解锁条件会让部署方误判。归一之后仍被映射引用的条目不再列出，这一条留作待清理文本的护栏。
- **`--set-default` 硬要求 variant 在每个引擎都存在**：与 preflight「按本 run 用到的引擎判」矛盾，单引擎团队要凭空推另一引擎镜像；改警告。
- **variant 缺失时静默回落默认**：静默换 step 集与「不判内容」矛盾；严格退 2 带提示。
- **push-worker 不校版本 skew**：CLI 超前的人会把镜像推进无人解析的版本命名空间，提交者的提示又把人推回这一步；skew 三态前置。
- **同一 prefix 内双版本后端并行（蓝绿）**：Lambda / 模板 / 版本戳都是单份，版本真源建立在此前提上；多版本用多 prefix。
- **镜像 tag 直接用 PEP 440 版本串**：`+`/`!` 非法；`names.image_tag` 归一化 + 正则校验。
- **task-def 指向 GHCR 直接拉基础镜像、不进 ECR**：运行时依赖 GitHub 可用性、出网流量、匿名拉取限额；基础镜像同步进使用方 ECR，运行时只拉自己账号的。
- **ECR 加 untagged 过期 lifecycle**：会静默删掉运行中 run 的旧 revision 按 digest 指着的镜像；回收与 `delete-worker` 同批设计。
- **孤儿的静默期从 `registeredAt` 起算**（曾采用，已取消）：`registeredAt` 是注册时刻，可能早于它离开映射很久；被替换的 revision 打 `retired-at` 失败（只警告不拦）后按孤儿处理，在替换它的那条命令末尾的 pass 里静默期就已满，「preflight 已解析、definition 尚未落库」的窗口失去覆盖，只剩引用检查一道保护。改为清理 pass 看到它不在任何映射里时补打 `gherkai:retired-at`（「不变量」清理 pass 条）。
- **另立只由清理 pass 打的 `gherkai:unmapped-at`、静默期从它起算，`retired-at` 只用于展示（以及当时孤儿复用的排除条件）**：两个时间 tag 并存，回答的都是「这个 revision 从何时起下岗」，语义重叠：`list-workers` 展示一个、回收看另一个，部署方看到的时刻不是决定回收的那个，两个 tag 的打与摘还要各守一套规则。另立它是为了保留「已打 `retired-at`、仍被映射引用」这一状态（摘掉仍在映射里的 revision 的 `retired-at` 会抹掉它），而这个状态除交错留下的短暂情形外只来自早先版本留下的共用，新的共用不会再产生，在发行边界下不需要保留（「不变量」清理 pass 条「已退休却仍被映射引用」段）。所以选定归一到 `retired-at`：孤儿第一次被识别时由清理 pass 补打。早先拒绝这一做法的理由有两条，现在都不成立：一是补打之后另一条推送可能把它写进映射，它便带着一个早于被映射的 tag——这由补打之后的重读与写映射一方的立即摘除处理，另立 tag 时需要的也是同一套处理（「打 tag 与写映射的交错」段）；二是摘掉会抹掉上面那个状态——它已不需要保留。
- **用 SSM 参数历史推算 revision 离开映射的时刻**：每个参数的历史有条数上限，要多一类 API 调用与权限；并发推送里先写者被后写者顶掉的情形，历史里找不到它离开的那一次写。打 tag 只依赖 revision 自身。
- **`_retire` 打不上 tag 就让 push-worker 失败**：失败时映射已经写好，命令失败撤不回，只给使用者一个错误的信号；并发推送产生的孤儿照样存在。
- **引用检查沿用以 `status` 为分区键的索引，两个非终态分区都没查到时隔几秒再查一遍**：`pending` 到 `running` 的换键仍在，复查之后漏检要求新索引项的传播超过一次分区读取加等待时长，对传播时长的余量只有秒级，远小于静默期给新建 run 留的约 1 小时；每当本趟真有东西要删，push 与 deploy 的末尾就多一段等待。
- **引用检查沿用以 `status` 为分区键的索引，候选第一次被确认无引用时打确认标记、相隔不少于 T 的下一趟再确认无引用才删**：换键与间隙仍在，漏检要求同一个间隙持续不少于 T；T 取到约 1 小时时，它对传播上界的依赖与选定方案的静默期（新建 run 的索引项须在约 1 小时内可见，两者都有）同一量级，差的是余量大小、不是有无。被拒在于其余几项：运行成本上，若只留 KEYS_ONLY 的列举索引，每趟要强一致读回全部非终态 run 的整个 STATE；协议上，多一个 revision 级的确认标记，回收多等一趟；余量取决于 T，T 取小了随之变小。比较见上「取舍依据」与 [0030](./0030-realtime-persistence-seam.md) 决定六被拒③。
- **清理不做就绪检查，靠「`Query` 失败即不删」保证安全**：依赖的是对回填中或已删除的索引做 `Query` 时的报错形态，这一点没有实测；若某种情形下返回的是不完整的结果，引用检查会判成「未被引用」。失败还被吞进不打印的回收结果，使用者看不到这次没有回收。
- **对每个候选 revision 逐个 `Query` 并以 `contains` 过滤**（曾采用，已取消）：过滤在读取之后应用，每个候选都要把整个非终态分区读一遍，读量随候选数成倍增长；改为每趟一次快照、在内存里求并集。

## 重议闸门

- 免容器引擎的基础镜像同步（registry 到 registry 直拷）→ deploy 机器不再需要 docker，零 step 团队零容器工具链；podman 等其它容器引擎经同一口子接入。
- `delete-worker` 落地：套退休 tag + 静默期 + 运行中 run 引用检查；顺带清旧版本 variant 的 ECR tag / untagged 层与 SSM 映射（届时才定 ECR 回收策略）。
- ARM64 / Graviton 省钱需求成真 → 多架构基础镜像 + 按 ZoneId 排除不支持的 AZ + variant 架构属性，方案已知、依赖侧静态核查已过；届时再评估复杂度是否值。
- 出现「一个 run 内不同引擎用不同 variant」的真实需求 → `--worker-variant` 扩成 `engine=name` 形式，是加法。
- Node 端 `module.registerHooks()` / 其它与镜像无关的 worker 运行时演进归 [0037](./0037-distribution-and-packaging.md)。
