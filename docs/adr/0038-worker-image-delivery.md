# 0038. worker 镜像交付：基础镜像、variant 与推送注册

> **Status:** Accepted（2026-09-09）—— runs 表 GSI（现为状态分组索引，[0030](./0030-realtime-persistence-seam.md) 决定六）；曾有的默认指针兼容路径已随 [0037](./0037-distribution-and-packaging.md) 决策 7 撤除。[0033](./0033-iac-aws-backend-and-composition-wiring.md) 的镜像/task-def/ECR/权限表述已加历史注与权限登记。这一篇描述的设计有一部分尚未实装，code 跟上之前，实际行为以 code 为准。

## 背景与问题

[0037](./0037-distribution-and-packaging.md) 决策 5 定了 worker 镜像**两层分工**：发布方按版本发基础镜像到 GHCR，使用方在本地叠自己的确定性 step 构建定制镜像。本 ADR 定**最后一层怎么交付到云端后端并被 run 使用**。

**施工前**：每个引擎一个镜像；部署方用 `tools/build_push_workers.py` 从整个 repo 构建、推自己私有 ECR 的 `{prefix}{engine}-worker:latest`；task-def 由 IaC 建、镜像栏焊死 `tag="latest"`；RunTask 只传 task-def 的 **family 名**（ECS 取该 family 最新 ACTIVE revision）；CLI 完全不知道也不能选跑哪个镜像；「更新 steps」= 改 repo 里的脚手架文件、整体重建、重推 `latest`，下次起 task 自然拉到。使用方 build 时必须带 `--platform linux/amd64`，漏给的后果是 Fargate **启动期** `exec format error`（[0033](./0033-iac-aws-backend-and-composition-wiring.md) 记的坑）。

**要解的问题**：
- **多套 step 集并存**：不同测试开发 / 分支在同一个共享后端上各跑各的确定性 step 集而互不覆盖；跑时可选。单 tag cover 不了。
- **版本噩梦**：同一个 tag 名在不同人嘴里指不同内容。要让「用的是哪份」可见、可查、run 内一致。
- **所有权**：改共享后端用的镜像是一次部署变更，应归部署方；镜像**构建**是测试开发自己的容器工作，gherkai 不该拥有。默认画像 = 一人兼测试开发与部署方两顶帽子（同一台机器 build 完就推）；团队拆角色时权限边界要现成（角色模型与「帽子不是人」的一般化见 [0040](./0040-consumer-role-model-and-terminology.md)）。
- **架构错误提前暴露**：`--platform` 漏给的错误不该拖到 Fargate 启动期才炸，应在推送前 fail-loud。**不支持 ARM64**（被拒方案，理由见下）。

**AWS 事实（决定形状，均已对照官方文档）**：RunTask 的容器 override 字段全集是 command / environment / environmentFiles / cpu / memory / memoryReservation / resourceRequirements / name，**不能换镜像**；镜像与 `runtimePlatform` 都写在 task-def **revision** 里，revision 是不可变快照、无继承；RunTask 可传 `family`（最新 ACTIVE）或 `family:N`（精确）；task-def 镜像栏支持 `repo@sha256:<digest>`；`DeregisterTaskDefinition` 把 revision 置 INACTIVE——**不影响在跑的 task，但不能再用它起新 task，且注销后最多 10 分钟内这条限制可能尚未生效**；`DeleteTaskDefinitions` 永久删除 INACTIVE revision（有关联 task 时先 DELETE_IN_PROGRESS）；task-def 类 IAM 动作（Register / List / Describe）**不支持资源级权限，只能 `Resource: "*"`**；ECR 仓库 tag 可变性默认 MUTABLE；Fargate ARM64 的不可用面**按 AZ**（官方明列 us-east-1 的 `use1-az3`）。

## 概念模型

| 概念 | 定义 | 载体 |
|---|---|---|
| **基础镜像** | 由发布链发布的镜像 `ghcr.io/zhiyanliu/gherkai-worker-<engine>:X.Y.Z`，linux/amd64 单架构，零使用方内容，带两个镜像标注（下「镜像标注」段；发布通道见 [0037](./0037-distribution-and-packaging.md) 决策 5） | GHCR |
| **variant** | 一套具名的确定性 step 集 = 一个定制镜像；名字由测试开发自取（`login`、`checkout-v2`），只表示装了哪一套 step，不带发行版本，也不带 worker 协议版本；基础镜像同步进 ECR 的那份固定叫 `base` | 使用方私有 ECR，ECR 里的 tag 即 variant 名 |
| **镜像标注** | 构建基础镜像时写进镜像元数据的两个键值：镜像里 worker 的 worker 协议版本与能力（含 worker 所属的引擎）；定制镜像经 FROM 继承（下「镜像标注」段） | 镜像配置里的 labels |
| **对应关系记录**（下文也称映射） | 每个（引擎，variant）一条，记这个 variant 在这个引擎上的当前镜像：模板 revision ARN、revision ARN、digest、推送时刻、镜像的 worker 协议版本与能力（结构与读写见「SSM 参数与命名真源」节） | SSM `worker-variant/<engine>/<variant>` |
| **默认指针** | 提交时不给 `--worker-variant` 就用哪个 variant；部署级一个；deploy 初始化为 `base` | SSM |
| **revision** | 每个（引擎，variant）一个当前 task-def revision（新注册的 revision 只被发起注册的那条对应关系记录引用，见「`push-worker` 流程」步 5）：从模板复制、镜像栏换成 `repo@sha256:<digest>`、以 tags 记血缘与退休时刻 | ECS task-def family `{prefix}{engine}-worker` |
| **模板 revision**（revision 的母本） | deploy 时 CDK 建出的那个 revision，承载 cpu / memory / task role / execution role / 日志组 / `runtimePlatform`（X86_64）等只有部署后才存在或全局固定的值；**镜像栏保留 `tag="latest"` 作占位**（CDK 必填；该 tag 在 ECR 里可以不存在）——它**永不被 RunTask**、只作复制母本；definition 缺字段按定义违约标 error、不回落（见「运行时与 preflight」节「读侧不留兼容路径」） | ECS；其 ARN 由 stack 资源写进 SSM |
| **架构** | 固定 linux/amd64；push-worker 推送前按本机 `inspect` 校验，不匹配退 2（「`push-worker` 流程」步 2） | 模板 revision 的 `runtimePlatform`，variant revision 原样复制 |

**variant 名校验 = 单一真源、同时是单一校验点**：variant 名就是 ECR 里的 tag，`gherkai_runtime.names` 里的 variant 名校验按 docker/ECR tag 的字符集与长度 `[A-Za-z0-9_][A-Za-z0-9_.-]{0,127}` 核对，并拒绝 `latest`（模板 revision 的镜像栏用 `<repo>:latest` 作占位，见上表「模板 revision」行，variant 不与占位同名）；推送方、解析方与列出方都调这一处。`push-worker`、`list-workers` 与提交时的 variant 解析都不需要取得发行版本，从源码直接执行的 CLI 也能解析 variant。同处 `names.ecr_repo_name(prefix, engine)`（= `task_def_name`），收拢曾散在 `stack.py` 注释与（已退役的）`tools/build_push_workers.py` 内联副本里的「ECR repo 名复用 task-def family 名」规则。

**镜像标注（构建基础镜像时写入，推送时读出）**：镜像标注是镜像元数据里的键值，与镜像名冒号后面的 tag、AWS 资源上的 tag 是不同的东西。两个标注的键、取值与读法只在本段写全，[0037](./0037-distribution-and-packaging.md) 决策 5 只定构建时的写入并指向这里。基础镜像带两个：

- `gherkai.worker-protocol-version`：镜像里 worker 的 worker 协议版本，十进制正整数，构建时取自 core 的常量（数据版本的判据与常量见 [0037](./0037-distribution-and-packaging.md) 决策 7）。这个标注的键名、取值形态与含义属跨版本不变的约定（0037 决策 7「跨版本不变的约定」约定六）：各版本靠它读出镜像的协议版本。键名以产品名开头，不与基础镜像上游的标注相撞，也不随仓库托管的位置变。
- `gherkai.worker-capabilities`：一个 JSON 对象，现有三个键——`engine`，必有，取值同能力自述里的 `engine`，即镜像里 worker 所属的引擎（[0036](./0036-deterministic-capability-discovery.md) 决策 5 的身份位）；`targets`，必有，取值同能力自述里的 `targets`（[0049](./0049-worker-capabilities-targets-keys.md) 决策 1、2）；`session_warmup`，可省，布尔，同能力自述里的会话预热支持键（0049 决策 1）。只放构建时就确定、不随执行环境变化的键：随环境变量变化的（停止宽限下限、所用模型）与随定制层变化的（确定性 step 清单）都不放，否则记下的是构建那一刻的缺省值，与云端实际执行时的值不同，成为第二份事实源。其中的键归 worker 协议版本管（0037 决策 7「三个号各管什么」），守同篇「加号的纪律」，与能力自述是同一约定：必有键缺席即不合约定；新增一个可省的键不加号，读的一方遇到缺席的可省键读作不支持；给 `targets` 的取值集合加值要加号（同篇第 6 问）。

**用途**：两个标注在推送之前从将要推送的那一份镜像读出（下「读出」一段）、记进对应关系记录。提交时拿记录里的协议版本与后端的比较（命令行工具自己的协议版本同样要与后端的相同，它才解读得了记录里的能力对象，见下「读出」一段与 [0037](./0037-distribution-and-packaging.md) 决策 7「各入口比什么」）；能力标注让云端提交时与本机执行之前做同一种判断：判断只看一份能力对象，本机取自 worker 的能力自述，云端取自对应关系记录（「运行时与 preflight」节能力一项；被拒方案「云端提交时不核对镜像的能力，由 worker 建会话之前自检」条）。两边的能力对象进入判断之前都经命令行工具里同一处契约校验（[0036](./0036-deterministic-capability-discovery.md) 决策 5）：本机校验 worker 的能力自述，两个身份位是自述里的 `engine` 与 `schema_version`；云端在提交时、解读之前校验记录里的能力对象，两个身份位是能力对象里的 `engine`（须是这条记录所在的引擎）与记录里的协议版本（须与后端的相同，后端的又与命令行工具的相同）。推送时的校验只为提前拒绝（下「读出」）。缺 `targets` 两边都按不合约定处理。

写入归发布一侧（[0037](./0037-distribution-and-packaging.md) 决策 5「两个镜像标注」条）：构建基础镜像时以构建参数写入，构建里的冒烟核对它们与 worker 的能力自述一致。定制镜像经 FROM 继承两个标注；自定义层换了 worker 包、使标注与实际的 worker 不符时，由 worker 一侧兜底：建会话之前核 job 行的协议版本与目标，不合即逐个 job 记 `precheck_failed`、不建会话（[0049](./0049-worker-capabilities-targets-keys.md) 决策 7）；会话预热一侧见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「能力与拒绝点」。

读出：推送与部署同步基础镜像时，先把本地引用打成目标引用，再对目标引用做本机 `inspect`，在核对存在与架构的同一次读出两个标注（多平台索引取 linux/amd64 那一份的视图），都在推送与任何 ECS 调用之前（「`push-worker` 流程」步 2）。记进对应关系记录的协议版本与能力取自这一次读到的；digest 不取自本机 `inspect`，取自推送输出（同一流程步 4；被拒方案「digest 取自本机 `inspect`」条）。不执行镜像（被拒方案「推送与部署同步时执行镜像、问它的能力自述取协议版本与能力」条）。

能力对象的格式归 worker 协议版本，所以解读它（含校验其中的取值）的前提是解读方的 worker 协议版本与镜像标注的相同：持别的值的一方不认识它的取值集合，例如新协议给 `targets` 加了取值，旧的命令行工具按自己的集合校验就会拒绝一份合法的镜像。推送要求命令行工具、镜像与后端三者的 worker 协议版本相同（「命令族」节「`push-worker` 与 `list-workers` 的前置」；比什么写全在 [0037](./0037-distribution-and-packaging.md) 决策 7「各入口比什么」），所以推送时能力标注总由与它协议版本相同的命令行工具解读。协议版本相同还不保证双方认识同一组键：同一协议版本下新增可省的键不加号（上「`gherkai.worker-capabilities`」一项），各发行版本认识的键可以不同，推送方只核得了自己认识的键，记录里存下的是能力标注里那个对象的原样。因此推送时的校验只为提前拒绝；解读对应关系记录里能力对象的一方——云端提交（「运行时与 preflight」节能力一项）、`list-workers`（「命令族」节）与 `doctor --backend cloud` 的逐引擎一行（[0037](./0037-distribution-and-packaging.md) 决策 7「各入口比什么」的 `doctor` 一段）——在解读之前按自己的契约再校验一次，用的是本机读能力自述时的同一处校验（[0036](./0036-deterministic-capability-discovery.md) 决策 5）。推送时按下面的规则依次校验，任一项不合即结束。协议版本标注的三项排在能力标注各项之前：协议版本标注的名字属跨版本不变的约定（约定六），能力标注的名字不在约定之内、新协议可以改，协议版本不同的一方可能读不到能力标注，这时报的应是协议版本不同，而不是缺能力标注。
- 协议版本标注缺失；
- 协议版本标注不是十进制正整数；
- 协议版本标注与执行推送（含部署的基础镜像同步）的命令行工具的不同；
- 能力标注缺失：与协议版本标注缺失同样处理。1.5 起的基础镜像两个标注都有，定制镜像经 FROM 继承它们，自定义层只能改写、去不掉，所以不为缺能力标注的镜像设缺省；
- 能力标注不是 JSON 对象，缺必有键 `engine` 或 `targets`，`engine` 与推送给的引擎（`push-worker` 的 `--engine`；部署同步时是所同步的那个引擎）不同，或其中已知键的取值不合能力自述的同名约定。这一项与本机读到能力自述时的契约校验（[0036](./0036-deterministic-capability-discovery.md) 决策 5）是同一约定：自述的两个身份位在这里由 `engine` 与协议版本标注承担，载荷键按同名键的形态核。推送时不核这几项，操作者把 `--engine` 给错时，别的引擎的镜像就登记进这个引擎、替换掉这个 variant 原来的镜像，要到提交时解读之前的那次校验才被拒（本机执行之前的同一种错配由自述的身份位拒绝）；照原样记下形态不对的对象，问题同样要到那时才暴露。

结束时 `push-worker` 以退出码 2 结束、没有推送；`gherkai deploy` 的基础镜像同步不合时的退出码、是否继续部署，见「`gherkai deploy` 的 worker 镜像四步」第 2 步。说明只陈述事实：哪个标注缺失或不合约定；协议版本标注缺失时说这个镜像的元数据里没有它、读不出镜像的 worker 协议版本，gherkai 发布的基础镜像带这个标注，以它为 FROM 构建的镜像会继承；能力标注里的引擎与推送给的不同时陈述两边的值（「镜像 acme-midscene:login 的能力标注写的引擎是 midscene，这次推送给的是 novaact。没有推送这个镜像。」；不是数据版本不合，不加固定话）；协议版本不同时陈述三方的值，末尾加固定话（形态见 0037 决策 7「说明的要点」）。记进对应关系记录的形态见「SSM 参数与命名真源」节「对应关系记录的读写」段。

**tag 可变，replace 与否交给使用方**：重推同名 variant 直接放行、只在推送后打印「原 digest → 新 digest」。不设不可变仓库——bugfix 不想改 variant 名是正当需求，机制给到、用错不算产品欠缺。run 内一致性不靠 tag 靠 revision（下）。**护栏**：这条正确性依赖 ECR 保留被顶掉 tag 的 untagged 镜像（运行中 run 的旧 revision 按 digest 指着它），故 ECR 仓库**不设 untagged 过期的 lifecycle 规则**；代价是每次重推永久留一层 untagged 存储、随重推次数增长——记为已知运行期成本，回收与 `delete-worker` 同批设计（重议闸门）。

**定制镜像模板（唯一真源，[0037](./0037-distribution-and-packaging.md) 只指向此处）**：测试开发自己 build，任何本地名字，gherkai 不拥有构建；**必须 `--platform linux/amd64`**（arm Mac 上尤其）；FROM 行缺省写后端记下的那个发行版本的基础镜像（`gherkai doctor` 与 `gherkai deploy list-workers` 显示它），那一份的 worker 协议版本通常与后端相同，不保证：例如部署进行中版本戳先于数据版本参数更新，两者有一段不一致；后端记下的是非纯发行版本时 GHCR 上没有这一份；「PyPI 已发、镜像缺失」的半发布态里这个版本的基础镜像还没有发出（0037 决策 8）。真正的要求是镜像的 worker 协议版本与后端相同（发行版本在这里只是取哪一份的缺省，[0037](./0037-distribution-and-packaging.md) 决策 7），推送时由「`push-worker` 流程」步 1 与步 2 核对。两个镜像标注经 FROM 继承，自定义层不要改写它们：

```dockerfile
FROM ghcr.io/zhiyanliu/gherkai-worker-novaact:<后端记下的发行版本>
COPY steps/ /app/steps
ENV GHERKAI_STEPS_DIR=/app/steps
```

```
docker build --platform linux/amd64 -t acme-novaact:login .
```

## 命令族（全在 `gherkai-deploy-aws`，云端写操作归部署方）

- **`gherkai deploy push-worker <本地镜像> --engine <novaact|midscene> --variant <名> [--set-default]`**：推送一个本地镜像并注册为该引擎的一个 variant。一次一个引擎，两个引擎跑两次（两引擎镜像本就分别 build）。
- **`gherkai deploy list-workers`**：按 family 列 revision 并读 tags 与 SSM，输出各引擎的全部 variant，每个（引擎，variant）一行：variant、是否默认、digest、推送时刻、镜像的 worker 协议版本（与后端不同时标出）与能力（支持的目标、是否支持会话预热）、revision；记录里的协议版本与执行它的命令行工具的不同时，这一行的能力各列不解读、显示 `-`（解读能力对象的前提见「镜像标注」段的「读出」一段）：推送要求三者的协议版本相同，这样的行仍会出现，例如后端升级之前推送、还没有重推的 variant，或者执行 `list-workers` 的命令行工具自己与后端不同（它不比这一项，下「前置」条）；协议版本相同时，解读之前按命令行工具自己的契约校验记录里的能力对象（同一段），不合约定时这一行的能力各列同样不解读、显示 `-`；`--json` 照样原样带出记录里的能力对象与协议版本，不解读也不校验；表头写后端的 worker 协议版本与后端记下的发行版本（版本戳另读一次，[0037](./0037-distribution-and-packaging.md) 决策 7）；之后是已退休待清理与孤儿 revision。`--json` 出机读形态，键集与 stdout/stderr 分流见 [0041](./0041-agent-facing-cli-affordances.md) 决策三；表头里后端记下的发行版本只在文本形态里，`--json` 不带；顶层也不带 `version`（1.4 的形态带着它，删去是对已发行形态的非加法改动，列进 1.4 到 1.5 的升级须知，[0037](./0037-distribution-and-packaging.md) 决策 7「1.4 到 1.5」）。**待清理条目**（随「不变量」清理 pass 条把静默期起点归一到 `gherkai:retired-at`）：只列不在任何对应关系记录里、带血缘 tags 的 ACTIVE revision，判据与清理 pass 的候选判据是同一份（全部对应关系记录所引用的 revision ARN 集合）。`reason` 仍是 `retired` / `orphan` 闭集：带 `gherkai:retired-at` 的为 `retired`，`retired_at` 即静默期的起点，替换映射时打上的与清理 pass 补打的不再区分；还没有这个 tag 的为 `orphan`（`retired_at` 为 null），之后的清理 pass 在满足补打条件时（注册时刻早于那一趟开始读映射的时刻）给它补打，此后列为 `retired`。文本形态：`retired` 行写「已退休 <时刻>」，`orphan` 行写「孤儿：没有任何对应关系记录引用」。仍在某个映射里的 revision 不列为待清理，即使它带着 `retired-at`：那是之后的清理 pass 会摘掉的 tag，它是在用的 revision。曾有的布尔字段 `still_mapped` 与对应文本已删除（被拒方案「在 `list-workers` 里把『已退休、仍被映射引用』单独标出」条）；它没有随任何发行版发出，删去它不破坏已发布的契约（0041 决策五的加法兼容）。字段登记在 `--json` 字段契约页，由 0041 决策五的护栏对照真实输出核对。
- **`gherkai deploy delete-worker`**：留口子，落地时套同一套清理 pass 语义（退休 tag + 静默期 + 运行中 run 引用检查，见「不变量」；静默期一律从 `gherkai:retired-at` 起算、缺这个 tag 的由清理 pass 补打；引用检查读状态分组索引的 `live` 分组，同见该条）。
- **`gherkai deploy` 的 worker 镜像四步**：登记模板（随 cdk 事务）、同步基础镜像为 `base`、初始化默认指针、重派生既有 variant（后三步在 cdk 之后；协议版本要变时同步的两个前提在 cdk 之前核，见该节第 2 步）。
- **`push-worker` 与 `list-workers` 的前置**：开头先读数据版本参数，比云端后端接口版本（[0037](./0037-distribution-and-packaging.md) 决策 7）：不同、或后端没有记下或记下的内容读不懂，即以退出码 2 结束，另读一次版本戳放进说明（0037 决策 7「版本戳另读」），不读写其余云端资源；读取本身失败以退出码 2 结束、说明点名这个参数。`push-worker` 接着用同一次读到的值比命令行工具自己的 worker 协议版本，不同同样以退出码 2 结束、不读写其余云端资源；镜像一侧在「`push-worker` 流程」步 2 比，三者相同才推送与登记（各入口比什么写全在 0037 决策 7「各入口比什么」；不同时为什么不只打印提醒、照常推送，见被拒方案「推送时协议版本不同不拦、只打印提醒」条）。`list-workers` 不比命令行工具自己的协议版本，同一次读取取得的后端协议版本只用作列出时的标注。两条命令不以取得本机的发行版本为前提（取不到时照常执行）。**`gherkai deploy` 的四步不做这一前置**：cdk 之前有 deploy 自己的数据版本检查（0037 决策 7），协议版本要变时同步基础镜像的前提核对排在它之后（第 2 步）；后三步走推送路径，开头读一次数据版本参数，与本次部署的三个常量比，比不上按「四步的失败语义」以退出码 1 结束，后三步都不做。
- **定制镜像的构建不在命令族里**：模板见上。

## `push-worker` 流程

1. **解析目标**：ECR repo = `names.ecr_repo_name(prefix, engine)`、tag = variant 名（经「概念模型」节下的 variant 名校验）、对应关系记录的键 = `worker-variant/<engine>/<variant>`；region/prefix 与 `gherkai deploy` 同一解析链；读后端的数据版本参数，比云端后端接口版本与命令行工具自己的 worker 协议版本，不同以退出码 2 结束（上「`push-worker` 与 `list-workers` 的前置」；deploy 的基础镜像同步不做这一比对，由 deploy 自己的数据版本检查与后三步开头的比对承担，同节末句）。
2. **打成目标引用、对它做本机 `inspect`**：先取仓库的地址（boto3 `ecr:GetAuthorizationToken`，只读、不改动账户；步 3 的登录用同一次的结果），引擎把本地引用 `tag` 成目标引用（仓库加以 variant 名命名的 tag），再对**目标引用** `inspect`，同一次读出两个镜像标注（「概念模型」节下「镜像标注」段），依次核对：存在；架构是 linux/amd64；协议版本标注在、是正整数且与命令行工具的相同；能力标注在、是 JSON 对象，必有键 `engine`（与 `--engine` 相同）与 `targets` 都在，已知键的取值合约定（与本机读能力自述同一处契约校验；规则、次序的理由与说明写全在同段「读出」）。随后按步 7 将要写出的形态算出对应关系记录的大小（这时还没有的 digest、revision ARN 与推送时刻按各自形态的最大长度计），超过 SSM 标准参数的上限（4 KB）即拒绝：过大的记录会让写记录那一步在 revision 注册之后才失败。打好 tag 之后才读，是因为目标引用此后不随本地源名字的改动而变：读到的就是将要推送的那一份（被拒方案「读本地引用的标注、再按名字打 tag 与推送」条；同一台机器上另一条推送同时改指同一个目标引用的情形见「与版本升级的交互」节「并发与失败」）。架构不对时提示 `docker build --platform linux/amd64`——把 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 记的启动期 `exec format error` 提前到推送前。任一不过 → 退 2；deploy 的基础镜像同步经同一条流程，这几项不合时的处置见「`gherkai deploy` 的 worker 镜像四步」第 2 步。这几项校验都在**推送与任何 ECS 调用之前**（先于它们的远程调用只有步 1 的几次 SSM 点读——数据版本参数与本引擎模板 revision ARN——和取仓库地址的那一次，都不改动账户）。这一步读到的协议版本与能力就是步 7 记下的；这一步不取 digest：推送之前本机给出的值不证明仓库里有这份内容（被拒方案「digest 取自本机 `inspect`」条），digest 取自步 4 的推送输出。**本地引用是多平台索引时**（containerd 镜像存储——Docker 29 起新装的缺省、GitHub 托管 runner 亦然；打成的目标引用同样是这个索引）：`inspect` 顶层给的是本机平台那一份的视图——本机平台的内容不在时（amd64 主机只拉了 arm64；arm 主机上按文档只构建 linux/amd64）`Os` / `Architecture` 是空串、`Descriptor` 是 index，此时再问一次目标平台的视图（`inspect --platform linux/amd64`）——本机有 linux/amd64 的内容才算匹配，两个标注也从这一视图读出；索引列了该平台却没拉取内容（视图两字段仍为空）或根本不含该平台（引擎报「找到了镜像但没有这个平台」）都拒，提示只构建 linux/amd64 一个平台。旧的 overlay2 存储装不下索引、`inspect` 恒给单平台视图：arm Mac 上得到 arm64、被拒（实测项 7）。
3. **读原 digest、ECR 登录**：推送之前按目标 tag 调 `ecr:DescribeImages`，读出这个 tag 现在指向的 digest，供步 4 打印「原 digest → 新 digest」（tag 从未推过或仓库里还没有它时没有原 digest）；引擎用步 2 取得的登录凭据 `login`。
4. **推送、取 digest**：引擎 `push` 目标引用；`push` 以非零退出码失败即报错，走不到取 digest。**digest 的唯一来源是推送输出**：容器引擎在推送成功之后报出的那个摘要，docker 是推送结果那一行（输出的最后一行，形如 `<tag>: digest: sha256:<64 位十六进制> size: <字节数>`）里的摘要。只认这种形态的行；取不到（没有这样的一行，或不止一行）即按推送失败结束，不注册 revision、不写对应关系记录，说明写明没有从推送输出里取到这次推上去的镜像的摘要。依据（实测项 13）：推送输出里的摘要在单平台镜像与「多平台索引、本机只有 linux/amd64 一份内容」两种情形下都等于仓库对这个 tag 给出的摘要；本机 `inspect` 的 `RepoDigests` 在后一种情形下报的是索引的摘要，仓库里没有它；照它登记，用这个 variant 的云端提交在提交前的存在性核对里被拒（「运行时与 preflight」节），重推仍登记同一个摘要。步 6 注册的 revision 引用这个 digest，步 7 记下它。目标 tag 原已存在、步 3 读到的原 digest 与新的不同时，此时打印「原 digest → 新 digest」。
5. **查重**：SSM 现映射的（模板 revision ARN、digest）二元组与本次（digest 取自步 4）一致、且映射指向的 revision 仍为 ACTIVE → 跳过注册（digest 相同就是同一个镜像，两个标注也相同，记录里的协议版本与能力仍然成立），沿用映射记录的 revision，并在确认之后对它无条件摘除一次 `gherkai:retired-at`（这个分支不经过步 7 的写映射，此前某次交错留下的 tag 不该等到命令末尾的清理 pass 才摘，命令在末尾之前失败时就摘不掉）。除此以外一律往下新注册一个 revision（步 6），在步 7 写映射替换：二元组不一致、映射缺失或读不懂（读不懂的判据见「SSM 参数与命名真源」节「对应关系记录的读写」段），或未能确认映射指向的 revision 仍为 ACTIVE（按映射缺失处理，见「不变量」清理 pass 条「注册与回收的竞争」段）。映射存在时，所指 revision 是否仍为 ACTIVE 在这一步确认（判据同「运行时与 preflight」节「缺失的判定口径」），二元组不一致的分支也据此决定步 8 是否给它打 tag：未确认仍为 ACTIVE 的不打。不在 family 里找未被映射、同二元组的 revision 复用（被拒方案「孤儿复用」条）。中断在步 6 与步 7 之间时，重新执行会再注册一个，上次注册的那个从未被映射引用，由清理 pass 在静默期之后回收（ECR 镜像层共享，只多一条 task-def）。deploy 第 4 步的重派生同样不复用。于是每个新注册的 revision 只被发起注册的那一条映射引用，被替换即离开它唯一的那条映射，退休与清理按（引擎，variant）判。
6. **注册 revision**：`DescribeTaskDefinition`（模板，`include=["TAGS"]`）→ 剔除只读字段（`taskDefinitionArn` / `revision` / `status` / `requiresAttributes` / `compatibilities` / `registeredAt` / `registeredBy`）→ 镜像栏改 `repo@sha256:<digest>`，其余（含 `runtimePlatform`）原样 → `RegisterTaskDefinition`，**tags 记血缘**：`gherkai:variant`、`gherkai:version`（执行这次推送的 gherkai 的发行版本，只作事实，取不到记 `unknown`）、`gherkai:digest`、`gherkai:template`（模板 ARN）。注册之后、步 7 写映射之前，对新注册的 revision 再 `DescribeTaskDefinition`（`include=["TAGS"]`）一次，仍为 ACTIVE 且不带 `gherkai:retired-at` 才往下写映射；否则（含描述返回 `ClientException` 且本次 ACTIVE 列举未发现它，判据同「缺失的判定口径」，这不证明它已被注销或删除；其余读失败原样抛出）重新注册一个、同样再读，至多重新注册一次，第二次仍不满足时命令失败并提示稍后重新执行。不满足的情形包括进程于两步之间停留超过静默期、恰有一趟清理 pass 在注册之后读映射并给它补打，以及刚注册的 revision 尚未在查询结果中可见；后者会额外注册一个 revision，连续两次都未可见时命令失败。被补打或额外注册的那个从未被映射引用，满静默期后照常回收，只多一条 task-def。这次再读看到的只是那一刻的状态，不证明没有一趟清理已把它收为成熟候选（另一趟清理可能已摘掉自己补打的 tag），也不证明再读与写映射之间没有清理改动它，见「不变量」清理 pass 条「注册与回收的竞争」段与残余风险的总括。
7. **写 SSM**：`worker-variant/<engine>/<variant>` = JSON（模板 revision ARN、revision ARN、digest、推送时刻，以及步 2 从标注读出的 `worker_protocol_version` 与 `capabilities`；整条换新）；写成功之后立即对写进映射的 revision 无条件摘除 `gherkai:retired-at`（`UntagResource`，不先读它带不带这个 tag；对不带这个 tag 的 revision 摘除成功返回、不改变它（ECS 文档没有写明，真实账户上核过，实测项 11）；失败只警告，留给之后的清理 pass；理由见「不变量」清理 pass 条「打 tag 与写映射的交错」段）；`--set-default` 时在步 8 的退休之后写默认指针（次序见步 8 末），若没有读到该 variant 在其它引擎上的有效登记则**警告不拦**（只陈述读到的：「没有读到 variant `X` 在 midscene 上的有效登记」；不拦的理由：提交时按本 run 用到的引擎判，单引擎团队不必凭空推另一引擎）。
8. **退休被替换的旧 revision**：给它打 tag `gherkai:retired-at=<时刻>`（**不在本次删除**；打不上只警告）；清理 pass（不变量）在写默认指针之后执行（次序见本步末）。未确认仍为 ACTIVE 的旧 revision 不打（步 5 已核对它的状态）。时刻紧邻 `TagResource` 请求之前现读时钟，不用命令开始时取的时刻（「不变量」清理 pass 条「时钟」段）；回收不依赖这一步打上，没打上的由清理 pass 按孤儿补打；清理 pass 照旧不注销仍在任何对应关系记录里的 revision。输出 tag / digest / revision，以及「提交时用 `--worker-variant <名>`」。次序 = 写映射 → 退休旧 revision → 写指针 → 清理（退休与写指针之间无依赖）；`--set-default` 不在与基础镜像同步共享的推送路径上。registry host 的取法见「权限面增量」。

## `gherkai deploy` 的 worker 镜像四步（第 1 步随 cdk 事务，后三步在 cdk 之后；全部幂等）

1. **登记模板**：各引擎 task-def revision 的 ARN 由 **stack 资源**（`ssm.StringParameter`，值取 CDK 内 `taskDefinition.taskDefinitionArn`——`AWS::ECS::TaskDefinition` 的 `Ref` 返回带 revision 的 ARN；CDK 更新 task-def 属性即替换出新 revision、参数值随之更新）写进 SSM `worker-template/<engine>`——与 0037 的 `version`/`vpc`/`data-versions` 同理，随部署事务同生死、回滚不留错值，deploy 命令不事后 `put_parameter`。push-worker 永远从它复制，**不抄「最近一次」revision**——那可能是某个 variant 的、且模板改过后已过期。
2. **同步基础镜像**：经容器引擎从 GHCR `pull` 执行这次部署的那个发行版本的基础镜像（发行版本在这里是取哪一份的缺省，[0037](./0037-distribution-and-packaging.md) 决策 7），走 push-worker 同一条内部流程推成 variant `base`（ECR 里的 tag 即 `base`）：推送之前在目标引用上读出两个镜像标注并校验（同 push-worker 步 2；能力标注里的 `engine` 须是所同步的引擎），digest 取自推送输出（同步 4），记进对应关系记录，注册 revision。每次同步覆盖同一条 `base` 记录，被换下的 revision 照常退休；在执行的 run 按 digest 钉住，不受影响。零 step 的团队在同步成功之后即可提交，不碰 docker build。**非纯发行版本（`.dev`/`.post`/本地段）或取不到发行版本（如直接从源码执行，0037 决策 6「版本戳」条）时跳过本步**并打明确警告，`base` 停在原来的镜像——那些版本由 tag 之后的 commit 派生或根本没有版本号、GHCR 上不可能有对应基础镜像（0037 决策 2b）；contributor 在 dev 树上部署是正常用法，硬失败只会逼人绕过命令手工推。第 3/4 步照常（默认指针仍初始化为 `base`；dev 版要能用：本地 build 后 `push-worker … --variant base`）。容器引擎也只在本步探活——跳过本步时不探，没装 docker 的机器上第 3/4 步照样收敛。**协议版本要变时，两个前提在 cdk 之前核**：这次部署会改变一个已有后端的 worker 协议版本（stack 已在；要变与否按 0037 决策 7「`deploy` 入口的检查」的比较，后端没有记下或读不懂也算要变，同那里）、并且会做本步（纯发行版本）时，在 deploy 自己的数据版本检查放行之后（照常部署或带了旗标）、找回或建立 Device Farm 项目与调用 cdk 之前，核两项不改动账户的前提：容器引擎可用；两个引擎的基础镜像拉得到——就在这时拉下来，并按 push-worker 步 2 的规则校验它们的两个标注。任一不成以退出码 2 结束、不改动账户（不建立 Device Farm 项目、不调用 cdk），`--allow-data-version-change` 不放行，说明陈述事实。理由：cdk 把后端的协议版本改成新值之后，记录里还是旧协议镜像的 variant 都不能提交（通常是 `base` 与全部自定义 variant）；这两项在 cdk 之前核得出、核时不改动账户，不成时后端的协议版本不变，各 variant 能不能用与部署之前相同。推送本身留在 cdk 之后（被拒方案「推送提到 cdk 之前」条）。协议版本不变或首次部署时不做这项核对：容器引擎不可用在 cdk 之前只警告（「容器引擎口子」节），本步在 cdk 之后失败按「四步的失败语义」以退出码 1 结束。`gherkai deploy --diff` 不部署、不同步基础镜像，也不做这项核对（它输出什么见 0037 决策 7「`deploy` 入口的检查」里「`deploy --diff`」一项）。**已知边界**：同步在 cdk 之后，协议版本要变的部署里，数据版本参数更新之后，记录里还是旧协议镜像的 variant，用它的云端提交因 variant 的协议版本与后端不同被拒（「与版本升级的交互」节）。`base` 的记录由本步的同步换成新协议的镜像，持新值的命令行工具在参数更新之后推送也换得掉它，部署之前推不进（推送要求三者的协议版本相同，「命令族」节「`push-worker` 与 `list-workers` 的前置」）；记录是哪一份镜像看最后写成的那一笔（「不变量」节「并发写者」条）。协议版本要变时，本步在 cdk 之后仍可能因两个前提之外的原因失败（例如 ECR 登录或凭证存储失败、出网放行 GHCR 却挡住 ECR、缺推送的权限）：以退出码 1 结束并说明原因（「四步的失败语义」），原因排除之后重新执行 `deploy`。
3. **初始化默认指针**：缺失 → `base`；存在 → **不动**（升级不重置，见「与版本升级的交互」）。
4. **重派生 + 清理**：对全部对应关系记录（读不懂的不改写：提交时它按这个引擎没有可用的镜像处理，重新推送这个 variant 即整条换新，见「SSM 参数与命名真源」节「对应关系记录的读写」段），记录的模板 ARN 与新模板一致、且映射指向的 revision 仍为 ACTIVE → 跳过，并在确认 ACTIVE 之后对它无条件摘除一次 `gherkai:retired-at`（同 push-worker 步 5：ACTIVE 的判定、读失败的口径与跳过分支的摘除都同那里）。否则——模板 ARN ≠ 新模板，或未能确认映射指向的 revision 仍为 ACTIVE（按映射缺失处理，同步 5）——用新模板 + 映射里记录的 digest 新注册一个 revision（血缘 tags 同上；不在 family 里匹配已有的 revision，同 push-worker 步 5；写映射之前的再读同步 6）、更新映射（写成功之后同步 7 立即摘除新 revision 上的 `gherkai:retired-at`）、旧 revision 打 `gherkai:retired-at`（时刻同步 8 现读时钟；未确认仍为 ACTIVE 的旧 revision 不打，模板变了的分支同样先确认，同「不变量」清理 pass 条「注册与回收的竞争」段其三）。重派生中断在注册与写映射之间时，映射仍指向本次准备替换的原 revision，重新执行会再注册一批；前一批从未被映射引用，由清理 pass 在静默期之后回收。原因：revision 是不可变快照、无继承，deploy 调了 cpu 后旧 variant 会一直跑旧 cpu 直到有人重推；重派生让所有 variant 与模板同步而镜像一个字节不动。重派生改写记录时先读、再改、再写，**保留原 `pushed_at`**（记的是镜像推上去的时刻）、`worker_protocol_version`、`capabilities`（镜像一个字节不动，标注也不变）与不认识的键（[0037](./0037-distribution-and-packaging.md) 决策 7 写的一方的规则）；repo URI 从模板容器的镜像栏反推（模板即 `<repo-uri>:latest` 占位）——重派生不登录 registry。随后跑一次清理 pass（不变量）。

**四步的失败语义**：cdk 已成功而后三步任一失败 → 退 1，提示陈述 stack 已生效、哪一步没有完成与得到的错误，以及可以重新执行 `gherkai deploy`；不预告重新执行会做到哪一步、结果怎样。后三步开头读到的数据版本与本次部署的三个常量不同时同样退 1、后三步都不做，比的是什么、为什么这样做见 [0037](./0037-distribution-and-packaging.md) 决策 7「`deploy` 入口的检查」末条；基础镜像 pull 失败 → 给出拉取的是哪一份与容器引擎的原话，不断定原因（可能是这个版本的基础镜像还没有发布，即 [0037](./0037-distribution-and-packaging.md) 决策 8 承认的「PyPI 已发、镜像缺失」半发布态，也可能是出网、限流、鉴权，命令分不清）；协议版本要变时 cdk 之前那两项前提不成的处置见第 2 步（退 2、不调用 cdk）。

## 不变量

- **运行时只用 definition 里的显式 revision，永不用 family 取最新**（迁移前的 IaC 曾传 family，理由见下「被拒方案」的『RunTask 传 family』条）。
- **revision 按 digest 引用镜像**，重推同名 variant 产生新 revision、运行中的 run 手里的旧 revision 不受影响；一个 run 内镜像固定。
- **幂等**：push-worker 与 deploy 四步的每一步先查再做，中断后重跑收敛。同一份内容重推到同一个 tag 时 ECR 不重传已有的层，tag 仍指向同一个 digest；`RegisterTaskDefinition` 不幂等，故以二元组查重；中断在注册与写映射之间时，重新执行会再注册一个，上次注册的那个不被任何映射引用，由清理 pass 在静默期之后回收，收敛的是映射与在用的 revision，多出的 revision 只滞留到回收（不复用这类 revision，被拒方案「孤儿复用」条）；ECR 登录令牌 12 小时有效、重跑重登；SSM 写是覆盖语义。
- **并发写者：最后写者赢，孤儿由对账回收**。SSM 无条件写，两人同时 push 同名 variant 会各注册一个 revision、后写者的映射赢；先写者的 revision 不在映射里也没被打退休 tag——**清理 pass 按 family 全量对账**（凡带血缘 tags、ACTIVE、不在任何对应关系记录里的 revision 视作孤儿，与已退休的 revision 同样进入清理候选，清理 pass 看到它不在任何映射里、且它的注册时刻早于那一趟开始读映射的时刻时给它补打 `gherkai:retired-at`、静默期从补打的时刻起算（下条「候选与静默期起点」；不以 `registeredAt` 作起点，见被拒方案「孤儿的静默期从 `registeredAt` 起算」条）），不只看映射。同一 variant 的并发 push 不建议但不禁止。
- **清理 pass = 静默期 + 运行中 run 引用检查，机会式执行、无定时任务**：pass 由 `push-worker` 末步与 `gherkai deploy` 第四步末各跑一次（将来 `delete-worker` 也跑）；列 family 全部 revision 读 tags，对已退休（`gherkai:retired-at`）或对账出的孤儿，只在**退休满 1 小时**（覆盖「提交侧 preflight 刚解析成 R、definition 尚未落库」的窗口与注销后最多 10 分钟的生效延迟）且**无未到终态的 run 引用**时才 `DeregisterTaskDefinition` + `DeleteTaskDefinitions`；有引用或未满静默期 → 留到下次 pass。长期无人 push/deploy 时退休 revision 会滞留，无害（ACTIVE 但无人引用）。「退休满 1 小时」的起点见本条下「候选与静默期起点」段，引用检查的做法见「引用检查」段。引用判定的访问路径定死：run 用到的 revision ARN 在 `create_run` 时**同时写成 STATE item 的顶层属性 `worker_task_def_arns`**（同 [0034](./0034-detached-batch-reconciler.md) 的 `detached` 顶层标记先例），清理经 runs 表的稀疏 GSI（只索引 STATE item）读非终态 run 的这个属性——不扫全表（runs 表 `RETAIN`、无 TTL、随历史单调增长，Scan 成本无上界）。detached run 逐 job 起 task，删早了剩余 job 全部起不来。ECS 侧稳态只留每个（引擎，variant）当前一个 revision。**实装细则**：孤儿判据要枚举全部对应关系记录，枚举失败 → **整趟放弃清理**（当作「没有映射」会把每个在用 revision 都判成孤儿并补打 `gherkai:retired-at`，一小时后的下一趟就会批量回收）；`registeredAt` 只用作补打 `gherkai:retired-at` 的附加条件，取不到时本趟不打，宁滞留不早删（若一直取不到，这个 revision 每一趟都不被补打，一直滞留、永不回收，偏保守。真实 ECS 上不应发生，依据是本模块在真账户上的观察（`list-workers` 输出的就是这个字段，真账户上读得到；一次真实账户会话里 344 次注册的响应与清理、推送读到的 126 个带血缘 tags 的 revision 的描述都带这个字段，实测项 10；moto 不返回这个字段，单测里取不到是模拟层的差异），没有文档保证：ECS API 参考里 `TaskDefinition` 的返回字段（含 `registeredAt`）都标为非必有，观察不构成保证）。
  - **候选与静默期起点**：`gherkai:retired-at` 的含义改为「这个 revision 从何时起不被任何映射引用」，静默期一律从它的值起算。打这个 tag 的有两处：替换映射的那一步（push-worker 步 8 与重派生）给被替换的旧 revision 打，时刻紧邻 `TagResource` 请求之前现读时钟；清理 pass 给缺这个 tag 的孤儿补打。每趟 pass 读完全部对应关系记录（开始读之前记下时刻 t1）之后，对每个带血缘 tags 的 ACTIVE revision：在任一映射里的，不是候选；它若带着 `gherkai:retired-at`，摘掉这个 tag（`UntagResource`，失败留到下一趟）——任何一趟见到「仍在映射里却带着这个 tag」的 revision 都摘。不在任何映射里、还没有这个 tag 的：`registeredAt` 早于 t1 的补打（值为此刻），本趟不作为候选、留下；`registeredAt` 不早于 t1 或取不到的本趟不打，留到下一趟（一直取不到时一直滞留，见上「实装细则」）；打不上同样留下，下一趟再打。不在任何映射里、tag 已满 1 小时的是成熟候选，进入引用检查；未满的留下。**重读**：本趟补打过 tag 或有成熟候选时，在补打与引用检查的快照都完成之后、注销之前重读一次全部对应关系记录，两件事共用这一次读：本趟补打过的 revision 若已在映射里，当场摘掉；成熟候选若已在映射里，不注销、摘掉 tag（理由见下「注册与回收的竞争」段）。重读失败时把本趟补打的 tag 全部摘掉（下一趟重打，回收晚一趟），成熟候选全部留下。「本趟补打过」含 `TagResource` 调用报错的那些：报错（如超时）不说明服务端没有打上，摘一个不存在的 tag 无害。依据：静默期要覆盖的是「preflight 已解析出 R、definition 尚未落库」的窗口，所以起点必须不早于 R 离开最后一个映射的时刻——R 离开之后，新的 preflight 不再解析到它。两处打的值都满足这一点：替换的一步在写映射成功之后现读时钟，值不早于 R 离开被替换的那条映射；补打的那一趟读到的映射里已经没有 R，值不早于这次读取，也就不早于 R 离开映射。每个 revision 只被发起注册的那一条映射引用（下「已退休却仍被映射引用」段），R 离开被替换的那条映射也就不再被任何映射引用，替换的一步打下的值不早于这一刻。命令开始的时刻与 `registeredAt` 都不满足这一点：前者早于写映射（下「时钟」段），后者可能早于它离开映射很久（被拒方案「孤儿的静默期从 `registeredAt` 起算」条）。孤儿与替换时没打上 tag 的 revision 走同一条补打路径，回收不依赖替换的一步打上 tag。摘除对这个 revision 自身的回收只会推迟、不会提前：已被某一趟收为成熟候选的，摘除在那一趟注销之前的最后核对之前可见时，核对读到 tag 已不在，那一趟不注销（下「引用检查」段⑤）；晚于核对的见下例二。依据是取消孤儿复用之后，一个 revision 进入映射只有一条路：发起注册的那条命令把自己刚注册的它写进自己那条映射（步 5、步 6 与重派生）。被摘掉 tag 的 revision 若在映射里，它本来就不该带这个 tag；若不在任何映射里，它不会被别的命令写回映射，只会在之后某一趟被再次补打、从更晚的时刻起算，回收晚一趟。例一：同一 variant 的两条推送并发，一条读到旧映射、走步 5 的跳过分支，另一条随即替换了这条映射并给旧 revision 打 tag，跳过分支确认 ACTIVE 之后的摘除落在打 tag 之后。例二：一趟清理凭它读到的、已过时的映射，摘掉一个此后已离开映射的 revision 的 tag，而另一趟清理已把它收为成熟候选：摘除在那一趟的最后核对之前可见时，那一趟不注销，下一趟重新补打，回收晚一趟；落在最后核对之后时，那一趟照旧注销，它确实不在任何映射里，那次注销本来就满足前置条件。「不会被写回映射」的唯一例外是某条命令刚注册、尚未写映射的那个 revision。摘除与它有关：推送写映射之前的再读以「不带 tag」为放行条件，一趟清理摘掉自己补打的 tag（如重读失败之后），会让推送的再读放行，而另一趟清理可能已凭这个 tag 的旧值把它收为成熟候选；这一交错由注销之前的最后核对关掉，余下的部分在残余风险的总括之内（下「注册与回收的竞争」段与残余风险⑥）。本段与下面各段所说「进入映射只有一条路」，指 1.5 起的命令；1.5 之前的命令行工具不比对数据版本、仍会从 family 里复用孤儿，它们对 1.5 后端的推送不在这些论证之内（升级须知写明不要这样用，[0037](./0037-distribution-and-packaging.md) 决策 7）；它们把映射写在另一个根下（「SSM 参数与命名真源」节「对应关系记录的读写」段），注册的 revision 不在任何对应关系记录里，1.5 的清理按孤儿回收。
  - **打 tag 与写映射的交错**：取消孤儿复用之后，替换的一步（push-worker 步 8 与重派生）只给它从映射里读到、随即被自己替换掉的 revision 打 tag；那个 revision 已离开这条映射、不会被写回（上段末），也不在别的映射里（每个 revision 只被发起注册的那条映射引用，下「已退休却仍被映射引用」段）。所以会让 R 带着一个早于它被映射的 tag 的，只剩清理 pass P 的补打：P 读映射时，另一条 push 或重派生 Q 已注册了 R（步 6）、还没把它写进映射（步 7），P 给它补打，Q 随后把它写进映射。若不摘，R 日后离开映射、而替换的一步没能以新值覆写时，静默期可能早已满。处置有三道：P 打了 tag 之后重读全部对应关系记录，R 已在映射里就当场摘掉（上段「重读」）；Q 写映射成功之后立即对 R 无条件 `UntagResource`（步 7 与重派生写映射处；步 5 跳过分支确认 ACTIVE 之后的摘除是又一道，处置此前任何交错留下的 tag）；Q 末尾的 pass 见到「仍在映射里却带着 tag」再摘一次。论证按读到 Q 所写那个参数的时刻进行：映射枚举是分页读取，每一页在各自的时刻取回，结果不是某一时刻的快照，所以不按读取开始或结束的时刻论证。设 P 的第一次读与重读取回含该参数那一页（参数此前不存在时，指它若存在应在的那一页）的时刻分别为 r1、r3，P 在 t2 打上 tag（r1 < t2 < r3），Q 在 tw 写映射成功、随后在 tu 摘除：tw 早于 r1 时，P 第一次读就看到 R 在映射里，不打；tw 在 r1 与 r3 之间时，重读看得到 R，当场摘掉；tw 晚于 r3 时也就晚于 t2，Q 在 tu 的摘除发生在 tag 落下之后，把它摘掉（Q 末尾的 pass 是又一道）。这几种次序的论证依赖三条可见性与次序：①写映射成功之后，其它调用方的 `GetParametersByPath` 取回含该参数的那一页时读得到它；②`TagResource` 成功之后，此后发出的 `DescribeTaskDefinition`（`include=["TAGS"]`）读得到这个 tag（Q 末尾的 pass、「注册与回收的竞争」段的再读依赖它）；③在一个已成功返回的 `TagResource` 之后发出的 `UntagResource` 作用在它之上、不被它覆盖（Q 的立即摘除依赖它）。ECS 的官方文档明确它的 API 采用最终一致模型，②③因此没有保证，③是推断；SSM 没有找到跨调用方读后写可见、或分页读取构成一致快照的官方保证，`GetParametersByPath` 文档里分页的说明也证明不了强一致或最终一致，①同样没有保证。所以上面的论证只在这三条成立时闭合，不成立时的落空写进残余风险①；实测项 10 只能补充观察，不能关闭这一风险。立即摘除相对只靠 Q 末尾的 pass 缩小了两类窗口：不必等整条命令执行到末尾（写映射之后命令中途失败、在清理之前返回，如 push-worker 写默认指针失败、deploy 的基础镜像同步之后的步骤失败，Q 一侧不再因此留下 tag），也不必先读到 tag（不依赖②）。它消除不了三种情形：写映射之后、摘除之前进程崩溃或被中断；摘除失败；tag 晚于摘除落下（`TagResource` 报错而服务端在摘除之后才生效，或③不成立）。它缩小窗口，不是绝对的保证。多趟 pass 并发时论证逐趟成立：每个误补打的 tag 都出自某一趟，那一趟的 t2 早于它自己的 r3，tw 早于 r3 时由那一趟的重读摘掉，晚于 r3 时由 Q 的摘除摘掉；另一趟若在 P 的 tag 可见之前列了 family，会再补打一次、以它自己的值覆盖（同一个 key 再打，新值覆盖旧值，ECS 官方文档明确；文档不保证并发请求落下的先后，后落下的值不一定更晚，见残余风险①），这一次出自那一趟，按那一趟自己的 r1、t2、r3 同样落在上面三种次序之内。「`registeredAt` 早于 t1 才补打」是附加的一道：Q 在 t1 之后才注册的 R，P 根本不打，不依靠后面的摘除；步 6 到步 7 之间只有一次再读与一次 SSM 写，新注册的 revision 多半落在这里；注册早于 t1、写映射晚于 t1 的仍靠写映射之前的再读（「注册与回收的竞争」段）、重读与摘除。`registeredAt` 由 ECS 的时钟给出、t1 取本机时钟：本机时钟偏慢只让本趟少打（偏保守），偏快时这道附加保护变弱，仍有重读与 Q 一侧的摘除。t1 是 P 开始读映射之前的本机时刻，只用于这道附加条件；上面三种次序按 r1、r3 论证，与 t1 无关。
  - **注册与回收的竞争**：步 6 注册之后、步 7 写映射之前（重派生同样在注册与写映射之间），新注册的 revision R 不在任何映射里。推送进程 Q 在这两步之间停留超过静默期（命令长时间执行或进程被挂起）时，一趟 pass P 可能给 R 补打 tag，满 1 小时之后另一趟 pass P′ 把 R 收为成熟候选，Q 这时才把 R 写进映射。它不依赖 AWS 的可见性。取消孤儿复用之后，这是不在映射里的 revision 进入映射的唯一一条路，也是「写进映射」与回收竞争的唯一来源（离开映射一侧，替换的一步打 tag 与回收的竞争见残余风险①）。后果按 Q 写映射与 P′ 注销 R 的操作次序分两类，两类的后果并不互斥。**先注销、后写映射**：映射悬空。注销状态对读取可见之后，用这个 variant 的提交在 preflight 因 revision 不是 ACTIVE 以退出码 2 结束、提示推送；在此之前，刚注销的 revision 可能短时仍读作 ACTIVE（推断，见残余风险⑥），preflight 也可能接纳提交，该 run 随后起 task 失败（同残余风险②）。同一 digest 重推时，步 5 若只比二元组，就会直接沿用这条映射、跳过注册，按提示操作也恢复不了（下面其三处理）。**先写映射、后注销**：Q 写映射并立即摘掉 tag 之后，P′ 内存里仍是它此前收下的候选与快照——摘除撤销不了它们，P′ 若不再核对就会注销 R（下面其二的最后核对处理）。这时 R 已在映射里，新的 preflight 可能已解析到它、STATE 尚未落库，快照看不到这类 run，清理误删了在用的 revision；这也破坏下面「为什么一次快照就够」的前提其一（候选在静默期内没有被写进映射）。设计上补三条。其一，写映射之前对 R 再 `DescribeTaskDefinition`（`include=["TAGS"]`）一次，仍为 ACTIVE 且不带 `gherkai:retired-at` 才写；不满足（含描述返回 `ClientException` 且本次 ACTIVE 列举未发现它）即重新注册一个、同样再读，第二次仍不满足时命令失败并提示稍后重新执行（步 6 末尾）。它挡下的是再读时已可见的 tag 与注销，不证明写进映射的 revision 没有正被回收：再读依赖上段的可见性②；再读与写映射之间被打上的 tag 由上段的各道摘除处理；再读看到「不带 tag」也可能是因为补打它的那一趟清理已摘掉了自己补打的 tag（如那一趟的重读失败），而另一趟清理此前已凭这个 tag 的旧值把它收为成熟候选（下面其二的最后核对处理）。剩下的情形见残余风险⑥。其二，清理在注销候选之前做两道核对。先重读一次全部对应关系记录，已在映射里的候选不注销、摘掉 tag（上「候选与静默期起点」段的「重读」，与补打之后的重读是同一次读）；再逐个重读仍不在映射里的候选的 `gherkai:retired-at`，与判定成熟时读到的值不一致（被改写或被摘掉）或这次读取失败的，本趟不注销（下「引用检查」段⑤）。Q 写映射落在映射重读之后时，只要 Q 写映射之后的立即摘除在最后核对之前可见，就由最后核对拦下；上面「再读看到不带 tag」的那种交错同样由它拦下，只要摘掉 tag 的那一步在最后核对之前可见。映射重读检查当时可见的映射，最后核对检查当时可见的 tag 与 ACTIVE 状态。写映射后的摘除未执行、失败，或旧值被恢复时，即使写映射早于最后核对，也可能未被识别；剩余边界见残余风险总括与⑥。其三，步 5 的第一个判断在二元组一致时还要求映射指向的 revision 为 ACTIVE；未能确认它仍为 ACTIVE（描述成功且状态不是 ACTIVE，或描述返回 `ClientException` 且本次 ACTIVE 列举未发现它）时按映射缺失处理：往下新注册，写映射替换悬空的那条；被替换的那条未确认仍为 ACTIVE，步 8 不对它打 `gherkai:retired-at`。二元组不一致的分支同样先确认被替换的那条仍为 ACTIVE，未确认就不打。列举未发现它不证明它已被注销或删除：它若只是尚未在查询结果中可见，即多注册一个 revision，被替换的那条成为不在映射里、不带 tag 的 revision，由之后的清理 pass 按孤儿补打、满静默期后回收。只有上述两种情形按缺失处理，其余读失败（描述报权限不足、限流、网络等其余错误，这时不列举；描述报 `ClientException` 而它仍被列出；或列举本身失败）原样抛出、命令失败，与 preflight「缺失的判定口径」同一判据。这给出悬空映射的恢复路径，与 preflight 的提示一致：同一镜像再执行一次 `push-worker`；纯发行版本的 `base` 也可由 `gherkai deploy` 的基础镜像同步经同一条推送路径恢复（非纯发行版本或取不到发行版本时跳过这一步，用 `push-worker … --variant base`）。代价是步 5 与重派生在映射存在时多一次 `DescribeTaskDefinition`（跳过分支用它确认 ACTIVE，二元组或模板不一致的分支用它在给被替换的旧 revision 打 tag 之前确认它仍为 ACTIVE），描述报 `ClientException` 时另加一次按 family 的 `ListTaskDefinitions`；有成熟候选或补打过 tag 的那一趟清理多一次映射枚举，每个走到注销这一步的候选多一次 `DescribeTaskDefinition`。剩下的风险见残余风险⑥。
  - **时钟（实装要求）**：tag 的值紧邻 `TagResource` 请求之前现读时钟，读时钟与发出请求之间不插入其它远程调用（替换的一步与清理 pass 的补打都如此）；紧邻只缩短取值与请求之间的间隔，进程在两者之间被挂起时，恢复后仍会把较早的值写回（残余风险①）。t1 在开始读映射之前现读。两者都不用命令开始时的时刻：push-worker 的命令开始早于 docker push、deploy 的早于 cdk 与基础镜像同步，都早于本命令写映射，拿它当 tag 的值会让起点早于 R 离开映射，破坏上面的核心不变量。静默期的比较可以用命令的时刻：它早于实际时刻，算出的已过时长偏小，偏保守。测试注入时钟函数，守「补打的值不早于本趟读完映射的时刻、替换的一步打的值不早于写映射成功的时刻」，含命令在读映射之前已执行很久的用例。t1 取开始读之前的时刻是有意的：它越早，`registeredAt` 早于它的 revision 越少，附加保护越保守；tag 的值则须不早于读完映射，因为 R 可能在开始读之后、读到它那条映射之前离开映射。
  - **引用检查（已实装）**：每趟一次快照，与候选数无关。①先收齐全部引擎的候选（上条），没有成熟候选就不读 runs 表（多数 pass 如此），本趟补打过 tag 时仍做上条的「重读」。②就绪检查：对 runs 表做一次 `DescribeTable`，`status_group-run_id-index` 的 `IndexStatus` 为 `ACTIVE` 才继续；缺失、`CREATING`、`UPDATING`、`DELETING` 或 `DescribeTable` 本身失败，全部候选留下，打一行产品语言的警告（说明索引的状态与这次没有回收旧的 worker revision）。判据比 `list-runs` 严（[0041](./0041-agent-facing-cli-affordances.md) 决策七「索引就绪判据」放行 `UPDATING`）：清单读不到只是少一行，清理误判会让 run 后续的 job 起不来；跳过一趟只是让 revision 多留到下一趟。也不依靠「`Query` 一个建立中的索引会报错」这一行为（它没有实测过；若某种情形下返回不完整的结果，就会误删）。③快照：`Query` 分区 `status_group = live`，`ProjectionExpression` 取 `worker_task_def_arns`，按 `LastEvaluatedKey` 翻页读完，把全部 ARN 并成一个集合。不加过滤：过滤在读取之后才应用，不减少读量；一次读回全部 ARN，就不必对每个候选各查一遍。④候选的 ARN 在集合里的留下；其余候选经上条的「重读」，已在映射里的不注销、摘掉 tag。⑤最后核对：仍不在任何映射里的候选，注销之前逐个再 `DescribeTaskDefinition`（`include=["TAGS"]`）一次，读出的 `gherkai:retired-at` 与本趟判定成熟时读到的值逐字相同、且它仍为 ACTIVE，才紧接着发出 `DeregisterTaskDefinition` + `DeleteTaskDefinitions`（`failures` 的处置不变），读取与注销请求之间不插入其它远程调用；值不同、tag 已不在、revision 已不是 ACTIVE，或这次读取失败时，本趟跳过该 revision 并打印一行警告，继续核对其余候选。后续 pass 仅对仍为 ACTIVE 的 revision 按届时状态重新判定。它关掉两种交错，都是本趟收下候选之后、别的命令改了它的 tag：其一，一个在映射里却带着早于它离开映射的 `gherkai:retired-at`（值为 t0）的 revision（残余风险①：补打之后被写进映射、各道摘除都没有生效），t0 超过静默期之后它的映射被替换，替换的一步写入新时刻之前，本趟已按 t0 把它收为成熟候选，新时刻随后成功写入；其二，一条推送注册了 R、尚未写映射，一趟清理给 R 补打之后停留超过静默期，本趟把 R 收为成熟候选、完成快照与映射重读，补打的那一趟随后重读失败、按协议摘掉自己补打的 tag，推送的再读于是看到 ACTIVE、不带 tag，把 R 写进映射。新时刻或摘除在核对之前可见时，最后核对读到的值已不是判定成熟时的值，本趟不注销。限度：它只看得到核对时刻已可见的改动——核对之后的改动（含核对与注销请求之间的）看不到，读取依赖可见性②，改动已成功而尚不可读时同样看不到；其一里替换的一步晚于核对才打上新时刻的，本趟按 t0 注销（残余风险的总括）。逐字相同也不证明其间没有改动：tag 的值没有变化的落空（替换时没有覆写、旧值被写回），以及 tag 被摘掉之后又被同一个值写回（补打的请求在服务端晚于摘除才生效），都不在它能识别的范围内（残余风险①与⑥）。②③任一步失败（`Query` 报错、权限不足、索引不存在）或重读失败，全部候选留下并打一行警告；②③失败时，本趟补打过 tag 的仍照常做上条的「重读」，处置补打的那些；⑤里被跳过的候选各打印一行警告（见⑤），不影响其余候选。
  - **为什么一次快照就够**：过了静默期的候选，引用它的未到终态的 run 只减不增，前提有三。其一，候选确实不在任何映射里，且静默期内没有被写进映射：「不在映射里」是本趟读映射得出的，依赖上面「打 tag 与写映射的交错」段的可见性①；取消孤儿复用之后，不在映射里的 revision 被写进映射只有一种情形，即它是某条命令刚注册、在写映射之前停留超过静默期的那一个（「注册与回收的竞争」段的「先写映射、后注销」），注销之前的映射重读与最后核对降低但不排除这一风险，具体边界见残余风险总括与⑥；这一部分不在论证之内。其二，新的 preflight 解析不到不在映射里的它，解析到它的 run 在 preflight 之后几分钟内落库，远短于 1 小时。其三，已落库的 run 从 `live` 分组离开只有成为终态一条路，不会回来（run 级状态只进不退，[0034](./0034-detached-batch-reconciler.md) 机制三；run 一到终态，运行态的任何写都不成立，端口也没有整份重写运行态的方法，[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策五：run 成为终态之后 `status_group` 是那个终态的值、不再变化）；分组属性属于运行态的公共部分，1.5 起各版本的写者都维护它（[0037](./0037-distribution-and-packaging.md) 决策 7「跨版本不变的约定」）；1.5 之前的命令行工具写出的 run 不带它，对快照不可见，这类 run 不在论证之内（下面残余风险⑤）。这些前提成立时，快照与注销之间相隔的几秒不会漏掉新的引用。
  - **两种边界情形**：(a) run 正在从 `pending` 换到 `running`：`status_group` 随同一次写写成同值 `live`，revision 列表不变，索引键不变、不计写，索引项一直在 `live` 分组，快照看得到它。依据分三层：DynamoDB 官方的 GSI 写入规则明确，索引写按这次写入实际改变了哪些属性判定，只改既非索引键、也不在投影里的属性时索引项不变、不写索引；同值写没有改变 `status_group` 的值，按这条规则不产生索引写，这是对规则的解读，0034 实测项 6 在以 `status` 为键的索引上对索引键属性的同值写测得为 0；新索引上已实测：认领、前台 job 写与把 run 级写成 `running` 的投影对它都计 0，换值前后各一秒内的 `live` 分组查询全部见到该 run（实测项 8；成员资格只是观测，给不出上界）。(b) run 刚建、STATE 还没传播进索引：快照看不到它，保护只来自静默期——它的 preflight 在 R 离开映射之前就解析到 R，`gherkai:retired-at` 的值不早于 R 离开映射，删除至少再等 1 小时，只要从 preflight 到 STATE 在索引里可见短于 1 小时就不会漏。GSI 的传播没有承诺上界（文档只说通常不到一秒、异常时可能更长），所以这是一条对传播时长的依赖，余量约为 1 小时减去 preflight 到落库的时长。这条依赖是本条原有的静默期论证本来就有的，任何经 GSI 找引用的做法都有，本设计没有新增，只是让它对孤儿与替换时没打上 tag 的 revision 也成立。收尾中的 run 若因传播滞后仍留在 `live` 分组，只会让它的 revision 多留一趟，偏保守。
  - **残余风险**：**总括**：清理的各项读取与注销不是原子操作，ECS 与 SSM 之间没有跨服务的条件写。映射以最后一次映射重读中各页分别取回的时刻为依据，tag 与 ACTIVE 状态以逐候选最后核对（上「引用检查」段⑤）为依据。从各自读取到服务端实际执行注销之间的变化，包括注销请求在途期间的变化，均可能未被本趟识别；可见性延迟（上「打 tag 与写映射的交错」段①②）还可能隐藏读取之前已发生的变化。最后核对读到同一 tag 值，不证明映射没有变化，也不证明 tag 中途未被改动。各道重读只缩短各自的窗口，不能保证互斥。同样的非原子性还出现在另外三处：两处先检查后执行的写，即清理的补打（读映射在前、打 tag 在后）与推送、重派生写映射之前的再读（再读在前、写映射在后）；以及替换的一步（push-worker 步 7 与步 8、重派生）先写映射、后给被替换的 revision 打 tag，两次写之间它已离开映射、仍带着此前的 tag（若有），一趟清理在这期间读映射、做完核对并发出注销，依据的就是这个此前的值。tag 与映射都是无条件写。下面 ① 与 ⑥ 里与其它命令交错的各项是这一形态的已知实例，逐条注明由哪一道核对关掉、或仍在总括之内；其余各项是调用失败、进程中断与并发写造成的落空，不由核对关掉。① R 在映射里时带上了一个早于它离开映射的 `gherkai:retired-at`，离开映射时又没有被新值覆写、新值晚于某一趟清理的最后核对才可见，或覆写之后又被旧值覆盖（上面「打 tag 与写映射的交错」段剩下的落空）。已知实例：(a) 补打之后推送写映射，各道摘除都没有生效：Q 写映射晚于 P 的重读取回该参数的时刻，Q 的立即摘除没执行到（写映射之后、摘除之前进程崩溃或被中断）、失败，或 tag 晚于摘除落下（`TagResource` 调用报错、服务端在摘除之后才生效），且 Q 末尾的 pass 也没有摘掉（没执行到：映射枚举失败整趟放弃、命令在清理之前失败返回或被中断；或摘除失败）；或 P 自己的摘除失败（重读看到 R 已在映射里而摘除失败、重读失败之后摘除也失败）；或 `TagResource` 调用报错、服务端在 P 重读并摘除之后才生效。属调用失败与进程中断，不由核对关掉。(b) 可见性与次序（上「打 tag 与写映射的交错」段①②③）不成立：P 的读没看到已写的映射、Q 末尾的 pass 没看到已打的 tag、Q 的摘除被晚生效的 tag 覆盖，各方调用全部成功而 tag 留在正在使用的 revision 上。仍在总括之内；这三条没有官方保证，实测只能观察、不能排除。(c) 补打的旧值写回：P 读映射时 R 已注册、尚未写进映射，P 取了 tag 的值之后、发出打标请求之前长时间停留（如进程被挂起），这期间 Q 把 R 写进映射并摘除，之后另一条命令 S 替换了这条映射、在替换的一步给 R 打上正确的值；P 恢复后发出请求，以较早的值覆盖 S 写下的值（新值覆盖旧值是官方明确的行为，文档不保证并发请求落下的先后，也不保证后落下的值更晚），而 P 重读时 R 已不在映射里，不摘。它要求 P 的停留跨过 Q 写映射与 S 替换两件事，不需要任何调用失败或可见性异常。这是补打一侧的总括实例；最后核对关不掉它：写回的旧值就是此后各趟读到的值，核对时值一致。上「时钟（实装要求）」段的「紧邻打标请求之前现读时钟」只缩短取值与请求之间的间隔。缓解：此后只要有任何一趟 pass 在 R 仍在映射里、且读得到这个 tag 时执行到摘 tag 这一步，tag 就会被摘掉；R 日后被替换时，替换的一步以新值覆写这个 tag（同一个 key 再打，新值覆盖旧值，ECS 官方文档明确），覆写可见之后，按旧值的判定不再成熟；覆写之前已按旧值收下它的那一趟，覆写在它的最后核对之前可见时由最后核对拦下，晚于最后核对的仍在总括之内（(c) 所说的旧值覆盖新值除外）。所以 (a)(b) 还要求从 Q 到 R 离开映射之间没有这样一趟 pass，且 R 离开映射时没有被覆写，或覆写晚于按旧值收下它的那一趟的最后核对。以上任一种发生时，R 离开映射时静默期可能已满，只剩快照这一道保护，它覆盖不到当时正处于 preflight 与落库之间的 run。后果与下面的 ② 相同。② 误删的后果有界：该 run 剩下的 job 起 task 失败、判为 error，不会挂死，也不会自愈（revision 钉在 definition 里），重新提交即可恢复；已在执行的 task 不受影响。③ 部署方机器之间的时钟偏差直接加减到静默期上：tag 由一台机器的时钟写入，在另一台机器上比较。④ 推进停住的 run 在被结束之前一直在 `live` 分组，它引用的 revision 一直保留（以 `status` 为键时同样如此），快照读量随这类 run 增长。这类云端 run 的出口有两个：后端到期结束（怎样结束见 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九第 1 条，含前提）与用户一侧的处置方（0054 决策八），都经结束写（[0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节），结束之后离开 `live` 分组。⑤ 前提是全部 STATE 写者都维护 `status_group`（[0030](./0030-realtime-persistence-seam.md) 决定六）：没写它的 STATE 对快照不可见。`status_group` 属于运行态的公共部分（[0037](./0037-distribution-and-packaging.md) 决策 7「跨版本不变的约定」），1.5 起各版本的写者都维护它；本版本的写端在 core 的 DynamoDB RunStore 一处，由覆盖全部写路径的不变量测试守。盲区只剩不比对数据版本的 1.5 之前的命令行工具：它向 1.5 的后端建的 run 不带分组属性，对引用检查与 `list-runs` 都不可见，这时它引用的 revision 的静默期可能早已开始；这样的 run 的记录格式版本读作 0，由后端的闸以 error 变体结束（[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九「落实时，后端各入口先过同一道闸」），在此之前它的 job 可能起不来（后果同 ②）。这一情形列为已知盲区（下「已退休却仍被映射引用」条末的「已知盲区」）；升级须知写明不要用 1.5 之前的命令行工具操作 1.5 的后端（0037 决策 7）。⑥ 注册与回收的竞争（上「注册与回收的竞争」段）。各实例都要求 Q 从注册到写映射的总间隔超过静默期：成熟候选的 tag 是在 R 注册之后才补打的，满 1 小时才成熟（部署方机器之间的时钟偏差会缩短这个要求，见 ③）。两类按操作次序区分，后果并不互斥。已知实例：(a) **先注销、后写映射**，Q 写映射之前的再读没拦下：再读没看到已打的 tag 或已做的注销（tag 的可见性②不成立、注销状态尚不可读，或 tag 与注销在再读之后才落下），或补打的那一趟在再读之前已摘掉自己的 tag、而另一趟此前已按这个 tag 注销了 R。这是写映射一侧的总括实例，清理的核对关不掉它。后果是映射悬空：注销状态可见之后，用这个 variant 的提交被 preflight 以退出码 2 拦下；此前 ECS 的读取可能仍把刚注销的 revision 读作 ACTIVE（ECS 官方文档明确它的 API 最终一致，注销之后的具体表现是推断），preflight 也可能接纳提交，该 run 随后起 task 失败（同 ②）。恢复：同一镜像再执行一次 `push-worker`（纯发行版本的 `base` 也可再执行一次 `gherkai deploy`），按「未能确认映射指向的 revision 仍为 ACTIVE 即按映射缺失处理」新注册一个 revision、替换映射；推送若仍把它读作 ACTIVE，会沿用悬空的映射，稍后再执行一次即可。(b) **先写映射、后注销**，补打的那一趟摘掉了自己的 tag：P0 给 R 补打之后停留超过静默期，P′ 把 R 收为成熟候选、完成快照与映射重读，P0 随后重读失败、按协议摘掉自己补打的 tag，Q 的再读看到 ACTIVE、不带 tag，写映射。P0 的摘除在 P′ 的最后核对之前可见时，由最后核对关掉（核对读到 tag 已不在）；摘除晚于最后核对或核对时尚不可读的，仍在总括之内（P′ 实际注销早于 Q 写映射时，落入 (a)；晚于 Q 写映射时，仍属 (b)）；P0 补打的请求在服务端晚于 P0 的摘除与 Q 写映射之后的摘除才生效、写回同一个值的（推断：报错之后的重试请求延迟落下），核对读到的值与判定成熟时相同，不由核对关掉，属 ①(a) 所列的调用失败。(c) **先写映射、后注销**，Q 的写映射落在 P′ 的映射重读之后，且 Q 的再读没拦下（tag 在再读之后才打上并在写映射之前成熟，或再读没看到已打的 tag）：Q 写映射之后的立即摘除在最后核对之前可见时，由最后核对关掉；摘除晚于最后核对或核对时尚不可读的，仍在总括之内；摘除没执行到或失败的，属调用失败与进程中断，不由核对关掉。(b)(c) 漏过时后果是误删在用的 revision：写映射之后解析到 R 的 run 后续 job 起不来（同 ②），映射随之悬空，恢复同 (a)。(b)(c) 还要求清理一侧的核对与 Q 的写映射、摘除恰好交错，比 (a) 更窄，但不能排除。
  - **取舍依据**：可选的做法按「先保证不误清在用的 revision，再看运行成本与结构，最后看部署次数」排序。引用检查对 GSI 的依赖有两处：一是以 `status` 为键时，`pending` 到 `running` 的换键在删旧项与写新项之间可能留下两个分区都查不到的间隙；二是新建 run 的索引项要在静默期之内可见（上面边界情形 (b)）。第二处是以 `status` 为键的旧索引上本来就有的依赖，任何经 GSI 找引用的做法都有，选定方案不新增、也不消除。选定方案关闭的是第一处：换值不改变索引键，没有这次换键，也就没有它的间隙。以 `status` 为键的做法保留这次换键，靠复查降低漏检：趟内复查要求间隙短于一次分区读取加等待时长，余量是秒级；跨趟确认要求同一个间隙短于两趟的间隔 T，T 取到约 1 小时时，它对传播上界的依赖与第二处同一量级，两者在这一点上差的是余量大小、不是有无。跨趟确认与选定方案的区别因此在其余几项：运行成本上，只留 KEYS_ONLY 的列举索引时每趟要强一致读回全部非终态 run 的整个 STATE，选定方案每个 run 3 个索引写单位、表上一个索引、清理一次 `Query` 不读回；协议上，它多一个 revision 级的确认标记，回收多等一趟；对传播上界的依赖余量取决于 T。从当时表上两个以 `status` 为键的索引出发，选定方案要经过多次 stack 更新（CloudFormation 一次更新只改动一个索引），多于只留其中一个索引的一次；部署次数这一项只在从更早的索引形态迁移时才起作用，而状态分组索引这一形态确定时产品还没有使用者、不提供这种迁移的路径（[0041](./0041-agent-facing-cli-affordances.md) 决策七「更早的索引形态」），所以排在最后（被拒方案见下「被拒方案」节与 [0030](./0030-realtime-persistence-seam.md) 决定六）。
  - **已退休却仍被映射引用**：上面「打 tag 与写映射的交错」段的交错会短暂留下这个状态，由那里的各道摘除处理；不靠交错、持续存在的这个状态不会产生：每个 revision 只被发起注册的那一条映射引用（步 5、步 6 与重派生都只把自己刚注册的 revision 写进自己那条映射）；跳过注册的分支沿用的是本条映射自己记录的 revision，不写映射；本模块不把一个已有的 revision 写进任何映射，所以一个 revision 不会同时被两条映射引用。对应关系记录的根 `worker-variant/` 只由 1.5 起的命令写（「SSM 参数与命名真源」节「对应关系记录的读写」段）；手工改 SSM 不在论证之内，1.5 之前的命令行工具写在另一个根下、不在这些论证之内（上「候选与静默期起点」段末）。映射引用仍是清理的前置条件，与运行中 run 引用并列：在任一映射里的 revision 不是候选，即使它带着 `retired-at`（下一趟清理 pass 摘掉它）。**已知盲区**：1.5 之前的命令行工具写出的 run 不带分组属性，它的 revision 引用对这道引用检查不可见（上面残余风险⑤）。
- **默认指针不自动重置**（含版本升级）：它记的是团队意图。
- **不判 steps 内容**：镜像里的 steps 是否最新由使用方管理；preflight 不比对镜像内 steps 与本地 steps——越权替使用方判断，且提交者（feature 作者、CI 机器）手头未必有 steps 目录、会被误拦。想区分就换 variant 名。

## 运行时与 preflight

- **选择进 definition**：`submit --backend cloud [--worker-variant <名>]`（云端后端只有 `submit`，[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 A），缺省取默认指针；CLI 在 preflight 把 variant 解析成各引擎的 revision ARN，写进 definition——`RunMeta.worker_variant`（人读）与 `RunMeta.worker_task_defs`（引擎 → revision ARN），本机后端为 null（必有键，[0037](./0037-distribution-and-packaging.md) 决策 7）；definition 另记 `worker_protocol_version`，云端写后端的值（提交时已拿它与命令行工具自己的值、所选镜像的值比过，三者相同），后端的闸与 `explain` 比它（0037 决策 7）；沿用 `max_concurrency`/`extra_http_headers` 随 definition 走的惯例（[0034](./0034-detached-batch-reconciler.md)/[0035](./0035-local-app-testing-via-tunnel.md)）；同一批 ARN 同时写成 STATE 顶层属性（清理的引用检查用）。云端推进器（kicker / reconciler）一律照 definition 起 task。local 后端忽略该 flag（直接读 steps 目录）。
- **读侧不留兼容路径**（[0037](./0037-distribution-and-packaging.md) 决策 7：新版本不保留读旧值的分支，同一个 run 记录格式版本之内必有键缺席即违约）：云端 definition 必带 `worker_task_defs`（提交侧解析 variant 后写入），推进器读到缺值按运行定义不可用处理——不推进该 run、记一条诊断，以结束写的 error 变体结束它（[0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节、[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九「落实时，后端各入口先过同一道闸」）；**不**按后端当前默认指针解析（那会让运行中的 run 中途换 step 集，破坏「一个 run 内镜像固定」的不变量），**不**回落 family 最新 ACTIVE（那可能是别人的 variant），**也不**用模板 revision（其 `latest` 占位在从未推过 `latest` 的全新 prefix 上根本拉不到镜像）。曾有的「缺字段按默认指针解析」兼容路径服务的是引入本 ADR 那一次升级前提交的 run 与旧 CLI 提交的 run，1.5 不假设存量用户、读端对旧 definition 一律拒绝，该路径随之删除。
- **preflight 只做存在性、一致性与能力的核对，不判内容**，位置在**云端后端接口版本、run 记录格式版本与命令行工具的 worker 协议版本的比对（[0037](./0037-distribution-and-packaging.md) 决策 7）与既有资源 preflight（[0033](./0033-iac-aws-backend-and-composition-wiring.md) preflight 节「preflight 探哪些资源」条）之后**——数据版本比不上时重推镜像解决不了问题，排在后面会让用户白推一轮。对**本 run 用到的每个引擎**（对齐既有 task-def 判据「不探全注册表——没用到的引擎不该拦」），依次核对三项，都在生成运行定义、写任何记录、起隧道、上传安装包之前：
  - **存在性**：请求的 variant 在这个引擎上有对应关系记录、记录读得懂、revision ACTIVE、ECR 镜像（按 digest `describe-images`）存在——任一缺 → 退 2，**不回落默认**（回落是静默行为）；说明陈述没有读到这个 variant 在这个引擎上的有效登记（点名参数路径；本项列的几种缺失是同一句），给出两条出路：部署方用 `gherkai deploy push-worker … --variant <名>` 推送，或改用另一个已推送的 variant 提交（不点名 `base`：没有读它的记录）。这不是数据版本不合，说明末尾不加 0037 决策 7 的那句固定话。
  - **协议版本**：记录里的 `worker_protocol_version` 与后端的（取自命令开头那一次读到的数据版本参数）不同 → 退 2，每个引擎一句，陈述两边的值（说明的形态归 0037 决策 7）。
  - **能力**：协议版本相同之后，先按命令行工具自己的契约校验记录里的 `capabilities`，与本机读能力自述是同一处校验（[0036](./0036-deterministic-capability-discovery.md) 决策 5；两个身份位是能力对象里的 `engine` 须是这条记录所在的引擎，记录里的协议版本已在上一项与后端比过；推送时的校验不能代替它，理由见「概念模型」节下「镜像标注」段「读出」）：不合约定 → 退 2，说明点名这个 variant 在这个引擎上的对应关系记录与不合约定的那一项（形态见 [0037](./0037-distribution-and-packaging.md) 决策 7「说明的要点」；不是数据版本不合，不加固定话）。校验通过之后，用本机执行之前的同一个能力判断核对它（判断只看一份能力对象，不管它来自本机 worker 的自述还是对应关系记录）：本 run 用到的目标都在 `targets` 里、job 墙钟预算不超过该目标的 `max_session_s`（[0048](./0048-test-targets-device-and-ui-kind.md) 决策 3 的两项目标检查；`max_session_s` 是 `targets` 条目里的键，[0049](./0049-worker-capabilities-targets-keys.md) 决策 4，本来就在同一个判断里核），带 `--expose-local` 时 `session_warmup` 为真（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13）；不满足 → 退 2，说明点名哪个引擎的哪个 variant 不支持什么并给出改法，写法见 0048 决策 4（目标）与 0051 决策 13「能力与拒绝点」（会话预热）。本机与云端在这几项上是同一种判定。worker 建会话之前的自检保留，作最后一道（[0049](./0049-worker-capabilities-targets-keys.md) 决策 7）：标注与镜像里实际的 worker 不符时只有它照得出。

  通过则打印各引擎解析到的 variant / digest；运行定义写入各引擎的 revision ARN 与后端的 worker 协议版本（上「选择进 definition」条）。

  **缺失的判定口径**（存在性一项）：AWS 读失败按以下规则分流；其中 ECS 的「本次未确认可用」不等于确认资源不存在。算作缺失的——SSM `ParameterNotFound`；ECS 的 revision 描述报 `ClientException` 时，列举它所在 family 的 ACTIVE revision，本次列举未发现该 ARN 即按本次未确认可用处理、算作缺失（这个错误码泛指请求本身有问题、ECS 的说明里也包括调用方对动作或资源没有权限，单凭错误码分不出「资源不在」与其它客户端错误；列举成功而其中有它，原错误原样抛出；列举本身失败，抛出列举的错误；revision ARN 不是完整的任务定义 revision ARN 形态 `arn:<分区>:ecs:<区域>:<账号>:task-definition/<family>:<编号>` 时不列举、原错误原样抛出），描述报其余错误（访问被拒、限流、服务端错误、网络错误）时含义明确，原样抛出、不发列举请求——列举只在确有歧义时发生，描述被拒时使用者看到的是缺描述权限，不会被随后一次列举的结果盖住；分流只看错误码，不解析报错文本。本实现仅在描述返回 `ClientException` 时列举核对。从未注册过的 revision 在真实 ECS 上返回这个错误码；本次真实账户观察中，发起删除后仍能描述该 revision，返回状态为 `DELETE_IN_PROGRESS`，按「状态不是 ACTIVE」判为不可用、不经过列举；它最终消失之后描述返回 `ClientException`、与从未注册过的编号相同（实测项 11）。若返回其他错误，则原样抛出，该次调用不会修复这条映射（push-worker 与重派生以该错误失败、不注册新的 revision 替换它）。这条限定只能做在代码里：`ecs:ListTaskDefinitions` 与 `ecs:DescribeTaskDefinition` 不支持资源级权限，`Resource` 必须为 `"*"`；仍可使用适用的 IAM 全局条件键，例如 `aws:RequestedRegion`（依据 AWS Service Authorization Reference 的 Amazon Elastic Container Service 一页：这两个动作的资源类型一栏为空；条件键一栏为空只说明没有 ECS 自己的条件键，该参考的表格说明写明适用于任意动作的全局条件键不列在表里，IAM 文档写明 `aws:RequestedRegion` 始终在请求上下文里），IAM 条件表达不了「描述报某个错误码之后才列举」，用到列举的时机由判据本身收窄；ECR `ImageNotFoundException` / `RepositoryNotFoundException`；权限不足、限流、网络等其余 botocore 错误原样抛出，由 `submit` 入口以退出码 2 结束并提示核对凭证 / region / 权限，不给推镜像的提示——翻成缺失会把缺只读权限（`ecr:DescribeImages` / `ecs:DescribeTaskDefinition` / `ecs:ListTaskDefinitions`）的提交者引去重推镜像、原地绕圈。push-worker 与重派生判断映射所指的 revision 是否仍为 ACTIVE、注册之后的再读，都用这一个判据。列举未发现该 ARN 不证明 revision 已被注销或删除：刚注册的 revision 可能尚未出现在列举结果里；查询结果尚未可见时，push-worker 与重派生可能额外注册一个 revision，提交侧可能暂时拒绝提交（说明同上「存在性」一项）。
- **一个 run 一个 variant 名**，跨引擎同名；某引擎缺该 variant 即上条的退 2。

## 多版本与多环境

**一个部署（一个 prefix）只有一份后端**：Lambda 代码、模板 revision、SSM 版本戳与数据版本参数都是单份；不做同一 prefix 内的双版本并行（不设两套并存的后端、按 run 分派）。这不是「任一时刻只运行一个发行版本」：部署进行中与回滚中，各 Lambda、参数与映射在不同时刻换上新值，新旧代码会交错（[0037](./0037-distribution-and-packaging.md) 决策 7「部署进行中」），本 ADR 与 0037 的设计不以没有交错为前提，跨版本的读写由三个数据版本的比对与跨版本不变的约定接住（0037 决策 7）。**要多个版本并存（多人/多团队各用各的），用不同 prefix 部署成不同环境**——prefix 本就是全部云资源的命名空间（[0033](./0033-iac-aws-backend-and-composition-wiring.md)），CLI 经 `--prefix` 显式选择连哪个环境，这是现有机制、无新增设计；闲置成本近零（[0034](./0034-detached-batch-reconciler.md) 的事件驱动、无常驻），只多一份 ECR 存储。local 后端不涉及云端部署、无此问题：CLI 升级即全部升级（worker 经 `[local]` 装在同一 venv）。

## SSM 参数与命名真源

| 参数（前缀 `/{prefix}backend/`） | 值 | 写者 |
|---|---|---|
| `worker-template/<engine>` | 模板 revision ARN | stack 资源（随 `gherkai deploy` 事务） |
| `worker-variant/<engine>/<variant>` | 对应关系记录，JSON：`template_arn`、`revision_arn`、`digest`、`pushed_at`、`worker_protocol_version`、`capabilities` | `push-worker`（含 deploy 的基础镜像同步与重派生） |
| `worker-default` | 默认 variant 名（部署级一个） | deploy 初始化、`push-worker --set-default` |
| `device-farm-project` | 云端 Device Farm 项目 `{prefix}devices` 的 ARN（stack 拿不到项目 ARN 时不建这个参数） | stack 资源（值由 `deploy` 在 cdk 之前找回或建立项目后经 context 传入，随 `gherkai deploy` 事务写、随 `destroy` 删除；项目本身不归 stack 管理，`destroy` 保留） |

键名常量与路径构造**单点在 `gherkai_runtime.names`**（`ssm_path` / `worker_template_key` / 对应关系记录的单条键构造与按路径列举时用的根 `worker-variant` / `WORKER_DEFAULT_KEY` / `BACKEND_VERSION_KEY` / `DATA_VERSIONS_KEY` / `VPC_KEY` / `DEVICE_FARM_PROJECT_KEY`）——推送方、解析方、IaC、Lambda 拼同一个函数/常量，调用点不写裸字面量（曾在组合根、IaC 命名层、deploy 皮三个模块各写裸 `"version"`）。

退休时刻与血缘**不进 SSM**、以 task-def 的 tags 承载（`gherkai:variant` / `version` / `digest` / `template` / `retired-at`；`retired-at` 表示从何时起不被任何映射引用，由替换映射的一步与清理 pass 打，由写映射一方与清理 pass 摘，见「不变量」清理 pass 条）——与 revision 同生死、不撑 SSM 标准参数 4KB 上限、清理对账只看一处。`data-versions`、`version`、`vpc` 三个参数归 [0037](./0037-distribution-and-packaging.md)（决策 6、7），`device-farm-project` 的找回或建立、核对与无权限降级归 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 10。全部落在 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 已授的 `/{prefix}backend/*` 通配内。枚举用 `GetParametersByPath`（`Recursive=true`，单页最多 10 条须翻页）。

**对应关系记录的读写**：每个（引擎，variant）一条，任一时刻每个 variant 在每个引擎上只有一个当前镜像（按协议版本各存一条被拒，见「被拒方案」节）。`worker_protocol_version` 与 `capabilities` 取自推送之前从目标引用读出的两个镜像标注（「`push-worker` 流程」步 2；校验规则见「概念模型」节下「镜像标注」段「读出」）：`capabilities` 是能力标注里的那个对象，原样记下（两个标注都必须有，缺能力标注的镜像推不进）；推送时按推送方的契约核过，那只是提前拒绝，解读它的一方在解读之前按自己的契约再校验（「概念模型」节下「镜像标注」段「读出」）；记录不记整份能力自述（被拒方案「对应关系记录带上整份能力自述」条）；按 Midscene 现有的三个目标加上 `engine` 键估算，一条记录约 580 字节，远在 SSM 标准参数 4 KB 的上限之内；推送时按将要写出的形态核对一条记录不超过这一上限（「`push-worker` 流程」步 2）。读的一方忽略不认识的键；缺 `worker_protocol_version` 或它不是正整数、缺 `capabilities` 或它不是 JSON 对象，这条记录算读不懂：提交时按这个引擎没有可用的镜像处理（「运行时与 preflight」节存在性一项），推送时按映射缺失处理、整条换新（「`push-worker` 流程」步 5）；重派生不改写它：重派生改写记录时原样保留其中的协议版本与能力，读不懂的记录缺这两项或形态不对，改写出来仍然读不懂，要由重新推送整条换新。两者同为必有键：1.5 起的写方每次都写出两者，缺席即违约。清理 pass 对账只看记录里的 `revision_arn`，取得到它的记录即使读不懂也算引用：这条记录仍指着那个 revision，宁滞留不早删（同「不变量」清理 pass 条「实装细则」）。写的一方：推送换了镜像是整条换新；重派生是改写，先读、再改、再写，保留不认识的键与 `pushed_at`、`worker_protocol_version`、`capabilities`（[0037](./0037-distribution-and-packaging.md) 决策 7 写的一方的规则）。记录的根是 `worker-variant/`：键的形态与记录的内容都与 1.5 之前的命令行工具所写的 `worker-image/<engine>/<发行版本>-<variant>` 不同，新根下不会有按旧形态写的键；旧根下的参数不被读取，1.5 之前的命令行工具在 1.5 的后端上注册的 revision 不在任何对应关系记录里，清理按孤儿回收。

## 权限面增量

[0033](./0033-iac-aws-backend-and-composition-wiring.md)「资源清单」末段是编排机器权限的单一登记处（已按下列增量改毕），此处只列增量；**资源域按 0033「结构上只能 `*` 的动作诚实保留、单开 statement」的纪律标注**：

- **部署方**：ECR repo 域动作 `ecr:BatchCheckLayerAvailability` / `InitiateLayerUpload` / `UploadLayerPart` / `CompleteLayerUpload` / `PutImage` + **`ecr:DescribeImages`**（推送前读旧 digest 以打印「原 → 新」，「`push-worker` 流程」步 3；限两个 `{prefix}{engine}-worker` repo ARN）；**只能 `*`** 的 `ecr:GetAuthorizationToken`（其 `proxyEndpoint` 即 registry host——授权响应里的权威值、与 moto 一致，**不需要** `sts:GetCallerIdentity`）、`ecs:RegisterTaskDefinition` / `ListTaskDefinitions` / `DescribeTaskDefinition`（task-def 类动作官方明文不支持资源级权限）、`ecs:TagResource`（注册时打血缘 tag、退休时打 `retired-at`）；`ecs:DeregisterTaskDefinition` / `DeleteTaskDefinitions`（清理 pass 回收 revision 用）同属 task-def 类动作、按 `Resource: "*"` 授；`iam:PassRole`（task / execution role，RegisterTaskDefinition 需要）；SSM `GetParameter`（点读模板/对应关系记录/默认指针，以及数据版本参数与版本戳）+ `PutParameter` + `GetParametersByPath`（`/{prefix}backend/*`）；runs 表 `dynamodb:Query` 供清理的引用检查——**资源须含索引 ARN** `table/{prefix}runs/index/status_group-run_id-index`（只给表 ARN 查不了 GSI）；runs 表 ARN 上的 `dynamodb:DescribeTable`（清理的就绪检查）；`ecs:UntagResource`（push-worker 步 7、重派生写映射之后与步 5 跳过分支确认 ACTIVE 之后立即摘除，清理 pass 摘掉仍在映射里的 revision 上的 `gherkai:retired-at`；与 `TagResource` 同样按 `Resource: "*"` 授）；`ecs:TagResource` 另用于清理 pass 补打 `gherkai:retired-at`，`ecs:ListTaskDefinitions` 另用于描述 revision 报 `ClientException` 时的核对，只在这一类无法从错误码区分「资源不在」与其它客户端错误的报错时用到（「缺失的判定口径」；这个动作不支持资源级权限，`Resource` 必须为 `"*"`，仍可使用适用的 IAM 全局条件键，例如 `aws:RequestedRegion`；用到它的时机只能限定在代码里）。
- **提交者**：只读 `ecr:DescribeImages`（repo 域）、`ecs:DescribeTaskDefinition` 与 `ecs:ListTaskDefinitions`（两个动作不支持资源级权限，`Resource` 必须为 `"*"`；仍可使用适用的 IAM 全局条件键，例如 `aws:RequestedRegion`；依据 AWS 的服务授权参考，见「缺失的判定口径」；后者只在描述 revision 报 `ClientException`、无法从错误码区分「资源不在」与其它客户端错误时用于核对它是否仍在 ACTIVE revision 里，描述报访问被拒、限流等其余错误时不发列举请求）；SSM 读落在已授通配内。
- **云端推进器**：`ecs:RunTask` 资源域须覆盖 family 全部 revision——当前 IaC 已按 `task-definition/{family}:*` 授权（reconciler 与 kicker 同源），**无增量**；不读 SSM（曾为兼容回落默认指针授过 `GetParameter` + `GetParametersByPath`，随「读侧不留兼容路径」撤除；exit-observer 从未授过）。
- **测试开发不需要任何 AWS 写权限**（不推送时）：这是构建与推送解耦的直接收益。

## 容器引擎口子

只需五个动词：`inspect`（对打好 tag 的目标引用读存在、架构与两个镜像标注，「`push-worker` 流程」步 2；不经它取 digest）、`tag`（把本地引用打成目标引用，同一步）、`login`、`push`（推送目标引用，返回推上去的镜像的摘要：取自推送输出，同一流程步 4）、`pull`。推送与同步都不执行镜像，部署方的机器不需要能执行 linux/amd64 镜像（执行镜像问自述的做法被拒，见「被拒方案」节）。默认 docker，`--container-engine podman` / env `GHERKAI_CONTAINER_ENGINE` 切换（podman 子命令相同），只实现 docker（podman 经同一口子接入，见重议闸门）。产品 code 里碰 docker 的只有 `gherkai_deploy_aws/container.py`（push-worker 与 deploy 的基础镜像同步经它；密码只走 `--password-stdin`）与两个 Dockerfile，CLI / runtime / CDK 都不碰它；发布链另在 `.github/workflows/release.yml` 用 docker 官方 action 构建并推基础镜像，`release.yml` 与 `ci.yml` 的镜像 gate 另以 local 态构建同样两个镜像、不推送（均见 [0037](./0037-distribution-and-packaging.md) 决策 8）。`--container-engine` 在 `deploy` 与 `push-worker` 上都收（deploy 的第 2 步也要它）；两类失败分开决定退出码——名字不认 → 退 2（本地参数问题，先于 VPC 取值比对）；装了但不可用 → 这次部署要改变已有后端的 worker 协议版本、并且会同步基础镜像时，在 cdk 之前退 2、不调用 cdk（「`gherkai deploy` 的 worker 镜像四步」第 2 步）；其余情形 cdk 前只警告，cdk 后按「四步的失败语义」退 1。**deploy 机器需要容器引擎**（同步基础镜像要 pull / push；非纯发行版本或取不到发行版本时跳过该步、不探活）；免容器引擎的 registry 直拷是重议闸门里的加法。

## 与版本升级的交互

后端升级时，一个 variant 能不能用只看 worker 协议版本（[0037](./0037-distribution-and-packaging.md) 决策 7），不看发行版本：用它的提交过不过得了协议版本那一项，看它在用到的各引擎上的对应关系记录里记下的协议版本与后端的是否相同（「运行时与 preflight」节协议版本一项）；记录是哪一份镜像，看最后写成的那一笔（推送、同步或重派生，「不变量」节「并发写者」条）。本节只说镜像：云端提交另要求命令行工具自己的协议版本与后端的相同（0037 决策 7「各入口比什么」）；推送要求命令行工具、镜像与后端三者相同（「命令族」节「`push-worker` 与 `list-workers` 的前置」），所以新协议的镜像只能在后端的协议版本改成新值之后、用持新值的命令行工具推送。在执行的 run 用哪个镜像不变：definition 钉住 revision，revision 按 digest 引用镜像，推进器只按它起 task；definition 另记下的协议版本供后端的闸比较（[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策九「落实时，后端各入口先过同一道闸」），数据版本变了时后端怎样处理它们见 0037 决策 7「后端遇到别的格式写出的 run」。

部署对镜像做的事不随协议版本变没变而不同：纯发行版本的部署同步 `base`（「`gherkai deploy` 的 worker 镜像四步」第 2 步，协议版本要变时另有 cdk 之前的两项前提），模板变了时重派生（第 4 步），自定义 variant 的镜像不动。所以协议版本变了的那次升级之后，记录里协议版本与后端不同的自定义 variant 要用新的基础镜像重建、用新的命令行工具推送。次序是先部署后端、再推送：参数仍是旧值时新协议的镜像推不进，持新值的命令行工具在推送开头与后端的协议版本比不上，持旧值的与新协议的镜像比不上，都以退出码 2 结束、没有推送（理由见被拒方案「推送时协议版本不同不拦、只打印提醒」条）。

**默认指针不重置**：它记的是 variant 名（如 `common`），升级不改它；用它的提交过不过得了协议版本那一项，同样看这个 variant 在用到的各引擎上的记录（上），不必因为协议版本变了而重新 `--set-default`。

**并发与失败**：两条推送同时推同一个 variant，记录写入后写的赢（同一 variant 的并发推送不建议但不禁止，「不变量」节「并发写者」条）。两条推送在不同的机器上时，各自打 tag、读标注与推送的是自己机器上的目标引用，每条记录里的协议版本、能力与 digest 出自它自己的镜像，记录本身前后一致。**已知边界**：同一台机器上两条推送同时推同一个 variant 时共用本地的目标引用，一方的打 tag 落在另一方从打 tag 到推送完成为止的这一段里时，另一方记下的标注与摘要可能出自两份镜像；不防：这样用没有意义，遇到自动化工具这样用时再处理（被拒方案「按不可变标识打 tag 并在取 digest 时核对目标引用」条）。重派生与推送交错，按「不变量」节「并发写者：最后写者赢」条。推送之后后端的协议版本被一次部署改变时，记录里的协议版本与后端不同，用这个 variant 的提交在比协议版本那一步被拒（「运行时与 preflight」节协议版本一项）。

## 实测项（1-11 与 13 **已核**；12 待部署之后核；10 的可见性与次序三项只是观测，不关闭残余风险①；「绿≠对」——每条都依赖 mock 之外的真实行为，证据内联于各条）

1. 使用方按模板 build 后 `push-worker`，自定义 variant 与 `base` 并存、各自跑通两引擎；arm Mac 上不带 `--platform` build 出的镜像被步 2 拒绝并给出提示；`--worker-variant` 对某引擎缺失时严格退 2；`--set-default` 在另一引擎缺失时只警告。（**真账户已验**（独立 prefix、dev 版本、本地态基础镜像作 `base`）：两引擎 `push-worker … --variant base` 真推 ECR → 推后取 digest → 注册 revision → 写 SSM；`--worker-variant nope` 退 2 并给 push 提示；`--set-default probe2` 只警告 midscene 缺映射，随后不带 flag 的双引擎 submit 在 preflight 被 midscene 缺映射拦下退 2；恢复 `base` 后双引擎 run passed。**发行版基础镜像亦已验**：v1.4.0 首发后用 `uvx gherkai==1.4.0` 提交双引擎 run，两 task 分别用 GHCR 同步来的 `1.4.0-base` revision（ECR 里的 tag 带发行版本前缀是当时的形态）（两引擎的 ECR 镜像 digest 与 GHCR manifest digest 逐字相同），exit 0、run passed。**自定义 variant 携带真实使用方 step 亦已验**（v1.4.0 发行版）：使用方项目 `steps/title_check.py` + `steps/title-check.mts` 注册同一条 `页面标题包含 "…"` 的确定性 step，按三行模板 `FROM ghcr.io/…:1.4.0` + `COPY steps/` + `ENV GHERKAI_STEPS_DIR` 各 build 一个镜像、`push-worker --variant custom` ×2，`submit --worker-variant custom` 的三 scope run：novaact 与 midscene 正例各 passed、novaact 故意错的标题断言 **failed**（证明走的是确定性 handler 而非 AI 兜底），三个 task 用的正是 custom 的 revision、worker 均 exit 0。**未另跑（判据已验、场景等价）**：arm Mac 上不带 `--platform` 真 build 这一场景没单独跑——`inspect` 得 arm64 → 步 2 拒的判据已在真 docker 上用真 arm64 镜像验过（见下 6），同一分支不重复跑。）
2. push-worker 幂等：在推送与注册之间、注册与写 SSM 之间人为中断后重跑收敛；两个终端并发 push 同名 variant 后 `list-workers` 标出孤儿、静默期后清理回收。（**真账户部分已验**：同镜像重推 → 「映射已是（当前模板，本 digest）→ 跳过注册」；同名 variant 换 digest 重推 → 打印「原 → 新 digest」、旧 revision 打 `retired-at`、`list-workers` 列为待清理；与 `base` 同 digest 的新 variant 注册自己的 revision、不复用 `base` 的（此处真跑抓出并修掉「跨 variant 复用」，见被拒方案「孤儿复用」条）；**中断重跑**（按血缘 tags 手工注册一个 variant 的 revision、不写 SSM 以模拟中断在注册与写 SSM 之间 → 重跑 push-worker 复用它、不重复注册；验的是当时的孤儿复用，它已取消（被拒方案「孤儿复用」条），取消之后改为新注册、留下的那个由清理回收，已在真实推送上核过，见实测项 10）；**并发 push 同名 variant**（两进程不同 digest 同时推 → 各注册一个 revision、后写者映射赢，`list-workers` 把先写者标为孤儿）。**静默期回收已验**：退休满 1 小时的 revision 在下一次 push-worker 末尾被回收，同趟未满 1 小时的留着（见下 3）。）
3. 清理 pass：有运行中的 detached run 引用时被拦下、run 结束且静默期满后下次 pass 成功；「preflight 刚解析完立即 submit」的对抗用例不被清理打断；deploy 改 cpu 后重派生使既有 variant 的 revision 更新且旧 revision 被打 `retired-at`。（**真账户已验**：`gherkai deploy --stop-timeout 100` 只改模板 → 六个（引擎，variant）全部重派生到新 revision（继承 `stopTimeout=100`、镜像仍按原 digest、`pushed_at` 保留）、旧 revision 打 `retired-at`、默认指针不动；**静默期回收**：退休满 1 小时后的下一次 push-worker 末尾清理 pass 真回收了该 revision（`DeregisterTaskDefinition` + `DeleteTaskDefinitions`，AWS 侧随即 `DELETE_IN_PROGRESS`），同一趟里未满 1 小时的退休/孤儿 revision 全部留着。**运行中 run 拦截已验**：把一个已退休 3 小时的 revision 交给一条非终态 STATE（`worker_task_def_arns` 含它）引用，清理 pass 留下它（ECS 仍 ACTIVE）；把该 run 置终态后下一趟回收（`DELETE_IN_PROGRESS`）——GSI Query + `contains` 的引用检查在真 DynamoDB/ECS 上成立。「preflight 刚解析完立即 submit」的窗口由 1 小时静默期覆盖，未另做对抗。）
4. 重推同名 variant 期间运行中 run 的后续 job 仍用旧 revision；无 `worker_task_defs` 的 definition 由推进器标 error、不执行（「读侧不留兼容路径」；曾有的默认指针兼容路径在真账户验过后随 [0037](./0037-distribution-and-packaging.md) 决策 7 撤除）。（**重推期间运行中 run 的后续 job 仍用旧 revision已验**：3 个 scope `--max-concurrency 1` 串行 run 跑到第一段时重推同名 variant（digest 换、旧 revision 打退休 tag、新 revision 注册），随后的第二、第三段 task 仍用旧 revision（definition 钉死），run passed。）
5. 部署写版本戳并从 GHCR 同步基础镜像。（**真 `gherkai deploy` 写新版本戳 + 同步 GHCR 基础镜像已验**：用发行版 `uvx --from 'gherkai[deploy-aws]==1.4.0' gherkai deploy` 把验证环境从 dev 版升到 1.4.0——SSM 戳变 `1.4.0`、两引擎从 GHCR 拉 `1.4.0` 基础镜像推成 ECR 里的 `base`（当时 tag 为 `1.4.0-base`）并注册 revision、默认指针不动、无需重派生（新版本尚无其它 variant）；随后 `uvx gherkai==1.4.0 submit` 的 run 用新 revision 跑通。）
6. 本地未推送镜像的 `inspect` 在两种镜像存储下给出的 `RepoDigests` 都不能证明目标仓库已有该内容；按仓库里这份镜像的 digest 注册的 revision 能被 RunTask 拉起。（**已验**：真 docker——overlay2 存储（Docker 29.9.3）下未推送镜像 `RepoDigests` 空、`docker tag` 到 ECR ref 后仍空；containerd 镜像存储（Docker 29.1.3，amd64 主机）下，刚构建、从未推送的镜像 `RepoDigests` 即有一条 `<本地名>@sha256:X`，`docker tag` 到 ECR ref 后多出一条 `<该 repo>@sha256:X`（同一个 X），全程没有推送——本地出现某个仓库的条目不证明仓库里有这份内容，所以登记的 digest 不取自本机（「`push-worker` 流程」步 4 取自推送输出，被拒方案「digest 取自本机 `inspect`」条）；arm64 镜像被步 2 拒。真引擎用例自带一个现构建的测试镜像、按引擎报告的镜像存储分两支断言，不借用本机已有的 worker 镜像：做过 push-worker 的机器上它已带着 ECR 的 repo digest，「从未推送」的前提不成立。真账户——（当时 digest 取自推送之后本机上本仓库的条目）这个 digest 被 `describe-images` 认（preflight 三环通过），kicker 起的 Fargate task 的 `taskDefinitionArn` 正是 push-worker 注册出的那个 revision（显式 revision、非 family 最新），两引擎 task 各 exit 0、run passed；containerd 镜像存储下的 digest 链逐环对过（两个引擎各一份、由不带构建证明的经典构建器构出的单平台镜像）：本地镜像上该仓库条目的 digest、ECR 里该对象的 digest、注册出的 revision 引用的 digest 三者相同，ECR 里的对象是单个 OCI image manifest，云端 task 由这个 revision 拉起并执行；这一存储下本地的 image Id 与该 digest 相同。这些只说明在不带构建证明的单平台镜像上本机条目与仓库一致，不作为取 digest 的依据。**已验范围到此为止**：本地是多平台索引、缺别的平台的内容时，本机条目与仓库收下的不同，见实测项 13；带构建证明（provenance / SBOM）而在本地成为内容齐全的 OCI 索引的镜像，推送后仓库收下的是什么对象、推送输出里的摘要是否与之一致，没有核过（实测项 12）；基础镜像的发布关掉了构建证明（[0037](./0037-distribution-and-packaging.md) 决策 8），同步路径上不会遇到，使用方自己构建的定制镜像可能遇到。）
7. 多平台本地镜像的两种存储形态（**两种形态都已在真引擎上核过**；ECS 对索引的平台选择不在其内，没有在 ECS 上执行过）。overlay2 存储**装不下多平台镜像**——`docker buildx build --platform linux/amd64,linux/arm64 --load` 直接报 `docker exporter does not currently support exporting manifest lists`，`inspect` 恒给单平台视图（arm 主机上得到 arm64 → 被拒，过严但安全）。containerd 镜像存储（Docker 29.1.3，amd64 主机）：`docker pull --platform linux/arm64 alpine:3.20` 后本地引用是索引——`inspect` 顶层 `Os` / `Architecture` 为空串、`Descriptor` 是 index、`RepoDigests` 是索引 digest；`inspect --platform linux/arm64` 给出 linux/arm64 与该平台 manifest 的 Descriptor；`inspect --platform linux/amd64` 退出码 0 但两字段仍为空（索引列了 amd64、内容没拉）；同一索引只拉 amd64、或 amd64 与 arm64 都拉时，顶层直接给 linux/amd64（顶层 = 本机平台那一份的视图，有则填、无则空）；对本地 `docker build --platform linux/amd64` 构出的单平台镜像，顶层字段有值、`--platform linux/arm64` 报 `does not provide the specified platform`。步 2 据此以「顶层为空就问目标平台视图」为判据：由此推演（未在 arm 主机真跑）arm Mac 开 containerd 存储时按文档 `--platform linux/amd64` 构出的镜像，顶层为空而目标平台视图有值，能通过校验——旧判据会把它拒成「平台是 ?/?」（GitHub 托管 runner 换到 containerd 存储后，CI 的真引擎用例先暴露了旧判据把索引当成未知平台）。`docker image ls --tree` 仍是实验特性、不用。amd64 主机上含 amd64 内容的索引通过校验后 `docker push`，推送之后本机的 `RepoDigests` 是 index digest；按实测项 6，本机的这一条目证明不了仓库收下的是什么。索引里别的平台缺内容时，推送成功、推上去的是本机有的那一份单平台 manifest，本机报的仍是索引的摘要，它在仓库里不存在（实测项 13）；登记的 digest 取自推送输出（「`push-worker` 流程」步 4），实测与仓库收下的相同。索引内容齐全时推上去的是什么、推送输出里的摘要与云端按它拉取的情形待核（实测项 12）。
8. 状态分组索引上的索引写与成员资格（**已核**）。在部署出的 runs 表上做，表上只剩 `status_group-run_id-index`；同一组探测此前在它与以 `status` 为键的 `status-run_id-index` 并存的表上做过一遍，作对照。
    - 索引写（`ReturnConsumedCapacity=INDEXES`）：由一个探测脚本直接调用 `DynamoDBRunStore` 的各条写路径写四个探测 run（用后即删，删后核过零残留），逐个请求从响应里取对 `status_group-run_id-index` 的写入消耗（这些写不经 gherkai 命令发出；探测脚本没有入库）：`create_run` 的 STATE 那一次写 1.0（META 那一次为 0）；全 pending 的投影（只写事件进度）0；认领（run 级 `pending` 换到 `running`，同一次写带同值 `live`）0；把 job 写成 `running` 的前台 job 写（run 级 `pending` 换到 `running`）0；把 run 级写成 `running` 的投影 0；run 级已是 `running` 时的投影与 job 写（含把两个 job 写成 `passed` 的投影）0；`try_finalize`（`live` 换到 `passed`、`error`）与 `finalize_run`（`live` 换到 `failed`）各 2.0；终态被改写（`finalize_run` 把 `passed` 改为 `failed`）2.0（`try_finalize` 与 `finalize_run` 此后都已从端口删除，投影也不再写 job 的终态：run 与 job 的终态只由终态写与结束写写下、不再能被改写，[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策五；这几项读数留作当时的记录）。正常生命周期合计 3 个写单位（建 run 1、收尾 2），与 [0030](./0030-realtime-persistence-seam.md) 决定六「运行成本前后对照」的估算相同。对照：两个索引并存时，状态分组索引的各项读数与上面完全相同；`status-run_id-index` 对建 run 计 1、对三条把 run 级从 `pending` 换到 `running` 的写各计 2、对收尾计 2——同一次换值在新索引上是同值写、不计写，在以 `status` 为键的索引上按换键计 2。
    - `live` 分组的成员资格，做法一（真实 run）：三个云端 run（一次两个 job 的 `submit`、一次断言必然不成立的 `submit`、一次前台云端 run，两个引擎都有）执行期间，四个并发循环不停查询 `live` 分组（约每秒 18 次，共 4056 次），同时以强一致读连续读各 run 的运行态。判定一次查询「该见到它」的条件：这次查询开始之前最近一次、与结束之后最早一次的运行态读回都未到终态。满足条件的查询三个 run 分别为 1702、1317、1553 次（合计 4572），没有一次缺席；run 级从 `pending` 换到 `running` 的前后各一秒内，三个 run 的 48、47、52 次查询全部见到它；运行态读到终态之后才开始的查询，没有一次还在 `live` 分组里见到它。两个索引并存时做过同一观察（4836 次），同样没有缺席。
    - 做法二（探测 run，时刻可控）：建 run 返回后 0.37 秒第一次在 `live` 分组里查到；此后到收尾之间的 145 次查询、认领前后半秒内的 15 次查询都查到它；收尾返回之后开始的查询都在终态分组里查到它，没有一次两个分组都查不到（约每秒 9 次，一次观察）。有 2 次采样先后两次查询分别在 `live` 与终态分组里各见到它：两次查询不是同一时刻，不能据此断定两个分组曾同时含有它。
    - 写端：两个 run 从建 run 到收尾以强一致读连续读运行态（183 次与 165 次），分组属性与 run 级状态没有一次不对应（未到终态恒为 `live`，收尾那一次读即为终态值）。
    - 边界：成员资格只是观测，给不出上界；它支持「不计写即索引项不受影响」这一推论，不构成保证，清理也不依赖间隙的长度。建 run 之后、索引项出现之前的那一小段（这次 0.37 秒）查询不到，是已知的最终一致读，由静默期覆盖（「不变量」清理 pass 条「两种边界情形」(b)）。

    - 新注册的推送：在注册之后、再读之前给新注册的 revision 打上 `gherkai:retired-at`，推送改为重新注册，写进映射的是不带这个 tag 的那个——协议用例 `test_reread_before_writing_the_mapping_registers_again_once`；在再读之后、写映射之前打上，写映射之后它不再带这个 tag（写映射一方的立即摘除）——协议用例 `test_writing_the_mapping_is_followed_by_removing_retired_at_from_the_new_revision`。
    - 真实命令另核：与 `base` 同 digest 的新 variant 注册自己的 revision，不沿用 `base` 的（实测项 2 的判据在现行 code 上仍成立）。
    - `registeredAt`：记录真账户上 `DescribeTaskDefinition` 返回的带血缘 tags 的 revision 是否都带这个字段——观察：协议用例对真实账户执行的那一次会话里，344 次注册的响应都带这个字段；清理与推送经 `DescribeTaskDefinition`（带 TAGS）读到的带血缘 tags 的 revision 共 126 个（按 ARN 去重），描述结果都带，没有一个不带。「实装细则」所说的一直滞留只在取不到时出现，这次没有出现；观察不构成保证。
    - 可见性与次序（「打 tag 与写映射的交错」段的①②③；各 40 次，只是观测，给不出上界或保证，不关闭残余风险①）：①一个连接 `PutParameter` 写入成功返回后，另一个独立建立的连接立刻 `GetParametersByPath`（翻完全部页），40 次都读到；②一个连接 `TagResource` 成功返回后，另一个独立连接立刻 `DescribeTaskDefinition`（带 TAGS），40 次都读到这个 tag；③同一连接 `TagResource` 紧接着 `UntagResource`，之后立刻读与隔 2 秒再读、从两个连接读，40 次都读不到这个 tag，全部结束 10 秒后再读仍不在。①②原先的表述是「另一进程」，观察用的是另一个独立建立的连接，未另做跨进程观察。对不存在的 tag 键执行摘除、同键再次赋值的观察记于实测项 11。
    - 装置的边界（不读作已核）：协议用例的交错由钩子在同一进程里摆出，组合用例的多方次序由用例在同一进程里用线程摆出，都不是真实并发的进程；协议用例与组合用例的时钟都是注入的，真实时钟下核到的只有上面标「真实命令」的各条；「写映射之后立即清理、而映射对清理尚不可见」这种依赖服务端可见性延迟的交错，装置构造不出来，只能由上面的可见性观察估计窗口。
11. ECS 对任务定义 revision 在各阶段的真实返回（已核）。在真实账户上用一个临时 family 注册一个 revision，依次观察：
    - 刚注册之后：`DescribeTaskDefinition` 返回 `ACTIVE`，同一 family 的 `ListTaskDefinitions`（`status=ACTIVE`）在注册后约一秒的第一次查询起就列出它（连续八次都列出）。「刚注册的 revision 暂时不在列举结果里」在这次观察里没有出现，仍按最终一致对待，不作为保证。
    - 从未注册过的编号、从未注册过的 family：`DescribeTaskDefinition` 返回 `ClientException`（消息为无法描述该任务定义）。「缺失的判定口径」只在这个错误码上列举核对，与真实返回相符。
    - 注销之后：`DescribeTaskDefinition` 成功、状态为 `INACTIVE`，`ACTIVE` 列举里不再有它；对它打 tag 成功。
    - `DeleteTaskDefinitions` 之后：响应里状态为 `DELETE_IN_PROGRESS`、没有 `failures`；此后至少八分钟内 `DescribeTaskDefinition` 一直成功、状态为 `DELETE_IN_PROGRESS`，不返回错误，它出现在 `status=DELETE_IN_PROGRESS` 的列举里；对它打 tag、摘 tag 都成功，再次注销返回 `ClientException`。因此，本次观察到的 `DELETE_IN_PROGRESS` 响应由「状态不是 `ACTIVE`」这一支判为不可用，不经过 `ClientException` 加列举这一支（最终消失之后的返回见本项末条）；moto 对已删除的 revision 返回 `ClientException`，与真实 ECS 在这段时间里的形态不同，测试里以 moto 的形态模拟删除的用例守的是列举这一支本身。
    - 同一个 tag 键再打一次：读回的是后一次的值（与官方文档的说法一致）。对不带某个 tag 键的 revision 摘除这个键：成功返回，不报错。
    - `DELETE_IN_PROGRESS` 最终消失之后：发起删除约三四十分钟后的一次描述返回 `ClientException`（消息同上），与从未注册过的编号相同；这时由「描述报 `ClientException`、ACTIVE 列举未发现」这一支判为本次未确认可用。
12. 镜像标注的读取与记录、推送输出的形态（待部署之后核）：arm Mac（Docker Desktop）与 amd64 主机上推送定制 variant 时，步 2 从目标引用的 linux/amd64 视图读出两个标注、经 FROM 继承（arm 主机上对目标引用 `inspect` 读到的是不是 linux/amd64 那一份的标注，同在待核之列）；没有协议版本标注的镜像、协议版本标注与命令行工具不同的镜像、能力标注里的 `engine` 与 `--engine` 不同的镜像都在推送与任何 ECS 调用之前被拒；命令行工具的协议版本与后端不同时推送在开头被拒；改写了能力标注（去掉某个目标或把 `session_warmup` 置为 false）的镜像，用到那项能力的提交被拒、不写记录；标注与 worker 不符的镜像由 worker 的核对记 `precheck_failed`；deploy 同步的 `base` 记下协议版本与能力；重派生保留它们。其中 containerd 镜像存储与多平台索引下从 linux/amd64 视图读出标注、定制镜像继承标注这两项，还没有在真实引擎上核过，设计以它们成立为前提。另核推送输出（「`push-worker` 流程」步 4）：多平台索引内容齐全时（较新的容器引擎在本机构建、带构建证明），推送输出里的摘要与仓库里这个 tag 的是否相同、注册的 revision 引用它时云端能否拉起；经典镜像存储与 podman 下推送输出的形态。
13. 推送输出里的摘要、本机报的摘要与仓库收下的（**已核**，Docker 29.1.3、containerd 镜像存储、amd64 主机，推到 worker 镜像仓库的临时 tag，用完即删）：
    - 推送输出的形态：把一份已在仓库里的单平台镜像另打一个 tag 推送，`docker push` 以 0 退出，输出的最后一行形如 `<tag>: digest: sha256:<64 位十六进制> size: <字节数>`，整段输出里带 digest 的只有这一行；它与仓库对这个 tag 给出的 digest 相同。
    - 三个摘要的比较：两份源镜像各打一个目标 tag 推送，比较推送之后本机 `inspect` 的 `RepoDigests` 里本仓库的那一条、推送输出最后一行里的、仓库对这个 tag 给出的。源镜像是多平台索引、本机只有 linux/amd64 一份内容（从公共仓库按 `--platform linux/amd64` 拉下来的多平台镜像）时：打 tag 之后、推送之前，本机就已对目标引用报出一个本仓库的摘要，即索引的摘要；推送以 0 退出，输出里另有一句提示别的平台的内容不在、只推了本机有的那一份单平台镜像（提示里另以别的形态给出两个摘要，不是推送结果那一行的形态）；推送之后本机报的仍是索引的摘要，仓库里这个 tag 指向单平台 manifest，与推送输出最后一行里的相同；本机报的那个摘要在仓库里不存在，按它向仓库读得到镜像不存在。源镜像是产品发布的基础镜像（单平台 manifest）时：三个摘要相同。
    - 结论：本机报的摘要与仓库收下的不同是真实存在的，条件是推送的镜像是多平台索引而本机缺别的平台的内容；照本机报的登记，登记的摘要不在仓库里；按提交前的存在性核对（「运行时与 preflight」节）推出，用这个 variant 的云端提交会被拒，不会执行别的镜像。推送输出里的摘要在两种情形下都等于仓库里的，所以步 4 取它；单平台镜像不受影响。
    - 仓库读回行为的记录（不作设计依据）：只用 ECR 的接口（`BatchGetImage`、`GetDownloadUrlForLayer` 加一次对下载地址的 GET）按 tag 读得出这个 tag 指向的 manifest 与配置对象，配置对象的 SHA-256 等于 manifest 里记的摘要；仓库按请求里可接受的媒体类型转换返回的 manifest（只接受 OCI 两种时，Docker 格式的 manifest 与 manifest list 被转换，返回文本的 SHA-256 与 digest 不同；不指定或接受全部四种时返回原文）；只请求单平台 manifest 的媒体类型时，指向索引的 tag 返回的仍是索引；写成之后立即按 tag 读，9 次都读到新值，只是观测，不构成对一致性的保证。
- **mock / 无凭证层的覆盖面**（真账户证据见上各条；下列协议用例（当时的 103 条）另经当时的装置（整理后的复用版现位于 `tools/workers_real_aws/`）原样对真实账户执行过一遍，之后补的 11 个组合用例经同一装置另行对真实账户执行、全部通过，结果与边界见实测项 9、10）：真 synth 出的模板含 runs 表 `status_group-run_id-index`（分区键 `status_group`、排序键 `run_id`、INCLUDE `worker_task_def_arns`）、推进器角色无 SSM 读策略、ECR 无 lifecycle、无模板 env；moto 验了八步幂等（二元组查重、中断后重新执行即新注册、不匹配 family 里已有的 revision、退休 tag）、清理的三个前置条件（静默期 + 对 `live` 分组的一次 GSI Query + 映射引用）、就绪检查只认状态分组索引（表上其它索引 `ACTIVE` 而它缺失时不注销、不 Query）、快照翻页读完、重派生、指针不重置、`--set-default` 只警告；数据版本比对（接口版本；命令行工具、镜像与后端三者的协议版本相同才推送）的 moto 用例待实装，不在已验之列；**跨组件真互通**——真 `DynamoDBRunStore` 的 `create_run`、把 run 级写成 `running` 的 job 写与收尾写（当时为 `finalize_run`）写出的 STATE 被真实的清理快照在键与投影都与 stack 相同的索引上读到：建 run 后与换到 `running` 后都在快照里，收尾之后不在，META item 与不带 revision 列表的 run 不贡献 ARN；其余快照用例以 core 写端的同一个派生函数写出分组属性，验 `pending` 与 `running` 的 run 在同一次查询里被读到、各终态的 run 不在快照里；core 侧另有用例守真写端写出的分组与 META 不进索引。真 push 写的 SSM/ECS/ECR 三件套被提交侧的 `resolve_worker_variant` 原样读回。synth 断言 runs 表恰有 `status_group-run_id-index` 一个索引，`status-index` 与 `status-run_id-index` 都不在。

## 被拒方案（护栏，防未来重踩）

- **gherkai 拥有定制镜像的构建（曾拟 `build-workers` 命令即时生成 Dockerfile、build、push 一体，且住 CLI 本体）**：镜像构建是测试开发自己的容器工作，gherkai 拥有它就得替所有构建方式与引擎负责；只保留三行模板，云端侧的推送与注册归部署方、归 `gherkai-deploy-aws`。
- **支持 ARM64 / 多架构基础镜像、架构随 variant 走**：Fargate ARM64 的不可用面按 AZ（us-east-1 的 `use1-az3`），要按 ZoneId 排除子网、维护排除表、多架构 buildx、`--base-arch` 旋钮，换来约 20% 的 task 单价；复杂度不值，且使用方 build 仍需注意平台。固定 linux/amd64，push-worker 推送前校验把 `--platform` 漏给的错误提前 fail-loud。锁文件静态核查两侧依赖均有 linux/arm64 产物（Python 侧 playwright 等 18 个平台 wheel、Node 侧 esbuild/sharp），将来要省钱路是通的，见重议闸门。
- **preflight 校验 steps 漂移（steps 目录摘要作第二个 tag 或存 SSM 比对）**：越权替使用方判断内容；提交者手头未必有 steps 目录会被误拦；需要区分就换 variant 名。
- **variant 参数叫 `--tag`**：它命名的是一套 step，ECR 里的 tag 只是它在镜像仓库里的落点，与镜像 tag、AWS 资源上的 tag 都要分开叫；`--variant` / `--worker-variant`。
- **push-worker 一次收两个引擎（`novaact=<img> midscene=<img>`）**：参数形式重、两引擎镜像本就分别 build；一次一个引擎、`<本地镜像>` 作唯一位置参数。
- **按镜像标注判断定制镜像用的是哪个发行版本的基础镜像**：发行版本不决定能不能一起工作（[0037](./0037-distribution-and-packaging.md) 决策 7）；标注只带 worker 协议版本与能力这两项判断要用的事实，step 内容由使用方负责（「不变量」节「不判 steps 内容」条）。
- **digest 取自本机 `inspect`**（推送之前用本地 `inspect` 的 `Id`；或推送之后对目标引用再 `inspect`、取 `RepoDigests` 里本仓库的那一条）：本机报的不一定是仓库收下的。推送之前本机给出的值只说明本机有什么：overlay2 存储下 `Id` 是配置对象的摘要、不是 `repo@sha256:` 需要的 manifest 摘要，拿它注册 ECS 只校格式，RunTask 拉镜像时才 `manifest unknown`；containerd 存储下 `tag` 到 ECR ref 时就出现该仓库的 `RepoDigests` 条目，没有推送过也有（实测项 6）。推送之后的 `RepoDigests` 同样可能对不上：推送多平台索引而本机缺别的平台的内容时，仓库收下的是单平台 manifest，本机报的仍是索引的摘要，它在仓库里不存在，照它登记，用这个 variant 的云端提交在提交前的存在性核对里被拒（实测项 13 与「运行时与 preflight」节）。实测推送输出里的摘要在这一情形与单平台镜像下都等于仓库里的（同项），所以 digest 取自推送输出（「`push-worker` 流程」步 4）。
- **读本地引用的标注、再按名字打 tag 与推送**：本地的名字可变，读标注与打 tag 之间另一次构建把同名的本地 tag 改指别的镜像时，记录里是甲的协议版本与能力、推上去并注册的是乙，提交方据错的镜像作判断。所以先把本地引用打成目标引用、再对目标引用读标注（「`push-worker` 流程」步 2）：目标引用此后不随本地源名字的改动而变。
- **按不可变标识打 tag 并在取 digest 时核对目标引用**（读标注时取下镜像的不可变标识，按它打 tag 与推送，取 digest 时核对目标引用仍是它，不是即按推送失败结束）：为同一台机器上两条推送同时推同一个 variant 而设，这一情形不防：这样用没有意义，遇到自动化工具这样用时再处理（「与版本升级的交互」节「并发与失败」的已知边界）。
- **推送之后从仓库把镜像读回、核对内容、从仓库读标注**（按 tag 调 `BatchGetImage` 读 manifest，经 `GetDownloadUrlForLayer` 取回配置对象、从中读架构与两个标注，登记与记下的都取自读回的那一份；连带的做法：每次推送用这一次独有的 tag、tag 指向索引时登记其中那一份单平台 manifest 的摘要、请求带全四种可接受的媒体类型并核对返回文本的 SHA-256）：已证实的问题只有登记的摘要一项——多平台索引缺别的平台的内容时本机报的摘要不在仓库里（实测项 13），取推送输出即解决：实测推送输出里的摘要在单平台镜像与这一情形下都等于仓库里的（同项）。读回要给部署方加两项仓库读权限（`ecr:BatchGetImage`、`ecr:GetDownloadUrlForLayer`），多出若干步骤与各自的边界：独有的 tag 会在同一份镜像上累积到仓库的配额；按 variant 名的 tag 读，依赖仓库写成之后立即读到新值，没有保证（实测 9 次都读到新值，只是观测）；仓库还会按请求里可接受的媒体类型转换返回的 manifest，要另核返回文本。这些仓库行为的实测记在实测项 13，不作设计依据。
- **不可变 ECR tag（重推同名 variant 须先删）**：bugfix 不想改名是正当需求；replace 交给使用方，run 内一致性由 digest 引用的 revision 保证。
- **默认镜像 = 不带 variant 后缀的裸版本 tag，重推即覆盖**：会把 `base` 从映射里抹掉、退路只能重拉；默认改为指针，所有镜像都有 variant 名。
- **RunTask 传 family（取最新 ACTIVE revision）**：多 variant 下任何一次 push 都会劫持默认；一律显式 revision。缺失字段时也不回落 family，按定义违约标 error。
- **缺字段时回落模板 revision（`latest` 占位）**：全新 prefix 从未推过 `latest`，RunTask 拉镜像直接失败、错误拖到 Fargate 启动期；缺字段按定义违约标 error（默认指针解析也曾作为回落、已随「读侧不留兼容路径」撤除）。
- **revision 按 tag 引用镜像**：重推同名 variant 会让运行中 run 的后续 job 换镜像；按 digest 引用。
- **push-worker 抄「最近一次」revision 作模板**：最近一次可能是某个 variant 的、且模板改过后已过期；永远从 deploy 登记的模板 revision 复制。
- **模板 revision ARN 由 deploy 命令事后 `put_parameter`**：回滚留错值；stack 资源随事务。
- **deploy 改模板后不重派生既有 variant**：旧 variant 会一直跑旧 cpu/配置直到有人重推，且无人会想起来；重派生按模板 ARN 与映射所指 revision 是否仍为 ACTIVE 判定是否需要、幂等。
- **升级时自动把默认指针重置回 `base`**：抹掉团队意图；不重置，preflight 提示指向 push 或改用另一个已推送的 variant。
- **重派生/重推后立即删旧 revision**：INACTIVE 不能再起新 task（且注销后最多 10 分钟才生效），detached run 逐 job 起 task 会断；先打退休 tag、静默期满且无运行中 run 引用才删。
- **退休名单存 SSM 参数（JSON 列表）**：撑 4KB 标准参数上限（一轮连续推送即可撑爆）、与 revision 分家、对账要看两处；改为 revision 自身的 `gherkai:retired-at` tag。
- **清理靠定时任务**：多一个常驻资源与凭证面；机会式 pass 挂在 push-worker / deploy / delete-worker 上，滞留无害。
- **清理靠全表 Scan runs 表**：runs 表 `RETAIN`、无 TTL、无界增长；改 STATE 顶层属性 + GSI 的 Query（状态分组索引 `live` 分组的一次 Query，不 Scan）。
- **孤儿复用（从 family 里捡回未被映射的同配置 revision）**（曾采用，已取消）：推送与重派生在二元组不一致时，先按血缘 tags 在 family 里找同（模板 ARN、digest）、未被映射的 revision 写进映射，找不到才注册。它让「不被引用」的 revision 多出「可能被捡回去」这一种状态，判定与使用之间、摘 tag 与回收之间都会与清理竞争。已核到的几种：复用一方扫描 family 时它不带 tag，扫描结果被持有超过静默期之后才写映射，这期间清理已补打并把它收为成熟候选；一趟清理凭过时的映射，摘掉一个已离开映射、已是成熟候选的 revision 的 tag，使它重新满足复用条件、被另一条推送当场写进映射，而另一趟清理按此前收下的候选正要注销它——不需要谁停留，也不需要 AWS 读写延迟；早先版本留下的跨版本共用，在清理摘掉 tag 之后，经旧版本重推旧 digest 被复用而重新形成。每一种都要另加判据与再读才能收窄，且收窄不到互斥；判据本身也一再要补限定：不限 variant 时，variant B 的镜像 digest 恰与 A 相同就复用了 A 在用的 revision，A 换 digest 重推后它被退休回收、B 的映射悬空（真账户上遇到过）；不限版本时，升级后模板 ARN 不变，新版本推同一份镜像就复用旧版本映射着的 revision，两个版本的映射共用它，它的去留由另一版本的映射决定；排除已退休的则要靠 tag 区分「已判下岗」与「可捡回」。而它省下的只是一次 `RegisterTaskDefinition`：ECR 镜像层共享，多出的 revision 不被引用、由清理在静默期之后回收。取消之后，一个 revision 只剩两种状态：被映射引用，或不被引用、等待回收；进入映射只有发起注册的那条命令一条路，上面几种竞争连同为它们设的限定一起消失（「不变量」清理 pass 条「打 tag 与写映射的交错」「注册与回收的竞争」「已退休却仍被映射引用」三段）。
- **在 `list-workers` 里把「已退休、仍被映射引用」单独标出（另立一个 `reason` 取值，或加布尔字段 `still_mapped`）**：`retired-at` 归一之后这个状态不再需要保留，下一趟清理 pass 就摘掉 tag，单独标出只报告一个短暂的中间态，而它是在用的 revision、不是待清理的。另立 `reason` 取值另有两个问题：`reason` 是机读形态里的闭集，按它分支的消费方会把新取值当成未知；`reason` 说的是条目为何成了清理候选，「此刻哪个前置条件阻止回收」是另一个维度，混进同一枚举后再有别的阻塞条件就只能组合取值。`still_mapped` 曾被采用（没有随发行版发出），已随归一删除（「命令族」节）。
- **待清理条目的文本写成单一的解锁条件（如「删除旧版本 variant 后才会回收」）**：`delete-worker` 尚未提供，这句指向一个不存在的入口；何时回收取决于静默期、未到终态的 run 引用与下一次清理 pass 何时执行，写成单一解锁条件会让部署方误判。归一之后仍被映射引用的条目不再列出，这一条留作待清理文本的护栏。
- **`--set-default` 硬要求 variant 在每个引擎都存在**：与 preflight「按本 run 用到的引擎判」矛盾，单引擎团队要凭空推另一引擎镜像；改警告。
- **variant 缺失时静默回落默认**：静默换 step 集与「不判内容」矛盾；严格退 2 带提示。
- **push-worker 按发行版本比对**：发行版本不决定兼容，按它比对在格式没变时拦错、格式变了时放错；推送比云端后端接口版本，并要求命令行工具、镜像与后端三者的 worker 协议版本相同（下「推送时协议版本不同不拦、只打印提醒」条）。
- **同一 prefix 内双版本后端并行（蓝绿）**：Lambda / 模板 / 版本戳 / 数据版本参数都是单份，版本真源建立在此前提上；多版本用多 prefix。
- **variant 名、ECR 里的 tag 或记录键带发行版本**（如 `<发行版本>-<variant>`）：把「哪一套 step」与「哪一版协议」绑在同一个名字上，每升一个发行版本 variant 都要重推，哪怕协议没变；按发行版本的映射越积越多，回收要另立规则；提交时的解析还要取得发行版本，从源码直接执行的 CLI 取不到。PEP 440 的 `+`（本地段）与 `!`（epoch）也不在 tag 字符集内（`1.4.0.post3.dev0+28c1684` 直接 `docker tag` 报 `invalid reference format`，实测），要另做归一化。
- **对应关系记录按 worker 协议版本各存一条**：任一时刻每个 variant 只有一个当前镜像，提交用哪个镜像没有歧义，替换即退休，回收沿用现有规则；按协议版本各存一条就多出一个「当前」的维度，要另立旧协议版本的记录何时删的规则，回收又回到按版本越积越多的形态。它换来的只是协议版本加号的那次升级里可以先推新镜像、升级之后立即可用，而先推新镜像还要先放开跨协议的推送（下「推送时协议版本不同不拦、只打印提醒」条）；协议版本加号少见，那次部署本身已是要协调的升级，部署之后立即推送就能把自定义 variant 不可用的时段压到推送所需的时间；`base` 由部署在 cdk 之后同步，协议版本要变时容器引擎可用与基础镜像拉得到这两个前提在 cdk 之前核过（「`gherkai deploy` 的 worker 镜像四步」第 2 步）。
- **推送时协议版本不同不拦、只打印提醒**（好让协议版本加号的那次升级里，部署之前就能把新协议的镜像推进旧后端）：放行之后，执行推送的命令行工具要处理协议版本与自己不同的镜像，多出几条分支。能力标注的取值它校验不了：按自己的约定校验会拒绝合法的新协议镜像（新协议给 `targets` 加了取值），不校验就要把一份没人核过的对象原样记下；推送因此要按协议版本相同与否分情形校验。能力标注的键名与「值是 JSON 对象」要冻结成跨版本不变的约定，旧工具才搬运得了它：键名在新协议里改了，旧工具就读不到能力标注，按缺标注拒绝这份合法的镜像；若为它另设缺省、记下空对象，新的命令行工具提交时又会把镜像实际支持的目标判成不支持。加号纪律的护栏还要分清原样搬运与判定。换来的却不是更短的不可用时段：新协议的镜像登记之后、后端升级之前，用这个 variant 的提交在比协议版本那一步被拒，预先推送只是把 variant 不可用的时段挪到升级之前；部署之后立即推送，自定义 variant 不可用的时段就是推送所需的时间（`base` 的同步各步与 cdk 的先后见上「对应关系记录按 worker 协议版本各存一条」条）。所以推送要求命令行工具、镜像与后端三者的协议版本相同（「命令族」节「`push-worker` 与 `list-workers` 的前置」、「`push-worker` 流程」步 2），升级的次序固定为先部署、再推送（「与版本升级的交互」节）。
- **推送提到 cdk 之前**（stack 已在时，基础镜像同步的拉取、校验、登录与推送都在调用 cdk 之前，注册与写记录在 cdk 之后；首次部署另按一种次序）：要求镜像仓库在 cdk 之前已经存在，新增引擎或仓库改名的版本做不到（仓库由这次 cdk 建立）；推送之后的步骤或 cdk 失败时账户已有改动，推上去的镜像留在仓库里。所以推送留在 cdk 之后，协议版本要变时只把两项不改动账户的前提提到 cdk 之前核；cdk 之后的同步仍可能失败，作为已知边界写在同一处（「`gherkai deploy` 的 worker 镜像四步」第 2 步）。
- **推送与部署同步时执行镜像、问它的能力自述取协议版本与能力**：部署方的机器就得能执行 linux/amd64 镜像（arm 主机要靠仿真，没有仿真的 arm Linux 上 cdk 已经改了后端、同步却会失败），还要在部署方机器上加载使用方的 step 代码，另需执行的时限与失败的处置；标注是构建时写进镜像元数据的事实，读它只是推送之前一次已有的 `inspect`（「概念模型」节下「镜像标注」段）。备选的依据（实测）：取镜像自带的启动命令、接 `--capabilities`，在断网的容器里两个引擎都报得出（约 2 秒，不需要 AWS 凭证）；直接在镜像名后接 `--capabilities`，两个引擎都失败。
- **推送时不读镜像、用推送者 CLI 的发行版本代替镜像的协议版本**：定制镜像用的基础镜像可能与推送者的 CLI 不是同一版。
- **对应关系记录带上整份能力自述、提交时按它核对能力**：自述里有随环境变量变化的键（停止宽限下限、所用模型）与随定制层变化的确定性 step 清单，记下的是某一刻的缺省值，与云端实际执行时的值不同，是第二份事实源；记录只带能力标注里那几个构建时就确定的键（「概念模型」节下「镜像标注」段）。
- **云端提交时不核对镜像的能力，由 worker 建会话之前自检**：本机在执行之前以退出码 2 拒绝的 run，云端会写下记录、逐个 job 记 `precheck_failed`，同一种情形因执行方式不同得到不同的结果与说明；能力标注只多一个构建时写入、推送时读出的标注，就让两边用同一个判断，各自从能力自述或对应关系记录取能力对象（「概念模型」节下「镜像标注」段、「运行时与 preflight」节能力一项）。worker 建会话之前的自检保留，作最后一道（[0049](./0049-worker-capabilities-targets-keys.md) 决策 7）：标注与镜像里实际的 worker 不符时只有它照得出。
- **云端提交与 `list-workers` 信任推送时的校验、解读记录里的能力对象之前不另行校验**（理由是推送时协议版本相同的命令行工具已核过取值）：同一协议版本下各发行版本认识的可省键可以不同，推送方只核得了自己认识的键，记录里存下的是原样的对象。例如较新的发行版本加了一个有确定形态的可省键，较旧的命令行工具推送一个自定义层把这个键写坏的镜像，较新的命令行工具提交时若不校验，写坏的键就直接进入判断，可能误放行、误拒或抛出异常，而本机执行之前同一份对象会被契约校验拒绝。记录里的对象有没有按提交方的约定核过，就取决于推送方是哪个版本。所以解读的一方在解读之前按自己的契约校验（「概念模型」节下「镜像标注」段「读出」）。
- **task-def 指向 GHCR 直接拉基础镜像、不进 ECR**：运行时依赖 GitHub 可用性、出网流量、匿名拉取限额；基础镜像同步进使用方 ECR，运行时只拉自己账号的。
- **ECR 加 untagged 过期 lifecycle**：会静默删掉运行中 run 的旧 revision 按 digest 指着的镜像；回收与 `delete-worker` 同批设计。
- **孤儿的静默期从 `registeredAt` 起算**（曾采用，已取消）：`registeredAt` 是注册时刻，可能早于它离开映射很久；被替换的 revision 打 `retired-at` 失败（只警告不拦）后按孤儿处理，在替换它的那条命令末尾的 pass 里静默期就已满，「preflight 已解析、definition 尚未落库」的窗口失去覆盖，只剩引用检查一道保护。改为清理 pass 看到它不在任何映射里时补打 `gherkai:retired-at`（「不变量」清理 pass 条）。
- **另立只由清理 pass 打的 `gherkai:unmapped-at`、静默期从它起算，`retired-at` 只用于展示（以及当时孤儿复用的排除条件）**：两个时间 tag 并存，回答的都是「这个 revision 从何时起下岗」，语义重叠：`list-workers` 展示一个、回收看另一个，部署方看到的时刻不是决定回收的那个，两个 tag 的打与摘还要各守一套规则。另立它是为了保留「已打 `retired-at`、仍被映射引用」这一状态（摘掉仍在映射里的 revision 的 `retired-at` 会抹掉它），而这个状态除交错留下的短暂情形外不会出现，不需要保留（「不变量」清理 pass 条「已退休却仍被映射引用」段）。所以选定归一到 `retired-at`：孤儿第一次被识别时由清理 pass 补打。早先拒绝这一做法的理由有两条，现在都不成立：一是补打之后另一条推送可能把它写进映射，它便带着一个早于被映射的 tag——这由补打之后的重读与写映射一方的立即摘除处理，另立 tag 时需要的也是同一套处理（「打 tag 与写映射的交错」段）；二是摘掉会抹掉上面那个状态——它已不需要保留。
- **用 SSM 参数历史推算 revision 离开映射的时刻**：每个参数的历史有条数上限，要多一类 API 调用与权限；并发推送里先写者被后写者顶掉的情形，历史里找不到它离开的那一次写。打 tag 只依赖 revision 自身。
- **`_retire` 打不上 tag 就让 push-worker 失败**：失败时映射已经写好，命令失败撤不回，只给使用者一个错误的信号；并发推送产生的孤儿照样存在。
- **引用检查沿用以 `status` 为分区键的索引，两个非终态分区都没查到时隔几秒再查一遍**：`pending` 到 `running` 的换键仍在，复查之后漏检要求新索引项的传播超过一次分区读取加等待时长，对传播时长的余量只有秒级，远小于静默期给新建 run 留的约 1 小时；每当本趟真有东西要删，push 与 deploy 的末尾就多一段等待。
- **引用检查沿用以 `status` 为分区键的索引，候选第一次被确认无引用时打确认标记、相隔不少于 T 的下一趟再确认无引用才删**：换键与间隙仍在，漏检要求同一个间隙持续不少于 T；T 取到约 1 小时时，它对传播上界的依赖与选定方案的静默期（新建 run 的索引项须在约 1 小时内可见，两者都有）同一量级，差的是余量大小、不是有无。被拒在于其余几项：运行成本上，若只留 KEYS_ONLY 的列举索引，每趟要强一致读回全部非终态 run 的整个 STATE；协议上，多一个 revision 级的确认标记，回收多等一趟；余量取决于 T，T 取小了随之变小。比较见上「取舍依据」与 [0030](./0030-realtime-persistence-seam.md) 决定六被拒③。
- **清理不做就绪检查，靠「`Query` 失败即不删」保证安全**：依赖的是对建立中或已删除的索引做 `Query` 时的报错形态，这一点没有实测；若某种情形下返回的是不完整的结果，引用检查会判成「未被引用」。失败还被吞进不打印的回收结果，使用者看不到这次没有回收。
- **对每个候选 revision 逐个 `Query` 并以 `contains` 过滤**（曾采用，已取消）：过滤在读取之后应用，每个候选都要把整个非终态分区读一遍，读量随候选数成倍增长；改为每趟一次快照、在内存里求并集。

## 重议闸门

- 免容器引擎的基础镜像同步（registry 到 registry 直拷）→ deploy 机器不再需要 docker，零 step 团队零容器工具链；直拷时两个镜像标注从镜像仓库里的镜像配置读出，代替本地 `inspect`；podman 等其它容器引擎经同一口子接入。
- `delete-worker` 落地：套退休 tag + 静默期 + 运行中 run 引用检查；顺带清 variant 的 ECR tag、untagged 层与对应关系记录（届时才定 ECR 回收策略）。
- ARM64 / Graviton 省钱需求成真 → 多架构基础镜像 + 按 ZoneId 排除不支持的 AZ + variant 架构属性，方案已知、依赖侧静态核查已过；届时再评估复杂度是否值。
- 出现「一个 run 内不同引擎用不同 variant」的真实需求 → `--worker-variant` 扩成 `engine=name` 形式，是加法。
- Node 端 `module.registerHooks()` / 其它与镜像无关的 worker 运行时演进归 [0037](./0037-distribution-and-packaging.md)。
