# 0035. 本地应用测试：自动隧道把开发机上的被测应用暴露给云端浏览器

> **Status:** Partially-superseded-by 0051 —— 决策 4 的「凭据内嵌地址」被 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13 改为「令牌换 cookie、worker 预热一次」；随之改写的还有决策 1 的 `TunnelInfo` 形态与服务商能力要求、决策 2 的匹配规则（由子串替换精化为带边界的识别）、决策 5 的脱敏规则与「明确不脱敏」清单、「边界与不变量」里「core 对隧道无知」一条（加了 worker 的预热导航）并新增 definition 完整性不变量；其余决策不变。这一篇描述的设计有一部分尚未实装，code 跟上之前，实际行为以 code 为准。

## 背景与问题

浏览器跑在 AWS AgentCore（`aws.browser.v1`，CDP 驱动），此前隐含假设被测应用公网可达（wikipedia/example.com 级）。但本工具的主场景之一恰恰相反：**被测应用跑在开发者本机**——依赖只在本地环境齐备、开发到一半的东西不该为了测试走发布流程。矛盾固有：云端浏览器无法路由到开发机的 `localhost`。

## 调研结论（内联，自包含）

对四条候选路线做过源码级/文档级核查（Playwright 1.61 bundle、nova-act SDK 源码、AWS 文档与官方 samples、CDP 协议定义）：

**① CDP 请求拦截喂送**（worker 侧 `page.route()` 拦截远端浏览器请求、本地取内容、`Fetch.fulfillRequest` 喂回）——能力边界在协议层焊死：
- **WebSocket 不可拦截**：CDP Fetch 域对 ws upgrade 不产生 `requestPaused`，Network 域只有观测事件、无干预命令（devtools-protocol#147；Playwright `routeWebSocket` 是页面内 JS mock，真实连接仍从远端网络发起、够不到客户端 localhost）。
- **SSE/流式响应不支持**：`fulfillRequest` 的 body 是一次性 base64 全量；Playwright 流式 fulfill 至今是 open issue。
- Service Worker 发起的请求绕过 route（需 block SW）；redirect body 不可得；`https→http` 改写 URL 被禁（须同协议）。
- **性能税**：只要挂 route，Playwright 就强制 `Network.setCacheDisabled` 且 `Fetch.enable` 用 `urlPattern:'*'`——每个请求（含不拦的域）全量 pause 往返，body 以 base64（×1.33）过 WAN。实测参照：一个 4.9MB 静态站单次加载 ≈6.6MB 过 wss，且浏览器缓存全程失效。
- **Nova Act 侧执行模型脆**：SDK 自注册 `context.route("**")` 做 SSL 校验且从不 fallback（后注册先匹配 → 我们的 context 级 route 被静默遮蔽，只能用 page 级）；SDK 在 teardown/HITL 时 `unroute_all` 抹 context 级 route；Python sync route handler 跑在 greenlet 里、CDP 翻译在独立 node driver 子进程——被 pause 的请求要经「driver→stdio→greenlet 调度→stdio→driver」往返，而 greenlet 只在 worker 泵 Playwright 时被调度，**两次 act 之间的静默期请求会 stall**（与 [0024](./0024-worker-core-protocol.md) sync-over-greenlet 雷区同源）。

**② Playwright `exposeNetwork`**（官方 remote browser 访问客户端本地网络的方案，反向 SOCKS5）——机制：Playwright server 在浏览器同机起 SOCKS 代理、浏览器以 `--proxy-server=socks5://127.0.0.1:<port>` 启动、匹配规则的拨号经 client↔server 的 **Playwright 自有协议**连接 relay 回客户端进程执行。**对 AgentCore 三个环节全断**：托管浏览器启动 flags 不可配；浏览器同机没有我们的进程；relay 通道寄生在 Playwright protocol 上而我们只有 CDP 连接（`connectOverCDP` 无此 option）。

**③ AgentCore Browser VPC 模式**——自建 browser 资源支持 `networkMode=VPC`（2025-09 起，`vpcConfig{subnets,securityGroups}`，创建后不可改），可访问 VPC 内私有 IP（官方 sample 08 演示内网应用）。但**够不到开发者笔记本**：AWS Client VPN 对 IPv4 做 SNAT、VPC 侧无法反向寻址 client。它适配的是「被测应用本身跑在 VPC 内（云上开发机）」的场景——与本 ADR 的「本地应用」正交，留作口子（见被拒方案）。

**④ 出站隧道**（行业标准：BrowserStack Local / Sauce Connect / LambdaTest 全为此架构）——本机隧道 client 主动建 outbound 长连到服务商边缘，边缘分配公网 URL，浏览器流量经该长连回传、client 本地拨号。**本机零入站端口**；对浏览器而言被测应用就是普通公网 HTTPS 站点，故 HTTPS/WebSocket/cookie 天然全通、**双引擎零协议侵入**（不碰 Nova SDK 黑盒）、local/cloud 执行模式全通。Playwright `exposeNetwork` 本质是同构方案（relay 宿主不同）。AWS 原生无对应物（SSM 端口转发方向相反；IoT Secure Tunneling 两端 localproxy、不产 URL）。

**决策：走路线④。**

## 决策

### 1. `TunnelProvider` 可插拔口子（`gherkai-runtime` 组合根共享层），首个实现 = ngrok 官方 Python SDK

- 协议形状：`start(local_origin, *, closes_at, timeout_s) -> TunnelInfo`（没有关掉鉴权的开关：隧道模式下 definition 必带额外请求头与预热地址，见「边界与不变量」的完整性判据）（frozen dataclass `url` / `local_origin` 加本 run 的会话预热地址 `warmup_url`；`url` 就是干净的隧道地址、直接替换进 job 文本，不再内嵌凭据；`warmup_url` 含令牌、不进 repr——鉴权契约见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13）；`closes_at` 是本 run 的到点时刻（决策 3「边缘到点拒绝」），`timeout_s` 是起隧道的时限（下「起隧道的时限」一条）。返回对象的 `close()` 关闭会话：可以重复调用，自身有时限，关闭期间的任何异常都不外抛（含等待关闭时到达的中断，并发的第二次调用在等前一次期间到达的也是：前台 `run` 在退出时关闭会话，外抛会在终端上留下回溯）——会话随宿主进程消失，正常路径上的关闭不必成功才算收尾。返回对象同时持有 SDK 给出的监听对象：实测这个对象不再被引用、被回收之后隧道仍在线（下「实测依据」），持有它是为了不依赖这一行为。口子另有前置检查（下「前置条件」一条）。停止是宿主进程内的动作：隧道是宿主进程里的一个会话（决策 3），起隧道的进程就是宿主、也是唯一收尾的一方，不能由别的进程代做，所以 `TunnelInfo` 不带进程号，口子上也没有按进程号停止的入口。就绪判据 = SDK 建立监听的调用返回，**不另加就绪等待，也不做持续健康探活**：调用返回之后公网入口可能还有不到半秒答「端点不在线」（下「实测依据」），这一段由 worker 的会话预热覆盖——预热导航得到没有标记的页面时原地重导航、有界重试（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「预热页面有三种可见结果」一条）；隧道断的失败形态已够清晰（导航失败，见「边界与不变量」），不值守护复杂度。住 `runtime/gherkai_runtime/`（组合根共享层——cli/未来 WebUI 复用；core 与 worker 各知道什么，见「边界与不变量」里「core 对隧道无知」一条）。
- 选择参数：`--tunnel <provider>`（默认 `ngrok`，当前唯一实现）——机制与 flag 同期落，将来加实现零接口变化。
- **首发只做 ngrok**：服务商要具备四项能力：边缘能按路径、查询参数与 cookie 精确值分支，并返回带固定头的自定义响应（这两项是鉴权所需，见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13）；流量策略能按时刻拒绝（决策 3「边缘到点拒绝」）；会话建在宿主进程里、随进程消失（决策 3「寿命」）。ngrok 在免费层都具备（下「实测依据」）。免费层已实测的约束：每个策略的规则上限按账号不同（下「实测依据」里「六条规则」一条），`remove-headers` 是付费功能。不具备这几项能力的服务商不能作为隧道实现；前三项是流量策略的能力，策略不被接受时启动隧道 fail-loud。
- **本项是对 [0009](./0009-maximize-aws-hard-constraint.md)「最大化用 AWS」的显式例外**（按 0009 要求登记）：ngrok 是 AWS 外的第三方 SaaS，但「开发机 → 云端浏览器」的入站通道在 AWS 内实查无等价物（SSM 端口转发方向相反；IoT Secure Tunneling 两端 localproxy、不产公网 URL；AgentCore Browser VPC 模式够不到开发者笔记本，已评估并缓——见调研结论③与被拒/被缓方案；同一隧道也供 Device Farm 公共真机上的浏览器访问（[0048](./0048-test-targets-device-and-ui-kind.md) 第 8 条、[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13），真机进入私网要靠私有设备加 VPC-ENI，进的是使用方 VPC，同样够不到开发者笔记本）。例外面压到最小：经 `TunnelProvider` 口子隔离、隧道仅在显式给出 `--expose-local` 时起（「边界与不变量」第一条）、数据面只有被测应用自身流量（模型/浏览器/存储/编排仍全在 AWS 内）。
- **公网地址是 SDK 调用的返回值**：本 run 的流量策略随这次调用在内存里交给 SDK、不落盘。不启动 ngrok 可执行文件，没有代理进程、进程号、本机接口与日志文件；也不提供 ngrok 自带的本机查看页面与请求记录（SDK 1.8.0 的类型声明里没有这一类选项，宿主进程在本机有没有监听端口见「实测项」里「尚未核」的第 3 条）。SDK 自己经 Python 的 logging 发日志（被测应用连不上时每个请求一条警告，没有配置 logging 时写到标准错误），产品在导入 SDK 的那一处把它静默：这些不是产品的输出，使用者从 job 的失败证据里看到同一原因。静默的是 SDK 原生库用到的各族 logger：原生库里的日志目标经桥接成为 logger 名（`ngrok::tunnel_ext` 成为 `ngrok.tunnel_ext`），`ngrok` 之外还有 `muxado`、`rustls`、`tokio` 几族；漏掉一族，后台宿主就可能在回报之前往标准错误写字（决策 3「输出」）。免费层配额 1GB/月 + 2 万请求/月——页面资源全经隧道，重度使用可能碰顶，报错形态为 ngrok 侧 429/断流（文档预告）。
- **交给 SDK 的上游地址**：归一化之后的 origin（决策 2「取值先校验并归一化成 origin」一条），只把 scheme 转成小写：scheme 不区分大小写，映射按书写形式逐字匹配、所以保留原样（决策 2），交给隧道服务的那一份统一写法，判断是不是 https 也看这一份。https 的 origin 不校验上游证书（SDK 的 `verify_upstream_tls` 给假）：这一跳只在宿主与使用方指定、宿主可达的被测应用之间（通常是本机或使用方的内网），本机开发常用自签证书；实测同一个自签证书的应用，SDK 缺省校验时隧道能建成、每个请求都答 502，ngrok 可执行文件以缺省设置转发则答 200（下「实测依据」）。被拒方案：取 SDK 的缺省（校验）——自签证书的被测应用每个请求都失败，表现为被测应用不可达的假失败；另加一个选项让使用方开启校验——被测应用是使用方自己指定的地址，隧道暴露的风险在公网一侧、由边缘鉴权挡住（决策 4「隧道鉴权」一条），这一跳的证书校验不在这个安全面里，没有要使用方另作选择的情形。
- **起隧道的时限**：SDK 建立监听的调用是同步的、不带时限参数。宿主在一个守护线程里调用它、按 `timeout_s` 等待，到时即以下面第 4 种说法结束；迟到建成的监听由那个线程立即关闭，不留在宿主里无人关闭（关闭也失败时，三种宿主在起隧道失败之后都随即退出，会话随进程消失）。`timeout_s` 缺省 20 秒（实测建成在 2.2 秒以内），三种宿主都用缺省值、不设命令行选项，计入运行期限里 900 秒的一次性余量（[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策二）。产品自己的时限是必需的：连不上隧道服务时，macOS 上 SDK 约 5 秒自己放弃，Linux 上 80 秒内不返回。这个截法成立要两项前提，两个平台都已直接调用 SDK 核过（下「实测依据」）：SDK 等待网络时释放解释器锁，主线程照常运行、放弃等待能按时返回；被放弃的线程还阻塞在调用里时，进程照常退出。
- **前置条件**：装了 SDK 这个可选依赖（PyPI 上的包名 `ngrok`，使用者装 `gherkai[tunnel]`；extras 的落点、版本下限与导入时机见 [0037](./0037-distribution-and-packaging.md) 决策 2c）；令牌只取环境变量 `NGROK_AUTHTOKEN`，经 SDK 的 `authtoken_from_env` 取用，gherkai 不转交、不记录令牌的值（按 1.8.0 的接口声明，SDK 只有显式传入与这个环境变量两种取法，不读 ngrok 命令行工具的配置文件；只设这个环境变量即可起隧道，直接调用 SDK 与经产品代码都核过）；SDK 给出的说明在输出之前把其中出现的令牌值替换掉（实测无效令牌的说明里不带令牌，替换是对其余错误的防备）。机器上不需要 ngrok 可执行文件。两项前置在 `run` 与 `submit` 共用的前置检查里先查（补全运行定义、上传安装包之前），缺了即以退出码 2 结束，不上传、不起后台进程：配置错误与其余前置检查一样挡在开始执行之前。前置检查在给了 `--expose-local` 时真正导入一次 SDK，能导入才算装好，「没有装」与「装了但无法加载」分开报（下一条第 1 种）；起隧道时经同一处导入，同一情形在三种组合里给出同一句说明、同一退出码。被拒方案：只看包能否被找到、不导入——找得到却载入失败的情形查不出，失败推迟到起隧道的那一刻、经三种宿主各自的出口报出，三种组合的退出码与说明各不相同。两种后台宿主（决策 3）由同一个解释器、同一份环境、以不把当前目录放进模块搜索路径的方式启动（决策 3「本机 `submit`」里「启动方式」一条），`submit` 查到的就是它们会遇到的。
- **启动失败的说法按原因分**：产品语言，不带内部说法，都以退出码 2 结束（开始执行之前的问题，[0031](./0031-job-lifecycle-states-and-severity.md) 决定五「退出码 2」一条）；第 1、2 种在上一条的前置检查里查出，第 3、4 种在起隧道时遇到（哪个进程起隧道、`submit` 怎样得到原因并报出，见决策 3「三种组合的宿主与次序」）；不提结束 ngrok 进程（没有这个进程）。起隧道时的失败按 SDK 异常里的错误码字段分类（实测的形态是三项参数，第三项为 `ERR_NGROK_<数字>`），不解析说明文字：说明是服务商写给人读的英文，措辞与换行都可能变，错误码是结构字段：
  1. 没有装可选依赖：说明怎么装（安装 gherkai 时加上 tunnel 组件；已经装了别的组件的，要一并列出）。装了但无法加载（导入时出错）另给一句：带上导入的错误，请重新安装。
  2. 没有令牌：说明设哪个环境变量。
  3. 这个账号的隧道地址已经被另一条在线的隧道占用（只认错误码 `ERR_NGROK_334`，报错带上这个错误码）：等那条隧道下线之后再试。它通常属于另一个带 `--expose-local` 的 run，隧道随那个 run 的宿主退出而消失，run 已经是终态而隧道还在线一段时间是可能的（决策 3「寿命」）。在线的隧道也可能不是 gherkai 起的，所以报错说「这个账号上另一条在线的隧道」，不点名 run。报错不提 `gherkai settle-runs`：处置只改记录、不涉及隧道（决策 3「寿命」）。
  4. 其余：「隧道没有建成」，带 SDK 给出的原因（压成一行）与错误码。包括其余错误码（实测到的有无效令牌 `ERR_NGROK_105`、同时在线的会话数超限 `ERR_NGROK_108`、规则超限 `ERR_NGROK_2264`）、没有错误码的异常（连不上隧道服务时就是这种）与超时（上「起隧道的时限」一条；说明在时限内没有连上隧道服务，请确认本机能访问外网）。
- **实测依据**（ngrok 官方 Python SDK 1.8.0，Python 3.13；macOS 上新注册的账号与较早注册的账号各一次，Linux（内核 7.0，x86_64）上较早注册的账号一次；没有注明的三次结果相同）：
  - 宿主进程里的隧道带 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「边缘策略」的五条规则，macOS 上约 1 秒建成（1.09 秒、0.97 秒），Linux 上 0.29 秒；没有 cookie 的请求答 401，带令牌的预热请求答 200 并下发 cookie，带 cookie 的请求转发到本机应用。
  - 宿主被 SIGKILL 或 SIGTERM 之后，公网请求得到「端点不在线」（404，`ERR_NGROK_3200`）：macOS 上第一次请求就是，Linux 上第一次请求是连接被对端关闭、0.5 秒内转为 404。SDK 的发行包里没有 ngrok 代理的可执行文件，只有 Python 文件、一个原生扩展与一个 `ngrok-asgi` 入口脚本（查看 macOS 上装好的 1.8.0 的文件清单）。
  - 宿主主线程在忙循环里（占着解释器锁）时，8 个带 cookie 的请求全部正常转发。
  - 宿主被暂停（SIGSTOP）45 秒：公网请求先超时（客户端时限 20 秒），下一次请求（约 23 秒时）macOS 上得到 404，Linux 上先答 503（`ERR_NGROK_3004`）、27 秒时转为 404；恢复后 2 秒内重新在线、带 cookie 的请求照常转发。
  - 到点规则经 SDK 生效：到点之后带 cookie 的请求答 403。
  - 同一账号第二条隧道：新注册的账号上建不成，SDK 抛出的错误里带 `ERR_NGROK_334`（地址已在线）；较早注册的账号上建成、地址不同。
  - 六条规则：较早注册的账号上建不成，错误里带 `ERR_NGROK_2264`（每个策略至多 5 条）；新注册的账号上建成。
  - 请求耗时（macOS，新注册的账号，同一个本机应用，各 10 个请求，一次）：经 ngrok 可执行文件（3.39.13）成功 9 个、中位数 1.64 秒，经 SDK 成功 8 个、中位数 1.73 秒；没有成功的几个，原因没有记下。
  - 发行包（PyPI 上的 1.8.0）：许可 MIT 或 Apache-2.0，没有别的依赖，要求 Python 3.12 或更新；有 macOS（x86_64、arm64 与通用包）、Linux（glibc 的 x86_64、aarch64、armv7l，musl 的 x86_64、aarch64）、Windows 的预编译包，每个 3 到 7 MB，装好之后约 17 MB（macOS arm64）。本机后端的两个平台都有预编译包。
  - 直接调用 SDK 核到的另一组（较早注册的账号，macOS 与 Linux（内核 7.0）各一次，标了平台或次数的除外）：
    - 上游地址带 `http://` 前缀被接受；只设 `NGROK_AUTHTOKEN`、经 `authtoken_from_env` 取到令牌；建立监听的调用同步返回监听对象。
    - 在守护线程里调用建立监听的函数：调用期间主线程照常运行，最大停顿 macOS 2.5 毫秒（调用 1.63 秒）、Linux 6.1 毫秒（调用 0.35 秒）；线程结束之后监听仍在，别的线程可以关闭它。主线程只等 0.05 秒即放弃：0.055 秒与 0.051 秒返回，迟到建成的监听由那个线程关闭、公网一侧不在线。线程还阻塞在调用里时主线程返回，进程照常退出、`atexit` 照常执行。
    - 连不上隧道服务（服务地址指向不可达处）：macOS 上 5.03 秒后抛出两项参数、没有错误码的异常；Linux 上 80 秒内没有返回（由此有上「起隧道的时限」一条）。
    - 关闭（SDK 的 `disconnect`，线程里没有运行中的异步事件循环时同步返回）之后公网一侧答 404（`ERR_NGROK_3200`）：macOS 上约 1 秒之后，Linux 上随即。
    - 建立监听的调用返回之后紧接着发的请求：macOS 上 4 次都直接得到策略的回答；Linux 上 5 次里 2 次先答 404（`ERR_NGROK_3200`），0.10 秒与 0.47 秒之后转为正常。
    - 失败的异常形态：无效令牌与同时在线的会话数超限（短时间内连续起 6 个会话，第 6 个失败；Linux 上一次）都是三项参数，第二项是 ngrok 给的英文说明，第三项是错误码（`ERR_NGROK_105`、`ERR_NGROK_108`）。无效令牌的说明里不带令牌的值（格式不对的令牌、把真令牌倒过来的令牌各一次，macOS）。
    - https 上游、自签证书：SDK 缺省校验上游证书，隧道建成、每个请求答 502（上游证书无效）；关掉校验答 200（macOS；Linux 上请求早于入口上线，没有取到）。同一情形经 ngrok 可执行文件（3.39.13）以缺省设置转发，两个平台都答 200。
    - SDK 的日志经 Python 的 logging 发出，上游连不上时每个请求一条警告；没有配置 logging 时由缺省处理器写到标准错误。实测到发出日志的只有 `ngrok` 一族，其余几族取自原生库里的日志目标名，它们会不会发出警告没有核过。
    - 建立监听的调用返回的对象不再被引用、被回收之后，隧道仍在线（5 个请求都转发，macOS）。
  - 没有核过的：长时间运行、宿主断网之后重连、SDK 与 CLI 进程里别的线程长期共存（「实测项」里「尚未核」的第 3 条）。
- **用 ngrok 可执行文件做的实测**（macOS，ngrok 3.39.13，各一次）：较早注册的账号上五条规则的策略照常建立，到点之后所有请求答 403，带令牌的预热请求也是、不下发 cookie（按本机时钟，记下的第一个 403 是过点后 1.7 秒发出、2.9 秒收到回答的请求），六条规则以 `ERR_NGROK_2264` 启动失败；新注册的账号上地址是 `ngrok-free.dev` 下的一个固定域名、停掉再起不变，第一条在线时第二条以 `ERR_NGROK_334` 失败（只给第二条加 `--pooling-enabled` 同样失败，两条都加的没有核过），第一条的边缘规则已经到点而它仍在线时同样失败，六条规则能建成；较早注册的账号上每次启动的地址不同（`*.ngrok-free.app`）。较早注册的账号上另有一次经 `submit` 的实测（ngrok 可执行文件 3.39）：先后两个带 `--expose-local` 的 `submit` 各建立一条隧道、两条同时在线，后起的一条没有被拒。

### 2. URL 映射：feature 写原始地址，组装 job 时替换

- feature 里自然书写本地地址（如 `http://localhost:3000`）——它是用例的**逻辑事实**，不感知隧道。
- CLI 加 `--expose-local <origin>`：组合根起隧道拿到公网 URL 后，**在 job 组装（job-in 之前）把 step 文本**及其 argument（docString 内容 / dataTable 各单元格——URL 可能出现在任一处）**中的该 origin 替换成干净的隧道地址**——映射对 worker/引擎/AI 透明（AI 看到的就是可导航的公网地址；鉴权由 worker 的一次预热导航完成，见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13，step 文本里不出现令牌）。flag 值须与 feature 中书写形式一致（`localhost` vs `127.0.0.1` 不互认，大小写也须一致，文档写明）。
- **识别带边界，不是子串替换**：URL 字符集按 RFC 3986（unreserved、reserved 与 `%`；全部非 ASCII、空白、双引号、尖括号、反引号、竖线都不是 URL 字符；单引号是 RFC 3986 的 sub-delim、算 URL 字符，所以只在收尾标点里处理）；左边界为串首或非 scheme 字符（`[A-Za-z0-9+.-]` 之外），所以 `next=http://localhost:3000/x` 这类嵌在别的地址查询里的写法照常映射、`xhttp://…` 不映射；右边界为 origin 之后最长的连续 URL 字符串 R 为空、或以 `/ ? #` 开头、或全部由尾随标点 `. , ; : ! ) ] '` 构成。钉死的用例：`http://localhost:3000.evil/` 与 `http://localhost:30001/x` 不命中；`去 http://localhost:3000。`、`Go to http://localhost:3000.`、`(see http://localhost:3000)`、`打开http://localhost:3000/a页面` 命中。step 正文、DocString、表格单元格各自独立套用，一段文本可以有多处命中。曾是裸子串替换：`http://localhost:3000` 会命中 `http://localhost:30001/x`。
- **取值先校验并归一化成 origin（`scheme://host[:port]`），不做隐式截断**：末尾恰好一个 `/` 时去掉（origin 语义没有歧义，这种写法也常见）；含路径、查询串、片段、用户信息、http 与 https 之外的 scheme、空主机、非法端口（冒号之后为空，或不是 1 到 65535 的整数）或空白的取值，在 plan / run / submit 的入口、启动隧道之前以退出码 2 拒绝，提示只写到端口为止、路径写在 step 里；大小写原样保留（映射按书写形式逐字匹配；交给隧道服务的上游地址只把 scheme 转成小写，见决策 1「交给 SDK 的上游地址」一条）。不归一化时的失败形态：取值为 `http://localhost:3000/` 时，`http://localhost:3000/login` 在 origin 之后剩下 `login`，按上条右边界规则判为不命中，job 文本里仍是本机地址，云端浏览器导航失败、表现为假失败且已经计费；取值恰好是 step 地址的前缀，逐字符对照也看不出原因。被拒方案：截断到 origin——截掉路径会静默改变使用方的意图。判据与归一化只在 `tunnel.normalize_origin` 一处，CLI 入口、`NgrokTunnel.start` 与 `map_origin_in_jobs` 共用。
- **origin 语义 =「跑 CLI 的机器可达」的任意地址，不限 localhost**：局域网/内网另一台机器上的应用（如 `http://192.168.1.50:3000`）同样支持——ngrok 的隧道会话本就是转发器，upstream 可为任意本机可达 host:port；目标机器**零配置**，唯一前提是 CLI 机器 → 目标地址网络可达（隧道宿主始终在 CLI 机器，含 cloud submit 的守护进程，决策 3；CLI 机器关机时见「边界与不变量」里「本机关机或宿主进程崩溃时隧道随之消失」一条）。flag 名中的 "local" 取「CLI 视角的本地网络」义。
- **`plan` 输出替换前的原始地址**：plan 是纯本地零副作用预检，隧道 URL 是运行时产物（每 run 起一条隧道，地址由服务商在起隧道时给出；ngrok 上不指定地址时按账号不同：新注册的账号落在 `ngrok-free.dev` 下的一个固定开发域名上、停掉再起不变，较早注册的账号每次启动的地址不同（`*.ngrok-free.app`），实测见决策 1「用 ngrok 可执行文件做的实测」），plan 时起隧道既违背「不连外」也无意义。给了 `--expose-local` 时 plan 在输出中**标注**该 origin 将经隧道映射（可见性，零副作用）。

### 3. 执行方式与执行后端的三种组合全支持；隧道建在宿主进程里，宿主按组合分三形态

给出 `--expose-local` 时，隧道是宿主进程里由 ngrok 官方 Python SDK 建立的一个会话（决策 1），把被测应用转发到一个公网地址，带本 run 的流量策略（规则见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「边缘策略」，其中到点拒绝那一条的时刻见下「边缘到点拒绝」）；策略怎样交给 SDK 见决策 1「公网地址是 SDK 调用的返回值」一条。

| 组合 | 隧道宿主 | 隧道何时消失 |
|---|---|---|
| 前台 `run`（只有本机后端，[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 A） | 执行它的 CLI 进程 | 宿主怎样退出都随之消失（下「寿命」），正常路径上执行完先关闭会话再退出；公网入口到运行期限加 300 秒在边缘关闭（下「边缘到点拒绝」） |
| 本机 `submit` | 后台推进进程（`submit` 以新会话启动它） | 同上；正常路径上推进到 run 结束之后先关闭会话再退出 |
| 云端 `submit` | 本机的隧道守护进程（`submit` 以新会话启动它） | 同上；守护进程轮询 run 的状态，到终态或到运行期限加 300 秒时关闭会话、退出（下「云端 `submit`」） |

- **寿命**：宿主怎样退出（正常结束、未捕获的异常、被任何信号结束），隧道都随进程消失；正常路径上宿主先显式关闭会话。没有拆隧道的记录或命令：`status --wait` 与 `settle-runs`（[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策八）不涉及隧道；处置只改记录（0054 决策七「处置只改记录」一条），被结束的 run 的宿主发现之后照常退出，隧道随之消失。前台 `run` 与本机后台推进进程怎样发现 run 已结束，见 0054 决策五「执行方服从记录」一段；云端守护进程何时退出，见下「云端 `submit`」一条里「守护进程轮询 run 的状态」那一句。所以 run 已经是终态而隧道还在线一段时间是可能的（云端守护进程读不到 run 的状态时要到运行期限加 300 秒；宿主被暂停时要等它恢复）。理由：隧道的寿命就是宿主进程的寿命，由操作系统给出，与生命期锁同一个思路（0054 决策三的理由）：宿主怎样退出隧道都随之消失，没有另一样东西可留下，也就不需要记下它、找到它、核对它再拆（被拒方案「隧道由独立的 ngrok 代理进程持有……」）。实测见决策 1「实测依据」。
- **三种组合的宿主与次序**（创建时刻的取法见 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策二「落点是运行定义」一段）：
  - **前台 `run`**：执行它的 CLI 进程。做完各项检查与补全运行定义之后，取创建时刻，起隧道，生成运行定义，建 run（生成记录时，[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策三「谁在何时拿」），执行，退出。起隧道期间被 Ctrl-C 打断：一句说明没有开始执行、退出码 130、不打回溯，与本机 `submit` 在同一时段被打断相同（那里是一句说明加 130）。建 run 的那一段（建 run、打开 worker 日志、建事件库）被打断同样以 130 结束、不打回溯，做法按建 run 的调用是否已经返回分两种：已经返回时 run 已经建成，这个进程持着生命期锁、就是这个 run 的推进器，由它自己做结束写（说明取 [0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节说明表「使用方中断」一行；全部 job 还是 `pending`，记 `skipped`），写成之后生成报告，说明给出 run 的标识、说这个 run 已因中断记为已结束；还没有开始建（或 `--no-report`）时与起隧道期间是同一句。结束写本身失败时按 [0030](./0030-realtime-persistence-seam.md) 决定七运行期落库失败的说明结束，退出码仍按信号取。建 run 的那一次调用期间推迟 SIGINT（[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策三），期间按下的 Ctrl-C 在它返回之后处理，run 这时已经建成，按前一种做。理由：这与执行期间被中断是同一种情形，只是已启动的 job 数为零；推进器还在，由它按真实的来路结束，记录里的原因就是中断。被拒：让这个 run 停在 `pending`、说明里请使用者另用 `settle-runs` 把它记为已结束——多一步手工操作，记录里的原因也只剩「执行这个 run 的 gherkai 进程已退出」，比真实原因笼统。
  - **本机 `submit`**：后台推进进程。`submit` 做完计划与补全运行定义（各项检查、账号比对与安装包上传都在这之前；各项检查里含对报告目录的那一次边界检查，不过即以退出码 2 结束、不启动后台推进进程，见 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策四「边界检查」一条）之后以新会话启动后台推进进程，经它的标准输入把建 run 所需的输入一次交给它，另给它一条通向 `submit` 的回报管道；标准输入的写端只在 `submit` 手里，一直开到收到回报。后台推进进程依次取创建时刻、起隧道、生成运行定义、查 `submit` 是否还在（下「`submit` 在收到回报之前退出或被强杀」一条）、建 run（含边界检查；在暂存目录上取锁，写好运行定义与运行态之后改名成 run 标识，[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策三「谁在何时拿」、决策四「边界检查」一条）、装配推进所需的各部分（含建事件库）、打开 `reconcile.log`，回报结果（建成了：run 的标识与公网地址；没有建成：原因与退出码，退出码见 [0031](./0031-job-lifecycle-states-and-severity.md) 决定五「退出码 2」一条），然后推进到 run 结束、退出。装配与打开日志放在回报之前：它们在回报之后失败时，使用者已经看到「已提交」。`submit` 收到回报之后输出结果并退出：建成时输出进度行（stdout 只有 run 的标识），退出码 0（已提交，0031 决定五）；没有建成时报出原因、以回报里的退出码结束。由此本机的一个 run 从建立到结束都在一个进程里，前台是 `run` 的进程，后台是后台推进进程，步骤与次序相同。由后台推进进程自己建 run 的理由与锁怎样持有，见 0054 决策三「本机后台由后台推进进程自己建 run」一条与「谁在何时拿」。
    - 启动方式：两种后台进程（后台推进进程与云端的隧道守护进程）以不把当前目录放进模块搜索路径的方式启动（Python 的 `-P`）。它们继承使用方的项目目录，不这样启动时项目里与标准库或 SDK 同名的文件会被优先导入，前置检查查到的与宿主实际导入的就不是同一个（决策 1「前置条件」）。
    - 输出：后台推进进程回报之前的输出接在 `submit` 的标准错误上（`submit` 这时还在等，崩溃的原因直接显示在终端；run 目录这时可能还不存在），回报之后写进 run 目录里的 `reconcile.log`。回报之前不启动子进程，也不往标准错误写字（崩溃的回溯除外）：子进程会继承接在 `submit` 标准错误上的描述符，调用方经管道捕获 `submit` 的输出（如 `out=$(gherkai submit …)`）时，要等那个子进程退出才读到文件结束（本机进程实测：回报之前起的子进程还在时，调用方一直读不到文件结束）。回报之后把标准输出与标准错误改接 `reconcile.log`、标准输入改接空设备，之后起的 worker 继承的是日志。回报管道的写端不可继承，由进程退出关闭、不在回报之后另行关闭：回报之前崩溃时，回溯先写到 `submit` 的标准错误，`submit` 之后才读到文件结束，它那句「它退出之前如果有输出，原因在上面」才成立；说明写成有条件的，因为被信号结束的后台进程不留输出。
    - 失败的出口：起隧道之后的各个失败出口都先关闭会话、再回报：回报一到 `submit` 就退出，使用者可能立刻重试，新注册的账号上这条会话还在线时，重试会以决策 1 启动失败的第 3 种说法失败。建 run 之后装配或打开 `reconcile.log` 失败：记录已经写下，后台推进进程以退出码 2 回报「记录已写下、还没有开始执行、停在 pending」，说明里给出把它记为已结束的 `settle-runs` 整条命令、请使用者之后重新提交（与前台 `run` 在同一处失败时同一句，只是「重新执行」换成「重新提交」，[0030](./0030-realtime-persistence-seam.md) 决定七「失败退出码分层」），不推进它，随后退出。
    - `submit` 在收到回报之前退出或被强杀（如按下 Ctrl-C；后台推进进程在另一个会话里，收不到终端的信号）：后台推进进程在建 run 之前查一次 `submit` 交来的标准输入——对这条管道的读端做一次非阻塞读，读到文件结束即 `submit` 已不在——不建 run、不输出，关闭会话、退出；`submit` 在交完输入之前就不在（读输入时读到文件结束）时同样不建 run、不输出。理由：没有人收到 run 的标识，使用者多半是要放弃这次提交；在建 run 之前停下，没有记录要收拾。这个判据两个平台同义（本机进程实测：`submit` 被 SIGKILL 或因 SIGINT 退出之后读到文件结束，还在时读不到数据、也不阻塞）。被拒方案：对回报管道的写端轮询——读端关闭之后写端上报什么随平台不同（macOS 上实测不注册事件时什么都不报，Linux 按文档报错误事件）。`submit` 这一侧：从启动后台推进进程到收到回报之间被 Ctrl-C 打断，以 130 结束，并说明已停止等待提交结果、这次提交可能仍会建立 run 并执行（界线是上面那一次检查：查到 `submit` 已经退出即不建立、自行退出，查过之后照常建立并执行），请使用者先用 `list-runs` 确认，再决定是否重新提交。说明不写成「还没有建立的不再建立」：使用者据此立刻重新提交时，查过之后才被打断的那一次仍会建成，得到两份运行。中断落在已经收到「建成」的回报之后、输出结果之前时，说 run 已经提交、提交命令随后被中断，给出查进度的命令，与云端建 run 之后被打断同一句。
    - 这次检查之后 `submit` 才退出：run 已经建成，回报写不出去，后台推进进程照常推进，只在 `reconcile.log` 记一句。理由：建成之后它就是一个有推进器、持着锁的普通 run，与 `submit` 收到回报之后、输出之前被强杀相同；要在这时结束它，结束写就得多一种来路与说明（[0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节），只为建 run 的那一刻。它照常出现在 `list-runs` 里。
    - 后台推进进程在回报之前退出：`submit` 读到回报管道关闭而没有回报，报错、退出码 2，说明 run 可能已经建成而没有推进器，给出不带 run 标识的 `settle-runs` 整条命令（`submit` 这时不知道 run 的标识）：这条命令把报告目录里推进器已不在的 run 记为已结束（0054 决策六；锁随进程释放，按 0031 决定三「结束写」小节说明表「锁拿到了」一行），同时清理建 run 中断时留下的暂存目录；处理好原因之后重新提交。退出落在改名成 run 标识之前时没有建成的 run，报告目录里可能留下这次的暂存目录（它不是 run，由不给 run 标识的 `settle-runs` 清理，0054 决策八）；落在改名之后、回报之前时 run 已经建成而没有推进器，即上面那句说明所指的情形。`submit` 分不出是哪一种，所以说明写「可能已经建成」。
    - `submit` 不另设等待时限：起隧道的时限是 `TunnelProvider` 的 `timeout_s`（怎样截住 SDK 的调用见决策 1「起隧道的时限」一条），其余是本机操作；后台推进进程被暂停时 `submit` 一直等，使用者结束 `submit` 即落到「`submit` 在收到回报之前退出或被强杀」与「这次检查之后 `submit` 才退出」两条之一（看暂停落在它查 `submit` 是否还在之前还是之后）。
  - **云端 `submit`**：本机的隧道守护进程。云端的推进器在云上、读不到本机起的隧道，本机必须另有一个进程持有它。`submit` 先过云端的各道闸并补全运行定义（版本、资源 preflight、worker variant、设备请求与安装包；这些闸在生成运行定义之前执行，所需的 job 与有没有隧道从 job 与有没有给 `--expose-local` 取，[0037](./0037-distribution-and-packaging.md) 决策 7 的缺戳例外同样「在生成运行定义之前按各 job 的目标与命令行参数、对整次 run 判断」），再取创建时刻、算出运行期限，以新会话启动守护进程（启动方式同本机，上「启动方式」一条），经它的标准输入一次交给它到点时刻（运行期限加 300 秒）、origin、隧道服务、runs 表、region 与 profile，另给它一条回报管道；守护进程起隧道，把公网地址与预热地址经回报管道交给 `submit`，并保持回报管道的写端打开（写端只在它手里，`submit` 据此判断它是否还在）；`submit` 生成运行定义、建 run，经标准输入把 run 的标识交给守护进程；守护进程等 run 的标识也以到点时刻为上限，等待期间读到文件结束（`submit` 没有交出标识就关闭了标准输入：建 run 失败、退出或被强杀）或过了到点时刻即关闭会话、退出；收到标识之后，守护进程轮询 run 的状态，到终态或到运行期限加 300 秒（墙钟，[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策二「检查用墙钟」）时关闭会话、退出。守护进程在收到 run 的标识之前不启动子进程、不往标准错误写字（崩溃的回溯除外，理由同本机「输出」一条）。
    - 轮询：间隔 5 秒。读不出或读不到这个 run 时继续轮询，按情形的种类记一句（读不到、读失败、恢复读到），种类变化时记一句、同一种类连续出现不重复记，判断只看种类、不看说明文字：这种情形可能一直持续到到点时刻，每轮记一句只会淹没日志。
    - 守护进程起不来隧道或在回报之前退出：`submit` 报出原因（后者是回报管道关闭）、退出码 2，没有建 run。建 run 失败（云端不可达或条件不成立）：`submit` 先关闭守护进程的标准输入（守护进程读到文件结束即关闭会话、退出），等它退出（它一直开着回报管道的写端，退出时读端读到文件结束），最多等关闭会话的时限加 1 秒、到时不再等，然后报错、以退出码 2 结束；先关会话再报错，理由同本机「失败的出口」一条。被 Ctrl-C 打断的出口只关闭标准输入、不等待。
    - 与本机同一条规则，建 run 的一方在建 run 之前查一次对端是否还在：`submit` 在装配好存储之后、紧挨建 run 对回报管道的读端做一次非阻塞读（判据同本机），读到文件结束即守护进程已不在，不建 run，报错、退出码 2。这次检查之后守护进程才退出：run 已经建成、由云端推进，`submit` 交出标识时写不进守护进程的标准输入，照常输出 run 的标识、退出码 0（已提交，[0031](./0031-job-lifecycle-states-and-severity.md) 决定五），另在 stderr 说明隧道已不再可用、这个 run 里要访问被测应用的 job 会失败；与守护进程在 `submit` 退出之后才没了相同（「边界与不变量」「云端的守护进程没了」一条）。理由（本机与云端相同）：另一端已经不在时不建，免得留下一个没有人知道、或一开始就没有隧道的 run；查过之后的那一刻不另设防，它与建成之后才没了是同一种情形。
    - `submit` 在交出 run 的标识之前退出或被强杀：守护进程的标准输入随之关闭，它关闭会话、退出；这时 run 已经建成的，由云端照常推进，要访问被测应用的 job 会失败（同上一条）。被 Ctrl-C 打断时 `submit` 以 130 结束：等守护进程回报时被打断，说明没有建立 run；从建 run 到交出 run 的标识之间被打断（给不给 `--expose-local` 都一样），标准输出不输出（下「`submit` 的标准输出与退出码」一条），按建 run 是否已经返回给两种说明——已经返回的，说 run 已经提交、提交命令随后被中断，给出查进度的命令；中断落在建 run 里面的，说 run 可能已经写入云端，给出确认用的命令；带隧道时两种都说明隧道已不再可用、这个 run 里要访问被测应用的 job 会失败（只说不再可用，不说原因与时刻：守护进程可能在中断之前已经退出，它关闭会话也可能在 `submit` 退出之后才完成）。理由：建 run 是数次网络往返，中断落在里面时记录可能已经写下、也可能没有，只留下回溯的话使用者不知道有没有提交。
    - 守护进程的存活上限由运行期限推出（到运行期限加 300 秒；等 run 的标识与轮询两个阶段都以它为上限；这个上限不依赖一次读何时返回：装配存储与读 run 状态在另一个线程里做，轮询按轮询间隔与距到点时刻的余量里较小的一段分段等这次读的结果、每段之后重读墙钟，墙钟过了到点时刻而读还没有回来即放弃它、关闭会话、退出，一次读没有回来之前不另起一次读——取凭证的外部助手不带时限，它不返回时一次读可以一直阻塞。被拒方案：给连接与读取设时限并限定重试次数，它管不到取凭证的外部助手，上限仍取决于一次读何时返回），没有另外的公式，使用者也不另给存活时长：调大没有意义（期限之后 job 已被截断，0054 决策二第 2 条；公网入口在边缘到点关闭，下「边缘到点拒绝」），调小会在 run 未完时断掉隧道（被拒方案「保留 `--tunnel-ttl`，只允许调小」）。
    - 守护进程对 SIGTERM、SIGHUP、SIGINT 取缺省处置、不转成退出：进程结束，隧道随之消失（实测见决策 1「实测依据」）。两种后台进程的入口进门即把这三个信号设成缺省处置、不装处理器：被设为忽略的处置会由子进程继承（如经 nohup 启动的 `submit` 把 SIGHUP 设成了忽略），不恢复时对它发这个信号结束不了它。SIGINT 一并取缺省处置，是因为后台进程在另一个会话里、收不到终端的 Ctrl-C，显式发给它的 SIGINT 与 SIGTERM 一样只是结束这个进程：后台没有「使用方中断」这个入口（留下的 run 由处置结束，0054 决策八；取消一个后台 run 的命令不在本篇），也就不让它在解释器里变成中断、走到一半的收尾。日志：回报之前接在 `submit` 的标准错误上，收到 run 的标识之后写进系统临时目录里的 `gherkai-tunnel-watch-<run_id>.log`；日志打不开时照常持有隧道、不留日志：持有隧道是它唯一的职责，日志只是旁证。
  - **`submit` 的标准输出与退出码**（两种 `submit` 相同）：以 0 结束的路径上，最后一步在标准输出写出 run 的标识，标准输出只有它；`submit` 自己给出非零退出码的路径上（含被 Ctrl-C 打断的 130）不写标准输出。开始写出标识之前，`submit` 把 SIGINT 的处置设为忽略、直到进程退出：之后到达的 Ctrl-C 不改变结果，照常以 0 结束；这一步放在接住中断的范围之内，已经到达、还没有处理的中断仍走 130 的出口。理由：这时 run 已经建成，标识即将交给调用方，已经写进管道的字节收不回来，所以结果在写之前定下。这是做法，不是对结果的保证：被信号结束的进程（SIGKILL，或缺省处置下的 SIGTERM）没有自己给出的退出码，它的标准输出里有没有标识不在此列。已知边界：调用方不读标准输出、管道写满时，写出标识这一步会阻塞，这期间 Ctrl-C 已被忽略，要结束它得用别的信号；调用方恢复读取之后照常以 0 结束（真实管道实测）。
  - **公网地址那一行**：三种组合同一句——隧道已建立，给出 origin 与公网地址，说明访问受本次运行专用的会话保护、持有隧道的 gherkai 进程退出时隧道随之关闭；前台由执行它的进程在建成隧道时给出，两种 `submit` 由 `submit` 在收到回报之后给出。不打印存活时长：隧道的寿命就是宿主进程的寿命（上「寿命」），没有另一个时长可报。
- **边缘到点拒绝**：
  - 流量策略里最前面一条是到点拒绝，规则本身（条件、回答与所用的 ngrok 变量）见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「边缘策略」。时刻是这个 run 的运行期限加 300 秒，与 [0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策六「可以处置的条件是两者之一」一条里的期限加 300 秒是同一个时刻。三种组合都带，`run --no-report` 同样（它也有运行期限）。
  - 时刻怎样得到：创建时刻的取法（何时取、期限与策略里的时刻怎样由它算出）见 0054 决策二「落点是运行定义」一段；三种组合各由哪个进程在哪一步取，见上「三种组合的宿主与次序」。
  - 它给出什么、不给什么（这是做法，不是保证）：到点之后公网入口在 ngrok 边缘关闭，不依赖本机的任何进程，带令牌的预热请求同样被拒；到点之后宿主如果还在，会话还在，请求一律答 403。令牌与 cookie 除随隧道关闭失效之外（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13），由这条规则到点失效，对正常结束的 run 同样起作用。时钟的边界见「边界与不变量」「边缘规则按起隧道那台机器的时钟」一条。
  - 规则条数：策略有几条、为什么不多于这个数，见 0051 决策 13「边缘策略」（`tunnel.POLICY_RULE_LIMIT` 是 5）；各种账号上每个策略的规则上限见决策 1「实测依据」里「六条规则」一条。ngrok 的免费套餐说明页写的是「Traffic policy rules (per policy) 15」，与较早注册的账号上看到的不同。
  - 理由：宿主一直不退出时（被暂停之后恢复、卡在别处），公网入口照样到点关闭；ngrok 自己没有到期释放，免费套餐说明页（`https://ngrok.com/docs/pricing-limits/free-plan-limits/`）原话「Free endpoints have no timeout—they can stay online indefinitely. To keep one running unattended, run it as a background service.」。时刻对齐到 run 而不是 job：一条隧道只有一份策略、启动时定下；各 job 什么时候开始在那时还不知道；运行期限已经是每个 job 截止时刻的上限（0054 决策二第 2 条）。运行期限加 300 秒之外不另加余量。
- cloud submit 的语义澄清：「提交完就走」=不阻塞 CLI，**不等于关机**——机器继续开着时本地应用与隧道均可用，云端 Lambda 链驱动的浏览器经隧道访问本机应用完全成立。但本机关机时隧道随之消失，云端的 run 此后怎样，见「边界与不变量」里「云端的守护进程没了」一条；所以 submit 时打印明示（守护进程日志落点 + 「本机需保持开机联网直到 run 终态」），把例外变成明示边界而非静默失败。

### 4. `ngrok-skip-browser-warning` 头恒注入（仅隧道模式、仅桌面浏览器）

- ngrok 免费层对浏览器返回 interstitial 警告页（对自动化致命）；带任意值的 `ngrok-skip-browser-warning` 头即绕过。付费户带着无害（服务端忽略）→ 不做付费检测、隧道模式下恒注入。设备浏览器（Android Chrome、iOS Safari）没有注入请求头的通道；四台公共真机实测都没有出现警告页，若服务商改变行为则设备目标在隧道模式下要求付费层（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13）。
- 注入通道（通用形状「额外请求头」，全链路单一事实源在此）：组合根把 header 表填进 **`RunMeta.extra_http_headers`**（definition 层字段，tuple pairs；落盘为 dict、键序在写端排序规范化，空表与 `None` 同义、落盘为 null——键集随结构版本固定，[0037](./0037-distribution-and-packaging.md) 决策 7——随 META 落盘 DDB/文件）→ 推进器（本机后台推进进程 / 云端推进 Lambda）据它重建 engine → engine adapter 注 `GHERKAI_EXTRA_HTTP_HEADERS` env → worker 在 browser context 上 `setExtraHTTPHeaders`——纯 CDP 命令、无回调，**不触碰 Nova 的 route/greenlet 雷区**。两个 worker 各有一处注入点（URL 替换那半边才是 worker 零改动）。**载体为什么是 definition 而非只走 env**：cloud detached 下起隧道、生成运行定义的本机进程与重建 engine 的 Lambda 不同进程，env 传不过去，header 表必须随 META 持久化。`GHERKAI_EXTRA_HTTP_HEADERS` 与 `GHERKAI_SESSION_WARMUP_URL` 同属组合根拥有的 worker env，守同一条「有值显式注、无值显式清」的不变量（宿主继承的同名值不得越过 definition），清单与细则见 [0037](./0037-distribution-and-packaging.md) 决策 4。
- **隧道鉴权：默认开启，方案 = 令牌换 cookie、worker 预热一次**（契约全文在 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13，此处只记与本篇的接口）。组合根每 run 生成访问令牌与会话 cookie 值，写进本 run 的流量策略（策略不落盘、没有日志文件，见决策 1「公网地址是 SDK 调用的返回值」一条）。边缘在哪条路径凭什么放行、不放行时答什么，见 0051 决策 13「边缘策略」；worker 对哪些目标、在什么时候导航预热地址，怎样在页面标记上确认，见 0051 决策 13「做什么」与「预热页面有三种可见结果」两条。安全面：每 run 一换的令牌与 cookie、隧道随宿主进程消失（决策 3「寿命」）、令牌与 cookie 到点失效（公网入口到运行期限加 300 秒在边缘关闭，决策 3「边缘到点拒绝」里「它给出什么、不给什么」一条）、精确比对；隧道地址不算保密面（地址怎样分配见决策 2「`plan` 输出替换前的原始地址」一条），可达性全靠边缘鉴权。**对本篇的影响**：step 文本里只有干净的隧道地址，业务地址（`page.url()`、失败消息、AI 提示）里不再有 userinfo 形态的凭据；预热地址里的令牌落在哪些地方，见 0051 决策 13「令牌与 cookie 的残留面」一条，gherkai 自己的出口由决策 5 的规则 ② 盖住；原方案「文档地址带 userinfo 使被测应用用绝对地址调 `history.pushState` 时抛 SecurityError」这类隧道模式特有的假失败随之消失。
  **曾用方案（被取代，护栏）**：URL 内嵌 basic-auth 凭据（`https://user:pass@host`，经 ngrok 流量策略的 basic-auth 在边缘拦截，靠浏览器按域 auth cache 带后续请求）。它在桌面 Chromium 与 Android Chrome 成立，但 iOS Safari 不采用地址内嵌凭据、改弹系统级鉴权表单且网页上下文看不到；凭据还会进入 job 文本、AI 提示、引擎原生产物与 `page.url()`，并触发上述 `pushState` 假失败。
  被拒候选（防重复调研）：② extra headers 注 `Authorization`——**全域广播**给页面加载的所有第三方域，泄面严格大于 cookie，且设备浏览器没有注入请求头的通道；③ CDP Fetch 域 authChallenge——需开 Fetch 拦截、`authRequired` 事件同样要 handler 响应，撞 Nova 的 greenlet/node-driver 泵动问题（见上「调研结论①」）；④ 令牌作为查询参数写进 step 文本——映射器无法区分导航地址与地址断言的正则参数，令牌又会进入 AI 提示与设备录像（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 被拒方案）；⑤ 浏览器层 HTTP 认证（Playwright `httpCredentials`）——只有桌面 Playwright 上下文能用，Appium 驱动的设备浏览器没有对应通道，且要求边缘回到 basic-auth 质询；它想解决的地址带凭据与 `pushState` 假失败已由令牌换 cookie 消除，Nova Act 的浏览器启动面能否设置也未核实。

### 5. 工具自产文字里的凭据脱敏：剥 URL userinfo、签名类查询参数与设备端点的路径令牌，落盘的 run 定义不动

- **动机（演示项目云端真跑实测）**：确定性 step 的失败消息带 `page.url()`、AI 证据的 `url` / `prompt` / `thought`、`explain` 输出、`run --json`、本机转发的 worker 日志，都可能原样带着凭据（原方案里是 `https://用户:口令@主机`；现方案里是预热地址上的令牌参数，以及设备端点与预签名地址上的签名参数）。凭据虽是每 run 一换的短命物，但会随报告复制进工单与聊天、随 S3 产物留存、投屏时打在屏幕上；凭据还有效时（隧道凭据的有效期见决策 4「隧道鉴权」一条），能看到这些文字的人就能访问被测机器上的应用或设备端点。
- **规则三条，三份实现规则相同**：① 把文本里每个 `scheme://userinfo@host` 的 userinfo 段替换成 `***`（`https://***@host`，沿用 pip / git 的显示惯例）。正则作用于 `://` 之后、`@` 之前由 RFC 3986 userinfo 字符（字母数字与 `._~%!$&'()*+,;=:-`）组成的一段：不含双引号与反斜杠，所以能直接作用在已序列化的 JSON 行上而不破坏结构；不含中文与全角标点，所以中文叙述里「地址，用户邮箱@」不会被一路吞到邮箱的 `@`（排除式字符集会）。代价是 userinfo 里未做百分号编码、又不在这个字符集里的字符（中文、`|`、空格等）让那一段不被盖（见下「已知残余」），地址里的凭据按 RFC 本就该百分号编码。② 封闭名单里的查询参数，值替换成 `***`：`X-Amz-Signature`、`X-Amz-Security-Token`、`X-Amz-Credential`、`gherkai_tunnel_token`，参数名不区分大小写；参数名前是 `?`、`&` 或 XML 实体转义形态的 `&amp;`（控件树属性里 `&` 写成 `&amp;`，[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 11），值到下一个 `&` 或遇到空白、`"`、`#`、`\`、`<` 为止（不含双引号与反斜杠，所以同样能作用在已序列化的 JSON 行上）。`X-Amz-Date`、`X-Amz-Expires`、`X-Amz-Algorithm`、`X-Amz-SignedHeaders` 与会话端点上的 `arn` 不是凭证，保留明文以便诊断预签名地址过期一类问题；`X-Amz-Credential` 不是秘密，但带 access key id，盖住的代价为零。不用「名字含 token 或 signature 就盖」这类宽泛形态：会误伤被测应用的普通参数，三种语言的正则也难保持一致。③ Device Farm Appium 端点的路径令牌：`/remote-endpoint/` 之后的那一段（到下一个 `/`、`?`、`#`、`@`、空白、`"`、`\` 为止）替换成 `***`。该端点没有查询参数，凭据就是这一段令牌（形态与长度见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 实测依据「会话端点结构」行），按查询参数名脱敏盖不住它。规则 ② ③ 的停止字符里空白用显式字符类、规则 ② 的参数名大小写折叠限 ASCII（规则 ① 是正向字符集，没有这两项）：Python 与 JS 对 `\s` 和非 ASCII 大小写折叠的语义不同，三份实现要对同一输入给同一结果。不做「拿本次凭据精确回替」：本次凭据分在不同持有者手里——隧道令牌随 definition 下发，设备端点与预签名地址由 worker 在运行时生成且不进任何事件（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 11），core 的 `wire.py` 与 CLI 的 `explain` 这些出口拿不到全部凭据，要回替就得把秘密再传一遍；按形态匹配不需要传递秘密，三份实现的行为也一致。实现三份（`gherkai_core/redact.py`、Nova worker `lib/redact.py`、Midscene worker `lib/redact.mts`）——Nova worker 零 core 依赖、Midscene 是另一种语言，三份文件头互指、测试用同一组用例。
- **收口在出口、不在产生点**：worker 侧两个 worker 共有三处（事件 `emit` 序列化后的整行、evidence.json 写盘前的整份、worker 自己的 stderr 诊断行）。stderr 诊断行在 Nova worker 是 `run_scope` 的 `log()`、未捕获异常的 fatal 出口与上传器的 `_log`（包内能写到 stderr 的出口恰为这三处，各自在自己的函数体里调用 `redact_secrets`；出口以模块相对路径加类名与函数名标识，类里同名的方法、嵌套函数与 lambda 各算一处。由 `engines/novaact/tests/test_stderr_redaction.py` 的静态差集守，计入出口的写法、出现即报的写法与已知识别不了的间接取法（不穷尽），以该文件静态差集一节的开头注释为准。判据是：能直接解析到的写 stderr 引用都登记为出口，并核对它自己调用了脱敏；登记不了的两类出现即报——绕过这些出口直接写 stderr 的（logging、`traceback.print_*`、`warnings.warn`），与静态分析追踪不了的写法（如星号导入与动态导入、把 sys 模块或写函数当作值使用、类体内的 import、同一个名字在文件内由 import 绑定到不同对象）；脱敏后的值是否流到写出处，由运行期用例逐处核对。检查解析 import 时不区分作用域、整个文件共用一张表，同名绑定到不同对象时，表里的一项代表不了各处引用，取哪一项都可能漏掉写 stderr 的那一处。被拒方案是按词法作用域解析 import：函数内 import 对整个函数体的遮蔽、类体不传给方法、`global` / `nonlocal` 与推导式作用域，各是一处新的漏判来源；出现即报更简单、不会漏，真实包里没有这种写法，遇到时改名即可通过）；在 Midscene worker 是 worker 自己的日志出口、bin 的 fatal 行、上传器、steps 加载器与 evidence 抽取的缺省日志出口。云端 worker 的 stderr 不经 core 的转发层、原样进 CloudWatch，所以要在 worker 写出的那一刻盖住。Nova 的 fatal 出口是 `main()` 第一步装上的 `sys.excepthook`：由解释器缺省的 `sys.__excepthook__` 把 traceback（含被链接的上游异常）写进内存缓冲、整段脱敏后再写 stderr；`main()` 之前的失败只来自模块 import 期（依赖缺失、环境变量取值不合法），文本里没有运行期才拿到的地址与令牌，交给解释器的缺省输出。被拒方案是在钩子里自行用 traceback 模块格式化：Python 3.13 实测它让未捕获的 KeyboardInterrupt 从按 SIGINT 结束（退出码 130）变成以 1 退出，经缺省钩子生成文字则退出方式与缺省一致（仍为 130，普通异常仍以 1 退出）。Midscene worker 另有设备目标的两份写盘（`device-session.json`、原始控件树 `page_source`），WebdriverIO 自己写到 stderr 的行不经这些出口、由它的 logger 掩码盖住（出口清单与掩码见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 11）；core 两处（`wire.py` 解码事件 `message` 时、`subprocess_engine` 转发 worker 日志每行时），CLI 两处（`explain` 的机读文档整份深度脱敏、`run --json` 输出整份深度脱敏）。放在出口是为了把 `steps/` 里使用方自写 handler 的消息、SDK 自己的 stdout 一并盖住，而不是逐个改消息模板。导航实参（`go_to_url` / `page.goto` 的参数）与 job 文本本身不经过这些出口，凭据照常生效。worker 把异常文本压成一行并截到 300 字时须先脱敏再截断（否则截在 userinfo 中间会丢掉 `@`、规则失效）。
- **明确不脱敏（执行依赖明文）**：`run_meta.json`（0600） / DDB META / S3 参数卸载对象里的 run 定义（推进器要读回会话预热地址注入 worker）、worker 进程环境里的预热地址、云端 RunTask 的 `containerOverrides`。判定明细（`jobs/` 下的文件）不在此列：它不是执行输入，且现方案下 step 文本不含秘密，保持 0644；谁读它、CI 怎样读状态与读取权限见 [0030](./0030-realtime-persistence-seam.md) 决定三。Fargate job-in 同样不含秘密：它只有 job 文本，预热地址经 RunTask 的 `containerOverrides` 注入。另有一处**原样落库**：worker 发出的原始事件行（本机前台 `run` 与 detached 都写报告目录下的 SQLite 事件库 `events.db`，[0042](./0042-step-evidence-and-explain.md) 决策七；云端的 DDB events 表）在解码前写入，两个官方 worker 已在 emit 处脱敏、故行内干净，第三方 worker 若不脱敏则行内有明文——core 的 `wire.py` 只盖住解码后的视图。也不改引擎原生产物（Nova 轨迹 html / json、Midscene 报告 html）、云端 CloudWatch 里 SDK 自己写的 stdout / stderr（worker 自己的诊断行已在写出时脱敏）与 Device Farm 的录像、Appium 日志——它们由 SDK 或服务商写、不经我们的出口，仍按「短命凭据」对待，用户指南与 skill 的安全段照实说明。
- **已知残余**：模型在 thought 里复述地址时若去掉了 `scheme://` 只写 `用户:口令@主机`，规则抓不到；userinfo 里未做百分号编码、又不在 RFC 3986 userinfo 字符集里的字符（`https://u:密钥@h/`、`https://u:p|q@h/`）让那一段不被盖；纯 ASCII 逗号把地址与邮箱连写（`https://a.com,x@b.com`）仍会误吞到邮箱的 `@`；隧道 cookie 会到达被测应用的访问日志（剥离是服务商的付费功能）；被测页面自己把地址里的参数值以非查询串形态印在页面上时（回显服务把查询参数回显成 JSON 键值 `"X-Amz-Signature": "…"`，或错误页把令牌印成纯文字），规则②按参数名加 `=` 匹配、认不出这种形态，值会原样留在原始控件树、控件摘要与 `explain` 的页面文字里，与截图不脱敏同一性质（真机实测：同一页上地址形态的 `url` 字段与 `&amp;` 形态全部盖住，JSON 键值形态原样留下）；不为它加「按值盖」的规则——那要把每次运行的真值带进三份脱敏实现，而这类内容本就随截图原样可见；云端 RunTask 的 `containerOverrides` 带预热地址，task 停止后约 1 小时内仍可经 `ecs:DescribeTasks` 读到；CloudTrail 不是这段地址的残留面：RunTask 事件的 `requestParameters` 与 `responseElements` 里 `containerOverrides[].environment` 整个被替换成固定字面量 `HIDDEN_DUE_TO_SECURITY_REASONS`，连键名都不出现（验证环境里 CLI 与推进器两种发起方的 26 条 RunTask 事件全部如此，实测），事件历史与账号级落 S3 的 trail 都不必清理。

## 被拒/被缓方案（护栏）

- **CDP 请求拦截喂送**——拒。WS/SSE/SW 能力断崖对「开发中的全栈应用」是真实缺口；带宽税（缓存强制关闭+全请求 pause+base64）；Nova 侧 page 级 route + greenlet/node-driver 泵动的执行模型脆弱（stall 形态偶发、难排障）。静态站场景隧道同样覆盖，无需为其保留第二条路线。
- **Playwright `exposeNetwork`**——不可用而非不好：机制寄生在 Playwright 自有协议与浏览器启动权上，AgentCore 托管场景两者皆无。若未来浏览器宿主换成自管（如自起容器跑 Chromium），此路线值得重估。
- **cloudflared quick tunnel**——缓。零账号是其残留优势，但零认证、官方点名不支持 SSE、`*.trycloudflare.com` 被恶意软件滥用致企业网常见封锁。TunnelProvider 口子已留：ngrok 门槛（authtoken/配额）被用户反馈证明是问题时再加它作第二实现。
- **AgentCore Browser VPC 模式**——口子，非本 ADR 范围：它解决「应用在 VPC 内（云上开发机）」而非「应用在本地」，且需自建 browser 资源（IaC 新资源、创建后网络模式不可改）。真实需求出现时单独立项。
- **隧道由独立的 ngrok 代理进程持有，留下时由处置命令按隧道记录补拆**（连同它带出的隧道记录与「已拆」标记、拆之前在回环地址上按端点名问代理的本机接口、按进程号发信号、云端借用状态分组索引列举、本机接口的使用前提）：代理是与宿主分开的另一个进程，宿主没有走完收尾就退出（如被 SIGKILL）时代理与公网地址一直留着，要补拆就得另有记录；记录与进程是分开的两样东西，记录只能在确知时写，代理自己没了的记录会一直留着；问到连接被拒分不出「代理没了」与「这条命令不在启动它的环境里」，在别的环境里执行有误发信号的可能。依据（ngrok 3.39.13 在 macOS、3.39.11 在 Linux）：按端点名问接口，代理在时答 200，问另一个代理或端口被后来的代理占用时答 404，代理被强杀之后连接被拒，代理被暂停时不回答；Linux 的容器里，缺省网络下问到连接被拒，与宿主共用网络而进程命名空间各自独立时核对通过、记录的进程号在容器里却不存在（发信号得到「没有这个进程」）；代理被暂停 12 秒时公网一侧仍按在线回答，34 秒时与它已退出时相同（macOS，两种账号各一次）。
- **经 ngrok 云端的 API 查端点、远程让代理退出**：要另配一个账号级的 API key；代理仍是独立进程。
- **保留 ngrok 可执行文件、由宿主直接启动并把它的寿命绑在宿主上**：代理仍是另一个进程，要它随宿主退出得另靠操作系统的机制，各平台有没有、怎样用没有核过；会话建在宿主进程里不需要这一层。
- **本机 `submit` 也用一个单独的隧道守护进程**（同云端 `submit`）：多一个进程；隧道的寿命是守护进程的而不是推进器的，推进器没了之后要靠它自己发现才退出。
- **建 run 之后才起隧道、公网地址在启动 job 时再替换**：云端做不到（云端的推进器读不到本机起的隧道，地址必须在运行定义里），本机与云端就成了两种做法；隧道起不来要等到 run 建成之后才报。
- **边缘规则的时刻按 job 对齐**：一条隧道只有一份策略、启动时定下，那时还不知道各 job 什么时候开始（决策 3「边缘到点拒绝」）。
- **保留 `--tunnel-ttl`，只允许调小**：调小会在 run 未完时断掉隧道，剩余 job 在被测应用不可达下以导航失败告终；守护进程的存活上限已由运行期限推出（决策 3「云端 `submit`」），公网入口在边缘到点关闭（决策 3「边缘到点拒绝」），不需要使用者另给一个时长。

## 边界与不变量

- 隧道仅在显式给出 `--expose-local` 时起（命令行选项，或项目配置文件 `[common]` 节的同名键，[0053](./0053-project-config-file.md) 决策 3）——内建默认里没有这一项，默认路径零新依赖、零出网变化。
- core 对隧道无知（映射在组合根完成）；worker 不感知令牌与 cookie 的值，它对哪些目标、在什么时候导航预热地址，怎样在页面标记上确认，见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「做什么」与「预热页面有三种可见结果」两条。额外请求头与会话预热地址**不新增 worker↔core 协议事件**——definition 层各加一个字段（`RunMeta.extra_http_headers`、`RunMeta.session_warmup_url`，无值为 null）+ 复用既有 env 注入面（`GHERKAI_EXTRA_HTTP_HEADERS`、`GHERKAI_SESSION_WARMUP_URL`），core 只搬运不解释语义。
- **definition 完整性不变量**：隧道模式下 definition 必带「额外请求头」与「会话预热地址」两项；worker 收到额外请求头却没有预热地址即记 `precheck_failed`「后端未传递会话预热地址，部署版本可能低于命令行工具，请重新部署后再提交」——两个既有事实绑成一个完整性判据，能抓到旧后端丢字段的部署残缺，不按文本猜测；它要防的开发版本混搭场景见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13。
- 本机关机或宿主进程崩溃时隧道随之消失：前台 `run` 与本机 `submit` 的宿主就是推进器，它没了即推进器中断，按 [0054](./0054-run-deadline-lifetime-lock-and-settling.md)「边界与已知局限」里「三种组合的对照」表「推进器中断」一行；云端 `submit` 见下「云端的守护进程没了」一条。断网、休眠之后会话是否恢复见「实测项」里「尚未核」的第 3 条。明示边界（云端 `submit` 时的提示见决策 3「cloud submit 的语义澄清」一条），gherkai 自己不做「断线重连恢复」（测试可重跑，不值守护复杂度）。
- **与设备目标的关系**：鉴权契约（预热页面的三种可见结果与归因、cookie 规格、边缘策略的规则数约束、导航路线由能力探测决定）归 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13；脱敏规则对查询串凭证与设备端点的扩展见决策 5 的规则 ② ③，为什么要扩展见 0051 决策 11「端点是凭证」一条；本篇的地址映射与三形态宿主不变。
- **同一个账号同一时间只有一条隧道在线（新注册的 ngrok 账号）**：现在的隧道实现用 ngrok；在它的免费套餐、新注册账号（固定开发域名）这种用法下，同一个账号同一时间只有一条隧道能在线（实测见决策 1「实测依据」里「同一账号第二条隧道」一条）。起隧道时遇到它的 run 怎样报错、使用者怎么办，按决策 1「启动失败的说法按原因分」一条的第 3 种说法，这里不另作概括。这是这个服务商在这种用法下的限制，不是 gherkai 的设计：设计上每个 run 一条隧道、彼此无关，工具不加互斥，服务商经决策 1 的 `TunnelProvider` 替换。较早注册的账号上各条隧道地址不同、可以并存（实测见决策 1「实测依据」里「同一账号第二条隧道」一条与「用 ngrok 可执行文件做的实测」），同时在线的会话数仍有上限，超过时按第 4 种说法报出（实测见决策 1「实测依据」里「失败的异常形态」一条）；付费套餐与自定义域名下怎样没有核过，端点数上限随 ngrok 账号套餐。
- **宿主被暂停**：请求不再转发到本机，恢复后重新在线；暂停期间与恢复时公网一侧的回答见决策 1「实测依据」里「宿主被暂停（SIGSTOP）45 秒」一条，公网一侧从什么时候开始答不在线没有测到；宿主所在的机器休眠、断网时怎样没有核过（「实测项」里「尚未核」的第 3 条）。这期间访问被测应用的 job 会失败。
- **云端的守护进程没了**（被强杀、本机关机）：隧道随之消失，云端的 run 照常推进，之后要访问被测应用的 job 以导航失败（AI 报错形态）告终。
- **流量策略的规则在较早注册的账号上已经用满**（规则条数见 [0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「边缘策略」，各种账号的上限见决策 1「实测依据」里「六条规则」一条）：再要加规则，先要合并现有的规则（例如 0051 决策 13「边缘策略」里答 401 的两条），没有实测。
- **边缘规则按起隧道那台机器的时钟**：策略里的时刻按起隧道那台机器的墙钟算出（三种组合都是使用者的机器），由 ngrok 边缘的时钟比较；job 由执行它的一方（本机或云端的推进器）按自己的时钟在期限截断（[0054](./0054-run-deadline-lifetime-lock-and-settling.md) 决策二第 2 条）。执行方的时钟比边缘的慢得超过 300 秒时，公网入口会在 job 还没有到期限时关闭。不为它再加余量。
- **SDK 是带原生库的包，实测的是 1.8.0**：长时间运行、断网之后的重连、与 CLI 进程里别的线程长期共存都没有核（「实测项」里「尚未核」的第 3 条）。流量策略的时间变量、规则上限与「地址已在线」的错误都是 ngrok 的，换隧道服务商时这一块要重做。

## 实测项（实装时逐项核，结果内联回这里）

读法同 [0054](./0054-run-deadline-lifetime-lock-and-settling.md)「实测项」一节开头的那一句。经产品代码、用真实的 ngrok 账号。

**已核**（macOS 与 Linux 各一次，注明的除外；Linux 上用真实的引擎，macOS 上没有引擎可用的凭证，worker 换成照同样次序预热、再带 cookie 访问被测应用的替身）：

- 本机的两种组合（前台 `run`、含 `--no-report`，本机 `submit`）起隧道并执行：访问被测应用的 job 通过（Linux），替身的预热与带 cookie 的请求都答 200（macOS）；公网地址那一行各出现一次；`run --json` 的标准输出是单一一份 JSON；判定不通过时退出码为 1、退出时没有回溯；宿主退出之后公网一侧答 404，没有留下与隧道有关的进程与文件。全程只设 `NGROK_AUTHTOKEN`。
- 三种宿主各被 SIGKILL 一次（云端的守护进程是直接启动、照 `submit` 的做法与它交接）：公网一侧在 1.5 秒之内转为不在线（Linux 上下一次探测即是），没有留下与隧道有关的进程。
- 本机 `submit` 的回报：建成时标准输出只有 run 的标识、退出码 0，后台推进进程回报之后的输出在 `reconcile.log` 里；起隧道失败时原因经回报由 `submit` 输出、退出码 2、没有 run。`submit` 在后台推进进程查它是否还在之前被强杀：不建 run，后台推进进程退出；之后才被强杀：run 照常建成并推进到结束，日志里记一句。后台推进进程在回报之前被强杀：`submit` 以退出码 2 给出一句说明，标准输出为空。`submit` 等回报时被 Ctrl-C 打断（落在后台推进进程查它是否还在之前、之后各一次，macOS）：以 130 给出那一句说明，其余与被强杀相同。前台 `run` 在起隧道期间被 Ctrl-C 打断（macOS）：以 130 给出一句说明，没有回溯，没有建 run。前台 `run` 在建 run 的那一次调用期间收到真实的 SIGINT（macOS 的 APFS 与 Linux 的 `ext4`，落在改名之前、之后各一次）：调用照常完成，随后以 130 结束、标准输出为空，建成的记录完整、没有留下暂存目录，锁到进程退出才放开。
- 报告目录不合要求时本机 `submit` 在前置检查里即被拒、不经回报：退出码 2、标准输出为空，不启动后台推进进程，带 `--expose-local` 时也不起隧道，说明与前台 `run` 同一句（Linux 的 `ext2` 回环镜像，macOS 的 HFS+ 与 FAT 磁盘映像）。
- 守护进程：回报之后回报管道的写端保持打开；`submit` 没有交出 run 的标识就关闭标准输入时以 0 退出；收到标识之后到了到点时刻退出（到点后 0.1 秒与 0.4 秒），读 run 状态失败的说明只记一次；对 SIGTERM 按缺省处置结束。回报之前没有往标准错误写字。
- 到点前后边缘的回答（脚本经产品的隧道模块以 25 秒之后的到点时刻起隧道，过点之后继续存活）：到点之前没有 cookie 答 401、预热答 200 并下发 cookie、带 cookie 转发到被测应用；到点之后 0.13 秒（macOS）与 0.16 秒（Linux）发出的请求上出现第一个 403，之后预热与带 cookie 的请求都答 403。
- 启动失败，都以退出码 2 结束、不建 run：没有装可选依赖（一个没有装这个组件的环境里，macOS）与没有令牌时，三种组合给出第 1、2 种说法，不起后台进程，云端组合在没有 AWS 凭证的环境里同样；无效令牌给出第 4 种说法（带 `ERR_NGROK_105`），前台与本机 `submit` 同一句；新注册的账号上第二条隧道给出第 3 种说法（macOS），前台与本机 `submit` 同一句，第一条下线之后再执行照常；连不上隧道服务（把服务地址改到不可达处）时，Linux 上到 20 秒的时限以第 4 种说法结束（前台 22 秒、本机 `submit` 21 秒），macOS 上 SDK 约 5 秒自己放弃、同样以第 4 种说法结束，两种宿主都随即退出。

**尚未核**：

1. 云端 `submit` 这一组合经真实的 run 执行通过；守护进程读到终态之后退出；守护进程在 `submit` 交出 run 的标识之前、之后各被强杀一次，`submit` 在交出标识之前被强杀一次（决策 3「云端 `submit`」各条与「边界与不变量」里「云端的守护进程没了」一条）。前提是云端后端部署了能读这一版提交记录的版本。
2. 后台推进进程在建成 run 之后、回报之前被强杀：`submit` 以退出码 2 给出指向 `settle-runs` 的那一句；随后不给 run 标识的 `settle-runs` 按 [0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节说明表「锁拿到了」一行结束这个 run，并清理可能留下的暂存目录。
3. 记下：长时间运行（数小时）的隧道；宿主所在的机器断网、休眠一段时间之后会话是否恢复，恢复之后规则是否照常；SDK 与前台的线程池、后台的读事件线程长期共存；宿主被暂停时新注册的账号上另一条隧道能否建成；宿主进程在本机有没有监听端口；SDK 请求耗时实测里没有成功的那几个请求的原因。
4. 前台 `run` 在建 run 的那一次调用期间与调用返回之后、开始执行之前各收到一次真实的 SIGINT（macOS 的 APFS 与 Linux 的 `ext4`）：它自己按 [0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节说明表「使用方中断」一行做结束写，全部 job 记 `skipped`，报告生成，以 130 给出这个 run 已因中断记为已结束的那一句、标准输出为空，锁到进程退出才放开。
