# 0054. 运行期限与遗留前台 run 的收尾：每个 run 遵守由 job 预算推出的期限，终态不可变、执行方服从记录，settle-runs 把发起进程已不在的 run 记为已结束

> **Status:** Draft（2026-11-14）—— 设计稿，尚未实装。owner 已定：运行期限是硬约束，前台与后台、本机与云端的执行方都遵守；run 级终态对所有写入方不可变；判据用最初定的两条；期限进运行定义而发起进程标识放运行态记录顶层。翻 Accepted 时同步校准 0030 / 0033 / 0034 / 0037 / 0038 / 0041 的相应条文与 CONTEXT 词表（见「对既有文档与 code 的影响」），并关闭 0041 文末「遗留的非终态 run」重议闸门。

## 背景与问题

前台 run（`run`，本机后端与 `--backend cloud` 都算）只有发起它的那个 CLI 进程会推进：两个云端 Lambda 与本机的接力都只处理带后台执行标记的 run（[0034](./0034-detached-batch-reconciler.md)「filter 必须区分写入者」）。这个进程不写 run 级终态就消失时，run 永远停在 `pending` 或 `running`。code 里这样的路径有四条：进程被 SIGKILL 或宿主失联；收到 SIGHUP（只装了 SIGINT 与 SIGTERM 的处理器）；`run --backend cloud` 运行期落库抛出 botocore 异常后直接以退出码 1 返回；调度抛出其它未捕获的异常。

留下的 run 没有出口，后果有四处：

- `status --wait` 对它只等待、不接力，会一直等下去；`explain` 还提示「可先用 status --wait 等到终态」。
- `list-runs` 的未结束部分不截断（[0041](./0041-agent-facing-cli-affordances.md) 决策七），这类 run 只增不减。
- 云端的清理协议把 `live` 分组里的 run 当作 worker 版本的占用者（[0038](./0038-worker-image-delivery.md) 残余风险④），它引用的版本一直回收不了。
- 没有任何记录说明「这个 run 最晚什么时候必然已经停手」。各 job 有墙钟预算，但它是进程内用单调时钟做的保护：系统休眠时单调时钟不走，各 job 的截止时刻顺延休眠的时长；进程被暂停时它不检查截止时刻；落库或云端调用卡住时也没有上界。所以从外面看，一个前台 run 可以在任意晚的墙钟时刻仍在执行。

现有的写入规则也与「把遗留 run 记为已结束」不相容，三处都能改掉一个已有的 run 级终态：

- 前台执行者的 `finalize_run` 是无条件写。
- 本机存储的前台写路径（`update_job_state`、`finalize_run`）是不加文件锁的读改写，与别的进程并发时可能把 run 级写回 `running`。
- `create_run` 与 `save_run` 是无条件的整份重写，对一个已有的 run 再调一次就回到初始状态或被改成任意状态。生产 CLI 不这样调，但端口允许。

0041 文末的重议闸门原定「遗留成为清单常态时再议」。它的两个触发条件都是使用面的证据，产品现在没有使用者，所以关闭它的依据不是触发条件已满足，而是 owner 的判断：只增不减、没有出口的状态是设计上的缺口，索引迁移的真实环境核验里已经实际留下过一条。

## 决策

### 一、定位与范围

- 收尾（`settle-runs`）是系统对遗留状态的处理：认出发起进程已经不在、或已过运行期限的前台 run，把它记为已结束。它不是「使用者放弃一个 run」，判定只靠建 run 时记下的事实，不靠使用者事后担保，拿不准就不动。
- 收尾只处理不带后台执行标记的未结束 run。带标记的后台 run 到期由推进步骤自己结束（决策二），推进已中断的由 `status --wait` 接力完成；取消一个后台 run 是另一件事，不在本 ADR。
- `run --no-report` 不建任何记录，不在范围内。

### 二、运行期限：进运行定义，所有执行方都遵守

每个 run 在建立时得到一个运行期限 `deadline_at`（UTC 的 ISO 时刻），它是这个 run 的一条规则：

`deadline_at = created_at + 900 秒 + Σ（各 job 的墙钟预算 + 每 job 尾段）`

- 每 job 尾段：本机后端取 `2 × G + 10` 秒，云端后端取 210 秒（隧道存活时间上限已在用的 `CLOUD_PER_JOB_MARGIN_S`）。G 是停止宽限：前台 `run` 取这次调用解析出的值（`--grace`、配置文件或各引擎自报值）；本机 `submit` 没有 run 级的宽限，取这个 run 用到的各引擎自报宽限里最大的一个。
- 900 秒是一次性余量，与隧道存活时间上限的一次性余量同值，留给建 run 到起第一个 job 之间的装配与各次落库、云端调用。
- 任一 job 不超时（桌面 scope 加 `--default-job-timeout` 不大于 0）时没有期限，`deadline_at` 为空。
- 求和而不按并发折算：并发大于 1 时真实墙钟小于各预算之和，串行总和对任何并发取值都偏宽，与 `compute_watch_ttl_s` 同一做法。健康的 run 远在期限之前结束。

尾段与余量是预算的取值，不是「执行一定已停」的上界：停止等待预算是执行方愿意等的时长，停止调用本身、起 worker 的调用、落库调用都可能阻塞得更久（0034 已区分等待预算与平台保证）。它们只决定期限定得多宽；收尾的安全不靠它们，靠决策五。取值的来历：前台 run 的 job 从线程池取到它时起算预算，到点后本机一次停止等 G 加约 3 秒、排空等到停止请求之后 G 加 5 秒、仍未结束会再发一次停止，合计约预算加 `2G + 9` 秒；云端的停止等待预算不超过 140 秒，加排空余量与心跳约预算加 146 秒，取 210 秒。job 级重试共享同一个截止时刻，不另外延长。

**落点是运行定义**（`RunMeta`，用户文档里的「提交记录」）。期限由 job 的墙钟预算与停止宽限推出、建 run 时确定、之后不变，执行方要遵守、所有读者都要看，它与 job 的墙钟预算、并发上限是同一类东西，后两者已在运行定义里。运行定义的键集因此变化，结构版本由 1 升到 2；按 [0037](./0037-distribution-and-packaging.md) 决策 7，读端拒读版本不是 2 的记录，产品没有使用者，不为版本 1 的记录做兼容。云端把它摊成 META 条目的顶层属性（同结构版本与写出版本的做法），列举时投影这个属性，不取回整份运行定义。

**所有执行方都遵守期限，前台与后台、本机与云端是同一种表现。** 规则只看当前时刻与各 job 的状态，任何一次推进都能独立算出同一个结论，不需要记住期限那一刻发生过什么：

1. 当前时刻已过 `deadline_at` 减 60 秒，不再启动新的 job（含同一个 job 的重试）。提前 60 秒是启动余量：从发出启动到 job 真正开始执行需要时间，卡着期限启动的 job 来不及被正常停止。
2. 在跑的 job 的截止时刻以 `deadline_at` 封顶：取「开始时刻加它的墙钟预算」与 `deadline_at` 中较早的一个，到点的处理与 job 自己的预算到点完全相同，包括 0034 机制二已有的规则：内容已经完整、随后正常退出的 job 保留它的判定，不因为收尾越过了截止时刻而改判。被期限截断的 job 记为 `error`、类型为超时，说明按实际起作用的那个时刻写（可由认领时刻、job 预算与期限重算出是哪一个）。
3. 已过第 1 条的时刻、没有在跑的 job、仍有未启动的 job：run 级以条件写收尾为 `error`，说明是「已超过允许运行的时间」（写在 run 级 `message`：run 的时间用完不是哪一个 job 的原因）。未启动的 job 保持 `pending`，不替它们下结论。
4. 没有在跑的 job、也没有未启动的 job：照常按各 job 的状态聚合收尾，不管当前时刻是否已过期限。被期限截断的 job 自身是 `error`，聚合自然得出 `error`；全部 job 都给出了完整内容的 run 得到它们的真实结果。

第 3 条的「没有在跑的 job」必须在提交的那一刻仍然成立，光靠读到的快照不够：另一个推进方可能在停止启动的时刻之前通过了时间检查、认领写在这次读取之后才落下，随后它照常启动 job。所以第 3 条的收尾写除了要求 run 级未结束，还要求从读到运行态以来没有新的认领：运行态带一个认领计数，每次认领成功时加一，收尾写以它等于读到的值为条件（本机在文件锁内重读后再判）。条件不成立即放弃这一次收尾、继续推进，新认领的 job 照第 2 条在期限时刻被停止。第 4 条不需要这个条件：没有未启动的 job 就不会再有认领。

run 级的状态与说明以条件写提交的那一份为准：`RunResult` 增加 run 级说明，第 3 条收尾的 run 在 `RunResult` 与报告里同样是 `error` 加这句说明，未启动的 job 标为没有执行。写的次序不变：已结束的 job 的判定明细先落库，再条件写 run 级终态，最后生成报告。

各执行方的落实：

- 前台执行（`run`）：调度循环按墙钟检查，过了第 1 条的时刻不再从队列里启动 job、也不再重试；到了 `deadline_at` 把在跑的各 worker 的截止时刻视为已到并发停止请求，等它们结束后按第 3、4 条收尾。未启动的 job 不落判定明细、运行态保持 `pending`。
- 后台推进（本机的推进进程与 `status --wait` 的接力、云端的 Lambda，都经 core 的同一个推进步骤）：过了第 1 条的时刻，推进步骤不再认领；认领 job 时算出的截止时刻以 `deadline_at` 封顶，本机的计时、云端的一次性定时触发与防御性超时扫描都按封顶后的时刻；满足第 3 条时为已结束的 job 落判定明细、条件写 run 级 `error` 与说明、生成报告。现在的收尾只在全部 job 都到终态时才走，落判定明细与生成报告的两步、以及它们依赖的两种投影（[0031](./0031-job-lifecycle-states-and-severity.md) 的收尾投影契约）要能在有 job 未启动时照常工作。
- 本机接力把别人认领的 job 判为超时，要等到它的截止时刻加上停止尾段（`2G + 10` 秒，G 取该 job 引擎的停止宽限）之后。现在的余量是固定的 10 秒，比停止宽限短：原推进进程到点催停、worker 还在宽限内正常收尾时，接力方会先写下一条未知退出，把本可保留的判定固定成超时。期限让许多 job 在同一时刻到点，这个窗口必须先关上。
- 云端后台 run 另在 `deadline_at` 设一次定时触发（定时触发的命名与授权按 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 资源清单里 job 超时触发的同一形态登记）。这一次触发对所有仍在跑的 job 做超时处置，与各 job 自己的超时触发是同一处理：它们的截止时刻此刻都已到。不靠各 job 自己的定时触发，是因为那些触发是尽力而为地建立的，某一个没建成、它的 worker 又不出任何事件时，没有别的东西会再来推进这个 run。处置引出的退出事件再触发推进步骤，走到第 3、4 条。这一次触发本身调用失败时由平台的异步重试补上；整条触发链都失效时与今天一样，由 `status --wait` 接力。
- 本机后台 run 的推进进程已不在时，下一次 `status --wait` 接力把它推进到结束。

检查用墙钟而不用单调时钟：期限是别的机器也要拿来比较的时刻，而且单调时钟在系统休眠时不走，合盖几小时再打开的进程只有按墙钟才知道自己已经过期。

这给每个 run 加了一个由 job 预算推出的总时长上限，是对 0034「job timeout」节「先不做 run 级总墙钟预算」的改变：期限不是使用者单独配置的预算，调整它的途径仍是各 job 的墙钟预算与停止宽限。选它而不把期限只当作「推定发起进程已不在」的阈值，理由是：

- 对测试工具，一次 run 的总时长有上界本身是该有的性质：CI 可以据此排期；云端浏览器会话与真机按分钟计费，休眠后恢复的发起进程会自己把过期的会话停掉，没有人查看的后台 run 也不会无限期挂着。
- 前台与后台、本机与云端同一种表现：「允许运行至」对所有 run 是同一个意思，上层不必按执行方式分别理解。代价是后台 run 的接力有了期限：推进中断之后要在期限之前接力，过了期限 run 以 `error` 结束，要重新提交。
- 清单里这一列的名字是「允许运行至」，硬约束才名副其实。

### 三、发起进程标识：放运行态记录的顶层

前台 run 建立时另写下发起进程标识 `launcher`：pid 空间标识、pid、进程启动时刻的原值，另带主机名（只用于显示）。取法见决策八。它由发起进程在建 run 那一刻确定，之后的每次写都原样保留，查看或处置的一方不重新生成。

落点是本机 `run_state.json` 的顶层键、云端 STATE 条目的顶层属性，与后台执行标记同处：只由存储 adapter 读写，不进 `RunState`、`RunMeta` 两个 core 模型，列举时作为 `RunListing` 的字段带出，core 不据它分支；写入沿后台执行标记的做法，经 adapter 的构造参数给出。

理由：它说的是「谁在执行这个 run」，不是「要执行什么、怎么执行」，与后台执行标记是同一类属性，0034 已定这类属性的位置。它也不该进运行定义：运行定义会随 `run --json` 输出，主机名与 pid 不属于那里。期限与标识因此分在两处，这是按性质分的：一个是 run 的规则，一个是执行它的进程的事实。

本机 adapter 现在每次写回运行态时从模型重建整份文件、只逐个补回后台执行标记，漏补一个键就静默丢失。改为：建 run 时写下的顶层附加键整体原样保留。

### 四、判定：owner 最初定的两条

三个触发面共用一个判定，对前台的未结束 run：

| 情形 | 结果 | 处置 |
|---|---|---|
| 与记录在同一个 pid 空间，这个 pid 不存在、启动时刻与记录不同，或已是僵尸 | 发起进程已退出 | 可立即记为已结束 |
| 上一行不成立，且当前时刻已过 `deadline_at` 加 300 秒 | 已过运行期限 | 可记为已结束 |
| 其余 | 不能处置 | 不动 |

- 第二行不问发起进程是否还在。它安全的依据是决策五：记下终态之后，发起进程即使还在，也不能再改这个终态、不能再认领与启动新的 job，发现之后会停手。期限与 300 秒只决定什么时候可以这样做，不承担「此刻执行一定已停」的证明。
- 300 秒是给时钟偏差与发起进程自己到期收尾留的余量：发起进程按自己的时钟在 `deadline_at` 停手并收尾，别的机器按自己的时钟等到 `deadline_at` 加 300 秒才处置。判定方的时钟比发起方快出 300 秒以上时，处置会早于发起进程自己认为的期限，这个 run 被提前结束（发起进程随后按决策五停手）；它记在「边界」。
- 没有期限的 run 只有第一行可用。
- 「同一个 pid 空间」核对不了（另一台机器或另一个容器、同一台机器重启过、记录里没有标识或标识不完整、读不到进程信息）时第一行不成立。标识不完整时不退回只看 pid：只看 pid 分不清复用者。
- 后台执行标记读不出或取值不合法的 run 不当作前台 run，一律不动；`deadline_at` 不是合法时刻时按没有期限处理。

### 五、run 级终态不可变，执行方服从记录

**终态不可变。** run 级状态只往前走：`pending` 到 `running` 到终态，到了终态不再变。这条规则原先只对后台的条件写成立，现在对端口上的每一个写入口成立：

- 前台执行者的收尾改用与别的写入方相同的条件写（`try_finalize`：只在 run 级为 `pending` 或 `running` 时写，可带说明）。无条件的 `finalize_run` 从 `RunStore` 端口删除。
- 建 run 只在这个 run 还不存在时成立：`create_run` 改为条件写（云端要求条目不存在，本机要求 run 目录里还没有运行态），对已有的 run 再调用即失败、不改任何东西。整份重写的 `save_run` 从端口删除，测试里需要的初始状态经 `create_run` 加各条件写得到。
- 本机 adapter 的前台写路径（`update_job_state` 与收尾）纳入现有的 fcntl 文件锁，与 `try_claim_job`、`project_state`、`try_finalize` 互斥；run 级已是终态时 `update_job_state` 只写 job。[0030](./0030-realtime-persistence-seam.md) 决定三「文件锁护 run_state.json 的读改写」由此对全部写入口成立。

理由：终态之后再变，对任何基于状态做事的上层（等待者、清理、以后的界面或服务）都是错的行为：已经返回的退出码撤不回，已经据终态做的处置撤不回。

**执行方服从记录。** 终态不可变只保护记录，不能让执行停下来。要让「记下终态之后不再有新的执行」成立，执行方每次启动 job 之前先认领，认领以 run 级未结束为条件：

- 后台推进本来如此（`try_claim_job` 要求 run 级为 `pending` 或 `running`）。
- 前台执行改为同一做法：从队列里取到 job、第一次起 worker 之前先做同一个认领，认领时刻随之记进运行态。一个 job 只认领一次；同一个 job 因网络故障重试时不再认领（它已是 `running`，再认领会被自己拒掉），改为在每次重新启动之前读一次 run 级状态。认领被拒或读到 run 级已是终态，说明 run 已被别处记为已结束：这个 job 不启动，调度循环对在跑的 worker 发停止请求，然后结束。
- 前台此后写 job 状态（开始执行、结束）时保留认领时刻。现在这两处是整项替换，不带认领时刻的写会把它抹掉。
- 前台执行者写 job 状态时发现 run 级已是终态（条件写落到只写 job 的那一支）同样触发停手。
- 结束时前台执行者不覆盖已有的终态；在终端说明这个 run 在本次执行结束之前已被记为已结束、已得出的判定照常写入；以非零退出码结束。

这一条不依赖时钟：不管两台机器的时钟差多少、发起进程是否被暂停过，run 级一旦是终态，它的下一次认领或启动前的检查就会拦住。能越过它的只有检查已经通过、启动还没有完成的 job（至多并发上限那么多）：首次启动是认领已成功，重试是启动前的那一次读已通过，而启动调用还没有发出、正在进行，或句柄还没有返回。它们会启动。启动之后由谁停，各执行方式不同，见「边界与已知局限」的表。

云端的索引写随之少一种：不再有终态被改写成另一个终态的那次分组变化（0041 决策七列的「终态被改写」边界不再存在）。

### 六、处置：run 级 `error` 加说明，job 保持原样

- 写入口就是决策五的条件写。两个处置同时发生、或处置与发起进程自己的收尾同时发生时，只有一个写成，另一方得到「已记为已结束」。
- 各 job 的状态不动，不替它们下结论；`ended_at` 写的是记为已结束的时刻，不是发起进程实际消失的时刻。
- 说明写在 run 级 `message`，事实在前、处置在括号里：「发起它的 gherkai run 进程已退出（已记为已结束）」「已超过允许运行的时间（已记为已结束）」。执行方自己到期收尾时写「已超过允许运行的时间」（决策二第 3 条）。
- 这扩大了 run 级 `message` 的写入方：0037 决策 7 原定只有云端推进器写、同步 run 不写。含义的边界不变，仍是「没有任何 job 能承载的原因」；写入方多出本 ADR 的处置与各执行方的到期收尾，两个后端都写。
- 「读到 run 级终态即各 job 的判定已全部落库」（0030 决定三、CONTEXT「终态提交点」）多出一类例外：带着说明的 run 级 `error` 表示这个 run 没有运行完成，有的 job 可能没有判定（未启动，或发起进程消失时还在跑）。同类例外原先已经存在（推进器在运行定义不可用时收尾），几处一并写明：凭「run 级终态」取产物的读者，对带说明的 `error` 要按「可能不全」处理；`explain` 对这类 run 的提示随之改。
- 清理协议不用改：记为 `error` 后 run 离开 `live` 分组，不再占住它引用的 worker 版本（0038 残余风险④随之改写）。此后执行方不再认领新的 job（决策五），余下未启动的 job 不会再用到这些版本；检查已经通过、启动调用还没有发出的那几个 job 可能因为版本刚被回收而启动失败，这个 run 此时已是终态，不影响记录。

### 七、触发面

- **`gherkai settle-runs [run_id] [--dry-run] [--json]`**，加 0041 决策六的三项定位参数。不给 `run_id` 时处理这个后端里全部前台的未结束 run，给了只处理那一个。`--dry-run` 只判定、不写。人读输出逐条给出 run、判定结果与处置；`--json` 给一个对象：落点字段同 `list-runs`，`dry_run`，`runs[]` 每项带 `run_id`、`outcome`（`settled`、`would_settle`、`skipped`）与 `reason`（`launcher_exited`、`past_deadline`、`launcher_alive`、`undetermined`、`detached`、`already_finished`、`unreadable`）。退出码只有 0（执行完成，含一个都没处理）与 2（用法错误、后端不可达、给出的 run 不存在）。它是变更类命令里带 `--json` 的一个：0041 决策三把变更类命令的机读面定为退出码，这里的结果是逐条的处置清单，退出码承载不了，作为该条的明示例外。
- **`status --wait`**：对前台的未结束 run 不再无条件空等，每次轮询做同一个判定，可以记为已结束的就记下，然后照常渲染并给终态的退出码（`error` 记 1）。前台 run 有期限、后台执行标记读得出时，最晚等到期限过后 300 秒；没有期限的 run 在发起进程核对不了或还在时照旧只等待，并说明原因。
- **`list-runs`** 保持只读、零写入。表格加两列：「已运行」（未结束的 run 是到现在的时长，有期限时括注还剩多久或已超多久；已结束的 run 是总时长）与「允许运行至」（本机时区，没有期限时为 `-`）。列序：run_id、状态、开始、结束、已运行、允许运行至、job、版本、提示。提示列按判定给出：「发起它的 gherkai run 进程已退出（可用 settle-runs 记为已结束）」「已超过允许运行的时间（可用 settle-runs 记为已结束）」；后台 run 已过期限而仍未结束时为「已超过允许运行的时间（可用 status --wait 收尾）」；其余不给提示，现有那句「status --wait 对它只等待、不接力」删除。`--json` 每项加 `deadline_at`（没有时省略）与 `liveness`（`launcher_exited`、`past_deadline`，不适用时省略）；发起进程标识不进机读输出。清单里的进程核对只读本机的进程信息。
- 判定与处置放在 runtime 包（与本机接力的期限恢复同层），CLI 的三处都调它。

### 八、发起进程标识怎么取

不引入新依赖，两个平台各用系统自带的手段，记录时与事后核对用同一种取法，按原值严格相等比较：

| | pid 空间标识 | 进程启动时刻 | 进程状态 |
|---|---|---|---|
| macOS | `darwin:` 加 `kern.bootsessionuuid`（每次开机一个） | `ps -p <pid> -o lstart=,stat=`，执行时固定 `LC_ALL=C` 与 `TZ=UTC` | 同一条命令的 `stat` 列 |
| Linux | `linux:` 加 `/proc/sys/kernel/random/boot_id` 加 `/proc/self/ns/pid` 的取值 | `/proc/<pid>/stat` 第 22 字段（自开机起的时钟滴答数），从最后一个右括号之后切分 | 同一文件的状态字段 |

- pid 空间标识相等才核对 pid：它相等说明是同一个内核实例里的同一个 pid 命名空间。主机名会重名（克隆的镜像、容器、不同网络下的同名机器），重名会把另一台机器上的进程误判成已不在，所以主机名只用于显示，不参与判定。
- 启动时刻用来挡 pid 复用：复用者的启动必然晚于原进程退出，原值不会相等。
- 僵尸进程算已退出；被暂停的进程算还在（它过了期限由判定的第二行处理）。
- 任何一项取不到（沙盒、`/proc` 受限、命令不存在）时，建 run 那一侧不写 `launcher`，核对那一侧按核对不了处理，都回落到期限。
- 其它平台不支持：三个包实际只能在 POSIX 系统上运行（用了 `fcntl` 与进程组）。

实测（一台 macOS 与一台 Ubuntu）：

- macOS：同一进程的 `lstart` 连读两次、换语言环境变量后再读，三次相等；不固定 `TZ` 时输出随本机时区变，所以必须固定；被暂停的进程 `stat` 以 `T` 开头；已退出、未被父进程回收的进程 `stat` 为 `Z`，这时 `os.kill(pid, 0)` 仍然成功，只看它会误判为存活；回收后 `ps` 以退出码 1 结束、没有输出。
- Linux：同一进程的滴答数连读两次相等；被暂停为 `T`，僵尸为 `Z`，`os.kill(pid, 0)` 对僵尸同样成功；进程名里带空格与括号时，从最后一个右括号之后切分取到的字段正确；同一台宿主上，容器里读到的 `boot_id` 与宿主相同、pid 命名空间不同，所以标识里必须带命名空间。

## 边界与已知局限

run 到终态之后各执行方式下还会发生什么，按 code 现有的结构逐格列出，不作统一的概括：

| | 前台执行 | 本机后台 | 云端后台 |
|---|---|---|---|
| run 级终态被改 | 不会 | 不会 | 不会 |
| 认领并启动新的 job | 不会：认领与重试前的检查被拦 | 不会：认领被拦 | 不会：认领被拦 |
| 检查已通过、启动还没有完成的 job（调用未发出、调用中、句柄未返回；首次启动与重试都算） | 会启动；发起进程下一次写运行态时发现 run 已结束，对它发停止 | 会启动；推进进程还在时由它的计时在截止时刻停止 | 会启动；没有组件再去停它（Lambda 遇到已结束的 run 不再处理，0034 已接受的窗口） |
| 已经在跑的 job | 发起进程还在时由它停止；它被暂停或卡死时要等它恢复；它已不在时见下 | 推进进程还在时由它停止；已不在时见下 | 到期收尾之前都已按超时处置；处置之后才出现的 task 同上一格 |

执行方已不在、又没有别的组件去停时，留下的执行没有期限兜底：

- 本机 worker 靠核验所属进程是否还在来自行退出（[0024](./0024-worker-core-protocol.md)）。这个核验有已知的失效情形：worker 核验的是传给它的所属进程 pid，所属进程成了未被回收的僵尸时这个 pid 仍然查得到；worker 经包装进程启动、或所属进程在核验启用之前已经退出时，没有「直接父进程变了」这条辅助线索可用，核验可能一直不触发。所属进程的 pid 在被发现消失之前被复用时，它也被误认为还在。本 ADR 的判定能认出僵尸与 pid 复用，worker 的核验不能，所以会出现 run 已被记为已结束、本机 worker 仍在执行的情形。
- 云端 task 不会因为 run 结束而停。worker 不按预算计时自停（0034「job timeout」节）；浏览器会话与设备会话各有存活上限，但会话到期不保证 task 退出：确定性 step 可以一直等下去。所以前台 `run --backend cloud` 的发起进程消失之后留下的 task，以及云端后台 run 结束之后才启动起来的 task，可能继续执行并计费，直到有人在 ECS 上停掉它。前一种是今天就有的行为，本 ADR 不改变它，也不为它担保任何上界。

处置（`settle-runs`）只改记录，不停任何东西；表里的停止都是执行方自己做的。

其它局限：

- 结构版本升到 2 之后，版本 1 的运行定义在 `status`、`explain` 与推进器那里读不了（`list-runs` 仍能列出），它们也没有期限与发起进程标识，不处理。产品没有使用者，不为它们另设出口。
- 永远不会被处置的未结束 run 有三类，`status --wait` 对它们照旧只等待并说明原因：没有期限，且发起进程核对不了（换了机器、重启过）或建 run 时没能记下标识（沙盒、权限）；后台执行标记读不出或不合法（即使期限已过）；运行态本身读不出。
- 重启过的同一台机器与另一台机器分不开，一律按核对不了处理、回落到期限。不用跨重启稳定的机器标识来补：它会随镜像克隆被复制，认错的方向是把还在执行的 run 记为已结束。
- 判定方的时钟比发起方快出 300 秒以上时，一个仍在期限之内的 run 会被提前记为已结束，发起进程随后停手。同一种情形下若发起进程已经得出全部真实结果、只差收尾那一次写，记录是 `error` 而判定明细里是真实结果，`run` 进程的终端输出会说明。两者都要求时钟偏差超过 300 秒加这个 run 离期限的余量。

## 被拒方案

- **期限只当推定阈值、执行方不遵守**：见决策二的理由。由此还要引出两条补丁式的规则（同机确认进程还在时不处置；真实结果覆盖处置写下的 `error` 并清除说明），都随它一起不取。
- **真实结果覆盖处置写下的终态**：终态之后再变对上层是错的行为，见决策五。
- **靠期限加余量证明执行已停**：尾段与余量都是预算，时钟也可能有偏差，证明不了。收尾的安全改由「终态不可变、认领以未结束为条件」承担。
- **到期时把未启动的 job 记为 `error` 或 `skipped`**：run 的时间用完不是这些 job 的原因。记 `error` 要么沿用启动失败的补偿（错误类型与说明都对不上，认领之后退出记录没写成还会留下一个没有人管的在跑状态），要么新设一种记录；记 `skipped` 在后台路径上同样要新设一种记录。保持 `pending` 加 run 级说明不需要这些，也与处置的写法一致。
- **到期时把在跑的 job 一律改判为超时**：反转 0034 机制二「内容已完整的不改判」，同一个 job 还会因为停止请求到得早晚在四种执行方式下得到不同结论。
- **期限与标识都放运行态记录的顶层**：期限是 run 的规则，放在只由 adapter 读写的附加属性里，core 的调度与推进就得绕开模型去拿它。**都放运行定义**：发起进程标识不是「要执行什么、怎么执行」，还会随机读输出带出主机名与 pid。
- **期限不存、读时现算**：停止宽限不在任何记录里；算式随 CLI 版本变化时，同一个 run 在不同版本下会算出不同的期限，而它必须是各执行方与所有读者共同认的那一个时刻。
- **同一 run 下另立一条记录放标识**：现行的建 run 不是事务写，多一条记录就多一处要协调的一致性；列举每个 run 多读一个条目或文件。
- **只看 pid 是否存在**（现有 code 判断进程或进程组存活的做法，`os.kill(pid, 0)` 与 `os.killpg(pgid, 0)`）：pid 被复用或进程是僵尸时都判为存活，做不到立即判定；主机不同也无从知道。
- **引入 psutil**：为取一个启动时刻加一个带编译扩展的依赖；它在 Linux 上给出的是由开机时刻换算的墙钟浮点数，系统时钟被校正后同一进程前后读到的值可能不等，按「不等即被复用」处理会把活着的进程判成已不在。
- **用主机名或跨重启稳定的机器标识判「同一台机器」**：见决策八与「边界」。
- **使用者单独配置 run 级期限**（0034 预留的 `--default-run-timeout`）：期限要保证不早于各 job 预算能合法用到的时刻，单独配置就得再定义它与 job 预算冲突时谁让谁；现在只由 job 预算推出。
- **让使用者强制把某个 run 记为已结束**：判定不靠使用者担保是 owner 定的原则；不超时又核对不了的 run 是这条原则的代价，记在「边界」。
- **心跳或租约**：见「重议闸门」。

## 实测项（实装时逐项核，结果内联回这里）

1. 本机后端：前台 run 执行中把 CLI 进程 SIGKILL，同机 `settle-runs --dry-run` 报发起进程已退出、不写；`settle-runs` 写入 run 级 `error` 与说明，各 job 状态不变；`status` 与 `list-runs` 的显示与退出码符合决策六、七。
2. 本机后端：建 run 之后经过若干次 job 状态写回，`launcher` 仍在 `run_state.json` 里。
3. 前台到期：把期限设到执行中途，发起进程不再启动新的 job、在跑的 worker 按超时停止、run 级收尾为 `error` 并带 run 级说明、未启动的 job 保持 `pending`、已结束的 job 的判定明细齐全、报告里 run 级是 `error` 加同一句说明；云端后端同样，在跑的 task 被停止。
4. 暂停后恢复：发起进程被 SIGSTOP 到期限之后，别处先处置；SIGCONT 之后它的下一次认领被拒、对在跑的 worker 发停止，收尾不覆盖已有的终态，终端有说明、退出码非零；本机与云端各一次。
5. pid 复用：把记录里的启动时刻改成另一个值，判为已退出；僵尸进程判为已退出。
6. 云端后端：`run --backend cloud` 执行中把 CLI 进程 SIGKILL，同机处置成功；处置后 run 离开 `live` 分组，下一趟清理不再把它当占用者；`list-runs` 的读量与请求数不因新属性变化。
7. 另一台机器或容器里对同一后端查询：期限加 300 秒之前不动，之后处置。
8. 终态不可变：处置与前台的 job 状态写交错进行，run 级不出现从终态回到 `running`；对已有的 run 再次建 run 失败且不改任何东西（云端包括不重写已卸载到 S3 的内容），两个后端各核一次。
9. 两个 `settle-runs` 同时处置同一个 run，只有一个写成。
10. 本机后台 run 到期：推进进程在跑时，到期后在跑的 job 按超时停止、未启动的 job 保持 `pending`、run 以 `error` 结束并带 run 级说明、报告生成；推进进程被杀之后过了期限再执行一次 `status --wait`，这一次接力把 run 推进到结束，不启动任何 job。
11. 本机接力不抢先：原推进进程到点催停、worker 在停止宽限内正常收尾时，同时进行的 `status --wait` 不把这个 job 记为超时，它保留完整的判定。
12. 云端后台 run 到期：部署后提交一个期限落在执行中途的 run，没有任何人查看，期限到时在跑的 task 被停止、未启动的 job 不再启动、run 以 `error` 结束；核对期限时刻的定时触发确实发出、Lambda 日志里没有异常。
13. 四路一致：前台与后台、本机与云端各一个到期的 run，对照 run 级状态与说明（`status --json`）、各 job 的状态（`status --json`）与已结束 job 的错误类型和说明（判定明细，经 `explain` 读），四者一致。
14. 内容完整的不改判：让一个 job 在期限之前给出完整内容、收尾越过期限，它在四种执行方式下都保留原判定；这个 run 没有未启动的 job 时，run 级按聚合得到真实结果、不带到期说明。
15. 前台重试：job 因网络故障重试时照常重新启动、不被自己的认领拦住；退避期间 run 被别处记为已结束时不再重新启动；经过开始执行与结束两次状态写之后，认领时刻仍在运行态里。
16. 到期收尾与认领并发：一个推进方读到「没有在跑的、仍有未启动的」之后，另一个推进方的认领落下，前者的收尾写被条件挡下、run 没有结束，新认领的 job 在期限时刻被停止；本机与云端各核一次。
17. 云端期限触发承担处置：让一个 job 自己的超时触发缺失、worker 不出事件，期限时刻的触发仍把它停掉并使 run 结束。

## 重议闸门

- **心跳或租约**：跨机器的判定只能等到运行期限，宽松的期限可以是实际时长的数倍；不超时的 run 换了机器就没有出口。出现「需要在另一台机器上早于期限确认发起进程已不在」的使用需要时，再议由发起进程定期续写的心跳或租约（它们作为写者互斥的手段在 0030、0034 里是被拒方案，这里是另一个用途）。
- **停掉遗留的云端 task**：前台 `run --backend cloud` 的发起进程消失后，以及云端后台 run 结束之后才启动起来的 task，可能继续执行并计费，没有期限兜底（见「边界」）。owner 不接受这个范围、或它成为可见的费用问题时，再议处置时一并停 task、云端启动之后复查一次并停掉不该再跑的 task，或让云端组件处理前台 run 的退出。
- **强制处置**：不超时又核对不了的遗留 run 积累成清单里的常态内容时，再议一类由使用者确认的处置。
- **使用者可调的 run 级期限**：由 job 预算推出的期限对某类 run 明显过宽、影响到 CI 排期或费用时，再议单独的配置项。
