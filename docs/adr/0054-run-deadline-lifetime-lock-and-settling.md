# 0054. 运行期限与遗留前台 run 的收尾：每个 run 遵守由 job 预算推出的期限，终态不可变、执行方服从记录，settle-runs 把发起进程已不在的 run 记为已结束

> **Status:** Accepted（2026-11-14）—— 设计经 owner 逐条裁定：运行期限是硬约束，前台与后台、本机与云端的执行方都遵守；run 级终态对所有写入方不可变；判据用最初定的两条；期限进运行定义而发起进程标识放运行态记录顶层；云端 run 留下的 task 由云端后端自己停掉，在现有的 Lambda 里做（决策九）；job 的墙钟预算有一个产品上限、不再有不超时（决策十）。实装分批进行，「实测项」的结果随批内联；它改变的其它 ADR 条文与 CONTEXT 词条在对应的实装批里随 code 一起校准（见「对既有文档与 code 的影响」），0041 文末「遗留的非终态 run」重议闸门在 `settle-runs` 落地的那一批关闭。

## 背景与问题

前台 run（`run`，本机后端与 `--backend cloud` 都算）只有发起它的那个 CLI 进程会推进：两个云端 Lambda 与本机的接力都只处理带后台执行标记的 run（[0034](./0034-detached-batch-reconciler.md)「filter 必须区分写入者」）。这个进程不写 run 级终态就消失时，run 永远停在 `pending` 或 `running`。code 里这样的路径有四条：进程被 SIGKILL 或宿主失联；收到 SIGHUP（只装了 SIGINT 与 SIGTERM 的处理器）；`run --backend cloud` 运行期落库抛出 botocore 异常后直接以退出码 1 返回；调度抛出其它未捕获的异常。

留下的 run 没有出口，后果有四处：

- `status --wait` 对它只等待、不接力，会一直等下去；`explain` 还提示「可先用 status --wait 等到终态」。
- `list-runs` 的未结束部分不截断（[0041](./0041-agent-facing-cli-affordances.md) 决策七），这类 run 只增不减。
- 云端的清理协议把 `live` 分组里的 run 当作 worker 版本的占用者（[0038](./0038-worker-image-delivery.md) 残余风险④），它引用的版本一直回收不了。
- 没有任何记录说明「这个 run 最晚什么时候必然已经停手」。各 job 有墙钟预算，但它是进程内用单调时钟做的保护：系统休眠时单调时钟不走，各 job 的截止时刻顺延休眠的时长；进程被暂停时它不检查截止时刻；落库或云端调用卡住时也没有上界。所以从外面看，一个前台 run 可以在任意晚的墙钟时刻仍在执行。

原先的写入规则也与「把遗留 run 记为已结束」不相容，三处都能改掉一个已有的 run 级终态（决策五改写了这三处）：

- 前台执行者的 `finalize_run` 原是无条件写。
- 本机存储的前台写路径（`update_job_state`、`finalize_run`）原是不加文件锁的读改写，与别的进程并发时可能把 run 级写回 `running`。
- `create_run` 与 `save_run` 原是无条件的整份重写，对一个已有的 run 再调一次就回到初始状态或被改成任意状态。生产 CLI 不这样调，但端口允许。

0041 文末的重议闸门原定「遗留成为清单常态时再议」。它的两个触发条件都是使用面的证据，产品现在没有使用者，所以关闭它的依据不是触发条件已满足，而是 owner 的判断：只增不减、没有出口的状态是设计上的缺口，索引迁移的真实环境核验里已经实际留下过一条。

## 决策

### 一、定位与范围

- 收尾（`settle-runs`）是系统对遗留状态的处理：认出发起进程已经不在、或已过运行期限的前台 run，把它记为已结束。它不是「使用者放弃一个 run」，判定只靠建 run 时记下的事实，不靠使用者事后担保，拿不准就不动。
- 收尾只处理不带后台执行标记的未结束 run。带标记的后台 run 到期由推进步骤自己结束（决策二），推进已中断的由 `status --wait` 接力完成；取消一个后台 run 是另一件事，不在本 ADR。
- `run --no-report` 不建任何记录，不在范围内。

### 二、运行期限：进运行定义，所有执行方都遵守

每个 run 在建立时得到一个运行期限 `deadline_at`（UTC 的 ISO 时刻），它是这个 run 的一条规则：

`deadline_at = created_at + 900 秒 + Σ（各 job 的墙钟预算 + 每 job 尾段）`

- 每 job 尾段：本机后端取 `2 × G + 10` 秒，云端后端取 210 秒（隧道存活时间上限已在用的 `CLOUD_PER_JOB_MARGIN_S`）。G 是停止宽限：前台 `run` 取这次调用解析出的值（`--grace`、配置文件或各引擎自报值）；本机 `submit` 没有 run 级的宽限，取这个 run 用到的各引擎自报宽限里最大的一个。
- 900 秒是一次性余量，与隧道存活时间上限的一次性余量同值，留给建 run 到起第一个 job 之间的装配与各次落库、云端调用。
- 每个 job 的墙钟预算都是有限的（决策十），所以每个 run 都有期限。
- 求和而不按并发折算：并发大于 1 时真实墙钟小于各预算之和，串行总和对任何并发取值都偏宽，与 `compute_watch_ttl_s` 同一做法。健康的 run 远在期限之前结束。

尾段与余量是预算的取值，不是「执行一定已停」的上界：停止等待预算是执行方愿意等的时长，停止调用本身、起 worker 的调用、落库调用都可能阻塞得更久（0034 已区分等待预算与平台保证）。它们只决定期限定得多宽；收尾的安全不靠它们，靠决策五。取值的来历：前台 run 的 job 从线程池取到它时起算预算（认领时刻就在这时取，见第 2 条），到点后本机一次停止等 G 加约 3 秒、排空等到停止请求之后 G 加 5 秒、仍未结束会再发一次停止，合计约预算加 `2G + 9` 秒；云端的停止等待预算不超过 140 秒，加排空余量与心跳约预算加 146 秒，取 210 秒。job 级重试共享同一个截止时刻，不另外延长。

**落点是运行定义**（`RunMeta`，用户文档里的「提交记录」）。期限由 job 的墙钟预算与停止宽限推出、建 run 时确定、之后不变，执行方要遵守、所有读者都要看，它与 job 的墙钟预算、并发上限是同一类东西，后两者已在运行定义里。运行定义的键集因此变化，结构版本由 1 升到 2；按 [0037](./0037-distribution-and-packaging.md) 决策 7，读端拒读版本不是 2 的记录，产品没有使用者，不为版本 1 的记录做兼容。云端把它摊成 META 条目的顶层属性（同结构版本与写出版本的做法），列举时投影这个属性，不取回整份运行定义。读端把缺失、为空或不是带时区的合法时刻的 `deadline_at` 当作定义违约拒绝，与空预算同一处理：每个 run 都有期限，各执行方与判定拿到的必须是同一个可比较的时刻。

**所有执行方都遵守期限，前台与后台、本机与云端是同一种表现。** 规则只看当前时刻与各 job 的状态，任何一次推进都能独立算出同一个结论，不需要记住期限那一刻发生过什么：

1. 当前时刻已过 `deadline_at` 减 60 秒，不再启动新的 job（含同一个 job 的重试）。提前 60 秒是启动余量：从发出启动到 job 真正开始执行需要时间，卡着期限启动的 job 来不及被正常停止。
2. 在跑的 job 的截止时刻以 `deadline_at` 封顶：取「认领时刻加它的墙钟预算」与 `deadline_at` 中较早的一个，到点的处理与 job 自己的预算到点完全相同，包括 0034 机制二已有的规则：内容已经完整、随后正常退出的 job 保留它的判定，不因为收尾越过了截止时刻而改判。被期限截断的 job 记为 `error`、类型为超时，说明按实际起作用的那个时刻写（可由认领时刻、job 预算与期限重算出是哪一个）。预算从认领时刻起算，四种执行方式相同（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 2 与 0034 已定后台自认领起算）：认领时刻是认领方在发出认领的那次写之前取的墙钟，随认领写进运行态；前台在线程池取到 job、通过起 worker 之前的检查之后取它，没有记录的 `run --no-report` 在同一位置取、不写。job 自己的截止时刻就是认领时刻加预算，与 `deadline_at` 同按墙钟比较，起作用的是两者里较早的一个，相等时算 job 自己的预算到点。前台原先按单调时钟计 job 预算，改按墙钟（理由见下「检查用墙钟」一段）：两个截止时刻都由认领时刻、预算与期限这三个已经记下的值算出，前台与后台按同一个算法得到同一个结论，不需要另记「实际是哪一个起了作用」。被期限截断的 job 的说明是「这个 run 已超过允许运行的时间，job 被中止」，被自己的预算截断的仍是原有的超时说明；两句都由前台与后台共用的终结函数给出。超时的停止原因仍只有一种，起作用的是哪一个截止时刻是终结函数的另一项输入、只决定说明：期限截断的 job 与预算截断的走真值表的同一行，「内容已完整不改判」等已有规则原样适用，不另立一行。停止等待、排空这些时长仍按单调时钟计，它们不进记录。
3. 已过第 1 条的时刻、没有在跑的 job、仍有未启动的 job：run 级以条件写收尾为 `error`，说明是「已超过允许运行的时间」（写在 run 级 `message`：run 的时间用完不是哪一个 job 的原因）。未启动的 job 保持 `pending`，不替它们下结论。
4. 没有在跑的 job、也没有未启动的 job：照常按各 job 的状态聚合收尾，不管当前时刻是否已过期限。被期限截断的 job 自身是 `error`，聚合自然得出 `error`；全部 job 都给出了完整内容的 run 得到它们的真实结果。

四条里的「已过」「到了」一律指当前时刻严格晚于那个时刻：停止启动的时刻、期限与 job 的截止时刻三处取法相同，与前台原有的预算到点判断一致；job 的截止时刻恰等于期限时，两处判断在同一时刻得出同一结论。

一次前台执行可能因三种原因停下：到期（第 1、2 条）、因 fail-fast 或使用方中断而中止、发现 run 已被别处记为已结束（决策五）。它们同时或先后成立时，各 job 的结果这样定：

- 排队中、从未启动的 job，起 worker 之前依次检查。已过停止启动的时刻（第 1 条），或已发现 run 被别处记为已结束：不启动、不产出判定、运行态保持 `pending`。否则 run 已因 fail-fast 或使用方中断而中止的，照旧记为 `skipped`。都不成立才认领并启动。不产出判定的两种排在前面，因为它们都表示不再为没有执行过的 job 下结论：被期限截断的 job 是 `error`，开了 fail-fast 时它会触发中止，不能因此把未启动的 job 改记为 `skipped`；run 已被别处结束时记录已是终态，job 不动（决策六）。已经记为 `skipped` 的 job 不因后来成立的原因改回。
- 在跑的 job，停止原因按 0034 机制二的首次仲裁落定一次、之后不改：做出停止决定的那一刻它的截止时刻已过即为超时，否则为中止，中止的说明取最先成立的那个来源。「最先成立」指最先登记：三种来源都登记在 run 的中止标志上、只记下第一次，fail-fast 在判定得出时登记，发现 run 被别处结束在发现时登记（写 job 状态时的发现，在那次落库回调返回之后当场登记），使用方中断在调度循环轮询到它时登记（两次轮询之间到达的以轮询时刻为准，同一次轮询里先读停手信号、再处理中断）。发现 run 已被别处结束是 fail-fast、使用方中断之外的第三种中止来源（说明是「这个 run 已被记为已结束，job 被中止」），走同一个仲裁、不另立规则；内容已经完整的 job 保留判定。判定照常写入（run 级已是终态时只写 job，决策五）。
- 上一次尝试已经结束、正在等待重试的 job：三种原因下都不再重试，保留上一次的判定并注明没有再重试及原因，运行态随这个判定落定。重新启动之前的检查与排队中的 job 是同一次序，只是最后一步的认领换成读一次 run 级状态（决策五）：已过停止启动的时刻；已发现 run 被别处记为已结束；已因 fail-fast 或使用方中断而中止；这时读到 run 级已是终态。注明的原因取最先命中的一条。

run 级只要有 job 保持 `pending` 就按第 3 条收尾，优先于使用方中断的 `aborted`（[0031](./0031-job-lifecycle-states-and-severity.md) 决定三的例外）；退出码是另一回事，处理过使用方中断时仍按信号取。run 已被别处结束时，本次执行的 run 级结果不成为记录：收尾写被已有的终态挡下（决策五）。裁决函数对这种情形给 `aborted`：万一收尾写成了（记录其实没有结束，属于不该发生的不一致），写下的也不是 `passed`，因为发现之后执行已中止，各 job 的判定不代表这个 run 的结果。有 job 没有判定而不属于这两种原因时，裁决函数同样给 `aborted`：「有 job 没有判定的 run 不会得到 `passed`」由它自身成立，不靠调用方传对标记。

第 3 条的「没有在跑的 job」必须在提交的那一刻仍然成立，光靠读到的快照不够：另一个推进方可能在停止启动的时刻之前通过了时间检查、认领写在这次读取之后才落下，随后它照常启动 job。所以第 3 条的收尾写除了要求 run 级未结束，还要求从读到运行态以来没有新的认领：运行态带一个认领计数，每次认领成功时加一，收尾写以它等于读到的值为条件（本机在文件锁内重读后再判）。条件不成立即放弃这一次收尾、继续推进，新认领的 job 照第 2 条在期限时刻被停止。第 4 条不需要这个条件：没有未启动的 job 就不会再有认领。

认领计数是运行态模型（`RunState`）的一个字段：建 run 时为 0，只有认领成功的那一次写把它加一，其它写入口不改它；写端恒写这个键，读端缺键读作 0。它随运行态序列化，出现在 `status --json` 里，作为诊断用的键。收尾写的计数条件是可选的：给出期望的计数时才比较（本机在文件锁内重读后判，云端进条件表达式），不给时只判 run 级未结束。

run 级的状态与说明以条件写提交的那一份为准：`RunResult` 增加 run 级说明，第 3 条收尾的 run 在 `RunResult` 与报告里同样是 `error` 加这句说明，未启动的 job 标为没有执行。`RunResult` 的 job 清单只装有判定的 job（[0031](./0031-job-lifecycle-states-and-severity.md) 决定一的补充不变：判定记录只有终态），未启动的 job 不在其中；文本汇总与报告把运行定义里有、判定清单里没有的 scope 列出并标为「没有执行」。`run --json` 顶层增加 run 级 `message`（键恒在，没有时为 null），不另设「没有执行」的清单：它就是 `run_meta.jobs` 与 `jobs` 的差，只在 run 级 `message` 有值时出现，另设一份是同一个事实写两处。run 级的 `error` 与说明由前台与后台共用的一个裁决函数给出，不靠各 job 状态的聚合（全部已启动的 job 都通过时聚合会得出 `passed`）。判定清单不全之后，设备计量两项合计是否出现改按运行定义里有没有设备目标判断、不按判定清单（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 7 的出现条件不变）：设备 job 全部没有启动时两项都是 0，不省键。写的次序不变：已结束的 job 的判定明细先落库，再条件写 run 级终态，最后生成报告。

各执行方的落实：

- 前台执行（`run`）：调度循环按墙钟检查，过了第 1 条的时刻不再从队列里启动 job、也不再重试；到了 `deadline_at` 把在跑的各 worker 的截止时刻视为已到并发停止请求，等它们结束后按第 3、4 条收尾。停止启动一经成立不撤销：任何一次检查观察到已过第 1 条的时刻就记下，此后起 worker 之前与重试之前的检查都按已过处理，收尾时判断第 3 条也用这个记下的事实、不重读时钟，系统时钟回拨不会抹掉已经发生的停止启动。job 的截止时刻同样一经观察到已过就不撤销：触发停止决定的那次检查看到已过，首次仲裁即按超时落定，不因随后读到回拨的时钟落成中止。规则本身不变（真实的时刻只会越来越晚），记下它们只是不让回拨的时钟撤回已经得出的结论。未启动的 job 不落判定明细、运行态保持 `pending`。墙钟由组合根注入调度循环，缺省取系统时钟，调度循环自己不另取；组合根注入的是它写时间戳的同一个读取点，记录里的时刻只有一种写法。认领时刻由调度循环从注入的墙钟取一次、交给认领写，写进记录的值与算截止时刻的值是同一个。core 里的墙钟时刻是带时区的时刻值，ISO 串只是记录里的写法，解析与写出各只有一处；不带时区的值一参与比较即报错，误注入的时钟不会悄悄得出结论。`deadline_at` 减 60 秒这个提前量、run 级说明的文字与「是否已过」的判断放在 core，前台与后台共用一份。前台按第 3 条收尾时不带认领计数的条件：发起进程是这个 run 唯一的认领方，认领在工作线程里同步完成，收尾发生在线程池排空之后，没有在途的认领。`run --no-report` 没有记录，照样遵守第 1、2 条，第 3 条只体现在 `RunResult` 上。
- 后台推进（本机的推进进程与 `status --wait` 的接力、云端的 Lambda，都经 core 的同一个推进步骤）：过了第 1 条的时刻，推进步骤不再认领；认领 job 时算出的截止时刻以 `deadline_at` 封顶，本机的计时、云端的一次性定时触发与防御性超时扫描都按封顶后的时刻；满足第 3 条时为已结束的 job 落判定明细、条件写 run 级 `error` 与说明、生成报告。原先的收尾只在全部 job 都到终态时才走，落判定明细与生成报告的两步、以及它们依赖的两种投影（[0031](./0031-job-lifecycle-states-and-severity.md) 的收尾投影契约）改为在有 job 未启动时照常工作。实装时定下的细节如下。
  - 时刻：推进步骤自己不取时钟，经宿主注入的时钟取时刻（与前台同一个读取点）。每次读取运行态之前取一次，用于随后的推进决策与收尾时刻（同一轮里重新读取时重新取；各次取的都是墙钟，回拨时收尾时刻可以早于这一轮里的认领时刻，记录不保证两者的先后）；每次认领之前再取一次，作这个 job 的认领时刻，并重做一次停止启动的检查（已过即不认领）。一轮里靠后的认领因此不沿用轮首的时刻：前面的读取与启动调用有耗时，沿用会让靠后的 job 少拿到预算。这一轮里有认领因为已过停止启动的时刻而没有做时，推进步骤在同一轮里重新读取运行态与事件、按已过停止启动再决策一次（这一轮里先前认领成功的 job 计入其中），不拿轮首的快照收尾，也不就此返回：云端没有别的东西会再触发一轮，停在这里的 run 明明满足到期收尾却没有人收。重新决策只做一次，直接按已过停止启动处理、不再拿重新取的时刻判断，系统时钟在这之间回拨也不会让这一次又提议启动。启动调用失败时也再取一次时刻，记为这条退出记录的退出时刻：它晚于这个 job 的截止时刻时投影按超时处理，与前台起 worker 失败的分支得到同一个判定；不晚于就是启动失败。后台的启动失败补偿交给终结函数的输入改为与前台相同（退出码未知，带启动失败的原因），不再用平台失败的哨兵退出码：两条路径原先对同一个启动异常给出两句不同的说明，四种执行方式的对照（实测项 13）包括这类 job。
  - 决策：是否已过停止启动的时刻是推进决策（`plan_next`）的一项输入，决策仍是一处纯函数。已过时不再提议启动；没有在跑的 job 而仍有未启动的 job 时提议到期收尾；其余不变。这里的「未启动」指这个 job 在事件流里没有任何记录。有记录而投影仍是 `pending` 的 job（别的推进方刚认领、worker 只发出了结果未知的建会话尝试）说明已经有人启动了它，这一轮不到期收尾、继续推进。「哪些 job 在事件流里有记录」由推进步骤从这一轮读到的事件算出、作为另一项输入交给推进决策，决策本身不碰存储。到期收尾是推进决策给出的一种单独的动作，与第 4 条的收尾分开：只有它的收尾写带认领计数的条件，两种收尾在推进步骤里由动作本身区分，不靠附加的标记。
  - 快照：推进步骤先读运行态、后读事件，手里的运行态可能比事件旧。收尾（第 3、4 条都算）之前要求每个有记录的 job 在这一轮读到的运行态里都带认领时刻（读不出或不带时区的同样算不带，后台各处的时刻都经 core 的同一处严格解析读回）；有一个不带，说明它是在这一轮读运行态之后才被认领的，这一轮不落判定明细、不收尾，按继续推进处理，下一轮读到新的运行态再做。不用「取不到认领时刻就按预算说明」这样的回落：那会让拿着旧运行态的推进方用错的说明覆盖别人已经写对的判定明细。
  - 截止时刻与说明：认领时由认领时刻、预算与期限算出这个 job 的截止时刻（与前台同一个算法），随启动交给启动器。本机的推进进程按墙钟检查它（每个在跑的 job 一个按短间隔读墙钟的检查，取代原先从 worker 启动起按单调时钟计的定时器）：检查读的墙钟由组合根注入启动器，与推进步骤取认领时刻的是同一个读取点，两处比较的才是同一个时钟；间隔只决定到点之后最多晚多少发出停止请求，不进任何记录；检查持续到 worker 进程退出、不止到事件流结束，关了事件通道却不退出的 worker 过了截止时刻同样被停下。退出记录另带一项事实，退出时刻：本机是推进进程看到 worker 退出的那一刻（经注入的墙钟读取），云端是 task 对象里的执行停止时刻（退出观察者与超时处置都从 task 对象取，同一个 task 两处取到同一个值），启动失败的补偿记失败的那一刻；补写的未知退出没有可观察的退出时刻，不带这一项。投影时，退出时刻晚于这个 job 的截止时刻的退出与带超时标志的退出同样处理（内容完整的照旧不改判）：worker 在截止时刻之后、停止请求发出之前自己退出时，本机后台与云端后台得到的判定与前台终结之前的那次检查相同。观察者只记事实，不判断是否已过截止时刻：截止时刻要由运行态与运行定义算出，云端的退出观察者只看 task 对象；判断放在各执行方式共用的投影里，规则只有一份。超时标志因此只表示发过超时的停止请求、或补写时已判为超时，不兼管「退出时已过截止时刻」。本机的推进进程里，看到 worker 退出（读退出时刻、读超时标志）与检查线程的到点决定（确认还没有看到退出、读墙钟、置超时标志）互斥进行，先后只有一种：已经看到退出之后检查线程不再置标志，退出记录里不会出现「退出时刻不晚于截止时刻、却带着之后才置上的超时标志」的组合。云端的一次性定时触发定在这个时刻，Lambda 对超时触发的复查与防御性超时扫描按同一个算法重算。定时触发早于截止时刻时处置方等到那时再停；醒来之后重新读墙钟确认已到，还没到（等待期间时钟被回拨）就在这次调用的等待额度内接着等，额度用完仍没到的这一次不停止、留给之后的推进检查：发出停止之前必须有一次读到已过截止时刻。后台被截断的 job 的说明同样分两句，投影时由运行态里的认领时刻、预算与期限重算是哪一个截止时刻起了作用，不在退出记录里另记。终结函数的这项输入没有缺省值：前台在认领时算出、后台在投影时重算，两条路径都必须给出它，不会因为漏传而悄悄落到预算那一句。
  - 收尾与报告：run 级的状态与说明由共用的裁决函数给出（第 4 条下它就是聚合），随条件写写入。到期收尾的条件写带上这一轮读到的认领计数。条件写写不成时重读一次运行态：仍未结束（第 3 条下说明读取之后有了新的认领）按继续推进处理；已是终态说明别人已经收尾，照现有的做法按已收尾处理。读不到运行态的那一轮不做到期收尾。报告由推进步骤这一轮的结果直接生成，不再另读一次事件重算：重算用的事件可能已经变了（接力方补写的未知退出之后又被真实的退出码覆盖），得出的结果会与提交的终态不同。报告只由条件写写成的那一方生成，用它这一轮落库的各 job 判定与它的裁决：报告因此与提交的那一份出自同一个快照。推进步骤只在写成时把这一轮的结果随推进结果交还宿主，没写成的一方拿不到结果，结构上无从生成报告；run 级墙钟（运行态的开始时刻到收尾时刻）由宿主在生成报告时补上，因为收尾时刻由那次条件写落下，推进步骤给出结果时还没有这个值。没写成的一方不生成报告（原先收尾分支里写赢写输都生成）。它手里的快照可能与写成的一方不同：它按到期准备收尾时，另一方又认领并完成了别的 job，拿它的各 job 判定去生成报告，会把已经执行过的 job 显示成没有执行；靠比较两方的 run 级状态与说明分辨不出这种不同（两方都是到期收尾时状态与说明相同，没有执行的 job 却不同）。代价是写成的一方在提交之后、生成报告之前中断时，这个 run 没有报告（原先没写成的一方会补上一份）；判定明细与运行态不受影响，宁缺不错。
  - 不记「已过停止启动」：推进步骤是无状态的，每一轮按当前时刻判断。某个推进方的时钟回拨或落后时它可能在这个时刻之后又认领，新认领的 job 照样在封顶的截止时刻被停下。认领计数的条件保证的是记录层面的一致：读取之后有新的认领就不到期收尾。它不保证 run 记为终态时没有 worker 还在执行，那属于「边界与已知局限」里已列的情形。
- 本机接力（`status --wait` 处置别人认领、处于执行中、没有退出记录的 job）的判定条件这一步不改，改法已定、随认领方的进程标识一起实装（下一条）。这一步里接力方仍在墙钟过了这个 job 的截止时刻加固定 10 秒之后补写一条未知退出；截止时刻与认领方用同一个算法（以期限封顶），认领时刻读不出或不带时区的 job 没有起算点、不判。补写改为条件写：只在这个 job 还没有退出记录时写入，「没有」的判断与写入是同一次操作，原推进进程恰在接力方查过之后、写入之前落下真实的退出记录时补写不成立，观察到的退出不被未知退出盖掉；补写之后才到的真实退出照旧覆盖补写的那一条（云端超时处置找不到 task 时直接写的那一条同样是条件写）。这个判定条件保证不了「认领方还在、会自己催停时接力方不抢先」：10 秒比停止宽限短，worker 还在宽限内收尾时接力方就会补写，run 若在补写与真实退出之间完成收尾，这一次收尾按超时提交，run 级的结果与报告就此定下；期限让许多 job 在同一时刻到点，这种情形比以前常见。
- **本机接力的改法**（owner 2026-11-16 定，尚未实装；实装之前上一条的判定条件照旧）。接力方不再凭时钟推断认领方是否已经收尾完，改看认领方的进程是否还在：
  1. 认领时把认领方的进程标识（与决策三、八的发起进程标识同一种）随认领写进这个 job 的运行态；推进进程与每个接力的 `status --wait` 认领时都写自己的。
  2. 认领方还在时接力方不补写，不论过了截止时刻多久：保护所有还在的认领方，没有期限上的例外。
  3. 核对到认领方已经退出时，接力方立刻以条件写补记结果未知的退出，并记下发现的时刻。发现的时刻只说明何时确认认领方已经退出，不是 worker 的退出时刻，也不作超时的依据：认领方不在了不说明 worker 已经停下，更说明不了它何时停下。是否超时仍由收尾投影按已有的退出事实统一判，不为接力单设规则；这条补写没有可观察的退出时刻、也不带超时标志，按未知退出的既有归因处理（[0034](./0034-detached-batch-reconciler.md) 机制二的真值表），不论发现得早还是晚都不记为超时。
  4. 期限之后的兜底只结束 run：本机的 `status --wait` 对后台的未结束 run 持续接力时，当前时刻严格晚于运行期限加 300 秒，而仍有执行中、没有退出记录、认领方还在或核对不了的 job，就按决策六的写法以条件写把 run 记为 `error`，说明是「已超过允许运行的时间（已记为已结束）」。这次兜底不改任何 job 的记录，不给它们补结果。它是本机后台接力新增的一种处置，不扩大 `settle-runs` 的范围，接力也不因此去推进前台 run。写入口及它与同一轮推进的次序在实装那一批的设计里定。
  5. 「run 能结束」以有一个接力进程在持续执行为前提。

  理由：靠时钟加一段固定时长的做法已经三次失守。固定 10 秒比停止宽限短；改为墙钟超过「截止时刻加两倍停止宽限加 10 秒」，墙钟在宽限内前跳时条件立刻成立，合盖休眠之后恢复即是；再改为接力方从自己观察到已过截止时刻起按单调时钟等满这段时长，一次只被接力方看到的短暂前跳加上不撤销的首次观察，使接力方在认领方刚发出停止时就补写（后两种都由另一家模型用真实的 worker 与停止信号复现）。三次是同一种结构：接力方只凭自己看到的时钟读数，推断认领方要么不在了、要么已经收尾完，手里没有来自对方的证据。把这段时长再放宽、或让接力方看到墙钟回拨就重新计时，都还是这种结构：认领方被暂停之后在这段时长快满时恢复并催停，接力方照样紧接着补写。不用心跳或租约（见「重议闸门」）时，对核对不了身份的记录，「认领方已经不在」与「认领方还在、稍后恢复」留下的记录相同，「不抢先」与「每个 job 都得到结果」不能同时无条件成立；取前者，后者退为「run 能结束」，job 的显示由 run 级终态与它停留的状态推出。期限加 300 秒之后给每个 job 补未知退出的做法不取：这个时刻证明不了认领方已经收尾完（墙钟一次跳到它之后时，接力方先拿到执行机会就会抢先）。细则在实装那一批的设计里定：标识与认领是同一次原子写、标识在随后的各次写里原样保留、核对的三种结果（已退出、还在、核对不了；僵尸算已退出）、接力方自己认领的 job 不走认领方核对与未知退出的补写，run 级的期限兜底独立判断、不受这一条排除。这个改法不需要接力方知道停止宽限：停止尾段连同接力方向 worker 查询停止宽限的做法已经撤掉，原先设想的把停止宽限记进运行定义也不再做。
- 云端后台 run 另在 `deadline_at` 设一次定时触发（由 kicker 在 run 新建时建立，见决策九；定时触发的命名与授权按 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 资源清单里 job 超时触发的同一形态登记）。这一次触发对所有仍在跑的 job 做超时处置，与各 job 自己的超时触发是同一处理：它们的截止时刻此刻都已到。不靠各 job 自己的定时触发，是因为那些触发是尽力而为地建立的，某一个没建成、它的 worker 又不出任何事件时，没有别的东西会再来推进这个 run。处置引出的退出事件再触发推进步骤，走到第 3、4 条。这一次触发本身调用失败时由平台的异步重试补上；整条触发链都失效时与今天一样，由 `status --wait` 接力。
- 本机后台 run 的推进进程已不在时，下一次 `status --wait` 接力把它推进到结束（前提是运行定义与相关的认领时刻读得出、接力持续执行）：被原推进进程认领而没有退出记录的 job，过了封顶后的截止时刻加 10 秒之后由接力方按上面的条件补写。开始接力时已过停止启动的时刻的，接力方不再启动 job，补写之后按第 3、4 条收尾；还没到的，接力方照常认领并启动余下的 job。

检查用墙钟而不用单调时钟：期限是别的机器也要拿来比较的时刻，而且单调时钟在系统休眠时不走，合盖几小时再打开的进程只有按墙钟才知道自己已经过期。job 自己的预算同理：发起机器休眠期间，云端的 task 与远端的会话照常消耗，浏览器会话的存活时间也是按墙钟由预算推出的；按墙钟计，前台与后台的截止时刻才是同一个算法。代价是系统时钟被大幅调整时，job 的预算随之变长或变短，这是 [0026](./0026-schedule-module.md) 原先让前台用单调时钟避开的情形。

这给每个 run 加了一个由 job 预算推出的总时长上限，是对 0034「job timeout」节「先不做 run 级总墙钟预算」的改变：期限不是使用者单独配置的预算，调整它的途径仍是各 job 的墙钟预算与停止宽限。选它而不把期限只当作「推定发起进程已不在」的阈值，理由是：

- 对测试工具，一次 run 的总时长有上界本身是该有的性质：CI 可以据此排期；云端浏览器会话与真机按分钟计费，休眠后恢复的发起进程会自己把过期的会话停掉，没有人查看的后台 run 也不会无限期挂着。
- 前台与后台、本机与云端同一种表现：「允许运行至」对所有 run 是同一个意思，上层不必按执行方式分别理解。代价是后台 run 的接力有了期限：推进中断之后要在期限之前接力，过了期限 run 以 `error` 结束，要重新提交。
- 清单里这一列的名字是「允许运行至」，硬约束才名副其实。

### 三、发起进程标识：放运行态记录的顶层

前台 run 建立时另写下发起进程标识 `launcher`：pid 空间标识、pid、进程启动时刻的原值，另带主机名（只用于显示）。取法见决策八。它由发起进程在建 run 那一刻确定，之后的每次写都原样保留，查看或处置的一方不重新生成。

落点是本机 `run_state.json` 的顶层键、云端 STATE 条目的顶层属性，与后台执行标记同处：只由存储 adapter 读写，不进 `RunState`、`RunMeta` 两个 core 模型，列举时作为 `RunListing` 的字段带出，core 不据它分支；写入沿后台执行标记的做法，经 adapter 的构造参数给出。

理由：它说的是「谁在执行这个 run」，不是「要执行什么、怎么执行」，与后台执行标记是同一类属性，0034 已定这类属性的位置。它也不该进运行定义：运行定义会随 `run --json` 输出，主机名与 pid 不属于那里。期限与标识因此分在两处，这是按性质分的：一个是 run 的规则，一个是执行它的进程的事实。

本机 adapter 原先每次写回运行态时从模型重建整份文件、只逐个补回后台执行标记，漏补一个键就静默丢失。改为：建 run 时写下的顶层附加键整体原样保留。

### 四、判定：owner 最初定的两条

三个触发面共用一个判定，对前台的未结束 run：

| 情形 | 结果 | 处置 |
|---|---|---|
| 与记录在同一个 pid 空间，这个 pid 不存在、启动时刻与记录不同，或已是僵尸 | 发起进程已退出 | 可立即记为已结束 |
| 上一行不成立，且当前时刻已过 `deadline_at` 加 300 秒 | 已过运行期限 | 可记为已结束 |
| 其余 | 不能处置 | 不动 |

- 第二行不问发起进程是否还在。它安全的依据是决策五：记下终态之后，发起进程即使还在，也不能再改这个终态、不能再认领与启动新的 job，发现之后会停手。期限与 300 秒只决定什么时候可以这样做，不承担「此刻执行一定已停」的证明。
- 300 秒是给时钟偏差与发起进程自己到期收尾留的余量：发起进程按自己的时钟在 `deadline_at` 停手并收尾，别的机器按自己的时钟等到 `deadline_at` 加 300 秒才处置。判定方的时钟比发起方快出 300 秒以上时，处置会早于发起进程自己认为的期限，这个 run 被提前结束（发起进程随后按决策五停手）；它记在「边界」。
- 「同一个 pid 空间」核对不了（另一台机器或另一个容器、同一台机器重启过、记录里没有标识或标识不完整、读不到进程信息）时第一行不成立。标识不完整时不退回只看 pid：只看 pid 分不清复用者。
- 后台执行标记读不出或取值不合法的 run 不当作前台 run，一律不动；运行定义读不出、或 `deadline_at` 不是合法时刻的 run 只有第一行可用。

### 五、run 级终态不可变，执行方服从记录

**终态不可变。** run 级状态只往前走：`pending` 到 `running` 到终态，到了终态不再变。这条规则原先只对后台的条件写成立，现在对端口上的每一个写入口成立：

- 前台执行者的收尾改用与别的写入方相同的条件写（`try_finalize`：只在 run 级为 `pending` 或 `running` 时写，可带说明）。无条件的 `finalize_run` 从 `RunStore` 端口删除。
- 建 run 只在这个 run 还不存在时成立：`create_run` 改为条件写（云端要求条目不存在，本机要求 run 目录里还没有运行态），对已有的 run 再调用即失败、不改任何东西。整份重写的 `save_run` 从端口删除，测试里需要的初始状态经 `create_run` 加各条件写得到。本机的判断与两个文件的写在同一把文件锁内完成。云端在把 step 参数正文卸载到 S3 之前，先以强一致读确认这个 run_id 下的 META 与 STATE 都不存在，已存在即失败、不重写已卸载的正文；随后两次写都带「条目不存在」的条件，写序仍是 META 在前、STATE 在后。
- 本机 adapter 的前台写路径（`update_job_state` 与收尾）纳入现有的 fcntl 文件锁，与 `try_claim_job`、`project_state`、`try_finalize` 互斥；run 级已是终态时 `update_job_state` 只写 job。[0030](./0030-realtime-persistence-seam.md) 决定三「文件锁护 run_state.json 的读改写」由此对全部写入口成立。

理由：终态之后再变，对任何基于状态做事的上层（等待者、清理、以后的界面或服务）都是错的行为：已经返回的退出码撤不回，已经据终态做的处置撤不回。

**执行方服从记录。** 终态不可变只保护记录，不能让执行停下来。要让「记下终态之后不再有新的执行」成立，执行方每次启动 job 之前先认领，认领以 run 级未结束为条件：

- 后台推进本来如此（`try_claim_job` 要求 run 级为 `pending` 或 `running`）。
- 前台执行改为同一做法：从队列里取到 job、第一次起 worker 之前先做同一个认领，认领时刻随之记进运行态。一个 job 只认领一次；同一个 job 因网络故障重试时不再认领（它已是 `running`，再认领会被自己拒掉），改为在每次重新启动之前读一次 run 级状态。认领被拒或读到 run 级已是终态，说明 run 已被别处记为已结束：这个 job 不启动，调度循环对在跑的 worker 发停止请求，然后结束。起 worker 之前各项检查的次序、停手时各种处境的 job 怎么记，见决策二「一次前台执行可能因三种原因停下」一段：发现 run 已被别处结束是一种中止来源。认领排在各项检查之后、紧贴起 worker，免得留下已认领却没有执行的 job。发起进程自己的时钟已过停止启动的时刻时，拦住它的是时间检查；认领被拒这一支在它的时钟落后于处置方时才会走到。认领或读取本身失败（存储不可达）按运行期落库失败处理，与落库回调抛出异常相同。代价是前台每个 job 多一次条件写（认领）。
- 前台此后写 job 状态（开始执行、结束）时保留认领时刻。现在这两处是整项替换，不带认领时刻的写会把它抹掉。做法是落库服务记住每个 job 的认领时刻、此后的写带上它（与代表会话同一做法），存储 adapter 的整项替换不变。
- 前台执行者写 job 状态时发现 run 级已是终态（条件写落到只写 job 的那一支）同样触发停手。为此 `update_job_state` 返回 run 级在这次写时是否仍未结束，两个 adapter 对拍：本机取文件锁内读到的 run 级；云端由两次 run 级条件互斥的写里写成的是哪一次给出，不另读（[0034](./0034-detached-batch-reconciler.md) 机制三③），对写入的任何 job 态都如实。认领、重试之前的读、job 状态写三处的发现汇成同一个停手信号，调度循环不碰存储（[0030](./0030-realtime-persistence-seam.md) 决定一不变），经组合根注入的能力取得它：job 状态写时的发现在那次落库回调返回之后当场读进来，等待循环另与使用方中断同一节拍地轮询它、先于中断读（登记的次序见决策二「一次前台执行可能因三种原因停下」一段）。认领、重试之前的读与停手信号三项合成一个注入对象：有记录的执行三项都有，`run --no-report` 三项都没有，不会出现只注入其中一部分的状态（形态见 0030 决定一）。
- 结束时前台执行者不覆盖已有的终态；在终端说明这个 run 在本次执行结束之前已被记为已结束、已得出的判定照常写入；以非零退出码结束。报告也不生成：它从本次执行的结果派生，会与记录里的终态矛盾。同一理由，`run` 不输出汇总与 `--json` 文档（两者的 run 级状态都是本次执行聚合出的），说明与判定明细的位置写在 stderr，退出码取 1（处理过使用方中断时仍按信号取 130 或 143）。

这一条不依赖时钟：不管两台机器的时钟差多少、发起进程是否被暂停过，run 级一旦是终态，它的下一次认领或启动前的检查就会拦住。能越过它的只有检查已经通过、启动还没有完成的 job（至多并发上限那么多）：首次启动是认领已成功，重试是启动前的那一次读已通过，而启动调用还没有发出、正在进行，或句柄还没有返回。它们会启动。启动之后由谁停，各执行方式不同，见「边界与已知局限」的表。

云端的索引写随之少一种：不再有终态被改写成另一个终态的那次分组变化（0041 决策七列的「终态被改写」边界不再存在）。

### 六、处置：run 级 `error` 加说明，job 保持原样

- 写入口就是决策五的条件写。两个处置同时发生、或处置与发起进程自己的收尾同时发生时，只有一个写成，另一方得到「已记为已结束」。
- 各 job 的状态不动，不替它们下结论；`ended_at` 写的是记为已结束的时刻，不是发起进程实际消失的时刻。
- 说明写在 run 级 `message`，事实在前、处置在括号里：「发起它的 gherkai run 进程已退出（已记为已结束）」「已超过允许运行的时间（已记为已结束）」。执行方自己到期收尾时写「已超过允许运行的时间」（决策二第 3 条）。
- 这扩大了 run 级 `message` 的写入方：0037 决策 7 原定只有云端推进器写、同步 run 不写。含义的边界不变，仍是「没有任何 job 能承载的原因」；写入方多出本 ADR 的处置与各执行方的到期收尾，两个后端都写。
- 「读到 run 级终态即各 job 的判定已全部落库」（0030 决定三、CONTEXT「终态提交点」）多出一类例外：带着说明的 run 级 `error` 表示这个 run 没有运行完成，有的 job 可能没有判定（未启动，或发起进程消失时还在跑）。同类例外原先已经存在（推进器在运行定义不可用时收尾），几处一并写明：凭「run 级终态」取产物的读者，对带说明的 `error` 要按「可能不全」处理；`explain` 对这类 run 的提示随之改。
- 清理协议不用改：记为 `error` 后 run 离开 `live` 分组，不再占住它引用的 worker 版本（0038 残余风险④随之改写）。此后执行方不再认领新的 job（决策五），余下未启动的 job 不会再用到这些版本；检查已经通过、启动调用还没有发出的那几个 job 可能因为版本刚被回收而启动失败，这个 run 此时已是终态，不影响记录。
- 处置只改记录。云端后端在记录变为终态之后由后端自己停掉这个 run 仍在跑的 task（决策九）；本机后端的 worker 靠核验所属进程自行退出，它的局限见「边界」。

### 七、触发面

- **`gherkai settle-runs [run_id] [--dry-run] [--json]`**，加 0041 决策六的三项定位参数。不给 `run_id` 时处理这个后端里全部前台的未结束 run，给了只处理那一个。`--dry-run` 只判定、不写。人读输出逐条给出 run、判定结果与处置；`--json` 给一个对象：落点字段同 `list-runs`，`dry_run`，`runs[]` 每项带 `run_id`、`outcome`（`settled`、`would_settle`、`skipped`）与 `reason`（`launcher_exited`、`past_deadline`、`launcher_alive`、`undetermined`、`detached`、`already_finished`、`unreadable`）。退出码只有 0（执行完成，含一个都没处理）与 2（用法错误、后端不可达、给出的 run 不存在）。它是变更类命令里带 `--json` 的一个：0041 决策三把变更类命令的机读面定为退出码，这里的结果是逐条的处置清单，退出码承载不了，作为该条的明示例外。
- **`status --wait`**：对前台的未结束 run 不再无条件空等，每次轮询做同一个判定，可以记为已结束的就记下，然后照常渲染并给终态的退出码（`error` 记 1）。后台执行标记读得出的前台 run 每次轮询都做判定：运行定义读得出时最晚等到期限过后 300 秒；运行定义读不出时只是用不了期限那一行，进程核对照做，同机确认发起进程已退出即处置，否则继续等待并说明原因。后台执行标记读不出的 run 一律只等待并说明原因。
- **`list-runs`** 保持只读、零写入。表格加两列：「已运行」（未结束的 run 是到现在的时长，有期限时括注还剩多久或已超多久；已结束的 run 是总时长）与「允许运行至」（本机时区，读不到期限时为 `-`）。列序：run_id、状态、开始、结束、已运行、允许运行至、job、版本、提示。提示列按判定给出：「发起它的 gherkai run 进程已退出（可用 settle-runs 记为已结束）」「已超过允许运行的时间（可用 settle-runs 记为已结束）」；后台 run 已过期限而仍未结束时为「已超过允许运行的时间（可用 status --wait 收尾）」；其余不给提示，现有那句「status --wait 对它只等待、不接力」删除。`--json` 每项加 `deadline_at`（没有时省略）与 `liveness`（`launcher_exited`、`past_deadline`，不适用时省略）；发起进程标识不进机读输出。清单里的进程核对只读本机的进程信息。
- 判定与处置放在 runtime 包（与本机接力的期限恢复同层），CLI 的三处都调它。

### 八、发起进程标识怎么取

不引入新依赖，两个平台各用系统自带的手段，记录时与事后核对用同一种取法，按原值严格相等比较：

| | pid 空间标识 | 进程启动时刻 | 进程状态 |
|---|---|---|---|
| macOS | `darwin:` 加 `kern.bootsessionuuid`（每次开机一个） | `ps -p <pid> -o lstart=,stat=`，执行时固定 `LC_ALL=C` 与 `TZ=UTC` | 同一条命令的 `stat` 列 |
| Linux | `linux:` 加 `/proc/sys/kernel/random/boot_id` 加 `/proc/self/ns/pid` 的取值 | `/proc/<pid>/stat` 第 22 字段（自开机起的时钟滴答数），从最后一个右括号之后切分 | 同一文件的状态字段 |

- pid 空间标识相等才核对 pid：它相等说明是同一个内核实例里的同一个 pid 命名空间。主机名会重名（克隆的镜像、容器、不同网络下的同名机器），重名会把另一台机器上的进程误判成已不在，所以主机名只用于显示，不参与判定。
- 启动时刻用来挡 pid 复用：复用者的启动必然晚于原进程退出，原值不会相等。
- 僵尸进程算已退出；被暂停的进程算还在（它过了期限由判定的第二行处理）。
- 任何一项取不到（沙盒、`/proc` 受限、命令不存在）时，建 run 那一侧不写 `launcher`，核对那一侧按核对不了处理，都回落到期限。
- 其它平台不支持：三个包实际只能在 POSIX 系统上运行（用了 `fcntl` 与进程组）。

实测（一台 macOS 与一台 Ubuntu）：

- macOS：同一进程的 `lstart` 连读两次、换语言环境变量后再读，三次相等；不固定 `TZ` 时输出随本机时区变，所以必须固定；被暂停的进程 `stat` 以 `T` 开头；已退出、未被父进程回收的进程 `stat` 为 `Z`，这时 `os.kill(pid, 0)` 仍然成功，只看它会误判为存活；回收后 `ps` 以退出码 1 结束、没有输出。
- Linux：同一进程的滴答数连读两次相等；被暂停为 `T`，僵尸为 `Z`，`os.kill(pid, 0)` 对僵尸同样成功；进程名里带空格与括号时，从最后一个右括号之后切分取到的字段正确；同一台宿主上，容器里读到的 `boot_id` 与宿主相同、pid 命名空间不同，所以标识里必须带命名空间。

### 九、云端由后端兜底：到期把 run 记为已结束，run 一结束就停掉它的 task

本机后端与云端后端有一处天然的不同：本机的 worker 能核验发起它的进程还在不在，不在就自己退出；云端的 task 不知道发起进程在哪，做不到。前台 `run --backend cloud` 的推进者仍是本机的 CLI 进程，云端的两个推进 Lambda 现在不处理这类 run（避免两个推进者同时动一个 run），所以这个进程一消失，云端就没有东西在看它，task 也没有人停。云端后端里一直都在的只有 Lambda，兜底放在那里；用现有的两个推进 Lambda，不新增。

Lambda 对前台 run 仍然不推进（不认领、不启动 job，0034「filter 必须区分写入者」的目的不变），只对所有云端 run 做两件事：

1. **期限触发。** runs 表的流触发 kicker 的过滤，从「新建且带后台执行标记」放宽为「STATE 条目的新建」（`INSERT` 且 `item_type` 为 STATE）。建 run 时先写 META 再写 STATE，两条都是新建；原过滤靠只有 STATE 才带的后台执行标记隐含地只收 STATE，放宽时要把这个条件明写出来，否则 kicker 会在 STATE 还没落库时就收到 META 的事件，把后台 run 认成前台 run。kicker 对每个有期限的新 run 建一个一次性的定时触发（与 job 超时触发同一机制、同一角色，到点自动删除）；对前台 run 的新建事件只做这一件事，不推进。
   - 后台 run：时刻取 `deadline_at`，到点对仍在跑的 job 做超时处置再推进（决策二）。
   - 前台 run：时刻取 `deadline_at` 加 300 秒，与判定第二行（决策四）是同一个时刻，先让还在的发起进程自己到期收尾。到点时 run 仍未结束，Lambda 以条件写把它记为已结束，说明与处置相同：「已超过允许运行的时间（已记为已结束）」。它相当于云端替没有人执行的 `settle-runs` 做了第二行。
2. **结束即清扫。** run 级一到终态，就把这个 run 仍在跑的 task 停掉。task 启动时都带着 run 的 id（`startedBy`，前台与后台是同一个 engine），清扫按它列出仍在运行的 task 逐个停止，可以重复执行。清扫只对 run 级已是终态的 run 做。触发有三处：
   - runs 表的流里写后处于终态的 STATE 条目（kicker 新增一个过滤：新映像的状态分组不是 `live`）。`settle-runs` 把云端的 run 记为已结束、前台发起进程自己收尾、Lambda 收尾，都经这里。流只带新映像，这个过滤分不出「这一次写把 run 变成了终态」与「run 已是终态之后的又一次写」：终态之后只写 job 的那些写（前台执行者发现 run 已结束之前的 job 状态写、后台投影里晚到的逐 job 写）同样命中。流事件按批调用，同一批里按 run 去重；跨批的事件、迟到的事件与期限触发可能再次清扫。清扫可以重复执行，不要求恰好一次。
   - 推进 Lambda 的现有入口遇到已结束的 run 时（迟到的 worker 事件、job 超时触发），在「不再改写它的结果」之外做同一个清扫，停掉结束之后才启动起来的 task。
   - 期限触发到点时 run 已经结束，同样清扫一次。

正常结束的 run 在收尾之前它的 task 都已停止（前台读到完整内容之后仍等 task 停止才收尾，后台的退出记录来自 task 停止的观察链），清扫不会打断还在做最后上传的 task；列 task 的调用可能仍返回刚停止的 task，对它们没有要停的。清扫不写 runs 表，不会形成「清扫引出写、写再引出清扫」的回路；它停掉 task 引出的退出事件、终态之后外部迟到的写会带来更多调用，性质不同。

要用到的东西都已具备：Lambda 的角色已有列 task、停 task 与建定时触发的权限；runs 表已开流。要新增的是期限触发的名字空间与流上的一个过滤，在 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 登记。代价按调用的批次与实际清扫的次数计：每个 run 结束时至少清扫一次（一次列 task），终态之后还有对 STATE 的写、跨了批时再清扫；多个 run 的事件可能合在一次 Lambda 调用里。每个有期限的 run 另多一个一次性的定时触发。

落实时两处位置要对：

- 现有入口进来先过两道跳过：不带后台执行标记的 run 跳过、已结束的 run 跳过。只放宽流的过滤不会让它们开始推进前台 run，第一道跳过仍然在。期限触发的建立要在进入推进的装配之前分流，前台 run 做完这一件事就返回。清扫必须在第一道跳过之前就能走到，不能只加在第二道里，否则前台 run 迟到的事件永远到不了它；job 超时的入口也要先看 run 级是否已结束，再去看 job 的状态。
- 前台 run 的到期入口不套用 job 超时的处理：定时触发只承诺分钟精度、表达式不带小数秒，收到触发本身不能当作期限已过的证据。入口按判定第二行重新核对当前时刻已过 `deadline_at` 加 300 秒，再条件写终态；run 已是终态时只清扫。

这样两个后端在「到期就停、run 记为 `error`」上是同一种表现，云端的 run 结束之后也不再有它的 task 在执行与计费；差别只在由谁来停：本机是执行方与 worker 自己，云端是后端。停不到的情形见「边界」。

### 十、job 的墙钟预算有一个产品定的上限，不再有不超时

- 一个 job 的墙钟预算最长 7200 秒（2 小时）。它是产品的设定，放在 core，对所有目标是同一个数。
- 引擎与平台各自的限制是另一回事，仍归引擎：桌面目标的浏览器会话，平台允许的最长存活时间是 28800 秒，两个引擎的 worker 把会话的存活时间设为 job 预算加 120 秒；设备目标的会话上限由引擎在能力自述里报出，现在是 8880 秒。core 不抄这些数。两者之间只有一个关系：产品上限不大于任何一个引擎对任何目标能支持的最长预算，由测试守住（设备对照能力自述里的上限，桌面对照会话存活时间的封顶值减 120 秒），引擎那一侧的数哪天低于产品上限，测试即失败。引擎自己的检查保留，作为最后一道。
- `@timeout:N` 与显式给出的 `--default-job-timeout` 正值超过上限时，计划阶段报错、以退出码 2 结束，与设备目标低于下限是同一处理。桌面目标的显式值原先没有上限，设备目标原先到引擎的 8880 秒为止，现在都到 7200 秒为止。
- `--default-job-timeout` 给 0 或负数，对任何目标都表示取这个上限：桌面 scope 由「不超时」改为 7200 秒，设备 scope 由「仍取设备缺省」改为 7200 秒。什么都不给时的缺省不变（桌面 300 秒，设备为获取预算加 900 秒）。设备预算的下限（获取预算加 180 秒，获取预算最大 3600 秒）最大是 3780 秒，在上限之内。
- 上限检查与给 0 的含义都落在现有的取值次序之后，次序不变：scope 里有场景标了 `@timeout` 就用标的值，否则用显式给出的缺省，都没有才按目标补缺省。被检查的是这样解析出的有效预算；被 `@timeout` 盖住、没有生效的缺省值不检查，给 0 或负数也只作用于没有标 `@timeout` 的 scope。
- `Job.timeout_s` 不再有空值。运行定义里这个键恒为正数（随结构版本 2 一并生效），读端把空预算当作违约拒绝；调度与推进里「没有预算即不设截止时刻」的分支、超时说明里没有预算时的回退写法、云端「有预算才建超时触发」的条件都随之删除，隧道存活时间上限里给不超时的 job 记账用的固定值也不再需要。缺 job、缺认领时刻、能力自述没给上限这几种含义不同的判空照旧保留；计划阶段「没有显式给出缺省」的空值含义不变。
- worker 协议不升版。协议里 job 输入的预算仍可以为空，两个 worker 的空值分支与规范样本保留，只是 core 不再产出空值。把协议也收为恒正要两个方向一起升协议版本，使用者自建的 worker 变体都得重建，为去掉一个不再出现的取值不值得。

理由：

- 「不超时」今天实际上也不是无限。job 没有预算时，Midscene 的 worker 不向平台传会话的存活时间，平台缺省是 3600 秒（最长可设 28800 秒）；Nova 的 worker 不向 SDK 传这个参数，SDK 自己取 3600 秒写进请求。两条路径的结果都是一小时。所以今天把桌面 job 设成不超时，得到的是 job 不会被停、它的浏览器会话一小时后被平台关掉，之后的 AI 步骤全部失败。设了上限之后预算恒有值，会话的存活时间按现有的算式随预算取值，给 0 的使用者能用到的是 2 小时，比今天实际的一小时长。
- 每个 run 都有期限。没有期限的 run 要单独对待的地方（收尾只能靠同机的进程核对、`status --wait` 可能一直等、云端到期兜底覆盖不到）都不再存在。
- 云端不再有「没有期限、所以后端永远不会去处置」的 run：发起进程消失、又恰好有 job 自己不结束时，到期限加 300 秒之后后端的到期兜底会去处置它。这不是费用的硬上界：处置受决策九里触发、列举与停止各自的边界约束。

代价是不能有超过 2 小时的单个 job：桌面目标原先可以显式给更大的值（浏览器会话最长撑约 8 小时），设备目标原先可以到 8880 秒。上限是产品的选择，不是引擎的极限；以后要放宽只改 core 的这一个数，前提仍是不超过各引擎能支持的最长预算。

## 边界与已知局限

run 到终态之后各执行方式下还会发生什么，按 code 现有的结构逐格列出，不作统一的概括：

| | 前台执行 | 本机后台 | 云端后台 |
|---|---|---|---|
| run 级终态被改 | 不会 | 不会 | 不会 |
| 认领并启动新的 job | 不会：认领与重试前的检查被拦 | 不会：认领被拦 | 不会：认领被拦 |
| 检查已通过、启动还没有完成的 job（调用未发出、调用中、句柄未返回；首次启动与重试都算） | 会启动；发起进程下一次写运行态时发现 run 已结束，对它发停止 | 会启动；推进进程还在时由它的计时在截止时刻停止 | 会启动；它发出的事件、或在它可见之后才到点的超时触发带来下一次 Lambda 调用时被清扫停掉（决策九）；此后没有任何触发时没有人停 |
| 已经在跑的 job | 发起进程还在时由它停止；它被暂停或卡死时要等它恢复；它已不在时，云端后端的 task 由后端清扫停掉（决策九），本机后端的 worker 见下 | 推进进程还在时由它停止；已不在时见下 | 到期收尾之前都已按超时处置；run 结束时再清扫一次；之后才出现的 task 同上一格 |

执行方已不在、又没有别的组件去停时，留下的执行没有期限兜底：

- 本机 worker 靠核验所属进程是否还在来自行退出（[0024](./0024-worker-core-protocol.md)）。这个核验有已知的失效情形：worker 核验的是传给它的所属进程 pid，所属进程成了未被回收的僵尸时这个 pid 仍然查得到；worker 经包装进程启动、或所属进程在核验启用之前已经退出时，没有「直接父进程变了」这条辅助线索可用，核验可能一直不触发。所属进程的 pid 在被发现消失之前被复用时，它也被误认为还在。本 ADR 的判定能认出僵尸与 pid 复用，worker 的核验不能，所以会出现 run 已被记为已结束、本机 worker 仍在执行的情形。
- 云端 task 自己不会因为 run 结束而停：worker 不按预算计时自停（0034「job timeout」节）；浏览器会话与设备会话各有存活上限，但会话到期不保证 task 退出，确定性 step 可以一直等下去。所以由后端来停（决策九）。发起进程消失之后，已经启动的 task 不依赖它：各自把手上的 job 执行完就退出；还没有发出启动请求的 job 不会再启动，已经提交、还在启动中的请求仍可能完成（见上表）；留下来的只有自己不结束的 task（卡住的 step、一直等待的确定性 step）。这样的 task 在期限加 300 秒之后由后端的到期兜底去处置（把 run 记为已结束并发起停止）。后端停不到的有两种：清扫时没有被列到、之后又没有任何触发的 task；流与定时触发整条链都失效的时候。前一种包括：启动调用在清扫时还没完成的；已经启动、ECS 的列举因最终一致性暂时看不到的（发起进程刚调完启动就消失、随即被处置）；以及它自己的超时触发在它可见之前已经执行并删除的。这样的 task 只要此后发出任何事件就会带来一次清扫，一直不出事件的留下。

处置（`settle-runs`）只改记录，自己不停任何东西；表里的停止，本机后端是执行方与 worker 自己做的，云端后端另有后端在 run 结束时的清扫。

其它局限：

- 结构版本升到 2 之后，版本 1 的运行定义在 `status`、`explain` 与推进器那里读不了（`list-runs` 仍能列出），它们也没有期限与发起进程标识，不处理。产品没有使用者，不为它们另设出口。
- 本机接力在改法实装之前仍可能抢在 worker 的协作收尾之前补写未知退出（决策二「本机接力」条）。run 若在补写与真实退出之间收尾，这次收尾按超时提交，run 级的结果与报告就此定下。
- 多个推进方竞争收尾时，各方在条件写之前各自落下判定明细（[0030](./0030-realtime-persistence-seam.md) 决定三的写序：明细先于 run 级终态）。各方看到的事件相同时落下的明细相同，先后覆盖没有差别。看到的不同出在接力方给一个 job 补写了未知退出之后：这个 job 的 worker 的事件、原推进进程写下的真实退出码都还可能补到，两个推进方先后读到的快照因此不同（退出记录不同，或退出记录相同而会话是否已确认释放不同）。这时没写成的一方落下的明细可能盖掉写成的一方的，`explain` 看到的这个 job 的判定或提示与提交时的不一致。本机接力的改法（决策二）实装之后，认领方还在时接力方不再补写，这个窗口随之缩小；彻底消除要让退出记录或判定明细的写带条件，本 ADR 只把补写的未知退出改成了条件写，观察到的真实退出与判定明细的写仍可覆盖已有的记录。
- 前台按它看到退出的那一刻判断是否已过截止时刻，后台按退出记录里的退出时刻判。本机两者几乎是同一刻；云端的前台执行靠轮询得知 task 停止，看到的时刻晚于 task 实际停止的时刻，task 在截止时刻之前几秒内自己异常退出、发起进程过了截止时刻才看到时，前台记超时而后台按退出码归因。这一处还没有统一：让前台也按实际的退出时刻判要改引擎端口，随决策九的云端改动一起做，并用真实的 task 核验。
- 云端后台 run 在期限时刻的那一次定时触发（决策九）实装之前，到期靠各 job 自己的定时触发带起。某个 job 的触发没有建立、丢失，或到达之后没能处置（如等待预算不足而跳过），它的 worker 又不出任何事件时，没有别的东西来推进这个 run，这是 [0034](./0034-detached-batch-reconciler.md) 已接受的降级情形；决策九的那一次触发是为它加的兜底。
- 永远不会被处置的未结束 run 有两类，`status --wait` 对它们照旧只等待并说明原因：后台执行标记读不出或不合法的（即使期限已过）；运行态或运行定义本身读不出、同机又核对不了发起进程的。
- 重启过的同一台机器与另一台机器分不开，一律按核对不了处理、回落到期限。不用跨重启稳定的机器标识来补：它会随镜像克隆被复制，认错的方向是把还在执行的 run 记为已结束。
- 云端建 run 的先读与两次条件写之间，另一方若建了同一个 run_id，META 与 STATE 条目仍只有一方写成，另一方失败；但它已卸载到 S3 的 step 参数正文可能已重写对方的同名对象。run_id 由发起进程新生成、带随机尾，这个窗口不另设机制防护。
- 判定方的时钟比发起方快出 300 秒以上时，一个仍在期限之内的 run 会被提前记为已结束，发起进程随后停手。同一种情形下若发起进程已经得出全部真实结果、只差收尾那一次写，记录是 `error` 而判定明细里是真实结果，`run` 进程的终端输出会说明。两者都要求时钟偏差超过 300 秒加这个 run 离期限的余量。

## 被拒方案

- **期限只当推定阈值、执行方不遵守**：见决策二的理由。由此还要引出两条补丁式的规则（同机确认进程还在时不处置；真实结果覆盖处置写下的 `error` 并清除说明），都随它一起不取。
- **本机接力凭时钟加一段固定时长推断认领方已经收尾完**（停止尾段，按墙钟或按接力方自己观察起算的单调时钟）：三次失守，见决策二「本机接力的改法」的理由。
- **真实结果覆盖处置写下的终态**：终态之后再变对上层是错的行为，见决策五。
- **靠期限加余量证明执行已停**：尾段与余量都是预算，时钟也可能有偏差，证明不了。收尾的安全改由「终态不可变、认领以未结束为条件」承担。
- **到期时把未启动的 job 记为 `error` 或 `skipped`**：run 的时间用完不是这些 job 的原因。记 `error` 要么沿用启动失败的补偿（错误类型与说明都对不上，认领之后退出记录没写成还会留下一个没有人管的在跑状态），要么新设一种记录；记 `skipped` 在后台路径上同样要新设一种记录。保持 `pending` 加 run 级说明不需要这些，也与处置的写法一致。
- **到期时把在跑的 job 一律改判为超时**：反转 0034 机制二「内容已完整的不改判」，同一个 job 还会因为停止请求到得早晚在四种执行方式下得到不同结论。
- **期限与标识都放运行态记录的顶层**：期限是 run 的规则，放在只由 adapter 读写的附加属性里，core 的调度与推进就得绕开模型去拿它。**都放运行定义**：发起进程标识不是「要执行什么、怎么执行」，还会随机读输出带出主机名与 pid。
- **期限不存、读时现算**：停止宽限不在任何记录里；算式随 CLI 版本变化时，同一个 run 在不同版本下会算出不同的期限，而它必须是各执行方与所有读者共同认的那一个时刻。
- **同一 run 下另立一条记录放标识**：现行的建 run 不是事务写，多一条记录就多一处要协调的一致性；列举每个 run 多读一个条目或文件。
- **只看 pid 是否存在**（现有 code 判断进程或进程组存活的做法，`os.kill(pid, 0)` 与 `os.killpg(pgid, 0)`）：pid 被复用或进程是僵尸时都判为存活，做不到立即判定；主机不同也无从知道。
- **引入 psutil**：为取一个启动时刻加一个带编译扩展的依赖；它在 Linux 上给出的是由开机时刻换算的墙钟浮点数，系统时钟被校正后同一进程前后读到的值可能不等，按「不等即被复用」处理会把活着的进程判成已不在。
- **用主机名或跨重启稳定的机器标识判「同一台机器」**：见决策八与「边界」。
- **使用者单独配置 run 级期限**（0034 预留的 `--default-run-timeout`）：期限要保证不早于各 job 预算能合法用到的时刻，单独配置就得再定义它与 job 预算冲突时谁让谁；现在只由 job 预算推出。
- **让使用者强制把某个 run 记为已结束**：判定不靠使用者担保是 owner 定的原则；每个 run 都有期限之后，记录读得出的 run 最晚在期限之后都有出口，不需要它。
- **为停 task 新设一个 Lambda**：要用的触发（runs 表的流、定时触发）、权限（列 task、停 task）都已在现有的推进 Lambda 上，另设一个只是把同一套装配再复制一份。
- **由 `settle-runs` 自己停 task**：它就得带上操作 ECS 的权限，只有 DynamoDB 写权限的机器用不了；没有人执行它的时候 task 照样没人停。停 task 是「云端的 run 结束之后不再有它的 task」这条后端自己的性质，放在后端。
- **让 Lambda 接手推进发起进程已不在的前台 run**：前台 run 的结果是给发起它的那条命令看的，命令已经不在，接着执行没有接收方；Lambda 也无从确认发起进程真的不在了，接手就是两个推进者。它只做收尾与清扫。
- **给 0 时取引擎的上限**（桌面约 8 小时、设备 8880 秒）：`run --backend cloud` 时 CLI 在计划阶段不查询引擎的能力自述，拿不到设备的数；在 core 里抄一份则是同一个事实写两处，引擎改了而这一份没人记得改。桌面那个数同样是从平台的会话上限推出来的引擎事实。
- **给 0 时设备 scope 仍取设备缺省**（原先的行为）：同一个写法对桌面是「尽可能长」、对设备是「等于没写」，一个参数两种含义。
- **按目标各定一个产品上限**（桌面取平台允许的最长、设备另取一个数）：桌面那个数仍是把引擎与平台的事实搬进 core；一个产品设定用一个数，引擎的限制留在引擎。
- **心跳或租约**：见「重议闸门」。

## 实测项（实装时逐项核，结果内联回这里）

1. 本机后端：前台 run 执行中把 CLI 进程 SIGKILL，同机 `settle-runs --dry-run` 报发起进程已退出、不写；`settle-runs` 写入 run 级 `error` 与说明，各 job 状态不变；`status` 与 `list-runs` 的显示与退出码符合决策六、七。
2. 本机后端：建 run 之后经过若干次 job 状态写回，`launcher` 仍在 `run_state.json` 里。
3. 前台到期：把期限设到执行中途，发起进程不再启动新的 job、在跑的 worker 按超时停止、run 级收尾为 `error` 并带 run 级说明、未启动的 job 保持 `pending`、已结束的 job 的判定明细齐全、报告里 run 级是 `error` 加同一句说明；云端后端同样，在跑的 task 被停止。
4. 暂停后恢复：发起进程被 SIGSTOP 到期限之后，别处先处置；SIGCONT 之后它不再启动新的 job（它的时钟已过停止启动的时刻，时间检查先拦下；时钟落后于处置方时改由认领被拒拦下，这一支用注入的时钟核）、在跑的 worker 被停止，收尾不覆盖已有的终态，终端有说明、退出码非零；本机与云端各一次。
5. pid 复用：把记录里的启动时刻改成另一个值，判为已退出；僵尸进程判为已退出。
6. 云端后端：`run --backend cloud` 执行中把 CLI 进程 SIGKILL，同机处置成功；处置后 run 离开 `live` 分组，下一趟清理不再把它当占用者；`list-runs` 的读量与请求数不因新属性变化。
7. 另一台机器或容器里对同一后端查询：期限加 300 秒之前不动，之后处置。
8. 终态不可变：处置与前台的 job 状态写交错进行，run 级不出现从终态回到 `running`；对已有的 run 再次建 run 失败且不改任何东西（云端包括不重写已卸载到 S3 的内容），两个后端各核一次。
9. 两个 `settle-runs` 同时处置同一个 run，只有一个写成。
10. 本机后台 run 到期：推进进程在跑时，到期后在跑的 job 按超时停止、未启动的 job 保持 `pending`、run 以 `error` 结束并带 run 级说明、报告生成；推进进程被杀之后过了期限再执行一次 `status --wait`，这一次接力把 run 推进到结束，不启动任何 job。
11. 本机接力的改法（实装之后核）。保护：认领方还在时，同时进行的 `status --wait` 自始至终不补写未知退出，墙钟前跳、认领方被暂停之后恢复两种情形各核一次；其中 worker 发出 `scope_done` 并以 0 退出、run 没有被兜底结束的一例，job 保留完整的判定。认领方已退出：认领方在截止之前被强杀、接力方过了截止时刻才发现时，补写的是结果未知而不是超时；随即发现的同样。核对不了：记录里没有认领方标识或不在同一个 pid 空间时，接力方不补写。期限兜底：认领方还在、worker 过了停止宽限仍不退出，直到运行期限加 300 秒之后，整个期间没有逐 job 的补写，最后只有 run 级被记为已结束、各 job 保持原样。
12. 云端后台 run 到期：部署后提交一个期限落在执行中途的 run，没有任何人查看，期限到时在跑的 task 被停止、未启动的 job 不再启动、run 以 `error` 结束；核对期限时刻的定时触发确实发出、Lambda 日志里没有异常。
13. 四路一致：前台与后台、本机与云端各一个到期的 run，对照 run 级状态与说明（`status --json`）、各 job 的状态（`status --json`）与已结束 job 的错误类型和说明（判定明细，经 `explain` 读），四者一致。
14. 内容完整的不改判：让一个 job 在期限之前给出完整内容、收尾越过期限，它在四种执行方式下都保留原判定；这个 run 没有未启动的 job 时，run 级按聚合得到真实结果、不带到期说明。
15. 前台重试：job 因网络故障重试时照常重新启动、不被自己的认领拦住；退避期间 run 被别处记为已结束时不再重新启动；经过开始执行与结束两次状态写之后，认领时刻仍在运行态里。产品的 `run` 不开 job 级重试（[0028](./0028-transient-network-ssl-resilience.md)），重试的两条在调度层用注入的重试次数核，认领时刻的保留在真实的 run 上核。
16. 到期收尾与认领并发：一个推进方读到「没有在跑的、仍有未启动的」之后，另一个推进方的认领落下，前者的收尾写被条件挡下、run 没有结束，新认领的 job 在期限时刻被停止；本机与云端各核一次。
17. 云端期限触发承担处置：让一个 job 自己的超时触发缺失、worker 不出事件，期限时刻的触发仍把它停掉并使 run 结束。
18. 云端前台 run 的 task 被清扫：`run --backend cloud` 执行中把 CLI 进程 SIGKILL，同机 `settle-runs` 之后，这个 run 仍在跑的 task 在流触发的清扫里被停止；核对停止来自 Lambda、`settle-runs` 自己没有调用 ECS。
19. 云端前台 run 的到期兜底：`run --backend cloud` 执行中把 CLI 进程 SIGKILL，不执行任何命令，到 `deadline_at` 加 300 秒之后 run 被 Lambda 记为已结束、task 被停止；发起进程还在并已自己收尾的 run，到点只清扫、不改记录。
20. 清扫不误伤：正常进行中的 run（前台与后台各一个）在同一后端里另一个 run 结束时不受影响；正常结束的 run 触发的清扫没有要停的 task（列举可能仍返回刚停止的 task），没有打断任何 task 的最后上传。
21. kicker 对前台 run 的新建事件只建期限触发：没有认领、没有启动 task，前台 run 的 job 没有被执行两次。
22. 预算上限：`--default-job-timeout 0` 的桌面 scope 与设备 scope 在运行定义里都得到 7200 秒的预算；桌面 job 的浏览器会话存活时间设为 7320 秒（两个引擎各核一次，从 worker 发出的建会话请求里读）；有效预算 7201 秒在计划阶段被拒、7200 秒通过，两种目标各核一次；标了 `@timeout:1500` 的 scope 在 `--default-job-timeout` 给出超过上限的值时照常通过（没有生效的缺省值不检查）；产品上限不大于每个引擎对每种目标能支持的最长预算的那条测试，在把引擎一侧的数改小时失败。
23. 退出时刻的两种取法一致（云端）：同一个已停止的 task，从它的停止事件取到的执行停止时刻与主动查询 task 取到的，写成退出记录之后相同；两处先后写同一条退出记录时内容不变。
24. 截止时刻之后自行退出的归因：worker 在截止时刻之后、停止请求发出之前以非零的退出码退出时，本机后台与云端后台都记为超时，错误类型与说明和前台相同；在截止时刻之前这样退出时按退出码归因；内容完整的 job 不因退出时刻晚于截止时刻而改判。本机一侧用真实进程核，云端一侧在部署之后用真实的 task 核。
25. 补写不覆盖：原推进进程的真实退出记录落在接力方「查有没有退出记录」与「补写未知退出」之间时，留下的是真实的那一条；云端超时处置找不到 task 时的直接写入同理。

## 重议闸门

- **心跳或租约**：跨机器的判定只能等到运行期限，宽松的期限可以是实际时长的数倍。出现「需要在另一台机器上早于期限确认发起进程已不在」的使用需要时，再议由发起进程定期续写的心跳或租约（它们作为写者互斥的手段在 0030、0034 里是被拒方案，这里是另一个用途）。
- **使用者可调的 run 级期限**：由 job 预算推出的期限对某类 run 明显过宽、影响到 CI 排期或费用时，再议单独的配置项。
