# 0054. 运行期限、生命期锁与 run 处置：每个 run 遵守由 job 预算推出的期限；本机 run 由持有生命期锁的进程推进，死活由锁回答；run 结束之后记录不变、不再接受新的认领；管它的进程不在了、或已过期限加 300 秒的 run 可由处置方结束

> **Status:** Accepted —— 这一篇描述的设计有一部分尚未实装，code 跟上之前，实际行为以 code 为准。

## 背景与问题

管一个 run 的进程可能不写终态就消失。本机后端是执行 `run` 的进程或 `submit` 启动的后台推进进程，它们会被 SIGKILL、随宿主失联、收到没有处理器的 SIGHUP、或因未捕获的异常退出；云端后端的 run 由后端推进，触发链断开（一次调用最终失败、触发丢失）时同样停住。这样的 run 停在 `pending` 或 `running`，没有出口，后果有三处：

- `status --wait` 一直等下去。
- `list-runs` 的未结束部分不截断（[0041](./0041-agent-facing-cli-affordances.md) 决策七），这类 run 只增不减。只增不减、没有出口是设计上的缺口，不等它在清单里成为常态再处理。
- 云端的清理协议把 `live` 分组里的 run 当作 worker 版本的占用者（[0038](./0038-worker-image-delivery.md) 残余风险④），它引用的版本一直回收不了。

要给这类 run 出口，先要回答两个问题。

一是这个 run 允许运行到什么时候：要有一个所有执行方都认、别的机器也能拿来比较的时刻。各 job 的墙钟预算只在执行它的进程里起作用，给不出这个时刻：按单调时钟计时，系统休眠时单调时钟不走，各 job 的截止时刻顺延休眠的时长；进程被暂停时它不检查截止时刻；落库或云端调用卡住时也没有上界。所以从外面看，一个 run 可以在任意晚的墙钟时刻仍在执行。

二是管它的进程还在不在。从外面推断不可靠：凭时钟加一段固定时长判断对方是否已经收尾完，三种取法都失守，后两种由真实进程复现（[0034](./0034-detached-batch-reconciler.md) 被拒方案「本机接力，及其改法」）；凭进程标识核对，每一种取法都有新的反例（「被拒方案」里「读对方进程的信息」一条）。

## 决策

### 一、定位与范围

- 本篇管一个 run 的生命期：每个 run 允许运行到什么时候（运行期限，决策二），以及让每个 run 都有期限的前提，即每个 job 的墙钟预算有产品上限（决策十）；本机 run 由持有生命期锁的进程推进，锁回答它在不在（决策三），锁只在本机文件系统上的报告目录里有效（决策四）；run 到终态之后记录不变、执行方服从记录，所以期限之后结束一个可能还在执行的 run 也安全（决策五）；何时可以处置（决策六）、处置做什么（决策七）、谁来做、从哪个入口做（决策八）；云端没有本机进程，到期结束 run 与清扫 task 放在后端（决策九，到期结束的前提见其第 1 条）。
- 执行方式与执行后端有三种组合，云端后端只有后台（[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 A）：本机前台（`run`）、本机后台（`submit --backend local`）、云端后台（`submit --backend cloud`），下文称三种组合。处置对两个后端、前台与后台的 run 都适用。
- 处置不是「使用者放弃一个 run」：判定只靠记录与生命期锁，不靠使用者事后担保，拿不准就不动。取消一个 run 的命令不在本篇，它以后是处置方之一（决策八）。
- `run --no-report` 不建记录、不拿锁，不在范围内。
- 本篇依赖、写全在别处的：本机的 run 任何时刻至多一个推进器、云端多次调用可以重叠推进，在 [0034](./0034-detached-batch-reconciler.md)「推进器与触发源」；各命令写什么在 0034「命令形态」；run 与 job 的状态怎样取、结束写给未结束的 job 记什么，在 [0031](./0031-job-lifecycle-states-and-severity.md) 决定三与其中的「结束写」小节；`list-runs` 的列与提示在 [0041](./0041-agent-facing-cli-affordances.md) 决策七。

### 二、运行期限：进运行定义，所有执行方都遵守

每个 run 在建立时得到一个运行期限 `deadline_at`（UTC 的 ISO 时刻），它是这个 run 的一条规则：

`deadline_at = created_at + 900 秒 + Σ（各 job 的墙钟预算 + 每 job 尾段）`

- 每 job 尾段：本机后端取 `2 × G + 10` 秒，云端后端取 210 秒（[0035](./0035-local-app-testing-via-tunnel.md) 隧道存活时间上限已在用的 `CLOUD_PER_JOB_MARGIN_S`）。G 是停止宽限：前台 `run` 取这次调用解析出的值（`--grace`、配置文件或各引擎自报值）；本机 `submit` 没有 run 级的宽限，取这个 run 用到的各引擎自报宽限里最大的一个。
- 900 秒是一次性余量，与隧道存活时间上限的一次性余量同值，留给建 run 到起第一个 job 之间的装配与各次落库、云端调用。
- 每个 job 的墙钟预算都是有限的（决策十），所以每个 run 都有期限。
- 求和而不按并发折算：并发大于 1 时真实墙钟小于各预算之和，串行总和对任何并发取值都偏宽，与 `compute_watch_ttl_s` 同一做法。健康的 run 通常远在期限之前结束。

尾段与余量是预算的取值，不是「执行一定已停」的上界：停止等待预算是执行方愿意等的时长，停止调用本身、起 worker 的调用、落库调用都可能阻塞得更久（0034 已区分等待预算与平台保证）。它们只决定期限定得多宽；期限之后结束一个 run 的安全不靠它们，靠决策五。取值的来历：前台 run 的 job 从线程池取到它时起算预算（认领时刻就在这时取，见第 2 条），到点后本机一次停止等 G 加约 3 秒、排空等到停止请求之后 G 加 5 秒、仍未结束会再发一次停止，合计约预算加 `2G + 9` 秒；云端的停止等待预算不超过 140 秒，加排空余量与心跳约预算加 146 秒，取 210 秒。job 级重试共享同一个截止时刻，不另外延长。

**落点是运行定义**（`RunMeta`，用户文档里的「提交记录」）。期限由 job 的墙钟预算与停止宽限推出、建 run 时确定、之后不变，执行方要遵守、所有读者都要看，它与 job 的墙钟预算、并发上限是同一类东西，后两者已在运行定义里。`deadline_at` 是运行定义键集的一项，键集由结构版本固定（[0037](./0037-distribution-and-packaging.md) 决策 7）。云端把它摊成 META 条目的顶层属性（同结构版本与写出版本的做法），列举时投影这个属性，不取回整份运行定义。读端把缺失、为空或不是带时区的合法时刻的 `deadline_at` 当作定义违约拒绝，与空预算同一处理：每个 run 都有期限，各执行方与判定拿到的必须是同一个可比较的时刻。

**所有执行方都遵守期限，三种组合是同一种表现。** 规则只看当前时刻与各 job 的状态，任何一次推进都能独立算出同一个结论，不需要记住期限那一刻发生过什么：

1. 当前时刻已过 `deadline_at` 减 60 秒，不再启动新的 job（含同一个 job 的重试）。提前 60 秒是启动余量：从发出启动到 job 真正开始执行需要时间，卡着期限启动的 job 来不及被正常停止。
2. 执行中的 job 的截止时刻以 `deadline_at` 封顶：取「认领时刻加它的墙钟预算」与 `deadline_at` 中较早的一个（`run_deadline.job_cutoff`），两者同按墙钟比较，相等时算 job 自己的预算到点。到点的处理与 job 自己的预算到点相同，都是 job 到点停止（0034「job timeout」节）；内容已经完整、随后正常退出的 job 保留它的判定（0034 机制二）。被期限截断与用完自己预算的 job 各记什么见 [0031](./0031-job-lifecycle-states-and-severity.md) 决定一。起作用的是哪一个截止时刻，由记录里的认领时刻、job 的预算与 run 的期限算出，不看说明，也不另记：前台与后台按同一个算法得到同一个结论。它是前台与后台共用的终结函数的一项输入，决定走真值表里预算那一行还是期限那一行（0034 机制二「终结函数与真值表」）。预算从认领时刻起算，三种组合相同（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 2 与 0034 已定后台自认领起算）：认领时刻是认领方在发出认领的那次写之前取的墙钟，随认领写进运行态；前台在线程池取到 job、通过起 worker 之前的检查之后取它，没有记录的 `run --no-report` 在同一位置取、不写。job 的截止时刻按墙钟计、从认领时刻起算（理由见下「检查用墙钟」一段）；停止等待、排空这些时长按单调时钟计，它们不进记录。
3. 已过第 1 条的时刻、没有执行中的 job、仍有未启动的 job：执行方做结束写（0031 决定三「结束写」小节），未启动的 job 记 `skipped` 并带到期的说明，run 随之成为终态。
4. 没有执行中、也没有未启动的 job：run 在最后一个 job 的终态写里随之成为终态（0031 决定三），不论当前时刻是否已过期限；全部 job 都给出了完整内容的 run 得到它们的真实结果。

四条里的「已过」「到了」一律指当前时刻严格晚于那个时刻：停止启动的时刻、期限与 job 的截止时刻三处取法相同，与前台的预算到点判断一致；job 的截止时刻恰等于期限时，两处判断在同一时刻得出同一结论。

一次前台执行可能因三种原因停下：到期（第 1、2 条）、因 fail-fast 或使用方中断而中止、发现 run 已被别处记为已结束（决策五）。它们同时或先后成立时，各 job 的结果这样定：

- 排队中、从未启动的 job，起 worker 之前依次检查：已过停止启动的时刻（第 1 条）；已发现 run 被别处记为已结束；run 已因 fail-fast 或使用方中断而中止。任一条成立即不启动，都不成立才认领并启动。不启动的 job 由谁记下：已过停止启动的时刻、或 run 因 fail-fast 或使用方中断而中止的，留在 `pending`，执行中的 job 都结束之后由执行方的结束写记为 `skipped`（第 3 条；fail-fast 与中断的来路见 0031 决定三「结束写」小节）；已发现 run 被别处结束的，记录已是终态，执行方不写。
- 执行中的 job，停止原因按 0034 机制二的首次仲裁落定一次、之后不改：做出停止决定的那一刻它的截止时刻已过即为到点（记什么按第 2 条看起作用的是哪一个截止时刻），否则为中止，中止的说明取最先成立的那个来源。「最先成立」指最先登记：三种来源都登记在 run 的中止标志上、只记下第一次，fail-fast 在判定得出时登记，发现 run 被别处结束在发现时登记（写 job 状态时的发现，在那次落库回调返回之后当场登记），使用方中断在调度循环轮询到它时登记（两次轮询之间到达的以轮询时刻为准，同一次轮询里先读停手信号、再处理中断）。发现 run 已被别处结束是 fail-fast、使用方中断之外的第三种中止来源（说明是「这个 run 已被记为已结束，job 被中止」），走同一个仲裁、不另立规则；内容已经完整的 job 保留判定。run 已被别处结束时这个 job 的终态写写不成，执行方也不存它的明细（决策五）。
- 上一次尝试已经结束、正在等待重试的 job：三种原因下都不再重试。已过停止启动的时刻、或已因 fail-fast 或使用方中断而中止时，把上一次的结果作为终态写下，并注明没有再重试及原因；已发现 run 被别处记为已结束时不写（决策五）。重新启动之前的检查与排队中的 job 是同一次序，只是最后一步的认领换成读一次 run 的状态（决策五）：已过停止启动的时刻；已发现 run 被别处记为已结束；已因 fail-fast 或使用方中断而中止；这时读到 run 已是终态。注明的原因取最先命中的一条。

run 级说明只由结束写写下（0031 决定三「结束写」小节）；`run --json` 的 `jobs[]` 怎样列出没有启动的 job 见 0041 决策三。设备计量两项合计是否出现按运行定义里有没有设备目标判断、不按有明细的 job（0051 决策 7 的出现条件）：设备 job 全部没有启动时两项都是 0，不省键。

各执行方的落实：

- 前台执行（`run`）：调度循环按墙钟检查，过了第 1 条的时刻不从队列里启动 job、也不重试；到了 `deadline_at` 把执行中的各 worker 的截止时刻视为已到并发停止请求，等它们结束后按第 3、4 条。停止启动一经成立不撤销：任何一次检查观察到已过第 1 条的时刻就记下，此后起 worker 之前与重试之前的检查都按已过处理，判断第 3 条也用这个记下的事实、不重读时钟，系统时钟回拨不会抹掉已经发生的停止启动。job 的截止时刻同样一经观察到已过就不撤销：触发停止决定的那次检查看到已过，首次仲裁即按到点落定，不因随后读到回拨的时钟落成中止。规则本身不变（真实的时刻只会越来越晚），记下它们只是不让回拨的时钟撤回已经得出的结论。未启动的 job 不存明细，由第 3 条的结束写记为 `skipped`。墙钟由组合根注入调度循环（[0026](./0026-schedule-module.md)），缺省取系统时钟，调度循环自己不另取；组合根注入的是它写时间戳的同一个读取点，记录里的时刻只有一种写法。认领时刻由调度循环从注入的墙钟取一次、交给认领写，写进记录的值与算截止时刻的值是同一个。core 里的墙钟时刻是带时区的时刻值，ISO 串只是记录里的写法，解析与写出各只有一处；不带时区的值一参与比较即报错，误注入的时钟不会悄悄得出结论。`deadline_at` 减 60 秒这个提前量、run 级说明的文字与「是否已过」的判断放在 core，前台与后台共用一份。`run --no-report` 没有记录，照样遵守第 1、2 条，第 3、4 条的结果按同一套规则在内存里给出。
- 后台推进（本机的后台推进进程、云端的 Lambda，都经 core 的同一个推进步骤）：过了第 1 条的时刻，推进步骤不认领；认领 job 时算出的截止时刻以 `deadline_at` 封顶，本机的检查、云端的一次性定时触发与防御性超时扫描都按封顶后的时刻；满足第 3 条时做到期的结束写。细节如下。
  - 时刻：推进步骤自己不取时钟，经宿主注入的时钟取时刻（与前台同一个读取点）。每次读取运行态之前取一次，用于随后的推进决策与结束时刻（同一轮里重新读取时重新取；各次取的都是墙钟，回拨时结束时刻可以早于这一轮里的认领时刻，记录不保证两者的先后）；每次认领之前再取一次，作这个 job 的认领时刻，并重做一次停止启动的检查（已过即不认领）。一轮里靠后的认领因此不沿用轮首的时刻：前面的读取与启动调用有耗时，沿用会让靠后的 job 少拿到预算。这一轮里有认领因为已过停止启动的时刻而没有做时，推进步骤在同一轮里重新读取运行态与事件、按已过停止启动再决策一次（这一轮里先前认领成功的 job 计入其中），不拿轮首的快照做结束写，也不就此返回：云端此后可能没有别的东西触发下一轮，满足到期结束写的 run 会停住，只剩处置这一个出口（谁能处置见决策八，条件见决策六）。重新决策只做一次，直接按已过停止启动处理、不再拿重新取的时刻判断，系统时钟在这之间回拨也不会让这一次又提议启动。启动调用失败时也再取一次时刻，记为这条退出记录的退出时刻：它晚于这个 job 的截止时刻时投影按到点处理（第 2 条），与前台起 worker 失败的分支得到同一个判定；不晚于就是启动失败。后台的启动失败补偿交给终结函数的输入与前台相同（退出码未知，带启动失败的原因），不用平台失败的哨兵退出码：哨兵退出码会让两条路径对同一个启动异常给出两句不同的说明。实测项 4（三种组合一致）包括这类 job。
  - 决策：是否已过停止启动的时刻是推进决策（`plan_next`）的一项输入，决策是一处纯函数。已过时不提议启动；没有执行中的 job 而仍有未启动的 job 时提议到期的结束写；其余照常推进。这里的「未启动」按运行态判断：job 在这一轮读到的运行态里是 `pending`，不读事件（结束写只看运行态，0031 决定三「结束写」小节）。推进决策给出的结束动作只有到期的结束写（读不到可用的运行定义时的那种结束写不经推进决策，见 0031 决定三「结束写」小节）；第 4 条不是一个单独的动作，run 在最后一个 job 的终态写里随之成为终态。
  - 快照：推进步骤先读运行态、后读事件，手里的运行态可能比事件旧。为一个有事件记录的 job 存明细、写终态之前，要求它在这一轮读到的运行态里带认领时刻（读不出或不带时区的同样算不带，后台各处的时刻都经 core 的同一处严格解析读回）；不带说明它是在这一轮读运行态之后才被认领的，这一轮不为它存明细、不写终态，下一轮读到新的运行态再做。不用「取不到认领时刻就按预算说明」这样的回落：截止时刻要由认领时刻算出，回落得出的可能是错的那一句。
  - 截止时刻与说明：认领时由认领时刻、预算与期限算出这个 job 的截止时刻（与前台同一个算法），随启动交给启动器。本机的后台推进进程按墙钟检查它，每个执行中的 job 一个按短间隔读墙钟的检查：检查读的墙钟由组合根注入启动器，与推进步骤取认领时刻的是同一个读取点，两处比较的才是同一个时钟；间隔只决定到点之后最多晚多少发出停止请求，不进任何记录；检查持续到 worker 进程退出、不止到事件流结束，关了事件通道却不退出的 worker 过了截止时刻同样被停下。退出记录另带一项事实，退出时刻：本机是推进进程看到 worker 退出的那一刻（经注入的墙钟读取），云端是 task 对象里的执行停止时刻（退出观察者与 job 到点停止都从 task 对象取，同一个 task 两处取到同一个值），启动失败的补偿记失败的那一刻；补写的未知退出没有可观察的退出时刻，不带这一项。投影时，退出时刻晚于这个 job 的截止时刻的退出与带超时标志的退出同样处理（内容完整的不改判）：worker 在截止时刻之后、停止请求发出之前自己退出时，本机后台与云端后台得到的判定与前台终结之前的那次检查相同。观察者只记事实，不判断是否已过截止时刻：截止时刻要由运行态与运行定义算出，云端的退出观察者只看 task 对象；判断放在两种后台共用的投影里，规则只有一份。超时标志因此只表示发过到点的停止请求、或补写时已判为到点，不兼管「退出时已过截止时刻」。本机的后台推进进程里，看到 worker 退出（读退出时刻、读超时标志）与检查线程的到点决定（确认还没有看到退出、读墙钟、置超时标志）互斥进行，先后只有一种：已经看到退出之后检查线程不置标志，退出记录里不会出现「退出时刻不晚于截止时刻、却带着之后才置上的超时标志」的组合。云端的一次性定时触发定在这个时刻，Lambda 对到点触发的复查与防御性超时扫描按同一个算法重算。定时触发早于截止时刻时，job 到点停止在这次调用的等待额度之内等待，额度之内没有读到已过的这一次不停止、留给之后的推进检查（何时等待、额度怎样定，见 0034「job timeout」节「到点不早于 deadline」条②）：发出停止之前必须有一次读到已过截止时刻。后台被截断的 job 同样按起作用的截止时刻分开（0034 机制二「终结函数与真值表」，各记什么见 0031 决定一），投影时由运行态里的认领时刻、预算与期限重算是哪一个起了作用，不在退出记录里另记。终结函数的这项输入没有缺省值：前台在认领时算出、后台在投影时重算，两条路径都必须给出它，不会因为漏传而悄悄落到预算那一行。
  - 收尾与报告：到期的结束写在云端以这一轮读到的写入序号为条件，写不成即重读再算：仍满足第 3 条就再写；有了新的认领、不再满足的按继续推进处理；本机在 `.runstate.lock` 内读改写，按锁内读到的整份运行态计算（两侧见 0034 机制三②）。读到已是终态说明别处已经结束了它，按已结束处理。读不到运行态的那一轮不做到期的结束写。逐 job 的写序（先存明细、再写终态并点名）见 [0030](./0030-realtime-persistence-seam.md) 决定三，报告由使 run 成为终态的那次写的写入方从记录生成（[0027](./0027-runreport-aggregation-index.md)「ReportStore 接口：整 run 一次写」节）。
  - 不记「已过停止启动」：推进步骤是无状态的，每一轮按当前时刻判断。某个推进器的时钟回拨或落后时它可能在这个时刻之后又认领，新认领的 job 的截止时刻照样以期限封顶（第 2 条）。云端写入序号的条件保证的是记录层面的一致：读取之后有新的认领就不做到期的结束写。它不保证 run 记为终态时没有 worker 还在执行，那属于「边界与已知局限」里已列的情形。
- 云端后台 run 另有两次 run 级的定时触发，属于后端：各做什么、成立的前提与前提不成立时怎样，见决策九第 1 条。

**检查用墙钟**：期限与 job 的截止时刻都按墙钟检查，不用单调时钟。期限是别的机器也要拿来比较的时刻，而且单调时钟在系统休眠时不走，合盖几小时再打开的进程只有按墙钟才知道自己已经过期。job 自己的预算同理：执行方的机器休眠期间，云端的 task 与远端的会话照常消耗，浏览器会话的存活时间也是按墙钟由预算推出的；按墙钟计，前台与后台的截止时刻才是同一个算法。代价是系统时钟被大幅调整时，job 的预算随之变长或变短；按单调时钟计能避开这一点，但给不出别的机器能比较的时刻（前台调度循环的两个时钟见 0026）。

每个 run 因此有一个由 job 预算推出的总时长上限。它不是使用者单独配置的 run 级预算（0034「job timeout」节不设 run 级总墙钟预算），调整它的途径是各 job 的墙钟预算与停止宽限。选它而不把期限只当作「推定管 run 的进程已不在」的阈值，理由是：

- 对测试工具，一次 run 允许运行的总时长有上界本身是该有的性质：CI 可以据此排期；云端浏览器会话与真机按分钟计费，休眠后恢复的执行方会自己把过期的会话停掉，后台的推进器同样遵守期限，不靠有人查看。
- 三种组合是同一种表现：「允许运行至」对所有 run 是同一个意思，上层不必按执行方式分别理解。代价是推进停住的 run 满足处置的条件之后可以被结束（条件见决策六），被处置的要重新提交。
- 清单里这一列的名字是「允许运行至」，硬约束才名副其实。

### 三、生命期锁：加在 run 目录上

本机后端的 run 由持有它的生命期锁的进程推进：前台是执行 `run` 的进程，后台是 `submit` 启动的后台推进进程（本机任何时刻至多一个推进器，这条规则在 0034「推进器与触发源」）。管这个 run 的进程还在不在，由别的一方试拿这把锁回答（决策六）。

- **对象**：run 目录本身。持有方以只读方式打开 `<report-dir>/<run_id>/`、取排他的 `flock`；锁按打开的文件描述计：同一进程另一次打开同样被挡，共用这个打开的进程里有一个还开着，锁就在。
- **谁在何时拿**：
  - `run`（生成记录时）：建出 run 目录、拿到锁之后才写运行定义与运行态，持有到进程退出；锁已被持有时以退出码 2 结束（试拿方只碰运行态已读得出的目录，这只在 run_id 重复时出现）。
  - `submit --backend local`：提交进程同样先拿锁再建 run，启动后台推进进程时把描述符交给它，只关掉自己那一份、不解锁，退出；交接期间两者都持锁，提交进程关掉之后推进进程退出即释放（见本节末尾的前提）。推进进程先核对交来的描述符是目录、设备号与 inode 同这个 run 目录，再对它取一次锁；核对不过或没有交来锁时不推进、退出。
  - 云端后端没有锁。
- **谁在何时试拿**：等待中的 `status --wait` 在 run 未结束时每次轮询试一次，`settle-runs` 对每个未结束的本机 run 试一次（决策八），都只对运行态已读得出的目录；不阻塞，拿到之后持有到这次处置做完。
- **结果的判读**：只有成功算拿到，只有「已被持有」（`EWOULDBLOCK`）算持有者还在；其余错误一律按锁不可用：建 run 的一方以退出码 2 结束，处置的一方只剩期限一条（决策六）。
- **不被子进程继承**：描述符不可继承，持锁的进程只经 exec 启动子进程（worker、隧道 agent），收到交接的推进进程先置为不可继承。
- 理由：死活由操作系统在进程退出时给出，不需要对方配合，也不靠时钟。真实进程核过（macOS 的 APFS，Linux 清单里的类型与绑定挂载，括注的除外；清单见决策四）：被暂停的持有方仍持有，已退出未回收的已释放；交接后仍持有，交出方关掉自己那一份之后接收方被杀即释放（关掉之前仍被挡：macOS 的 APFS、Linux 的 ext4）；fork 而不 exec 的子进程延长持有，`subprocess` 缺省方式启动的不会，`multiprocessing` 以 fork 起的会（Linux 上 Python 3.12、3.13 的缺省）；交出方显式解锁连同接收方的一并解开；对交来的持锁打开、或一个没被锁的别的文件再取锁都立即成立（同一 run 目录另一次未加锁的打开被挡），所以接收方先核对对象。放弃：POSIX 记录锁（只读打开的目录取不上排他的；按进程计，关掉任一指向该文件的描述符即释放；交接后原进程一关即释放，Linux 的 ext4 上核过）；长期持有 `.runstate.lock`（读改写用的短锁，长期持有挡住所有写）。
- **前提**：持锁的进程启动子进程只经 exec；交接只经启动后台推进进程那一次，接收方核对交来的是这个 run 目录。依赖方：「拿得到锁即管它的进程已不在」（决策六）与「本机至多一个推进器」。交接期间提交进程也持锁：它在关掉自己那一份之前被暂停时，推进进程退出了也拿不到锁，锁这一条要等它关掉那一份或退出才成立，在此之前只剩期限一条（决策六）。

锁只在决策四的边界之内有效。

### 四、生命期锁的前提：本机后端报告目录的产品边界与边界检查

- **产品边界：本机后端的报告目录及其中的 run 目录要在本机文件系统上**（检查见下一条）。同一个内核上经同一个挂载或其绑定挂载访问的在边界之内（实测宿主与容器、容器之间）；网络文件系统、经虚拟机共享进来的目录在边界之外（实测 macOS 的 Docker Desktop：宿主目录在容器里是 `fakeowner` 类型、被拒，宿主一侧是 APFS、放行，两侧的锁互不阻挡）；多台机器共用记录用云端后端。用户文档写明并列出清单。
- **边界检查**（本机后端）在取锁与试拿锁的动作里、先于取锁（`run`、`submit`、等待中的 `status --wait`、`settle-runs`），对要取锁的那个 run 目录的描述符判断（后台推进进程用提交进程判断过的那一次打开，不另判断）；建 run 的一方另在建 run 目录之前对报告目录（不存在时取最近一层已存在的上级）判断一次，这一次被拒时不留目录。类型不在清单里或判断不了（如读不到挂载信息、平台不是 macOS 与 Linux）即以退出码 2 结束，说明写原因（这样的目录上无法确认执行 run 的进程是否还在）、检测到的类型与怎么办（列出清单）。`settle-runs` 在报告目录存在时另查它（不存在即没有可处理的 run，照常结束）；某个 run 目录不过只跳过它、在结果里写明原因（决策八）。`doctor` 的报告目录一项用同一判断（0041 决策四）；其余命令不碰锁，也不查。放行不证明在边界之内、锁有效（见下面「文件锁有效」一条；不靠读回，见「被拒方案」）。两个平台同一条规则（macOS 不只看本机标志，见「被拒方案」）：各处都对打开的目录的描述符取文件系统类型，由内核解析路径（含符号链接、绑定挂载与盖住它的上层挂载；两个平台上实测按挂载表的最长前缀会取到被盖住的那条），只放行清单里的类型；清单只收照决策三理由实测过的，先实测再加：
  - macOS 由 `fstatfs` 取类型名。实测（arm64）：APFS 为 `apfs`，HFS+、FAT 的磁盘映像为 `hfs`、`msdos`，autofs 自动挂载点为 `autofs`。清单：`apfs`。HFS+、FAT 上的锁只核过互斥、同一进程再开被挡、被杀后释放，不进清单。
  - Linux 由描述符的 `mnt_id`（`/proc/self/fdinfo`）在 `/proc/self/mountinfo` 取那一条。实测（内核 7.0）：被盖住、经符号链接、容器里的路径都取到实际所在的挂载，绑定挂载显示源的类型，不存在的目录取上级、与新建后同类型，懒卸载后取不到；NFS 为 `nfs4`、`nfs`。清单：`ext4`、`tmpfs`、`overlay`（宿主与容器上实测）；`xfs`、`btrfs`、`ext3`（回环镜像、缺省选项、`btrfs` 顶层子卷上重做，除数值外与 `ext4` 相同）。
- **前提：本机文件系统，文件锁有效**。产品边界之内保证的前提是 `flock` 对所有读写这个 run 目录的进程按打开的文件描述互斥（运行态的写锁本来就依赖它，0030 决定三）。边界之外的共用不在保证之内：两侧的锁（含运行态的短锁）可能互不可见（NFS 上的实测见「被拒方案」），运行态的写可能互相覆盖。检查放行而在边界之外的：同一块设备挂在两个内核上、两边取到的类型都在清单里；同一个内核里经两个文件系统实例访问同一份数据（实测：容器 overlay 与它的上层目录之间锁互不阻挡）。依赖方：两个本机处置方与「本机至多一个推进器」。
- **前提：边界检查信任内核给出的挂载信息**（macOS 的类型名，Linux 的挂载表与描述符的挂载 ID），不防伪造它的一方，与「边界与已知局限」里「有人改动、删除 run 目录里的文件」一条同类；判断与取锁对同一次打开做。

### 五、终态不可变，执行方服从记录：run 结束之后不再接受新的认领

**终态不可变。** run 的状态只往前走：`pending` 到 `running` 到终态；run 一到终态，运行态的任何写都不成立。这对端口上的每一个写入口成立（形态见 0030 决定四），前提是写都经端口的写入口。它不丢信息：run 是终态当且仅当全部 job 是终态（0031 决定三），到终态时每个 job 都已有终态，此后到达的结果是迟到的结果、不被采用。

- 建 run 只在这个 run 还不存在时成立：云端要求条目不存在，本机要求 run 目录里还没有运行态，对已有的 run 再调用即失败、不改任何东西；端口不提供整份重写与无条件改写终态的入口（0030 决定四）。本机的判断与两个文件的写在同一把文件锁内完成；云端的两次条件写与卸载 step 参数正文之前的先读见 0030 决定六。
- 本机的全部写入口在同一把短锁（`.runstate.lock`）内读改写、互相排斥，按锁内读到的整份运行态计算（0034 机制三②）；0030 决定三的并发不变量因此对全部写入口成立。

理由：终态之后再变，对任何基于状态做事的上层（等待者、退出码、清理、处置，以后的界面或服务）都是错的行为：已经返回的退出码撤不回，已经据终态做的清理与处置撤不回。依赖方：`status --wait`、`list-runs`、CI 把读到的终态当定论，报告据记录生成。

**执行方服从记录。** 终态不可变只保护记录，不能让执行停下来。执行方每次启动 job 之前先认领，认领以 run 未结束为条件（0034 机制三「run 级状态只进不退」条①；各命令写什么见 0034「命令形态」），所以 run 记下终态之后不再接受新的认领；检查已经通过、启动还没有完成的 job 仍会启动（本节「这一条不依赖时钟」一段）。各执行方的做法：

- 后台推进的认领要求 run 为 `pending` 或 `running`（`try_claim_job`）。
- 前台执行同样先认领（0026）：从队列里取到 job、第一次起 worker 之前先做同一个认领，认领时刻随之记进运行态。一个 job 只认领一次；同一个 job 因网络故障重试时不认领（它已是 `running`，再认领会被自己拒掉），而在每次重新启动之前读一次 run 的状态（[0028](./0028-transient-network-ssl-resilience.md)「重试之前的检查」）。认领被拒或读到 run 已是终态，说明 run 已被别处记为已结束：这个 job 不启动，调度循环对执行中的 worker 发停止请求，然后结束。起 worker 之前各项检查的次序、停手时各种处境的 job 怎么记，见决策二「一次前台执行可能因三种原因停下」一段：发现 run 已被别处结束是一种中止来源。认领排在各项检查之后、紧贴起 worker，免得留下已认领却没有执行的 job。执行方自己的时钟已过停止启动的时刻时，拦住它的是时间检查；认领被拒这一支在它的时钟落后于处置方时才会走到。认领或读取本身失败（存储不可达）按运行期落库失败处理，与落库回调抛出异常相同。代价是前台每个 job 多一次条件写（认领）。
- 前台此后写 job 状态（开始执行、结束）时保留认领时刻。这两处是整项替换，不带认领时刻的写会把它抹掉。做法是落库服务记住每个 job 的认领时刻、此后的写带上它（与代表会话同一做法），存储 adapter 的整项替换不变。
- 前台写 job 状态时发现 run 已是终态（这次写写不成）同样触发停手。为此 `update_job_state` 返回 run 在这次写时是否仍未结束，run 已结束时写不成、返回 `False`（0034 机制三③），两个 adapter 对拍。认领、重试之前的读、job 状态写三处的发现汇成同一个停手信号，调度循环不碰存储（0030 决定一），经组合根注入的能力取得它：job 状态写时的发现在那次落库回调返回之后当场读进来，等待循环另与使用方中断同一节拍地轮询它、先于中断读（登记的次序见决策二「一次前台执行可能因三种原因停下」一段）。认领、重试之前的读与停手信号三项合成一个注入对象：有记录的执行三项都有，`run --no-report` 三项都没有，不会出现只注入其中一部分的状态（形态见 0030 决定一）。
- **执行方得知 run 已结束之后就不存明细**（迟到的结果不被采用）：前台在停手信号成立之后，本机后台与云端在一轮读到终态之后。run 到终态之后新落下的明细只剩已开始的保存（前台是那一次，本机后台与云端是那一轮的各个 job），三种组合都有；读者怎样只认被终态点名的那一份见 0030 决定三。
- 结束时前台执行方不覆盖已有的终态，在终端说明这个 run 在本次执行结束之前已被记为已结束，说明与判定明细的位置写在 stderr，以非零退出码结束（退出码见 0031 决定五）。报告不由它生成：报告只由使 run 成为终态的那次写的写入方生成（0027「ReportStore 接口：整 run 一次写」节），这里是结束它的那一方。`run` 也不输出汇总与 `--json` 文档（0041 决策三）：run 由别处结束，结果从记录读（`status`），本次执行看到的只是其中一部分。

这一条不依赖时钟：不管两台机器的时钟差多少、执行方是否被暂停过，run 一旦是终态，它的下一次认领或启动前的检查就会拦住。能越过它的只有检查已经通过、启动还没有完成的 job（至多并发上限那么多）：首次启动是认领已成功，重试是启动前的那一次读已通过，而启动调用还没有发出、正在进行，或句柄还没有返回。它们会启动。启动之后由谁停，三种组合不同，见「边界与已知局限」里「run 到终态之后各组合下还会发生什么」那张表。

由此终态之间没有分组变化（0041 决策七）。

### 六、死活的判断与处置的条件

- 管这个 run 的进程还在不在，由试拿生命期锁回答（决策三）：拿得到即已不在；被暂停的进程仍持有锁，算还在。
- **管它的进程不在了的 run 不续**：此后不认领、不启动 job，只能由别的一方把它结束，即 run 处置（本篇单说「处置」都指它）；job 到了截止时刻被停下另称 job 到点停止（0034「job timeout」节）。谁能处置见决策八。
- **可以处置的条件是两者之一**：试拿锁拿到了；或当前时刻严格晚于运行期限加 300 秒。云端只有后一条。300 秒给时钟偏差与仍在的推进器按期限自己结束（决策二第 3 条）留出余量，不是收尾时长的上界（下一条）。期限读不出（运行定义读不出，或 `deadline_at` 不合法）时只剩试拿锁一条，云端即无从处置。
- **期限加 300 秒按墙钟判断，不是推进器收尾时长的上界**：处置方与推进器各读自己的墙钟，本机两者读同一个内核的；云端两者的时钟可能不同，处置方的比推进器慢时处置推迟，快时提前，推进器在期限之后的余量是 300 秒减去快出的量，快出的量超过 300 秒加这个 run 离期限的余量时，在推进器看来仍在期限之内的 run 已满足处置的条件。停止与落库调用可能阻塞更久（决策二「尾段与余量」一段），被暂停的推进器不受时长约束。处置做的结束写只看运行态（0031 决定三「结束写」小节）：`running` 的 job 记 `aborted`、`pending` 的记 `skipped`，不论推进器一侧走到哪一步；没写进运行态的结果不论是什么都不被采用（决策五），run 不会是 `passed`（推进器本会使它通过的也是）。此后的事按既有各条：`run` 的退出码见 0031 决定五，终端输出见决策五；还会落下哪些明细见决策五，报告由谁生成见 0027；留下的执行由谁停见决策七「处置只改记录」一条。
- 运行态本身读不出的 run 无法做条件写，不处置。

### 七、处置做什么

- 读运行态，已结束则不动；否则做结束写（0031 决定三「结束写」小节，说明取其中说明表里处置的两行），写成的一方生成报告（0027「ReportStore 接口：整 run 一次写」节）。两个处置同时发生、或处置与推进器自己的结束写同时发生时，只有一方写成，另一方读到已结束（决策五）。
- 处置不推演事件，不替事件里有、运行态里还没有的结果下结论：推进器在 worker 退出之后、写下终态之前中断（云端触发链断开时这段可以很久），处置看到 `running`，记 `aborted`「没有结果」；同一次中断在云端通常由流的重试与之后的触发记下真实结果，三种组合的 job、run 状态与退出码可能不同。不取「处置方先按事件记下已有结果的 job，再结束其余的」：它与云端一致，但本机处置方要推演事件，云端的 `status --wait`、`settle-runs` 要多出读 events 表、写明细的权限，不给则两种云端处置方结果不同。
- 本机推进器因保存明细一直失败而退出时，执行中的 job 留在 `running`，被处置时记「进程已退出」那一句（重试与放弃见 0030 决定三）。
- 清理协议不用改：run 被结束后离开 `live` 分组，不再占住它引用的 worker 版本（0038 残余风险④）。此后执行方不认领新的 job（决策五），余下未启动的 job 不会再用到这些版本；检查已经通过、启动调用还没有发出的那几个 job 可能因为版本刚被回收而启动失败，这个 run 此时已是终态，不影响记录。
- **处置只改记录**，不停执行：本机 worker 在推进器退出之后靠核验所属进程自行退出（[0024](./0024-worker-core-protocol.md) 终止契约，通常十余秒，失效情形见「边界与已知局限」）；前台推进器发现 run 已结束之后对它启动的 worker 发停止（决策五），本机后台推进进程发现之后退出；云端由后端清扫 task（决策九第 2 条）。

### 八、处置方与入口

- **能处置的只有**：`settle-runs`；等待中的 `status --wait`；云端的 run 另有后端到期结束（决策九第 1 条，含前提）；以后的取消命令（条件与对推进器的作用在取消的设计里定）。`list-runs`、不带 `--wait` 的 `status`、`explain` 只读、不碰锁。各处置方写什么见 0034「命令形态」的表。判定与处置放在 runtime 包，`status --wait` 与 `settle-runs` 都调它。
- **本机没有常驻的处置方**：推进器退出或停住之后，没有人执行 `status --wait` 或 `settle-runs` 时，没有别的一方结束这个 run，`list-runs` 照常列出。
- **`gherkai settle-runs [run_id] [--dry-run] [--json]`**，加 0041 决策六的三项定位参数，取值来源（含项目配置文件那一层，[0053](./0053-project-config-file.md) 决策 1）与 `status` 相同。不给 `run_id` 时处理这个后端里全部未结束与运行态读不出的 run，不分前台与后台；给了只处理那一个。每个 run 依次看运行态、边界检查与试拿锁（本机，决策四、三）、期限，`reason` 取第一条成立的：`unreadable`（运行态读不出）、`already_finished`（已结束，含结束写被别处抢先）、`unsupported_filesystem`（run 目录不过边界检查）、`advancer_exited`（锁拿到了）、`past_deadline`（已过期限加 300 秒）、`lock_held`（锁被持有，未必是推进器）、`undetermined`（锁不可用或期限读不出）、`within_deadline`（云端未过期限加 300 秒）。`advancer_exited` 与 `past_deadline` 的 `outcome` 是 `settled`，`--dry-run` 下是 `would_settle`（不写，锁拿到即放开）；其余是 `skipped`。人读输出逐条给出 run、判定结果与处置；`--json` 给一个对象：落点字段同 `list-runs`，`dry_run`，`runs[]` 每项带 `run_id`、`outcome` 与 `reason`。跳过不改变退出码；写入失败时就此停止，再执行一次是安全的：已处置的给 `already_finished`。退出码见 0031 决定五。它是变更类命令里带 `--json` 的一个：0041 决策三把变更类命令的机读面定为退出码，这里的结果是逐条的处置清单，退出码承载不了，作为该条的明示例外。
- **等待中的 `status --wait`**：两个后端、前台与后台的 run 都一样，在 run 未结束时每次轮询看处置条件（决策六）：本机先试拿锁（决策三），再比期限；云端比期限。条件成立即处置，然后照常渲染、给终态的退出码（0031 决定五）。条件不成立时继续等待：锁被持有不另说明，锁不可用时说明原因。运行态本身读不出时只等待并说明原因（决策六）。它只盯到终态、条件成立时处置，不推进；云端不调用 `kicker`（唤醒推进的只有流与定时触发，0034「推进器与触发源」）。
- **云端用户一侧的处置方**（`status --wait`、`settle-runs`）要能做 runs 表的条件写、读运行定义与判定明细、写报告；缺后两项时结束写照样写成而这个 run 没有报告。依赖方：被处置的云端 run 有报告。权限逐项登记在 0033 编排进程角色，梯级见 [0040](./0040-consumer-role-model-and-terminology.md) 决策 3。
- `list-runs` 的「已运行」「允许运行至」两列、期限提示与 `--json` 的 `deadline_at` 见 0041 决策七。

### 九、云端后端：到期结束 run，run 结束之后清扫它的 task

本机的 worker 能核验管它的进程还在不在，不在就自己退出；云端的 task 做不到。云端的每个 run 都由后端推进（0034「推进器与触发源」），云端后端里一直都在的只有 Lambda，所以到期结束 run 与停掉 task 也放在后端，由两个推进 Lambda（`kicker`、`reconciler`）承担，不另设。

1. **定时触发。** `kicker` 收到 STATE 条目的新建（META 已先写）时建两次一次性的定时触发（与 job 超时触发同一机制、同一角色，触发之后自动删除）。runs 表流的过滤明写 `INSERT` 且 `item_type` 为 STATE：建 run 时先写 META 再写 STATE，两条都是新建，只收 STATE 才保证 kicker 处理时 META 已在。建不成时这次调用失败、由流重试（名字确定，重试不重复建）。
   - 期限那一次：时刻取 `deadline_at`，对仍在执行的 job 做 job 到点停止，再推进。它与各 job 自己的定时触发是同一处理：各 job 的截止时刻以期限封顶（决策二第 2 条），确认已过期限时它们都已过。另设这一次，是因为各 job 自己的定时触发是尽力而为地建立的（0034「job timeout」节「best-effort 边界」条），某一个没建成、它的 worker 又不出任何事件时，可能再没有别的调用带到这个 run。停止引出的退出事件带起之后的推进，推进按决策二第 3、4 条处理。
   - 期限加 300 秒那一次是**后端到期结束**：run 仍未结束即按决策六、七处置，说明取「已超过允许运行的时间」那一行（0031 决定三「结束写」小节）。
   - 到点的处理重新读墙钟确认已过（期限那一次比 `deadline_at`，后一次比期限加 300 秒，按决策六的墙钟判断），不以收到触发为证据（定时触发只承诺分钟精度、表达式不带小数秒）；未过则照 job 到点停止的到点复查在这次调用里等待，等待额度用完仍未过的这一次不动手（0034「job timeout」节「到点不早于 deadline」条②）；run 已结束时只清扫。
   - 两次的时刻是计划触发的时刻，不是处理完成的时刻。两次是彼此独立的异步调用：各自可能晚到，失败时按 Lambda 异步调用的重试再调用，调用到达与处理的耗时没有上界（0034「job timeout」节「到点不早于 deadline」条③）；两次完成的先后没有保证。期限加 300 秒那一次可以先结束 run，期限那一次随后到达时 run 已结束、只清扫；run 结束时仍在执行的 task 交给清扫（第 2 条），不依赖期限那一次先做过 job 到点停止。
   - 前提：每一次都要 `kicker` 收到 STATE 的新建、建成这一次的定时触发、这一次的调用成功，并在等待额度之内确认已过它的时刻。期限那一次任一环不成立时，执行中的 job 剩下的出口是它自己的定时触发与防御性超时扫描（0034「job timeout」节「best-effort 边界」条与 `JobState.claimed_at` 条②），run 结束之后另有第 2 条的清扫。后端到期结束一侧：推进链断开的 run 只能由之后的事件或定时触发带起，云端 `status --wait` 不唤醒推进（决策八）；都没有把它带到终态而前提成立时，期限加 300 秒那一次结束它，没有 job 出错或未通过时以 `aborted` 告终，需要重新提交。任一环最终失败时不保证后端自行结束它；此后也没有别的后端触发带到这个 run 时，只有用户一侧的处置方（决策八）能结束它。
2. **结束之后清扫。** run 到终态之后，后端按启动时带的 run id（`startedBy`）列出仍在执行的 task 逐个停掉（可重复，不写 runs 表；失败时这次调用失败，流触发的由流重试，定时触发的按 Lambda 异步调用的重试）。触发有三处：
   - 使 run 成为终态的那次写经流（新映像的状态分组不是 `live` 的 STATE 条目）触发 `kicker` 清扫，过滤命中的只有这一次写（终态之后运行态不再有写，决策五）。处置方的结束写、推进器自己的结束写与终态写、后端到期结束都经这里。流事件按批调用，同一批里按 run 去重；跨批的事件、迟到的事件与定时触发可能再次清扫。清扫可以重复执行，不要求恰好一次。
   - 没停到的（如 run 结束之后才启动的，0034 机制三「run 级状态只进不退」条①）由此后带到这个 run 的任一次调用停掉：worker 的事件、退出记录、定时触发。推进 Lambda 的各入口遇到已结束的 run 时，在「不改写它的结果」之外做同一个清扫。
   - 定时触发的调用到达时 run 已经结束，同样清扫一次。

正常结束的 run，job 的退出记录来自 task 停止的观察链时，这个 task 在 run 结束之前已经停止，清扫不会打断还在做最后上传的 task；退出记录是补写的未知退出时（0034「job timeout」节），task 可能还在执行，它的 job 已按到点处理，由清扫停掉；列 task 的调用可能仍返回刚停止的 task，对它们没有要停的。清扫不写 runs 表，不会形成「清扫引出写、写再引出清扫」的回路；它停掉 task 引出的退出事件、终态之后迟到的事件会带来更多调用，性质不同。

用到的权限（列 task、停 task、建定时触发）都在推进 Lambda 的角色上，runs 表开流；两次定时触发的名字空间、kicker 流上的两个过滤与授权登记在 0033 资源清单 13、15 与 IAM 一段。代价按调用的批次与实际清扫的次数计：每个 run 结束时至少清扫一次（一次列 task），跨了批时再清扫；多个 run 的事件可能合在一次 Lambda 调用里。每个 run 另多两次一次性的定时触发。

落实时清扫的位置要对：清扫必须在各入口「已结束的 run 跳过」那一道之前就能走到，不能只加在推进里，否则 run 已结束之后迟到的事件永远到不了它；job 超时的入口也要先看 run 是否已结束，再去看 job 的状态。

这样两个后端在到期时的停止与 run 的结束上是同一种表现（job 与 run 记什么按结束写，0031 决定三「结束写」小节）；差别只在由谁来停：本机是执行方与 worker 自己，云端是后端（本决策第 1、2 条）。停不到的情形见「边界与已知局限」。

### 十、job 的墙钟预算有一个产品定的上限

- 一个 job 的墙钟预算最长 7200 秒（2 小时）。它是产品的设定，放在 core，对所有目标是同一个数。
- 引擎与平台各自的限制是另一回事，归引擎：桌面目标的浏览器会话，平台允许的最长存活时间是 28800 秒，两个引擎的 worker 把会话的存活时间设为 job 预算加 120 秒；设备目标的会话上限由引擎在能力自述里报出，现在是 8880 秒。core 不抄这些数。两者之间只有一个关系：产品上限不大于任何一个引擎对任何目标能支持的最长预算，由测试守住（设备对照能力自述里的上限，桌面对照会话存活时间的封顶值减 120 秒），引擎那一侧的数哪天低于产品上限，测试即失败。引擎自己的检查保留，作为最后一道。
- `@timeout:N`（[0019](./0019-feature-tags-scope-and-engine.md)）与显式给出的 `--default-job-timeout` 正值超过上限时，计划阶段报错、以退出码 2 结束，与设备目标低于下限是同一处理；桌面与设备目标相同。
- `--default-job-timeout` 给 0 或负数，对任何目标都表示取这个上限。什么都不给时的缺省是桌面 300 秒、设备为获取预算加 900 秒。设备预算的下限（获取预算加 180 秒，获取预算最大 3600 秒）最大是 3780 秒，在上限之内。
- 上限检查与给 0 的含义都落在 [0025](./0025-plan-module-feature-to-jobs.md) 的取值次序之后：scope 里有场景标了 `@timeout` 就用标的值，否则用显式给出的缺省，都没有才按目标补缺省。被检查的是这样解析出的有效预算；被 `@timeout` 盖住、没有生效的缺省值不检查，给 0 或负数也只作用于没有标 `@timeout` 的 scope。
- `Job.timeout_s` 恒为正数。运行定义里这个键恒为正数，读端把空预算当作违约拒绝；调度与推进里没有「没有预算即不设截止时刻」的分支，超时说明没有无预算时的回退写法，云端每个 job 都建超时触发，隧道存活时间上限（0035）里没有给不超时的 job 记账的固定值。缺 job、缺认领时刻、能力自述没给上限这几种含义不同的判空保留；计划阶段的空值只表示「没有显式给出缺省」。
- worker 协议里 job 输入的预算可以为空，两个 worker 的空值分支与规范样本保留，core 不产出空值。不把协议也收为恒正：那要两个方向一起升协议版本，使用者自建的 worker 变体都得重建，为去掉一个不会出现的取值不值得。

理由：

- 「不超时」实际上也不是无限。job 没有预算时，Midscene 的 worker 不向平台传会话的存活时间，平台缺省是 3600 秒（最长可设 28800 秒）；Nova 的 worker 不向 SDK 传这个参数，SDK 自己取 3600 秒写进请求。两条路径的结果都是一小时：不超时的桌面 job 不会被停，它的浏览器会话一小时后被平台关掉，之后的 AI 步骤全部失败。有上限时预算恒有值，会话的存活时间按 job 预算加 120 秒随预算取值，给 0 的使用者能用到的是 2 小时，比不超时实际得到的一小时长。
- 每个 run 都有期限，处置的期限一条（决策六）对每个 run 都可用：没有期限的 run，本机只能靠试拿锁处置，云端没有任何一方能处置它。
- 云端的 run 另有后端到期结束（决策九第 1 条，含前提）：推进停住、又恰好有 job 自己不结束时，它是后端一侧的出口。这不是费用的硬上界：处置受决策九里触发、列举与停止各自的边界约束。

代价是不能有超过 2 小时的单个 job（浏览器会话最长撑约 8 小时、设备引擎允许 8880 秒）。上限是产品的选择，不是引擎的极限；以后要放宽只改 core 的这一个数，前提是不超过各引擎能支持的最长预算。

## 边界与已知局限

**三种组合的对照**：三种组合在各情形下的结果，每格只写结论，规则在所指处（「说明表」指 0031 决定三「结束写」小节里的那张）。

| 情形 | job | 三种组合 |
|---|---|---|
| 被期限截断 | `aborted`、期限那句（0031 决定一） | 相同；到了期限加 300 秒推进器还在收尾时见决策六「期限加 300 秒按墙钟判断」一条 |
| 推进器中断（本机进程退出；云端一次调用失败） | 本机不续，被处置时按说明表「锁拿到了」一行（交接期间提交进程被暂停时按下一行，决策三的前提；谁能处置见决策八）；云端可以由流的重试与之后的触发接着推进，推进链断开时怎样结束见决策九第 1 条（含前提） | 不同，出自 0034「推进器与触发源」与决策六 |
| 推进停住，按期限一条被处置（决策六） | 按说明表「已过期限」一行 | 被处置时相同；谁能处置见决策八，云端后端的到期结束见决策九第 1 条（含前提） |
| 保存明细失败，重试成功之前没有被处置 | 照常记下 | 相同 |
| 保存明细一直失败 | 本机重试 3 次之后推进器退出，云端可以由流的重试或之后的触发再做；本机推进器退出之后、云端推进链断开时，同「推进器中断」一行 | 不同，出自 0030 决定三 |
| 运行定义不可用 | 未结束的 job `error`（0031 决定三「结束写」小节） | 两种后台相同（前台没有这种情形） |

其余情形三种组合相同：job 得出结果或用完预算（终结函数，0034 机制二）、到期有 job 没有启动（`skipped`，决策二第 3 条）、启动失败（`error`，决策二后台推进条「时刻」）、终态之后到达的结果（不采用，0031 决定一·补）。run 的状态都按 0031 决定三取；前台才有的几样见 0016 决策 A。

run 到终态之后各组合下还会发生什么，逐格列出，不作统一的概括：

| | 本机前台 | 本机后台 | 云端后台 |
|---|---|---|---|
| run 的终态被改 | 不会 | 不会 | 不会 |
| 认领并启动新的 job | 不会：认领与重试前的检查被拦 | 不会：认领被拦 | 不会：认领被拦 |
| 检查已通过、启动还没有完成的 job（调用未发出、调用中、句柄未返回；首次启动与重试都算） | 会启动；推进器下一次写运行态时发现 run 已结束，对它发停止 | 会启动；推进进程发现 run 已结束之后退出，worker 见下 | 会启动（task 的启动不随记录分出先后，0034 机制三「run 级状态只进不退」条①）；它发出的事件、或在它可见之后才到达的定时触发调用带到这个 run 时，由那次调用清扫（决策九第 2 条）；此后没有任何调用带到这个 run 时没有人停 |
| 已经在执行的 job | 推进器还在时由它停止；它被暂停或卡死时要等它恢复；它已不在时 worker 见下 | 推进进程还在时发现 run 已结束之后退出；worker 见下 | run 结束之后交给后端的清扫（决策九第 2 条）；期限那一次定时触发对它做什么、成立的前提，见决策九第 1 条；之后才出现的 task 同上一格 |

推进器已不在、又没有别的组件去停时，留下的执行不受期限约束：

- 本机 worker 在推进器退出之后靠核验所属进程是否还在来自行退出（0024）。这个核验有已知的失效情形：worker 核验的是传给它的所属进程 pid，所属进程成了未被回收的僵尸时这个 pid 仍然查得到；worker 经包装进程启动、或所属进程在核验启用之前已经退出时，没有「直接父进程变了」这条辅助线索可用，核验可能一直不触发。所属进程的 pid 在被发现消失之前被复用时，它也被误认为还在。生命期锁不受这两种情形影响（已退出未回收的进程已释放锁，决策三），worker 的核验受影响，所以会出现 run 已被结束、本机 worker 仍在执行的情形。
- 本机推进器被暂停期间，它启动的 worker 照常执行、没有人按截止时刻停它们。
- 云端 task 自己不会因为 run 结束而停：worker 不按预算计时自停（0034「job timeout」节）；浏览器会话与设备会话各有存活上限，但会话到期不保证 task 退出，确定性 step 可以一直等下去。所以由后端来停（决策九）。推进停住时，已经启动的 task 各自把手上的 job 执行完就退出；留下来的只有自己不结束的 task（卡住的 step、一直等待的确定性 step），对它们的出口是 job 到点停止（决策二第 2 条）与后端到期结束（决策九第 1 条，含前提）。后端停不到的有两种：清扫时没有被列到、之后又没有任何触发的 task；流与定时触发整条链都失效的时候。前一种包括：启动调用在清扫时还没完成的；已经启动、ECS 的列举因最终一致性暂时看不到的；以及它自己的超时触发在它可见之前已经执行并删除的。这样的 task 只要此后发出任何事件就会带来一次清扫，一直不出事件的留下。

处置只改记录（决策七），自己不停任何执行；表里的停止，本机后端是执行方与 worker 自己做的，云端后端另有后端在 run 结束之后的清扫（决策九第 2 条）。

其它局限：

- 有人改动、删除 run 目录里的文件，以及掉电与内核崩溃（原子写不做 fsync，0030 决定三），不在防护之内。
- 运行态本身读不出的 run 怎样处理，见决策六最后一条与决策八。
- 云端多次调用重叠推进时，各记录靠什么分出先后见 0034 机制三的开头。
- 云端建 run 的先读与两次条件写（0030 决定六）之间，另一方若建了同一个 run_id，META 与 STATE 条目仍只有一方写成，另一方失败；但它已卸载到 S3 的 step 参数正文可能已重写对方的同名对象。run_id 由建 run 的一方新生成、带随机尾，这个窗口不另设机制防护。

## 被拒方案

- **期限只当推定阈值、执行方不遵守**：见决策二的理由。由此还要引出两条补丁式的规则（推进器还在时不处置；真实结果覆盖处置写下的终态），都随它一起不取。
- **真实结果覆盖处置写下的终态**：终态之后再变对上层是错的行为，见决策五。
- **靠期限加余量证明执行已停**：尾段与余量都是预算，时钟也可能有偏差，证明不了。期限之后结束一个 run 的安全由「终态不可变、认领以未结束为条件」承担（决策五）。
- **到期时把执行中的 job 一律改判**（不看内容是否已完整）：违背 0034 机制二「内容完整后不再仲裁」，同一个 job 还会因为停止请求到得早晚在三种组合下得到不同结论。
- **期限放运行态记录的顶层**：期限是 run 的规则，放在只由 adapter 读写的附加属性里，core 的调度与推进就得绕开模型去拿它。
- **期限不存、读时现算**：停止宽限不在任何记录里；算式随 CLI 版本变化时，同一个 run 在不同版本下会算出不同的期限，而它必须是各执行方与所有读者共同认的那一个时刻。
- **使用者单独配置 run 级期限**（0034 预留的 `--default-run-timeout`）：期限要保证不早于各 job 预算能合法用到的时刻，单独配置就得再定义它与 job 预算冲突时谁让谁；现在只由 job 预算推出。
- **让使用者替某个 run 下一个判定**（如把它记成 `passed`）：判定不靠使用者担保，结果只来自执行与记录。以后的取消命令结束一个 run 时走结束写（决策八），不替任何 job 下结论。
- **心跳或租约**：续写本身也会被暂停与时钟偏差打断，判「过期」仍要一段时长。见「重议闸门」。
- **读对方进程的信息**（pid 空间标识、进程启动时刻、进程状态）：只看 pid 是否存在（`os.kill(pid, 0)` 与 `os.killpg(pgid, 0)`）在 pid 被复用或进程是僵尸时都判为存活（实测 macOS 与 Linux 上 `os.kill(pid, 0)` 对已退出、未被回收的进程仍然成功）；加上 pid 空间标识与启动时刻之后，Linux 上连续五轮复核每轮都出现新的反例（pid 命名空间、同一滴答里启动的两个进程、时间命名空间的偏移、`/proc` 被换掉或预先绑定挂载），macOS 与 Linux 各要一套取法（macOS 的 `ps -p <pid> -o lstart=` 输出随本机时区变，必须固定 `TZ=UTC` 与 `LC_ALL=C`；Linux 读 `/proc/<pid>/stat`，同一台宿主上容器里读到的 `boot_id` 与宿主相同、pid 命名空间不同）。引入 psutil 也不解决：它在 Linux 上给出的启动时刻是由开机时刻换算的墙钟浮点数，系统时钟被校正后同一进程前后读到的值可能不等，按「不等即被复用」处理会把活着的进程判成已不在。锁把同一个问题交给内核回答。
- **机器标识**（含主机名）：主机名会重名（克隆的镜像、容器、不同网络下的同名机器）；跨重启稳定的机器标识会随镜像克隆被复制，认错的方向是把仍在执行的 run 结束。锁只在同一个内核里有意义，不需要它。
- **在 run 目录之外另放锁文件**：锁与 run 目录分处两地，run 目录被移动、复制或换报告目录时两者对不上，还要另定命名与清理。
- **改用 run 目录里的锁文件**（写方式打开）：为网络盘换它也不干净。Linux 的 NFS（同机回环挂载）上没有写委托时四个挂载两两互斥，持锁方有写委托时 v4.2 不共用超级块的挂载之间不互斥，服务端本地路径与各挂载之间两种情形下都不互斥；文件锁的非阻塞试拿有的 10 到 87 秒才返回（服务端刚启动、另一版本的挂载持锁时），有的到 30 秒上限、一次到 6 分钟以上仍未返回（进程被杀为止）。APFS 与 Linux 的 ext4、tmpfs、overlay、绑定挂载上两者各项行为相同（锁文件没有测 `multiprocessing`），目录锁少一个文件，也没有锁文件删掉重建、新旧两份各被一方持有的问题。
- **启动时自检**（拿到锁的一方再开一次 run 目录试取），以及凡取锁之后读回的做法：Linux 的 NFS（v4.2、v3，同机回环挂载）上对只读打开的目录取排他 `flock` 不报错、同一进程再开一次也被挡，锁却只在共用超级块的挂载之间互斥（nosharecache 挂载、另一版本的挂载、服务端本地路径都拿得到）；它只查得出同一进程两次打开是否互斥。
- **macOS 只看本机标志**（`fstatfs` 的 `MNT_LOCAL`）：带这个标志的都放行，含没有照决策三理由实测过的类型（实测 HFS+ 与 FSKit 挂载的 FAT 都带）；两个平台用同一条规则，只放行实测过的类型。
- **由后台推进进程自己建 run 并拿锁，提交进程等它回报**：要另建一条回报通道，提交侧的报错要经它转述；交接用同一把锁覆盖了全程。
- **没有交来锁的后台推进进程自己试拿、拿到即接着推进**：那就是续一个管它的进程已不在的 run（决策六）。
- **为停 task 新设一个 Lambda**：要用的触发（runs 表的流、定时触发）、权限（列 task、停 task）都在两个推进 Lambda 上，另设一个只是把同一套装配再复制一份。
- **由 `settle-runs` 自己停 task**：它就得带上操作 ECS 的权限，没有这项权限的机器用不了；没有人执行它的时候 task 照样没人停。停掉已结束的 run 的 task 是后端自己的职责（决策九），不依赖有人执行命令。
- **给 0 时取引擎的上限**（桌面约 8 小时、设备 8880 秒）：`submit --backend cloud` 时 CLI 在计划阶段不查询引擎的能力自述，拿不到设备的数；在 core 里抄一份则是同一个事实写两处，引擎改了而这一份没人记得改。桌面那个数同样是从平台的会话上限推出来的引擎事实。
- **给 0 表示不超时**：每个 run 都要有期限，处置的期限一条与云端的后端到期结束都依赖它（决策六与决策九第 1 条）；不超时实际也只撑到浏览器会话的一小时（决策十的理由）。
- **给 0 时设备 scope 取设备缺省**：同一个写法对桌面是「尽可能长」、对设备是「等于没写」，一个参数两种含义。
- **按目标各定一个产品上限**（桌面取平台允许的最长、设备另取一个数）：桌面那个数仍是把引擎与平台的事实搬进 core；一个产品设定用一个数，引擎的限制留在引擎。

## 实测项（实装时逐项核，结果内联回这里）

期限：

1. 前台到期：把期限设到执行中途，执行方不启动新的 job、执行中的 worker 被期限截断记 `aborted` 加期限的说明、执行中的 job 都结束之后结束写把未启动的 job 记 `skipped`、run 状态按 0031 决定三取、已结束的 job 的判定明细齐全、报告与 `status --json` 一致。
2. 本机后台 run 到期：推进进程还在时，到期后执行中的 job 被期限截断记 `aborted`、未启动的 job 由结束写记 `skipped`、run 状态按 0031 决定三取、报告生成。
3. 云端后台 run 到期：部署后提交一个期限落在执行中途的 run，没有任何人查看，过了期限之后执行中的 task 被停止、未启动的 job 不启动、run 按 0031 决定三结束；核对期限那一次定时触发确实发出、Lambda 日志里没有异常。
4. 三种组合一致：三种组合各一个期限落在执行中途的 run，`status --json` 与 `explain` 一致且符合决策二第 2 条、0031 决定一与 0031 决定三「结束写」小节的说明表（内容完整的保留判定）；启动失败的 job 包括在内。
5. 内容完整的不改判：让一个 job 在期限之前给出完整内容、结束越过期限，它在三种组合下都保留原判定；这个 run 没有未启动的 job 时，run 按 0031 决定三得到真实结果、没有到期的说明。
6. 前台重试：job 因网络故障重试时照常重新启动、不被自己的认领拦住；退避期间 run 被别处记为已结束时不重新启动、不写终态；经过开始执行与结束两次状态写之后，认领时刻仍在运行态里。产品的 `run` 不开 job 级重试（0028），重试的两条在调度层用注入的重试次数核，认领时刻的保留在真实的 run 上核。
7. 到期结束写与认领并发（云端）：一个推进器读到「没有执行中的、仍有未启动的」之后，另一方的认领落下，前者的结束写被写入序号的条件挡下、重读之后不满足第 3 条、run 没有结束，新认领的 job 过了期限之后被 job 到点停止截断。
8. 云端期限触发承担 job 到点停止：让一个 job 自己的超时触发缺失、worker 不出事件，task 被停掉、run 结束；期限那一次到达时 run 仍未结束的，由它的 job 到点停止停掉 task。记下两次触发的到达时刻、停掉 task 的是期限那一次还是清扫（决策九第 2 条）、结束 run 的那次写出自哪一方。
9. 预算上限：`--default-job-timeout 0` 的桌面 scope 与设备 scope 在运行定义里都得到 7200 秒的预算；桌面 job 的浏览器会话存活时间设为 7320 秒（两个引擎各核一次，从 worker 发出的建会话请求里读）；有效预算 7201 秒在计划阶段被拒、7200 秒通过，两种目标各核一次；标了 `@timeout:1500` 的 scope 在 `--default-job-timeout` 给出超过上限的值时照常通过（没有生效的缺省值不检查）；产品上限不大于每个引擎对每种目标能支持的最长预算的那条测试，在把引擎一侧的数改小时失败。
10. 退出时刻的两种取法一致（云端）：同一个已停止的 task，从它的停止事件取到的执行停止时刻与主动查询 task 取到的，写成退出记录之后相同；两处先后写同一条退出记录时内容不变。
11. 截止时刻之后自行退出的归因：worker 在截止时刻之后、停止请求发出之前以非零的退出码退出时，本机后台与云端后台都按到点处理（预算截断记 `error` 加超时，期限截断记 `aborted`），状态与说明和前台相同；在截止时刻之前这样退出时按退出码归因；内容完整的 job 不因退出时刻晚于截止时刻而改判。本机一侧用真实进程核，云端一侧在部署之后用真实的 task 核。
12. 补写不覆盖（云端）：job 到点停止找不到 task 时补写的未知退出只在没有退出记录时写入，观察者的真实退出记录落在「查有没有退出记录」与补写之间时，留下的是真实的那一条。

锁与边界：

13. macOS 上目录的 `flock` 与目录里文件的 POSIX 记录锁（事件库）互不阻挡（Linux 清单的类型上已核）；`btrfs` 其他子卷与快照里照做决策三理由的各项。
14. 边界检查：Linux 的 NFS 与 FUSE 挂载、macOS 的 SMB、NFS 挂载与 HFS+ 磁盘映像、Docker Desktop 容器里的绑定挂载上，四个命令按决策四处理、`doctor` 那一项不过，报告目录不过时没有留下目录；已有的 run 目录本身是挂载点或符号链接、落在这类文件系统上时不取锁、不写记录。
15. 交接：经 CLI 重做决策三理由里交接的各项（锁这一层已核）；交来的描述符不是这个 run 目录时不推进。

处置：

16. 推进器不在：本机两种推进器各被 SIGKILL 一次（后台的在提交进程退出之后），`status --wait` 下一次轮询即按 0031 决定三「结束写」小节说明表的「锁拿到了」一行处置、有报告、退出码 1，孤儿 worker 释放会话后退出；SIGSTOP 时过了期限加 300 秒之后才处置，SIGCONT 之后推进器的写被拒、停手、不再存明细。
17. 暂停后恢复（前台）：执行 `run` 的进程被 SIGSTOP 到期限加 300 秒之后，别处先处置；SIGCONT 之后它不启动新的 job（它的时钟已过停止启动的时刻，时间检查先拦下；时钟落后于处置方时改由认领被拒拦下，这一支用注入的时钟核）、执行中的 worker 被停止，不覆盖已有的终态，终端有说明、退出码非零。
18. 终态不可变：处置与推进器的写（前台的 job 状态写，本机后台与云端的认领与终态写）交错进行，run 不出现从终态回到 `running`，终态之后的 job 写都写不成；对已有的 run 再次建 run 失败且不改任何东西（云端包括不重写已卸载到 S3 的内容），两个后端各核一次。
19. 两个 `settle-runs` 同时处置同一个 run，只有一个写成。
20. `settle-runs` 的结果：本机推进器不在、仍在、另一处置方持锁、被暂停过了期限加 300 秒，run 目录在清单之外、运行态损坏、已结束，云端期限加 300 秒前后，`settle-runs` 的结果与 `list-runs`、`status` 的提示都相符，`--dry-run` 之后锁拿得到。

云端：

21. 云端到期与清扫：停掉 events 表流的事件源映射、不执行处置命令，过了期限之后 task 被停，过了期限加 300 秒之后 run 由后端结束，记下两次触发的到达时刻；流上只有 STATE 的新建与使 run 成为终态的写触发 `kicker`；`settle-runs` 结束的 run、结束之后才启动的 task 都被清扫。
22. 清扫不误伤：正常进行中的 run 在同一后端里另一个 run 结束时不受影响；正常结束的 run 触发的清扫没有要停的 task（列举可能仍返回刚停止的 task），没有打断任何 task 的最后上传。

对照：

23. 运行定义不可用：云端与本机后台都得到未结束的 job `error`、run `error` 与同一句说明。

## 重议闸门

- **跨机器早于期限判死活**，或**本机后端的报告目录放到网络文件系统上、跨内核共用**成为使用需要时：再议心跳、租约或跨内核的死活判断。云端与跨机器的处置只有期限一条条件（决策六），宽松的期限可以是实际时长的数倍。
- **使用者可调的 run 级期限**：由 job 预算推出的期限对某类 run 明显过宽、影响到 CI 排期或费用时，再议单独的配置项。
