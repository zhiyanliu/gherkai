# 0054. 运行期限、生命期锁与 run 处置：每个 run 遵守由 job 预算推出的期限；本机 run 由持有生命期锁的进程推进，死活由锁回答；run 结束之后记录不变、不再接受新的认领；管它的进程不在了、或已过期限加 300 秒的 run 可由处置方结束

> **Status:** Accepted —— 这一篇描述的设计有一部分尚未实装，code 跟上之前，实际行为以 code 为准。

## 背景与问题

管一个 run 的进程可能不写终态就消失。本机后端是执行 `run` 的进程或 `submit` 启动的后台推进进程，它们会被 SIGKILL、随宿主失联、收到没有处理器的 SIGHUP、或因未捕获的异常退出；云端后端的 run 由后端推进，触发链断开（一次调用最终失败、触发丢失）时同样停住。这样的 run 停在 `pending` 或 `running`，没有出口，后果有三处：

- `status --wait` 一直等下去。
- `list-runs` 的未结束部分不截断（[0041](./0041-agent-facing-cli-affordances.md) 决策七），这类 run 只增不减。只增不减、没有出口是设计上的缺口，不等它在清单里成为常态再处理。
- 云端的清理协议把 `live` 分组里的 run 当作它所引用的 worker 任务定义修订的占用者（[0038](./0038-worker-image-delivery.md) 残余风险④），这些修订一直回收不了。

要给这类 run 出口，先要回答两个问题。

一是这个 run 允许运行到什么时候：要有一个所有执行方都认、别的机器也能拿来比较的时刻。各 job 的墙钟预算只在执行它的进程里起作用，给不出这个时刻：按单调时钟计时，系统休眠时单调时钟不走，各 job 的截止时刻顺延休眠的时长；进程被暂停时它不检查截止时刻；落库或云端调用卡住时也没有上界。所以从外面看，一个 run 可以在任意晚的墙钟时刻仍在执行。

二是管它的进程还在不在。从外面推断不可靠：凭时钟加一段固定时长判断对方是否已经收尾完，三种取法都失守，后两种由真实进程复现（[0034](./0034-detached-batch-reconciler.md) 被拒方案「本机接力，及其改法」）；凭进程标识核对，每一种取法都有新的反例（「被拒方案」里「读对方进程的信息」一条）。

## 决策

### 一、定位与范围

- 本篇管一个 run 的生命期：每个 run 允许运行到什么时候（运行期限，决策二），以及让每个 run 都有期限的前提，即每个 job 的墙钟预算有产品上限（决策十）；本机 run 由持有生命期锁的进程推进，锁回答它在不在（决策三），锁只在本机文件系统上的报告目录里有效（决策四）；run 到终态之后记录不变、执行方服从记录，所以期限之后结束一个可能还在执行的 run 也安全（决策五）；何时可以处置（决策六）、处置做什么（决策七）、谁来做、从哪个入口做（决策八）；云端没有本机进程，到期结束 run 与清扫 task 放在后端（决策九，到期结束的前提见其第 1 条）。
- 执行方式与执行后端有三种组合，云端后端只有后台（[0016](./0016-execution-architecture-core-lib-run-model.md) 决策 A）：本机前台（`run`）、本机后台（`submit --backend local`）、云端后台（`submit --backend cloud`），下文称三种组合。处置对两个后端、前台与后台的 run 都适用。
- 处置不是「使用者放弃一个 run」：判定只靠记录与生命期锁，不靠使用者事后担保，拿不准就不动。取消一个 run 的命令不在本篇，它以后是处置方之一（决策八）。
- `run --no-report` 不建记录、不拿锁，不在范围内。
- 本篇依赖、写全在别处的：本机的 run 任何时刻至多一个推进器、云端多次调用可以重叠推进，在 [0034](./0034-detached-batch-reconciler.md)「推进器与触发源」；各命令写什么在 0034「命令形态」；run 与 job 的状态怎样取、结束写给未结束的 job 记什么，在 [0031](./0031-job-lifecycle-states-and-severity.md) 决定三与其中的「结束写」小节；`list-runs` 的列与提示在 [0041](./0041-agent-facing-cli-affordances.md) 决策七。

### 二、运行期限：进运行定义，所有执行方都遵守

每个 run 在建立时得到一个运行期限 `deadline_at`（UTC 的 ISO 时刻），它是这个 run 的一条规则：

`deadline_at = created_at + 900 秒 + Σ（各 job 的墙钟预算 + 每 job 尾段）`

- 每 job 尾段：本机后端取 `2 × G + 10` 秒，云端后端取 210 秒（两者的组成见下「尾段与余量是预算的取值」一段）。G 是停止宽限：前台 `run` 取这次调用解析出的值（`--grace`、配置文件或各引擎自报值）；本机 `submit` 没有 run 级的宽限，取这个 run 用到的各引擎自报宽限里最大的一个。
- 900 秒是一次性余量，留给取创建时刻到起第一个 job 之间的各步：给了 `--expose-local` 时的起隧道、生成运行定义与建 run、装配与各次落库、云端调用；云端建 run 只写 runs 表，之后还要经流投递、`kicker` 冷启动才轮到首次认领。这部分每个 run 只发生一次、与 job 数无关。创建时刻何时取见下「落点是运行定义」一段。
- 每个 job 的墙钟预算都是有限的（决策十），所以每个 run 都有期限。
- 求和而不按并发折算：并发大于 1 时真实墙钟小于各预算之和，串行总和对任何并发取值都偏宽。健康的 run 通常远在期限之前结束。

尾段与余量是预算的取值，不是「执行一定已停」的上界：停止等待预算是执行方愿意等的时长，停止调用本身、起 worker 的调用、落库调用都可能阻塞得更久（0034 已区分等待预算与平台保证）。它们只决定期限定得多宽；期限之后结束一个 run 的安全不靠它们，靠决策五。认领之后的启动调用、拉取镜像与挂接网络接口已计入 job 的预算（0034「job timeout」节），尾段与余量记的是预算之外的耗时。取值的来历：

- 本机：前台 run 的 job 从线程池取到它时起算预算（认领时刻就在这时取，见第 2 条），到点后本机一次停止等 G 加约 3 秒、排空等到停止请求之后 G 加 5 秒、仍未结束会再发一次停止，合计约预算加 `2G + 9` 秒，取 `2G + 10` 秒。
- 云端：job 用尽预算后被停止时，预算点之后有三段耗时，并发为 1 时逐个 job 串行累加，与 job 数成正比，三段之和 210 秒。①超时触发的调度精度，60 秒：job 到点停止由 EventBridge Scheduler 的一次性 schedule 在 job 的截止时刻触发（0034「job timeout」节），Scheduler 文档写明所有 schedule 类型的触发精度都是 60 秒，关闭 flexible time window 也只保证在指定时刻所在的那一分钟内触发，停止请求因此最多晚约一分钟发出；Scheduler 异步调用 Lambda 的排队与 job 到点停止本身的调用另有秒级的常态耗时，没有文档上界。②停止宽限，120 秒：停止请求之后 worker 在 container `stopTimeout` 的宽限内收尾，到点才被强制结束；Fargate 上 `stopTimeout` 的平台上限是 120 秒，按上限取对任何 variant 都成立（部署侧的取值见 [0032](./0032-fargate-execution-environment.md) 结论 3）。③事件链尾延迟，约 30 秒：ECS 记下 task 停止（`executionStoppedAt`）到退出可被归约、下一个 job 被认领之间的固有延迟，0034 实测每步约 20 到 30 秒，瓶颈在 ECS 平台的清理开销。在预算内结束的 job 只有第③段，按 210 秒取是高估，与求和而不按并发折算同一取向。
- 云端的 210 秒是按已知组成的估算，不是无条件的上界：60 秒与 120 秒分别来自 Scheduler 文档写明的触发精度与 Fargate 的平台上限；30 秒是实测的经验值，服务方没有为它给出上界，平台降级、Lambda 限流或极大批量时实际尾延迟可能超出。另有一段已知滞后没有单列：ECS 记下 `executionStoppedAt` 比容器实际退出晚约 11 秒（0032 结论 2），被强制结束的 job 三段都取到最大时尾部约 220 秒，比 210 秒多约 10 秒；只有大批 job 同时取到三段最大值时这一差额才累计成缺口，而在预算内结束的 job 实际尾部约 40 秒、每个留出约 170 秒，所以不另加项。估算偏短时，靠后的 job 可能来不及启动，或在用完自己的预算之前被期限截断（第 1、2 条）。
- 不取「余量取一个不随 job 数变化的常数」：每 job 部分随 job 数线性增长，常数覆盖不了；并发为 1 时按每个最多 210 秒计，5 个用尽预算后被停止的 job 的尾部耗时（1050 秒）就已超过 900 秒。不取「每 job 部分按这个 run 所用 variant 的 task 定义里实际的 `stopTimeout` 取值」（部署方可以把它设在 120 秒以下）：更精确，但期限的计算要依赖 variant 的解析结果，多一层耦合；120 秒已是 Fargate 的平台上限，按上限取只会偏宽，偏在安全的一侧。

job 级重试共享同一个截止时刻，不另外延长。

**落点是运行定义**（`RunMeta`，用户文档里的「提交记录」）。期限由 job 的墙钟预算与停止宽限推出、建 run 时确定、之后不变，执行方要遵守、所有读者都要看，它与 job 的墙钟预算、并发上限是同一类东西，后两者已在运行定义里。创建时刻 `created_at` 在起隧道之前取一次，给不给 `--expose-local` 都在同一位置取（三种组合各由哪个进程在哪一步取，见 [0035](./0035-local-app-testing-via-tunnel.md) 决策 3「三种组合的宿主与次序」）；期限与隧道边缘规则里的到点时刻（0035 决策 3「边缘到点拒绝」）都由这一次读数算出，生成运行定义时用同一个值。期限要的各 job 预算与停止宽限在起隧道之前都已取得，起隧道的耗时由此计入 900 秒的一次性余量。`deadline_at` 是运行定义的必有键（哪些键必有、怎样新增，按 [0037](./0037-distribution-and-packaging.md) 决策 7 的基线与登记）。云端把它摊成提交记录的头（runs 表里的 META 条目）的顶层属性，同 run 记录格式版本与写出版本的做法；列举时只读头、不取 jobs 对象（头与 jobs 对象的形态见 [0030](./0030-realtime-persistence-seam.md) 决定六，读量见决策八「处置的次序」一条里的「读量」）。读端把缺失、为空或不是带时区的合法时刻的 `deadline_at` 当作定义违约拒绝，与空预算同一处理：每个 run 都有期限，各执行方与判定拿到的必须是同一个可比较的时刻。

**所有执行方都遵守期限，三种组合是同一种表现。** 规则只看当前时刻与各 job 的状态，任何一次推进都能独立算出同一个结论，不需要记住期限那一刻发生过什么：

1. 当前时刻已过 `deadline_at` 减 60 秒（停止认领的时刻），不再认领新的 job，也不再重试同一个 job。提前 60 秒是启动余量：从认领到 job 真正开始执行需要时间，卡着期限认领的 job 来不及被正常停止。这一条管的是认领，不是启动请求发出的时刻，按认领方自己的墙钟读数判断：认领之前读一次墙钟（下「后台推进」条「时刻」一项），读数已过即不认领。认领的条件写在读数之后才写成，库里认领生效的时刻可能晚于停止认领的时刻；推进器的墙钟回拨或落后时，它也可能在这个时刻之后再认领（同条里不记已过停止认领的那一项）。所以这一条承诺的是推进器按自己的墙钟读数不再认领，不是库里不出现晚于这个时刻的认领。前台的认领紧贴起 worker，云端认领之后还要建这个 job 的定时触发、上传 job 输入，才发出启动 task 的请求，所以停止认领的时刻之前一刻认领的 job，启动请求可能晚于期限发出。这样的 job 按到点时还在执行处理，由 job 到点停止去停（决策九第 1 条、0034「job timeout」节）；那时它的 task 还列不出来的，交给之后的清扫（决策九第 2 条开头：哪一次停得到、都没有停到时怎样、多出的执行时间有什么后果）。发出启动请求之前不另查一次时钟（被拒方案「发出启动请求之前再查一次停止认领的时刻」）。
2. 执行中的 job 的截止时刻以 `deadline_at` 封顶：取「认领时刻加它的墙钟预算」与 `deadline_at` 中较早的一个（`run_deadline.job_cutoff`），两者同按墙钟比较，相等时算 job 自己的预算到点。到点的处理与 job 自己的预算到点相同，都是 job 到点停止（0034「job timeout」节）；内容已经完整、随后正常退出的 job 保留它的判定（0034 机制二）。被期限截断与用完自己预算的 job 各记什么见 [0031](./0031-job-lifecycle-states-and-severity.md) 决定一。起作用的是哪一个截止时刻，由记录里的认领时刻、job 的预算与 run 的期限算出，不看说明，也不另记：前台与后台按同一个算法得到同一个结论。它是前台与后台共用的终结函数的一项输入，决定走真值表里预算那一行还是期限那一行（0034 机制二「终结函数与真值表」）。预算从认领时刻起算，三种组合相同（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 2 与 0034 已定后台自认领起算）：认领时刻是认领方在发出认领的那次写之前取的墙钟，随认领写进运行态；前台在线程池取到 job、通过起 worker 之前的检查之后取它，没有记录的 `run --no-report` 在同一位置取、不写。job 的截止时刻按墙钟计、从认领时刻起算（理由见下「检查用墙钟」一段）；停止等待、排空这些时长按单调时钟计，它们不进记录。
3. 已过第 1 条的时刻、没有执行中的 job、仍有未启动的 job：执行方做结束写（0031 决定三「结束写」小节），未启动的 job 记 `skipped` 并带到期的说明，run 随之成为终态。
4. 没有执行中、也没有未启动的 job：run 在最后一个 job 的终态写里随之成为终态（0031 决定三），不论当前时刻是否已过期限；全部 job 都给出了完整内容的 run 得到它们的真实结果。

四条里的「已过」「到了」一律指当前时刻严格晚于那个时刻：停止认领的时刻、期限与 job 的截止时刻三处取法相同，与前台的预算到点判断一致；job 的截止时刻恰等于期限时，两处判断在同一时刻得出同一结论。

一次前台执行可能因三种原因停下：到期（第 1、2 条）、因 fail-fast 或使用方中断而中止、发现 run 已被别处记为已结束（决策五）。它们同时或先后成立时，各 job 的结果这样定：

- 排队中、从未启动的 job，起 worker 之前依次检查：已过停止认领的时刻（第 1 条）；已发现 run 被别处记为已结束；run 已因 fail-fast 或使用方中断而中止。任一条成立即不启动，都不成立才认领并启动。不启动的 job 由谁记下：已过停止认领的时刻、或 run 因 fail-fast 或使用方中断而中止的，留在 `pending`，执行中的 job 都结束之后由执行方的结束写记为 `skipped`（第 3 条；fail-fast 与中断的来路、几条来路先后成立时取哪一条，见 0031 决定三「结束写」小节）；已发现 run 被别处结束的，记录已是终态，执行方不写。
- 执行中的 job，停止原因按 0034 机制二的首次仲裁落定一次、之后不改：做出停止决定的那一刻它的截止时刻已过即为到点（记什么按第 2 条看起作用的是哪一个截止时刻），否则为中止，中止的说明取最先成立的那个来源。「最先成立」指最先登记：三种来源都登记在 run 的中止标志上、只记下第一次，fail-fast 在判定得出时登记，发现 run 被别处结束在发现时登记（写 job 状态时的发现，在那次落库回调返回之后当场登记），使用方中断在调度循环轮询到它时登记（两次轮询之间到达的以轮询时刻为准，同一次轮询里先读停手信号、再处理中断）。发现 run 已被别处结束是 fail-fast、使用方中断之外的第三种中止来源（说明是「这个 run 已被记为已结束，job 被中止」），走同一个仲裁、不另立规则；内容已经完整的 job 保留判定。run 已被别处结束时这个 job 的终态写写不成，执行方也不存它的明细（决策五）。
- 上一次尝试已经结束、正在等待重试的 job：三种原因下都不再重试。已过停止认领的时刻、或已因 fail-fast 或使用方中断而中止时，把上一次的结果作为终态写下，并注明没有再重试及原因；已发现 run 被别处记为已结束时不写（决策五）。重新启动之前的检查与排队中的 job 是同一次序，只是最后一步的认领换成读一次 run 的状态（决策五）：已过停止认领的时刻；已发现 run 被别处记为已结束；已因 fail-fast 或使用方中断而中止；这时读到 run 已是终态。注明的原因取最先命中的一条。

run 级说明只由结束写写下（0031 决定三「结束写」小节）；`run --json` 的 `jobs[]` 怎样列出没有启动的 job 见 0041 决策三。设备计量两项合计是否出现按运行定义里有没有设备目标判断、不按有明细的 job（0051 决策 7 的出现条件）：设备 job 全部没有启动时两项都是 0，不省键。

各执行方的落实：

- 前台执行（`run`）：调度循环按墙钟检查，过了第 1 条的时刻不从队列里认领 job、也不重试；到了 `deadline_at` 把执行中的各 worker 的截止时刻视为已到并发停止请求，等它们结束后按第 3、4 条。停止认领一经成立不撤销：任何一次检查观察到已过第 1 条的时刻就记下，此后起 worker 之前与重试之前的检查都按已过处理，判断第 3 条也用这个记下的事实、不重读时钟，系统时钟回拨不会抹掉已经发生的停止认领。job 的截止时刻同样一经观察到已过就不撤销：触发停止决定的那次检查看到已过，首次仲裁即按到点落定，不因随后读到回拨的时钟落成中止。规则本身不变（真实的时刻只会越来越晚），记下它们只是不让回拨的时钟撤回已经得出的结论。未启动的 job 不存明细，由第 3 条的结束写记为 `skipped`。墙钟由组合根注入调度循环（[0026](./0026-schedule-module.md)），缺省取系统时钟，调度循环自己不另取；组合根注入的是它写时间戳的同一个读取点，记录里的时刻只有一种写法。认领时刻由调度循环从注入的墙钟取一次、交给认领写，写进记录的值与算截止时刻的值是同一个。core 里的墙钟时刻是带时区的时刻值，ISO 串只是记录里的写法，解析与写出各只有一处；不带时区的值一参与比较即报错，误注入的时钟不会悄悄得出结论。`deadline_at` 减 60 秒这个提前量、run 级说明的文字与「是否已过」的判断放在 core，前台与后台共用一份。`run --no-report` 没有记录，照样遵守第 1、2 条，第 3、4 条的结果按同一套规则在内存里给出。
- 后台推进（本机的后台推进进程、云端的 Lambda，都经 core 的同一个推进步骤）：过了第 1 条的时刻，推进步骤不认领；认领 job 时算出的截止时刻以 `deadline_at` 封顶，本机的检查、云端的一次性定时触发与防御性超时扫描都按封顶后的时刻；满足第 3 条时做到期的结束写。细节如下。
  - 时刻：推进步骤自己不取时钟，经宿主注入的时钟取时刻（与前台同一个读取点）。每次读取运行态之前取一次，用于随后的推进决策与结束时刻（同一轮里重新读取时重新取；各次取的都是墙钟，回拨时结束时刻可以早于这一轮里的认领时刻，记录不保证两者的先后）；每次认领之前再取一次，作这个 job 的认领时刻，并重做一次停止认领的检查（已过即不认领）。一轮里靠后的认领因此不沿用轮首的时刻：前面的读取与启动调用有耗时，沿用会让靠后的 job 少拿到预算。这一轮里有认领因为已过停止认领的时刻而没有做时，推进步骤在同一轮里重新读取运行态与事件、按已过停止认领再决策一次（这一轮里先前认领成功的 job 计入其中），不拿轮首的快照做结束写，也不就此返回：云端此后可能没有别的东西触发下一轮，满足到期结束写的 run 会停住，只剩处置这一个出口（谁能处置见决策八，条件见决策六）。重新决策只做一次，直接按已过停止认领处理、不再拿重新取的时刻判断，系统时钟在这之间回拨也不会让这一次又提议认领。启动调用失败时也再取一次时刻，记为这条退出记录的退出时刻：它晚于这个 job 的截止时刻时投影按到点处理（第 2 条），与前台起 worker 失败的分支得到同一个判定；不晚于就是启动失败。后台的启动失败补偿交给终结函数的输入与前台相同（退出码未知，带启动失败的原因），不用平台失败的哨兵退出码：哨兵退出码会让两条路径对同一个启动异常给出两句不同的说明。实测项 4（三种组合一致）包括这类 job。
  - 决策：是否已过停止认领的时刻是推进决策（`plan_next`）的一项输入，决策是一处纯函数。已过时不提议新的认领；没有执行中的 job 而仍有未启动的 job 时提议到期的结束写；其余照常推进。这里的「未启动」按运行态判断：job 在这一轮读到的运行态里是 `pending`，不读事件（结束写只看运行态，0031 决定三「结束写」小节）。推进决策用的运行态是这一轮读到的那一份，加上这一轮自己记下的终态（终态写的作用，0031 决定三）；「没有执行中的 job」与「未启动」都按它判断，不看事件推出的投影。同一轮的重做重新读取，先前记下的终态已在其中。推进步骤先写终态、后决策的次序与理由见 0034 机制三「收尾各步的先后与之后会不会变」的步骤。推进决策给出的结束动作只有到期的结束写（云端推进器遇到别的格式写出的 run、或读不到可用的运行定义时的 error 变体不经推进决策，见 0031 决定三「结束写」小节与决策九「落实时」一段）；第 4 条不是一个单独的动作，run 在最后一个 job 的终态写里随之成为终态。
  - 快照：推进步骤先读运行态、后读事件，手里的运行态可能比事件旧。为一个有事件记录的 job 存明细、写终态之前，要求它在这一轮读到的运行态里带认领时刻（读不出或不带时区的同样算不带，后台各处的时刻都经 core 的同一处严格解析读回）；不带说明它是在这一轮读运行态之后才被认领的，这一轮不为它存明细、不写终态，下一轮读到新的运行态再做。不用「取不到认领时刻就按预算说明」这样的回落：截止时刻要由认领时刻算出，回落得出的可能是错的那一句。
  - 截止时刻与说明：认领时由认领时刻、预算与期限算出这个 job 的截止时刻（与前台同一个算法），随启动交给启动器。本机的后台推进进程按墙钟检查它，每个执行中的 job 一个按短间隔读墙钟的检查：检查读的墙钟由组合根注入启动器，与推进步骤取认领时刻的是同一个读取点，两处比较的才是同一个时钟；间隔只决定到点之后最多晚多少发出停止请求，不进任何记录；检查持续到 worker 进程退出、不止到事件流结束，关了事件通道却不退出的 worker 过了截止时刻同样被停下。退出记录另带一项事实，退出时刻：本机是推进进程看到 worker 退出的那一刻（经注入的墙钟读取），云端是 task 对象里的执行停止时刻（退出观察者与 job 到点停止都从 task 对象取，同一个 task 两处取到同一个值），启动失败的补偿记失败的那一刻；补写的未知退出没有可观察的退出时刻，不带这一项。投影时，退出时刻晚于这个 job 的截止时刻的退出与带超时标志的退出同样处理（内容完整的不改判）：worker 在截止时刻之后、停止请求发出之前自己退出时，本机后台与云端后台得到的判定与前台终结之前的那次检查相同。观察者只记事实，不判断是否已过截止时刻：截止时刻要由运行态与运行定义算出，云端的退出观察者只看 task 对象；判断放在两种后台共用的投影里，规则只有一份。超时标志因此只表示发过到点的停止请求、或补写时已判为到点，不兼管「退出时已过截止时刻」。本机的后台推进进程里，看到 worker 退出（读退出时刻、读超时标志）与检查线程的到点决定（确认还没有看到退出、读墙钟、置超时标志）互斥进行，先后只有一种：已经看到退出之后检查线程不置标志，退出记录里不会出现「退出时刻不晚于截止时刻、却带着之后才置上的超时标志」的组合。云端的一次性定时触发定在这个时刻，Lambda 对到点触发的复查与防御性超时扫描按同一个算法重算。定时触发早于截止时刻时，job 到点停止在这次调用的等待额度之内等待，额度之内没有读到已过的这一次不停止、留给之后的推进检查（何时等待、额度怎样定，见 0034「job timeout」节「到点不早于 deadline」条②）：发出停止之前必须有一次读到已过截止时刻。后台被截断的 job 同样按起作用的截止时刻分开（0034 机制二「终结函数与真值表」，各记什么见 0031 决定一），投影时由运行态里的认领时刻、预算与期限重算是哪一个起了作用，不在退出记录里另记。终结函数的这项输入没有缺省值：前台在认领时算出、后台在投影时重算，两条路径都必须给出它，不会因为漏传而悄悄落到预算那一行。
  - 收尾与报告：第 3 条里看运行态的条件由到期的结束写按它写下时的运行态判断：run 未结束，且没有 `running` 的 job（run 未结束而没有执行中的 job，即仍有未启动的 job；0031 决定三「结束写」小节）。云端由 RunStore 强一致读运行态、以读到的写入序号为条件写，写不成即重读再算，序号只保证判断用的是最新的运行态；本机在 `.runstate.lock` 内读改写，按锁内读到的整份运行态计算（两侧见 0034 机制三②）。写下时运行态里有执行中的 job，结束写不成立、返回未写成，推进步骤按继续推进处理：这一轮读运行态之后新认领、还没有结果的 job 即属此类；新认领的 job 在结束写之前已记下终态（如启动失败的补偿）时，写下时没有执行中的 job，结束写照常写成。推进步骤不经手写入序号。读到已是终态说明别处已经结束了它，按已结束处理。读不到运行态的那一轮不做到期的结束写。逐 job 的写序（先存明细、再写终态并点名）见 [0030](./0030-realtime-persistence-seam.md) 决定三，报告由使 run 成为终态的那次写的写入方从记录生成（[0027](./0027-runreport-aggregation-index.md)「ReportStore 接口：整 run 一次写」节）。
  - 不记「已过停止认领」：推进步骤是无状态的，每一轮按当前时刻判断。某个推进器的时钟回拨或落后时它可能在这个时刻之后又认领，新认领的 job 的截止时刻照样以期限封顶（第 2 条）。记录层面的一致由到期的结束写自带的条件保证：写下时有执行中的 job 就不写，两侧都按写下时的运行态判断，云端的写入序号只保证这一判断用的是最新的运行态。它不保证 run 记为终态时没有 worker 还在执行，那属于「边界与已知局限」里已列的情形。
- 云端后台 run 另有两次 run 级的定时触发，属于后端：各做什么、成立的前提与前提不成立时怎样，见决策九第 1 条。

**检查用墙钟**：期限与 job 的截止时刻都按墙钟检查，不用单调时钟。期限是别的机器也要拿来比较的时刻，而且单调时钟在系统休眠时不走，合盖几小时再打开的进程只有按墙钟才知道自己已经过期。job 自己的预算同理：执行方的机器休眠期间，云端的 task 与远端的会话照常消耗，浏览器会话的存活时间也是按墙钟由预算推出的；按墙钟计，前台与后台的截止时刻才是同一个算法。代价是系统时钟被大幅调整时，job 的预算随之变长或变短；按单调时钟计能避开这一点，但给不出别的机器能比较的时刻（前台调度循环的两个时钟见 0026）。

每个 run 因此有一个由 job 预算推出的总时长上限。它不是使用者单独配置的 run 级预算（0034「job timeout」节不设 run 级总墙钟预算），调整它的途径是各 job 的墙钟预算与停止宽限。选它而不把期限只当作「推定管 run 的进程已不在」的阈值，理由是：

- 对测试工具，一次 run 允许运行的总时长有上界本身是该有的性质：CI 可以据此排期；云端浏览器会话与真机按分钟计费，休眠后恢复的执行方会自己把过期的会话停掉，后台的推进器同样遵守期限，不靠有人查看。
- 三种组合是同一种表现：「允许运行至」对所有 run 是同一个意思，上层不必按执行方式分别理解。代价是推进停住的 run 满足处置的条件之后可以被结束（条件见决策六），被处置的要重新提交。
- 清单里这一列的名字是「允许运行至」，硬约束才名副其实。

### 三、生命期锁：加在 run 目录上

本机后端的 run 由持有它的生命期锁的进程推进：前台是执行 `run` 的进程，后台是 `submit` 启动的后台推进进程（本机任何时刻至多一个推进器，这条规则在 0034「推进器与触发源」）。两者都自己建 run，从建 run 起持有锁到进程退出。管这个 run 的进程还在不在，由别的一方试拿这把锁回答（决策六）。

- **对象**：run 目录本身。建 run 的一方在报告目录里建出暂存目录（名字以 `.gherkai-creating-` 开头、后接随机串，形态见下「谁在何时试拿」），以只读方式打开它并取排他的 `flock`，写好运行定义与运行态之后把它原子改名成 run 标识；锁随这次打开留在改名之后的 run 目录 `<report-dir>/<run_id>/` 上。试拿的一方同样以只读方式打开要试拿的目录、不阻塞地取排他的 `flock`。锁按打开的文件描述计：同一进程另一次打开同样被挡，共用这个打开的进程里有一个还开着，锁就在。
- **持锁的描述符**：改名之后由建 run 的入口交给构造存储时注入的持有者（[0030](./0030-realtime-persistence-seam.md) 决定四），生产用的持有者不关闭它、也不交出它，锁随进程退出释放。它的号不落在标准输入、标准输出、标准错误的 0 到 2 号上，取到锁时号小于 3 的换到 3 以上：后台推进进程回报之后把日志接到这三个号上（[0035](./0035-local-app-testing-via-tunnel.md) 决策 3「本机 `submit`」一条里「输出」），改接会关掉这几个号上原来的打开，锁落在其中一个号上就随之放开、没有任何报错。
- **谁在何时拿**：
  - `run`（生成记录时）：从在暂存目录上取到锁起持有到进程退出。暂存目录建不出（名字已被占用）、打开时已不存在、取不到锁（另一个进程持有它，即清理方，含只看不删的那一种），或拿到之后它的名字已不指向这个目录（取锁之前已被删去、换掉）时，换一个名字重来，至多 3 次，都不成即以退出码 2 结束；run 标识重复由改名失败给出（目标已是非空目录，0030 决定四），也以退出码 2 结束。
  - `submit --backend local`：提交进程不拿锁、不建 run（它只在前置检查里对报告目录做一次边界检查，决策四）。它启动的后台推进进程同 `run`：在暂存目录上取锁、写好两个文件再改名，持有到进程退出；锁不可用、暂存目录连续被占用时不建 run，经回报由 `submit` 以退出码 2 结束（次序与回报见 [0035](./0035-local-app-testing-via-tunnel.md) 决策 3「三种组合的宿主与次序」里「本机 `submit`」一条）。
  - 云端后端没有锁。
- **建 run 不被中断打断**：前台 `run` 起好隧道之后即装上只记标志的中断处理器（执行期间用的同一个，[0024](./0024-worker-core-protocol.md) 终止契约「使用方中断」条），从这时到命令结束，Ctrl-C 与 SIGTERM 只记下、不打断正在做的一步，解释器里不再有中断引起的异常（进入命令时已被设为忽略的那一个信号不装处理器、保持忽略）；它在两处看这个标志：建 run 之前（已有中断即不建 run），建 run 与准备执行的各步之后、启动第一个 job 之前（已有中断即不启动任何 job，由它自己做结束写）。后一处是一次检查：检查之后、第一个 job 启动之前才到的中断，按执行期间被中断处理。建 run 自己失败而期间收到过中断的，按建 run 失败结束（退出码 2）。两处的出口见 [0035](./0035-local-app-testing-via-tunnel.md) 决策 3「前台 `run`」一条。后台推进进程对 SIGINT 取缺省处置（0035 决策 3「云端 `submit`」里讲两种后台进程信号处置的一条），收到即结束，同样没有解释器层面的中断。Ctrl-C 因此不会落在建 run 的各步之间：要么还没有开始建、什么都没有留下，要么已经建成、记录完整。理由：解释器可以在任意两条字节码之间抛出中断引起的异常，取得描述符与记下它之间、改名与交给持有者之间的间隔在入口内部补不完；把这一段包进一个推迟 SIGINT 的区间也不够，进入区间之前、离开区间之后仍有几条字节码会被打断（两种都见「被拒方案」）。不经解释器的结束（SIGKILL 一类）不受它影响，留下什么见下「锁取在暂存目录上、写完再改名」一条。
- **删去自己的暂存目录只凭自己那次打开**：建 run 失败时，名字仍指向自己打开的那个目录才删，持着锁时连同里面的文件（只删这一层：里面只有建 run 写下的文件，枚举用的描述符不多于写入时一次用的；按整棵树删要多一个，实测进程只剩两个描述符名额时它枚举不了、把错误吞掉，暂存目录连同两个文件留下），没有取到锁时（对它的边界检查不过、锁不可用）只删空目录；建出之后没有打开成功的不删，留给清理方。删除是尽力而为：删除本身失败时（如进程的描述符已用尽、枚举不了这一层），暂存目录留在原处，它按名字认得出、建它的进程退出之后没有人持锁，由清理方按协议清（见下一条），与进程被强杀留下的是同一个出口，不为这种情形另设保障（见「被拒方案」）。理由：没有打开成功就无从核对这个名字是否仍指向自己建出的那个目录；没有取到锁的两种出口上锁不能作依据（文件系统被拒，或取锁出错），删的是自己建出的空目录，清理方拿到锁之后要核对名字仍指向它打开的目录（见下一条），发现已不在即不删、不列出（它已不是暂存目录）。前提：暂存目录名字里的随机尾（64 位）在同一个报告目录里的两个创建者之间不相撞，不为相撞另设防；自己建出的名字在打开之前被清理方删去、又被另一个创建者取到同一个名字的情形因此不在其内。
- **谁在何时试拿**：等待中的 `status --wait` 在 run 未结束时每次轮询试一次，`settle-runs` 对每个未结束的本机 run 试一次（决策八），都只对以 run 标识命名（名字以点开头的不是 run 标识，0030 决定四）、运行态已读得出、这个 run 的记录格式版本与本机相同（决策六）的目录；不阻塞，拿到之后持有到这次处置做完，含生成报告（各步的次序见决策八「处置的次序」）。
  - 清理建 run 残留的一方（`settle-runs` 不给 run 标识时，决策八）只认名字是暂存目录的前缀加 16 位小写十六进制、本身是目录（不跟随符号链接）的条目，这个形态与建 run 的一方生成名字的形态在 code 里同一处定义；文件、符号链接与形态不符的名字不碰，也不看时间与内容。以点开头的名字留给暂存目录、暂存目录的命名形态，凭名字形态与锁认它、不读内容的这套判法，以及暂存阶段的互斥（上「对象」一条里锁的取法，建 run 的一方改名前后持有的是同一把锁），属跨版本不变的约定（[0037](./0037-distribution-and-packaging.md) 决策 7「跨版本不变的约定」约定五）：清理方不读记录、不比格式，任何版本的清理方都要挡得住任何版本正在建的 run。对每个这样的条目依次：以只读方式打开它，打开时已不存在即已不是暂存目录、不列出，别的打开失败记为跳过；对这次打开做边界检查（决策四），不过即跳过；试拿，被持有、锁不可用都跳过；拿到之后核对这个名字仍指向打开的那个目录，核对不过即已不是暂存目录（建它的进程已改名成 run 并退出，或它被换掉），不列出，按旧名字删会删错；核对通过才持着锁删去它，删除中途出错记为跳过并带上原错误，已删去的部分不恢复，下一次接着删。空的、没有人持锁的暂存目录（建 run 的一方建出之后没有打开成功而留下的，见上一条）照同一套协议清。
  - 只看不删的清理方（`--dry-run`）同样试拿、拿到即放开：建 run 的一方恰在这时得到「已被持有」即换名，丢下的空暂存目录由下一次不带 `--dry-run` 的清理删去。
  - 理由：前缀之外再核形态，挡住使用者恰好以前缀起名的目录（实测名为 `.gherkai-creating-user-named` 的目录不碰）；只看不删也试拿，才能如实分出「被持有」与「会删除」。实测（macOS 的 APFS，真实进程按上面的协议逐步执行）：4 个创建者与 3 个不带 `--dry-run` 的清理方连续反复建 run 1600 次、8 个创建者与 8 个只看不删的清理方 2400 次，没有一次因暂存目录连续被占用而建不成，没有 run 目录被删或缺文件，只看不删的那一组多留下 1 个空暂存目录；清理方在删除中途被强杀时余下的文件留着、锁随之释放，下一次删去。
- **结果的判读**：只有成功算拿到，只有「已被持有」（`EWOULDBLOCK`）算持有者还在（建 run 的一方在暂存目录上遇到即换名，见上「谁在何时拿」）；其余错误一律按锁不可用：建 run 的一方删去这个空的暂存目录、以退出码 2 结束（本机后台的 run 经回报由 `submit` 给出，见上「谁在何时拿」），处置的一方只剩期限一条（决策六），清理方跳过这个暂存目录。试拿之前的那次打开另有两种结果，都不是锁不可用：处置的一方打开 run 目录得到「不存在」（`ENOENT` 或 `ENOTDIR`）时，这个名字下已没有 run（各入口怎样处理见决策八「处置的次序」）；别的打开失败（没有权限、描述符用尽、符号链接成环）是读写记录失败，也不是判断不了文件系统，不按期限处置（各入口怎样结束见决策八）。理由：没有打开成功就没有可做边界检查与试拿的描述符，按锁不可用继续会在一个没有核过文件系统的目录上按期限写记录（实测：run 目录的权限为 0o300 时打开得到 `EACCES`，运行态照样读得出、结束写照样写得成）；权限问题与「换到本机磁盘」的处理办法不同，与决策四对报告目录打开失败的取法相同。
- **不被子进程继承**：锁按打开的文件描述计，子进程手里只要还有这次打开的副本，持锁的进程退出之后锁仍在。子进程不带着它，按起子进程的两种方式各有一条做法：经 exec 启动的子进程（worker；隧道建在宿主进程里、不是子进程，0035 决策 3），描述符不可继承，exec 时即没有它；fork 而不 exec 的子进程（直接 fork、fork 方式的 `multiprocessing`、停在 `preexec_fn` 里的子进程），由生产用的持有者在收下描述符时登记的钩子处理（`os.register_at_fork`，fork 之后在子进程里执行）：子进程里先核对这个号仍指向持锁的那个目录（设备号与 inode 相同），是则关掉自己这一份。关掉子进程里的副本不放开锁，锁仍由父进程的那一份持有；核对是为了这个号之后若被关闭并另作他用，钩子不关到别的打开。生产用的持有者不保存、也不交出它收下的描述符的号。不在其内的几种：本进程里的代码绕过持有者拿到这个描述符，把它设成可继承、或经 `pass_fds` 带给子进程（见下「前提」；同一进程里的代码总能遍历描述符表找到它，这一类靠约定、不靠机制）；不经解释器的 fork（C 扩展、`ctypes` 直接调系统库）不触发钩子；建 run 的那一次调用中途由别的线程 fork 出的子进程（下一条单列）；fork 出的子进程在钩子执行之前被暂停时，锁持有到它继续执行；子进程关掉副本之后在同一个号上另开这个目录、再 fork 的，孙进程里的那一份同样被关。收下描述符时取不到它的身份即不登记钩子、不报错：改名之后没有会失败的步骤。
- **已知的间隔：钩子在建 run 的末尾才登记**。建 run 的那一次调用依次在暂存目录上取到锁、写两个文件、改名，最后才把描述符交给持有者，钩子在这时登记。从取到锁到登记之间（几次本机文件操作，毫秒级），本进程别的线程经解释器 fork 而不 exec 出的子进程拿到了这次打开的副本、却没有钩子替它关掉：持锁的进程退出之后锁仍被这个子进程持有，试拿的一方得到「已被持有」，处置要等到期限加 300 秒（或那个子进程退出）。实测一个不停 fork 而不 exec 的后台线程与建 run 同时进行时，建 150 个 run、强杀持有方之后 150 个都仍被持有。这个间隔现在不可达：两种推进器在建 run 的这一段只有一个线程在做事，生产代码里没有 fork 而不 exec 的起法（起 worker 经 exec，不经过这个钩子，也不受影响）。**以后改动时要先处理它的情形**：往持锁的进程（前台 `run`、后台推进进程）里加线程，并且这个线程会 fork 而不 exec（直接 fork、fork 方式的 `multiprocessing` 或进程池、带 `preexec_fn` 的 `subprocess`）。处理办法见「重议闸门」里「持锁的进程里出现 fork 而不 exec 的线程」一条；不处理就加，是把这条前提悄悄破掉。
- 理由：死活由操作系统在进程退出时给出，不需要对方配合，也不靠时钟。真实进程核过（macOS 的 APFS，Linux 清单里的类型与绑定挂载；清单见决策四）：被暂停的持有方仍持有，已退出未回收的已释放；fork 而不 exec 的子进程延长持有，`subprocess` 缺省方式启动的不会，`multiprocessing` 以 fork 起的会（Linux 上 Python 3.12、3.13 的缺省）。子进程还活着时强杀持锁进程，另核过（macOS 的 APFS）：`start_new_session`、`close_fds=False` 起的与 `multiprocessing` 以 spawn 起的不延长持有，经 `pass_fds` 交出锁描述符的延长；锁描述符被复制成可继承的号之后，`close_fds=False` 或 fork 加 exec 起的延长持有，缺省方式起的不延长（它关掉了这个号）。风险因此只在两类写法：fork 而不 exec；把描述符变成可继承、同时以不关描述符的方式 exec。`preexec_fn` 属于前一类：它在子进程里先于关描述符与 exec 执行，子进程停在其中时带着父进程的全部描述符（实测父进程被 SIGKILL 之后锁仍被持有，到这个子进程退出才释放）。前一类由持有者登记的钩子去掉：登记之后，直接 fork（含在线程里、fork 之后再 fork）、`forkpty`、fork 方式的 `multiprocessing` 与进程池、停在 `preexec_fn` 里的子进程在父进程被 SIGKILL 之后都不再持锁，经 exec 的各种起法（缺省方式、`close_fds=False`、新会话、`pass_fds` 传别的描述符、`posix_spawn`、`os.system`、spawn 与 forkserver 方式的 `multiprocessing`）同样；`ctypes` 直接调系统库的 fork 仍持锁（实测 macOS 与 Linux 内核 7.0，Python 3.13；不登记时直接 fork、fork 方式的 `multiprocessing` 与 `preexec_fn` 三种都仍持锁）。后一类要先拿到锁描述符的号：持有者不保存、不交出它，本进程里的代码不绕过持有者去找它是前提（见下「前提」），不靠机制保证（实测：同一进程里的代码从持有者的内部状态取得这个号、把它设成可继承、再以不关描述符的方式起子进程，父进程被 SIGKILL 之后锁仍被持有；持有者因此不再保存这个号，而遍历进程的描述符表仍找得到它）。这条前提不成立时的后果与「已知的间隔」相同：试拿的一方得到「已被持有」，处置推迟到期限加 300 秒或那个子进程退出，不会把活着的 run 结束，也不会出现两个推进器。放弃：POSIX 记录锁（只读打开的目录取不上排他的；按进程计，关掉任一指向该文件的描述符即释放）；长期持有 `.runstate.lock`（读改写用的短锁，长期持有挡住所有写）。
- 锁取在暂存目录上、写完再改名，理由：以 run 标识命名的目录只经改名出现，改名之前锁已取上、两个文件已写下，试拿方只碰这样的目录（先后颠倒时的问题见「被拒方案」里「先改名、再取锁」一条）；建 run 的进程中途被强杀时（掉电与内核崩溃不在其内，见「其它局限」），留在报告目录里的是暂存目录，清理方凭名字的形态与锁认它（见上「谁在何时试拿」），不凭内容判断是不是建到一半（见「被拒方案」里「以 run 标识直接建目录、残留按内容就地清理」一条）。暂存目录的名字只有建它的进程与清理方会碰，建 run 的一方在它上面得到「已被持有」只说明清理方正在处理它，换一个名字即可；拿到锁之后核对名字仍指向这个目录，挡的是它在取锁之前已被清理方删去的情形。实测：持锁改名之后，另一个进程按新名试拿得到「已被持有」，持有方的 `fstat` 与按新名的 `stat` 是同一个 inode，持有方被暂停期间仍持有、被 SIGKILL 之后约 15 毫秒内即拿得到（macOS 的 APFS；Linux 内核 7.0 的 `ext4` 上 20 毫秒之内；HFS+ 与 FAT 的磁盘映像上同样保锁，二者不在清单）。创建者与清理方的三种交错（清理方在创建者打开之前删去、在创建者打开之后取锁之前删去、清理方正持有）由「拿到锁且名字仍指向它」一条判出：前两种创建者打开得到「不存在」或核对不过，第三种得到「已被持有」，都换名；创建者改名并退出之后，清理方此前打开的描述符拿到锁、核对不过，不删、不列出，run 目录完好（macOS 上两个真实进程逐步交错）。
- 本机后台由后台推进进程自己建 run，理由：给了 `--expose-local` 时隧道要由推进器持有（持有隧道的进程没了，run 也就没有推进器，两者一起没了），公网地址要在建 run 之前拿到（替换进运行定义里 job 的文本，0035 决策 2），所以起隧道与建 run 都在后台推进进程里；锁由建 run 的进程从建 run 起持有到退出，前台与后台是同一种做法。回报通道本来就要有：`submit` 要把公网地址、run 的标识或失败原因告诉使用者。由 `submit` 建 run 再把锁交给后台推进进程、后台推进进程接手已经建成的 run，见「被拒方案」。
- **前提**：持锁的进程启动子进程经 exec，或经解释器的 fork（见上「不被子进程继承」）；建 run 的那一次调用期间，本进程别的线程不 fork 而不 exec（见上「已知的间隔」）；本进程里的代码不绕过持有者去拿锁描述符，不把它设成可继承，不把它带给子进程（现在的生产代码没有这样的写法：起子进程都用缺省的关描述符方式，`pass_fds` 只传自己刚建出的管道，即 worker 的事件管道与回报管道）；锁只在建 run 的那个进程里，描述符只在建 run 的入口与持有者手里，不在进程之间传递。依赖方：「拿得到锁即管它的进程已不在」（决策六）与「本机至多一个推进器」。

锁只在决策四的边界之内有效。

### 四、生命期锁的前提：本机后端报告目录的产品边界与边界检查

- **产品边界：本机后端的报告目录及其中的 run 目录要在本机文件系统上**（检查见下一条）。同一个内核上经同一个挂载或其绑定挂载访问的在边界之内（实测宿主与容器、容器之间）；网络文件系统、经虚拟机共享进来的目录在边界之外（实测 macOS 的 Docker Desktop：宿主目录在容器里是 `fakeowner` 类型、被拒，宿主一侧是 APFS、放行，两侧的锁互不阻挡）；多台机器共用记录用云端后端。用户文档写明并列出清单，并提醒不要把报告目录放在文件同步服务的文件夹里（下「文件锁有效」一条）。报告目录的路径另有长度上限，超出即在入口拒绝，规则与推导见 [0030](./0030-realtime-persistence-seam.md) 决定四「报告目录的路径长度」条。
- **边界检查**（本机后端）在取锁与试拿锁的动作里、先于取锁（`run`、本机 `submit` 启动的后台推进进程、等待中的 `status --wait`、`settle-runs`，含它清理暂存目录的一步），判断的是随后取锁的那一次打开的描述符：建 run 的一方对暂存目录的描述符判断，不过即删去这个空目录、以退出码 2 结束；试拿的一方对要试拿的目录（run 目录，或清理方要清的暂存目录）的描述符判断。建 run 的一方另在建暂存目录之前对报告目录判断一次，这一次被拒时不留目录。报告目录不存在时，沿路径向上只越过打开时得到「不存在」的各层，取最近一层已存在的上级判断；别的打开失败（路径上有文件、没有权限、符号链接成环）按写记录失败报出，不当作判断不了：两者对使用者的处理办法不同，权限问题按「换到本机磁盘」说会误导。报告目录在入口统一解析成绝对路径（解析其中的符号链接），前台与后台交给建 run 的都是解析之后的路径；经符号链接指定的报告目录因此沿链接判断与建立，链接的目标还不存在时按目标最近一层已存在的上级判断，随后在目标处建出目录。类型不在清单里或判断不了（如读不到挂载信息、平台不是 macOS 与 Linux）即以退出码 2 结束，说明写原因（这样的目录上无法确认执行 run 的进程是否还在）、检测到的类型与怎么办（列出清单）；判断不了时另给出改用云端后端这条出路：原因可能在整台机器上（平台不是 macOS 与 Linux、读不到挂载信息），换哪个目录都判断不了，这一句对判断不了的各种原因相同、不按原因分支。`settle-runs` 在报告目录存在时另查它；报告目录不存在时没有可处理的 run，不给 run 标识的照常结束，给了的按 run 不存在处理（决策八）；某个 run 目录不过只跳过它、在结果里写明原因（决策八）。`doctor` 的报告目录一项用同一判断（0041 决策四），本机 `submit` 的提交进程只做下一条的前置一次，两者都不碰锁；其余命令不碰锁，也不查。放行不证明在边界之内、锁有效（见下面「文件锁有效」一条；不靠读回，见「被拒方案」）。两个平台同一条规则（macOS 不只看本机标志，见「被拒方案」）：各处都对打开的目录的描述符取文件系统类型，由内核解析路径（含符号链接、绑定挂载与盖住它的上层挂载；两个平台上实测按挂载表的最长前缀会取到被盖住的那条），只放行清单里的类型；清单只收照决策三理由实测过的，先实测再加：
  - macOS 由 `fstatfs` 取类型名。实测（arm64）：APFS 为 `apfs`，HFS+、FAT 的磁盘映像为 `hfs`、`msdos`，autofs 自动挂载点为 `autofs`。清单：`apfs`。HFS+、FAT 上的锁只核过互斥、同一进程再开被挡、被杀后释放、持锁改名之后按新名被挡，不进清单。取 64 位 inode 形态的结构（2168 字节）：先找符号 `fstatfs$INODE64`，找不到再用 `fstatfs`（实测 Rosetta 下编译的 x86_64 程序引用前者、arm64 程序引用后者，两者结构大小与各字段偏移相同、都读出 `apfs`）。读回之后核两项：类型名非空且是可打印 ASCII，挂载点以 `/` 开头；不合、或调用返回非零，即判断不了：布局出错只会变成拒绝，不会变成放行。
  - Linux 由描述符的 `mnt_id`（`/proc/self/fdinfo`）在 `/proc/self/mountinfo` 取那一条。实测（内核 7.0）：被盖住、经符号链接、容器里的路径都取到实际所在的挂载，绑定挂载显示源的类型，不存在的目录取上级、与新建后同类型，懒卸载后取不到；NFS 为 `nfs4`、`nfs`。清单：`ext4`、`tmpfs`、`overlay`（宿主与容器上实测）；`xfs`、`btrfs`、`ext3`（回环镜像、缺省选项、`btrfs` 顶层子卷上重做，除数值外与 `ext4` 相同）。
- **前置检查里的一次**：`run`（生成记录时）与本机 `submit` 在共用的前置检查里、补全运行定义与上传安装包之前，另对报告目录判断一次（取法同上一条对报告目录的那一次），不过即以退出码 2 结束、说明与建 run 时相同；打开失败同样在这里按写记录失败报出。不过时两者都不上传安装包、不起隧道；本机 `submit` 的这一次由提交进程自己做，不过时也不启动后台推进进程。这一次只为早拒：报告目录在清单之外是确定的配置错误，与前置检查里的其余各项一样挡在上传安装包、起隧道之前。保证仍来自建 run 时对同一次打开的判断与取锁：前置检查之后这个位置所在的文件系统可能变了（解析之后的路径上某一层被盖上挂载、换成了符号链接），建 run 时的判断不因此省去；使用者原来给的那个符号链接此后改了指向不在其内，报告目录在入口已经解析，run 仍建在解析出的位置。
- **前提：本机文件系统，文件锁有效**。产品边界之内保证的前提是 `flock` 对所有读写这个 run 目录的进程按打开的文件描述互斥（运行态的写锁本来就依赖它，0030 决定三）。边界之外的共用不在保证之内：两侧的锁（含运行态的短锁）可能互不可见（NFS 上的实测见「被拒方案」），运行态的写可能互相覆盖。检查放行而在边界之外的：同一块设备挂在两个内核上、两边取到的类型都在清单里；同一个内核里经两个文件系统实例访问同一份数据（实测：容器 overlay 与它的上层目录之间锁互不阻挡）；文件同步服务管理的目录（如 iCloud Drive、Dropbox、OneDrive 的同步文件夹，macOS 上实测类型是 `apfs`），内容会同步到别的机器，锁只在本机内核里。依赖方：两个本机处置方与「本机至多一个推进器」。
- **前提：边界检查信任内核给出的挂载信息**（macOS 的类型名，Linux 的挂载表与描述符的挂载 ID），不防伪造它的一方，与「边界与已知局限」里「有人改动、删除 run 目录里的文件」一条同类；判断与取锁对同一次打开做。

### 五、终态不可变，执行方服从记录：run 结束之后不再接受新的认领

**终态不可变。** run 的状态只往前走：`pending` 到 `running` 到终态；run 一到终态，运行态的任何写都不成立。这对端口上的每一个写入口成立（形态见 0030 决定四），前提是写都经端口的写入口。它不丢信息：run 是终态当且仅当全部 job 是终态（0031 决定三），到终态时每个 job 都已有终态，此后到达的结果是迟到的结果、不被采用。

- 建 run 只在这个 run 还不存在时成立：云端要求条目不存在，本机要求以 run 标识命名的位置还没有非空目录，对已有的 run 再调用即失败、不改任何记录；端口不提供整份重写与无条件改写终态的入口（0030 决定四）。本机建 run 的互斥由暂存目录与改名给出：两个文件先写进暂存目录，再原子改名成 run 标识，目标已是非空目录即失败、删去暂存目录、不改任何东西（0030 决定四；锁怎样随改名留下见决策三「对象」）。云端依次以条件写写下 jobs 对象（键不存在才写）、头与运行态（条目不存在才写），不覆盖已有的任何一项；各步的条件、run 已存在时报什么、留下什么，见 0030 决定六「建 run 是条件写」条。
- 本机建 run 之后的各写入口在同一把短锁（`.runstate.lock`）内读改写、互相排斥，按锁内读到的整份运行态计算（0034 机制三②）；0030 决定三的并发不变量因此对这些写入口成立。建 run 不取这把短锁：暂存目录里的两个文件没有别的写入方会碰，互斥出自上一条的改名。

理由：终态之后再变，对任何基于状态做事的上层（等待者、退出码、清理、处置，以后的界面或服务）都是错的行为：已经返回的退出码撤不回，已经据终态做的清理与处置撤不回。依赖方：`status --wait`、`list-runs`、CI 把读到的终态当定论，报告据记录生成。

**执行方服从记录。** 终态不可变只保护记录，不能让执行停下来。执行方每次启动 job 之前先认领，认领以 run 未结束为条件（0034 机制三「run 级状态只进不退」条①；各命令写什么见 0034「命令形态」），所以 run 记下终态之后不再接受新的认领；检查已经通过、启动还没有完成的 job 仍会启动（本节「这一条不依赖时钟」一段）。各执行方的做法：

- 后台推进的认领要求 run 为 `pending` 或 `running`（`try_claim_job`）。
- 前台执行同样先认领（0026）：从队列里取到 job、第一次起 worker 之前先做同一个认领，认领时刻随之记进运行态。一个 job 只认领一次；同一个 job 因网络故障重试时不认领（它已是 `running`，再认领会被自己拒掉），而在每次重新启动之前读一次 run 的状态（[0028](./0028-transient-network-ssl-resilience.md)「重试之前的检查」）。认领被拒或读到 run 已是终态，说明 run 已被别处记为已结束：这个 job 不启动，调度循环对执行中的 worker 发停止请求，然后结束。起 worker 之前各项检查的次序、停手时各种处境的 job 怎么记，见决策二「一次前台执行可能因三种原因停下」一段：发现 run 已被别处结束是一种中止来源。认领排在各项检查之后、紧贴起 worker，免得留下已认领却没有执行的 job。执行方自己的时钟已过停止认领的时刻时，拦住它的是时间检查；认领被拒这一支在它的时钟落后于处置方时才会走到。认领或读取本身失败（存储不可达）按运行期落库失败处理，与落库回调抛出异常相同。代价是前台每个 job 多一次条件写（认领）。
- 前台此后写 job 状态（开始执行、结束）时保留认领时刻。开始执行的写（`update_job_state`）整项替换，不带认领时刻的写会把它抹掉：落库服务记住每个 job 的认领时刻、此后的写带上它（与代表会话同一做法）。结束的写（`commit_job_states`）与库中的条目按字段合并，认领时刻以库中的为准，库中没有时才取调用方给的（字段规则与理由见 0030 决定四「终态写的字段合并」条）。
- 前台写 job 状态时发现 run 已是终态（这次写写不成）同样触发停手。为此两种 job 状态写都让调用方知道 run 在这次写时是否已结束，run 已结束时写不成：执行中的 `update_job_state` 返回 `False`，终态的 `commit_job_states` 返回 `ALREADY_ENDED`（0034 机制三③、0030 决定四），两个 adapter 对拍。认领、重试之前的读、job 状态写三处的发现汇成同一个停手信号，调度循环不碰存储（0030 决定一），经组合根注入的能力取得它：job 状态写时的发现在那次落库回调返回之后当场读进来，等待循环另与使用方中断同一节拍地轮询它、先于中断处置（登记的次序见决策二「一次前台执行可能因三种原因停下」一段）。认领、重试之前的读与停手信号三项合成一个注入对象：有记录的执行三项都有，`run --no-report` 三项都没有，不会出现只注入其中一部分的状态（形态见 0030 决定一）。
- **执行方得知 run 已结束之后就不存明细**（迟到的结果不被采用）：前台在停手信号成立之后，本机后台与云端在一轮读到终态之后。run 到终态之后新落下的明细只剩已开始的保存（前台是那一次，本机后台与云端是那一轮的各个 job），三种组合都有；读者怎样只认被终态点名的那一份见 0030 决定三。
- 结束时前台执行方不覆盖已有的终态，在终端说明这个 run 在本次执行结束之前已被记为已结束，说明与判定明细的位置写在 stderr，以非零退出码结束（退出码见 0031 决定五）。报告不由它生成：报告只由使 run 成为终态的那次写的写入方生成（0027「ReportStore 接口：整 run 一次写」节），这里是结束它的那一方。`run` 也不输出汇总与 `--json` 文档（0041 决策三）：run 由别处结束，结果从记录读（`status`），本次执行看到的只是其中一部分。

这一条不依赖时钟：不管两台机器的时钟差多少、执行方是否被暂停过，run 一旦是终态，它的下一次认领或启动前的检查就会拦住。能越过它的只有检查已经通过、启动还没有完成的 job（至多并发上限那么多）：首次启动是认领已成功，重试是启动前的那一次读已通过，而启动调用还没有发出、正在进行，或句柄还没有返回。它们会启动。启动之后由谁停，三种组合不同，见「边界与已知局限」里「run 到终态之后各组合下还会发生什么」那张表。

由此终态之间没有分组变化（0041 决策七）。

### 六、死活的判断与处置的条件

- 管这个 run 的进程还在不在，由试拿生命期锁回答（决策三）：拿得到即已不在；被暂停的进程仍持有锁，算还在。
- **管它的进程不在了的 run 不续**：此后不认领、不启动 job，只能被处置。run 处置（本篇单说「处置」都指它）即以结束写把一个推进不下去的 run 结束：管它的进程已不在，或已过运行期限加 300 秒（下一条）；云端后端在期限加 300 秒时自己做的那一次（后端到期结束，决策九第 1 条）同样是处置。job 到了截止时刻被停下另称 job 到点停止（0034「job timeout」节）。谁能处置见决策八。
- **可以处置的条件是两者之一**：试拿锁拿到了；或当前时刻严格晚于运行期限加 300 秒。云端只有后一条。这个时刻在 code 里只有一处算法，隧道的边缘到点拒绝取同一个结果（[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 13「边缘策略」）。300 秒给时钟偏差与仍在的推进器按期限自己结束（决策二第 3 条）留出余量，不是收尾时长的上界（下一条）。期限读不出时只剩试拿锁一条，云端即无从处置。判定读整份运行定义，两个后端相同，不只读提交记录的头（记录格式版本、写出版本与期限）。期限读不出指提交记录不存在、内容不是 JSON 对象，或定义违约（含 `deadline_at` 缺失或不合法，决策二「落点是运行定义」一段；云端 jobs 对象的内容损坏同属定义违约）；读取本身失败（没有权限、描述符用尽、限流、网络不可达一类）不算读不出，按读写记录失败处理、不处置（决策八）。云端取不到 jobs 对象同样不算期限读不出：后端与用户一侧各怎样归类、理由是什么，见 [0030](./0030-realtime-persistence-seam.md) 决定六「jobs 对象取不到时」一项。理由：判定要严谨，记录损坏就按损坏的规则走，不因只读了头而对正文的损坏视而不见（被拒方案「判定只读提交记录的头」）。记录格式版本与本机不同的 run 不在其内：提交记录的头读得出、其中的 run 记录格式版本与本机不同（缺这个值读作 0），`settle-runs` 与等待中的 `status --wait` 都不处置它（各自怎样给出见决策八），依据见 [0037](./0037-distribution-and-packaging.md) 决策 7。
- **期限加 300 秒按墙钟判断，不是推进器收尾时长的上界**：处置方与推进器各读自己的墙钟，本机两者读同一个内核的；云端两者的时钟可能不同，处置方的比推进器慢时处置推迟，快时提前，推进器在期限之后的余量是 300 秒减去快出的量，快出的量超过 300 秒加这个 run 离期限的余量时，在推进器看来仍在期限之内的 run 已满足处置的条件。停止与落库调用可能阻塞更久（决策二「尾段与余量是预算的取值」一段），被暂停的推进器不受时长约束。处置做的结束写只看运行态（0031 决定三「结束写」小节）：`running` 的 job 记 `aborted`、`pending` 的记 `skipped`，不论推进器一侧走到哪一步；没写进运行态的结果不论是什么都不被采用（决策五），run 不会是 `passed`（推进器本会使它通过的也是）。此后的事按既有各条：`run` 的退出码见 0031 决定五，终端输出见决策五；还会落下哪些明细见决策五，报告由谁生成见 0027；留下的执行由谁停见决策七「处置只改记录」一条。
- 运行态本身读不出的 run 无法做条件写，不处置。读不出指内容解析不了；读取本身失败不在其内，按读写记录失败处理（决策八）。

### 七、处置做什么

- 读运行态，已结束则不动；否则做结束写（0031 决定三「结束写」小节，说明取其中说明表里处置的两行），写成的一方生成报告（0027「ReportStore 接口：整 run 一次写」节）。两个处置同时发生、或处置与推进器自己的结束写同时发生时，只有一方写成，另一方读到已结束（决策五）。各步的次序见决策八「处置的次序」。
- **报告**：写成的一方按被处置的那个 run 标识（run 目录的名字）读记录、生成报告，不取提交记录里的标识：复制出来的 run 目录里两者不同。run 目录在试拿之后被换掉属于有人改动 run 目录（「边界与已知局限」里「其它局限」第一条），不为它另加核对。提交记录读不出的 run 被处置之后没有报告：报告按运行定义逐个列出 job（0027「RunResult 的组装只有一处」条），组装不出，与云端结束写的 error 变体同一处理。生成报告的失败隔离在处置之内，不改变处置已写成这一结果。报告是否生成是处置结果里的一项结构化事实，没有生成时连同原因（原因的类别与说明分开记）交给调用方：两个入口说明已记为已结束、报告没有生成及其原因，不给报告的位置，也不把回溯打到终端（[0039](./0039-user-facing-surfaces-no-internal-references.md)）；后端到期结束把它连同原因的类别记进日志；`settle-runs` 的机读输出见决策八。原因按实际得到的错误给出：云端读判定明细时，处置方没有桶的列举权限，取一个不存在的键得到的是拒绝访问，记为读写失败并带上原错误，与 `explain` 对同一情形的说法相同（[0042](./0042-step-evidence-and-explain.md) 决策四）；后端到期结束在推进 Lambda 上执行，它有列举权限，同一情形记为明细缺失。两边各按实际得到的错误如实说明，不为让两边记成同一种原因给用户一侧另加列举权限（被拒方案）。
- 处置不推演事件，不替事件里有、运行态里还没有的结果下结论：推进器在 worker 退出之后、写下终态之前中断（云端触发链断开时这段可以很久），处置看到 `running`，记 `aborted`「没有结果」；同一次中断在云端通常由流的重试与之后的触发记下真实结果，三种组合的 job、run 状态与退出码可能不同。不取「处置方先按事件记下已有结果的 job，再结束其余的」：它与云端一致，但本机处置方要推演事件，云端的 `status --wait`、`settle-runs` 要多出读 events 表、写明细的权限，不给则两种云端处置方结果不同。
- 本机推进器因保存明细一直失败而退出时，执行中的 job 留在 `running`，被处置时记「进程已退出」那一句（重试与放弃见 0030 决定三）。
- 清理协议不用改：run 被结束后离开 `live` 分组，不再占住它引用的 worker 任务定义修订（0038 残余风险④）。此后执行方不认领新的 job（决策五），余下未启动的 job 不会再用到这些修订；检查已经通过、启动调用还没有发出的那几个 job 可能因为修订刚被回收而启动失败，这个 run 此时已是终态，不影响记录。
- **处置只改记录**，不停执行：本机 worker 在推进器退出之后靠核验所属进程自行退出（[0024](./0024-worker-core-protocol.md) 终止契约，通常十余秒，失效情形见「边界与已知局限」）；前台推进器发现 run 已结束之后对它启动的 worker 发停止（决策五），本机后台推进进程发现之后退出；云端由后端清扫 task（决策九第 2 条）。

### 八、处置方与入口

- **能处置的只有**：`settle-runs`；等待中的 `status --wait`；云端的 run 另有后端到期结束（决策九第 1 条，含前提）；以后的取消命令（条件与对推进器的作用在取消的设计里定）。`list-runs`、不带 `--wait` 的 `status`、`explain` 只读、不碰锁。各处置方写什么见 0034「命令形态」的表。判定与处置放在 runtime 包的一处（`settle.settle_run`），`status --wait`、`settle-runs` 与云端的后端到期结束三方都调它，Lambda 里不另写第二份判定（被拒方案「在 Lambda 里另写一份处置判定」）。三方共用这一处判定，适用于数据版本与后端相同、过了后端的闸的 run：别的数据版本写出的 run 到了后端先按闸的规则处理（error 变体，决策九「落实时」一段），按这个 run 自己的格式读写它的命令行工具仍可按处置的规则处置它，两者之中使 run 成为终态的那一笔为准（[0037](./0037-distribution-and-packaging.md) 决策 7「后端遇到别的格式写出的 run」里「与别的写方的先后」）。
- **处置的次序**：一次处置依次做：读一次提交记录，先核其中的记录格式版本：与本机不同即给出结果、不解读其余部分（决策六）；相同的读整份运行定义，读得出的记下期限，读不出的（含记录格式版本不是整数）即期限读不出（决策六）；读运行态，不碰锁，读不出或已结束即给出结果、不做后面各步（已结束的 run 不打开 run 目录、不做边界检查、不试拿）；本机以只读方式打开 run 目录，对这次打开做边界检查（决策四），不阻塞地试拿（决策三）；判定，取一次墙钟，结束时刻用同一个读数；结束写；写成的一方生成报告（决策七）；最后关闭描述符，锁随之放开，所以锁持有到报告生成之后。云端没有打开、边界检查与试拿三步。
  - 只有结束写改记录，它自带 run 未结束的条件（0031 决定三「结束写」小节），前面各步之间别的一方插进来的变化都由它裁定：推进器先写成，这一方读到已结束；两个处置方同时，只有一方写成（决策七），记下的是先写成的那一方的判定，一方拿到锁、另一方因锁被它持有而按期限判断时，可能记下期限那一行，两行都是真实情形，不另协调。理由：判定只在一处，各处置方共用；不在锁内重读运行态，条件写已是唯一的裁定。实测（macOS 的 APFS，两个真实进程同时开始，各 40 轮）：期限未到时每轮都是一方 `advancer_exited`、另一方 `lock_held`；期限已过时每轮只有一方写成，40 轮里有 21 轮写成的是因锁被另一方持有而按期限判断的那一方。
  - 读运行态之后的任一步遇到「不存在」（打开 run 目录、读提交记录、结束写时这个名字下已没有目录或文件），都按这个名字下已没有 run 处理，与读运行态时读不到同一口径；各入口怎样处理见下「`settle-runs`」与「等待中的 `status --wait`」两条。macOS 的 APFS 上，在正被删去的目录里建文件、把文件改名进去，系统给的可能是「参数无效」而不是「不存在」（实测与删除真实重叠时，这两步的失败里各有一部分是它）；本机 adapter 在目录确已不在时把它读作「不存在」，归类只在原子写与运行态短锁的打开两处，目录还在的原样报出。
  - `--dry-run` 给出的是判定那一刻的结果，不写，拿到的锁随即放开；同一时刻不带 `--dry-run` 执行时，读运行态之后才结束的 run 由结束写得到已结束，两者可能不同。
  - 读量：每次处置读一次提交记录与一次运行态，等待中的 `status --wait` 每次轮询都是一次处置，读量随轮询重复。云端读整份运行定义是强一致读一次头、再取一次 jobs 对象：头不随 job 数增长，普通 run 约三百字节，读一次 1 个读单位（读单位按整条记录计，只投影头部属性不减少读单位，实测见 [0030](./0030-realtime-persistence-seam.md) 决定六「依据」第 3 项）；取 jobs 对象是一次请求，同区域实测约 550KB 的对象（约相当于 500 个 job、每个 8 个 step）中位 31 毫秒。读单位与请求数都不随用例内容增长，与别的存放形态的对比写在 [0030](./0030-realtime-persistence-seam.md) 决定六。不为省这笔读另设「一条命令只读一次」或「只读头」的接口（被拒方案「判定只读提交记录的头」「为省读量让一条命令只读一次提交记录」）。
- **本机没有常驻的处置方**：推进器退出或停住之后，没有人执行 `status --wait` 或 `settle-runs` 时，没有别的一方结束这个 run，`list-runs` 照常列出。
- **`gherkai settle-runs [run_id] [--dry-run] [--json]`**，加 0041 决策六的三项定位参数，取值来源（含项目配置文件那一层，[0053](./0053-project-config-file.md) 决策 1）与 `status` 相同。不给 `run_id` 时处理这个后端里全部未结束与运行态读不出的 run，不分前台与后台；给了只处理那一个。本机后端不给 `run_id` 时，处理完 run 之后另清建 run 留下的暂存目录（协议见决策三「谁在何时试拿」）。云端不给 `run_id` 时先过与 `list-runs` 相同的索引就绪检查（[0041](./0041-agent-facing-cli-affordances.md) 决策七「索引就绪判据」），列举只保留读回未结束与运行态读不出的 run：索引滞后时列出而读回已结束的不列，两个后端的 `runs[]` 同一口径（本机按读回的状态归类，本来就不列出）；云端没有暂存目录（云端建 run 不经暂存目录），不做清理。每个 run 按上「处置的次序」处置，`reason` 取第一条成立的：
  - `other_version`（这个 run 的记录格式版本与本机不同，决策六）、`unreadable`（运行态读不出）、`already_finished`（已结束，含结束写被别处抢先）、`unsupported_filesystem`（run 目录不过边界检查）、`advancer_exited`（锁拿到了）、`past_deadline`（已过期限加 300 秒）、`lock_held`（锁被持有，未必是推进器）、`undetermined`（锁不可用或期限读不出）、`within_deadline`（云端未过期限加 300 秒）。`other_version` 排在最前：别的格式写出的运行态，本版本只按约定读得出其中的公共部分（[0037](./0037-distribution-and-packaging.md) 决策 7），其余部分未必解析得了，排在 `unreadable` 之后会把它说成记录读不出；它的说明陈述两边的记录格式版本与写出它的发行版本。`advancer_exited` 与 `past_deadline` 的 `outcome` 是 `settled`，`--dry-run` 下是 `would_settle`；其余是 `skipped`。两个后端用同一套 reason：云端没有锁，`advancer_exited`、`lock_held`、`unsupported_filesystem` 不出现，`undetermined` 在云端只表示期限读不出，`within_deadline` 只在云端出现。
  - 给与不给 `run_id`：不给时，列举之后被删去的 run（读运行态时已不存在，或之后任一步遇到「不存在」，见上「处置的次序」）略过，不出现在结果里，也不中止其余的处理；给了而它不合名字规则（含暂存目录的名字，0030 决定四）、目录或运行态不存在、报告目录不存在，都按给出的 run 不存在以退出码 2 结束。云端给出的 run 的运行态不存在时同样，说明请使用者核对 `--prefix` 与区域是否与提交这个 run 的 `submit` 一致。报告目录不存在而没有给 `run_id` 时没有可处理的 run，照常结束。读写记录失败（含打开 run 目录时别的失败，决策三「结果的判读」；含列举时读不了某个 run 的运行态）就此停止，先输出已处理的部分；出错的那个 run，失败出在结束写之前的各步时没有改动（这些步只读）；出在结束写这一步而没有收到响应时，写成与否不确定（结束写是原子写，要么整条写成、要么没有改动）。其余的没有处理，再执行一次是安全的：已处置的给 `already_finished`。
  - 人读输出：run 一张表，清理暂存目录时另有一张（有项时才出现）；原因列按 `reason` 与结构化的字段（期限读不读得出、文件系统类型、原错误）选句，说明只描述。`unreadable` 的说明给出怎么办：本机是这个 run 目录里的记录读不出，`settle-runs` 与 `status --wait` 不改动它，确认不需要之后可以手工移走；云端是运行状态表里这个 run 的记录读不出，处置命令不改动它，请部署方核对这条记录，不建议删去记录，也不说「用写出它的版本查看」（记录格式版本不合的已排在前面给出 `other_version`，同一记录格式版本下读不出出自记录被改动或环境损坏，见决策九「落实时」一段）。只有不给 run 标识、列举完成而列出的 run 为零时才给一句，陈述读到的结果：没有列出未结束的 run。两种后端同一句，不断言「没有未结束的 run」：云端的清单来自最终一致的索引，刚提交的 run 可能还没列出。给了 run 标识时不说，列举没有完成或列出的 run 一个都没有处理完就停下（读写记录失败、被中断）时也不说。说明与帮助里把按期限可以记为已结束的时刻说成「允许运行的时间之后再过 N 分钟」（N 由决策六那一处算法里的 300 秒换算，`status --wait` 的帮助用同一种说法），不说成允许运行的时间本身：期限之后、期限加 300 秒之前的 run 已超过允许运行的时间，还不能按期限处置。
  - 机读输出：`--json` 给一个对象。落点字段本机同 `list-runs`（`report_dir`）；云端在 `list-runs` 的 `prefix`、`region` 与 `ddb_table` 之外另带 `report_dir`，值是这条命令写报告所用的报告前缀，写成完整的 `s3://<产物桶>/<规范化之后的报告前缀>`（与本机给解析之后的绝对路径同一取法；键名与本机相同，两个后端里它都是这条命令写报告的位置，`status --json` 的产物位置也是同一个键在本机给路径、在云端给 `s3://`）：云端的 `settle-runs` 会生成报告，机读读者要知道报告写到了哪里，`list-runs` 不读报告、所以不带它（0041 决策七「机读形态」）。另有 `dry_run`，`runs[]`（按 run_id 降序）每项带 `run_id`、`outcome` 与 `reason`，`outcome` 为 `settled` 的项另带 `report_written`（布尔，报告是否生成，决策七）；本机清理暂存目录时另有 `staging_dirs[]`（云端没有这一项；按名字升序，报告目录不存在时为空数组），每项带 `name`、`outcome`（`removed`、`would_remove`、`skipped`）与 `reason`（前两种为 null，`skipped` 时为 `held`、`unsupported_filesystem`、`lock_unavailable`、`unopenable`、`remove_failed`），已不是暂存目录的（打开时已不在、拿到锁之后名字已不指向它）不出现。不带 `cli_version`：发行版本只作事实，处置的结果不需要它；要写出版本与记录格式版本的读者用 `list-runs --json` 取。被中断、读写记录失败或云端报告前缀比对不通过时同样先输出这一个对象（已处理的部分），读者按退出码分流。
  - 退出码：跳过不改变退出码，清理暂存目录的各种跳过也不改变：暂存目录不是 run，列举与按标识的读写都不认它，删不掉时让每次执行都以 2 结束，会让按退出码分流的调用方一直失败，而处置本身已经完成。退出码见 0031 决定五。它是变更类命令里带 `--json` 的一个：0041 决策三把变更类命令的机读面定为退出码，这里的结果是逐条的处置清单，退出码承载不了，作为该条的明示例外。
- **读写记录失败的类别**：两个入口与后端到期结束遇到读写记录失败时只接一种失败，带结构化的类别：`settle_run` 与列举要处置的 run 时把读写本身的错误包成它（「不存在」照旧按这个名字下已没有 run，上「处置的次序」）。类别有六种：凭证与权限（AWS 的 AccessDenied 一类、UnrecognizedClient、ExpiredToken、找不到凭证；本机的 PermissionError）；写入竞争的重读次数用尽；限流（ThrottlingException、ProvisionedThroughputExceededException、RequestLimitExceeded）；列举没有读完；表或索引不存在（ResourceNotFoundException）；其余（网络不可达、超时与别的错误，本机其余的 OSError）。说明里的「怎么办」按类别与后端选句：凭证与权限，云端说检查凭证、权限与 region，本机说检查报告目录的读写权限；写入竞争说这个 run 同时有别的写入、稍后重新执行同一条命令；限流说读写被限流、稍后重新执行同一条命令；列举没有读完说还有 run 没有读到、稍后重新执行同一条命令；表或索引不存在说出缺的是哪一项与它由前缀拼出的名字，不断定原因（同 [0033](./0033-iac-aws-backend-and-composition-wiring.md) preflight 节「不存在」条）；其余带上原错误，云端说检查网络与 region 之后重新执行，本机说检查报告目录所在的磁盘。云端用户一侧取不到 jobs 对象时同样按读写记录失败处理、不处置（两侧怎样归类及理由见 [0030](./0030-realtime-persistence-seam.md) 决定六「jobs 对象取不到时」一项）：得到的是拒绝访问还是「键不存在」，都归凭证与权限一类，「键不存在」也不当作上面的「不存在」；说明在凭证与权限那一句之后补半句：权限无误时，可能是这个 run 的提交记录已不完整。取 jobs 对象时的别的错误按上面的类别归类，不补这半句。补这半句的判据是失败出在取 jobs 对象的那一次读、且得到的是拒绝访问或「键不存在」这两种（凭证过期等别的凭证类错误不补）；拒绝访问与「键不存在」给出同一句说明，不随部署方授没授列举权限而变。判断只看类别，句子只描述。两个入口以退出码 2 结束，说明写明本命令没有把它记为已结束；失败出在结束写这一步而没有收到响应时，说明写的是不确定它有没有被记为已结束、重新执行同一条命令即可看到（这一项事实随失败的类别一起带出，判断不看说明文字；`settle-runs` 先输出已处理的部分）；后端到期结束的日志带上类别。理由：只给一句「检查凭证」时，对写入竞争与限流是错的指引，对已被删去的 jobs 对象也是。
- **等待中的 `status --wait`**：两个后端、前台与后台的 run 都一样。开始等待之前按这个 run 的记录格式版本比（[0037](./0037-distribution-and-packaging.md) 决策 7）：与本机不同的以陈述两边的值的那一句、退出码 2 结束，不进入等待（决策六）；提交记录不存在或内容不合法不在其内，按期限读不出处理。只在等得到头的两种情形下等待：锁被持有（有进程在管这个 run），或期限读得出（至多等到期限加 300 秒）；两者都不成立的不等待，见下「以退出码 2 结束的」。run 未结束时每次轮询做一次处置（上「处置的次序」）：本机先试拿锁（决策三），再比期限；云端比期限。两个后端用同一个等待函数；轮询间隔本机 1 秒、云端 3 秒（云端每次轮询都是计费的读），是方式固有的差别、不影响判定。云端在 run 未结束时比对一次报告前缀，在第一次处置得出结果之后、开始等待或写下处置之前（下「云端处置方的报告前缀」一条）。条件成立即处置，在标准错误说明一句本命令已把它记为已结束及原因（报告没有生成时一并说明、不给报告的位置，决策七），然后照不带 `--wait` 的 `status` 的规则渲染、给退出码（0031 决定五）；run 已是终态时直接渲染，不做边界检查、不碰锁、不比对报告前缀。
  - 条件不成立时继续等待。说明只描述，每种原因说明一次，原因变了再说明，是否已说明过按结构化的原因与错误码判断、不按文字：锁被持有而期限读得到不说明，云端期限读得出而未过期限加 300 秒时同样不说明；锁被持有而期限读不出时说明读不到允许运行到什么时候，只在执行它的进程退出之后才能把它记为已结束；锁不可用而期限读得出时说明原因，等到期限加 300 秒。理由：锁被持有而期限读不出时等待的长短取决于那个进程，使用者要知道；处置改了记录，要说出来。
  - `--json` 下等待中的各句说明与处置之后「已把它记为已结束」的那一句都不给（0041 决策三，`--json` 下不给人读提示），本命令是否处置了这个 run 由 JSON 文档里的状态与结束原因体现。属于诊断的照常写到标准错误、`--json` 下也给：以退出码 2 结束的原因，被 Ctrl-C 打断时的那一句，以及处置之后报告没有生成及其原因（JSON 文档里报告的位置始终给出、不表达那里有没有内容，不说就无从得知）。本命令处置了这个 run、随后却以退出码 2 结束而没有给出 JSON 文档时（如提交记录的头不合法，显示不了），已把它记为已结束这件事并进那一句诊断，报告没有生成的原因也在这一句里。
  - 以退出码 2 结束的：run 不存在（运行态不存在，含等待期间被删去；提交记录不存在而运行态在的不在其内，按期限读不出处理，次序同上「处置的次序」）；运行态读不出（内容解析不了；两个后端的每次写都整条原子落下，读不出是持续的状态，等不出结果），说明与不带 `--wait` 的 `status` 相同；锁不可用而期限也读不出（既不能凭锁判断，也没有期限可等）；云端期限读不出（提交记录不存在而运行态在、提交记录内容不合法）：云端只能按期限把它记为已结束，说明读不到这个 run 允许运行到什么时候，所以本命令不等待、也没有改动它的记录，并给出只查看它的 `status` 命令（带 `--backend cloud --prefix`）；run 目录不过边界检查（决策四），不处置，也不只读地等下去（见「被拒方案」）；云端的报告前缀与后端所用的不一致，或比对时读不到推进 Lambda 的配置（不存在或别的错误，下「云端处置方的报告前缀」一条），不处置、也不开始等待；处置时读写记录失败（含打开 run 目录时别的失败，决策三「结果的判读」；类别与说法见上「读写记录失败的类别」），说明本命令没有把它记为已结束。
  - 它只盯到终态、条件成立时处置，不推进；云端不调用 `kicker`（唤醒推进的只有流与定时触发，0034「推进器与触发源」）。
- **中断**：两个入口在开始时装上只记标志的中断处理器（与前台 `run` 同一个，决策三「建 run 不被中断打断」；SIGINT 与 SIGTERM 都记，进入命令时已被设为忽略的那一个不装、保持忽略），中断只记下、不打断正在做的一步。`settle-runs` 在列举之后与每一项之后（每处置一个 run、每清理一个暂存目录之后）看这个标志，给了 run 标识时在那一次处置之前也看一次（已有中断即不处置，说明没有改动任何记录），`status --wait` 在每次处置之后与等待的间隔里看（等待分成不超过 0.2 秒的小段）。看到之后不再做下一项，说明按已记下的结果给出：`settle-runs` 先输出已处理的部分，再说明其余没有处理、可以再执行同一条命令；`status --wait` 在本命令处置之前被打断，说明没有改动这个 run 的记录，处置之后被打断，说明已记为已结束（报告没有生成时带上原因，决策七「报告」）、给出查看它的命令；退出码按信号取（SIGINT 为 130、SIGTERM 为 143）。两个后端相同：云端的两个入口同样在开始时（先于任何云端读）装上这个处理器、在同样的检查点看标志、给出同样的说明，查看它的命令带 `--backend cloud --prefix`；装上之后的第一件事是比云端后端接口版本（[0037](./0037-distribution-and-packaging.md) 决策 7），先于资源检查与任何别的云端读。只有让命令少做了事的中断才改变结果：最后一个检查点之后才收到的（`settle-runs` 的最后一项或输出期间，`status --wait` 显示期间），命令照常做完，说明与退出码和没有中断时相同，与前台 `run` 在执行结束之后才收到中断的取法一致。读写记录失败与中断同时出现时按读写记录失败结束（退出码 2）：失败是更具体的事实，中断没有使它发生。输出只做一次，在处理器还装着时写完并刷新，不被打断。理由：只用一种已有机制，一次处置与记下它的结果之间不会被隔开，说明不必猜中断落在哪一步。代价见「边界与已知局限」里「其它局限」。
- **管它的进程退出而 run 未结束的出口**：本机推进器读写记录失败而退出（含后台推进进程推进期间遇到事件库错误）、记录写下之后准备执行用的文件失败、本机 `submit` 在回报之前读到后台推进进程退出（这时 run 可能已经建成），这些出口上 run 停在未结束、没有推进器，说明里给出把它记为已结束的 `settle-runs` 整条命令，带上 run 标识与报告目录（`submit` 在回报之前读到退出时不知道 run 标识，给不带 run 标识的那一条，它同时清理暂存目录），前台与后台同一说法；之后重新执行还是重新提交，按这个 run 出自 `run` 还是 `submit` 取，这是方式固有的差别。后台推进进程的这句说明写进它的日志，不带回溯。推进器因运行态解析不了而退出的不在这一组：这样的 run 处置方也不结束（决策六最后一条），说明给的是 `settle-runs` 对 `unreadable` 的同一句（记录读不出、处置命令不改动它、确认不需要之后可以手工移走这个 run 目录），不说可以记为已结束。前台 `run` 在建 run 之后、开始执行之前被中断不在其内：前台进程这时仍持锁、就是推进器，由它自己做结束写（[0035](./0035-local-app-testing-via-tunnel.md) 决策 3「三种组合的宿主与次序」里「前台 `run`」一条）；它自己的这次结束写失败时，run 停在未结束、进程退出之后没有推进器，仍属这一组，说明同样给出 `settle-runs` 的整条命令。理由：停在未结束、没有推进器的 run 只剩处置这一个出口（决策六），执行方式不改变判定，所以前台与后台给同一个出口。
- **云端处置方的报告前缀**：运行定义里没有这个 run 的报告落点：提交记录与运行态都不带报告前缀；头里指向 jobs 对象的地址落在产物桶里专放运行定义的前缀之下，不随报告前缀变化（0030 决定六），与报告落点无关。云端的判定明细与报告落在推进 Lambda 的 `REPORT_DIR` 下，用户一侧的前缀由 `--report-dir` 给出。云端两个处置入口照 `submit` 的做法比对两者（[0033](./0033-iac-aws-backend-and-composition-wiring.md) preflight 节「产物前缀一致性」条，三处调同一个函数）：用两个推进 Lambda 上的 `lambda:GetFunction` 读它们的 `REPORT_DIR`（缺这个键即 Lambda 内的缺省），两侧规范化之后再比，不一致即以 `submit` 同一句说明、退出码 2 结束，不处置；函数不存在或读它时得到别的错误（拒绝访问、限流、网络），说明照 [0033](./0033-iac-aws-backend-and-composition-wiring.md) preflight 节「不存在」与「探测得到别的错误」两条，同样以退出码 2 结束、不处置。一条命令至多比对一次：run 未结束时，在第一次处置得出结果之后、开始等待或写下处置之前比对；已结束的 run 直接显示、不比对。`status --wait` 的第一次处置只判定、不写，得出继续等待或要处置时比对，通过之后才开始等待或处置；`settle-runs` 没有等待，比对之前的各次处置只判定、不写，在第一个要处置的 run 处比对，通过之后再处置它（`--dry-run` 同样比对：真处置时会失败的配置在预览时就报出）；比对不通过时先输出已处理的部分（此前判为跳过的各项），再以退出码 2 结束，与读写记录失败时相同（上「给与不给 `run_id`」一项）。期限读不出、运行态读不出、记录格式版本不合各按自己的出口结束、不比对。本机不比对：记录与报告在同一个 run 目录里，没有第二个来源。后端到期结束不比对：它用的就是自己的 `REPORT_DIR`。边界：部署方在提交之后改了 `REPORT_DIR` 并重新部署时，之前提交的 run 的明细留在旧前缀下，使用者用新前缀通过比对、处置写成，报告因明细读不到而缺失（见「重议闸门」）。理由：比对挡住报告写到使用者看不到的前缀下；在 `status --wait` 开始等待之前比对、不等到期限加 300 秒，配置不对时尽早报出；只在要结束 run 时比对，已结束的 run 带不带 `--wait` 显示相同（被拒方案「在命令开始时对一切 run 比对报告前缀」）。
- **云端用户一侧的处置方**（`status --wait`、`settle-runs`）要能做 runs 表的条件写、读运行定义（runs 表的读，加产物桶 `definitions/` 前缀上读对象的权限，两者恒需）、读判定明细、写报告，另需两个推进 Lambda 上的 `lambda:GetFunction`（上「云端处置方的报告前缀」一条）；不给 `run_id` 的 `settle-runs` 另需 `list-runs` 的两项。读运行定义是判定所需，缺它时按读写记录失败结束、不处置（决策六）；缺「读判定明细、写报告」两项时结束写照样写成，这个 run 没有报告，说明给出原因（决策七「报告」）。不需要调用 Lambda 的权限 `lambda:InvokeFunction`（`status --wait` 不唤醒推进，见上「等待中的 `status --wait`」一条），也不需要桶的列举权限（决策七「报告」）。依赖方：被处置的云端 run 有报告。权限逐项登记在 0033 编排进程角色，梯级见 [0040](./0040-consumer-role-model-and-terminology.md) 决策 3。
- `list-runs` 的「已运行」「允许运行至」两列、期限提示与 `--json` 的 `deadline_at` 见 0041 决策七。

### 九、云端后端：到期结束 run，run 结束之后清扫它的 task

本机的 worker 能核验管它的进程还在不在，不在就自己退出；云端的 task 做不到。云端的每个 run 都由后端推进（0034「推进器与触发源」），云端后端里一直都在的只有 Lambda，所以到期结束 run 与停掉 task 也放在后端，由两个推进 Lambda（`kicker`、`reconciler`）承担，不另设。

1. **定时触发。** `kicker` 收到 STATE 条目的新建（META 已先写）时，先过后端的闸（本决策「落实时」一段），再各自尝试建立两次一次性的定时触发，然后做首轮推进。runs 表流的过滤明写 `INSERT` 且 `item_type` 为 STATE：建 run 时先写 META 再写 STATE，两条都是新建，只收 STATE 才保证 kicker 处理时 META 已在（两条过滤的确切形态见 0033 资源清单 13）。kicker 按流记录的种类分辨 STATE 的新建，不按读到的状态（被拒方案「按读到的状态决定建不建 run 级触发」）。两次触发与 job 到点停止的触发同一机制、同一执行角色、同一个 schedule group，触发之后自动删除；group、名字、表达式与载荷见 0033 资源清单 15。
   - 次序与失败：先建、后推进，理由同 0034「job timeout」节「武装先于 RunTask」条：推进中途失败、被超时截断时，已建的触发不缺位。建不成不挡首轮推进，同该节「best-effort 边界」条：冷启动不依赖 Scheduler 可用。有建不成的，推进之后把它记为这条记录的失败，按第 2 条「失败与批的隔离」一项让这次调用失败、由流重试：名字确定，重试时已建的得到「已存在」（`ConflictException`）即视为已建，推进幂等（已认领的 job 不再认领）。闸给出运行态不存在、读不出、已结束、run 由别的格式写出或运行定义不可用时不建。推进 Lambda 的环境里缺建定时触发所需的配置（目标函数与执行角色，由部署注入）时按建不成处理：run 级的两次记为这条记录的失败，job 到点停止的按 0034「job timeout」节「best-effort 边界」条。
   - 时刻：期限那一次取 `deadline_at` 本身（带秒、截去小数秒，与 job 到点停止的触发同一取法）；不取整：它要停执行中的 job，推迟即多占 task 的时间，与 0034 不给 job 到点停止的触发取整同理。期限加 300 秒那一次取这个时刻之后的第一个整分钟（严格晚于它）：Scheduler 在指定时刻所在的那一分钟之内触发（决策二「尾段与余量是预算的取值」一段），取整之后按文档精度到达时已过这个时刻，这次调用不必等待，整段执行时间留给结束写与报告（推进 Lambda 的时长约束见 0033 资源清单 12）；推迟不足一分钟，对已超过允许运行的时间 5 分钟的 run 没有影响。两个时刻都由 core 算出（`run_deadline.deadline_of`、`run_deadline.overdue_at`），Lambda 里不另写 300 秒。建立之前读一次墙钟，时刻（写进触发表达式的那个值）不晚于这个读数的那一次不建：期限已过时，同一次调用里的推进已过停止认领的时刻、不认领，没有执行中的 job 时做到期的结束写（决策二第 1、3 条），那一次触发没有可做的事；期限加 300 秒已过时同理。这样不依赖 Scheduler 对过去时刻的表现；贴近当下的时刻被拒时这条记录失败，重试时那个时刻已经过去、不再建。
   - 期限那一次：过闸之后等到严格晚于期限（下「到点的处理」一项），读一次运行态，已结束或已不存在即清扫，读不出与闸里同一情形一样只记日志（本决策「落实时」一段第一步）；对整个 run 列一次 task（运行中与已停止的都取全），对没有退出记录的执行中的 job 逐个做 job 到点停止（0034「job timeout」节的三路停止）；然后强制推进一次（某个 job 的停止失败时，其余的照常停、推进照常做，之后让这次调用失败，第 2 条「失败与批的隔离」一项）。各 job 的截止时刻以期限封顶（决策二第 2 条），确认已过期限时它们都已过，所以这一次与各 job 自己的定时触发是同一处理，只是对整个 run 列一次 task，不按 job 逐个列。这次推进不做防御性超时扫描：已对全部执行中的 job 做过 job 到点停止，再扫只会按 job 逐个列 task。另设这一次，是因为各 job 自己的定时触发是尽力而为地建立的（0034「job timeout」节「best-effort 边界」条），某一个没建成、它的 worker 又不出任何事件时，可能再没有别的调用带到这个 run。停止引出的退出事件带起之后的推进，推进按决策二第 3、4 条处理。时限前提：期限那一次要在期限之后约 150 秒内处理完（`stopTimeout` 至多 120 秒，退出到可归约约 30 秒，决策二「尾段与余量是预算的取值」一段），内容已完整的 job 才赶得上在期限加 300 秒那一次之前写下终态；投递推迟或重试越过这个界限时，两边由写入序号裁定，后端到期结束先写成时这些 job 记「没有结果」。
   - 期限加 300 秒那一次是**后端到期结束**。过闸（各分支见本决策「落实时」一段）：运行态不存在、已结束即清扫；运行态读不出即不处置、只按时间清扫；run 由别的格式写出、或运行定义不可用，即做结束写的 error 变体（只写运行态的公共部分，[0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节）并清扫。先过推进器的闸、再处置：后端就是这个 run 的推进器，遇到别的格式写出的 run、读不出运行定义时它有自己的规则（error 变体，本决策「落实时」一段与 0031 决定三），这条规则先于处置的规则，否则后端自己的不同入口会对同一个 run 给出 error 或 skipped 两种结果（与用户一侧的处置方的先后，见决策八「能处置的只有」一条）。其余的调 runtime 的 `settle_run`（决策八「能处置的只有」一条，判定只此一处；它自己读一次提交记录与运行态，与闸里的读不合并），按决策六、七处置，说明取 0031 决定三「结束写」小节说明表「处置：已过期限加 300 秒（含云端后端到期）」那一行。结果是还在期限加 300 秒之内时（只在触发早于文档精度时出现），按下「到点的处理」一项等待之后再处置一次。不推进。得到结果之后按第 2 条清扫：写成或读到已结束按③，这个名字下的运行态已不在按①，其余确认已过期限加 300 秒的按②：处置没有走到判定的（处置时运行态变得读不出、提交记录在过闸之后被改动），用处置读到的期限确认，处置没有读到期限的无从确认、只记日志、不清扫；等待之后再处置仍得到还在期限加 300 秒之内（等待期间墙钟回拨）时不再处置，等待已确认过那个时刻、照样清扫。推进链断开、之后的事件与定时触发都没有把它带到终态的 run 由这一次结束，没有 job 出错或未通过时以 `aborted` 告终，需要重新提交。
   - 到点的处理重新读墙钟确认已过（期限那一次比 `deadline_at`，后一次比期限加 300 秒，按决策六的墙钟判断），不以收到触发为证据（定时触发只承诺分钟精度、表达式不带小数秒）；未过则在这次调用里等待，与 job 到点停止的到点复查共用同一个等待（额度在第一次等待之前定下，每次至少 1 秒，累计按请求等待的秒数，0034「job timeout」节「到点不早于 deadline」条②），等待只决定等多久，可否动手仍按上面各项判断；额度用完仍未过的这一次不动手（期限那一次不做到点停止、也不推进，期限加 300 秒那一次不处置），留给另一次触发、各 job 自己的触发与之后的调用。运行态不存在或已结束时只清扫（本决策「落实时」一段）。
   - 两次的时刻是计划触发的时刻，不是处理完成的时刻。两次是彼此独立的异步调用：各自可能晚到，失败时由 AWS 的重试再调用（由 Scheduler 还是 Lambda 的异步调用重试、重试几次，见实测项 26），调用到达与处理的耗时没有上界（0034「job timeout」节「到点不早于 deadline」条③）；两次完成的先后没有保证。期限加 300 秒那一次可以先结束 run，期限那一次随后到达时 run 已结束、只清扫；run 结束时仍在执行的 task 交给清扫（第 2 条），不依赖期限那一次先做过 job 到点停止。Scheduler 至少投递一次，同一次触发可能到达两次：两次调用各自等待、各自停止，处置由写入序号裁定、只有一方写成，三路停止由条件写裁定，推进幂等，结果唯一。
   - 前提：每一次都要触发建成、调用成功，并在等待额度之内确认已过它的时刻。任一环失败时，执行中的 job 仍有它自己的定时触发与防御性超时扫描（0034「job timeout」节「best-effort 边界」条与 `JobState.claimed_at` 条②），这个 run 由之后的事件、另一次定时触发或用户一侧的处置方（决策八）收尾；重复执行与调用被丢弃见「边界与已知局限」里「其它局限」。
2. **结束之后清扫。** 清扫按启动时带的 run 标识（`startedBy`）列出这个 run 仍在执行的 task（期望状态为运行中，翻页取全），逐个停掉。清扫只在两个推进 Lambda 里做：退出观察者只写退出记录，用户一侧的处置方没有 ECS 的权限，它们的写经流带起推进 Lambda 的清扫（下①③）。`startedBy` 取 run_id、task 所在的 cluster 是 `{prefix}cluster`，两者属跨版本不变的约定（[0037](./0037-distribution-and-packaging.md) 决策 7），后端靠它们停掉别的版本起的 task。StopTask 的 reason 是一句不含超时哨兵的说明：含了哨兵，退出观察者会把这次退出记成超时（0034「job timeout」节）。列到之后才停下的 task 不另作处理：StopTask 对正在停止与已停止的 task 照常成功返回（已核，实测项 27）。清扫不写 runs 表，可以重复执行，不要求恰好一次。

   每次清扫停掉的是这一次列得出的 task。启动调用还没有返回的 task 可能列不到；ECS 的列举是最终一致的，刚启动的 task 也可能暂时列不出来；这一次都会漏掉。漏掉的 task 交给之后的清扫（何时清扫见下面三条规则）。哪一次停得到它，取决于那一次到来时它是否已经列得出；产品不承诺它在哪一次被停下，都没有停到时它留下（「边界与已知局限」）。按计划到来的最后一次是期限加 300 秒那一次，它停得到这个 task 要这次触发的前提成立（上第 1 条「前提」一项；运行态读不出的 run 另见下②），并且那时这个 task 已经列得出。后一项没有保证，已知的只是间隔的下界：启动请求在认领它的那一次推进调用之内发出，推进 Lambda 的限时是 120 秒（0033 资源清单 12），认领不晚于期限前 60 秒（决策二第 1 条，按认领一方的墙钟读数；墙钟由平台维护，读数与真实时刻的偏差属平台异常，决策二第 1 条写到的推进器墙钟回拨或落后也在其内），所以启动请求比期限加 300 秒那一次的计划时刻至少早 240 秒（这个下界等于 360 秒减去推进 Lambda 的限时，调限时要一并核对，0033 资源清单 12 约束①）；刚启动的 task 多久之后列得出，实测的 14 个样本都在 4 秒之内（实测项 27），样本不构成上界。决策二第 1 条里启动请求晚于期限的 job，run 未结束时与别的执行中的 job 一样由 job 到点停止处理，各种 task 状态下做什么只在 0034「job timeout」节写全（执行方式表 cloud 后台一行与「到点不早于 deadline」条②）；到点停止没有停到的 task 交给上面的清扫。这两种情形多出的执行时间里，task 可能已对被测应用做了操作、往桶里传了不完整的产物。job 与 run 记什么不在本条定：推进一侧写 job 终态的规则在 0034 机制三「收尾各步的先后与之后会不会变」的步骤，处置与后端到期结束的结束写在决策七。不为漏掉的 task 另设一次延后的清扫（被拒方案「清扫之后隔一会儿再清扫一次」）。

   何时清扫有三条规则：
   - ① 运行态不存在或已结束，即清扫：run 标识带随机尾、不会复用，不存在的 run 没有要保护的记录。推进 Lambda 的各入口遇到这样的 run 都走到这一条（本决策「落实时」一段），所以没停到的 task（如 run 结束之后才启动的，0034 机制三「run 级状态只进不退」条①）由此后带到这个 run 的调用去停，停不停得到取决于什么见本条开头。
   - ② 期限加 300 秒那一次确认已过那个时刻之后（时刻由读得出的期限算出），不论处置的结果是什么，都清扫一次：各 job 的截止时刻以期限封顶（决策二第 2 条），依据只是时间。运行态读不出的 run 不处置，这一次只取提交记录头里的记录格式版本与期限确认时刻（本决策「落实时」一段），它的 task 由这一条清扫（停掉这一次列得出的；前提是提交记录顶层的期限读得出、记录格式版本是后端的，这一次触发建成、调用成功）。
   - ③ 得知 run 已结束的那一次调用当场清扫：闸读到已结束；error 变体写成之后，或它重读到已结束（别的写方先使 run 成为终态）；推进步骤返回这一次写成了终态（生成报告之后）或 run 已结束；期限那一次重读到已结束；后端到期结束写成（生成报告之后）或读到已结束。使 run 成为终态的那次写另经流（新映像的状态分组不是 `live` 的 STATE 条目）触发 `kicker` 一次，过闸读到已结束即清扫（读到未结束只会出自记录被人改动，只记一行日志，不推进、不清扫）；过滤命中的只有这一次写（终态之后运行态不再有写，决策五），处置方的结束写、推进器自己的结束写与终态写、后端到期结束都经这里。当场清扫与流上的这一次两条都要：期限加 300 秒那一次是这个 run 最后一个按计划到来的触发，它结束 run 时还留着的恰是自己不结束、也不出事件的 task；它不当场清扫而只靠流上那一次时，那条记录被丢弃就没有人清扫。
   - 流事件按批调用，同一批里按 run 去重；跨批的事件、迟到的事件与定时触发可能再次清扫。
   - 失败与批的隔离：两个推进 Lambda 处理一批流记录时，每条记录（每个 run）各自处理，任何一条的失败不打断同批别的记录，全部处理完之后只要有失败，就让这次调用失败、由流重试；一次调用在 Lambda 的限时之内没有处理到的记录（排在前面的记录用完了时间），随这次调用的失败（超时）由流重试。重试时已做过的记录再做一遍，各步幂等、结果不变。一批最终被丢弃时，批里的记录未必都已做完：出错的那条之外，每次调用在限时之内没有处理到的也在其中。记为失败的：读运行态、读运行定义、结束写（含 error 变体）、推进步骤里的读写、建 run 级定时触发、清扫、处置时的读写记录失败；报告生成、防御性超时扫描与推进里为 job 建到点触发（尽力而为，0034「job timeout」节「best-effort 边界」条）的失败隔离在调用之内，运行态读不出不是失败、只记日志。定时触发的调用只带一个 run：上面记为失败的各项，与这次触发本身要做的 job 到点停止（job 的到点触发、期限那一次对执行中的 job 做的列 task、停 task、补写退出记录）里的失败，让这次调用失败，由 AWS 的重试再调用；隔离在调用之内的三项与运行态读不出不算。批大小与重试次数见 0033 资源清单 13。

清扫会不会打断还在做最后上传的 task，取决于 run 怎样结束。正常结束的 run，job 的退出记录来自 task 停止的观察链时，这个 task 在 run 结束之前已经停止，清扫不会打断它的最后上传；退出记录是补写的未知退出时（0034「job timeout」节），task 可能还在执行，它的 job 已按到点处理，由清扫停掉；列 task 的调用可能仍返回刚停止的 task，对它们没有要停的。run 由结束写结束时（别的格式写出的 run 或运行定义不可用时的 error 变体，用户一侧的处置与后端到期结束），执行中的 task 可能已发出最后的结果、正在上传其余的产物（worker 先发 `scope_done` 再上传），它的期望状态仍是运行中，清扫会停掉它，产物可能不完整。清扫不写 runs 表，不会形成「清扫引出写、写再引出清扫」的回路；它停掉 task 引出的退出事件、终态之后迟到的事件会带来更多调用，性质不同。

**落实时，后端各入口先过同一道闸**：reconciler 处理 events 表流的记录，`kicker` 处理两种流记录、job 到点停止的触发与两次 run 级触发，都先做下面三步，先于各入口的一切动作。清扫因此排在「已结束的 run 不再推进」之前，run 已结束之后迟到的事件也走得到它，不能只加在推进里；job 到点停止的入口也先看 run、再看 job。前两步先看运行态的公共部分、再看提交记录的头：公共部分与提交记录里记录格式版本的位置都属跨版本不变的约定（[0037](./0037-distribution-and-packaging.md) 决策 7），别的格式写出的 run 同样认得出、结束得了；运行态的其余部分与整份运行定义只按后端自己的格式读，头里的记录格式版本是后端的才读。
- 第一步，强一致读运行态，先只读其中的公共部分。读取本身的错误原样抛出，记为这条记录的失败（第 2 条「失败与批的隔离」）。
  - 运行态不存在即清扫（第 2 条①），不读提交记录、不写。
  - 公共部分读不出即记一行日志，不写、不推进，除下面期限加 300 秒那一次之外不清扫，同批别的 run 照常。公共部分在各个格式里形态相同，系统自己的每次写都整条原子落下，所以读不出只会出自人为改动或环境损坏，各入口不为它另设分支（期限加 300 秒那一次的清扫是第 2 条②对每个 run 的同一条时间规则）。这与用户一侧的 `unreadable` 是同一口径：读不出就无从做条件写，也分不清 run 是否已结束，清扫可能停掉仍在执行的 task。期限加 300 秒那一次遇到它时不走后面各步：结束写要以读得出的运行态为条件，error 变体与处置都写不成，所以只读提交记录头里的记录格式版本与期限（`deadline_at`），记录格式版本是后端的、期限读得出时，按第 1 条「到点的处理」一项确认已过期限加 300 秒，确认之后清扫（第 2 条②）；头不在、期限读不出，或记录格式版本不是后端的，只记日志，不解读别的格式的记录；读取本身的错误同上。
  - run 级状态已结束即清扫。
  - 未结束即进第二步。
- 第二步，强一致读提交记录的头（0030 决定六）。读取本身的错误原样抛出，记为这条记录的失败。
  - 头不在，或头里的记录格式版本不是整数：做结束写的 error 变体（[0031](./0031-job-lifecycle-states-and-severity.md) 决定三「结束写」小节），原因取「提交记录不完整或形态不对」那一句，之后清扫。
  - 头里的记录格式版本不是后端的（缺这个属性读作 0）：做结束写的 error 变体，原因取记录格式版本不合的那一句，之后清扫；不取 jobs 对象，也不按后端的格式读运行态的其余部分。
  - 头里的记录格式版本是后端的：按后端的格式读运行态的其余部分，读不出时与第一步「公共部分读不出」同样处理（只记日志，期限加 300 秒那一次确认已过之后清扫）。读得出时取 jobs 对象、读整份运行定义，不可用即做结束写的 error 变体，之后清扫：定义违约（含头顶层的记录格式版本是后端的、而 `meta_json` 里的副本不是：两处按 0030 决定六恒同）与 jobs 对象已不在取「提交记录不完整或形态不对」那一句，缺任务定义修订取没有记下 worker 镜像的那一句，运行定义记下的 worker 协议版本不是后端的取协议版本不合的那一句。jobs 对象已不在凭哪种错误认出，见 0030 决定六「jobs 对象取不到时」一项；取回 jobs 对象时别的错误与读头的错误一样原样抛出，记为这条记录的失败。
  - 各句原因的写法见 0031 决定三「结束写」小节说明表下。结束写本身的失败原样抛出。
- 第三步，其余装配之后推进或处置：要推进的入口另装配起 task 用的部分，后端到期结束不推进、不装配它们。

读量不因这一次序增加：已结束的 run 只读运行态、不读头；未结束的 run 读头与取 jobs 对象各一次，与读整份运行定义相同（下「每个 run 的代价」）。别的格式写出的未结束 run 不等到期限，第一次被带到就做 error 变体的结束写并清扫（run 的终态以第一笔使它成为终态的写为准，与别的写方的先后见 [0037](./0037-distribution-and-packaging.md) 决策 7「后端遇到别的格式写出的 run」里「与别的写方的先后」）；期限加 300 秒的按时间清扫只管运行态读不出、无从结束的 run。被结束之后它在后端是已结束的 run，此后带到它的事件只引起清扫；error 变体之后不生成报告（0034 机制三「不经推进步骤的收尾」）。后端回滚到写出这个 run 的那个版本之后，已被结束的照旧是已结束；回滚之前由新版本建的、未结束的 run，回滚之后的后端带到时按同一规则结束，这个方向不保证做到（[0037](./0037-distribution-and-packaging.md) 决策 7「后端遇到别的格式写出的 run」里「保证的范围」）。

退出观察者不走这道闸：它只写退出记录，不读 runs 表，按后端自己的格式写，数据版本不同时不保证对方读得出（[0037](./0037-distribution-and-packaging.md) 决策 7「写读次序」）。用户一侧的处置方也不走：它们没有 ECS 的权限，也不清扫（被拒方案「由 `settle-runs` 自己停 task」）。

用到的权限（列 task、停 task、建定时触发）都在推进 Lambda 的角色上，runs 表开流；两次定时触发所在的 schedule group 与名字、kicker 流上的两个过滤与授权登记在 0033 资源清单 13、15 与 IAM 一段。每个 run 的代价：2 次建立一次性 schedule 与 2 次 Scheduler 调用（一次性 schedule 完成之后自动删除，不长期占用账户配额）；3 次 `kicker` 调用（流上的终态写与两次定时触发），正常结束的 run 到点时早已结束，每次只有一次强一致的运行态读与一次列 task；使 run 成为终态的那次调用当场清扫，多一次列 task，终态之后迟到的事件带来的调用各多一次；到期仍未结束的 run，后端到期结束读两次提交记录（闸与处置各一次），只在这种少见的 run 上发生。退出观察者不读 runs 表，云端 `status --wait` 不调用 `kicker`。多个 run 的事件可能合在一次 Lambda 调用里。期限那一次不并进期限加 300 秒那一次：它让内容已完整的 job 经协作停止保住判定，后端到期结束只能把它们记成「没有结果」，两者结果不同（时限前提见第 1 条「期限那一次」一项）。

这样两个后端在到期时的停止与 run 的结束上是同一种表现（job 与 run 记什么按结束写，0031 决定三「结束写」小节）；差别只在由谁来停：本机是执行方与 worker 自己，云端是后端（本决策第 1、2 条）。停不到的情形见「边界与已知局限」。

### 十、job 的墙钟预算有一个产品定的上限

- 一个 job 的墙钟预算最长 7200 秒（2 小时）。它是产品的设定，放在 core，对所有目标是同一个数。
- 引擎与平台各自的限制是另一回事，归引擎：桌面目标的浏览器会话，平台允许的最长存活时间是 28800 秒，两个引擎的 worker 把会话的存活时间设为 job 预算加 120 秒；设备目标的会话上限由引擎在能力自述里报出，现在是 8880 秒。core 不抄这些数。两者之间只有一个关系：产品上限不大于任何一个引擎对任何目标能支持的最长预算，由测试守住（设备对照能力自述里的上限，桌面对照会话存活时间的封顶值减 120 秒），引擎那一侧的数哪天低于产品上限，测试即失败。引擎自己的检查保留，作为最后一道。
- `@timeout:N`（[0019](./0019-feature-tags-scope-and-engine.md)）与显式给出的 `--default-job-timeout` 正值超过上限时，计划阶段报错、以退出码 2 结束，与设备目标低于下限是同一处理；桌面与设备目标相同。
- `--default-job-timeout` 给 0 或负数，对任何目标都表示取这个上限。什么都不给时的缺省是桌面 300 秒、设备为获取预算加 900 秒。设备预算的下限（获取预算加 180 秒，获取预算最大 3600 秒）最大是 3780 秒，在上限之内。
- 上限检查与给 0 的含义都落在 [0025](./0025-plan-module-feature-to-jobs.md) 的取值次序之后：scope 里有场景标了 `@timeout` 就用标的值，否则用显式给出的缺省，都没有才按目标补缺省。被检查的是这样解析出的有效预算；被 `@timeout` 盖住、没有生效的缺省值不检查，给 0 或负数也只作用于没有标 `@timeout` 的 scope。
- `Job.timeout_s` 恒为正数。运行定义里这个键恒为正数，读端把空预算当作违约拒绝；调度与推进里没有「没有预算即不设截止时刻」的分支，超时说明没有无预算时的回退写法，云端每个 job 都建超时触发。缺 job、缺认领时刻、能力自述没给上限这几种含义不同的判空保留；计划阶段的空值只表示「没有显式给出缺省」。
- worker 协议里 job 输入的预算可以为空，两个 worker 的空值分支与规范样本保留，core 不产出空值。不把协议也收为恒正：那要两个方向一起升协议版本，使用者自建的 worker 变体都得重建，为去掉一个不会出现的取值不值得。

理由：

- 「不超时」实际上也不是无限。job 没有预算时，Midscene 的 worker 不向平台传会话的存活时间，平台缺省是 3600 秒（最长可设 28800 秒）；Nova 的 worker 不向 SDK 传这个参数，SDK 自己取 3600 秒写进请求。两条路径的结果都是一小时：不超时的桌面 job 不会被停，它的浏览器会话一小时后被平台关掉，之后的 AI 步骤全部失败。有上限时预算恒有值，会话的存活时间按 job 预算加 120 秒随预算取值，给 0 的使用者能用到的是 2 小时，比不超时实际得到的一小时长。
- 每个 run 都有期限，处置的期限一条（决策六）对每个 run 都可用：没有期限的 run，本机只能靠试拿锁处置，云端没有任何一方能处置它。
- 云端的 run 另有后端到期结束（决策九第 1 条，含前提）：推进停住、又恰好有 job 自己不结束时，它是后端一侧的出口。这不是费用的硬上界：处置受决策九里触发、列举与停止各自的边界约束。

代价是不能有超过 2 小时的单个 job（浏览器会话最长撑约 8 小时、设备引擎允许 8880 秒）。上限是产品的选择，不是引擎的极限；以后要放宽只改 core 的这一个数，前提是不超过各引擎能支持的最长预算。

## 边界与已知局限

**三种组合的对照**：三种组合在各情形下的结果，每格只写结论，规则在所指处（「说明表」指 0031 决定三「结束写」小节里的那张）。

| 情形 | job | 三种组合 |
|---|---|---|
| 被期限截断 | `aborted`、期限那句（0031 决定一） | 相同；到了期限加 300 秒推进器还在收尾时见决策六「期限加 300 秒按墙钟判断」一条 |
| 推进器中断（本机进程退出；云端一次调用失败） | 本机不续，被处置时按说明表「锁拿到了」一行（谁能处置见决策八）；云端可以由流的重试与之后的触发接着推进，推进链断开时怎样结束见决策九第 1 条（含前提） | 不同，出自 0034「推进器与触发源」与决策六 |
| 推进停住，按期限一条被处置（决策六） | 按说明表「已过期限」一行 | 被处置时相同；谁能处置见决策八，云端后端的到期结束见决策九第 1 条（含前提） |
| 保存明细失败，重试成功之前没有被处置 | 照常记下 | 相同 |
| 保存明细一直失败 | 本机重试 3 次之后推进器退出，云端可以由流的重试或之后的触发再做；本机推进器退出之后、云端推进链断开时，同「推进器中断」一行 | 不同，出自 0030 决定三 |
| 运行定义不可用、run 由别的格式写出 | 云端推进器读不到可用的运行定义、或 run 由别的格式写出时，做结束写的 error 变体，未结束的 job 记 `error`（0031 决定三「结束写」小节；别的写方先使 run 成为终态时保持它的结果，0037 决策 7「后端遇到别的格式写出的 run」里「与别的写方的先后」）；本机推进不受影响，提交记录不存在或内容不合法的 run 被处置时只剩试拿锁一条（决策六），处置之后没有报告（决策七） | 推进时只有云端后台有这种情形：本机的两个宿主推进时用自己生成的那份运行定义、不从记录读回（同一小节），别的格式写出的本机 run 由建它的那个发行版本推进（与云端结局不同，属方式固有的差别：0037 决策 7「后端遇到别的格式写出的 run」的「本机」条） |
| 隧道（给了 `--expose-local`） | 宿主中途没了：本机的宿主就是推进器，按「推进器中断」一行（0035「边界与不变量」里「本机关机或宿主进程崩溃时隧道随之消失」一条）；云端「隧道随之消失，云端的 run 照常推进，之后要访问被测应用的 job 以导航失败（AI 报错形态）告终」（同一节「云端的守护进程没了」一条） | 隧道随宿主退出而消失、公网入口在边缘到点关闭，这两条三种组合相同（0035 决策 3「寿命」「边缘到点拒绝」）；宿主中途没了时不同，出自 0034「推进器与触发源」（云端的推进器不在本机） |

其余情形三种组合相同：job 得出结果或用完预算（终结函数，0034 机制二）、到期有 job 没有启动（`skipped`，决策二第 3 条）、启动失败（`error`，决策二后台推进条「时刻」）、终态之后到达的结果（不采用，0031 决定一·补）。run 的状态都按 0031 决定三取；前台才有的几样见 0016 决策 A。

run 到终态之后各组合下还会发生什么，逐格列出，不作统一的概括：

| | 本机前台 | 本机后台 | 云端后台 |
|---|---|---|---|
| run 的终态被改 | 不会 | 不会 | 不会 |
| 认领并启动新的 job | 不会：认领与重试前的检查被拦 | 不会：认领被拦 | 不会：认领被拦 |
| 检查已通过、启动还没有完成的 job（调用未发出、调用中、句柄未返回；首次启动与重试都算） | 会启动；推进器下一次写运行态时发现 run 已结束，对它发停止 | 会启动；推进进程发现 run 已结束之后退出，worker 见下 | 会启动（task 的启动不随记录分出先后，0034 机制三「run 级状态只进不退」条①）；由此后带到这个 run、在它列得出之后到来的调用清扫（决策九第 2 条开头）；推进 Lambda 的超时小于停止认领的提前量加 300 秒（0033 资源清单 12 的约束），所以按认领一方的墙钟读数，期限加 300 秒那一次的计划时刻之前启动请求已经发出（响应未必已经返回），那时这个 task 是否已经列得出没有保证；都没有停到时没有人停 |
| 已经在执行的 job | 推进器还在时由它停止；它被暂停或卡死时要等它恢复；它已不在时 worker 见下 | 推进进程还在时发现 run 已结束之后退出；worker 见下 | run 结束之后交给后端的清扫（决策九第 2 条）；期限那一次定时触发对它做什么、成立的前提，见决策九第 1 条；期限加 300 秒那一次确认已过那个时刻之后，不论处置的结果都清扫一次（决策九第 2 条②）；之后才出现的 task 同上一格 |

推进器已不在、又没有别的组件去停时，留下的执行不受期限约束：

- 本机 worker 在推进器退出之后靠核验所属进程是否还在来自行退出（0024）。这个核验有已知的失效情形：worker 核验的是传给它的所属进程 pid，所属进程成了未被回收的僵尸时这个 pid 仍然查得到；worker 经包装进程启动、或所属进程在核验启用之前已经退出时，没有「直接父进程变了」这条辅助线索可用，核验可能一直不触发。所属进程的 pid 在被发现消失之前被复用时，它也被误认为还在。生命期锁不受这两种情形影响（已退出未回收的进程已释放锁，决策三），worker 的核验受影响，所以会出现 run 已被结束、本机 worker 仍在执行的情形。
- 本机推进器被暂停期间，它启动的 worker 照常执行、没有人按截止时刻停它们。
- 云端 task 自己不会因为 run 结束而停：worker 不按预算计时自停（0034「job timeout」节）；浏览器会话与设备会话各有存活上限，但会话到期不保证 task 退出，确定性 step 可以一直等下去。所以由后端来停（决策九）。推进停住时，已经启动的 task 各自把手上的 job 执行完就退出；留下来的只有自己不结束的 task（卡住的 step、一直等待的确定性 step），对它们的出口是 job 到点停止（决策二第 2 条）与后端到期结束（决策九第 1 条，含前提）。后端停不到的有两种：清扫时没有被列到、此后又没有做清扫的调用在它列得出之后带到这个 run 的 task（哪些 task 会漏、清扫在哪些调用里做、停不停得到取决于什么，见决策九第 2 条开头）；流与定时触发整条链都失效的时候。前一种按计划到来的最后一次是期限加 300 秒那一次（它确认已过那个时刻之后不论处置的结果都清扫一次，决策九第 2 条②）；那一次停得到它的前提有一项不成立（各项见决策九第 1 条「前提」一项与第 2 条开头），或运行态读不出而提交记录里的期限也取不到（含头里的记录格式版本不是后端的，无从确认时刻）时留下。

处置只改记录（决策七），自己不停任何执行；表里的停止，本机后端是执行方与 worker 自己做的，云端后端另有后端在 run 结束之后的清扫（决策九第 2 条）。

其它局限：

- 有人改动、删除 run 目录里的文件，不在防护之内。
- 建 run 中途被强杀时，暂存目录（以及这次新建的空报告目录）留在原处，暂存目录由不给 run 标识的 `settle-runs` 清理（决策八）。掉电与内核崩溃不在覆盖范围（原子写不做 fsync，0030 决定三），之后可能留下内容为空或截断的 run 目录，列举时是无法读取的一行。
- 运行态本身读不出的 run、记录格式版本与本机不同的 run 与 run 目录不过边界检查的 run，本版本的处置方都不结束它们（决策六、决策四），它们留在 `list-runs` 里（云端别的格式写出、未结束的 run 由后端结束，见下一条）；各入口怎样说明见决策八。云端运行态读不出的 run，后端同样不推进、不处置，它仍在执行的 task 由期限加 300 秒那一次清扫（停掉那一次列得出的；提交记录顶层的期限读得出、记录格式版本是后端的时，决策九第 2 条②）。
- 云端别的格式写出、未结束的 run（提交记录头里的记录格式版本不是后端的），后端在第一次带到它时做结束写的 error 变体并清扫（决策九「落实时」一段第二步），不等到期限；记录格式版本与它不同的处置方不结束它、给出 `other_version`（决策八），与它相同的处置方期限加 300 秒之后仍可按处置的规则结束它，两者之中使 run 成为终态的那一笔为准（[0037](./0037-distribution-and-packaging.md) 决策 7「后端遇到别的格式写出的 run」里「与别的写方的先后」）。清扫停掉期望状态为运行中的 task，其中可能有正在做最后上传的，产物可能不完整（决策九第 2 条之后「清扫会不会打断还在做最后上传的 task」一段）；被停的 task 也可能还没到它的截止时刻，换来的是不多计费。这类 run 的来路见 [0037](./0037-distribution-and-packaging.md) 决策 7「后端遇到别的格式写出的 run」的「这类 run 的来路」条；本机由建它的那个发行版本执行完、云端由被升级之后的后端结束，这一差别为什么属两种执行方式固有的差别，见同一节的「本机」条。
- 同一条事件可能让推进的逻辑执行不止一次，各步靠先读记录与带条件的写保证重复执行不改变结果。一次调用在平台的重试之后仍失败时那条事件被丢弃：丢掉的是建 run 时 STATE 新建的那条流记录时，两次 run 级的定时触发可能都没有建成；首轮推进不以建成为前提（决策九第 1 条），已经做过的，job 照常经 events 表流与 job 级的定时触发推进；后端一侧不再有按运行期限的那两次触发，此后推进停住的 run 由用户一侧的处置方在期限加 300 秒之后结束（决策六、八）；jobs 对象已不在的 run 除外：用户一侧取不到 jobs 对象时不处置（[0030](./0030-realtime-persistence-seam.md) 决定六「jobs 对象取不到时」一项），这样的 run 在没有任何调用带到它时没有一方结束，留在 `list-runs` 里。其余情形由到期的定时触发收尾。不配失败去向、不加告警：这类重试只在产品有缺陷或平台异常时出现，缺陷按修缺陷处理。
- runs 表流的事件源映射在部署中新建或更新的那一刻可能漏掉记录：映射的起始位置取最新（`LATEST`，[0033](./0033-iac-aws-backend-and-composition-wiring.md) 资源清单 13），AWS 文档写明建立或更新映射时对流的轮询是最终一致的、可能漏掉事件。漏掉的若是一个 run 唯一的那条 STATE 新建，这个 run 没有冷启动（一个 job 都不认领），也没有两次 run 级定时触发，后端再没有东西带到它，由用户一侧的处置方在期限加 300 秒之后结束（决策六、八）；jobs 对象已不在的 run 除外，同上一条。这次部署同时改了记录格式版本与云端后端接口版本、而这个 run 由持旧值的命令行工具写下时，不保证有处置方结束它，这样的 run 可能一直显示未结束（[0037](./0037-distribution-and-packaging.md) 决策 7「后端遇到别的格式写出的 run」里「保证的范围」）。只在新建或更新映射的那次部署里出现（0037 决策 7「部署进行中」）；只改过滤条件的更新有没有这样的投递空窗，部署之后核（[0037](./0037-distribution-and-packaging.md) 实测项 7）。
- 处置写成之后、报告生成之前进程被结束（不经解释器的信号，或没有处理器的 SIGTERM、SIGHUP）时，记录已是终态、没有报告，之后谁也不补：报告只由写成的一方生成（0027），再执行 `settle-runs` 得到 `already_finished`。与推进器在终态写之后、报告之前中断是同一取舍（0034 机制三「run 级状态只进不退」条④里的「代价」）。
- 处置的结束写要取运行态的短锁 `.runstate.lock`：另一个写入方停在这把锁内的读改写之中时（例如推进器恰在那几毫秒里被暂停），结束写一直等它，这期间中断只被记下（决策八「中断」）、不起作用，SIGTERM 同样，只有 SIGKILL 能结束这个命令，要等那个进程恢复或被结束（实测：持锁方放开之后结束写写成，随后才按中断结束）。标准输出写不出去时（读的一方一直不读）同样：输出在处理器还装着时写完，写不完就一直等。前台 `run` 收尾时的中断处理同样不打断这两种等待。命令结束时恢复原来的信号处置（先恢复 SIGTERM、后恢复 SIGINT，恢复途中到达的 SIGINT 不会使 SIGTERM 留在只记标志的处理器上），恢复之后到进程退出之间的几条字节码里收到的中断不在上述做法之内。处理器装上之前同样不在其内：两个处理器先后装上（先 SIGINT、后 SIGTERM），各自装上之前到达的那个信号按原来的处置（SIGTERM 是进程直接结束、没有说明）；这时命令还没有改动任何记录。
- 云端多次调用重叠推进时，各记录靠什么分出先后见 0034 机制三的开头。

## 被拒方案

- **期限只当推定阈值、执行方不遵守**：见决策二的理由。由此还要引出两条补丁式的规则（推进器还在时不处置；真实结果覆盖处置写下的终态），都随它一起不取。
- **真实结果覆盖处置写下的终态**：终态之后再变对上层是错的行为，见决策五。
- **靠期限加余量证明执行已停**：尾段与余量都是预算，时钟也可能有偏差，证明不了。期限之后结束一个 run 的安全由「终态不可变、认领以未结束为条件」承担（决策五）。
- **到期时把执行中的 job 一律改判**（不看内容是否已完整）：违背 0034 机制二「内容完整后不再仲裁」，同一个 job 还会因为停止请求到得早晚在三种组合下得到不同结论。
- **发出启动请求之前再查一次停止认领的时刻**（已过即不启动）：它只能缩小认领与启动请求之间的间隔，启动请求本身也有耗时，期限之后才开始执行的 task 照样会有；这样的 job 已按到期时还在执行处理（决策二第 1 条）。
- **期限放运行态记录的顶层**：期限是 run 的规则，放在只由 adapter 读写的附加属性里，core 的调度与推进就得绕开模型去拿它。
- **期限不存、读时现算**：停止宽限不在任何记录里；算式随 CLI 版本变化时，同一个 run 在不同版本下会算出不同的期限，而它必须是各执行方与所有读者共同认的那一个时刻。
- **使用者单独配置 run 级期限**（0034 预留的 `--default-run-timeout`）：期限要保证不早于各 job 预算能合法用到的时刻，单独配置就得再定义它与 job 预算冲突时谁让谁；现在只由 job 预算推出。
- **让使用者替某个 run 下一个判定**（如把它记成 `passed`）：判定不靠使用者担保，结果只来自执行与记录。以后的取消命令结束一个 run 时走结束写（决策八），不替任何 job 下结论。
- **心跳或租约**：续写本身也会被暂停与时钟偏差打断，判「过期」仍要一段时长。见「重议闸门」。
- **读对方进程的信息**（pid 空间标识、进程启动时刻、进程状态）：只看 pid 是否存在（`os.kill(pid, 0)` 与 `os.killpg(pgid, 0)`）在 pid 被复用或进程是僵尸时都判为存活（实测 macOS 与 Linux 上 `os.kill(pid, 0)` 对已退出、未被回收的进程仍然成功）；加上 pid 空间标识与启动时刻之后，Linux 上连续五轮复核每轮都出现新的反例（pid 命名空间、同一滴答里启动的两个进程、时间命名空间的偏移、`/proc` 被换掉或预先绑定挂载），macOS 与 Linux 各要一套取法（macOS 的 `ps -p <pid> -o lstart=` 输出随本机时区变，必须固定 `TZ=UTC` 与 `LC_ALL=C`；Linux 读 `/proc/<pid>/stat`，同一台宿主上容器里读到的 `boot_id` 与宿主相同、pid 命名空间不同）。引入 psutil 也不解决：它在 Linux 上给出的启动时刻是由开机时刻换算的墙钟浮点数，系统时钟被校正后同一进程前后读到的值可能不等，按「不等即被复用」处理会把活着的进程判成已不在。锁把同一个问题交给内核回答。
- **机器标识**（含主机名）：主机名会重名（克隆的镜像、容器、不同网络下的同名机器）；跨重启稳定的机器标识会随镜像克隆被复制，认错的方向是把仍在执行的 run 结束。锁只在同一个内核里有意义，不需要它。
- **在 run 目录之外另放锁文件**：锁与 run 目录分处两地，run 目录被移动、复制或换报告目录时两者对不上，还要另定命名与清理。
- **改用 run 目录里的锁文件**（写方式打开）：为网络盘换它也不干净。Linux 的 NFS（同机回环挂载）上没有写委托时四个挂载两两互斥，持锁方有写委托时 v4.2 不共用超级块的挂载之间不互斥，服务端本地路径与各挂载之间两种情形下都不互斥；文件锁的非阻塞试拿有的 10 到 87 秒才返回（服务端刚启动、另一版本的挂载持锁时），有的到 30 秒上限、一次到 6 分钟以上仍未返回（进程被杀为止）。APFS 与 Linux 的 ext4、tmpfs、overlay、绑定挂载上两者各项行为相同（锁文件没有测 `multiprocessing`），目录锁少一个文件，也没有锁文件删掉重建、新旧两份各被一方持有的问题。
- **启动时自检**（拿到锁的一方再开一次 run 目录试取），以及凡取锁之后读回的做法：Linux 的 NFS（v4.2、v3，同机回环挂载）上对只读打开的目录取排他 `flock` 不报错、同一进程再开一次也被挡，锁却只在共用超级块的挂载之间互斥（nosharecache 挂载、另一版本的挂载、服务端本地路径都拿得到）；它只查得出同一进程两次打开是否互斥。
- **macOS 只看本机标志**（`fstatfs` 的 `MNT_LOCAL`）：带这个标志的都放行，含没有照决策三理由实测过的类型（实测 HFS+ 与 FSKit 挂载的 FAT 都带）；两个平台用同一条规则，只放行实测过的类型。
- **用路径是否存在的判断代替打开时的错误码**（找报告目录最近一层已存在的上级时）：权限错误会被读成不存在（`Path.exists` 一类判断的读法还随 Python 版本而变），越过这一层去判断上级，把权限问题报成文件系统不合要求。
- **以 run 标识直接建目录、取锁之后再写，残留按内容就地清理**（没有运行态、只有运行定义与锁文件的目录，锁拿得到时删去）：凭内容分不清「建到一半」与「有人删了运行态的完整 run」（里面有 `jobs/` 与产物），会误删使用者的数据；建目录到取锁之间同样有锁还没取上的空档。改由名字区分，清理方只认暂存目录的名字形态（决策三「谁在何时试拿」）。
- **只跳过、不清理暂存目录**：残留随每一次建 run 中途被强杀只增不减、没有出口，与本篇要给停住的 run 出口是同一种缺口（「背景与问题」）。
- **建 run 时顺带清理**：每次建 run 都要列一次报告目录，`run` 与 `submit` 多出删除别的目录这一副作用；清理放在由使用者显式执行的处置方 `settle-runs` 里（决策八）。
- **清理方只认暂存目录的前缀**：会删到使用者恰好以这个前缀起名的目录；前缀之外再核名字的形态（决策三「谁在何时试拿」）。
- **只看不删的清理方不试拿、只列出候选**：给不出「被持有」与「会删除」的区别。试拿的代价是建 run 的一方恰在它持锁的那一瞬取锁时换名、多留下一个空暂存目录，由下一次不带 `--dry-run` 的清理删去（决策三「谁在何时试拿」）。
- **清理暂存目录的结果只给一行计数**：看不出哪一个没删、为什么没删。**暂存目录删不掉时以退出码 2 结束**：理由见决策八「`settle-runs`」一条的退出码。
- **先改名、再取锁**：改名到取锁之间，完整的 run 已以标识出现而没有锁，`status --wait` 或 `settle-runs` 试拿必然拿到，会把正在启动的 run 记成「进程已退出」；建 run 的一方随后取锁反而得到「已被持有」。
- **暂存目录放在报告目录之外**（如系统临时目录）：改名跨文件系统即失败（`EXDEV`），对暂存目录的边界检查也不再等于对 run 目录的。
- **建 run 的一方在暂存目录上得到「已被持有」即以退出码 2 结束**：持有它的是清理方，使用者会看到一个与他无关的竞争造成的锁错误；换一个名字即可（决策三「谁在何时拿」）。
- **保证建 run 失败之后一定删掉自己的暂存目录**（按已知的文件名直接删、不枚举，或预留一个描述符专供清理）：删除总要某种资源，也总可能因别的原因失败（权限被改、读写出错），写成保证时每一种让删除失败的条件都是它的反例；实测进程的描述符所剩无几时，另一个线程占去最后一个名额，枚举这一层即失败。留下的暂存目录已经有清理方这一个出口，与进程被强杀留下的相同，不为极端情形再加一层保障；按已知的文件名删还要让建 run 的入口知道调用方写了哪些文件。
- **建 run 时 fsync**（改名前后 fsync 两个文件、暂存目录与报告目录）：运行中每一次运行态的原子写同样不 fsync，只在建 run 时做覆盖不了别的写，与 0030 决定三「不做 fsync」的取舍相反。
- **在建 run 的入口里逐步收拾异步的中断**（每一步之前先记下名字、改名之后按文件系统里的事实判断是否已建成）：系统调用已经成功而结果还没有记下的空档补不完，实测在打开之后记下之前、复制描述符之后关原号之前、改名之后交给持有者之前被中断，各留下一个没有归属的描述符；先记下名字再建目录时，中断还会让收拾的一步按名字删到别的进程的暂存目录。改为不让中断进到这一段（决策三「建 run 不被中断打断」）。
- **把一步包进推迟 SIGINT 的区间、在区间外接住中断引起的异常**（建 run 的那一次调用、每一次处置、输出各包一个）：区间的入口与出口各有几条字节码不在保护之内，接住异常的一方分不清它来自区间结束时补发的那一次、还是进入区间之前就到的那一次。实测三处：前台建 run 之后连按两次 Ctrl-C，第二次落在区间入口，说明说已因中断记为已结束而结束写没有做；`settle-runs` 的输出被入口处的中断整个略去，处置却已写成；建 run 的保护区结束之后到装上执行期间的处理器之前被打断，打出回溯、run 停在 `pending`。改为整个命令期间只用一个只记标志的处理器，没有异常可接。
- **装处理器期间屏蔽 SIGINT 与 SIGTERM**（两个都装好再解除，使 SIGINT 的处理器已装上、SIGTERM 的还没有装上的那几条字节码里到达的 SIGTERM 也被记下）：信号落在处理器装上之前还是之后，分界本来就是任意的一刻，装上之前到达的 SIGTERM 落在哪一条字节码上都是进程直接结束、什么都没有改动（「其它局限」）；屏蔽只把这条分界从「SIGTERM 的处理器装上」挪到「开始装」，使用者看到的结果不变，多出一层屏蔽字的保存与恢复。
- **fork 闸门**（模块里放一把可重入的线程锁，登记成每次 fork 之前取、之后在父进程里放、在子进程里重建；建 run 的那一次调用全程持着它，别的线程的 fork 要等到钩子登记之后才发生）：它能消除决策三「已知的间隔」（实测加上之后同样的 150 个 run 没有一个仍被持有），现在不取。理由：这个间隔现在不可达，漏过去的后果是处置推迟到期限加 300 秒、不是错误的记录；闸门是钩子之上再叠的一层，它的登记在模块导入时发生、撤不掉，凡导入这个模块的进程每一次经解释器的 fork 都要过这把锁，线程锁与 fork 合用又有两处必须处理对的地方（建 run 的线程自己 fork 时不能锁死自己，子进程里要换一把新锁）。何时再议见「重议闸门」。
- **用扫描生产代码的静态测试守住「只经 exec 起子进程」**（先按拒绝清单逐个点名危险写法，后按放行清单只放行认得的入口与命令）：扫描按写法认，而同一个调用有许多种等价的写法，三轮复核各找出几种认不出的直接写法（`posix` 模块的同名函数、一次导入全部名字、`preexec_fn`、数字写的 `fcntl` 命令、经 `__call__` 调用入口），清单越补越长仍拦不全。它防的是以后的改动；漏过去时子进程带着锁，处置要等到期限加 300 秒。改为由持有者登记 fork 之后关掉子进程里那一份的钩子，不依赖 code 怎样写（决策三「不被子进程继承」）。只禁 `close_fds=False` 的更窄的一种同样不取：实测它单独不延长持有（锁描述符本身不可继承）。
- **`submit` 建 run、拿锁，启动后台推进进程时把锁交给它**：由后台推进进程自己建 run 的理由见决策三「本机后台由后台推进进程自己建 run」一条；回报通道本来就要有，交接省不下什么；交接期间锁在不是推进器的进程手里，它在关掉自己那一份之前被暂停时，推进进程退出了也拿不到锁，处置要等它关掉那一份或退出。交接本身可行（实测，macOS 的 APFS、Linux 的 ext4：交出方关掉自己那一份之后锁仍在、接收方被杀即释放；交出方显式解锁连同接收方的一并解开；对交来的持锁打开、或一个没被锁的别的文件再取锁都立即成立，所以接收方要先核对对象）。
- **`submit` 建 run，把锁经套接字传给先启动的后台推进进程**：同样有交接，交接期间同样有两个进程持锁，两个进程还互相等对方的产出（`submit` 等公网地址，后台推进进程等锁）。实测锁在传递之后保持（目录上的排他 `flock`，描述符经 UNIX 套接字传给已在运行的进程，发送方关掉自己那一份之后仍被持有、接收方关掉之后释放；macOS 与 Linux 各一次），可行但不取。
- **后台推进进程接手一个已经建成的 run**（试拿它的锁、拿到即接着推进）：那就是续一个管它的进程已不在的 run（决策六）。
- **处置方打开 run 目录失败时按锁不可用、只剩期限一条**：没有打开成功就没有做过边界检查的描述符，会在一个没有核过文件系统的目录上按期限写记录。**记为 `unsupported_filesystem`**：把可以修复的权限问题说成不在边界之内，说明误导（决策三「结果的判读」）。
- **处置时先试拿锁、再读运行态**：决策三只对运行态读得出的目录试拿。**判定之前在锁内重读运行态**：结束写的条件已是唯一的裁定，重读是第二套机制，多一次读、不改变记录的正确性（决策八「处置的次序」）。
- **处置方不比记录格式版本**（记录格式版本不同只使期限读不出，照常处置）：别的格式写出的运行态本版本可能解析不了，也不该用本版本的模型改写，理由写全在 [0037](./0037-distribution-and-packaging.md) 决策 7 与该篇「被拒方案」里「处置方不比 run 记录格式版本」一条（本篇决策六）。
- **列举之后被删去的 run 另给一个 `reason`**（如 `gone`）：结果里会出现一个已不在这个后端里的 run；略过即可（决策八「`settle-runs`」一条）。
- **再次执行 `settle-runs` 时为已结束而没有报告的 run 补报告**：报告的写入方就不再唯一（0027「报告由谁、在何时、从什么生成」条），是第二套机制；没有报告与推进器在终态写之后、报告之前中断是同一取舍（「其它局限」）。
- **在处置内部接住中断、带出是否已写成**：中断可能落在结束写的改名成功与返回之间，这一空档里事实不确定，只能多出一种「可能已写成」的说法。**按阶段登记（还没写、写到一半、已写成）再分三种说明**：是第二套机制，而且写成之后、报告之前被打断时报告永远缺失（决策八「中断」）。
- **锁被持有时一律不说明**：期限读不出时等待可能没有上界，而使用者得不到任何提示（决策八「等待中的 `status --wait`」）。
- **run 目录不过边界检查时 `status --wait` 只读地等到终态、不处置**：等不到终态时没有出口，与别的入口对同一个 run 的处理也不一致（`settle-runs` 记为跳过并写明原因）。
- **管它的进程退出而 run 未结束时，前台只说重新执行**：留下一个永远停在未结束的 run，与后台给出的出口不一致（决策八「管它的进程退出而 run 未结束的出口」）。
- **为停 task 新设一个 Lambda**：要用的触发（runs 表的流、定时触发）、权限（列 task、停 task）都在两个推进 Lambda 上，另设一个只是把同一套装配再复制一份。
- **由 `settle-runs` 自己停 task**：它就得带上操作 ECS 的权限，没有这项权限的机器用不了；没有人执行它的时候 task 照样没人停。停掉已结束的 run 的 task 是后端自己的职责（决策九），不依赖有人执行命令。
- **判定只读提交记录的头**（记录格式版本、写出版本与期限）：正文的损坏会被忽略，判定不再严谨；记录损坏要按损坏的规则走（决策六）。云端读头与读整份定义的差别只是一次取 jobs 对象的请求（决策八「处置的次序」一条里的「读量」），省下的这一次请求抵不上判定的严谨。
- **为省读量让一条命令只读一次提交记录**（等待中的 `status --wait` 只在第一次轮询时读，之后每轮只读运行态）：读量本身很小，云端每次轮询读头是 1 个读单位，另加一次取 jobs 对象的请求（约 550KB 的对象实测中位 31 毫秒），读单位与请求数都不随 job 数增长（决策八「处置的次序」一条里的「读量」）；为它要让处置模块多一种读法、调用方多传一份读好的提交记录，是为省一点读量加接口。
- **按读到的状态决定建不建 run 级触发**（而不按流记录的种类）：定时触发到来时读到的同样是未结束的 run，会重建已经触发、自动删除的同名触发；建立只能由 STATE 的新建引出（决策九第 1 条）。
- **建不成 run 级触发即不做首轮推进**：冷启动就依赖 Scheduler 可用（决策九第 1 条）。
- **只靠使 run 成为终态的那次写经流触发清扫**（各入口得知 run 已结束时不当场清扫）：那条流记录被丢弃时就没有人清扫（决策九第 2 条③）。
- **清扫之后隔一会儿再清扫一次**（为刚启动、还列不出来的 task）：多一次定时触发，而漏掉的 task 已有此后带到这个 run 的几条来路（决策九第 2 条开头）。
- **运行态读不出时各入口一律清扫**：分不清 run 是否已结束，可能停掉仍在执行的 task；只有期限加 300 秒之后，依据时间才成立（决策九第 2 条②）。
- **每次调用都先读提交记录的头**（再按头里的记录格式版本决定怎样读运行态）：已结束的 run 上迟到的事件也要多读一次提交记录，实测带投影的读按整条记录计读单位（决策八「处置的次序」一条里的「读量」）；先看运行态的公共部分，已结束的 run 不读头，未结束的 run 在第二步本来就读头（决策九「落实时」一段）。
- **别的格式写出的 run 当作运行态读不出，等到期限加 300 秒再按时间清扫**：期限是各 job 预算串行相加，大的 run 卡住的 task 可能多计费数天；公共部分跨格式读得出、结束得了，第一次带到就结束并清扫（决策九「落实时」一段）。
- **后端只靠 worker 启动时的核对来处理 worker 协议版本不同的未结束 run**（不在闸里比运行定义记下的协议版本）：余下的每个 job 都要起一个 task 才失败；执行中的 task 发出的事件会按另一版协议解读；后端对别的格式写出的 run 做到的那三件事不成立（[0037](./0037-distribution-and-packaging.md) 决策 7「后端遇到别的格式写出的 run」里「保证的范围」）。worker 建会话之前对 job 行协议版本的核对保留，作最后一道（[0024](./0024-worker-core-protocol.md)）。
- **后端到期结束先处置、后过推进器的闸**：后端自己的不同入口会对同一个 run 给出 error 或 skipped 两种结果（决策九第 1 条）。
- **在 Lambda 里另写一份处置判定**：判定分在两处必然漂移，三个处置方的结果不再由同一份 code 保证（决策八「能处置的只有」一条）。
- **一批流记录遇错即抛**：排在后面的记录这次不处理，持续失败时连同出错的那条一起被丢弃，同批别的 run 可能永不冷启动（决策九第 2 条「失败与批的隔离」一项）。
- **给用户一侧加桶的列举权限，让明细缺失在两边记成同一种原因**：为说法相同扩大权限；没有列举权限时如实说拒绝访问，已足够让使用者处理（决策七「报告」）。
- **在命令开始时对一切 run 比对报告前缀**：已结束的 run 不需要写任何记录，`status` 照常显示它，`status --wait` 却以退出码 2 结束（决策八「云端处置方的报告前缀」）。
- **给 0 时取引擎的上限**（桌面约 8 小时、设备 8880 秒）：`submit --backend cloud` 时 CLI 在计划阶段不查询引擎的能力自述，拿不到设备的数；在 core 里抄一份则是同一个事实写两处，引擎改了而这一份没人记得改。桌面那个数同样是从平台的会话上限推出来的引擎事实。
- **给 0 表示不超时**：每个 run 都要有期限，处置的期限一条与云端的后端到期结束都依赖它（决策六与决策九第 1 条）；不超时实际也只撑到浏览器会话的一小时（决策十的理由）。
- **给 0 时设备 scope 取设备缺省**：同一个写法对桌面是「尽可能长」、对设备是「等于没写」，一个参数两种含义。
- **按目标各定一个产品上限**（桌面取平台允许的最长、设备另取一个数）：桌面那个数仍是把引擎与平台的事实搬进 core；一个产品设定用一个数，引擎的限制留在引擎。

## 实测项（实装时逐项核，结果内联回这里）

各条写的是布置之下、本篇各决策及所引条文的前提成立时应当看到的结果；决策与「边界与已知局限」写明的例外出现时按那里的说法判。哪一次调用完成了哪件事、谁先谁后，布置没有固定的只记下，不作为通过的条件。

期限：

1. 前台到期：把期限设到执行中途，执行方不再认领新的 job、执行中被期限截断的 worker 记 `aborted` 加期限的说明、执行中的 job 都结束之后结束写把未启动的 job 记 `skipped`、run 状态按 0031 决定三取、由执行结果结束的 job 的判定明细齐全、报告与 `status --json` 一致。
2. 本机后台 run 到期：推进进程还在时，到期后执行中被期限截断的 job 记 `aborted`、未启动的 job 由结束写记 `skipped`、run 状态按 0031 决定三取、报告生成。
3. 云端后台 run 到期：部署后提交一个期限落在执行中途的 run，没有任何人查看，过了期限之后执行中的 task 被停止、未启动的 job 不再认领、run 按 0031 决定三结束（决策九第 1 条）；核对期限那一次定时触发确实发出、Lambda 日志里没有异常。
4. 三种组合一致：三种组合各一个期限落在执行中途的 run，`status --json` 与 `explain` 一致且符合决策二第 2 条、0031 决定一与 0031 决定三「结束写」小节的说明表（内容完整的保留判定）；启动失败的 job 包括在内。
5. 内容完整的不改判：让一个 job 在期限之前给出完整内容、期限之后正常退出，它在三种组合下都保留原判定；全部 job 都内容完整时，run 按 0031 决定三得到真实结果、没有到期的说明。
6. 前台重试：job 因网络故障重试时照常重新启动、不被自己的认领拦住；退避期间 run 被别处记为已结束时不重新启动、不写终态；经过开始执行与结束两次状态写之后，认领时刻仍在运行态里。产品的 `run` 不开 job 级重试（0028），重试的两条在调度层用注入的重试次数核，认领时刻的保留在真实的 run 上核。
7. 到期结束写与认领并发（云端）：一个推进器读到「没有执行中的、仍有未启动的」之后，另一方的认领落下、新认领的 job 还没有结果，前者的结束写不成立、run 没有结束（认领落在结束写自己的读与写之间时，由写入序号的条件挡下、重读之后不再满足）；记下新认领的 job 怎样结束、由哪一次调用停下。
8. 云端期限触发承担 job 到点停止：只有一个 job 的 run，让它自己的超时触发缺失、worker 不出事件，task 被停掉、run 结束（决策九第 1 条）。记下两次触发的到达时刻、停掉 task 的是期限那一次还是清扫（决策九第 2 条）、结束 run 的那次写出自哪一方。
9. 预算上限：`--default-job-timeout 0` 下未标 `@timeout` 的桌面与设备 scope 在运行定义里都得到 7200 秒的预算；桌面 job 的浏览器会话存活时间设为 7320 秒（两个引擎各核一次，从 worker 发出的建会话请求里读）；有效预算 7201 秒在计划阶段被拒、7200 秒通过，两种目标各核一次；标了 `@timeout:1500` 的 scope 在 `--default-job-timeout` 给出超过上限的值时不因此被拒（没有生效的缺省值不检查）；产品上限不大于每个引擎对每种目标能支持的最长预算的那条测试，在引擎一侧的数低于产品上限时失败。
10. 退出时刻的两种取法一致（云端）：同一个已停止的 task，从它的停止事件取到的执行停止时刻与主动查询 task 取到的，写成退出记录之后相同；两处先后写同一条退出记录时内容不变。
11. 截止时刻之后自行退出的归因：worker 在截止时刻之后、停止请求发出之前以非零的退出码退出时，本机后台与云端后台都按到点处理（预算截断记 `error` 加超时，期限截断记 `aborted`），状态与说明和前台相同；退出时刻不晚于截止时刻的按退出码归因；内容完整的 job 不因退出时刻晚于截止时刻而改判。本机一侧用真实进程核，云端一侧在部署之后用真实的 task 核。
12. 补写不覆盖（云端）：job 到点停止找不到 task 时补写的未知退出只在没有退出记录时写入，观察者的真实退出记录落在「查有没有退出记录」与补写之间时，留下的是真实的那一条。

锁与边界：

13. 目录锁与目录里的锁互不阻挡：另一个进程持有目录的 `flock` 时，对目录里 `.runstate.lock` 取 `flock`、对目录里的文件取 POSIX 记录锁（事件库）、在目录里以 WAL 模式写 SQLite 都立即成功。三项已核：macOS 的 APFS，Linux 清单的六种类型、绑定挂载、`btrfs` 的另一个子卷与快照，Docker Desktop 的命名卷（容器里取到的类型是 `ext4`）。
14. 边界检查：Linux 的 NFS 与 FUSE 挂载、macOS 的 SMB、NFS 挂载与 HFS+、FAT 磁盘映像、Docker Desktop 容器里绑定挂载的宿主目录上，四个命令按决策四处理、`doctor` 那一项不过；报告目录不过时 `run` 与本机 `submit` 在前置检查里以同一句说明、退出码 2 结束，没有留下目录、没有上传、没有起隧道，报告目录还不存在或经符号链接指定时同样；已有的 run 目录本身是挂载点或符号链接、落在这类文件系统上时试拿方不取锁、不写记录；改名的目标是挂载点时改名失败，按写记录失败报出。
    - 已核，`run` 与本机 `submit` 经命令：Linux 的 `ext2` 回环镜像与一个直通的 FUSE 挂载（类型 `fuse`；报告目录还不存在）、macOS 的 HFS+ 与 FAT 磁盘映像（报告目录还不存在、经悬空的符号链接指定各一次）上，两个命令同一句说明、退出码 2、标准输出为空、没有留下目录，带 `--expose-local` 时没有起隧道、没有启动后台推进进程；macOS 的 `/dev`（`devfs`）与 Linux 的 `/proc` 下 `run` 同样被拒。
    - 已核，类型的取法：Docker Desktop 容器里绑定挂载的宿主目录取到 `fakeowner`、被拒（报告目录还不存在时取上级，同样）；Linux 上被上层挂载盖住的目录取到上层的类型，经符号链接的沿链接取，懒卸载之后的同一个描述符判断不了；清单里各类型、绑定挂载、`btrfs` 的另一个子卷与快照上取到的类型与 `findmnt` 给出的相同。
    - 已核，改名的目标是挂载点：macOS 上是 `EXDEV`，Linux 上是 `EBUSY`，都不留暂存目录。
    - 已核，已有的 run 目录落在清单之外的文件系统上（macOS 上 HFS+ 映像、Linux 上 `ext2` 回环镜像挂在一个未结束的 run 的目录上）：`settle-runs` 跳过它（`unsupported_filesystem`），等待中的 `status --wait` 以退出码 2 给出说明、不等待，记录字节不变；不带 `--wait` 的 `status` 照常显示。
    - 尚未核：Linux 的 NFS 挂载、macOS 的 SMB 与 NFS 挂载上经命令的结果；`doctor` 的一项。
15. 本机后台的 run 自建立起锁就在后台推进进程手里：经 CLI 提交，以 run 标识命名的目录出现之后、后台推进进程退出之前的任何时刻（含 `submit` 退出之前与之后）别的进程试拿都得到「已被持有」（决策三「谁在何时拿」：「持有到进程退出」）；后台推进进程被 SIGKILL 之后即拿得到。已核（macOS 的 APFS 与 Linux 的 `ext4`，经命令提交，worker 换成停留十秒左右的替身）：推进期间与后台推进进程被暂停时试拿得到「已被持有」，它被 SIGKILL 之后、worker 还在时即拿得到；macOS 上从 run 目录出现起连续试拿，跨 `submit` 退出前后与暂停期间约 21 万次全部是「已被持有」。前台 `run` 执行期间同样，退出之后拿得到。

处置：

16. 推进器不在：本机两种推进器各被 SIGKILL 一次，`status --wait` 下一次轮询即按 0031 决定三「结束写」小节说明表的「锁拿到了」一行处置、标准错误有本命令已把它记为已结束的那一句、有报告、退出码 1，孤儿 worker 释放会话后退出；SIGSTOP 时过了期限加 300 秒之后才处置，SIGCONT 之后推进器发现 run 已结束、停手、不再存明细；等待期间按 Ctrl-C 以 130 结束，说明没有改动这个 run 的记录。macOS 的 APFS 与 Linux 的 `ext4` 各做一遍。
    - 已核（macOS 的 APFS 与 Linux 的 `ext4`；worker 换成等到所属进程不在才退出的替身，Linux 上另用真实的 Nova 引擎与隧道做了前台被 SIGKILL 的一次）：两种推进器被 SIGKILL 时，等待中的 `status --wait` 在下一次轮询结束（1 秒之内），结果如上，替身 worker 随即退出，真实的 worker 连同它的子进程 4 秒之内退出。两种推进器被 SIGSTOP 到期限自然经过（Linux，不改记录；macOS 上把记录里的期限改到过去，结果相同）：期限之后 150 秒与 293 秒执行的 `settle-runs` 都跳过（`lock_held`），等待中的 `status --wait` 在期限之后 300.5 秒把它记为已结束（「已超过允许运行的时间」）、退出码 1、有报告，处置之后锁仍被暂停着的推进器持有；SIGCONT 之后后台推进进程 0.1 秒之内退出、不存明细、记录字节不变，前台见第 17 项。等待期间收到 SIGINT 与 SIGTERM：130 与 143，标准输出为空，说明没有改动这个 run 的记录，记录字节不变；启动时 SIGINT 已被忽略的接着等待。
    - 尚未核：真实的引擎上孤儿 worker 退出之前是否已释放会话（只看了进程退出）。
17. 暂停后恢复（前台）：执行 `run` 的进程被 SIGSTOP 到期限加 300 秒之后，别处先处置；SIGCONT 之后没有新的 job 认领成功（它的时钟已过停止认领的时刻，时间检查先拦下；时钟落后于处置方时改由认领被拒拦下，这一支用注入的时钟核）、执行中的 worker 被停止，不覆盖已有的终态，终端有说明、退出码非零。
    - 已核（Linux 的 `ext4`，期限自然经过，一个执行中的 job）：SIGCONT 之后前台 0.1 秒退出，执行中的 worker 收到停止请求，退出码 1、标准输出为空、没有回溯，说明这个 run 在本次执行结束之前已被记为已结束、本次执行没有覆盖记录也没有生成报告；记录字节不变，明细目录里多出一份没被点名的明细（发现之前已经开始的那一次保存，决策五）。macOS 的 APFS（三个 job、并发二，期限改在记录里，其中一个 job 在 SIGCONT 之后结束）：没有新的认领，另一个执行中的 worker 收到停止请求，记录字节不变，退出码 1。Linux 上真实的 Nova 引擎与隧道（期限改在记录里）：SIGCONT 之后 6.7 秒退出，worker 协作停止并确认释放会话。认领被拒的一支由调度层的用例核。
    - 记下：做这一项要让期限自然经过，或让 SIGCONT 之后还有一次 job 状态写。只把记录里的期限改到过去时，前台自己的墙钟没有过期限，又没有写可供发现，执行中的 job 照常执行到它自己的截止时刻；产品里处置方按期限处置时，前台读的是同一个墙钟，不出现这种状态。
18. 终态不可变：处置与推进器的写（前台的 job 状态写，本机后台与云端的认领与终态写）交错进行，run 不出现从终态回到 `running`，终态之后的 job 写都写不成；对已有的 run 再次建 run 失败、不改任何记录（云端连同 jobs 对象的核对登记在 [0030](./0030-realtime-persistence-seam.md) 决定六「云端提交记录」条的实测项「同一个 run 标识再建一次」一项），两个后端各核一次。
    - 已核（本机后端，macOS 的 APFS，真实进程）：一次处置的各步之间（打开 run 目录之后、判定之后、结束写前后、生成报告时）各插入四种变化（推进器写终态、写终态并退出、删去 run 目录、另一个 `settle-runs`），结果都由结束写的条件裁定；替身推进器的终态写与真实的 `settle-runs` 随机交错 40 轮，没有一轮从终态回到 `running`；终态之后的认领、两种 job 状态写、状态投影与结束写都写不成，再建同一个 run 得到「已存在」、不改任何东西。
    - 尚未核：云端后端的各条。
19. 两个 `settle-runs` 同时处置同一个 run（期限未到与已过两种布置，各做多轮，macOS 的 APFS 与 Linux 的 `ext4` 上各做一遍）：每轮只有一个写成，run 级说明与写成的那一方的 `reason` 对应。
    - 已核：两个平台上各三种布置（期限未到而推进器已退出、期限已过而推进器已退出、期限已过而推进器被暂停）、每种 15 轮，每轮恰有一方写成，另一方得到 `lock_held` 或 `already_finished`、或列举时已不列出它，run 级说明与写成一方的 `reason` 对应。
20. `settle-runs` 的结果：本机推进器不在、仍在、另一处置方持锁、被暂停过了期限加 300 秒，run 目录在清单之外、运行态损坏、提交记录损坏、记录格式版本与本机不同、已结束，另有建 run 中途留下的暂存目录，云端期限加 300 秒前后，`settle-runs` 的人读与 `--json` 每一项符合决策八（提交记录损坏的那个处置之后没有报告），`list-runs`、`status` 的提示符合 0041 决策七，`--dry-run` 拿到的锁随即放开（另一进程立即拿得到）。处置中、清理暂存目录中按 Ctrl-C：已处理的部分在输出里（`--json` 下是单个对象），以 130 结束；另一进程持有 `.runstate.lock` 时 Ctrl-C 到它放开、结束写写成之后才起作用（「其它局限」）。
    - 已核（本机后端，真实进程）：macOS 上八种 run（推进器被 SIGKILL、仍在、被暂停且期限已过、运行态损坏、别的版本写出、取锁出错、提交记录不合法、run 目录在 HFS+ 映像上）与十种暂存目录形态的条目，人读与 `--json` 每一项符合决策八，`--dry-run` 前后整棵目录树逐字节相同。Linux 上推进器被 SIGKILL 之后 `--dry-run` 给出 `would_settle`、另一进程随即拿得到锁，处置之后再执行不再列出它，给出已结束的 run 的标识得到 `already_finished`；建 run 中途被强杀留下的暂存目录先后得到 `would_remove` 与 `removed`。中断：macOS 上 34 种时机（列举中、两项之间、结束写里、生成报告里、清理暂存目录里，两种输出、两种信号）符合决策八「中断」，进程内发出真实信号的用例在 Linux 上通过。
    - 尚未核：云端期限加 300 秒前后；`list-runs`、`status` 的提示。

云端：

21. 云端到期与清扫：停掉 events 表流的事件源映射、不执行处置命令，过了期限之后 task 被停、run 结束（决策九第 1 条），记下两次触发的到达时刻与结束 run 的是哪一次调用；两次触发在这个部署的 schedule group 里，名字与表达式符合 0033 资源清单 15，时刻符合本篇决策九第 1 条「时刻」一项，触发之后自动删除；流上只有 STATE 的新建与使 run 成为终态的写触发 `kicker`：分开产生可识别的 STATE 新建与确实改变条目、run 仍未结束的修改，记下映射实际投递给 kicker 的每条记录，修改不在其中（按事件种类过滤的直接核对；0033 资源清单 13 给出的是日志旁证）；`settle-runs` 结束的 run、结束之后才启动的 task 都被清扫；同一格式下运行态被改成读不出的 run 不被改动，它仍在执行、那一次列得出的 task 只在期限加 300 秒那一次被停；STATE 被删去的 run，它的 task 由之后带到它的调用停下；提交记录头里的记录格式版本被改成别的值、有执行中 task 的 run，下一次带到它的事件到来时被 error 变体记为 error、task 被停，运行态里公共部分之外的属性不变。
22. 清扫不误伤：正常进行中的 run 在同一后端里另一个 run 结束时不受影响；正常结束的 run 触发的清扫没有要停的 task（列举可能仍返回刚停止的 task），没有打断任何 task 的最后上传。
23. 运行定义不可用：云端推进器读不到可用的运行定义时，未结束的 job `error`、run `error`，说明取 0031 决定三「结束写」小节说明表的那一行；运行定义记下的 worker 协议版本与后端不同的 run，同样以 error 变体结束并清扫。删去 jobs 对象的那一种布置（含此前用户一侧两个入口的表现）登记在 [0030](./0030-realtime-persistence-seam.md) 决定六「云端提交记录」条的实测项「删去一个未结束的 run 的 jobs 对象」一项。

建 run 的暂存与改名：

24. 改名与锁：暂存目录持锁改名之后按新名试拿得到「已被持有」，持有者被暂停时仍是，被 SIGKILL 之后拿得到；改名的目标已被占着时「已存在」与「写记录失败」的区分按 0030 决定四。
    - 已核，改名与锁：macOS 的 APFS；Linux 清单的六种类型（`xfs`、`btrfs`、`ext3` 用回环镜像）、`btrfs` 的另一个子卷与快照、宿主上的绑定挂载、Docker Desktop 的命名卷，这一组上 SIGKILL 之后 10 毫秒之内拿得到；另有宿主与容器之间的绑定挂载（宿主建 run，容器里另一进程按 run 标识试拿）与容器自己的 overlay。
    - 已核，改名的目标：Linux 上目标是非空目录、文件、悬空的符号链接、指向目录的符号链接、空目录时，上一条里注明 10 毫秒的那一组上结果与 macOS 相同；目标是挂载点的见第 14 项。
    - 已核，创建者与清理方的交错（经产品代码，创建者停在指定的一步；清理方是照常与只看不删两种 `settle-runs`）：macOS 的 APFS 上创建者停在建出、打开、取锁、核对名字、写完、改名之后六处，Linux 的 `ext4` 上停在建出之后打开之前、持锁写完改名之前两处。创建者还没有取到锁时，照常的清理方删去这个空目录、创建者换名建成，只看不删的清理方放开之后创建者用原名建成；创建者持锁时清理方跳过（`held`）；改名之后不再列为暂存目录、那个 run 得到 `lock_held`。每次建成的 run 完整，不留暂存目录。清理方删到中途被 SIGKILL 之后锁即拿得到，下一次 `settle-runs` 把余下的删去（macOS）。
    - 尚未核：容器的 overlay 上的交错。
25. 建 run 中途被强杀：两种推进器在暂存目录里写下两个文件之后、改名之前被 SIGKILL，报告目录里只留下以 `.gherkai-creating-` 开头的目录；`list-runs`（含 `--json`）不列出它，以它的名字执行 `status` 与 `explain` 得到未找到 run、退出码 2；本机 `submit` 给出后台推进进程在回报之前退出的那一句、退出码 2。已核：macOS 的 APFS 与 Linux 的 `ext4` 上经命令各一次，结果如上；留下的暂存目录里是那两个文件，强杀之后另一进程对它试拿即拿得到。

云端的拆除与 AWS 行为：

26. 拆除：在临时前缀上留一个执行中的 run，执行 `destroy`，之后这个部署的 schedule group 与其中的触发（含还没有到点的）都已删除，没有投递到已不存在的目标。另记下：Scheduler 调用 `kicker` 失败时由谁重试、重试几次。
27. 按启动标识列 task 时另带期望状态：job 到点停止与期限那一次按启动标识分别列出运行中与已停止的 task（0034「job timeout」节），清扫只列运行中的（决策九第 2 条）。AWS 的 API 文档写按启动标识过滤时它须是唯一的过滤条件。已核（真实的集群上起一个带启动标识、容器立即退出的临时 Fargate task，每隔十来秒按三种写法各列一次）：启动标识加期望状态「运行中」，从 RunTask 返回之后的第一次列举（task 还在 PROVISIONING）起都列得出它，task 转入停止（期望状态变为已停止）之后列不出；启动标识加期望状态「已停止」，转入停止之前列不出，之后列得出，到 STOPPED 之后连看三次仍列得出；只给启动标识与「运行中」那一种相同，task 停止之后列不出。所以两个参数同时给，运行中与已停止两类都列得出；只给启动标识列不出已停止的 task，不能改为只按启动标识列、再在 code 里按状态分（本地过滤找不回服务端没有返回的已停止 task）。设计依赖的是这一实际行为，它与 API 文档的写法相反，以实际行为为准（与 [0033](./0033-iac-aws-backend-and-composition-wiring.md) 资源清单 13 对按事件种类过滤的取法相同）。刚启动的 task 多久之后列得出（已核）：另起 14 个临时 task（8 个逐个启动、6 个同时启动），发出 RunTask 之前就开始每 0.15 秒按启动标识加期望状态「运行中」列一次，第一次列得出距请求发出 0.7 到 4.0 秒、距调用返回 0 到 0.33 秒，没有在调用返回之前就列得出的，也没有列不出的；这是样本，不构成列举延迟的上界。StopTask 的返回（已核，同一个执行中的 task 连发三次，各带不同的 reason）：对执行中、正在停止、已停止的 task 都成功返回；发过第一次之后，按期望状态「运行中」立即列不出它、按「已停止」列得出；task 的停止原因一直是第一次给的那一句，后两次的 reason 不盖掉它；对不存在的 task 标识得到 `InvalidParameterException`（The referenced task was not found）；reason 至多 1024 个字符，1025 个被拒。

## 重议闸门

- **跨机器早于期限判死活**，或**本机后端的报告目录放到网络文件系统上、跨内核共用**成为使用需要时：再议心跳、租约或跨内核的死活判断。云端与跨机器的处置只有期限一条条件（决策六），宽松的期限可以是实际时长的数倍。
- **持锁的进程里出现 fork 而不 exec 的线程**（前台 `run` 或后台推进进程里新加的线程会直接 fork、用 fork 方式的 `multiprocessing` 或进程池、或给 `subprocess` 传 `preexec_fn`）：决策三「已知的间隔」随之可达，加这样的线程之前先二选一：把钩子的登记提前到取锁之前并加 fork 闸门（「被拒方案」里「fork 闸门」一条，实测可行），或让这个线程在建 run 完成之后才启动。
- **持锁的进程里出现把描述符带给子进程的写法**（前台 `run` 或后台推进进程里以不关描述符的方式起子进程、把某个描述符设成可继承、或给 `pass_fds` 传不是自己打开的描述符）：决策三「前提」里锁描述符不被带给子进程的一条靠约定成立，加这样的写法之前先核对带出去的描述符里没有锁描述符（按设备号与 inode 比对持锁的 run 目录）。
- **使用者可调的 run 级期限**：由 job 预算推出的期限对某类 run 明显过宽、影响到 CI 排期或费用时，再议单独的配置项。
- **部署之后改 `REPORT_DIR` 成为使用需要**（之前提交的 run 的明细留在旧前缀下，用新前缀处置时报告缺失，决策八「云端处置方的报告前缀」）：把报告落点记进运行定义（给 run 记录格式版本加号，[0041](./0041-agent-facing-cli-affordances.md) 决策六的定位规则随之改），处置方用记录里的落点、不再比对配置。
