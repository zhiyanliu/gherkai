# 0041. 面向 AI agent 驾驭的 CLI 能力：scenario 筛选、静默落盘、JSON 覆盖补齐、doctor 自检、JSON 契约

> **Status:** Partially-superseded-by [0043](./0043-agent-skill-for-driving-gherkai.md)（2026-09-14；范围 = 决策五「skill 只链接它，不复制字段表」这一子句被反转为「确定性转换副本随 CLI 发行」，决策一-四与决策五其余部分不变）。原 Accepted（2026-09-10）—— 五项均已实装并有护栏；agent skill（0043）以本 ADR 的命令面为教学对象。本 ADR「重议闸门」失败证据机读化一条已由 [0042](./0042-step-evidence-and-explain.md)（step 级 evidence + `explain`）落地，五项决策不变。决策七（`list-runs`）已实装：本机与原索引上的云端实测项已真实执行、结论内联在该条。决策七已改用与 worker revision 清理共用的状态分组索引 `status_group-run_id-index`（写端、索引与 `list-runs` 的读法均已实装，[0030](./0030-realtime-persistence-seam.md) 决定六）；原先所读的 `status-run_id-index` 已从部署模板删除，部署模板里 runs 表只定义状态分组索引（0030 决定六）；状态分组索引上的云端实测待核。

## 背景与问题

gherkai 的直接操作者越来越多是使用者侧 AI agent（Claude Code / Codex 这类），替人写 `.feature`、跑、读结果、改确定性 step。agent 的工作循环与人不同：每一轮都要把命令输出读进上下文，每一次真跑都花几分钟与真金白银的 AI 费用，且它只能靠机读输出与退出码分流、不会「看一眼」HTML。对照 [0039](./0039-user-facing-surfaces-no-internal-references.md)（产品面文案）、[0036](./0036-deterministic-capability-discovery.md)（worker 自述）与 [0037](./0037-distribution-and-packaging.md) 决策 3（定位链）已经给出的底子（退出码 0/1/2 边界清楚、错误带「怎么办」、`plan` 零费用预检、`run/plan/status/list-deterministic` 有 `--json`、stdout 只放数据），复盘一轮真实 agent 使用后仍有五个洞，全部落在「迭代循环成本」与「机读完备性」两条线上：

1. 只能整文件跑：改一句断言想验证，`.feature` 里全部 scenario 重跑一遍——最贵的一格。
2. `--quiet` 只静音 core 的逐事件进度，worker 的 stdout/stderr（SDK 的 think/act 噪声，每步数百字符）无条件透传，agent 的上下文被灌满。
3. JSON 覆盖有洞：`list-engines` / `deploy list-workers` 只有文本；`status --json` 没有产物位置。
4. 没有一条自检：「凭证/region、两个引擎、`steps/` 能否加载、后端可达、版本 skew」散在四处，agent 要试错才知道环境缺什么。
5. `--json` 的字段没有契约文档，agent 靠猜字段名，写进 skill 又必漂移。

## 决策

### 一、scenario 筛选：`--scope` / `--tags` / `--scenario`，run / plan / submit 三命令写法相同

- 三个可重复 flag，都在 **scope 分组与 engine/target/timeout 解析之后、Job 组装之前**筛（core `plan(features, config, select=…)` 收一个 `(ParsedScenario, scope_id) → bool` 谓词（scope_id 一并传入，业务概念按分组键判、不从 tags 反推））。**不变量：筛选只减少「跑哪几条」**——scope 的引擎、测试目标、墙钟预算、会话身份一律按全量成员解析，与不筛时逐字一致；否则筛后跑的与全量跑的不是同一件事，迭代结论不可迁移（曾在分组前筛：把带 `@engine:midscene @timeout:900` 的成员筛掉，剩下的成员静默跑在 novaact / 300s，对抗审查真跑复现）。整组被筛空的 scope 不进任何 job，且在解析 engine/target/timeout **之前**跳过——被筛掉的 scope 里的 tag 冲突不拦本次迭代；`_scope_key`（一个 scenario 多个 `@scope`）仍对全量成员 fail-fast；`scope_id` 命名空间撞名（`@scope` 的值 = 某条未标 scope 的 scenario 的 id，见 [0025](./0025-plan-module-feature-to-jobs.md)「id 派生」）同样按**全量**成员判、且判在施加筛选**之前**——`--scope` 收窄到只跑其中一个 scope 也仍退 2（已真跑核对）。**这是有意代价**，与上句「被筛掉的 scope 里的 tag 冲突不拦本次迭代」并不矛盾：tag 冲突只影响那个 scope 自己怎么跑，筛掉了就与本次无关；撞名撞的是下游主键（状态 Map 的键、结果文件、claim），会让**本次要跑的** job 丢结果，故不因筛选放过。跨文件合并 warning 按**要跑的**成员算。三个命令同一套解析（`_load_and_plan`），definition 即筛后的 job 集——`submit` 落库的就是它，`plan` 标注的也是它。空值（`--tags ""`）退 2，不静默降级成跑全批。
- **`--scope ID`**：可重复、彼此为**或**；值 = 报告与 `--json` 里的 `scope_id`（`@scope:` 的名字，未标 scope 时是 `<uri>:<行>`），按分组键**精确**匹配。这是「重跑某个失败 job」的直接回路：agent 从 `jobs/*.json` 读到 `scope_id` 原样填回来。scope 是业务概念，在 Gherkin 里靠 tag 承载（[0019](./0019-feature-tags-scope-and-engine.md) 的取舍——Gherkin 没有别的 per-scenario 元数据位）；筛选面上不让使用者反推这层实现细节（`--tags scope:x` 仍可用，那是通用 tag 筛选顺带覆盖的）。
- **`--tags TAG[,TAG…]`**：一个值内逗号分隔为**或**（任一命中）；flag 重复为**且**；`@` 可带可不带。tag 集 = gherkin 已合并的 feature 级 + scenario 级。
- **`--scenario SEL`**：可重复、彼此为**或**。`SEL` 三种写法**按序试、互斥**：等于 scenario id（`<uri>:<声明行>[:<Examples 行>]`）；ASCII 纯数字或 `:数字` = 行号（只当行号、不回落标题匹配，否则 `--scenario 3` 会连带选中标题「重试3次」；Scenario Outline 给声明行 = 选中它全部 example，给数据行 = 只选那一条）；否则按 scenario 标题**子串**匹配（大小写敏感）。三个 flag 同给为**且**。
- **筛后为空 → 退 2**，并列出本批全部 scenario（`id  标题  tags`）供改参数——不静默跑空批。筛掉了 scenario 时在 stderr 打一行「筛选：N/M」。**不筛选时的零 scenario 批同样以退出码 2 拒绝**（feature 只有头、没有一条 scenario）：零 job 的 run 没有执行任何东西，判 passed 退 0 是空洞的成功，与筛选后为空的情形同一处置：拒绝；run 级聚合对空输入仍返回 passed 只是函数层的兜底（[0031](./0031-job-lifecycle-states-and-severity.md) 决定三），不是放行的理由。
- **有意的语义代价**：named scope（`@scope:X`）里只选其中几个 scenario，会话仍按 scope 建，只是少跑几条——这是迭代用法，不是回归用法；scope 内 scenario 若互相依赖，筛掉前置即可能失败，由使用者判断。
- 被拒：cucumber 风格 tag 表达式（`@a and not @b`）——多一门小语言，agent 与人都得学；三个 flag 的且/或已覆盖迭代场景。行号范围、glob 同理不做。

### 二、`--quiet` 把 worker 日志落盘

- `run --quiet`（本机后端）：worker 的 stdout/stderr 透传改写到 **`<report_dir>/<run_id>/worker.log`**（`--no-report` 时落系统临时目录 `gherkai-worker-<run_id>.log`），结束时只打一行位置；`--json` 的 `artifacts` 加 `worker_log`。默认取值（不 quiet）行为不变——人看流水仍是最快的排障方式。云端后端的 worker 在云端跑、日志在 CloudWatch，无此文件、`artifacts` 无此键；`submit` 的 local per-run 进程本就落 `reconcile.log`，不变。
- **真跑坐实**（跳板机本机 novaact run）：`--quiet` 下终端只多一行 `worker 日志: file://…/worker.log`、无 SDK 流水；worker.log 收下了那批流水、零 ANSI 颜色码；`--backend cloud --quiet` 不建该文件、无未定义变量。`status --json` 的 `artifacts` 两个后端都对（local 全 `file://`；cloud `s3://` 报告与判定明细 + `ddb://` 元信息），且同步 `run` 落的 run_state 确实没有 `high_water_mark`（与本 ADR 决策五的契约页所记一致）。`deploy list-workers --json` 的 stdout 可被严格解析，skew 提示走 stderr。
- 机制：`SubprocessEngine(log_sink=…)` 注入一个文件句柄，`_pump_log` 有 sink 则写 sink（无颜色码）、无 sink 则照旧写 stderr；组合根（`compose.build_engines(worker_log=…)`）只转发。**句柄生命周期**：CLI 在 schedule 返回后关句柄，而透传是两条 daemon 线程——为让日志尾部（多半是失败原因）落完再关，`stop()` 与事件迭代器结束（自然 EOF / 被放弃）两处都对 pump 线程做**有界** join（进程已退即 EOF；带超时是因为定位链第 4 级 uvx 是包装进程、孙进程可能仍持写端）；join 超时后残余的写入撞上已关句柄只静默停转发，不让 traceback 打到 stderr（那正是 `--quiet` 要挡的东西）。
- 被拒：另开 `--worker-logs off|file` 旋钮——「少进上下文」是同一个意图，两个旋钮让 agent 多记一条；env 开关——不可见、难发现。

### 三、JSON 覆盖补齐：查询类命令都有机读形态

边界：`submit` 的机读形态就是 stdout 那一个 `run_id`（进度/结果走 `status --json`）；`deploy` / `destroy` / `push-worker` / `skill install`（[0043](./0043-agent-skill-for-driving-gherkai.md) 决策三；其 `--print` 只把 SKILL.md 正文打到 stdout 供管道）是变更类命令，机读面 = 退出码，只读查询面留给 `list-workers --json` 与 `doctor --json`。`--json` 下 stdout 只有一个 JSON 文档，诊断（含 skew 提示、读失败）一律走 stderr；退出码非 0 的前置/读取失败路径 stdout 可为空，按退出码分流。

- `list-engines --json`：每引擎 `{engine, available, cmd, cwd, source, hint}`。
- `deploy list-workers --json`：`{prefix, version, default_variant, engines: {<engine>: {family, ecr_repo, variants: […], pending_cleanup: […]}}}`。
- `status --json`：在 RunState 之外**附加** `artifacts`（与 `run --json` 同键：`run_meta` / `run_state` / `jobs_dir` / `report_index`），位置由 compose 单点拼、始终给出（是否已写成看 status 是否终态）。RunState 部分形状不变（加法兼容）。
- `explain --json`：判定树 + 每步 evidence 合成的排障视图，形状见 [0042](./0042-step-evidence-and-explain.md) 决策四。
- `list-runs --json`：一个后端里的 run 清单，形状见决策七。
- 原则：stdout 只放数据、诊断走 stderr、`--json` 下不打人读提示（沿用既有）。

### 四、`doctor`：一个入口、按组件分组

- `gherkai doctor [--backend cloud --prefix P --region R --profile NAME --report-dir DIR] [--steps-dir DIR] [--config FILE] [--json]`：**只读**自检，检查项按组件归类（机读形态以 `section` 字段表示），每项 `{ok, required, skipped, 一句诊断（怎么办）}`。**退出码只看 `required` 项**：全过退 0，任一 `required` 项 fail 退 2（agent 可直接分流）；`required=false` 的项失败只作能力展示、不改退出码（另一个引擎没定位到、容器引擎 daemon 没起；未查的项见下「未查是单独一种结果」条）。人读形态为三列表格（结果、检查项、说明，ADR 0047），检查项列写作「组件.项名」；结果列四种：`✓` 查过且通过，`✗` 必修项未通过，`-` 查过、可选能力缺失，`·` 未查。`required` 的判据 = **这次要跑的那个后端真跑得起来吗**。字段与项名取值见 `docs/internals/cli-json-contract.md`（单一事实源，不在此复述）。
- **未查是单独一种结果**：一行检查没有被执行时标 `skipped=true`，人读结果列显示 `·`（淡显），原因写在说明列，尾行在有未查项时点明 `·` 的含义。未查的行恒为 `required=false`、`ok=true`；其余行 `skipped=false`。读法：整体能不能跑看顶层 `ok` 与退出码（规则不变，只看必修项）；某一行「查过且通过」是 `skipped=false` 且 `ok=true`；`ok=false` 专指这一行自己报告了问题。
  - **哪些行算未查**（一行里一项检查都没有执行）：未给云端参数时的 `aws.identity` 与 `backend.reachability`；给了云端参数而 region 或凭证先失败时的占位行 `backend.reachability`（失败本身由其上的 `aws` 必修项报）；停止宽限比对在没有解析到镜像的引擎、或解析到了但本机一个对应的 worker 都没有时；`provider` 段的占位行在没装部署 provider、装了多个而未指名、或装上的 provider 不提供自检时——有没有装已经查到，未查的是部署工具链的自检。
  - **哪些不算**：一行里部分检查做了、部分没做（停止宽限比对只比了一个引擎），按已做的那部分给结果，没做的在说明列交代，`skipped=false`；探测本身抛错是检查失败，不是未查；`backend.version` 检查的是「查询后端版本戳（包括确认它缺失），并按 skew 规则得出结论」（[0037](./0037-distribution-and-packaging.md) 决策 7）：缺戳、CLI 自身版本未知、任一侧为非正式版本，都是规则已经给出结论，`skipped=false`，沿用「不是拦下即通过、读取异常即失败」；这一行的 `✓` 表示通过了这条规则，不表示两个版本已验证兼容。
  - **不为未查另造行**：只给现有的行加状态，行的出现条件不变（自述失败时不出模型与目标两行、前置失败时不出其下游各行，这些规则照旧）；承载「这一组为什么没查」的占位行保留。
  - **provider 的自检项**可带可选的布尔 `skipped`（缺省 false，[0037](./0037-distribution-and-packaging.md) 决策 6 的契约随之扩充），入口输出时每行补齐这个键；provider 给了 `skipped=true` 却同时报 `ok=false` 的，入口按它报告的问题输出（`skipped=false`，`ok` 与 `required` 照它给的），不当作未查，免得一个标记盖住失败。
  - 这是对单行 `ok` 含义的更正，不只是加一个键：占位行 `backend.reachability` 在前置失败时原为 `ok=false`，现为 `ok=true` 加 `skipped=true`。只读某一行 `ok` 的脚本要改为同时读 `skipped`；按「必修且未通过」筛选、或看顶层 `ok` 与退出码的不受影响。
  - 取代的旧规则：未查的行不单列，按来由分别画成 `✓`（没有要求查，记 ok）与 `-`（前置失败，记 ok=false）。`✓` 表示查过且通过，画在没查的行上会让人以为那一部分是好的；`-` 同时表示「查过、可选能力缺失」与「没查」，读者分不清；同一个「未查」对应两种符号、两种 `ok` 取值。
  - 被拒：未查的行记 `ok=false`——「没通过」的筛选结果里会混进没查的行，`ok=false` 不再专指一行自己报告的问题；记 `ok=null`——`ok` 是已发布的布尔契约，而「查没查」已有 `skipped` 回答，再让 `ok` 取第三个值是同一状态的重复表达；只改人读符号、机读不加 `skipped`——机读侧只能从说明文字里的「未查」二字判断；去掉承载未查原因的占位行——读者看不到「云端那部分这次没有查」这一事实，会把没有出现当成没有问题。
- 组件与归属（**按 extra 实施、单入口汇总**——自检能力跟着它检查的组件走，入口只做编排）：
  - `cli`：版本、Python。
  - `config`：本次加载的项目配置文件路径，或「未使用配置文件」；只作展示、可选（[0053](./0053-project-config-file.md) 决策 1）。
  - `engines`：两引擎的定位链结果（同 `list-engines`），各自 `required=false`（缺一个不算故障）；聚合项「至少一个可用」为 required 闸门——两个都定位不到时本机后端一个 job 也起不来；`--backend cloud` 时该聚合项降为可选（只提交、不在本机跑的人不需要 worker）。另有每个可用引擎 worker 自述出的模型与测试目标两行，纯展示、可选，自述失败时不出（[0004](./0004-novaact-iam-auth-via-workflow.md)、[0049](./0049-worker-capabilities-targets-keys.md) 决策 6）。
  - `steps`：解析到的 `steps/` 目录（显式给的目录不存在 = 必修失败，原因进 detail）；对每个可用引擎跑一次 worker 自述（`--capabilities`，清单取其 `deterministic_steps`）——有 steps 目录时是使用方 step 能否加载（必修，加载失败会静默降级成 AI），没有时只验 worker 起得来（可选，单引擎不连坐）。
  - `aws`（给了 `--backend cloud` 或 `--prefix` 才查）：region 解析（解析不出即必修失败、云端其余项标未查）、凭证身份（STS；profile 名不存在等解析期错误与探针失败同一句诊断）。
  - `backend`（同上）：版本戳与 skew 三态、资源 preflight（表/桶/cluster/两引擎 task-def/三 Lambda，并比对后端 `REPORT_DIR` 与 `--report-dir` 一致——复用 submit 的 `preflight_cloud_resources`）、默认 worker variant：先读指针（缺失 = 必修失败），再**逐引擎**解析（各自可选——单引擎团队不必为另一个引擎推镜像，同 submit 只按用到的引擎判）+ 聚合「至少一个引擎可用」为必修；其后两组可选项：停止宽限比对（本机 worker 自报的停止宽限期下限对云端 task-def 的 `stopTimeout`，只比解析到镜像的引擎，缺口按可选能力缺失报，[0032](./0032-fargate-execution-environment.md)「真容器校准结论」第 4 条的既定接受）与设备支持（部署记录的 Device Farm 项目、项目里未结束的远程访问会话，只列不停，[0051](./0051-device-session-lifecycle-and-app-distribution.md) 决策 6 / 10）。
  - `provider`：按 entry point 结构化判——没装 `[deploy-aws]` extra → 一行「部署方才需要」（未查）；装了多个未指名 → 未查；装了但加载失败 → 必修失败（明确装了的东西坏了）；装了且提供可选的 `doctor(args) -> list[dict]`（每项的字段见 [0037](./0037-distribution-and-packaging.md) 决策 6 的契约，含可选的 `required` 与 `skipped`；只读、不返退出码，[0037](./0037-distribution-and-packaging.md) 决策 6 契约）→ 并入输出。AWS provider 报 Node ≥ 22、cdk 可定位、容器引擎可用，**三项都可选**：provider 段是部署能力清单，doctor 不知道这台机器要不要部署；真正的硬拦在 `gherkai deploy` 自身。人读尾行单独点出「部署工具链有缺口」。
- 被拒：另起 `gherkai-deploy doctor` 独立入口——agent 要记两条、且「后端可达」这类检查本就横跨两包；把自检做成 `plan` 的副作用——plan 要保持零费用、零网络。

### 五、JSON 字段契约文档 + 护栏

### 六、定位参数：执行后端、报告落点、部署前缀三项与产生 run 的命令一致，查询才找得到

- **规则**：`status` / `explain` 查的是哪一个 run，由三项定位参数决定——执行后端（`--backend local|cloud`）、报告落点（本机后端的 `--report-dir`）、部署前缀（云端后端的 `--prefix`，连同它所在的 region 与 profile）。查询命令的这三项须与产生该 run 的 `run` / `submit` 逐项一致（前台同步执行与提交后台执行都算），否则以退出码 2 结束并说未找到 run。云端后端的报告前缀（`--report-dir`）同样须与产生 run 的命令一致：`explain` 据它读判定明细。`doctor` 的云端项同理按这三项定位后端；`list-runs` 列的是哪一个后端里的 run，也由这三项决定（决策七）。
- **为什么不跨后端搜、不猜**：run 的记录只存在于产生它的那个后端与落点——本机是 `--report-dir` 下的 run 目录与事件库，云端是 `<prefix>` 对应的 runs 表与产物桶（[0034](./0034-detached-batch-reconciler.md)）；CLI 不维护跨后端、跨目录的 run 索引，也不按 run_id 到处找：猜中是巧合，猜错会把另一个落点里同名 run 的判定当成这个 run 的。三项由使用方给出、与产生时相同，是唯一可靠的定位，所以不一致时直接拒绝、不降级成「找最像的」。
- **本条是权威，其余处只给结论与指针**：本机与云端各自的定位旗标在 [0034](./0034-detached-batch-reconciler.md)「命令形态」节；`explain` 的输入在 [0042](./0042-step-evidence-and-explain.md) 决策四；agent skill 教 agent 保持三项一致在 [0043](./0043-agent-skill-for-driving-gherkai.md) 决策五第 3 条；用户指南运行篇与云端篇写同一句。CONTEXT.md「定位参数」词条指向本条。

### 七、列出 run：`list-runs`

本条已实装。本机实测与当时所读的 `status-run_id-index`（已从部署模板删除）上的云端实测已完成；状态分组索引上的云端实测待核，见本条末「实测项」。

- **缺口**：`status` 与 `explain` 都要先有 run_id，此前没有任何命令回答「这个后端里有哪些 run」。找不回 run_id 时（换了终端、提交时没记下、接手别人提交的 run），只能到 DynamoDB 控制台翻 runs 表，或去 ECS、Device Farm 看执行资源，而执行资源对应的是 task 与远程访问会话，不是 run。
- **命令形态**：`gherkai list-runs [--backend local|cloud] [--report-dir DIR] [--prefix P] [--region R] [--profile NAME] [--ddb-table NAME] [--config FILE] [--status S]… [--limit N] [--json]`。按决策六的三项定位参数选定**一个**后端，旗标名与取值来源（含项目配置文件那一层，[0053](./0053-project-config-file.md)）与 `status` 相同，`--ddb-table` 与 `status` 同义。不跨后端、不跨报告落点搜，理由同决策六：每个后端只持有自己的 run 记录，把多处的清单合在一起会把不同落点里同名的 run 混为一谈。命令只读、零副作用（不接力推进、不起 task），机器只需读权限；云端后端与 `status` 一样，先经版本 skew 闸（[0037](./0037-distribution-and-packaging.md) 决策 7）再读任何云端资源。云端后端下 `--report-dir`（在云端是报告前缀）与清单无关，给了也忽略、不报错：清单不读报告，而使用者常把 `status` / `explain` 的整组定位参数原样复制过来。
- **列哪些 run**：默认列出该后端**全部非终态 run** 与**最近 N 条终态 run**（N 默认 20，`--limit N` 调整，只约束终态部分）。状态集取自 code 真源，本条不另行枚举：run 级状态值是 `core/gherkai_core/model.py` 的 `Status`，终态集是同文件的 `TERMINAL_STATUSES`，其余为非终态。`--status S` 可重复，接受 run 级状态值全集（含 `skipped`），给出时只列这些状态，其中终态部分仍受 `--limit` 约束。「最近」按创建时间计、不按结束时间（见下「排序」）。终态 run 随历史单调增长，必须有界。
  - **非终态不截断**：在途的 run 是使用者最需要找回的那部分。停在非终态的 run 有两类。一类是推进中断、无人接力的 detached run（`submit` 建的，带 detached 标记，[0034](./0034-detached-batch-reconciler.md)），`status --wait` 能接力把它推进到终态。另一类是前台 `run` 的进程被强制结束或宿主失联后留下的 run，没有 detached 标记：`status --wait` 对它只等待、不接力（0034「兜底/接力」条），本命令面也没有把它收尾的手段，它会一直停在非终态。人读表格对后一类行加一句提示，说明产生它的前台执行若已不在、它不会再到终态（措辞随实装定，受 [0039](./0039-user-facing-surfaces-no-internal-references.md) 约束）；判据是 detached 标记，它与运行态在同一处（云端 STATE item、本机 `run_state.json`），读回即有、不增读取（端口怎么带出见下「core 端口」）。后一类随前台执行被强制结束的次数累积、不会自行消失，所以非终态部分的规模是同时在途的 run 数加上停着未处置的 run 数（其中后一类无从处置、只增不减），不能当作恒小；遗留成为常态时再议标记为已放弃一类手段（见文末重议闸门）。
- **排序**：按 run_id 降序，依赖 [0027](./0027-runreport-aggregation-index.md)「run_id：归集索引的主键」节的保证（字典序即创建时间序，同一秒内创建的 run 之间不定；格式不入契约，本条不复述、也不依赖具体格式），所以不另读时刻字段排序。由此「最近 N 条」按创建时间计、不按结束时间：早建而刚结束的 run 不会因为刚结束就排到前面。创建时间取生成 run_id 的机器（执行 `run` 或 `submit` 的那台）的时钟，多台机器向同一后端提交时，各机时钟的偏差直接体现为清单里的先后。
- **人读形态**：`rich` 表格（[0047](./0047-cli-human-readable-tables-with-rich.md)），一行一个 run：run_id、状态（语义颜色同 `status`）、开始与结束时刻（换算到本机时区显示，机读输出保留原始 ISO 时刻）、job 数、版本（见下「写出版本的标记」）与提示。job 列是 job 总数，各 job 的状态与 run 的状态不全相同时括注各状态的个数（全相同时状态列已经说明，不重复）。run 级 `message` 有值时与上述遗留提示一同进提示列，没有任何一行有提示时整列不出现。**清单不给 job 没通过的原因**：运行态里每个 job 只有状态，原因类别与消息在判定明细里（[0030](./0030-realtime-persistence-seam.md) 的数据面），要列出就得为每个 run 的每个 job 多读一份判定明细，或把原因类别再投影进运行态成为第二份；多 job 的 run 还要把多个原因再聚合成一格。原因用 `explain` 或判定明细看（`status` 同样只读运行态，不给 job 的原因）。把原因类别投影进 JobState、让清单与 `status` 的摘要都能直接给出，记为重议闸门。STATE 解析失败的行只有 run_id 与版本列有值，状态列标「无法读取（可能由其它版本写出），用 status 查看」。清单为空时只打一行，点名所查的落点，并提示核对定位参数是否与产生 run 的命令一致：本机区分「报告落点目录不存在」与「目录下没有 run」两种说法，都点名解析后的目录；云端点名前缀、region 与解析后的 runs 表名（不按表名来自旗标、环境变量还是配置文件区分）。
- **机读形态**（进决策五的契约面，受加法兼容保护）：`list-runs --json` 输出一个对象，顶层带所查的落点：`backend` 恒有；本机另带 `report_dir`（各层解析后的绝对路径）；云端另带 `prefix`、`region` 与 `ddb_table`（解析后的 runs 表名）。不带 profile（它决定用哪份凭证，不决定落点），不带云端报告前缀（清单不读报告）。这些取值由 compose 单点给出，与 `cloud_artifact_locations`（`runtime/gherkai_runtime/compose.py`）同一做法，CLI 不另拼。空清单时读者凭它们才分得清「这里没有 run」与「查错了地方」（`--json` 下不打人读提示，决策三）。顶层另带 `cli_version`（恒有）：执行这次清单的 CLI 版本，取不到为 `null`，是各项写出版本的比对对象（见下「写出版本的标记」）。`runs` 为数组，每项含 `run_id`、`status`、`started_at`、`ended_at`、`message`、`job_counts`、`detached` 与 `cli_version`（写出版本，见下「写出版本的标记」）。`detached` 是布尔，恒有：非终态且为 false 的 run 是前台执行遗留的、`status --wait` 对它只等待不接力，与人读行的提示同源。前五项取自 RunState（`core/gherkai_core/model.py` 的 `RunState`）：`run_id` 与 `status` 必有，`started_at`、`ended_at`、`message` 无值时省略该键；`job_counts` 是按 job 状态的计数（`{<状态>: <个数>}`，只含出现的状态，缺的状态按 0 读）。键名不复用 `jobs`：`status --json` 里的 `jobs` 是逐 job 的数组，同一个键名在两个命令里形状不同，读契约的脚本容易用错。STATE 解析失败的项只含 `run_id`、`unreadable`（值为 `true`，只在解析失败时出现）与 `cli_version`，其余键省略；该键随实装进契约页。清单不带 `artifacts`，除写出版本外不带 definition 里的信息（worker variant、job 定义），也不带 `high_water_mark`（推进器内部的并发写守卫，[0034](./0034-detached-batch-reconciler.md) 机制三）：清单只回答「有哪些 run、各到哪一步」，细节对选中的 run_id 用 `status` 与 `explain` 取。
- **写出版本的标记**：清单不过 definition 的结构版本闸（[0037](./0037-distribution-and-packaging.md) 决策 7 的闸只在 `status` / `explain` 读某个 run 时生效）：它读的是 RunState 里跨版本稳定的几项（状态、起止时刻、job 状态），按宽容规则读，整条命令不因个别旧 run 失效。但每个 run 读其提交记录的头部（`RunStore` 既有的头部读取，不取整份 definition），拿到写出它的 CLI 版本。人读表格的「版本」列恒显示这个版本串，读不到头或头里没有版本的显示「未知」；写出版本与本 CLI 版本都已知且相同的 run（当前版本写出）在版本串后加 ` *`，表格上方一行图例「当前 gherkai 版本 X（版本列以 * 标出）」给出比对对象并说明记号，写法与 `deploy list-workers` 标默认 variant 相同。本 CLI 版本取不到（未装成包）时没有比对对象：不打图例，没有哪一行带星，版本列照常显示各自的写出版本。机读形态每项恒带 `cli_version`：写出它的版本串，读不到时为 `null`，运行态解析失败的项同样带；顶层另带 `cli_version`，是执行这次清单的版本，取不到为 `null`。是不是当前版本写出，由读者比较两者，每项不另设布尔键：每项的字段描述 run 本身，而「是否当前版本写出」取决于由哪个版本的 CLI 来列，同一个 run 换一个版本列出就会翻转，放进每项会让同一个 run 的记录随执行者变化；比对对象已在顶层，读者一次比较即得。「读不到」只指头部不存在、没有版本字段或内容无法解析；权限、凭证、网络一类访问失败不吞成「未知」，按读不到这个后端以退出码 2 结束。每格都给出事实，读者不必记住「空白代表什么」；当前版本只多一个星号、含义由图例说明，清单不会被同一句话占满。对版本后不带星的 run 用 `status` / `explain` 时仍走版本闸。代价是每个列出的 run 多一次提交记录头部的读取，读量随清单条数：本机多读一次该 run 的 `run_meta.json`（现行的头部读取解析整份文件、只取两个值）；云端把该 run 的 META 键并进同一批 `BatchGetItem`、不另起请求，但读量按 item 计，META 与 STATE 各算一次（投影只减少传回的数据、不减少读量），每批请求能装下的 run 数也随之减半。清单规模让这次读取的成本可感时，可把写出版本冗余进 STATE（见文末重议闸门）。
  - **本机与云端的不对称**：状态值本版本不认识的 run（由更新的版本写出）：本机逐目录读，能看到它并标「无法读取」；云端按分组查（见下「云端实现」），非终态 run 都在同一个 `live` 分组里被找到，本版本不认识的非终态状态值只要写出它的版本沿用同一分组规则，云端也能找到并标「无法读取」，本版本不认识的终态值不在任何被查分组里，云端看不到。状态值认识、但 STATE 其余部分解析失败的 run（如某个 job 状态值本版本不认识），两侧都标「无法读取」。无法读取的行没有可用的状态，不参与状态过滤与终态截取、不占「最近 N 条」的名额，找到即列出（跳过它会让人以为它不存在，同下被拒项）。名额规则两端相同：云端在终态分组里补读到凑满 N 条可读的 run（见下「云端实现」），所以在索引已收敛、且读取期间相关 run 的状态不变时，同一条命令在两个后端列出的可读 run 相同。不满足时可能不同，例：`--status passed --limit 1`，passed 分组里排第一的索引项所属的 run 已被改写为 failed、索引尚未跟上，云端读回它是一条可读的 run，计入 passed 的名额后停止，CLI 再按所请求的状态把它筛掉，清单为空；本机按读回的状态把它归入 failed，列出下一条 passed。剩下的差别在找得到哪些无法读取的行：本机逐目录读，全部列出；云端只列被查分组里凑满名额之前遇到的，排在该状态第 N 条可读 run 之后的不读、不列（默认清单的非终态部分不限条数，`live` 分组读完）。机读契约页写明这一点：本版本不认识的状态值的 run 以无法读取的项出现（`unreadable` 为 `true`），云端只对非终态的值如此，前提是写出它的版本沿用同一分组规则。
  - 被拒：只在写出版本与本 CLI 版本不同时显示、当前版本写出的留空（机读省略 `cli_version`）——空白既可读作「当前版本写出」也可读作「没有信息」，读者要先记住这条规则才看得懂，机读侧也要把「键缺失」解释成一个版本判断，写出版本这一事实被省略、要靠隐含规则还原；整条命令在遇到旧 run 时以退出码 2 结束（升级后这条命令就没法用了）；跳过旧 run（让人以为它不存在）；每行写一句「由其它版本写出」（重复、占满界面）。
- **退出码**：0 表示读到了清单，空清单与含「无法读取」行的清单也是 0；2 表示参数不合法（`--limit` 不是正整数、`--status` 不是 run 级状态值）或读不到这个后端：本机是报告落点存在但不可读（权限）；云端是 region 或凭证解析失败、表不存在或无权限、索引缺失或未就绪（判据见下「云端实现」）、`BatchGetItem` 未处理的键重试耗尽、版本 skew 闸拒绝。退出码不表判定，判定对具体的 run 用 `status --wait` 取。
- **本机实现**：本机后端没有跨 run 的状态文件，每个 run 的运行态只在它自己的目录 `<report_dir>/<run_id>/run_state.json`（与 `run_meta.json`、`events.db`、判定明细同目录）。列举的做法是列出报告落点下的子目录（目录名即 run_id），逐个读 `run_state.json`，没有该文件的目录跳过（不是 run 目录，或在写下运行态之前就中断的执行；`--no-report` 的执行不建 run 目录，见下「范围边界」）。报告落点目录不存在时按空清单处理（退出码 0），提示行说明目录不存在：本机后端的报告落点在第一次落盘时才建立，目录不存在可能是这里还没有落盘的 run，也可能是路径给错，命令无从区分，所以不报错，只把这一事实连同解析后的目录交使用者核对；目录存在但下面没有 run 时，提示行说目录下没有 run。读量随该落点的历史增长：默认清单是两次端口调用（见下「CLI 的合并」），本机 adapter 每次调用都把该落点下全部 `run_state.json` 读一遍，所以默认清单读的是 run 数的两倍，`--status` 只含一侧的状态时只做一次调用、读一倍；每个都是小文件。`run_meta.json` 只对每次调用入选的 run 读（见上「写出版本的标记」）：非终态那次是全部非终态 run，终态那次是每个终态状态至多 N 条可读的 run（CLI 合并后再截到 N 条），无法读取的行两次都入选。不改成只读一遍：那要么让端口在两次调用之间保留读回结果（端口变成有状态的，后一次调用返回的也不再是调用时的当前 STATE），要么让 CLI 对本机后端另走一次调用（默认清单的口径分成两套）。**不建全局索引文件**：目录名自带时间序，而索引文件会成为 run 状态的第二真值。同一个 run 的状态由三个宿主写（前台 `run`、per-run 推进进程、`status --wait` 接力者，[0034](./0034-detached-batch-reconciler.md)），索引要随每一处写入同步更新，任一宿主中途退出就会漂移，还要另配一套跨进程锁；直接读 `run_state.json`，清单与 `status` 读到的永远一致。
- **云端实现**：读 runs 表的状态分组 GSI `status_group-run_id-index`（runs 表唯一的索引；分区键 `status_group`、排序键 `run_id`、投影 INCLUDE `worker_task_def_arns`，与 worker revision 清理共用；只有 STATE item 带 `status_group`，run 级状态非终态时为 `live`、终态时为该终态值；schema、写入规则与取舍登记在 [0030](./0030-realtime-persistence-seam.md) 决定六）。索引名的真源是 `runtime/gherkai_runtime/names.py`，由 compose 注入云端 adapter，core 不依赖 runtime。adapter 把所请求的状态映射到分组（`ScanIndexForward=False`，即 run_id 降序）：所请求的非终态状态一律映射到 `live` 分组，只查一次、最先查（依据同下「CLI 的合并」的调用次序）；所请求的终态状态各映射到同名的分组，按请求里的顺序逐个查。`limit` 为 None 时各分组分页读完，键收齐后一并读回。`limit` 给出时每个终态分组读到凑满 N 条可读的 run 或该分组读完为止：每次按还差的条数取键（`Limit` 为 N 减去该状态已凑到的可读条数），读回、解析，名额未满且还有下一页时再取下一页；其间遇到的无法读取的行照常列出、不占名额，读回时 STATE 已不在的行同样不占（它不是可读的 run）。前面分组已读回过的 run 不再读回，它在后面状态里占不占名额按已读回的结果定。`live` 分组里读回状态是未被请求的非终态状态的行不列出（它不是经所请求的状态找到的）；读回已到终态的行与无法读取的行照旧列出、不复筛；同一个 run 也经所请求的终态分组找到时（索引传播期间可能同时在两个分组里），按经终态分组找到照常列出。`limit` 给出而请求里含非终态状态时，按所请求的各非终态状态分别计可读名额：读回状态为某个所请求非终态的可读行计入该状态的名额，该状态凑满之后的同状态行不列出（与本机每个状态取前 N 条一致），读回已到终态的行列出、不计入任何非终态的名额；每页取的键数是各状态还差的条数之和，各状态都凑满或分组读完即停（CLI 对非终态恒传 None，这几条只在一次调用同时含非终态与 `limit` 时起作用，见下「CLI 的合并」）。两种情形都是索引返回的键先按 run_id 去重（同一请求里出现重复的键，`BatchGetItem` 整个请求以 `ValidationException` 失败），再用 `BatchGetItem`（`ConsistentRead=True`，每次请求至多 100 个键，每个 run 取 STATE 与 META 两个键）读回；返回的 `UnprocessedKeys` 带退避重试、次数有界，耗尽时以退出码 2 结束，不给出缺行的清单。索引里有键、读回的 STATE 为空的行跳过（item 已不在，索引尚未跟上）。STATE item 到 RunState 的转换与 `load_run_state` 共用一处，不另写解析，解析点保持单一。
  - **一致性边界**：行内容强一致（读回走 `ConsistentRead`），成员资格最终一致（GSI 只有最终一致读）。正常生命周期里（以 `pending` 建 run、只收尾一次）成员资格只在建 run 与收尾两处变化：`pending` 到 `running` 的换值不改变分组；刚建的 run 可能短暂不在任何分组，刚收尾的 run 在传播完成前可能短暂仍在 `live` 分组、或短暂不在任何分组。正常生命周期之外还有两处：终态被改写（`finalize_run` 的条件只要求 STATE 存在，会覆盖已有终态）让 run 在两个终态分组之间移动，`save_run` 整体覆盖已有的 STATE 按新旧分组移动。所以状态、起止时刻与 job 计数一律以读回的 STATE 为准，索引只用来找 run_id，这守住 [0034](./0034-detached-batch-reconciler.md) 的单一读接口不变量（外部只从 RunState 读状态）；两次端口调用之间换分组的窗口由 CLI 的合并规则收窄，对清单的影响见下「CLI 的合并」。
  - **读量**：终态部分有界：每个被查的终态状态取的键数至多为 N 加上凑满之前遇到的无法读取的行数（含读回时 STATE 已不在的行），分组读完即止，读回的 run 数同此上界。非终态部分随在途与遗留的 run 数（见上「列哪些 run」）。两部分都不随可读的终态历史增长。上界多出的那一项可以接受：无法读取的行只在版本混用（更新的版本写出了本版本不认识的 job 状态值等，CLI 旧于后端时版本 skew 闸只警告不拦，[0037](./0037-distribution-and-packaging.md) 决策 7）或记录损坏时出现，常态下每个终态状态仍是至多 N 个键、一页即满；换来的是两端同一名额规则（两端列出的可读 run 相同的前提见上「本机与云端的不对称」）。按页补读时每页各自读回，`BatchGetItem` 的请求数随页数增加，读量（按 item 计）不随之增加。
  - **守 [0038](./0038-worker-image-delivery.md) 的红线**：runs 表 `RETAIN`、无 TTL、随历史单调增长，不许 Scan。
  - **代价**：索引写只发生在两处——建 run 时一次（写进 `live` 分组），收尾时两次（从 `live` 换到终态分组，删旧项、写新项）。run 级从 `pending` 换到 `running`（同一次写带同值的 `status_group`，0030 决定六的写入规则）与只改 job 级状态的写都不改索引键、也不改投影属性（投影只有键与 `worker_task_def_arns`，后者只在建 run 时写一次），不产生索引写（DynamoDB 官方的 GSI 写入规则明确按实际改变的属性判定索引写，同值写按此不写索引；0034 机制三实测项 6 在原先以 `status` 为键的索引上测得只改 jobs 的写与同值写对索引为 0，新索引上的核对见 [0038](./0038-worker-image-delivery.md) 实测项 8）。正常生命周期下（以 `pending` 建 run、只收尾一次）一个 run 计 3 个索引写单位；正常生命周期之外，终态被改写（`finalize_run` 的条件只要求 STATE 存在，会覆盖已有终态）另付 2，`save_run` 整体覆盖已有的 STATE 按新旧分组另付，直接以终态建的 run 只计建 run 那一次、不经过 `live` 分组，与 0030 决定六「运行成本前后对照」同一口径。原先表上两个以 `status` 为键的索引对经过 `running` 的 run 共计 10、对未经过的计 6。读量（与原先按 `status` 分区的 KEYS_ONLY 索引相比）：非终态部分由两次分区 `Query` 合成一次；每个索引项多带 revision 列表（一两个 ARN），终态部分每个被查状态的一页（至多 N 项）约由 0.5 个读单位升到 1 个，N 为 20、五个终态时索引侧多出约 2.5 个读单位；读回不变：终态部分读回的 run 数在 N 到 5N 之间（历史足够多时；`--status` 只含一个终态时至多 N，默认清单查五个终态、每个至多 N，CLI 合并之后再截到 N 条；不计凑满之前遇到的无法读取的行），每个 run 强一致读 STATE 与 META 两个 item、每个至少 1 个读单位，N 为 20 时约 40 到 200 个读单位，非终态部分另计；清单读量仍以读回为主。以上读量按项大小估算，没有实测，`ConsumedCapacity` 随新索引上的实测记录（本条末「实测项」）。
  - **更早的索引形态**：状态分组索引这一形态确定时产品还没有使用者，不提供从更早形态迁移的路径，用户文档也不写这类升级的操作说明。从更早形态升级要给已有的表加索引，需承担 `AWS::DynamoDB::Table` 文档写明的限制：新索引回填、`ACTIVE` 之前这张表不能再被更新；建索引期间 stack 更新失败回滚时，已发起的索引不随回滚删除；文档建议加索引的那次更新不改其它资源，而 `gherkai deploy` 是整个 stack 一次更新。
  - **索引就绪判据**：取自该表的 `DescribeTable` 结果（所需权限已在 preflight 只读探活里），不解析 `Query` 的报错文本。索引缺失、`IndexStatus` 为 `CREATING`（建立中）或 `DELETING` 时拦下，以退出码 2 结束；`ACTIVE` 放行；`UPDATING` 也放行，取舍是：文档只说索引正在更新、没写明期间能否读，拦下它会让一次与本命令无关的索引设置变更挡住清单，放行的风险是这期间 `Query` 若失败，该失败照样按读不到这个后端以退出码 2 结束，只是说明不如就绪判据具体；`UPDATING` 期间的查询有一次有限的实测，没有见到失败，为维持放行提供有限支持（见本条末「实测项」）。检查放在 compose 装配云端 RunStore 的路径上，只在 `list-runs` 调用时执行，不并入 `run` / `submit` 共用的资源 preflight：那些命令不用这个索引，不能因它缺失或尚未建立完成而被拦。`doctor` 也不加这一项：建立中是暂时的，`list-runs` 自己会说明；1.5 之前的部署没有使用者，不存在要靠 `doctor` 发现的旧部署。检查对象是 `status_group-run_id-index`，表上其它索引的状态不影响判定；worker revision 清理对同一索引另做一次就绪检查、只放行 `ACTIVE`，比这里严，理由见 [0038](./0038-worker-image-delivery.md)「不变量」清理 pass 条，不是两处不一致。
- **core 端口**：`RunStore` 加一个列举方法（形如 `list_runs(statuses, *, limit) -> list[RunListing]`），本机与云端两个 adapter 各自实现。语义：返回经这些状态找到的 run 的**当前** STATE（云端经状态所在的分组找），按 run_id 降序，**不按状态复筛**（读回的状态可能已不在 `statuses` 里）；`limit` 给出时每个状态取按 run_id 降序的前 `limit` 条可读的 run，其间遇到的无法读取的行照常列出、不占名额（云端按页补读，见上「云端实现」），为 None 时分页读完。本机 adapter 没有分组，逐目录读回后按读回的状态归入各状态，名额规则相同。每个列举项的 `run_id` 恒有（本机取自目录名、云端取自索引返回的主键，不依赖 RunState 能否解析，供 CLI 排序与去重），另带三样：读回的 RunState（解析失败时为空并标为无法读取）、detached 标记、提交记录头部（与 `peek_definition_header` 同一对值，读不到为空）。detached 标记仍是执行环境属性、不进 RunState 模型（0034「filter 必须区分写入者」条），这里作为列举项的字段出现在端口返回值上，是它第一次进入 RunStore 端口面：人读提示要它，而它与运行态在同一处、读回即有；改由 CLI 对每个非终态行调 adapter 的 `is_detached`，每行多一次读，CLI 还要绕过端口直接认 adapter。端口不认后端、不认引擎，也不承载默认清单的口径。云端的非终态状态共用 `live` 分组，非终态行是否「经所请求的状态找到」按读回的状态判定，与本机按读回的状态归入各状态一致；读回已到终态的行仍不复筛（见上「云端实现」末段）。这是「不按状态复筛」的一处例外：非终态部分按读回的状态判定是否列出，读回状态是未被请求的非终态的行不列出；`RunStore.list_runs` 的端口说明写明这一例外，两个 adapter 的对拍覆盖只请求 `pending`、只请求 `running`、两者都请求，带与不带 `limit` 的情形。
  - **CLI 的合并**：默认清单的口径只在 CLI。两次调用，先非终态（`limit=None`，端口内只查 `live` 一个分组）、后终态（`limit=N`）。先查非终态的依据是正常生命周期里 run 只从 `live` 分组走向终态分组，由两条终态写在写终态的同一次写里改分组保证（[0030](./0030-realtime-persistence-seam.md) 决定六），先查 `live` 才不会漏掉两次调用之间收尾的 run；终态被改写（`finalize_run` 覆盖已有终态）时 run 在两个终态分组之间移动，`save_run` 整体覆盖与直接以终态建 run 也不在这条依据之内。合并时按所请求状态的并集过滤读回的状态，按 run_id 去重（两份都有时保留后一次读回的那份：运行态只向终态推进，后读的不会更旧），截取终态部分按 run_id 降序的前 N 条（只截可读的终态行；无法读取的行没有状态，全部保留），最后整体按 run_id 降序。端口对每个终态状态给出前 N 条可读的 run；在索引已收敛、且读取期间相关 run 的状态不变时，全部终态里最新的 N 条可读 run 必在其并集之内，所以截取后的终态部分不被无法读取的行挤占。前提不成立时这一点不保证。只查部分终态时（如 `--status passed`），所查分组里某个索引项所属的 run 已被改写为未被请求的终态、索引尚未跟上，它占了名额又被 CLI 按读回的状态筛掉，所查终态的可读 run 少列一条（例见上「本机与云端的不对称」）；被改写为所查终态、索引项仍在别的分组的 run 这次找不到。查全部终态时，过时的索引项所属的 run 仍是终态，找到它的那一份仍在并集之内；仍会漏列它的是下面所说的两种成员资格边界。这一顺序加上端口不复筛，收窄了「两次调用之间收尾、或 GSI 尚未传播，导致 run 在两份结果里都不出现」的窗口：run 在第一次调用时仍在 `live` 分组（含已收尾而索引还没跟上的），就被第一次调用找到，读回的终态状态在并集内而保留；否则它在第二次调用时已在终态分组。顺序反过来时，它可能先不在终态分组、后已离开 `live` 分组。`--status` 只含一侧的状态时只做那一次调用。`pending` 与 `running` 只由强一致读回的状态区分：`--status` 只含其中之一时同样查整个 `live` 分组，按读回的状态筛，成员资格不再决定一个非终态 run 算哪个状态。剩余边界有两种，原先以 `status` 为键的形态同样都有。其一，传播期间两个分组都读不到：删旧项与写新项哪个先可见没有承诺，收尾时的换分组与终态被改写时的换分组都可能留下这样的间隙，两次查询都落在其中时这个 run 缺席；`pending` 到 `running` 那一处不再有。其二，读取期间从尚未查询的分组移到已经查询的分组：run 始终在某个分组里、没有间隙，仍整次没被查到。例：最新的 run 原为 `error`，终态分组中 `passed` 先于 `error` 查询，CLI 查完 `live` 与 `passed` 之后，它被 `finalize_run` 覆写为 `passed`、索引随即完成移动，随后查询 `error` 时它已不在。正常生命周期里的移动只有 `live` 到终态分组一个方向，`live` 先查，这一种不会发生；它只来自终态被改写与 `save_run` 整体覆盖。两种都只是这一次清单的缺席，之后的查询可见。
- **权限**：云端编排进程与 detached `submit` / `status` 的机器要用本命令，另需 runs 表索引 ARN `table/{prefix}runs/index/status_group-run_id-index` 上的 `dynamodb:Query`（表 ARN 上的 `Query` 授权覆盖不到 GSI）与表 ARN 上的 `dynamodb:BatchGetItem`（读回 STATE 与 META item）；清单登记在 [0033](./0033-iac-aws-backend-and-composition-wiring.md)「编排进程角色」段。
- **范围边界**：只列 run，不列 ECS task、Device Farm 远程访问会话与隧道：那是运维视角的执行资源，不进本命令面（未结束的远程访问会话由 `doctor` 的设备支持项只读列出，决策四）。不落 run 记录的执行同样不在清单里：本机 `run --no-report`，以及云端 `run --backend cloud --no-report`（不写 STATE item，与 [0038](./0038-worker-image-delivery.md) 记下的已知盲区同源）。
- **被拒方案**：
  - `status` 不带 run_id 时列出 run：同一个命令按有没有位置参数切换成两种语义（看一个 run 与列出很多 run），退出码与 `--json` 形状都要分叉，从帮助里也难分辨。
  - Scan runs 表：违背 [0038](./0038-worker-image-delivery.md) 的红线，读量随历史无上界。
  - 列产物桶报告前缀下的 run 目录、从报告取终态：报告是派生视图（[0027](./0027-runreport-aggregation-index.md)），只有写出了报告的 run 可见（在途的 run、`--no-report` 的 run、报告聚合失败的 run 都看不到），且清单与 `status` 读的 runs 表成了两个来源，两者可能不一致。
  - 复用只有分区键 `status` 的 `status-index`（原供清理读、已从部署模板删除）、不加排序键：按状态读出的是整个状态分区，取不到有界的「最近 N 条」，终态分区随历史增长、读量无上界；给它加排序键要替换索引（DynamoDB 不能修改已有 GSI 的键）。
  - 为本命令另建以 `status` 为分区键、`run_id` 为排序键、投影 KEYS_ONLY 的列举索引（本命令最初的形态 `status-run_id-index`），与清理各用一个索引：`pending` 到 `running` 的换值在以 `status` 为键的索引上计两次写、可能留下两个分区都查不到的间隙，表上两个索引又让每个 run 的每次换值在两处各付一次索引写；状态分组索引带 `run_id` 排序键，取得到有界的「最近 N 条」，清理要的 revision 列表由每个索引项多带承担（读量见上「代价」）。对照与其余被拒方案见 0030 决定六「为何按状态分组、不按状态」「为何一个索引」两条。
  - 新索引投影状态、起止时刻与 `jobs`（`INCLUDE` 或 `ALL`），直接从索引出清单、省掉读回：索引的读只有最终一致，清单会与紧接着的 `status` 读到的状态不同；`jobs` Map 随 job 数增长，投影它等于每个 run 存第二份，且每次刷 job 状态都多一次索引写。状态分组索引投影的 revision 列表不在此列：它只在建 run 时写一次、不随 job 状态变化，供清理而不供清单。
  - 本机建索引文件：第二真值，见上「不建全局索引文件」。
  - 端口按读回的状态复筛：两次调用之间换状态、或索引尚未传播的 run 会在两份结果里都被筛掉，清单里凭空少一条，见上「CLI 的合并」。
  - 云端保留「每个被查的状态至多读 N 个键」的上界，接受两端不一致（无法读取的行在云端占名额、在本机不占）：同一条命令在两个后端列出的可读 run 不同，云端每遇到一条无法读取的行，该状态就少列一条较旧的可读 run，CLI 的合并只截可读行，补不回被占掉的名额；无法读取的行成批出现正是在版本混用时，这时少列的最多，而使用者从清单上看不出缺了哪些。保住的只是读量上界里不含无法读取的行，这部分读量本来只在版本混用或记录损坏时出现。
- **实测项**：
  - 本机（已核）：同一报告落点下先后执行两次前台 `run`，`list-runs` 列出两条、新者在前，人读表格与 `--json` 一致，两条都识别为当前版本写出。在有凭证的机器上两次 run 都真实执行到 `passed`，清单的状态、起止时刻与 job 计数与各 run 的判定一致；`--limit 1` 只留较新的一条，`--status` 筛到没有结果时给出点名该状态的空清单说法。同时核了两类非终态 run 与两种空清单：`submit` 的 run 结束前以非终态列在最前、`detached` 为 true、不带遗留提示，`status --wait` 收尾后进入终态部分；前台 `run` 在写下运行态后被 SIGKILL，留下的 run 列为非终态、`detached` 为 false，人读行带遗留提示；报告落点目录不存在与目录下没有 run 两种空清单各给出对应说法，退出码都是 0。
  - 云端，当时所读的 `status-run_id-index`（已核，该索引已从部署模板删除）：在已有 run 数据的后端上升级部署（runs 表约两百个 item）。部署前索引不存在，`list-runs` 以退出码 2 结束并说明；CloudFormation 报更新完成时索引仍为 `CREATING`（建立中），之后又过了十余分钟才转为 `ACTIVE`，这段时间 `list-runs` 一直以退出码 2 结束并说明须等索引就绪——「部署结束不等于索引就绪」成立；约两百个 item 的小数据量也不能保证索引立即就绪，所以提示里不对等待时长作承诺。索引就绪后，升级之前写下的 run 出现在清单里，由其它版本写出的各行在版本列带各自的版本串；`--json` 顶层给出后端、前缀、region 与解析后的表名。随后 `submit` 一个执行时间较长的 run：执行中它列在非终态部分（`detached` 为 true、不带遗留提示），结束后进入终态部分并排在最前，识别为当前版本写出、与升级之前写下的各行可区分。执行中有一次读到 run 级状态仍是 `pending` 而它的 job 已是 `running`：当时 run 级只由推进器的下一次投影推进，清单如实显示读回的运行态。这一观察促成 0034 机制三「run 级状态只进不退」条（认领与 run 级同一次写、投影不把 run 级写回 `pending`、前台 job 离开 pending 时连带推进 run 级），真实环境的复核列在该条实测项。
  - **待核**：在部署出状态分组索引的后端上核清单：`live` 分组列出全部非终态 run，各终态分组按 `--limit` 截取，各行的状态与逐个 `status` 读到的一致；以 `ReturnConsumedCapacity` 记录默认清单在索引侧与读回侧的读量，对照上「代价」段的估算。
  - 当时所读的 `status-run_id-index`（已从部署模板删除）处于 `UPDATING` 期间的查询（有限实测，放行维持）：在一张与当时 runs 表的键结构及两个索引定义相同、按需计费的临时表上，六次调整这个索引的按需读吞吐上限；每次采样到索引为 `UPDATING` 后立即经 `list-runs` 所用的装配路径（先过索引就绪检查、再查索引并读回）列举全部状态，均成功返回 30 条 run，与索引 `ACTIVE` 时的数量相同。没有逐次确认装配内的就绪检查与各次 `Query` 发生时索引仍为 `UPDATING`；结果只覆盖这一种设置变更，没有覆盖其它进入 `UPDATING` 的原因，也不是在部署出来的表上做的。查询若在这期间失败，按上面「索引就绪判据」所述以退出码 2 结束。

## 重议闸门

- 失败证据的机读化（`explain` 子命令）：已由 [0042](./0042-step-evidence-and-explain.md) 落地——worker 在 step 边界产 gherkai 自有 schema 的 evidence、`explain` 合成判定树与证据；不是「引用 trajectory `.json`、格式由 skill 说明」那条路（被拒理由见该 ADR）。
- JSON Schema 生成：见决策五被拒项。
- 遗留的非终态 run（决策七「非终态不截断」条）：前台执行被强制结束留下的非终态 run 成为清单的常态内容（使用者反馈清单被它们占据，或它们的数量与在途 run 相当）时，再议一类把 run 标记为已放弃的手段；在那之前只在人读行提示。
- job 没通过的原因类别进运行态（决策七「人读形态」条）：使用者要在清单里一眼看到 run 为什么没通过、而逐个 `explain` 成为负担时，再议把 job 的原因类别投影进 JobState（与状态同一次投影、判定明细仍是权威），清单的提示列与 `status` 的摘要随之给出类别；多 job 的 run 如何聚合成一格届时一并定。
- 写出版本冗余进 STATE（决策七「写出版本的标记」条）：清单规模让每个 run 多一次提交记录头部读取的成本可感时，把写出它的 CLI 版本冗余进 STATE item 与 `run_state.json`，读回运行态即得、不再读 META 或 `run_meta.json`。
